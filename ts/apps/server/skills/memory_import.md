导入别家 AI 的记忆：把来源条目逐条判断成偏好 / 事实 / 经历，按内容决定写 global 还是项目，判不了就跳过。

只在用户明确让你「导入记忆 / 把别家 AI 的记忆接进来」时用这份手册。目标不是搬文件，是替用户判断：这条值不值得进记忆库、属于哪一类、放哪儿。

1. 先看来源
- 来源注册表和路径在 `ts/apps/server/src/memory-import-sources.ts`；也可以调 `GET /api/v1/agent/memory/import/sources` 看哪些 count > 0。
- 只处理用户点名或勾选的来源。count = 0 的直接跳过，不要替它编内容。
- 能调 `collectSourceEntries(sourceId)` 就直接用；不能就按注册表里的路径读源文件。不要整份文件直接 remember。

2. 逐条判断（一次看一条）
- 偏好：关于用户这个人的稳定口味、习惯、规矩。例：喜欢/不喜欢什么、称呼、沟通方式、配色、不要紫色、以后都这样。`USER.md` / feedback / preference 文件优先按偏好看。
- 事实：客观、可验证、项目怎么运作。例：路径、接口、配置、构建/部署方式、代码约束、项目规则。技术文本里出现「风格一致」「规范」不等于用户偏好。
- 经历：发生过的一件事，有时间、人物、动作、结果。例：任务描述 + 执行过程、mermaid、完成情况、某日修复/上线/踩坑。
- 判不了：不要默认塞成事实。跳过，记一句原因；宁缺毋滥。

3. 决定写到哪
- 只跟这个人有关、跨项目都成立 → global。
- 明确属于某个已登记项目（项目路径、项目名、只在该项目成立的规则）→ project；写之前确认项目已登记。
- 拿不准 → global，正文里保留项目名；不要新建一个不存在的 scope。

4. 写之前先去重
- 先用 recall 或搜索查同一句话是否已存在；已有的跳过。
- 一条只写一件事；不要把无关的几条合并成一条，也不要为了凑数拆开。
- 用 `remember` 工具写，带 `kind`；项目条目 `scope=project`。不要直接写 SQLite。

5. 批次与汇报
- 条目多就按 20–30 条一批处理，不要一次全塞进上下文。
- 最后只报：新增 X、重复跳过 Y、判不了 Z。判不了的列一句原因。
- 不要改已有记忆的正文或 scope；这一步只新增。
