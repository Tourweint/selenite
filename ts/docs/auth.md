# 鉴权

> 这份文档是 2026-10-28 从 Java 版归档（`docs/基线文档/系统架构.md` D2/D6、
> `接口文档.md` §0）里捞回来的设计，并按"通用个人 Agent"的新定位重新表述。
> 原实现的代码已删除，设计本身仍然有效。

## 一句话

**校验在 harness 本地，后端只负责签发和管额度。** 不是"每个请求都去问后端这个 token 有没有效"。

## 原来的三段式（App → Agent → 后端）

```
App
 │  Authorization: Bearer <JWT>   ← backend 签发，HS256
 ▼
harness（本仓库）
 │  ① 用同一把 JWT_SECRET 本地验签 → 拿到 subject = userId
 │  ② 需要配置/额度时，用 X-Internal-Token 走内网问 backend
 ▼
backend
   · GET /api/v1/internal/ai-config?since=<version>   非秘密的策略参数
   · 扣额接口（先扣再转发，幂等）
```

为什么是"同密钥本地验签"而不是"回调 backend 校验"：

- 每个对话请求都多一跳内网往返，延迟和故障面都变大；
- backend 挂掉时 harness 应该还能用（只要不涉及扣额）；
- JWT 是自包含的，签名一致就能验，没有必须问后端的理由。

**所以严格说：App 找 Agent，Agent 自己验，只有"要用户配置 / 要扣钱"时才找后端。**

## 原来的约束（逐条抄录，仍有参考价值）

| 约束 | 内容 |
|---|---|
| 密钥同源 | harness 与 backend 用**同一把** `JWT_SECRET`；换密钥必须同时换 |
| fail-closed | `JWT_SECRET` 未配置或短于 32 字节 → 一切请求 403 |
| 拒绝形态 | 缺 / 无效 / 过期 → **HTTP 403 空响应体**（和 backend 的 Spring Security 一样，App 不用区分两端） |
| 内部接口 | `X-Internal-Token` 与 backend 同值，只走内网；连接 200ms / 读 1s |
| 配置拉取 | `ai-config` 60s 缓存 + version 增量；失败沿用上次成功值，从不成功则用内置默认 |
| 频控分工 | 有额度的端点靠"鉴权 + 扣额"挡刷量；无额度的端点（如信号评估）才按 IP 限流 |

这套东西的服务对象是**多用户 SaaS**：要区分"是谁"、要管"有没有钱"。

## 现在该怎么做

新定位是**一个人的通用 Agent**：单用户、跑在自己机器上。鉴权的目标变了 ——
不再是"区分用户"，而是"**挡住局域网/公网上的陌生人**"。

分两档，按需要往上走：

### 第一档：单用户静态令牌（现在够用）

```
App  ──Bearer <自己设的 AGENT_TOKEN>──▶  harness ──▶ 模型
```

- `AGENT_TOKEN` 走环境变量，App 里配一次；调试页用 `http://127.0.0.1:8082/?token=xxx` 打开；
- 校验失败 → **403 空响应体**（口径和上面保持一致，将来换 JWT 时 App 不用改错误处理）；
- 比较用 `timingSafeEqual`，不把令牌长度泄露给计时攻击；
- **没配 `AGENT_TOKEN` 时不裸奔**：只放行本机回环地址（`127.0.0.1` / `::1`），
  其他来源一律 403。这样开发时不用配令牌，但也不会被局域网里的人直接用。

已实现（`apps/server/src/auth.ts`），只挂在 `/api/v1/*` 上；`/`（调试页静态 UI）
和 `/healthz` 不拦。

### 第二档：不做（2026-10-28 定）

原设计的 JWT 同源 + 扣额联动，服务的对象是**多用户 SaaS**。

本项目明确是**单用户自用**：一台机器、一个人、一份数据。**用户隔离不做。**

如果哪天真要做成多人共用的服务，那是**另一套系统** —— 要有账号、计费、数据隔离、
审计。在现在这套上打补丁会两头不讨好：单用户场景被多出来的复杂度拖累，
多用户场景又缺基础设施。

原设计的约束（同密钥、403 空体、`X-Internal-Token` 内部接口）留在这里备查就够了。
第一档已经把「403 空体」的口径固定下来，将来真有需要也接得上。

## 什么时候必须做

| 场景 | 做法 |
|---|---|
| 只在 `127.0.0.1` 自用 | 已默认保护（本机回环自动放行，其他 403） |
| 手机在同一个 Wi-Fi 里连电脑 | **第一档，必须**（不配令牌，手机连不上） |
| 接 Telegram / IM 网关 | 第一档 + 网关侧自己的鉴权 |
| 部署到 VPS 单人用 | 第一档，令牌换成长随机串 |
| 多用户共用 | **不做** —— 那是另一套系统 |

## 会话归属：拆成两层，做了第一层

会话按 `conversationId` 落盘（`.data/sessions/*.jsonl`）。如果 id 由客户端自己编，
那"有令牌 + 猜得到 id"就能读别人的历史。所以分两层处理：

### 第一层：不可猜（✅ 已做）

- **不带 `conversationId` = 新建会话**，服务端生成 UUID，通过 SSE 的 `start` 事件下发；
- 带了 id 就必须是服务端发过的，否则 **404 `unknown_conversation`**；
- 客户端之后一直带着这个 id 续话。

这样 id 是随机的、不可推测，持有令牌也拿不到别人的 id。

### 第二层：不做

「会话元数据记 ownerId、请求时校验归属」这一层的前提是**存在多个身份**。

单用户场景下没有第二个身份，校验 `owner === "self"` 永远成立，写了也是死代码。
所以不做 —— 不是没做完，是不需要。

真要变成多人服务时，这层必须补，同时补的还有账号、计费、数据隔离，一起做才有意义。

## 延伸：如果要做成 SaaS

这一节写的是**为什么不是"加个用户表"那么简单**，以及将来真要动手时的形态。现在不实施。

### 隔离单位是环境，不是用户数据

判断依据很直接：**这个 Agent 手里有什么权限**。看工具集 ——
`read_file` / `write_file` / `run_command` / `list_dir`，它能执行 shell、能写文件。

一旦有这个能力，**数据隔离就失效了**：共享进程里按 userId 过滤，只能挡住"查错表"，
挡不住 `ps aux` 看别人进程、`kill` 影响宿主、写满磁盘、抢占 CPU。

| 隔离粒度 | 能挡住 | 挡不住 |
|---|---|---|
| 数据隔离（同进程 + userId 过滤） | 查错表 | 命令执行、文件写入、端口、资源竞争 |
| 容器 | 文件、进程 | 内核漏洞、资源争抢 |
| **整机 / VM** | 以上全部 | — |

还有一条更朴素的理由：**Agent 是常驻的**。它有会话文件、记忆库、模型上下文、定时任务，
不是"一个请求一个响应"的微服务，更像一台你养着的机器。一台机器塞 100 个"用户"，
只会让每个人都难用。

### 「登录」其实是三件事

把登录当成一个东西，才会觉得"它应该在 App 里"。

| 层 | 回答什么 | 该在哪 |
|---|---|---|
| **平台账号** | 你是谁、付了多少钱、有几台机器 | 平台系统（另一个产品） |
| **实例凭证** | 你能连哪一台 Agent | 那台 Agent 自己 —— 就是本文件的 `AGENT_TOKEN` |
| **App 配对** | 我这台手机连哪台机器 | App 里，且**只需要这一层** |

App 里不该有注册、密码、验证码、订阅、配额 —— 那是第一层的东西。
但 App 总得知道"连哪个地址、用什么凭证"，这是第三层，跑不掉，也不叫登录，叫**配对**。

### 那套系统长什么样

```
用户 ──▶ 平台（账号 / 计费 / 开机器）
            │ provisioning：拉起容器，注入 AGENT_TOKEN
            ▼
        用户的 Agent 实例（云电脑，独立容器或 VM）
            ▲
            │ 地址 + token（配对）
        手机 App（只是遥控器）
```

成本上必须靠**空闲休眠**（hermes 走的是 Daytona / Modal 这类 serverless 容器）：
有交互时唤醒，闲置时休眠。否则"一人一台"在经济上不成立。

### 对当前代码意味着什么

**App 侧一行都不用改。**

现在做的「地址 + 令牌」正好就是第三层（配对）需要的东西。将来那套平台系统
只是替用户把这两个值生产出来（扫码 / 一键下发），App 拿到的仍然是同样的两个值。

需要新增的是平台侧：账号、计费、编排、镜像分发、实例生命周期。**和本仓库不是一个项目。**
