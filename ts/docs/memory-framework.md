# 记忆框架

> 这份文档定的是**分层与边界**，不是策略。策略（怎么打分、怎么去重、用什么算法）
> 以后一定会改，改的时候不该动这里的结构。

## 先对齐三层：记忆不是一个东西

（对齐 `<local-docs>\agent-design\05-记忆的三种做法.html` 的分层，那篇比这里细）

| 层 | 是什么 | 我们做到哪 |
|---|---|---|
| **L1** 会话内压缩 | 上下文快满时怎么办：保护头尾、摘要中段、剪工具输出 | ❌ **没做**，但这层 pi 已经给了 |
| **L2** 跨会话笔记 | 哪些事实带到下一次对话 | ✅ 本框架的主体 |
| **L3** 历史检索 | 笔记里没有的，回去翻原始记录 | ⚠️ 接口有，实现是最弱的 LIKE |

关键认知：**L2 是唯一真正的分歧点，L1 和 L3 各家方向都一致。** 所以下面四层流水线
覆盖的是 L2，加上一小部分 L3（用 store 里的记忆当检索源，而不是翻原始消息）。

### L1：已接（阈值触发），缺 overflow 兜底

一个重要的结构性事实：**pi 的代码分两层，压缩的判断不在内核里。**

| 层 | 有什么 |
|---|---|
| core（`pi-ai` + `pi-agent-core`） | `compact()`、`shouldCompact()`、`calculateContextTokens()` —— 都是**工具** |
| 应用层（`pi-coding-agent`） | `AgentSession._checkCompaction()` —— **什么时候用这些工具的策略** |

我们 vendored 的是 core，所以工具齐全但没有策略。这段策略是照 `_checkCompaction` 抄的，
落在 `apps/server/src/provider.ts` 的 `maybeCompact()` 里：

```ts
const tokens = calculateContextTokens(assistantMessage.usage);
if (shouldCompact(tokens, model.contextWindow, DEFAULT_COMPACTION_SETTINGS)) {
  await harness.waitForIdle();
  await harness.compact();
}
```

压缩在回复结束后异步执行，不阻塞用户；失败只记日志，不影响本轮对话。

**还没抄的部分**：`overflow` 兜底 —— 请求超窗报错后，把错误消息从上下文里摘掉、
压缩、自动重试一次。需要错误分类，等接真实模型拿到实际报错再做。

## 一句话

记忆不是一个"库"，是**四层流水线 + 一条生命周期**。库只是其中一层。

```
写入侧（会话边界）                    读取侧（每轮开头）
                                    
   对话                                用户这句话
    │                                     │
    ▼                                     ▼
┌─────────┐                          ┌─────────┐
│ Extract │  抽出候选                 │ Recall  │  按相关度挑
└────┬────┘                          └────┬────┘
     │                                    │
     ▼                                    ▼
┌─────────────┐  合并/去重/取代      ┌─────────┐
│ Consolidate │                      │ Inject  │  拼进 prompt
└──────┬──────┘                      └────┬────┘
       │                                  │
       └────────▶ ┌───────┐ ◀─────────────┘
                  │ Store │
                  └───────┘
```

接口都在 `packages/memory/src/`。四层加上引擎装配一共六个文件，每个都能单独替换。

## 四个层

| 层 | 文件 | 现在的实现 | 以后要长的东西 |
|---|---|---|---|
| **Store** 存储 | `store.ts` | SQLite（Node 内置 `node:sqlite`）+ 内存实现 | FTS5 全文索引、向量列、归档表 |
| **Extract** 抽取 | `extract.ts` | 纯规则：按句切分、过滤寒暄 | **LLM 提炼**（判断什么叫重要、分出 fact/entity/preference） |
| **Consolidate** 巩固 | `consolidate.ts` | 内容完全相同 → 强化不新增 | 语义去重、冲突消解、遗忘曲线、时间衰减 |
| **Recall** 召回 | `recall.ts` | 加权打分（重要性/新近度/关键词） | 语义召回、MMR 去冗余、相对时间理解 |

**抽取和巩固是真正决定效果的两层**，也是最该被替换的。存储几乎不用动。

## 一条生命周期

记忆什么时候动，比怎么打分更影响体验：

| 时机 | 动作 | 现状 |
|---|---|---|
| 每轮开头 | recall → inject | ✅ 已接 |
| 每轮结束 | extract → consolidate | ✅ 已接（异步，不阻塞回复） |
| 会话结束 | 收敛成当日记忆 | ❌ 待做 |
| 每天固定时刻 | 整理、合并、淘汰（"睡一觉"） | ❌ 待做 |

后两条是 lifediary 的核心场景（日记本来就是按天收敛的），现在留空。

## 作用域：为什么按天切

记忆按"谁的地盘"分区，召回时只在相关分区里找：

| scope | 存什么 | 寿命 |
|---|---|---|
| `global` | 用户是谁、偏好、长期目标 | 永久，最慢变化 |
| `day:2026-10-28` | 这一天发生的事、想法 | 长期，但只在"那天"相关时召回 |
| `topic:健康` | 某个主题的累积认识 | 长期 |
| `session:xxx` | 本次对话的原始片段 | 短期，容易过期 |

这一点和 coding agent 差别很大：它们是 `global / per-project`，我们是**以时间为第一维度**。
所以 `day` 是一等公民 —— 日记产品里"上个月你提到过…"是最有价值的一句话。

## 两份参考，各取了什么

| 维度 | oh-my-pi / mnemopi | hermes-agent |
|---|---|---|
| 形态 | 一体化引擎，包内自带 SQLite + FTS + 向量 + 图谱 | 极简内置（`MEMORY.md` + `USER.md` 两个文件）+ 可插拔 provider |
| 强项 | **召回质量**：多路融合、时间衰减、真伪合并 | **集成边界**：provider 单选、发现/装配、会话生命周期钩子 |
| 记录模型 | 重（importance / veracity / supersededBy / recallCount / validUntil） | 轻（就是 markdown） |
| 代价 | 重、难改、绑定一套算法 | 召回质量全靠 provider |

**我们的取法：记录模型照 mnemopi，集成方式照 hermes。**

- 记录字段抄 mnemopi 的那几个：`importance`、`veracity`（谁说的，可信度不同）、
  `supersededBy`（旧记忆不删，标记被谁取代，保留演化链）、`recallCount`（召回即强化）、
  `validUntil`（临时状态自动失效）。这几个字段是"记忆会演化"的物理基础。
- 集成方式抄 hermes：记忆是**可替换的一层**，不是焊死在 agent 里。换召回算法不该动业务代码。

不取 mnemopi 的部分：它的向量/图谱/遗忘曲线都很强，但那是召回质量阶段的事，
现在做等于在没数据的时候调参。

## 接入点

现在的注入点在 `apps/server/src/provider.ts`：召回结果拼进 `systemPrompt` 最前面。

以后如果换成 pi 的 `Agent`（而不是直接调 `stream()`），这个位置对应它的
**`transformContext` 扩展点**——pi 允许在不改内核的情况下改写上下文，正好是记忆该待的地方。

## 明确的取舍

- **记忆失败不能拖垮对话**：召回抛错 → 降级为无记忆；写入失败 → 只记日志。两级都做了兜底。
- **助手的话不入库**：只抽用户说的。把模型自己的输出记进记忆，会形成自我强化的回声。
- **日志不记内容**：只记条数与耗时，沿用整条链路"日志不含对话正文"的规矩。

## 已知缺陷（对照调研的四条「值得抄」）

| # | 调研结论 | 现状 | 影响 |
|---|---|---|---|
| 1 | 给记忆硬上限，写满**报错**而不是静默丢弃 | ❌ 无上限 | 库会无限长；模型没有"该忘什么"的压力 |
| 2 | 注入用冻结快照，写入立刻落盘 | ❌ 每轮重新召回 | 同一场对话里记忆会变；换 pi `Agent` 后会打掉 prefix cache |
| 3 | 别给模型 `replace`，只给 `patch` + `remove` | ✅ `store.patch()` 就是这个形状 | —— |
| 4 | 检索先上 FTS5，**中文必须换分词器** | ❌ 现在是 `LIKE '%关键词%'` | 中文靠双字切分硬凑，长对话里召回基本不可用 |

第 4 条是最该先补的：`LIKE` 在中文上既是正确性问题（分词不对，检索等于没有），
也是性能问题（全表扫描）。调研里提到的 `fts5_cjk` 是现成方案。

第 1 条要和产品形态一起定：日记场景下"记忆"是给人看的，硬上限该按**天**算还是按总量算，
现在没有答案。

## 一个已经印证方向的判断

调研说：**写入时机决定记的是「意图」还是「模式」** —— 当场记账能记因果、适合记偏好；
事后挖矿只能看轨迹、擅长抽重复模式。

lifediary 天然属于**当场记账**：用户说完，我们就在那儿。所以抽取层应该往"记因果、
记偏好"方向走，而不是往"定期挖模式"走。这也印证了按天收敛（`day:<date>`）比事后批量扫更对。
