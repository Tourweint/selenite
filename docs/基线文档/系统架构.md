# 系统架构（lifediary-harness）

> 状态：**2026-10-29 按 TS 实现重写**。当前实现 = `ts/`：Node + TypeScript + Hono + SSE，内核 `pi-durable@1.4.0`。
> 旧的 Java/Spring 版架构（2026-10-25 P1：无状态单体、JWT 与 backend 同密钥、先扣额再透传、`signal/session`）
> **已随实现退役，仅作历史**。契约见同目录 `接口文档.md`。

## 1. 定位

**一个人的通用 Agent。** 跑在自己机器上：模型、记忆、会话、密钥都不外流。
记录（日记、流水账、随手的想法）是它用得最多的场景，但**不是边界**——同一个 Agent 也读文件、翻历史、按指令动手。

```
手机 App（<lifediary 手机仓>，Kotlin/Compose）
   │  HTTP + SSE，Bearer <AGENT_TOKEN 或配对设备凭据>
   ▼
lifediary-harness（本仓库，:39847）
   ├ /api/v1/agent/*            自有协议：对话 / 回读 / 停止 / 用量 / 提醒
   ├ /api/v1/llm/chat/completions  OpenAI 兼容层（给现有 App，零改动接入）
   │        │
   │        ├→ pi-durable：会话 / 任务 / 压缩 / 崩溃恢复 / 用量（SQLite）
   │        ├→ @lifediary/memory：记忆四层（存储 / 抽取 / 巩固 / 召回）
   │        └→ 上游 LLM（百炼 OpenAI 兼容 / faux / mock）
   └ 工具 10 个（读写改跑 + 记住/回忆/提醒 + 技能 + delegate/propose_project）+ 条件注册 5 个（partner_skill_write / partner_manage / group_manage / web_search / propose_topic），执行环境 = 本机
```

| 派单死信 | `delegations.sqlite` 的 `delegation_dead_letters`（批次A A2） | 父单终态后子单结果无处并入的记账；只增不改，主键幂等 |
| 派单作废位 | `delegations.sqlite` 的 `delegation_cancellations`（2026-11-07 扫尾批 1 A1） | 取消 = 记一行作废位（`ticket_id` 主键幂等），非杀进程；结算跳过回写、进度/事件停发、列表与详情投影叠加 `canceled`；只增不改 |
| 服务端错误日志 | `.data/server-errors.log`（`AGENT_ERROR_LOG`） | 2026-11-07 起 `app.onError` 把未捕获异常的 message/stack 追加到这里（只记时间/方法/路径/错误，不记请求体与对话内容）。**为什么要文件**：桌面壳用 `cmd.Start()` 拉起服务且不重定向 stdout/stderr，"页面 500"否则完全无迹可查 |

**Harness 自愈（2026-11-07，长驻进程的硬要求）**：pi-durable 的 Session 把存储错误当**终局**——
第一次 `Storage` 抛错就让整份 Session 进 failed 态，此后每次 commit / 读快照都立刻 reject
（`SessionFailed: Session failed after a storage error; close and reopen it`）。
而 `getHarness()` 原来只在**首次**打开时开一次，从不重开；于是一次瞬时 IO 失败（WAL 被抢 /
磁盘抖动 / 杀毒扫描锁库）就会让进程进入"永久 500 到重启为止"的状态——现场表现正是
"页面 500、读历史失败"，同时 `/healthz`、`/policy` 这类不碰 Harness 的端点一切正常。
现在的口径（`agent.ts` 的 `discardHarness` / `getHarness`）：
- 订阅 `harness.closed`（也覆盖失败自动关闭），一旦兑现就丢掉这份并**在后台真正 close**；
- 新实例要等旧句柄交还（`closing`）后再开，避免两份挂在同一个 SQLite 文件上；
- 首次打开失败也不再缓存那份 rejected Promise，下一个请求重新尝试。

**没有做的**（刻意）：不做无限重试。重开后立刻又失败说明不是瞬时问题（磁盘满 / 库损坏），
继续重试只会把 500 变成慢 500；真实错误交给调用方与日志。

**旧口径"无状态、不建库、不落对话内容"已作废**：会话与记忆就是本服务的核心资产，落 SQLite 是刻意设计（关掉界面能继续跑、重启能恢复）。

## 4. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **单用户、无账号**，鉴权 = 一个共享令牌（+ 配对设备凭据；本机页面另有进程内 cookie，2026-11-03） | 个人自用；多用户是另一套系统。令牌是"密码"不是"通行证"，只能回答"你知道密钥吗" |
| D2 | **有状态**：会话/记忆落本机 | 关掉界面能跑完、杀进程能恢复、记忆能跨会话累积 |
| D3 | **历史在服务端**，客户端只发最后一条 user；OpenAI 协议无状态则用首句哈希/`X-Conversation-Id` 折中 | 两边协议并存，服务端适配比改客户端便宜 |

## 5. 与手机 App 的分工（2026-10-29 定稿）

| 数据 | 权威 | 手机是否留存 |
|---|---|---|
| 日记条目（成稿与派生） | **手机本地 Room** | 全量 |
| 会话清单（`conversationId` / 时间 / 首句 / 轮数） | **手机本地** | 只元数据 |

## 6. 部署与安全

- 默认只在本机/局域网跑；`AGENT_TOKEN` 必须配（否则仅 loopback）。
- **CORS 当前 `*`**：上公网前必须收紧来源，否则等于把私人 Agent 敞开。
- 工具以**当前用户权限**执行：`write` / `edit` / `bash` 等价于"你愿意让自己的账号在这台机器上做什么"。
- 密钥只走环境变量（`LLM_API_KEY`），不入库、不下发给客户端、不进日志。

### 6.1 运行时的起停（2026-11-07）

**谁持有进程**：桌面壳（`desktop/runtime.go` 的 `runtimeCtl`）。它是唯一的进程状态
持有者，服务不再只是"探不到就拉一个"——那个函数（`ensureService`）已经退役，因为它
不会记住 PID、也不会停。

- **接口**：`Shell.RuntimeStatus / StopRuntime / StartRuntime / RestartRuntime`，
  设置 → 服务 → 运行时那张卡在用。**页面不能自己干这件事**：它要停的就是自己的后端，
  停下去之后所有 `fetch` 都失败，连状态都问不出来。
- **四态**：`running / starting / stopped / failed`。`stopped`（用户停的）与
  `failed`（自己挂的）必须分开——界面上是两句话。
- **认人**：`stopped` 闩挡住的是**自动路径**（开窗、`watchService` 的失联重拉）；
  托盘的「重新连接」是人的明确要求，**越过闩**。没有这个区分，停完服务后托盘就再也救不回来。
- **以端口为准**：查 PID 先 `netstat` 找监听该端口的进程，查不到才回落到自己记的数——
  PID 会被系统回收，端口上那个才是现在真在服务的。
- **`taskkill` 带 `/T`**：`tsx` 是 loader，会再 fork 真正的服务进程；不带 `/T` 会留孤儿
  占着端口，下次启动直接 `EADDRINUSE`。
- **回滚**：`LIFEDIARY_SHELL_BINDINGS=off` 时整组 `Shell` 不挂，卡片退化成
  「仅桌面端可操作」。
- **开机自启（2026-11-08 扫尾批 4b）**：设置 → 服务 → 运行时的「开机自启」开关走
  `Shell.OpenAtLogin / SetOpenAtLogin`（MyGo 写 HKCU Run，任务管理器可关）；自启的是**壳**，
  服务仍由壳拉起；`LIFEDIARY_SHELL_BINDINGS=off` 时状态读不到，开关键不渲染。

### 6.2 发布形态（2026-11-08 扫尾批 4b）

- **服务端产物**：`pnpm --filter @lifediary/server build`（`scripts/build.mjs`）→ `dist/`：
  esbuild ESM bundle 落 `dist/src/index.js`（与源码 `src/` 同深度，`../web|skills|prompts`
  的相对位才对得上），`dist/index.js` 只是一行入口；资源目录整份复制。`.data` / `.env` 照旧落 cwd。
- **壳**：`desktop/build.ps1` 出 `lifediary-shell.exe`，`-X main.version=<git describe>` 注入版本
  （托盘 tooltip 显示）。**壳仍用 `node --import tsx src/index.ts` 起源码**，`dist` 只保证"能起、
  能服务"，切到 dist 留待下一轮。

## 7. 已知边界与风险

- `pi-durable` 标 **Experimental**：锁版本（1.4.0），不跟 main；跳版本时改动面主要在 `agent.ts`。
- 鉴权只有共享令牌，**不带用户身份**；设备凭据（配对）已实现（2026-11-04 核对，`pairing.ts`）。
- 记忆**偏好已闭环、其余仍是框架**（2026-11-06 核对）：
  - 偏好：会话结束后由 `memory-extract.ts` 做一次**独立**模型调用，只抽"长期偏好"（≤5 条、
    置信度 <0.6 丢弃），落 `kind=preference` 并**改挂更宽的 scope**（主对话 → `global`、
    执事 → `partner:<id>`）——偏好换会话不该失效。每条正文形如
    `偏好\nWhy: …\nHow: …`（照 cindy `feedback` 类与 ZCode 的硬要求：没有"为什么"和
    "何时生效"的偏好，下次照样会错）。模型不可用 / `MEMORY_EXTRACT=rule` → 整条链路
    逐字节回到 2026-11-06 之前（`MEMORY_EXTRACT` 见接口文档 §6）。
  - 其余：事实/经历仍由规则抽取（按句切、一律 `episode`）；`fact` / `entity` 两个 kind
    目前只有 `remember` 工具能写，抽取层产不出来。这是**已知缺口**，不是 bug。
  - 巩固：只做同 scope 字符串全等 → importance +0.1；**不做**语义去重与自动冲突消解。
    显式取代走 `MemoryEngine.supersede(id, byId)`（设置页"标过时"用），旧记录保留可追溯。
  - 召回：JS 双字片段打分 + 候选窗口默认 200（`MEMORY_CANDIDATE_FLOOR` 可调，50 = 旧行为）；
    候选集在 SQLite 上走 FTS5 trigram 3-gram 词袋 OR（查询 ≥3 字才启用，0 命中 / 短查询 /
    FTS 不可用回落窗口路径，`MEMORY_RETRIEVER=js` 整体回到批次一行为，2026-11-04 批次三 A2-F）。
  - 注入：偏好单独成段排最前（渲染分组，不改召回算法）；**没有偏好时输出与旧版逐字节一致**。
  - embedding/向量未做——两家参考实现（cindy / ZCode）也都没做，靠"一条事实一个文件 +
    一行 hook + 按需读取"控预算（调研见 `设计方案/2026-11-06-记忆系统调研与用户偏好落地（cindy·ZCode）.md`）。
- 会话管理（列出/重命名/删除）尚未做——这正是"手机本地清单"方案要补的缺口。
- **附件（图片）base64 直接进 durable，不做 blob 存储**（2026-11-08 扫尾批 4a 登记）：单图解码后 ≤8MB、
  单条 ≤4 张（服务端复核，`attachments.ts`）；会话库体积会随图片增长，导出（§2.5）也会带上 base64。
  **编辑重发 = fork 出新会话**（内核 append-only、无 truncate）：老会话完整保留，列表里会留一条
  分叉前的旧会话，用户可手动移除——不做删除、也不做"就地改写"；SSE 帧结构未动，图片是输入侧。
- **后台派单的会话映射只覆盖新单**（2026-11-04，A3a/A3b）：受理回执落库时带上 `conversation_id`，
  **旧行无映射（无法回填）**。重启后靠 chancellor 的 `inflight.json` 结算任务单：
  已落库（A3a）+ 启动恢复终态状态行回灌（A3b，`DELEGATION_RECOVER_REPORT=false` 可关）；
  用户 resume 过的单（`resumeTicket` 不写回执，没有会话映射）与续跑中单的完成仍不回灌
  （登记为覆盖缺口，观察后再议）。
- **项目前置已到执行层**（2026-11-04）：worktree 隔离、路径租约、按租约合并已落地；`CHANCELLOR_TASK_ISOLATION=direct`
  只用于非 git 项目或明确串行场景，非 git 项目不允许并行写同一项目。
- **恢复不自动重派**（2026-11-04）：跨过「合并进项目」的单即使 `DELEGATION_RESUME_POLICY=auto-before-merge` 也转「待你处理」；
  自动续跑最多一次（`resumeCount`），防止重启—续跑—再中断的循环。
- **工作区变更不迁移项目**（2026-11-03）：单工作区，切换根目录后旧项目若落在新根外，派单时会按当前工作区拒绝。
- **一个供应商只配一把 key（单 `keyEnv`，刻意没有）**（2026-11-04 登记）：多把钥匙的场景——按项目/按工作区发 key 的服务（如 Clarity 类，一个令牌对应一个项目）、按 key 限速需要轮换——暂不设计。同一上游要用多把钥匙时，变通办法是登记成多个供应商条目（同 `baseUrl`、不同 `keyEnv`）手动切。底座 `envApiKeyAuth` 本就接受变量名数组，将来把 `keyEnv` 升级成数组有现成退路（`schemaVersion` 起步即可），但单人自用大概率等不到那一天，不预先抽象。
- **手机寻址自动化（mDNS/DDNS 等，刻意没有，等中继）**（2026-11-05 登记）：手机侧存的是电脑局域网地址
  （`serverBaseUrl`），电脑 IP 变动后手机会连不上，需在设置页手动改一次地址；配对令牌不随 IP 变
  （令牌无期限、落 `.data/pairing.json`，重启不丢），**不用重新配对**（2026-11-05 实读 `pairing.ts` /
  手机端 `PairingRepository` 确认"一次配对长期有效"）。自动发现电脑新地址的能力不做——后期自建中继节点
  统一解决：中继持固定地址，手机只连中继，电脑出站长连中继，电脑 IP 变动对手机无感；选型（frp /
  自建 Tailscale 等）与契约改动（手机端 + harness 两端）届时先写方案（现成蓝本：参考项目 cindy 的自建中继
  `docs/self-hosted-relay-plan.md`——哑中继、凭证只存哈希、设备签名防冒充，与本仓配对令牌只存
  sha256 同口径，2026-11-05 调研）。多端登录 / 任务跨设备 / 执事认主机的总体方案见
  `docs/设计方案/2026-11-05-多端同步与设备矩阵方案（多端登录·任务跨设备·伙伴认主机）.md`
  （**三阶段已于 2026-11-05 当日落地**，探针 relay/matrix/home 全绿；机制：中继哑路由+盖章 src、
  通道白名单默认拒绝、事件镜像走重放库 250ms 轮询、矩阵派活轮询回报+离线 fail-fast、
  执事路由 CAS 在中继+降级 fail-closed+凭证不随行。已知边界：事件重放库只收 HTTP 发起轮次，
  服务端直写帧不进推送流；远端锚点/执事专线会话在 durable 列表快照的可见性未定。
  测试教训：tools.ts 静态可达 agent.ts 的链路会破坏"先设 env 再加载"的测试——relay-matrix 对
  agent.ts 只做函数内懒加载，新模块照此办理）。过渡期变通：路由器 DHCP 静态绑定，
  或 IP 变动后手动改地址。
- **主机优先制（2026-11-05，方案 `docs/设计方案/2026-11-05-主机优先制方案（先主机·满溢外流·设备描述）.md`）**：
  中继名册存**唯一任务主机位**（`homeDeviceId`，与执事归属 `actors[].homeDeviceId` 是两个概念，
  刻意不合并），由用户经 `POST /api/relay/home-device`（owner 或设备令牌）显式设置、不做自动抢占。
  `targetDevice="auto"` 决策器（`relay-auto.ts`，仍是纯函数）升级 v2：主机在线且未满载**永远选主机**
  （busy 不参与比较——产品口径"大部分工作都给主机用"），主机满载才按 busy 外流，主机离线/未设回落 v1；
  返回带 `pickedHome`，台账同步记。设备 `description`（≤200 字）只进名册投影给人点名参考，
  **不进决策路径**。回滚仍是一条：`DEVICE_AUTO_DISPATCH=false` 关掉整个 auto（含主机优先）。
- **工作区两层模型（2026-11-04，方案见 `docs/设计方案/2026-11-04-侧边栏工作区与当前项目.md`）**：**最大工作区 = 物理硬边界**——`write`/`edit` 的目标路径经 realpath（含符号链接祖先逃逸识别）解析后必须落在工作区根内，越界硬拒绝（`path-guard.ts`，挂 beforeTool 审批之前 + 批准后复判；未设工作区旁路）；**当前项目 = 逻辑归属**（`currentProjectId`，主工作区=杂事态）——会话执行 cwd、系统提示注入、任务归属跟它走，审批行为不因项目改变（用户定调：默认按需确认）；**2026-11-06 起侧栏不再提供切换入口**（改为「主项目+子项目」只读总览——没人在意固定在哪个目录干活），切换端点保留作程序化面。**bash/powershell 不做命令文本扫描是已知边界**：cwd 圈在边界内，命令里写绝对路径逃逸拦不住，靠审批兜底；`CURRENT_PROJECT=false` 一行回滚到无当前项目形态。
- **执事 = chancellor 分管宰相（批次D D2，2026-11-05，契约见 `接口文档.md` §2.11）**：`POST /api/v1/partners` 带 `domain` = 建执事——宿主 `ensureManager(domain, { partnerId })` 建宰相目录 + 执事档案（SOUL 一句话播种）+ `partner_session_links` 记 `role='delegation'`；`delegate(domain=x)` 时按 domain 反查执事，命中则请求带 `managerIdentity={name, soul=当前版本快照}`（宿主截 ≤4KB、单次派单内不变），chancellor 只透传、原文注入分管提示词「## 你是谁」；删执事 = 删档案 + `archiveManager` 把领域目录改名 `.archived-`（runs 历史保留）。查不到的 domain 照旧，兼容旧领域。**刻意没有（登记防补齐）**：宰相不接宿主记忆引擎、不吃 `partner:<id>` 键空间（记忆仍靠 chancellor 会话续用 + handoff.md，两套记忆不混）；worker（codebuddy / qoder / phone）不是角色、不给身份（它们是手，宰相才是脸）；不做跨电脑执事（远程锚点会话不装配身份缝）；不做 D3 `partner_manage` 工具；`domain` 建后固定不可 PATCH 改。**派发权（2026-11-06，按执事独立·默认关）**：`partners.dispatch_authority` 列 + env 总闸 `MINISTER_DISPATCH_AUTHORITY`；闸门接在宿主装配缝 `tools.ts` 的 `localIdentityHit`——关着时派单不注入该执事的 `managerIdentity`，chancellor 总管直派，不拒单（语义与取舍见设计方案同名篇）；chancellor 仓库不动。`partner_session_links` 的 delegation 行用 `session_id=0` 占位（不是真实宿主会话），`partnerIdOfSession` 以 `session_id > 0` 过滤。
**执事直派（2026-11-07）**：执事在自己领域内派活不再绕回分管宰相——`resolveDelegateRouting`
（`delegate-routing.ts`，纯函数）按"调用者是不是执事 / 请求的领域是不是自己"分四象限，
直派时 `managers:false` + 不注入 `managerIdentity`。理由：执事本身就是该领域负责人，
再注入一次等于同一身份跑两遍。跨领域明确拒绝而不是静默改道。回滚 `MINISTER_DIRECT_DISPATCH=false`。
