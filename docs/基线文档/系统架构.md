> 状态：**2026-10-29 按 TS 实现重写**。当前实现 = `ts/`：Node + TypeScript + Hono + SSE，内核 `pi-durable@1.4.0`。
> 旧的 Java/Spring 版架构（2026-10-25 P1：无状态单体、JWT 与 backend 同密钥、先扣额再透传、`signal/session`）
> **已随实现退役，仅作历史**。契约见同目录 `接口文档.md`。

## 1. 定位

**一个人的通用 Agent。** 跑在自己机器上：模型、记忆、会话、密钥都不外流。
记录（日记、流水账、随手的想法）是它用得最多的场景，但**不是边界**——同一个 Agent 也读文件、翻历史、按指令动手。

```
手机 App（<lifediary 手机仓>，Kotlin/Compose）
   │  HTTP + SSE，Bearer <AGENT_TOKEN 或配对设备凭据>
   ▼
lifediary-harness（本仓库，:39847）
   ├ /api/v1/agent/*            自有协议：对话 / 回读 / 停止 / 用量 / 提醒
   ├ /api/v1/llm/chat/completions  OpenAI 兼容层（给现有 App，零改动接入）
   │        │
   │        ├→ pi-durable：会话 / 任务 / 压缩 / 崩溃恢复 / 用量（SQLite）
   │        ├→ @lifediary/memory：记忆四层（存储 / 抽取 / 巩固 / 召回）
   │        └→ 上游 LLM（百炼 OpenAI 兼容 / faux / mock）
   └ 工具 10 个（读写改跑 + 记住/回忆/提醒 + 技能 + delegate/propose_project）+ 条件注册 10 个（recall_sessions / save_skill_advice / ask_user / report_progress / partner_skill_write / partner_manage / group_manage / routine_manage / web_search / send_to_agent；pi 的 powershell 本仓未注册，声明属防御性覆盖），执行环境 = 本机（2026-11-24 核对；2026-11-20 课题退役删掉 propose_topic；**2026-11-24 旧形态退役**：`persona_recall` / `persona_write` 已删，记忆工具面恒为 `recall` / `remember` 两个，槽位只换后面挂的库）
```

**Harness 自愈（2026-11-07，长驻进程的硬要求）**：pi-durable 的 Session 把存储错误当**终局**——
第一次 `Storage` 抛错就让整份 Session 进 failed 态，此后每次 commit / 读快照都立刻 reject
（`SessionFailed: Session failed after a storage error; close and reopen it`）。
而 `getHarness()` 原来只在**首次**打开时开一次，从不重开；于是一次瞬时 IO 失败（WAL 被抢 /
磁盘抖动 / 杀毒扫描锁库）就会让进程进入"永久 500 到重启为止"的状态——现场表现正是
"页面 500、读历史失败"，同时 `/healthz`、`/policy` 这类不碰 Harness 的端点一切正常。
现在的口径（`agent.ts` 的 `discardHarness` / `getHarness`）：
- 订阅 `harness.closed`（也覆盖失败自动关闭），一旦兑现就丢掉这份并**在后台真正 close**；
- 新实例要等旧句柄交还（`closing`）后再开，避免两份挂在同一个 SQLite 文件上；
- 首次打开失败也不再缓存那份 rejected Promise，下一个请求重新尝试。

**没有做的**（刻意）：不做无限重试。重开后立刻又失败说明不是瞬时问题（磁盘满 / 库损坏），
继续重试只会把 500 变成慢 500；真实错误交给调用方与日志。

**旧口径"无状态、不建库、不落对话内容"已作废**：会话与记忆就是本服务的核心资产，落 SQLite 是刻意设计（关掉界面能继续跑、重启能恢复）。

### 2.1 执行器池：本机唯一运行时（2026-11-22；2026-11-23 native 退役后唯一）

**定位**：派活的最底层 worker 不再每票起一个裸子进程，而是进一组常驻池进程
（`WORKER_POOL_SIZE`，默认 8；旧名 `SUPERVISOR_POOL_SIZE` 兼容）；一个池进程同一时刻只跑一票，进程跨票复用。
宿主侧 `pool/supervisor.ts` 负责起进程、绑槽位、SSE、心跳、回收与重派，
判断逻辑在 `pool/supervisor-core.ts`（纯函数）。

**两个入口都进池**：

1. **前端直派任务**：侧栏「任务 → 新建任务」→ `POST /api/v1/agent/tasks` →
   先分配单号并建 `task-<票号>` 专线、把用户那句话写成真 `pi.user`（不跑宿主模型），
   再 `startDelegation` 落单；缺省强制 `employee=pool`（`DIRECT_TASK_POOL=false` 回滚）。
   任务线程里的再说话：跑动中走 `POST /agent/delegations/:ticketId/message`（steer），
   等回答 / 空闲走 `POST /tickets/:id/say`（续跑）——两条都落到池进程。
2. **agent 派活**：总管 / 执事（历史 worker 会话仍可）调 `delegate` → `startDelegation` →
   设置里的默认执行器（`pool`）。带领域时 chancellor 仍起 manager 子进程；
   manager 子进程通过**宿主 loopback 池桥**（`pool/bridge.ts`）把子单投进池：
   宿主只在 127.0.0.1 起 HTTP+SSE，token 经 env 交给 manager 子进程，
   子进程里的 `createEmployee("pool")` 用这份 endpoint/token 连回来。
   **2026-11-23**：native 退役后池桥是 manager 子单唯一的本机执行路径，
   `POOL_MANAGER_BRIDGE` 开关随之退役（池可用即起桥；关掉它等于让子单全部失败）。

**通信**：插话 / 上报答复走 `supervisor.say`；取消先走票级 `AbortController`，
没有控制器时按 `employee=pool` 回落 `supervisor.abort`；manager 子单的上报由池桥
读子单 `ticket.json.originConversationId` 转发回父单来源会话，走既有
`emitDelegation` → 上报路由（总管/执事代答 → 升级用户 → 答复回 worker）。

**工具面**：池进程固定五件 `read / write / edit / bash / escalate`；
`worker-tools` 页勾选的 canonical 四件经 `run.tools` 下发，池进程取交集，
`escalate` 恒开（上报是池工人的通信手段）。manager 子进程经
`CHANCELLOR_WORKER_TOOLS` 继承同一份名单。

**边界（如实写）**：普通助手会话（`chatKind=worker`）**2026-11-23 起退役**——不再新建
（`WORKER_CHAT_ENABLED` 默认关、前端无入口）；已落盘的历史 worker 会话仍跑在宿主 Harness、
照常可读可续。本节的“会话进池”指任务线程的**执行**在池，不是把会话的完整模型循环搬走。
**native（每票一个裸子进程）2026-11-23 退役**：本机派活只剩池这一档；历史
`employee:"native"` / `CHANCELLOR_EMPLOYEE=native` 一律映射到 pool。dist 单文件产物仍跑不了池
（池入口是源码 `.ts`），`available()=false` 时单票如实报「池执行器未接线」，没有第二套本机
运行时可回落。等上报让出槽位、池崩溃按票重派、池业务队列可见性仍属后续批次。

## 4. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **单用户、无账号**，鉴权 = 一个共享令牌（+ 配对设备凭据；本机页面另有进程内 cookie，2026-11-03） | 个人自用；多用户是另一套系统。令牌是"密码"不是"通行证"，只能回答"你知道密钥吗" |
| D2 | **有状态**：会话/记忆落本机 | 关掉界面能跑完、杀进程能恢复、记忆能跨会话累积 |
| D3 | **历史在服务端**，客户端只发最后一条 user；OpenAI 协议无状态则用首句哈希/`X-Conversation-Id` 折中 | 两边协议并存，服务端适配比改客户端便宜 |
| D4 | **断开 ≠ 取消**：客户端断线只停推送，那一轮继续跑完并落库；真停走 `/stop`。2026-11-25 起 `GET .../messages` 带 `running`，刷新 / 断流后前端据此显示「还在后台跑」并轮询到收尾自动重读（不做 SSE 重接） | "取消等待"不等于"取消工作"；记忆抽取挂在轮次结束上；先解决"看不出还在跑"，不新造订阅契约 |
| D5 | **记忆在 harness**（四层，按会话作用域） | 它是 Agent 的长期状态；手机端不再做记忆策展 |
| D6 | **工具闸门：三档 + 独立审批轴**（2026-11-04 批次二 A1；2026-11-08 扫尾批 8c 形态升级、10-C 审批三档）：`read-only` / `no-shell` / 黑名单照旧；审批轴三档 `ask-all`（写类 ∪ 高危清单全问）/ `ask-critical`（只问高危清单：bash、powershell、delegate、partner_manage、send_to_agent，`AGENT_APPROVAL_CRITICAL_TOOLS` 可覆盖）/ `none`（默认，旧行为）。**缺省 async = 等待态落库**：落 pending、回拒绝性答复、本轮照常收尾（零挂起），人答复后服务端自动 followUp 让模型原样重发，闸门按「工具 + 参数指纹」的一次性放行清单核销；pending 永不自动过期。`AGENT_APPROVAL_MODE=blocking` 回到旧的 120s 挂起 + 超时拒绝（回滚，旧路径整段保留） | pi 只留 `beforeTool` 钩子。三档是"能力边界"，确认是"动作策略"，压成一个枚举无法表达"只读 + 确认"。独立轴默认关 = 旧行为；手机不进聊天流，走全局待办轮询（2026-11-04 批次六统一口径）。**不做工具结果回填**（1.4.0 无此口）——用"模型重发"换零内核改动，代价是每次批准多一轮模型调用 |
| D7 | **回合上限**（默认 100，`AGENT_MAX_TURNS` 可调、0 不限）多路兜底：拦工具 + 指令收尾 + 3 轮后硬停 | 没人看着时模型陷循环会烧 token；再发一句话即新预算 |
| D8 | **日志不含对话内容**（只记条数/字数/耗时/枚举） | 隐私边界；原始错误只进服务端日志（可能含上游地址） |

### 4.1 人设、关于我、记忆的分工：什么放哪（2026-11-16 立规矩；2026-11-19 加「关于我」）

**一句话判据：这句话你希望它每轮都在，还是说到相关话题才想起来？**

- **每轮都该在 + 说的是"我是谁 / 我怎么相处" → 人设**（`SOUL.md` / 人格模块 / 岗位契约）。
  人设是每轮**全量**进提示词的固定段，不占召回名额，所以只该放"任何时候都成立"的人格与底线。
- **每轮都该在 + 说的是"主人自己的习惯 / 称呼 / 雷区" → 关于我**（2026-11-19）。
  全局一份 `.data/user-profile.md`，每轮作为 system 段 `user_profile` 注入；
  每个 Agent 一个读取开关（`partners.user_profile_read`），普通 worker 与派活工人固定不读。
- **说到才想起来 → 记忆**。记忆每轮按相关度只挑 16 条 / 2000 字，放"越攒越多、按需取用"的东西。

| 放哪 | 放什么 | 不放什么 |
|---|---|---|
| **人设** | 它是谁、说话方式、底线、长期在做的事、"和这个人相处的定位" | **关于主人的具体事实 / 稳定习惯**（称呼、语音输入、雷区）——每轮都要在的放「关于我」，其余放记忆；人格设定本身不写用户档案 |
| **关于我** | 主人自己写的、客观稳定的背景：称呼、输入方式（如常用语音输入、可能有错字）、说话禁忌、工作节奏；**每轮都该在**且**不因话题变化** | 人格设定；一次性的偏好细节；会变的动态（心情、当前项目、最近在做什么）；模型自动抽取的内容 |
| **记忆** | 用户的偏好 / 事实 / 经历、执事的私有偏好、项目口径（怎么构建、怎么部署、踩过什么坑） | 人格设定；一次性的琐事；**必须每轮都在**的用户硬约束（那份进「关于我」） |

**为什么不能混**：
1. **重复占预算**——同一句"用户不喜欢被追问"写进人设 / 关于我，记忆里又有一条偏好，每轮就出现两遍：
   固定段那份白占开销，记忆那份还抢名额。
2. **冲突没有仲裁**——两处说了两套，模型只能自己猜谁新；而固定段是"每轮都在"的，实际会压过召回。

**冲突时谁赢（口径）**：
- 关于主人的事实 / 习惯：**「关于我」优先**（主人手写、每轮都在、可逐 Agent 关）；
- 人格与说话方式：**人设优先**；
- 记忆只是按相关度挑的候选，不能压过上面两层。

**边界**：人设里不写主人的隐私事实 / 稳定习惯——这些放「关于我」或记忆。
人设天然带一点"关于关系的记忆"（"和这个人相处三年了""我是他的纪要员"）可以留——判据不变：
它是不是**这个人格**每轮都该生效；如果只是关于主人的客观背景，归「关于我」。

**派活工人（池）（2026-11-23；普通助手会话退役后唯一的本机工人配置页）**：人设**全局一份，不按票存**——设置 → 注入 → 人设 → 派活工人（池）改的是池工人 + 外部 CLI 共用的那一份（`.data/worker-persona.md`，端点仍是 `worker-persona`）。页面四段：**人设正文**（唯一可编辑正文，按内容长高）/ **工具**（`worker-tools` 四件收成一行、逐条开关进 ⋯ 弹层；「上报」escalate 恒开只读）/ **模型与权限**（只读，读 `GET /agent/executor` 的 `profiles.pool`，改去「派活 → 执行器」）/ **上下文**（只读九段，读 `context-defaults?role=dispatch-worker`，逐段看原文去「注入 → 上下文」）。旧页面里的会话段（所处项目 / 技能覆盖）随 worker 会话一起退役。执事与总管的人设仍按人（家目录）各存一份，两套不混。

**这条没有代码强制**（2026-11-16 核实）：没有"写 SOUL 时检查是否像事实"的拦截，也没有"人设与记忆去重"的机制。它靠写人设 / 记记忆时的人为判断；要强制得单独立项（例如保存人设时提示"这句话更像一条记忆"）。

**现状**（2026-11-16 核查）：四个人设 SOUL 分别 11 / 15 / 15 / 34 字，契约最长 180 字——**都很短，暂时没有需要搬家的人设内容**。这条规矩先立在前面，避免写长了再回头拆。

|---|---|---|
| 系统提示词 / 工具 / 技能 | `conversation.context(CTX)` 的 `ContextView`，再用 `getCurrentSystemMessage(view.messages)` 取当前真正会发出去的那份 | 看的是"这一轮实际会发什么"，不是另算一份估算；不调 provider、不改工具顺序 |
| 记忆 | `beforeRequest` 在一轮**第一次模型请求**（`used === 1`）把 `collectInjections(...).message` 的 `{id,text}` 记进进程内表 | `recall()` 会回写 `lastRecalledAt` / `usageCount`；预览绝不能触发召回副作用。进程重启后首次打开显示"待下一轮"，这是安全口径的代价 |
| 会变的部分 | user/assistant 文本、assistant `toolCall`、`toolResult` 的条数与 token 估算；**2026-11-17 起再加 `entries`：逐条给出正文** | 页面 `2026-11-17 重画`后要能读到消息与调用正文；单条 4000 字截断，`chars`/`tokens` 仍按全文 |
| 请求历史 | **2026-11-19 起做**：同一页新增「请求与缓存」卡，来源是 durable `pi.assistant` entry 的 `usage`（`request-stats.ts`）；最近 500 条、每页 100 条，点一条用 `conversation.context({ at })` 重放当时的固定前缀 + 已存档消息，并与上一条对比 system / 工具面 | 用户要按请求排查缓存命中。数据已经在 `pi.assistant` 里，不落新存储；请求时临时注入不落 durable，详情里如实标注看不到 |

**数字口径（2026-11-16 用户拍板）**：页面主数字是 **token 估算**（`token-estimate.ts`：CJK 1 token/字 + 其它 1 token/4 字符，向上取整），带 `≈`；响应同时保留 `chars` 供排查 / 兼容。顶部「上一轮」用真实 usage，`used` = `input + cacheRead + cacheWrite`（完整 prompt tokens；原实现只取 `input`，命中缓存时低报）。工具定义仍然是最大块（2026-11-16 活服务总管默认面 22 个工具 ≈7,922 token，其中 `delegate` 一个 ≈2,128），是否压缩工具描述另立方案。

内存记录边界：每会话只留最新一轮，最多 64 个会话 LRU，不落盘、不进日志；开关 `CHAT_CONTEXT_INSPECT=false` 时端点整段 404。实现源 `apps/server/src/context-inspect.ts`，接口见 `接口-端点1-对话与兼容层.md` §2.2.4。

**页面形态（2026-11-17 用户拍板，同日两轮）**：一页一张卡 = 总量 + 上一轮真实用量 + **384 格棋盘图**（32×12 的逻辑分辨率，`paintWaffle()` 按占比用最大余数法分配、每组至少 1 格，格子按组上色，**面积就是占比**；缩放基准是请求总量而不是上下文窗口，所以格子总填满）+ 右侧图例 + 一行跳执事档案页的链接。
粒度：点格子或图例 → 从触发点浮起一张卡片，里面逐条列名字与 token，点条目读原文（卡片侧 3,000 字上限、服务端 4,000 字截断）。
工具栏另有一个两档基准开关（只在会话版出现）：「占比」= 384 格代表这一条请求本身（默认）；「窗口」= 384 格代表整条上下文窗口，没用到的余量**固定占 30%（115 格）**而不是真比例——1M 窗口只用 6K 时按真比例几乎空图，固定留一块才看得出各组大小；真实占用率仍由右上角「上一轮 6.3K / 1.0M · 1%」与图例「未使用 ≈N」负责，用量超过 70% 时余量按真实剩余收窄。选择存 `localStorage.lifediary.ctxScale`。
会话版只列**已经进请求**的组，0 token 整组不出现；默认开销版全列（含 0），0 token 的组卡片正文写「当前没有开销」（如「记忆：预算 16 条 / 2,000 字」）且悬停时不压暗棋盘。
工具描述不进主页面（卡片里才是真实 JSON 定义）；「系统底稿」行（`system.content`，恒空）从页面删掉。
**页内编辑（2026-11-21 恢复）**：`editable` 段在浮层里多一枚「可编辑」徽标，展开后有「改这一节」；保存写回各自源头（SOUL / worker 人设 / 关于我 / 契约 / 目标 / 纪律），代码固定段仍只读，档案页仍是另一条入口。
会话选择器显示执事的名字（`partner-<id>` → `state.partners` 的 `name`，总管 / worker 用角色名），与「默认开销」的角色选择器同一套口径。

### 4.4 低频工具索引：`tool_index` 段与 `tool_search` 的加载语义（2026-11-16 C 段；2026-11-25 默认常驻 + 尾部注入）

- **默认形态：全部常驻（2026-11-25）**：`DEFAULT_DEFERRED_TOOL_NAMES = []`，`markDeferred` 不再给任何
  工具补 `deferred`；按需池改为 `.data/tool-pool.json` 显式 opt-in（重启生效）。默认装配下
  **不注册 `tool_search`、不产生 `tool_index` 段**，工具声明在会话中途不再增删。代价是固定前缀
  多出约 2.6k token，由前缀缓存摊薄；换取工具面稳定（审计会话 3971 的 #7/#11 两次命中率坍塌
  正是加载低频工具导致的前缀断裂，见 `设计方案/2026-11-25-命中率下降与缓存前缀.md`）。
- **显式启用按需时**：`markDeferred` 只给名单内工具补属性，既不改描述也不调顺序；`tool_search`
  仍注册在 `createTools` 末尾。启用动作本身是有意的缓存前缀变化（变更记录已登记）。
- **`tool_search` 的加载是「下一轮生效」**：命中后回 `control.addTools:[name]`，内核在本轮工具跑完后

  才进工具面；本轮模型拿到的只是工具结果文本（完整定义 + 「已加载」句）。已加载的名字记在
  `AgentState.modelTools.add`，`agent.tools` 看得到；没加载的在 `agent.deferred`。
- **`tool_index` 是尾部消息注入，不是 system 段（2026-11-25）**：provider 的 `channel:"message"`、

### 4.5 提示词前缀不变量：什么能进 system、什么只能走尾部（2026-11-19）

上游的自动前缀缓存按「从第 0 个 token 起完全相同的前缀」命中；只要 system 或 tools 有一个字节
自动变了，整段 history 全部重算。2026-11-19 之前两条路都在破坏它（实测会话 3112 的 6 次全未命中，
原因就是新一轮记忆召回与当时的课题进展各改了一次 system（课题 2026-11-20 已退役）。

**不变量**：

1. **system / tools 只放「用户显式改才会变」的东西**：人设、关于我、验证铁律、开工前问清、注入防线、
   派活执行器、技能索引（按会话冻结）、工具定义（工具面本身）。项目切换、记忆召回、
   执事的在办 / 心情 / 印象**一律不进固定前缀**。
2. **动态注入走请求尾部的 user 消息**（`INJECTION_CONTEXT_HEADER` 开头，明确「只作背景、不是用户
   新指令」）。收集 / 排序 / 去重仍由注入框架负责；位置从「请求最前面」改成「最后面」。
3. **新增 system 段 = 有意的缓存契约变更**：必须进 `变更记录/`，并说明「为什么它不会自动变」。
4. **工具加载只动 tools，不动 system（2026-11-25）**：显式启用按需池时，`tool_search` 加载工具仍会
   打掉一次缓存（工具声明本身变了，用户加载动作的一次性代价）；但 `tool_index` 已改走尾部消息注入，
   不再连带 system 段。默认空清单下没有加载动作，工具面稳定。
5. **历史 assistant 的 thinking 不回放（2026-11-25，审计日期 2026-11-25）**：`beforeRequest` 默认
   剥离 assistant 的 `type:"thinking"` block 与多余的 `reasoning_content` 字段，只改这一次请求的视图；
   durable entry 保留 thinking（UI 步骤展示 / 刷新还原仍用）。pi-ai 的 openai-completions 适配层
   会为要求该字段的供应商自动补空 `reasoning_content`，工具调用不受影响。回滚 `CHAT_REPLAY_THINKING=true`。

**为什么不用「所有 section 按会话冻结」**：切项目 / 新增记忆在会话内会不可见，模型拿着过期信息
干活；拆「固定 + 尾部动态」既保住缓存又保住实时性。**为什么不做请求级持久化流水**：命中率可以从
已有 `pi.assistant` entry 的 `usage` 还原（`request-stats.ts`），不新增存储；请求时临时注入
不在 durable 里，如实标注为看不到。

### 4.6 记忆库槽位：工具名不变，后面换库（2026-11-23）

**口径**：`recall` 读当前库、`remember` 写当前库。槽位由 `.data/memory-bank.json` 的
`active` 决定（`builtin` / `external`），**本批只支持一个外接库**。外部库只暴露两个入口
文件：读入口 `ask <question> --json --limit N` 与写入口 `repair statement <body> --why <原因>`；
**入口不限语言**（文件名固定，扩展名决定运行器：`.py` → python、`.js` → 宿主 node、
`.sh` → bash、`.ps1` → powershell、其他/无扩展名 → 直接执行；子进程 cwd = 库根）。
harness 只起进程、传 argv、读 stdout，**不打开外部数据库、不跑 SQL、不知道表名**。

**工具分发**：`ToolDeps.memoryBank` 恒注入 `{active, ask, write, writable}`，`recall` / `remember`
在 execute 内按槽位分发；`persona_recall` / `persona_write` 已删（2026-11-24 旧形态退役；
工具面从「最多 4 个」收敛为**恒 2 个**，是缓存前缀资产变化，已登记变更记录）。
外部只读库仍注册 `remember`，调用回只读错误（**不动态摘工具**，免得工具面跟着库状态抖）。

外接库的读入口返回 `groups` 的**组名不固定**：解析成扁平 `hits`（`hit.group` 原样带出），
`groups:{}` 是合法空结果（不是失败）；内置 persona 六组仍走原 `parsePersonaAskOutput` 校验，
两条路径互不影响。

**失败语义**：外部读失败 → `err("memory_unavailable", ...)`；外部写失败 → `err(...)`；
都**不回落内置库**（两库条目不同构，悄悄换库比报错更危险）。`PERSONA_MEMORY_ENABLED=false`
时 `recall` 回「外部记忆库已关闭」；`PERSONA_WRITE_ENABLED=false`（默认）时 `remember`
回「写入未开启」，**不 spawn**。

**闸门**：外部 `remember` 是「起进程 + 写用户一生的库」，在 `beforeTool` 里按写工具对待——
`AGENT_TOOL_POLICY=read-only` 必须拦（文案说明换档）；审批按 critical
（`ask-all` / `ask-critical` 都问，`approval=none` 显式不问；不复用内置 remember 的
「本会话记住该工具」放行）；无人值守按外部 remember 的写工具能力面判 `skip`（不新增
`TOOL_CAPABILITIES` 登记）。判定提成纯函数 `externalRememberBlockReason()` /
`externalRememberApproval()`，内置模式判定逐字节不变。

**注入**：`active=external` 时 `persona_catalog` + 轻召回走当前 bank 的读入口，
内置 `memoryRecallProvider` 跳过；`active=builtin` 时目录与轻召回都不注、内置召回照旧；
`projectIndexProvider` / `taskMemoryProvider` 不动。2026-11-24 起没有 env 路径第二条分支
（旧形态已删）；两档超时：轻召回 `timeouts.lightMs`（默认 8s）、工具调用 `timeouts.askMs`
（默认 15s）。

**刻意不做**：`get` / 全文回读、MCP、Markdown 适配器、多库候选、库内化 / 定时任务、

### 4.7 插件开关：父子门、前置连开与界面显隐（2026-11-25）

清单仍是唯一真源 `ts/apps/server/src/plugins.json`（87 键、50 条 `requires`、8 个多父、最深 3 层）。

- **父子门**：父关 → 子 `effectiveValue=false`、界面锁住、`PUT` 400 `flag_locked`，**子项存储值保留**。
  `flagValue()` 不套父门（枚举档位消费方需要原值），需要父判的消费点自己补——这是刻意保留的语义缝。
- **前置连开**：四个端点（`enable-plan` / `enable` / `disable-plan` / `disable`）挂在 `mountFlags` 内，
  只做「离线拼图 + 按拼图写值」；`POST` 每次按当时状态重推演，按拓扑序逐键 `setFlag`。
  布尔键一律可关（关值 `"false"`）；枚举键没有 `offValue` 才不可关；`revive` 必须模拟计划写完之后的状态，
  二层恢复（父一开、被锁的中间父自动恢复、它的孩子跟着恢复）不能漏报。
- **显隐**：`web/surfaces.js` 一份声明式表（`{id, selector, requires, mode}`），只读 `effectiveValue`，
  缺键 fail-open；`mode` 三档 `hide / disable / empty`；PINNED 白名单禁止藏「回去的路」；
  深链落到已关闭功能时由 `settings-router.js` 给空态（保留 tab 条 + 「去插件中心」）。
  左栏一级项只在「整页只属一个插件」时整体消失（派活 / 定时任务），混装页只收页内 tab / section / 按钮。
- **回滚**：`FLAG_CASCADE_ENABLE=false` → 四端点 404；`PLUGIN_SURFACE_HIDE=false` → 注册表停用。
  两个门经 `GET /api/v1/agent/policy` 的 `flagCascade` / `pluginSurfaces` 下发，且与 `AGENT_FLAGS_UI` 合取。
- **已知边界**：① `AGENT_FLAGS_UI=false` 时 `/agent/flags` 404，注册表 fail-open，需求「关了界面就消失」
  在该部署下不成立；② `hot:false` 的开关界面立刻收、后端能力重启后才停，「待重启」只在插件卡上显示；
  ③ plan 无版本号，`POST` 以当时状态为准；④ 级联是逐键原子写、不是事务，中途失败回 500 `partial`。

方案与取舍：`docs/设计方案/2026-11-25-插件耦合与界面显隐.md`；落地记录：
`docs/变更记录/2026-11-25-插件耦合与前置连开.md`、`2026-11-25-界面显隐收口与精简.md`。

## 5. 与手机 App 的分工（2026-10-29 定稿）

| 数据 | 权威 | 手机是否留存 |
|---|---|---|
| 日记条目（成稿与派生） | **手机本地 Room** | 全量 |
| 会话清单（`conversationId` / 时间 / 首句 / 轮数） | **手机本地** | 只元数据 |
| 对话正文 | **harness** | 不留，按 id 回读 |
| 记忆 | **harness** | 不留 |

- **不做"列全部会话"接口**（会话多了太重）：手机本地存清单，点开带 id 取正文。
  例外：为"重装/换机恢复清单"，有轻量索引接口 `GET /api/v1/agent/chats`（只元数据，见接口文档 §5；2026-11-04 核对：已实现）。
- **配对**：harness 出一次性码二维码 → 手机换取长期设备凭据（设计见 App 仓库方案 §4.6；2026-11-04 核对：已实现，`pairing.ts`）。
  **硬件归并（2026-11-24 C-10）**：请求可带可选 `hardwareId`，服务端只存**二次** `sha256`（`hardwareHash`）作**内部归并键**——同 hash 的未撤销记录**复用原 deviceId**（覆盖令牌、刷新名字/时间、重算指纹、清 `keyChangedAt`；已撤销不复活），于是同一台手机反复扫码不再堆同名记录，旧令牌自然 403。`hardwareHash` **不进 `listDevices()` 投影、不进日志、不当鉴权依据**（鉴权仍只认 deviceToken）；缺字段 / `DEVICE_HARDWARE_MERGE=false` = 逐字的旧行为。中继名册各自内部同口径去重（两份库仍不合并）；显示层合并仍是 C-9 的事。
- **提醒与定时任务（2026-11-17 重做）**：方向仍是 harness 定时间（`sleepUntil` 落库不丢）+ 手机负责响。一套界面、两条引擎：**手动新建**走 `ReminderTask`（`/api/v1/agent/reminders`，保住手机本地闹钟）——新增 `enabled`（暂停：到点只续排、不跑模型）、`visibility`（`hidden` 隐藏触发 / `visible` 保留用户指令）、`PATCH` 可改内容/时间/暂停/可见性（同 `reminderId` 重排）、`POST /run_now`、执行历史落 `.data/reminder-runs.json`（`REMINDER_RUNS_STATE_PATH`，全局 ≤500 条、不存原始错误）；**Agent / 高级规则**走 `RoutineTask`（`routines`：interval / event / 复杂 cron、条件与游标），`GET /routines` 投影含 `prompt`，界面同一张清单、同一个编辑器，复杂触发只读。**已知边界**：一次性提醒没有暂停（`enabled=false` 到点静默终止，UI 不显示该按钮）；暂停项不进默认 reminders 列表（手机端不传 `includePaused`），因此不推本地闹钟；编辑提醒会取消原任务并用同 `reminderId` 重排，下一次触发时间按规则归一化（与改时间同口径）；旧任务上线前没有执行历史；**手动新建固定「接着聊」**（reminders 落目标执事主会话），「每次新开」只在 Agent / 高级例行规则的编辑面里可用。**可见触发的技术头**：`[Scheduled run context]` 只给模型看，`scheduled-run-context.ts` 在 `session-transcript.ts` / `session-search.ts` 回读时剥掉。

### 6.1 运行时的起停（2026-11-07）

**谁持有进程**：桌面壳（`desktop/runtime.go` 的 `runtimeCtl`）。它是唯一的进程状态
持有者，服务不再只是"探不到就拉一个"——那个函数（`ensureService`）已经退役，因为它
不会记住 PID、也不会停。

- **接口**：`Shell.RuntimeStatus / StopRuntime / StartRuntime / RestartRuntime`，
  设置 → 本机 → 运行时那张卡在用。**页面不能自己干这件事**：它要停的就是自己的后端，
  停下去之后所有 `fetch` 都失败，连状态都问不出来。
- **四态**：`running / starting / stopped / failed`。`stopped`（用户停的）与
  `failed`（自己挂的）必须分开——界面上是两句话。
- **认人**：`stopped` 闩挡住的是**自动路径**（开窗、`watchService` 的失联重拉）；
  托盘的「重新连接」是人的明确要求，**越过闩**。没有这个区分，停完服务后托盘就再也救不回来。
- **以端口为准**：查 PID 先 `netstat` 找监听该端口的进程，查不到才回落到自己记的数——
  PID 会被系统回收，端口上那个才是现在真在服务的。
- **`taskkill` 带 `/T`**：`tsx` 是 loader，会再 fork 真正的服务进程；不带 `/T` 会留孤儿
  占着端口，下次启动直接 `EADDRINUSE`。
- **回滚**：`LIFEDIARY_SHELL_BINDINGS=off` 时整组 `Shell` 不挂，卡片退化成
  「仅桌面端可操作」。
- **托盘退出 = 停服务 + 退壳 / 只退壳（2026-11-20，2026-11-22 补轻出口）**：
  窗口 X 仍只隐藏（手机与提醒要靠服务）。托盘两个退出项：
  - **只退出壳（服务继续跑）**（2026-11-22 补）：置 `quitting` 后直接 `Quit`，
    `checkBeforeQuit` 整个跳过；服务（`DETACHED_PROCESS`）留在后台。补它的直接原因：
    壳 exe 被运行中的进程占着，重编必须先退壳，而停服务不是用户想付的代价。
  - **退出并停止服务**（2026-11-20）：把壳与服务一起收掉的唯一完整入口。顺序：查在飞单
    （`GET /api/v1/tickets`，非终态 = received / planning / planned / dispatching）→
    有就确认「会中断」→ `runtime.Stop()` → 放行 `Quit`；停不掉时弹「重试 / 仍然退出 /
    取消退出」，不静默留下活着的 node。原托盘「设置」项同日退役（页面内可进）。
  `LIFEDIARY_QUIT_STOP_SERVICE=off` 仍回到旧形态（「退出并停止服务」退化为只关壳）。
- **开机自启（2026-11-08 扫尾批 4b）**：设置 → 本机 → 运行时的「开机自启」开关走
  `Shell.OpenAtLogin / SetOpenAtLogin`（MyGo 写 HKCU Run，任务管理器可关）；自启的是**壳**，
  服务仍由壳拉起；`LIFEDIARY_SHELL_BINDINGS=off` 时状态读不到，开关键不渲染。
- **原生截图（2026-11-25，方案 `docs/设计方案/2026-11-25-原生截图工具（壳内框选与窗口吸附）.md`）**：
  加号 →「截图」在壳里走 `Shell.CaptureSnapshot`（`desktop/snapshot*.go`）：先 GDI 抓帧，再铺一张
  mygo 原生遮罩窗（不是第二个 WebView 页面）——拖动框选 / 单击吸附光标下的顶层窗口 / Esc·右键取消，
  截完内联 base64 进待发条，不落盘。v1 只覆盖鼠标所在显示器（跨屏一次截取明确不做）。
  - **回滚**：`LIFEDIARY_NATIVE_SNAPSHOT=off`（或 `false` / `0`）→ Capabilities 报 `nativeScreenshot=false`，
    页面退回 `getDisplayMedia`；浏览器 / 老壳（没有这个方法）同样回退。
  - **坐标口径**：Win32 一律物理像素（壳是 Per-Monitor-Aware V2），mygo 窗口一律 DIP；换算只在
    `snapshot_geom.go` 的 `dipToPx / pxToDip` 一处，scale 取光标所在显示器的 `ScaleFactor`。

方案 `docs/设计方案/2026-11-25-目标模式（参考ZCode与Codex）.md`，契约 `接口-端点4` §2.11「目标模式」，
落地记 `变更记录/2026-11-25-目标模式.md`。

- **与 D13 的关系（不变）**：目标模式**没有裁判轮**。完成由执行方自报（回复末行 `[[goal-done]]`），
  与例行任务 `[[routine-done]]` 同一口径；D13「自报即终局」与拒绝概念表「常驻 `/goal` 每空闲判一次」原样有效。
  目标模式不触发（`GOAL_MODE=false`）时完全不进入这条链路。
- **归属**：目标挂在执事上（`partners.current_goal` 文本 + `partner_goals` 一行状态），不是挂在会话上。
- **状态机**：`active / paused / budget_limited / done` + `reason`。新建 = `paused / not_started`（不自动开跑）；
  用户 Stop 中断目标轮 = `paused / stopped`；续跑轮零工具连击 3 次 = `paused / no_progress`；
  轮数或 token 上限到 = `budget_limited`；末行 `[[goal-done]]` = `done / self_report`；
  `[[goal-blocked: …]]` = `paused / blocked`。恢复必须显式（start / resume / reopen）。
- **结算顺序**（纯函数 `goal-settlement.ts`，每轮收尾一次，顺序固定）：
  ① 不是 `active` → 不结算；② 末行标记 → 落 done / paused，结束；③ 记账（`rounds_used +1`，
  `tokens_used` 加本轮用量，读不到就不加）；④ 轮数 / token 上限 → `budget_limited`，结束；
  ⑤ 零工具连击（只数续跑轮；有工具调用清零）→ 满 3 暂停，结束；⑥ 忙 / 有待批审批 → 不排续跑，状态不变；
  ⑦ 排一轮续跑。
- **续跑**：durable 任务 `lifediary.goal-continue` 挂在执事主会话的任务图上；醒来先对三样——进程启动号
  （跨进程一律作废）、token（`partner_goals.updated_at`）、状态——对不上即作废。模型执行照 `runPartnerTurn` 走，
  身份 `autonomous`（过 C2 审批），提示词只在这一轮的尾部、不进固定前缀。start / resume / reopen 立刻排一轮
  （延迟 0），之后每轮结算完排下一轮（间隔 3 秒）。重启不自动重放。
- **任务必须进注册表**：`GoalContinueTask` 登记在 `agent/lifecycle-harness.ts` 打开 Harness 时的 `tasks` 表里
  （与 `ReminderTask` / `RoutineTask` 同一张）。不进表的任务建得出来但"缺定义"，排上不会醒
  （2026-11-25 `goal-mode-probe` 实证）。以后新增 durable 任务都过这张表。
- **失败时不许连累别的**（2026-11-25 返工）：轮末结算 `settleGoalTurn` **保证不抛**，返回值只回答"目标模式是不是开着"，
  不表示结算成功——结算抛异常（库锁等）也返回 `true`，调用方照常剔掉末行标记、带上工具数与用量；失败的后果只是
  这一轮不记账、不排续跑，留一条 warn。否则标记会原样显示给主人。任务图外的三个 promise 都自己兜底：
  续跑轮（`runGoalContinuation`）reject 被吞、不影响进程；排续跑时执事会话打不开 = 没排上、状态不变；
  续跑任务提交失败 = 没排上、状态不变。三者都只记枚举 / id 前缀 / 错误消息前 120 字。
- **探针**：`pnpm --filter @lifediary/server goal`（真起服务 + 真 HTTP + faux 模型；2026-11-25 落地与同日返工各跑一次，34 项全过）。
  真模型才看得出的项（末行标记、Stop 暂停、首页主对话结算）不在这条探针里，见落地记的未验证项。
- **已知边界**：① 客户端断开后服务端跑完的那一轮不结算，下一次轮末再结算；② 总管的续跑轮跑在总管的
  执事主会话（`partner-chief`），首页主对话只结算、不承接续跑；③ 例行专线 / 副会话 / 群会话不结算；
  ④ 完成 = 模型自报，可能过早，靠「reopen」撤销，不设校验；⑤ 续跑醒来时会话忙或有待批审批 = 这一轮不跑、
  状态不变、也不重排——目标停在 `active` 但没人推，要等下一次轮末结算或主人点一次「继续」；
  ⑥ `[[goal-blocked: …]]` 里的说明只落 `reason=blocked`，不从回复里带给主人，界面上只有"等你介入才能继续"。
- **回滚**：`GOAL_MODE=false`（§6 接口文档）→ 不结算、不排续跑、动作端点 404、界面不出状态行；状态表保留。

- **ego lite 浏览器本体闭源**（2026-11-10 登记）：Citro Labs 的 Chromium 分支（MIT 的只是手册与文档仓库），数据留本地是官方口径。回滚：`.data/skills-state.json` 删 `ego-browser` 条目（或 `PUT /api/v1/agent/skills/ego-browser/enabled` false）= 下架；彻底移除 = 卸载 app + 删 `~/.agents/skills/ego-browser` 软链。
- **符号链接技能不上管理列表（agent 侧照常可用）**（2026-11-10 登记，ego-browser 实例暴露）：管理列表按 path-guard 挡"指向外部的符号链接"（skills-api.ts，链接目标内容可能是任意文件），所以 ego-browser 在设置页**看不到**；加载器无此闸，L1 索引与 `skill()` 照常。启停走 API / 状态文件，不走界面。统一口径（列表放行只读显示 vs 加载器同守卫）另立项再议。对照：agent-desktop 的手册是**真实目录**（非软链），不触发此闸，进管理列表。
- **电脑操作 = 本机 agent-desktop CLI，走 OS 无障碍树（L2）**（2026-11-10 登记）：Vercel Labs 开源（Apache-2.0），`npm i -g --allow-scripts=agent-desktop agent-desktop`（**必须 allow-scripts**，否则 postinstall 不跑、走 JS launcher 每次多 125ms）。agent 经既有 `bash` 工具跑 CLI：`snapshot` 读界面（控件报名字/角色/状态/ref）→ `click @ref` → 再 snapshot 验证；**不注册新工具，闸门口径零变化**。手册 = 官方 SKILL.md 整目录拷贝（`~/.agents/skills/agent-desktop/`，**真实目录**——与 ego 的软链不同，**进设置页管理列表**，可界面开关；description 折成单行以适配解析器，见下条）。平台指南不由我们维护：手册教 agent 跑 `agent-desktop skills get platform`，二进制自带版本对应指南。**覆盖边界如实**：自绘 UI 的应用（如网易云音乐，2026-11-10 实测 ref_count=0）读不到控件，只能 `screenshot` 兜底或不做；UAC 弹窗/锁屏/管理员窗口（UIPI）/Session 0 一律不行；`key-down`/`mouse-down` 按住类全平台拒。回滚：技能启停（API/界面/删 state 条目）= 下架；彻底移除 = `npm rm -g agent-desktop` + 删 `~/.agents/skills/agent-desktop/`。方案与 V1~V4 实测：`docs/设计方案/2026-11-10-方案（agent-desktop 电脑操作接入）.md`。
- **桌面内容一律不可信；快照与截图含用户桌面隐私**（2026-11-10 登记，agent-desktop 批）：窗口标题/文档名/通知里可能携带提示词注入，**只能当数据不能当指令**（同 ego lite 口径）；快照/截图会拍到别的窗口内容，剪贴板命令能读用户剪贴板——桌面内容只进会话流，服务端日志仍只记条数/耗时/枚举。
- **agent 与用户共桌：默认语义操作不动鼠标不抢焦点，`--headed` 才动真光标**（2026-11-10 登记，agent-desktop 批）：官方设计默认 headless 语义操作（UIA 直达，窗口可在后台）；`--headed`（右键/双击/移动光标类必需）会占用物理鼠标键盘——用户在场时避免大范围 headed 操作，多个 agent 并发跑 headed 会互相抢前台。
- **技能 frontmatter 解析支持多行块标量（2026-11-12 落地，改写 2026-11-10 的"刻意不做"行）**：官方技能用目录形态 `<名>/SKILL.md` + `description: >` 多行块，当初 12 条受影响（agent-desktop 已手工折单行，余 11 条占名不生效）。`skills.ts` 的 `parseFrontmatter` 现认 `>` / `>-` / `|` / `|-` 四个块标量（后续行按缩进归属，`>` 折叠换行、`|` 保留换行、空行算段落换行）；单行 `key: value` 逐字节不变，解析失败仍走"valid=false 占名"老路。**仍刻意不做完整 YAML**：锚点 / 别名 / 嵌套 / 引号转义不认，`>+` / `|2` 等变体按单行值落下、由"裸符号守卫"挡成无摘要（2026-11-12 守卫放宽到含数字缩进位），tab 缩进未处理未测——description 用不到的就不在这里长出半成品 YAML。修复后真实目录实测：128 条扫描全 valid / 0 invalid（技能索引内容因此变化，缓存前缀资产口径见 AGENTS.md；工具描述与注册顺序未动）。
- **技能分类建议是快照不是仲裁；评估走总管对话不走后端**（2026-11-10 批 30/30b 登记）：Agent 评估存 `.data/skills-advice.json`（`SKILL_ADVICE=false` 回滚），**建议归建议、开关归开关**（`skills-state.json` 才是启停事实源），PUT 采纳的名字必须来自快照（防伪造建议开技能）。**评估流程**（批 30b，用户拍板）：设置页按钮 → GET advice 拿预填提示词 → 前端跳总管对话预填（不自动发送）→ 总管在**用户自己选的模型**上逐条评估 → 调 `save_skill_advice` 工具写快照 → 用户回设置页采纳。v1 的"后端候选链盲扫 provider×model"被用户否掉：不知道会撞上哪个模型，能力低计费高的风险不可控。**通用模式**（用户点名，后续批次照此办理）："需要模型决定"的功能（如定时任务模块）一律做成"界面预填提示词 → 引导 Agent 对话 → 结果经受闸门的工具落盘"，而不是后端自起模型调用。 子代理（派活工人/任务专线）现状就是主对话模型（`taskModelRef` 从当前模型派生，无独立子代理模型目录），无"子代理用了贵模型"风险。
- **回复里的交互卡 = 沙箱 iframe，模型产的 HTML 按不可信处理**（2026-11-21 落地，方案 `docs/设计方案/2026-11-21-表格渲染与交互消息/方案.md`）：助手回复里闭合的 ` ```html ` 围栏渲染成内联交互卡（无工具条直渲染，用户拍板），跑在 `sandbox="allow-scripts"`、`referrerPolicy="no-referrer"` 的 iframe 里——**无 same-origin，拿不到 cookie / 存储 / 父页 DOM，不开表单与弹窗**（ZCode 同款口径，app.asar 实读核实）；不拦外链图片/字体（本地单人服务）。渲染只产占位符，挂载与报高收在 `web/html-cards.js`；流式 reconciler 对同 srcdoc 的卡原地保活。已知边界：**手机端不渲染卡**（消息还是 markdown 文本，契约没动，手机显示代码块）；开关 `CHAT_HTML_CARDS` 关掉后已挂出的卡到刷新为止（渲染期读模块内默认值，开关晚到只影响之后的消息）；不做 HTML 白名单/消毒（沙箱已隔离，消毒反而让人误以为卡里的 HTML 是"安全的"）；高度自适应到 72% 视口上限，超出内部滚动。同日表格渲染换 C 卡片版（圆角卡 + 发丝线 + 短格不折行 + 数字列自动右对齐），并修两个 GFM 兼容 bug：单横线分隔行 `:-:` 整表塌段落、`:---` 左对齐误解析成右对齐。

- **工具超时全局一刀切**（2026-11-24 工具异常处理 M0–M2 登记）：不提供全局单一大超时（会误杀长构建、拖死证据检索），策略只按工具 / 能力组配；没有真实等待面的工具（本地读、同步扫描、写文件、必须人答）锁定不给超时——配了也不会按预期生效。翻案条件：出现"某个工具卡住整轮"且该工具有中止点的具体案例。
- **把记忆检索转后台**（2026-11-24 登记）：`recall` 外部槽与每轮轻召回是当轮回答的证据，超时只能失败 / 静默降级 / 更短预算；配置层直接拒绝 `background`。只有出现"检索慢但结果不参与当轮"的新形态时才另立。
- **任务中心伪票据承载通用后台命令**（2026-11-24 登记）：任务中心建在 chancellor 的票据模型上（租约 / 车道 / 死信 / 回执 / 取消），把一条 bash 命令塞进去会让这些语义失真；后台结果复用 `bg-jobs` 注册表，任务中心最多做只读入口（二期，未做）。
