# 接口文档（lifediary-harness）

> 状态：**2026-10-29 按 TS 实现重写**（本仓库现行实现 = `ts/`，Node + Hono + SSE，内核 `pi-durable@1.4.0`）。
> 旧的 Java/Spring 版文档（P1 2026-10-25：JWT、backend 同密钥、无状态、先扣额、`/signal/session`）**已全部作废**，
> 与实现一并退役。契约的唯一事实源 = `ts/apps/server/src/` 下的路由代码 + `ts/packages/shared/src/index.ts`。
> 客户端 = 独立原生 Android 工程 `<lifediary 手机仓>`（手机只连本服务，没有第二个服务端）。

## 0. 通用

- **基址**：`http://<host>:39847`（`PORT` 可改）。
- **响应形态**：非流式端点 = **裸 JSON**（**不是** backend 时代的 `{code,message,data}` 信封，客户端别按信封解析）；
  流式端点 = **SSE**，每帧只有 `data: <json>` 一行（**不另设 `event:` 行**，事件类型以 JSON 的 `type` 字段为准）。
- **CORS**：当前 `origin: *`、`allowHeaders` = `Content-Type, Authorization, X-Conversation-Id, X-Task, Accept`
  （`ts/apps/server/src/index.ts:171`；M0 本机/局域网调试用；**上公网前必须收紧**）。
  浏览器 / WebView 预检所需的 `X-Conversation-Id` / `X-Task` 已包含，不再被预检拦掉（2026-11-07 复核）。
- **未捕获错误（2026-11-07）**：任何未被端点自己 `try/catch` 的异常统一回
  `500` + `{ "error": "internal_error", "message": "服务端内部错误，详见服务端日志" }`。
  细节（message / stack）**只进服务端日志**，不下发客户端（可能带上游地址与本地路径）;
  日志同时追加到 `.data/server-errors.log`（`AGENT_ERROR_LOG` 可改），因为桌面壳拉起进程时
  stdout/stderr 无人接收。**注意**：这条口径不改变各端点自己定义好的错误码
  （如 `503 export_failed`、`500 task_render_failed`），那些仍然是端点内显式返回的。

## 1. 鉴权

- 所有 `/api/v1/*` 需 `Authorization: Bearer <AGENT_TOKEN>`（共享令牌）。
- **本机页面自动放行（2026-11-03）**：从 loopback 打开 `/` 时，服务端下发一枚 `lifediary_local` cookie
  （HttpOnly、SameSite=Strict）；来自 loopback 且带这枚 cookie 的请求直通。桌面壳与本机浏览器因此不再手填令牌。
  curl / 探针 / 其他本地脚本没有这枚 cookie，仍按下面的令牌规则处理。
  **cookie 密钥落盘（2026-11-05）**：密钥首用时写 `.data/local-secret`（`AGENT_LOCAL_SECRET_PATH` 可改），
  重启复用同一枚——后端重启不再把一直开着的页面踢回令牌框。安全边界没变宽：能读这个文件的本机进程
  本来就读得到 `.env` 里的 `AGENT_TOKEN`。文件缺失/损坏时下次访问自动补新枚并覆盖坏值；
  落盘失败退回旧口径（进程内随机，重启后要重填令牌）。
- 失败一律 **HTTP 403 + 空响应体**（与旧 Java 版行为一致，客户端不用区分是谁拒绝的）。
- **`AGENT_TOKEN` 未配置时**：只放行 loopback（`127.0.0.1` / `::1`），其余一律 403（fail-closed，不裸奔）。
- 令牌比较用定长比较（避免计时侧信道）。**没有用户身份**——它是密码，不是通行证（单用户自用）。

## 2. 端点

### 2.1 `POST /api/v1/agent/chat` —— 对话（SSE，自有协议）

请求：

```json
{ "conversationId": "uuid（可选，不带=新建）", "messages": [{ "role": "user", "content": "…" }], "requestId": "可选，重试幂等", "chatKind": "chief | worker（可选）", "whenBusy": "steer | followUp（可选）" }
```

- `messages`：**实际只取最后一条 user**；更早的历史在服务端（durable 的会话里）。
- **`content`（2026-11-08 扫尾批 4a，附件/图片）**：从 `string` 扩成 **union**
  `string | ContentPart[]`，`ContentPart = {type:"text",text} | {type:"image",mimeType,data}`，
  `data` 是**裸 base64**（不带 `data:` 前缀，形状对齐内核 pi-ai 的 `ImageContent`）。
  - 纯字符串的老调用方（手机、OpenAI 兼容层、旧脚本）**逐字节不变**；
  - 服务端把文本 parts 用 `\n` 拼成 `text`（与 pi-ai `contentText` 同口径）、图片 parts 原样
    随 `submit` 下传；**纯图无文本允许**；
  - 限制：**单图解码后 ≤8MB、单条 ≤4 张**，超限 `400 {"error":"bad_request","message":"…"}`；
  - 回滚 `AGENT_ATTACHMENTS=false`：分段请求 → `400 {"error":"attachments_disabled","message":"…"}`，
    纯字符串照常（§6）；
  - **不做 blob 存储**：base64 直接进 durable 条目（会话库体积增长是登记过的已知边界）。
    图片是**输入侧**，不进任何 SSE 帧（帧结构本批未动）。
- `conversationId`：**必须是服务端发过的 id**；不认识的 id → `404 {"error":"unknown_conversation"}`（不会偷偷新建）。
- `requestId`：同一条用户消息重发时带同一个值 → 认成同一轮，不重复扣 token、不重复写记忆。
- **`whenBusy`（2026-11-07 消息即引导，纯增量）**：这一轮正在跑时，这句话怎么进。
  - `followUp`（缺省，等于改动前行为）：排到本轮结束，作为下一轮；
  - `steer`：请求插进**当前这一轮**，模型在下一个边界（工具轮之后 / 收尾前）就能看到。
  - 它是**请求不是保证**：内核按"下一次边界"消费，没赶上就是下一轮的第一句。服务端会先发一帧
    `notice` 说明实际落点（见下表），不把"受理"说成"已插入"。不带该字段的老客户端零改动。
- **`chatKind`（2026-11-06 侧栏调整 B2，纯增量）**：新会话种类，`chief` / `worker`，**只在不带 `conversationId` 时采用**；
  缺省仍 `chief`（手机与旧调用方零改动）。身份落在 durable 的 `lifediary.chat-kinds`（内部会话 id → 种类）：
  - 续话时带**不匹配**的值 → `400 {"error":"chat_kind_mismatch"}`，不隐式改身份；
  - 续话时不带 → 沿用已存种类；
  - 执事的 canonical 会话种类由 `partner_session_links` 判定为 `partner`，客户端不能自报；
  - `WORKER_CHAT_ENABLED=false` 时**新建** worker → `400 {"error":"worker_chat_disabled"}`；
    已落盘的 worker 保持原身份（不会被重解释成总管），照常可续话。

  身份提示词也按种类分流（2026-11-06 B2）：`worker` 用独立的普通任务助手提示，**不读总管 SOUL**；
  执事 canonical 会话不注入总管 persona（身份来自其 `configure` instructions）；无记录旧会话仍走总管 SOUL。
  工具闸门 / 审批 / 工作区边界不因种类变化。

响应（SSE，`data:` 行，JSON 依次为）：

所有事件帧都可带 **`seq`**（2026-11-04，SSE seq 与断点重放方案）：**会话内**从 1 单调递增的事件序号，
服务端先落库再外发。断线重连后带 `sinceSeq`（本地已收最大 seq）到 §2.2 的 `/messages` 精确补缺帧。
`AGENT_SSE_SEQ=off` 回滚后帧不带 seq，客户端按"没有重放可用"对待。老客户端忽略该字段，行为不变。

| type | 字段 | 说明 |
|---|---|---|
| `start` | `id`, `conversationId` | 首帧；**客户端必须存下 `conversationId`**（之后回读/停止都用它） |
| `thinking` | `text` | 思考正文**增量**（2026-11-04 批次一，deep 档才有内容）。客户端累计成段，折叠展示；老客户端忽略 |
| `delta` | `text` | 文本增量 |
| `progress` | `phase` | `thinking` / `working`：这一轮在想还是在动手 |
| `tool` | `name`, `status`, `label?`, `ok?`, `output?`, `args?` | 工具调用起止；start / end 成对，客户端按 `name` 归并 |
| `delegate` | `ticketId`, `domain`, `phase`, `done`, `total`, `current`, `message?`, `project?`, `lastAction?`, `lastHeartbeat?`, `waitingOn?` | 派单进度与终态（2026-11-03）。`phase` 见下方 `DelegationPhase`；`done/total` 是单内已办件数/总件数。2026-11-04 补齐：`project` 项目名、`lastAction` 最近动作、`lastHeartbeat` 事件心跳（ISO，同一份也落进 `ticket.json`，§2.9）、`waitingOn` 卡在哪个文件租约 |
| `attention` | `ticketId`, `domain`, `kind`, `question` | 任务单要人回答；`kind` = `need_input` / `need_decision` / `need_action` |
| `approval` | `callId`, `tool`, `args`, `deadlineAt` | **写类工具要你确认**（2026-11-04 批次二；审批档不是 `none` 时才发：`ask-all` 写类全问、`ask-critical` 只问高危清单，§2.18）。`args` 是工具参数 JSON（截断 1200 字符）；`deadlineAt` 是 ISO 截止时间，blocking 形态下过了按拒绝处理（fail-closed）。答复走 `POST /api/v1/agent/approvals/:callId`（§2.5）。**手机不进这条聊天流**：手机不进 SSE 聊天流，审批走全局待办 `GET /api/v1/agent/approvals`（不带 `conversationId`）轮询（建议 20–30 秒，或拉任务页时顺带），答复用同一个 POST，与传输协议无关。`lifediary_approval` 非标字段保留但手机不再依赖；老客户端按 `type` 忽略即可 |
| `notice` | `text`, `steer?` | 系统提示行（2026-11-07 消息即引导）：`whenBusy=steer` 的诚实回执（"下一个边界带上它" / "这一轮刚好收尾，已作为新的一轮开始"）。不是模型正文，也不是错误；客户端渲染成中性一行即可，老客户端按 `type` 忽略。`steer`（2026-11-07 补，纯增量）是机器可读落点：`inserted` = 插进了正在跑的这轮，正文由原来那条流继续画；`new-turn` = 刚好收尾、成了新的一轮——这条短连接就是唯一正文来源，客户端只收回执的话必须在轮收尾后回读一次 `GET .../messages`，否则新一轮的回答没人画。判断只认 `steer`，不要匹配 `text` 文案。2026-11-10 批 13 起，执事的 `report_progress` 也发同一形状的 `notice`（`text` = `【进度】…`，≤200 字，无 `steer`）；不落盘，没开流就收不到 |
| `done` | `id`, `finishReason`, `usage?` | `stop` / `length` / `aborted` / `error`（表示"这条流怎么结束的"，不是"这一轮怎么结束的"）。`usage`（2026-11-04 批次一）= 本轮最后一条 assistant 消息的 token 用量 `{input, output, cacheRead}`，faux/mock 也给（数字仅供链路验证） |
| `error` | `message` | 例如工具回合撞上限（文案见 §4） |

`DelegationPhase`（对外的"在等谁"）：`accepted` / `planning` / `running` / `reviewing` / `done` / `needs_you` / `failed` / `aborted`。

- `delegate` 的进度帧**只在拿到 `ticketId` 之后才发**（前端靠它归并），所以第一帧一定是 `accepted` 或 `planning`。
- 终态帧（`done` / `needs_you` / `failed` / `aborted`）之后如果还有一条问题，会再发一个 `attention`。
- `approval` 的答复等待**不计入工具回合上限**；并行工具各自有独立的 `callId`，互不阻塞。
- 老客户端按 `type` 分发，认不出的类型直接忽略即可（这些都是**纯增量**事件）。

**关键语义：客户端断开 ≠ 取消。** 那一轮会在服务端跑完并落库；记忆抽取挂在"这一轮真正结束"上，不会因为关界面而漏写。
真要停请用 §2.3。

未配置模型（`LLM_API_KEY` 缺失）时：返回 mock 流（逐字回显 + 固定文案），**不建会话、不写库**。

### 2.2 `GET /api/v1/agent/chat/:conversationId/messages?limit=50&sinceSeq=0`

回读该会话的历史（每轮的正文 + 该轮的工作步骤）：

```json
{ "conversationId": "…", "messages": [ { "role": "user", "text": "…", "at": 1761234567890 } ], "chatKind": "chief" }
```

- 存在理由：一轮可以在客户端关掉之后继续跑完，客户端下次打开必须能把结果拉回来。
- **`id` / `images`（2026-11-08 扫尾批 4a，纯增量，只出现在 user 消息上）**：
  - `id` 是**可寻址 messageId**（uuid 形状，编辑重发用它定位）；**不是** durable 内部自增条目 id——
    由 `(会话 uuid, 条目 id)` 哈希得到（`agent.ts` 的 `messageIdOf`），离开会话 id 没有意义；
  - `images: [{mimeType, data}]` 是这条用户消息带的图片（base64 原样回读）；文字仍走 `text`，
    **纯图消息 `text` 可能是空串**；
  - 老客户端忽略这两个字段即可；手机端现行只读 `role`/`text`/`at`，零改动。
- **`steps` / `workMs`（2026-11-07，纯增量）**：`assistant` 条目上多这两个字段，回答"这一轮具体做了什么"。
  流式期间的 `tool` 事件只在当轮界面上活过一次，刷新/切会话就没了；而步骤本来就躺在 durable 里
  （`pi.assistant` 的 `toolCall` + `pi.tool-result`），服务端按调用顺序配成对下发，**没有新增存储**。

  ```json
  {
    "role": "assistant", "text": "…", "at": 1761234567890,
    "workMs": 41230,
    "steps": [
      { "name": "edit", "label": "ts/apps/server/web/app.js", "args": "{\"path\":\"…\"}",
        "output": "Successfully replaced 2 block(s) in …", "diff": "-12 +12 …", "ok": true, "ms": 18 },
      { "name": "bash", "label": "pnpm typecheck", "ok": false, "output": "error TS2339…", "ms": 9042 }
    ]
  }
  ```

  - 字段口径与 SSE 的 `tool` 事件一致（`args` 1200 字符、`output` 2000 字符，均截断后带"还有 N 字符"），
    「现场看到的」与「回头翻到的」是同一份事实。`diff` 只有 `edit` 这类带 `details.diff` 的工具才有。
  - `ok=false` 覆盖两种情形：工具真的失败，以及**这一轮被中断、始终没等到结果**的调用——
    后者不能画成成功（判据是"有没有配到 `tool-result`"，不是"有没有输出"）。
  - 只挂在**带正文的那条回答**上；中间的工具回合（正文为空）不会变成独立的"回答"。
    一轮里没有工具调用 → 不带这两个字段。被中断且始终没等到回答的那一轮没有挂靠点，历史里不回放它的步骤。
  - `workMs` = 提问时间 → 收尾时间（`assistant.timestamp + durationMs`）；读不到 `durationMs` 的旧记录
    退回 `timestamp`，可能偏小，不编数。
  - 手机端：手工解析 `messages` 只取 `role` / `text` / `at`，Kotlin 零改动。
- 未配置模型 → `{ "messages": [] }`；未知 id → 404。
- **`chatKind`（2026-11-06 B2，纯增量）**：`chief` / `worker` / `partner`。续话/刷新时前端据此恢复身份，
  不按 id 猜。旧客户端忽略该字段即可。
- **`sinceSeq`（2026-11-04，SSE seq 与断点重放方案，可选）**：带上后响应多一个 `events` 数组——
  该会话落库事件里 seq > `sinceSeq` 的部分（完整 `ChatEvent` 帧，含 seq），用于断线补帧；
  不带 `sinceSeq` 时无 `events` 字段，行为与改动前完全一致。落库窗口每会话只留最近 500 条，
  所以响应带 `fromSeq`（重放第一条的真实 seq）：若 `fromSeq > sinceSeq + 1`，说明窗口已滑过，
  客户端不能只补帧，要按 `messages` 全量重建。`AGENT_SSE_SEQ=off` 时 `sinceSeq` 被忽略。
- 手机端：契约纯增量，Kotlin 零改动（适配说明加一行"可忽略 `seq` / `events`"）。

### 2.2.1 `GET /api/v1/agent/chat/:conversationId/export?format=handoff&limit=30` —— 会话导出「接续文件」（2026-11-10 批 20 §一）

把一个会话导出成**能直接粘给任何 AI 继续聊**的 markdown（不是数据备份）。响应体是文件本身：

- `Content-Type: text/markdown; charset=utf-8`；`Content-Disposition: attachment; filename="lifediary-handoff-<会话 uuid 前 8 位>.md"`；
- **一次性响应，不落服务端磁盘**（隐私口径）：不写 `.data`、不排队、不加缓存（`Cache-Control: no-store`），
  请求结束即丢。要留存由客户端自己保存；
- 文件四块：角色说明（`chief` / `worker` / `partner` 各一句）+ 读取说明（"可以直接粘给任何 AI 继续聊"）+
  记忆摘要 + 最近 N 轮原文。标题取 `chat-meta.json` 的改名表，没有标题就写「会话 <前 8 位>」；
- **记忆摘要**：该会话**作用域**的 `preference` + `experience`，最多 20 条（主对话 = `global`，
  执事会话 = `partner:<uuid>`，与偏好落点同口径 `preferenceScopeOf`）。不导 `session:` 原始沉淀；
- **最近 N 轮**：`limit` 默认 30、取值 1–200（非整数 / 越界 → `400`），一轮从一条 user 消息起算，
  回答与工作步骤跟着走，不会把某轮回答切一半。更早的消息不进文件。
- 回滚：`CHAT_EXPORT_HANDOFF=false` → 端点 `404`（未启用，与其它能力端点同口径）。
- 错误：`format` 不是 `handoff` → `400`；未知会话 → `404`；未配置模型 → `503 {"ok":false,"reason":"llm_not_configured"}`。

**状态如实（三条口径，写进文案与产品说明）**：

1. **部分可读要标注原因，不冒充完整**：被 `limit` 截断时文里写「更早的 N 条消息未包含」；
   记忆未启用 / 读取失败 / 池子为空各有明确一句，不静默省略。
2. **导出成功 ≠ 对方已接收**：文件头明写这一句；服务端不知道也不追踪对方是否收到。
3. **默认不保存正文**：导出是一次性文件，服务端不落盘（见上）；这不影响服务端本来就会持久化的会话历史。

**探针**：`pnpm --filter @lifediary/server http` §28——200 + markdown + 附件头、四块文案、
`limit=2` 只含 2 轮、坏 `format` / 坏 `limit` / 未知会话各自的状态码。

### 2.2.2 `GET /api/v1/agent/chat/:conversationId/context?aroundIndex=<n>&radius=5` —— 旧会话定点找回（2026-11-10 批 20 §四）

从旧会话的某一处往回看（只做后端能力，不做界面、不做 fork）。

- **`aroundIndex` 是消息数组下标（从 0 开始）**，不是 seq——transcript 没有 seq 字段，不为这个改内核。
  必填；缺 / 负数 / 非整数 → `400`；
- `radius` 默认 5、取值 0–50（前后各取几条）；越界 / 非整数 → `400`；
- 返回：

```json
{
  "conversationId": "…", "total": 11, "aroundIndex": 5, "radius": 1,
  "from": 4, "to": 6,
  "messages": [ { "role": "user", "text": "…", "at": 1761234567890, "index": 4, "id": "…" } ]
}
```

  - `total` = 该会话消息总数，客户端据此知道边界；`from` / `to` 是窗口两端的**绝对下标**（含）；
  - 每条带 `index`（绝对下标）；user 消息另带可寻址 `id`（与 §2.2 同源）；
  - **不回放图片与工作步骤**（`images` / `steps` 不在这里出现）；纯图消息的 `text` 可能是空串；
- `aroundIndex >= total` → `400 {"error":"bad_request","message":"aroundIndex 超出范围（共 N 条）","total":N}`；
  会话为空 → 200，`total:0`、`from:0`、`to:-1`、`messages:[]`；
- **与同路径旧端点共存**：不带 `aroundIndex` 时仍是 §2.5 的「上下文占用」`{used, window}`（旧客户端零影响）；
  带 `aroundIndex` 才走本语义。
- 回滚：`CHAT_CONTEXT_LOOKUP=false` → **带 `aroundIndex`** 的请求 `404`；旧「上下文占用」不受影响。

**探针**：`pnpm --filter @lifediary/server http` §28——`total` 与 §2.2 一致、窗口两端与绝对下标、
越界带 `total`、`radius` / `aroundIndex` 非法各自 400。

### 2.2.3 `GET /api/v1/agent/chat/:conversationId/injections` —— 注入审计（2026-11-10 批 26b §二）

返回注入框架**当前接管**的注入清单，**只回元数据、不回正文**：

```json
[ { "id": "injection_guard", "source": "injection_guard", "scope": "session", "length": 142 } ]
```

- 字段固定四个：`id` / `source`（来源标识）/ `scope`（`session|once|turn`）/ `length`（正文字符数）；
  **没有 `text`，也没有任何正文片段** —— 审计端点不会泄露提示词实文。
- 批 A 只接管了 `injection_guard` 一个（`agent/injection.ts`），所以数组至多一行；
  `AGENT_INJECTION_GUARD` 关时该行也不列（返回 `[]`）。
- `:conversationId` 只作上下文：批 A 的注入是框架级静态清单，不按会话变化，
  因此不解析 durable 会话、不依赖 LLM 配置、不校验会话是否存在（诊断端点，不是会话数据接口）。
- 回滚：`AGENT_INJECTION_AUDIT=false`（§6，默认开）→ 端点 `404`。
- 逐字节约束：接管后 `injection_guard` 的正文与在 `sections` 数组里的位置与改造前完全一致
  （硬标准由 `src/agent/injection.test.ts` 钉住：`collectInjections([guardProvider], ctx).system[0].text === INJECTION_GUARD`）。

**探针**：`pnpm --filter @lifediary/server http` §4.5——200、只一行、形状齐、无正文。

### 2.3 `POST /api/v1/agent/chat/:conversationId/stop`

人工停止当前这一轮（走 `abort()`：排队的输入撤回、当前任务撤销）。之后再说一句话就是新一轮。
`{"ok":true,"conversationId":"…"}`；未配置模型 → `503 {"ok":false,"reason":"llm_not_configured"}`。

### 2.3.1 `POST /api/v1/agent/chat/:conversationId/say` —— 让助手说一句（2026-11-01）

手机端回顾页的钩子问题（"新版本装好之后的回读，结果跟预期一样吗？"）本来就是**助手要问的话**。
点卡片应该由助手说出来、然后等用户接，而不是塞进用户输入框（自问自答）。

- 请求 `{"text":"…"}`（必填，空 → `400 {"error":"bad_request"}`）；成功 `201 {"ok":true,"conversationId":"…"}`；
- **不调模型**：只在会话里追加一条 `pi.assistant` entry（走 `submit` 的 write，带 `model` 所以也进模型上下文，
  以后再聊时它知道自己问过这句）；会话忙时由 durable 排队到下一个边界落地，不打断正在进行的一轮；
- 之后 `GET .../messages` 就能读到这条（`role: "assistant"`）；
- 未配置模型 → `503`；未知会话 → `404`。

**探针**：`pnpm --filter @lifediary/server http` 里补一段——`POST /say` 后立刻回读，断言最后一条是 `assistant` 且文本一致。

### 2.3.2 `POST /api/v1/agent/chat/:conversationId/edit` —— 编辑重发（2026-11-08 扫尾批 4a）

改一句话并重说。语义决策见 `docs/设计方案/2026-11-08-扫尾批4方案（附件·编辑重发·壳发布）.md` §二：
内核 append-only、没有 truncate/edit，所以**不是就地改写**，而是
**fork 到那条消息之前 + 在新会话里提交新文本**。老会话完整保留（列表里会多一条分叉前的
旧会话，是方案登记的已知边界；不做删除）。

请求：

```json
{ "messageId": "GET .../messages 里 user 消息的 id", "text": "改过的话" }
```

- 校验：`messageId` 属于本会话且是 user 消息；`text` 去空白后非空。
- 分叉点：目标条目的**前一条**（fork 的 `at` 含该条目）；编辑会话第一条时没有"之前"，
  按同样形态（同模型、同种类）开一个空会话。
- 新会话的提交走 `chatStream` 主链路（SSE/用量/记忆全继承），在服务端后台跑完并落库；
  客户端拿到 id 后 `GET .../messages` 回读即可（与"关掉界面它照样跑完"同一语义）。
- 会话在跑 → `409 {"error":"conversation_busy"}`（与插话同口径，不排队）；消息不属于本会话 /
  不是 user → `400 {"error":"message_not_found"}`；未知会话 → 404；未配置模型 → 503。
- 回滚 `AGENT_EDIT_RESEND=false` → 端点 **404**（未启用，与其它能力端点同口径；§6）。
- 前端（web）：最后一条 user 消息 hover「编辑」→ 行内输入框 → 提交 → 用返回的新 id
  走 `openConversation()` 切换；更早的历史消息不提供编辑（方案登记的刻意没有）。
  现场刚发出的消息没有 messageId（SSE 契约未动），点编辑时按"从末尾对齐"拉一次历史补齐。

成功：`202 {"ok":true,"conversationId":"<新 uuid>"}`。

**探针**：`pnpm --filter @lifediary/server http` §21/§22——老会话完好、新会话 id 不同、
分叉点前历史完整、新文本在最末、跑着编辑 409、开关关闭 404。

### 2.4 `POST /api/v1/llm/chat/completions` —— OpenAI 兼容层

给"已经在说 OpenAI 协议"的客户端（现有手机 App）用。**分三条路**（2026-10-29 按 `system` 分流，2026-10-30 增 `X-Task` 任务通道）：

- 请求体：OpenAI Chat Completions 原样 JSON；`stream: true` 时按 OpenAI chunk 形状逐块回写，最后补 `data: [DONE]`。
- 非流式：返回标准 `chat.completion` 对象（**无 `usage`**；Agent 路径 `finish_reason` 恒 `stop`）。
- 错误：`400`（messages 空/无可用内容）、`503`（服务端未配 `LLM_API_KEY`；**流式也回 503**）、`502`（仅非流式，上游失败）。

#### 2.4.1 两条路径的分流（客户端必须知道；2026-10-31 直通已删除）

| 请求特征 | 路径 | 行为 |
|---|---|---|
| **带 `X-Task`** | **任务**（2026-10-30） | 服务端按任务名渲染模板 → 走 **Agent 会话**（建会话、落库、可回读）；**不判快/深档**，一律深档 + 客户端采样参数；`system` 被忽略；详见 §2.4.4 |
| **有非空 `system`** | **400 拒绝**（2026-10-31 直通已删除） | `400 system_prompt_not_supported`。直通分支（整套 system 原样转发、不建会话）已删除：生产端 12 个任务全部走任务通道、聊天从不带 `system`，它已无调用方。**故意不静默降级**——降级会让旧客户端的模板被当普通消息丢掉，产出看着成功、其实残废 |
| **没有 `task`、没有 `system`** | **聊天** | durable 会话：历史在服务端、有记忆与工具；**只取最后一条 `user`** 作为本轮输入；`model`/`temperature`/`max_tokens`/`response_format`/`reasoning_effort` **全部忽略**（归服务端配置，模型级 `maxTokens`）；会话 id 优先 `X-Conversation-Id`，否则"首条 user 内容" sha256 前 32 位（`oa-<hash>`）；**未见过的 id 直接新建同 id 会话**（不返回 404，与 §2.1 自有端点语义不同） |

**Agent 路径的思考强度档（2026-11-04 起替代快/深两档；方案见 `docs/设计方案/2026-11-04-思考强度档位.md`）**：
`Conversation.configure({ model })` 支持**会话中途换模型**，所以档位是**每轮**决定的，不是开局锁死：

| 来源 | 优先级 | 规则 |
|---|---|---|
| 请求头 `X-Mode: off\|low\|medium\|high` | 最高 | 说了就听（当轮生效）；旧值别名 `fast`→`off`、`deep`→`high`；越界档位（该模型未声明）按支持域落回 ≤ 该档的最高档（与 §2.8 换模型回退同规，2026-11-04 实施补充） |
| 已按 D3 切过非 off | 次高 | 保持切后的档（切一次就保持，不中途降档） |
| `JEV_ROUTE=gate` | 中 | 问 Jev（`deep_think` → `high`；`reply_direct` → `off`；confidence < 0.6 保守 `high`）；超时 `JEV_TIMEOUT_MS`（默认 1200）→ 直接 `off` |
| 默认 | 最低 | **off**（思考关变体，首字 0.8~0.9s） |

**档位 = 同模型 + 思考变体（2026-11-04 档位方案 D1/D3，替代 2026-10-31 的两变体）**：档位不靠换模型
（换模型 = 上游缓存清零），而是**同一模型的四条思考变体**
（派生模型 `#think-off` / `#think-low` / `#think-medium` / `#think-high`；旧后缀 `#think-on` 读兼容 = `high`）：
`off → enable_thinking:false`；`low / medium / high → reasoning_effort:<档>`。全部经 `samplingParams` 最后合并注入，
`model` 字段盖回真实模型名。**档位按模型支持域校验**：providers.json 每模型可选 `thinkingLevels`
（缺省 `["off","low","high"]`；`medium` 对 glm-5.3 实测 400，故只对声明支持的模型开放，见 §2.8）。
传未声明档位 → `400 bad_request`。换模型时当前档不在新模型支持域内 → 自动落回支持域内 **≤ 当前档的最高档**（`off` 兜底）。
两条变体链头块不同，缓存互不命中 —— 切档 = 当前前缀整段重算，所以默认**按会话定档、中途不切**。

**首次工具调用切一次（D3，2026-11-04 起目标档 = `AGENT_THINK_TOOL_LEVEL`，默认 `low`）**：模型发起第一次工具调用时（`beforeTool`），服务端看该会话
**上一轮的 `usage.input`**（D3a：客户端不知道前缀大小，harness 的 usage 是唯一可靠来源）：
`< 4000`（`AGENT_THINK_TOKEN_LIMIT` 可调）→ 切到目标档并保持；`≥ 4000` → 不切（长会话切一次就是整段重算）；
首轮无 usage → 视为短会话。`AGENT_THINK_ON_TOOL=off` 是总开关。
实测（2026-10-31，默认 deepseek-v4.1-flash）：聊天第 1 轮 2.31s（冷，思考关）→ 第 2 轮 1.20s（命中 1536）→ 首次调工具触发切思考（日志「首次工具调用 → 思考开（prompt≈126 < 4000）」）。

**`POST /api/v1/agent/chat/:conversationId/mode`（2026-11-04 登记进契约）**：body
`{ "thinking": "off"|"low"|"medium"|"high" }`，旧 `{ "mode": "fast"|"deep" }` 兼容映射（fast→off、deep→high）。
按当前模型支持域校验：未知值或未声明档位 → `400 {"error":"bad_request"}`；成功 `{ "ok":true, "thinking":"<档>" }`；
503 `llm_not_configured`；404 `unknown_conversation`；`LLM_PROVIDER=faux` 下空操作仍返回 ok。
写入即 `configure` 持久化（durable 会话模型引用，重启保留）。UI 选择器见 §2.8 `thinkingLevels`。

**`POST /api/v1/agent/chat/:conversationId/compact`（2026-11-07 扫尾批 1 B1）**：手动压缩。body
`{ "instructions"?: string }`；可选 `?wait=1`。内核 `Conversation.compact` 本就是**受理即返回**，
端点照实：受理即回 `200 {"ok":true,"taskId":<数字>}`（压缩在后台做、在空闲/边界落摘要）。
`?wait=1` 时再 `harness.waitForTask` 至多 `AGENT_COMPACT_WAIT_MS`（默认 60000）：完成
`200 {"ok":true,"compacted":true}`；超时 `200 {"ok":true,"waited":false,"taskId"}`（受理仍有效，
客户端可走 SSE / 刷新看结果）。404 `unknown_conversation`、503 `llm_not_configured` 与 `/mode` 同口径。
压缩事件（`compaction_start/end`）内核本就发，SSE 透传不动。
前端 composer：输入 trim 后匹配 `/^\/compact\b/i` → 不作为消息发送、不进历史，调本端点（剩余文字作
`instructions`、wait=1），完成后气泡提示；其余 `/xxx` 原样发送。**刻意不做通用斜杠命令系统**（登记防扩散）。

任务通道**一律思考开**（一次性会话无历史包袱）；每轮在 settle 时打一行
`[usage] 会话 N input=… cacheRead=… cacheWrite=… output=…`（验收口径见 App 仓库方案 §7）。

深档实测（历史，换模型语义时代）：同一收敛任务 `qwen-flash` 1.47s/157 tokens vs
`deepseek-v4.1-flash` 10.17s/1591 tokens，质量差距远小于时间差（App 仓库
`docs/设计方案/2026-10-29-聊天通道与思考模式.md` §5.3–§5.5）。

为什么要有直通：客户端把 prompt 模板放在 `system` 里（收敛 / 周报 / 分段 / 记忆策展 / 题目 / 深挖 / 回忆）。
修复前这些请求会被压成"只喂最后一条 user"，实测同一条收敛请求跑了 **129 秒、产出为空**；
修复后同一条 **2.5 秒**返回合规草稿（详见 App 仓库 `docs/基线文档/接口契约.md` §6 与 §7）。

#### 2.4.2 进度帧（2026-10-29）：让界面能显示"正在思考 / 正在动手"

工具回合可能几十秒没有正文。Agent 路径会额外下发**不带正文的进度帧**（非标准 OpenAI 字段，
只认 `choices[].delta.content` 的客户端会安全忽略）：

```json
data: {"object":"chat.completion.chunk","lifediary_progress":"working"}
data: {"object":"chat.completion.chunk","lifediary_progress":"thinking"}
```

- `working` = 工具正在执行（`beforeTool` 触发时发）；`thinking` = 工具返回后重新思考（`afterTool`）；
- 一次工具调用会成对出现 `working → thinking`，可能多次；
- 帧里**没有 `id`**（不是正文帧），客户端解析时要先判这个字段再判 delta；
- 只在 Agent 路径发；直通路径（带 `system`）没有工具，不发。
- 客户端意义：拿它把"空白等待"变成"正在动手…/正在思考…"，并且**它同时充当心跳**
  （工具跑几十秒也不会被判成读超时）。

#### 2.4.3 出错的呈现（不发独立 error 帧）

- Agent 路径一轮跑完却没有内容（上游 key 错、模型报错）→ 先吐 `delta.content = "这次没能生成回复，请再试一次。"`
  （`chatStream` 的 `unanswered` 事件）；
- 直通路径上游失败 / 一个字都没吐 → 吐 `"生成失败，请稍后重试"`；
- 两种情况都以 `finish_reason: "stop"` + `[DONE]` 收尾。
- **不再写 `{"error":{…}}` 帧**：只认 `choices[0].delta.content` 的客户端会把它当噪音丢掉，最后留下空气泡。
  客户端若自带 `error` 帧解析（旧版兼容），留着无害。

#### 2.4.4 任务通道 `X-Task`（2026-10-30，模板上移）

**为什么有**：日记任务（收敛 / 周报 / 分段 / 题目 / 回忆）原先由客户端把整份 prompt 塞进 `system` 走直通，
直通不建会话 ⇒ 那段对话**过完即弃**。"手机只留索引、正文归位 harness"要求这部分也落库，
所以模板搬到服务端、任务改走 Agent 会话。设计来源：App 仓库
`docs/设计方案/2026-10-29-对话正文归位Harness（手机只留索引）.md` §4（方案 A）。

请求（`X-Task` 大小写不敏感，同时忽略 `system`）：

```http
POST /api/v1/llm/chat/completions
X-Task: converge
Content-Type: application/json

{
  "messages": [{ "role": "user", "content": "请整理成稿" }],
  "task_vars": { "user_messages": "- 今天把方案重写了一遍", "entry_types": "（待用户确认）" },
  "temperature": 0.4,
  "max_tokens": 4000
}
```

| 项 | 口径 |
|---|---|
| 任务名 | `converge` / `weekly` / `segment` / `interview` / `chapter` / `question`；未知 → **400 `{"error":{"code":"unknown_task"}}`** |
| 模板 | 服务端 `apps/server/prompts/<name>_v<N>.md`，**与 App `core/ai/src/main/assets/prompts/` 同名同字节**；版本号 = 文件名去 `.md` |
| 变量 | `task_vars` 的键必须**齐**（缺一个或值不是字符串 → **500 `task_render_failed`，且不落半条会话**）；占位符是 `{{key}}`，与 App 的渲染算法相同 |
| system | 由服务端渲染后作为会话 `instructions` 段写入并**持久化**（进程重启仍是同一份 prompt）；客户端给的 `system` 一律忽略 |
| 人格 / 记忆 / 工具 | **全部摘掉**：任务会话不选我们的扩展（无人格、无记忆注入），`tools: []`（不给 pi 自带的读写改跑） |
| 档位 | 不参与思考档判定，**一律思考开**（`enable_thinking:true`，不带 effort 档；`LLM_MODEL`） |
| 参数透传 | `temperature` / `max_tokens` / `response_format` 照抄上游 —— 实现方式是按参数派生一个模型 id（`<model>#t0.4m4000r<8 位哈希>`），把参数挂在 `samplingParams` 上（pi-ai 最后写入、覆盖同名请求字段）；同参数复用同一个派生模型 |
| 会话 id | **一次调用一个新会话**（2026-10-31）：优先 `X-Conversation-Id`，没带就生成 `task-<uuid>`。任务之间没有对话关系，复用哈希 id 会把同一任务的多次调用挤成一条（实测三次收敛滚进同一条，token 越滚越长）；要续跑就显式带 `X-Conversation-Id`。**非流式回的 `id` / 流式 chunk 的 `id` 就是这个 id**，客户端拿它回读 |
| 落库内容 | transcript 里是**那句固定输入**（如「请整理成稿」）+ 模型输出；整份 prompt 不进 transcript（否则回读是一堵规则墙） |

**任务会话不进"历史对话"（2026-10-31）**：`task-` 前缀的会话被 `GET /api/v1/agent/chats` 过滤掉——
它们的首句是"请整理成稿"这类**指令**，不是用户说过的话，混进列表只会让人莫名其妙。
正文照旧可以按 id 回读（`GET /api/v1/agent/chat/:id/messages`），只是不露头。

**手机 worker 通道（2026-11-02 契约；2026-11-10 批 26 §一 加执行前重验）**：
`POST /api/v1/worker/poll`（要活，没活挂起后 204，同设备新 poll 顶掉旧的）、
`POST /api/v1/worker/model`（服务端 key 代理）、`POST /api/v1/worker/result`（交结果）。
服务端的保证只有两条：① **已取消 / 已超时的单不再交给 poll**（队列里跳过，收尾交各自的
计时器 / abort 监听）；② **已取消 / 已超时的单交回结果时不写回**——返回
`200 {"ok":true,"applied":false,"reason":"canceled"|"expired"}`（本批之前是 `404 unknown_task`；
正常路径仍是 `{"ok":true}`），并记一条只含单号的日志。取消墓碑在内存保留 10 分钟、上限 200 条。
回滚：`PHONE_ENSURE_ACTIVE=false`（§6）。
**已知边界（如实登记）**：手机拿到单之后、真正开始执行之前的那一段在手机侧，服务端无法代查——
本批不新增 preflight 端点，也不改手机端契约；取消只有发生在交付窗口内才保证"不产生副作用"。

审批（2026-11-04 批次二；2026-11-08 扫尾批 8c 改缺省形态、10-C 改三档）只在审批档不是 `none`
时产生（`ask-all` = 写类工具 ∪ 高危清单全问；`ask-critical` = 只问 `AGENT_APPROVAL_CRITICAL_TOOLS` 清单，
缺省 `bash` / `powershell` / `delegate` / `partner_manage` / `send_to_agent` / `routine_manage`）；
`none`（默认）时零行为变化，`GET .../approvals` 没有 pending（未配置模型时回 `503`，同 `/stop`）。

**缺省形态 = 等待态落库（async）**：被拦的写类工具**不阻塞本轮**——落一条 pending 记录（带工具名、
参数摘要与参数指纹）后，把「该操作在等用户批准」作为工具结果回给模型，本轮照常收尾（零挂起、零等待）。
人答复后服务端向该会话**自动提交一条 followUp**：批准 → 「用户已批准 X，立即原样重发这个调用」；
拒绝 → 「用户拒绝了 X，请继续其余工作」。模型重发同一个调用时，闸门按**一次性放行清单**
（工具 + 参数指纹，命中即核销）放行，不再问；换参数重发不会命中（防「批了 A 执行 B」），重新挂一条待批。
**pending 永不自动过期**：重启后仍保留可答（`load()` 不再置 `timeout`）；同一会话里同工具 + 同参数的
pending 只挂一条（模型重试不重复弹卡）。`/stop` 仍把该会话的 pending 按 `aborted` 结算，并作废该会话
未核销的放行。

**续跑轮进记忆（2026-11-08 批 10-A）**：自动 followUp 驱动的这一轮与普通轮走**同一个**收尾 handler
（观察层 / 记忆抽取 / 会话记忆修剪），不再有"审批续跑不进记忆"的缺口；任务专线（`task-` 前缀）照旧不进记忆。
代价是审批指令本身（服务端生成的文本）也会作为用户侧内容被抽取，属如实记账。

**回滚形态 = blocking**（`AGENT_APPROVAL_MODE=blocking`，见 §6）：完整回到 2026-11-04 的行为——工具回合
挂起等待，`AGENT_APPROVAL_TIMEOUT_S`（默认 120 秒）超时按拒绝；启动时遗留 pending 一律置 `timeout`。
两种形态的契约字段相同（`approval` 帧、GET 投影、POST 答复），前端按 `GET /agent/policy` 的
`approvalMode` 决定审批卡显示倒计时还是「等待处理」。

**已知边界（8c 登记）**：不做「工具结果回填」——pi-durable 1.4.0 没有向已收尾 run 回填工具结果的入口，
所以选「模型重发调用」（每次批准多一轮模型调用，但零内核改动、可靠）。

**全局待办的数据边界（2026-11-04 批次六）**：不带 `conversationId` 时，列表把**所有会话**的待批工具参数
（`args`，截断 1200 字符）返回给任一已配对设备（deviceToken 与共享令牌同权限）。这与 `GET /api/v1/agent/chats`
的既有边界一致——持令牌者本来就能列出全部会话并按 id 回读正文，**不是新增提权**。任务会话（`task-` 前缀）
天然没有工具、不产生审批；已「移除」的会话仍可能出现（标题可能为空）。列表不返回正文，只有审批所需的工具名与参数摘要。

**结构化提问（`ask_user`，2026-11-09 §3）**：它借审批 pending 管线，`GET .../approvals` 的每一项额外带
`kind:"ask_user"`（普通审批**不带该键**），`args` 是问题 JSON：`{question, options?, recommended?}`
（question ≤200 字；options 2-3 个、每个 ≤60 字；recommended 是建议项下标）。客户端据此渲染问题卡，
答复走 `POST .../approvals/:callId/answer`；`/stop`、重启保留、全局待办等语义与普通审批完全一致。
**答案沉淀（2026-11-10 批 19 §二）**：答复成功后额外把 `{question, answer}` 写成一条
`kind=fact`、`source=verified_answer` 的记忆（scope = 发起会话），下次同类问题不必再问；
群会话不落，`AGENT_VERIFIED_ANSWER=false` 关闭。只改记忆，不改答复与续跑语义。
手机端零改动（当前只会把它当普通审批卡；请走 `/answer` 的客户端才可答复）。

**审批的作用半径（2026-11-10 批 16 §三）**：审批档按"谁能改、多久生效"分三类，客户端文案与产品说明都按这个口径讲，
不要混成一句"关闭审批"：**即时生效**——API 引擎的 `AGENT_APPROVAL_*` 环境变量与界面开关，改完**下一轮**的工具调用
就按新档判（已在跑的那一轮里判过的调用不回改）；**turn 锁定**——自带模式的引擎（qoder / codebuddy 这类 CLI，
`--permission-mode` 在起子进程时写死）一个 turn / 一单内不变，换档只能重开一单；**代答型**——`ask_user` 的答复
与审批 pending 的答复，**立即生效、只作用于这一次调用**（批准 = 工具 + 参数指纹核销一次，问题答复 = 交回原单的一次输入），
不是"以后都放行"。三类都**不提升能力边界**：只读 / 黑名单的 `block` 永远优先于任何答复。

### 2.6 `POST /api/v1/diary/sync` —— 日记成稿镜像同步（2026-10-29）

手机是日记的**权威**，这里只是**镜像**：唯一写入路径就是这个端点，**没有任何"在 harness 改日记"的入口**
（不提供 PATCH/DELETE）。设计与合并规则见 App 仓库
`docs/设计方案/2026-10-29-对话正文归位Harness（手机只留索引）.md` §7.1。

请求：

```json
{ "since": 1761700000000,
  "entries": [{ "id": "01j…", "status": "CONFIRMED", "source": "MANUAL", "localSource": "MANUAL",
                "entryDate": "2026-10-29", "finalText": "…", "rawSnapshot": "…",
                "types": ["NOTE"], "mood": null, "createdAt": 1761700000000,
                "updatedAt": 1761700000000, "deleted": false, "conversationId": null }] }
```

响应：

```json
{ "entries": [ …同结构… ], "serverTime": 1761700005000 }
```

| 项 | 口径 |
|---|---|
| 鉴权 | 与其他 `/api/v1/*` 相同（共享令牌 ∪ 设备凭据；失败 403 空体） |
| `since` | **闭区间**（`updated_at >= since`）：同一毫秒的行宁可重复下发，客户端按 `updatedAt` 幂等跳过 |
| 上限 | 上行不限（客户端 200 条/页）；下行单次 ≤ 200 行，按 `updated_at` 升序 |
| 截断 | 单条 `finalText` / `rawSnapshot` 各 **8KB 字节**（按 UTF-8 逐码点截断） |
| `deleted` | **软标记**，永不物理删除；软删时**保留已有正文**（后期分析"写过又删了"） |
| 合并 | 见下表 |
| 幂等 | 按 `id` 对齐，重发不产生第二行 |

合并规则（服务端看到的视角）：

| 场景 | 处理 |
|---|---|
| 镜像无该 id | 插入 |
| 上行 `updatedAt` 更新 | 覆盖（手机赢） |
| 两边 `updatedAt` 相同且内容一致 | 跳过 |
| 两边 `updatedAt` 相同但内容不同 | 手机赢 + 日志一行（单用户单设备，正常不会发生） |
| 上行 `updatedAt` 更旧 | 镜像保留，**把胜出的那行塞回响应**（客户端据此覆盖本地） |
| 上行 `deleted=true` | **只置标记与 `updated_at`，其余字段一律不动**（无论 `updatedAt` 是新是旧）。墓碑是最小形状（只带 id + 删除时刻），走"整体覆盖"会把已镜像的正文抹成空 —— 2026-10-30 真机踩过 |

`GET /api/v1/diary/status`（只读自检）：`{count, items:[{id,status,source,localSource,entryDate,updatedAt,deleted,chars}]}` ——
**不含正文**（避免被随手当接口读全文）。

存储：`.data/diary.sqlite`（`DIARY_DB_PATH` 可改），**独立库、不混进 pi-durable 的表**；

  worker = 手机 worker（`CHANCELLOR_EMPLOYEE=phone`，chancellor `WorkerKind`）或带明确

### 2.8 模型：当前选择与运行时切换（2026-11-04，批次五改口径）

模型身份是 **`ModelRef`**：

```json
{ "providerId": "bailian", "modelId": "qwen3-max" }
```

`providerId` 是供应商配置键（`providers.json` 的 `id`，小写 slug），**不是安全边界**；
它是用户可读的配置键，所以不适用"对外 id 一律 uuid"那条（uuid 是为不可猜的会话 id 定的）。
`shared` 不定义这个类型（它只服务于服务端配置端点），手机端按 JSON 读写即可。

选择优先级：**`runtime.json`（用户显式切换）> `providers.json` 的 `defaultSelection` > 第一个供应商的第一个模型**。
`LLM_MODEL` / `LLM_BASE_URL` 是**播种来源**，文件生成之后以文件为准（§2.10）。

- `runtime.json`（`MODEL_RUNTIME_PATH`，默认 `.data/runtime.json`）只存
  `{"model":{"providerId":"…","modelId":"…"}}`，无密钥。
  旧版 `{"model":"<裸 id>"}` 仍能读：裸 id 按**默认供应商**解释；读成功后下次写入自动升级成新形状。
  **降级风险**：旧代码不认识新形状，会把选择当成"没有覆盖值"、回到 `LLM_MODEL` 默认（不报错）。
- 切换**下一轮对话生效**：新会话直接用；已有会话在下一轮开跑前按 `providerId+modelId` **成对**对齐
  —— 同名模型换供应商也算换模型，必须重配（否则是空操作）；思考档保持原样，
  当前档不在新模型支持域内则自动落回支持域内 ≤ 当前档的最高档（`off` 兜底；2026-11-04 思考档位）。
  快/深共用当前模型的口径不变（2026-10-31 方案 D1）。

#### `GET /api/v1/agent/model` —— composer 投影

**不含 `baseUrl` / `keyEnv` / 任何密钥值**：

```json
{ "current": { "providerId": "bailian", "modelId": "qwen3-max" },
  "providers": [ { "id": "bailian", "name": "百炼",
    "models": [ { "id": "qwen3-max", "thinkingLevels": ["off","low","high"],
                  "contextWindow": 131072, "maxTokens": 4096 } ], "hasKey": true } ] }
```

- `current`：mock（未配置）时 `null`；faux 时 `{"providerId":"faux","modelId":"faux"}`。
- `hasKey`：`process.env[keyEnv]` 非空；只表示"变量有值"，不代表连通。
- `models[]` 是**对象行**（2026-11-04 思考档位起，旧形状是裸字符串数组）：`id` + `thinkingLevels` =
  该模型支持的思考档（§2.4.1），来自 providers.json 可选 `thinkingLevels` 字段，缺省 `["off","low","high"]`；
  UI 据此渲染档位选择器。`POST /agent/model` 响应里的 `models` **保持扁平字符串数组不变**（旧字段兼容）。
- `contextWindow` / `maxTokens`（2026-11-05）：**已解析的生效值**——providers.json 的 `modelMeta` 有就按它，
  否则落到缺省 `131072` / `4096`（§2.10）。UI 在模型菜单里显示上下文，设置页编辑时直接回填。
- 每次打开选择器现拉，不缓存。

#### `POST /api/v1/agent/model` —— 运行时切换

请求 `{ "providerId": "bailian", "modelId": "qwen3-max" }`；
兼容旧形状 `{ "model": "<id>" }`（没给 `providerId` 时按**默认供应商**解析）。
成功：

```json
{ "ok": true, "provider": "bailian", "model": "qwen3-max", "models": ["qwen3-max"] }
```

`model` / `models` 是**保留的旧字段**（现有 web 与兼容层只认它们）；`provider` 是新增。
`models` = 切换后该供应商的模型清单（扁平）。

| 情形 | 返回 |
|---|---|
| 没有 `modelId` / `model` | `400 {"error":"bad_request"}` |
| `MODEL_RUNTIME_OVERRIDE=false` | `400 {"error":"override_disabled"}`（回滚开关，启动时也忽略已存选择） |
| `LLM_PROVIDER=faux` | `400 {"error":"faux"}`（假模型没有可切的真实模型） |
| 未配置（无 providers.json 且无 `LLM_API_KEY`） | `503 {"error":"llm_not_configured"}` |
| `providerId` 不存在 | `400 {"error":"unknown_provider"}` |
| 模型不在该供应商 `models[]` | `400 {"error":"unknown_model"}` |
| `PROVIDERS_CONFIG=false` | 只用 env 派生的默认供应商；其他 `providerId` → `unknown_provider` |

约束：**只切模型与供应商配置**。API key 值不进这个端点、不进任何界面——密钥只走环境变量（仓库硬约束）。
切换 = 会话的上游前缀缓存重建一次，属预期（D1 防的是快/深每轮互切，不是这种低频显式切换）。

**会话绑定的派生变体 id 随注册表重建预注册，重启不再丢**（2026-11-07 修复 A2）：新建会话把 `<模型>#think-<档>` 写进 durable 会话，重启后注册表重建时按目录确定性补注册这些变体（`#think-off` 恒注册、其余档按 `modelThinkingLevels`；`MODEL_VARIANT_PRESEEDED=false` 退回懒注册）。会话创建即绑模型、旧会话不跟随全局切模型、全局切换只影响新会话——这三条语义不变。任务温度变体（`<模型>#t…`）参数来自请求体、非确定，不预注册（边界见 `系统架构.md` §7 口径与变更记录）。

**手机端**：`GET/POST /agent/model` 协议无关（裸 JSON），Kotlin 暂不接入；接入时按上面的 `ModelRef` 读写即可。

#### 2.9.1 取消 / 重试（2026-11-07 扫尾批 1 A1，`DELEGATION_CANCEL`）

**取消 = harness 侧「作废」，不杀 chancellor 进程**（单据与执行都在 chancellor 仓，harness 杀不到）。
作废后：不再为该单发 SSE 事件、结算时不再写回会话 / 不再记结论文；执行端照常跑完、产物照常落盘——

```json
  "children": [{ "id": "…", "status": "…", "parentTicketId": "…", "updated_at": "…" }]
}
```

**`steps` / `repairRound`（2026-11-09 保证实现纵深 §2.3 / §1.5，纯增量）**：详情顶层可选字段——
`steps: string[]`（派单时 `delegate` 给的计划动作序列，≤12 条、每条 ≤200 字）与
`repairRound: number`（这张单已经自动返工到第几轮；1 起）。**没有就是不带这两个键**，老客户端零影响；
`ticket.steps` / `ticket.repairRound` 也原样落在 `ticket.json` 里（详情与看板同源）。

**`runSource`（2026-11-10 批 15 §三，纯增量）**：详情顶层可选字段
`runSource: "human" | "routine" | "routine_self" | "script" | "test" | "device"`
（人派 / 例行轮 / 执事自建例行的首轮 / HTTP 脚本 / 探针测试 / 设备矩阵）。来源落
`delegation_receipts.run_source`（可空）；**老数据 null 视为 `human`**。没有回执或
`RUN_SOURCE=false` 时**不出现这个键**，老客户端零影响。只记枚举，不含正文。

**`gates`（2026-11-10 批 19 §四，纯增量）**：详情顶层可选字段
`gates: [{name: string, passed: boolean, note?: string}]`——把**已有事实**投影成"过了哪些关"：
`reviews[]` 每条一个（`name` = `验收：<slug>`）、裁判结论（`DELEGATION_JUDGE` 打开且 `judge.json`
有记录时一条 `裁判`）、返工轮次（`repairRound > 0` 时一条 `返工`）。**只投影、不新增判定**；
没有这些事实 / `TICKET_GATES=false` 时**不出现这个键**。

**`acceptanceChecks`（2026-11-10 批 23 §一，纯增量）**：详情顶层可选字段
`acceptanceChecks: [{text: string, status: "passed" | "failed" | "unknown", note?: string}]`——
`steps` 里 `验：`（全角；半角 `验:` 同样认）开头的项才是验收项，去掉前缀放 `text`；
其余条目算动作，仍只在 `steps` 里。**状态只按已有事实判，不逐项编造**：
`reviews[]` 全 `pass` → 全部 `passed`；有 `fail` → 全部 `failed`（`note` 列未通过的 slug）；
没有 `reviews`（或只有 `blocked` 这类非 pass 非 fail 的结论）→ `unknown`，`note` 写明原因。
没有 `验：` 项 / `DELEGATION_ACCEPTANCE_CHECKS=false` 时**不出现这个键**。

**`bgJobs`（2026-11-10 批 23 §二，纯增量）**：详情顶层可选字段
`bgJobs: [{id: string, commandSummary: string, startedAt: string, endedAt?: string, exitCode?: number}]`——
bash 超时转后台的任务**摘要**。**不返回日志正文**（正文走 `GET /api/v1/agent/bg-jobs/:id/log`）。
`bg-jobs/index.json` 没有 ticketId，只能按单的时间窗口过滤：起点 `created_at`，终点是终态单的
`updated_at` / 在办单的当前时刻——**同时开着的别的单的后台任务可能混入，这是已知边界**
（不在这里猜归属）。窗口内没有 / `TICKET_BG_JOBS=false` 时**不出现这个键**。

**`groupId`（2026-11-10 批 19 §五，纯增量）**：列表行与详情顶层可选字段——
同一 `requestId`（落在 `ticket.idempotencyKey`）的多张副本单共用这个值（= requestId）。
没有 requestId / `DELEGATION_FANOUT_GROUP=false` 时为 `null`（详情不带键）。
前端把同 group 的 ≥2 张单折叠成一行"3 个副本，已完成 2"。

**组聚合（2026-11-10 批 26 §二）**：`GET /api/v1/tickets/groups/:groupId` 是"等最后一个副本"的只读口：
扫顶层 `workRoot/` 与各领域 `runs/` 里所有 `ticket.json`，按 `idempotencyKey` 数出
`total / done / pending`，**全部终态才算 `settled`**（作废位也算终态：harness 不再搬它的结果）。
只读、不自动消费、不改任何单。**人的消息不在这组里**：主人回话走 `POST /tickets/:id/say`（单线），
不进组、不影响 `settled`。开关沿用 `DELEGATION_FANOUT_GROUP`（关 = 组这个概念不存在 → 404）。
已知代价：每次请求按单全量读 `ticket.json`（上限 500 张/库），不做缓存。

**`messages`（2026-11-07 派活留言，纯增量）**：`[{direction, fromKind, fromName, body, createdAt}]`，按落库顺序（派出去的在前）。`direction` = `out`（派活原话 / 回答上一轮提问）/ `in`（交回的结论）/
`system`；`fromKind` = `chief` / `partner` / `worker` / `system`。**老单没有记录 = 空数组**，不报错。
这一层的意义：任务详情以前只有 `prompt` 一段裸文本，看不出是总管说的还是执事转的；
现在能回答"谁、什么时候、说了什么"。落地见 `delegation-messages.ts`。

- 查找顺序：顶层 `workRoot/<id>/ticket.json` → 各领域 `managers/<domain>/runs/<id>/ticket.json`。
- id 里出现 `/`、`\`、`..` 一律 `404`（不拼路径、不越工作区）。
- `project` 沿用登记表字段（不含密钥）；`domain=null` 表示不是分管派出的单。
- `children` 是同一父单下的子单（`parentTicketId`）；父单未全部终态时不会进 `done`（§4）。
- **近况字段落盘（2026-11-04）**：`lastAction`（最近一次动作，取事件里那句话）、`lastHeartbeat`（最近活动时间，ISO）、
  `waitingOn`（最近卡在哪个文件租约）已写进 `ticket.json`，列表与详情都直接返回（没有时为 `null`）。
  落盘有节流：动作或等待对象变了立刻写，只有心跳变化时最多每 10 秒写一次；终态保留最后一次的值；
  进程重启后从明文读回，看板不用依赖 SSE 历史。这三项是展示用的近况，不参与 sqlite 索引与排序。

#### 2.9.2 任务即对话（2026-11-08 扫尾批 8g，`TASK_AS_CONVERSATION`）

一张任务单自带一条**专线会话**（外部 id `task-<票号>`），单的动态与会话内容同一份：

| 写入方 | 内容 | 形态 |
|---|---|---|
| 派单进度（`emitProgress`） | 已受理 / 规划中 / 进行中 / 核对中，带 `done/total` 与等待对象 | `pi.assistant` 条目，一行 `【进度】…` |
| 终局汇报（`settle`） | 执行端交回的结论 | `pi.assistant` 条目，`【汇报】…`（与留言表 `in` 同源） |
| 留言（`recordMessage` 的 `out`） | 派活原话 / 回答上一轮提问 | `pi.assistant` 条目，`【留言】<发送者>：…` |
| 主人回话（`POST /tickets/:id/say`） | 用户输入 | 真 `pi.user` 条目（`whenBusy:"followUp"`） |

- **顺序**：delegation 侧在同一个同步调用栈里入队（镜像放到 `DelegationRuntime.mirror`），
  专线写入按单串行，条目顺序 = 事件发生顺序；进度**不合并、不节流**（事件几条就记几条）。
- **留言表照写**：`delegations.sqlite` 的 `delegation_messages` 保留并继续写，任务详情旧留言区
  不动，作为过渡期兜底视图。`in` 方向不重复镜像（由 REPORT 覆盖），`skipMessageMirror` 让
  `/say` 的用户条目不再抄一遍进来。
- **跳过三处**：`task-` 前缀沿用 `listChats` 的既有过滤（不进侧栏）；专线不是 ticket，任务中心
  不会为它出卡；`configureTaskChat` 摘掉 `lifediaryExt`（不注入记忆、无工具、无人格），
  `/say` 直接 submit 不挂 `onSettled`，且 `turnSettledHandler` 对 `task-` 前缀再兜一层
  （主人从会话页直接点开续聊时也不抽取记忆）。
- **回滚**：`TASK_AS_CONVERSATION=false` → 不建/不写会话，`POST /tickets/:id/say` 不挂（404），
  派活只写留言表（回到本批前形态）。专线残留数据无害（不进列表、不参与调度）。
- **键控基线（2026-11-10 批 21 §四，`TASK_KEYED_BASELINE` 默认开）**：验收标准
  （`ticket.steps` + `plan.json` 各任务的 `writes`）以一条**键控块**随专线双写：

  ```
  [[keyed:task:acceptance]]
  【验收标准·键控基线】…
  步骤：1. … 2. …
  声明要写的路径：…
  [[/keyed:task:acceptance]]
  ```

  写入点 = 专线首次被写（创建）时；还原点 = **每次**写系统事件 / 主人回话前检查一次，
  块不在（被压缩吃掉）就整块补回。判定只看起点标记（幂等，不解析正文）；没有 steps 也没有
  writes 时不写空块。读票面失败 / 写失败都只 warn，不挡专线主写入。
  `TASK_KEYED_BASELINE=false` → 不写不还原（回到批 20 形态）。
- **明确不做**：旧单留言迁移、侧栏展示专线、单完结后归档删除、专线压缩策略定制、chancellor 侧改动。

### 2.10 供应商管理（2026-11-04 批次五）

存储：`.data/providers.json`（`PROVIDERS_PATH` 可改），**只存环境变量名，不存密钥值**：

```json
{ "schemaVersion": 1,
  "providers": [ { "id": "bailian", "name": "百炼", "baseUrl": "https://dashscope.aliyuncs.com/compatible-mode/v1",
                   "keyEnv": "LLM_API_KEY", "models": ["qwen3-max"],
                   "modelMeta": { "qwen3-max": { "contextWindow": 262144, "maxTokens": 16384 } },
                   "modelThinkingLevels": { "qwen3-max": ["off", "low", "high"] },
                   "createdAt": "2026-11-04T00:00:00.000Z" } ],
  "defaultSelection": { "providerId": "bailian", "modelId": "qwen3-max" } }
```

校验（fail-closed：整份文件要么全收、要么不用）：

- zod **`.strict()`**，并**显式拒收** `apiKey` / `key` / `headers` 字段
  （strip 不等于拒收；写进文件就整份拒绝，不静默丢弃）；
- `id`：`/^[a-z0-9][a-z0-9-]*$/`，保留字 `faux` / `mock` 不可用；
- `keyEnv`：`/^[A-Z_][A-Z0-9_]*$/`；值只从 `process.env[keyEnv]` 取，**请求前一刻读**
  （pi-ai 的 auth 层本就每次读 env）；
- `baseUrl`：http/https 绝对地址；`models`：字符串数组（默认必须非空，见下方 `allowEmptyModels`）。
- `modelMeta` / `modelThinkingLevels`：可选对象，键只保留仍在 `models[]` 里的模型；
  `modelMeta` 值只收正整数（`contextWindow` / `maxTokens`，非法数值丢弃、空对象不落盘），
  `modelThinkingLevels` 值只收已知档位（拼错的过滤掉）——与思考档探活同口径。
- 写入 = 临时文件 + rename。文件损坏 / 目录只读 → **启动告警并回退 env-only**（不静默换端点）；
  运行期重载失败保留上一份可用配置（不因为一次坏文件把正在用的供应商换掉）。

**播种**（`PROVIDERS_CONFIG != false` 且文件不存在时）：有 `LLM_API_KEY` 且不是 faux →
把 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` / `LLM_MODELS` 写成默认供应商 + `defaultSelection`，
启动日志明确「env 仅播种，此后以文件为准」。**faux / 无 key 不播种**（避免探针与 mock 环境生成假配置）。
`LLM_MODEL_FAST` **不入文件**：它只是部署别名（D1 后快/深同模型），仍从 env 读，行为不变。
`PROVIDERS_CONFIG=false`：忽略文件、不播种、回到纯 env 行为（回滚开关，与 `MODEL_RUNTIME_OVERRIDE` 正交）。

逐模型元数据（2026-11-05）：`modelMeta[modelId] = { contextWindow?, maxTokens? }`，
缺省仍为 `contextWindow=131072` / `maxTokens=4096`（不写进文件 = 用缺省，默认值不落盘）。
UI 里由「添加模型」弹窗手填或走检测端点自动回填；服务端只做校验与解析，不猜。

配置改动**不用重启**：服务端是同进程换装（单例 `Models` 按版本号原子替换 provider 集合），
下一轮对话即生效；不会因为目录没刷新而打旧地址，也不会每请求重建。

#### `GET /api/v1/agent/providers` —— 设置页投影

比 composer 投影多 `baseUrl` / `keyEnv` / `isDefault`（回填编辑需要），**仍无任何密钥值**：

```json
{ "providers": [ { "id": "bailian", "name": "百炼", "baseUrl": "https://…",
                   "keyEnv": "LLM_API_KEY", "models": ["qwen3-max"],
                   "modelMeta": { "qwen3-max": { "contextWindow": 262144 } },
                   "modelThinkingLevels": { "qwen3-max": ["off", "low", "high"] },
                   "hasKey": true, "isDefault": true } ],
  "defaultSelection": { "providerId": "bailian", "modelId": "qwen3-max" } }
```

- `modelMeta` 是**稀疏**的（只列配置过元数据的模型）；`modelThinkingLevels` 给每个模型**生效档位**
  （声明过用声明，否则缺省 `["off","low","high"]`），设置页据此渲染多选框。

#### `POST /api/v1/agent/providers` —— 新增 / 更新

带 `id` 且已存在 = 更新；不带 `id` = 新建（服务端从 `name` 生成 slug，重名时加后缀）。

| 字段 | 说明 |
|---|---|
| `id` | 可选；必须符合上面的 slug 规则 |
| `previousId` | 编辑时携带原 id；与 `id` 不同 → `400 provider_id_locked`（**id 不能改**） |
| `name` | 展示名（1–80 字符） |
| `baseUrl` | OpenAI 兼容基址（不带 `/chat/completions`） |
| `keyEnv` | 环境变量名；指向不存在的变量**允许保存**（投影 `hasKey:false`，选中后请求报正常错误事件、不崩） |
| `models` | 模型 id 数组；默认必须非空（空 → `400 bad_models`），与 `modelsUrl` 二选一 |
| `allowEmptyModels` | `true` = 允许先建**空清单**供应商（新 UI 的流：先建档、再逐个添加并检测模型）；不传保持老语义。空清单供应商不会成为 `defaultSelection` |
| `modelMeta` | 可选 `{modelId:{contextWindow?,maxTokens?}}`；不传 = 保留旧值（编辑）并按 `models[]` 裁剪 |
| `modelThinkingLevels` | 可选 `{modelId:["off",…]}`；不传 = 保留旧值并按 `models[]` 裁剪 |
| `modelsUrl` | **仅本次请求用、不持久**：服务端代拉 `{baseUrl}/models`（key 从 env 取），超时 5s、响应 ≤1MB；兼容 `{data:[{id}]}` / `{models:[…]}` / 裸数组三种形状。失败 → `400 models_fetch_failed`，由用户手填。**新 UI 不再用它**（改成逐模型添加 + 检测），保留给旧客户端 |
| `test` | `true` = **不写文件**；只测 `keyEnv` 变量存在非空 + `GET {baseUrl}/models` 2xx。措辞是「钥匙已就位」，**不是"连接成功"**（只证明 key 有值、端点可访问，不证明模型可用） |

成功：`{ "ok": true, "provider": { …同 GET /providers 的单项… } }`。

#### `POST /api/v1/agent/providers/:id/models/detect` —— 单模型检测（2026-11-05）

body `{ "modelId": "<上游模型 id>" }`。**只读，不写配置**；允许检测尚未加入 `models[]` 的 id
（添加模型本来就是"先检测再添加"）。检测内容：真打一次 `/chat/completions`（`max_tokens=8`，无 `reasoning_effort`）、
`GET {baseUrl}/models` 抽上下文 / 输出上限（认 `context_length` / `max_model_len` / `max_input_tokens` /
`max_output_tokens` / `max_completion_tokens` 等常见字段，扫一层嵌套；拿不到退 `GET /models/{id}`），
并并行探 `low` / `medium` / `high` 三档（`reasoning_effort`，`off` 视为兼容基线）。三路并行，各自超时（ping 6s / 元数据 5s / 档位 8s）。

```json
{ "ok": true,
  "detection": { "providerId": "bailian", "modelId": "qwen3-max",
                 "reachable": true, "status": 200, "latencyMs": 320,
                 "contextWindow": 262144, "maxTokens": 16384,
                 "thinkingLevels": ["off","low","high"],
                 "levels": { "low": "ok", "medium": "rejected", "high": "ok" },
                 "message": "模型可用，已拿到上下文" } }
```

- `reachable` = 拿到过任何 HTTP 响应（不代表 2xx）；`levels` 逐档是 `ok` / `rejected` / `unknown`。
- 上游没给上下文字段时 `contextWindow` / `maxTokens` 是 `null`——**不猜、不用默认值冒充当真相**，由用户手填或留空用缺省。
- 错误：`404 unknown_provider`、`400 bad_request`（空 `modelId`）、`400 providers_disabled`。
- 密钥纪律：key 只从 `process.env[keyEnv]` 读；日志只记 `providerId/modelId/reachable/status/上下文/档位枚举`，
  **不记上游响应正文**，响应也不回显 key。
- 检测结果**不自动落盘**：前端把值填进弹窗，用户确认后随供应商一起保存。

#### `PUT /api/v1/agent/providers/:id/secret` —— 密钥直填（2026-11-05，用户拍板"界面直接填 API Key"）

body `{ "apiKey": "<明文>" }`（1–512 字符）。服务端：
1. 生成绑定 `keyEnv = LIFEDIARY_KEY_<ID大写>`；
2. 写入服务端本地密钥文件 `.data/provider-keys.json`（仅 `KEY=VALUE` 映射，文件权限收紧 0600，git 忽略）；
3. **热注入** `process.env[keyEnv]`（立即生效，无需重启）；
4. 同步该 provider 的 `keyEnv` 字段（providers.json 仍只存变量名）。

成功 `{ "ok": true, "keyEnv": "LIFEDIARY_KEY_…" }`——**绝不回显密钥值**。
错误：`404 unknown_provider`、`400 bad_request`（空/超长）、`400 providers_disabled`。
安全不变量：密钥值不进日志、不进任何 GET 响应、`hasKey` 仍只报布尔；**删除供应商时联动清除密钥条目**。
错误补充：密钥文件损坏时启动注入忽略、写入返回 `500 secrets_write_failed`（拒绝用空表覆盖，fail-closed）。
回滚开关：`PROVIDER_SECRETS=false` → 端点 400 `secrets_disabled`（文件里已有的 key 重启后照常注入生效）。
密钥文件路径可用 `PROVIDER_KEYS_PATH` 覆盖（默认 `.data/provider-keys.json`，探针隔离用）。
密钥落点口径（2026-11-05 起）：环境变量（手写 .env **或** 界面直填→服务端密钥文件+热注入）。热注入后，现有 `modelsUrl` 代拉清单（key 从 env 取）对新填密钥**立即可用**——UI 编排：保存→存密钥→拉清单回填，**用户不再手填模型清单**。

#### `DELETE /api/v1/agent/providers/:id`

成功 `{ "ok": true }`；未知 id → `404 {"error":"unknown_provider"}`。

**不变量（违反一律 400，带 `message`）**：

| 操作 | 规则 |
|---|---|
| 删除 | 默认供应商 → `provider_is_default`；当前选中供应商 → `provider_in_use`（提示先切走） |
| 删除被旧会话引用的供应商（非默认 / 非当前） | **允许**；会话下一轮对齐失败时**真正回退默认供应商**（不是继续拿旧引用打 404） |
| 编辑 | 当前选中（或 `defaultSelection`）的 `modelId` 不在新 `models[]` → `selected_model_missing`（先切走）；改 `id` → `provider_id_locked` |

#### 工作履历与当前目标（2026-11-08 员工人格化刀二 E2/E4）

**工作履历（E2）**：记忆引擎新增 `MemoryKind = "work"`，是 **append-only 台账**（只增不改）：

- **写入点**：harness 侧派单**终态结算**（`delegation.ts` 的 `settle` / `fail`，`settled` 守卫保证一次）落一条到**发起执事**的 `partner:<id>` scope（按 `originConversationId` 用 `partnerIdOfSession` 认执事，刀一同款判据；主人 / 总管会话不落账）。`kind=work`、`source="work"`、`id=work:<票号>`（稳定 id，终态重入是 upsert 不重复）。content 一行：`单号 ｜ 任务一句话摘要 ｜ 终态=<状态> ｜ 结果一行 ｜（产物目录，有则带）`；产物只记 `TicketResult.tasks[].dir` 目录路径，**不透传文件清单**（8e 之前不阻塞）。写失败只 warn，不影响结算主流程。

- **ledger 语义**：巩固不合并（同正文也是另一单）、时间衰减不作用、**召回默认排除**（`WeightedRetriever` 候选集过滤 `kind!=="work"`，work 因此也不参与 `touchRecall` 写回）、模型侧语义整理建议剔除 work、`applyProposal` 另有 400 守卫；模型 `remember` 工具的 kind 枚举**不含** work（履历只由结算落，模型不可伪造）；导入通道不接受 work。
- **封顶**：每 scope 上限 **200 条**、超出删最旧，在写入点用 `store.pruneOldest(scope, 200, {kinds:["work"]})` 现算（`PruneOptions.kinds` 是本次给既有修剪机制加的 kind 规则；不传 kinds 与改动前逐字节一致）。与 `MEMORY_SESSION_CAP` 的整体封顶取严。
- **读取**：执事轮装配与周期盘点用 `store.search({scopes, kinds:["work"], limit})` 的**结构化查询**，不走语义召回。`agent/partner-context.ts` 在【当前在办】段末尾挂一行「近 10 单：完成 X、失败 Y、中止 Z」（零记录不加）；在办 = 现在时（runs 扫描），履历 = 过去时（work 记录），两层互补别混。
- **回滚**：`PARTNER_WORK_RECORD=false`（§6）→ 一个字节都不写，回到刀二之前的形态；`MEMORY_ENABLED=false` 同样旁路。

**经验层（`kind=experience`，2026-11-10 批 17 §一）**：与 `work` 的分工是「下次怎么做」vs「这单发生过什么」。

- **写入点**：同一处结算（`work-record.ts` 的 `recordWorkSettlement`），只在 `status=done` 且过门槛时写一条到同一 `partner:<id>` scope；`id=experience:<票号>`（稳定 id，重入不重复）。
- **价值门槛（确定性，不调模型）**：结果行 ≥40 字且至少含一个具体动作词（改 / 写 / 读 / 跑 / 查 / 整理 / 合并 / 删除 / 替换 / 核对 / 回滚等）；不过门槛**一条都不写**（宁缺毋滥）。内容 = `下次同类活可以这样做：<结果行>`。
- **语义**：进召回（与 fact 同组、权重 ×1.08）、**不参与时间衰减**、**参与巩固合并**（同 scope 规范化等价的经验合并并强化——与 work 相反）、会话封顶修剪受保护；`list` 排在 fact 之后。
- **回滚**：`PARTNER_EXPERIENCE=false` / `0` → 只落 work 履历，一个字节经验都不写（§6）。

**当前目标（E4）**：`partners` 表加 `current_goal TEXT`（旧库 `PRAGMA` + `ALTER TABLE` 补列，老行读 `null`）。只进 detail 端点与 PATCH，**列表形状不变**、不进 shared（刀三）。**不版本化**：目标不是身份，改完不 bump `partner_versions`、不动 SOUL / 契约，现取现用。注入走刀一**同一装配点**：【岗位契约】段之后加一行「【当前目标】…」（有目标才出现），顺序固定为 契约 → 目标 → 在办。

**刻意不做（§五.5）**：不给执事**自动**创建周回顾规则（静默的自动轮 = 意外 token 账单）；回顾规则由用户配，或主人说一句「你每周五自己盘点」后由执事经 `routine_manage` 自建（人点头过一次）。盘点口径（提示词层）：读自己 work 履历 → 一段自然语言总结（几单、成几单、什么教训）→ 总结落一条 `episode` 记忆 → 向主人汇报，**不打分、不搞 KPI 数字**。

### 2.12 例行任务（2026-11-05 批次B）

触发层是 durable 任务（`sleepUntil` 落库），不是扫描定时器（系统架构 §3 口径）。

| 端点 | 说明 |
|---|---|
| `POST /api/v1/routines` | 建（`partnerId/name/prompt≤100k/triggers/sessionMode/enabled`），启用时自动排定时链 |
| `GET /api/v1/routines?partnerId=` / `GET /api/v1/routines/:id/runs` | 列表 / 执行历史（≤50 条有界） |
| `PATCH /api/v1/routines/:id` | 改即 `revision+1`：在飞任务醒来对不上号自动作废，还开着就重排 |
| `DELETE /api/v1/routines/:id` | 删定义；在飞任务醒来作废（没有取消 API 的替代机制） |
| `POST /api/v1/routines/:id/run_now` | 手动跑一次（entrusted，不占定时链） |

triggers 四型：`cron`（5 段：分 时 日 月 周）/ `interval`（seconds ≥60）/ `once`（ISO at）/ `event`
（kind = delegation/tool/phase + match 字段等值过滤；执事自己会话发出的事件不触发——防自环）。
执行铁律：同规则串行（上一轮没跑完下一次 deferred 30s）；终态落盘失败期间后续触发只排队不执行；
重启时 running 一律 interrupted **不自动重放**。例行轮是自主轮（`turnAuthority: autonomous`，
批次C 的高危审批只对它生效）。

**事件触发器三件门（2026-11-10 批 15 §一，`ROUTINE_TRIGGER_GATES` 默认开）**：`event` 触发器可选加
`baseline?: {key, delta}`（比上次观测值变化**超过** delta 才触发；首次记基线那次不受限）、
`edge?: true`（只从假变真那一下触发）、`cooldownSec?: number`（触发后 N 秒内不再触发）。
判定顺序固定 **cooldown → edge → baseline → 原 match**；三者可组合。门状态按
`<规则id>:<触发器序号>` 落 `routines.json` 的 `gates`，坏值/非数字观测值一律不触发
（宁可漏一次，不拿脏值硬比）。`ROUTINE_TRIGGER_GATES=false`/`0`/`off` → 三个字段全部被忽略，
行为回到改动前；纯函数在 `routine-conditions.ts`（`evaluateTriggerGate`）。

**看护单例交接（2026-11-10 批 15 §四，`ROUTINE_WATCH_SINGLETON` 默认开）**：
带 `until` 的"盯到条件达成"类规则，**同一执事同一时刻最多一个在看**。新一轮开始时若已有
别的看护在盯 → 旧规则只暂停（`enabled=false`，`revision+1` 让在飞闹钟作废），
**不删除**；交接账落 `.data/routine-watch.json`（`ROUTINE_WATCH_PATH` 可改）：
`{version:1, watches:{<partnerId>:{routineId,name,since}}, handedTo:{<旧id>:<新id>}}`。
同一对 old→new **只记一次** `handedTo`；规则置停（until 达成 / 跑满 maxRuns）时从 `watches`
摘除（`handedTo` 保留）。删除规则不额外清账——残留条目只是"指向一条不存在的规则"，
下一次同 key 认领会把它当作旧看护一次性交接掉（不删数据、不挡执行）。
`ROUTINE_WATCH_SINGLETON=false` → 不读不写此文件。

**触发来源 `runSource`（2026-11-10 批 15 §三，`RUN_SOURCE` 默认开）**：run 记录新增可空
`runSource`——定时/事件触发 = `routine`；执事 `routine_manage` 自建规则的**首轮** = `routine_self`；
`POST .../run_now` = `script`。`RUN_SOURCE=false`/`0`/`off` → 不写，行为回到改动前。
（派单回执的来源列见 §2.9。）

**条件门控（2026-11-10 批 13 §四，`ROUTINE_CONDITIONAL` 默认开）**：`RoutineDef` 新增两个**可选**
字段——`until?: {note}`（一句文字完成条件；每轮跑完由模型判断，达成时回复末行写
`[[routine-done]]`，服务端把规则 `enabled=false`（**不删**，保留历史））与 `maxRuns?: number`
（自动跑满 N 次即停；手动 `run_now` 不计入）。run 记录新增结构化 `outcome`
（`success|quiet|skipped|failed|done`，`skipped` = 无人值守跳过过步骤）；下一次触发把
"上一次的结果是 X"带给模型。`ROUTINE_CONDITIONAL=false`/`0`/`off` → 两个字段与 `outcome`
全部被忽略，提示词与 run 记录回到改动前（一行回滚）。HTTP 端点本批仍只接受老字段
（`until`/`maxRuns` 目前经 `routine_manage` 工具设置，端点透出为已知边界）。

**触发器 `if` / `ends`（2026-11-10 批 21 §三，沿用 `ROUTINE_CONDITIONAL`）**：任一触发器可带
- `if?: {note}`：触发前**先问一次模型**"这句条件此刻成立吗"（独立 `completeSimple` 调用，
  走 `AUX_MODEL_REVIEW` 可 pin 的小模型，超时 15s，maxTokens 4）。**失败即跳过**：没配模型 /
  faux / 超时 / 报错 / 答案不是明确的 YES/NO → 当"不成立"，记一条 `status:"skipped"`、
  `outcome:"skipped"`、`skipReason:"condition_not_met"` 的 run（不跑模型、不推进游标、
  不消耗 `maxRuns`/`ends.after` 额度）。多个触发器各带 `if` 时**全部成立才跑**；`note` ≤200 字。
- `ends?: {at?, after?}`：`at` = ISO 时间点，到点后该触发器不再被定时/事件唤醒（在飞的 durable
  闹钟到点仍会响一次——它排在 `at` 之前才可能被创建）；`after` = 跑满 N 次停，是 `maxRuns` 的
  别名，两者同时存在取**更小**。`ends` 至少要给一个；非法值在 `validateTriggers` 直接 400。
  运行态判定在 `routine-conditions.ts`（`triggerEndedAt` / `effectiveMaxRuns` / `routineConditionNotes`），
  模型调用在 `routine-gate.ts`。

**游标推进时机（2026-11-10 批 21 §六，沿用 `ROUTINE_QUIET`）**：`routines.json` 新增
`cursors: {<规则id>: ISO}`——"上次看到哪里"的时间水位 = 上一轮**产出被保留**的 `run.endedAt`。
只有 `ok && !quiet && 没跳步` 才推进；quiet（没事）、skipped（跳步）、failed（含读失败）
一律原地不动，下一轮仍从同一处看。有游标时提示词在原文前加
`[上次看到这里] <ISO>；这一轮只看这之后的新内容。`；首次运行没有这一段。
`ROUTINE_QUIET=false` → 不读不写游标（回到"每轮从头看"）。**边界**：宿主只能按 run 终态判，
模型"读失败但照样回了 `[[no-update]]`"这一层无法区分——那是模型自报，不是宿主事实。

**安静契约（2026-11-09 T2）**：例行轮的产出"没有实质内容"时不写汇报——模型侧提示词尾部会要求
"没内容就回 `[[no-update]]`"；服务端再按确定性规则兜底（去空白后 < `ROUTINE_QUIET_MIN_CHARS`（默认 40）
且不含数字/链接/日期 → quiet）。quiet 时 run 记录 `summary:"quiet"`，`[[no-update]]` 标记从产出中剔除，
日志只记"本轮无更新"不记正文。`ROUTINE_QUIET=false` 一行回滚。**边界**：模型这一轮的 assistant
条目由 durable 内核落盘，服务端没有撤回 API，quiet 保证的是"服务端不再写第二遍汇报"，
不是"transcript 里绝对无痕迹"。

**自建巡逻 `routine_manage`（2026-11-08 刀二 E4）**：此前只有 HTTP `POST /api/v1/routines` 能建规则，
现在给**带派发权的执事**一只模型侧的手（工具参数与端点校验共用 `routine-manage.ts` 一份核心实现）：

- `action=create|disable|enable|delete`；create 带 `name` / `prompt` / `triggers` / `sessionMode`，其余带 `id`。
- **只能动自己的**：`partnerId` 由调用者会话认出后绑定，动别人的规则一律 `not_found`（找不到与"不是自己的"同一句话，**不泄存在性**）；主人 / 总管会话明确拒绝。
- **上限**：每执事活动（`enabled`）规则 ≤ **10 条**，create / enable 都先数，超了带说明拒绝。
- **走既有引擎**：create / enable 后由装配层 `routineEngine().ensureScheduled` 排 durable 闹钟；disable / 改期靠 `updateRoutine` 的 `revision+1` 让在飞闹钟作废；delete 直接删定义，在飞闹钟醒来查不到规则自然作废；事件触发的"自我事件不触发自我"防自环原样生效。
- 进 `WRITE_TOOLS` 过闸门；10-C 三档里与 `partner_manage` **同档高危**（`DEFAULT_CRITICAL_TOOLS`，自主轮强制 ask、禁"记住"绕过）。
- 回滚 `ROUTINE_SELF_SERVICE=false`（§6）→ 工具不上架，回到"只有 HTTP 能建规则"的形态。
- **不自动建周回顾规则**；盘点口径见 §2.11「工作履历与当前目标」。

### 2.14 群组（2026-11-06 群组方案落地；`GROUPS_ENABLED` 默认开）

群 = 主人 + 2–6 名执事在同一条共享时间线里聊。谁发言由宿主按确定性规则编排：
**@点名 > @所有人 > 值日执事**（无 @ 时按 `responderKind`）。每个执事仍是独立 agent
（自己的会话、SOUL、模型链、闸门——群走 `chatStream` 主链路，D14 红线不变）。
`GROUPS_ENABLED=false` 或 `COMPANIONS_ENABLED=false`：本节端点一个不挂（404 = 未启用）。

**数据模型**（`partners.sqlite` 三张表；群 id = uuid；对外 id 一律 uuid）：
`groups(id, name≤40字, notice≤500字, responder_kind, responder_partner_id, created_at, updated_at)` /
`group_members(group_id, partner_id, position, joined_at)` /
`group_messages(id, group_id, seq 群内单调, kind message|system, author_kind user|partner|system,
author_id, author_name 快照, content≤8000字, at, round_id)`。
作者落**快照**（改名/离群历史不烂）；成员表只存引用不复制人格。

**成员会话**：每成员每群一条、懒建，对外 id `partner-<partnerId>-group-<groupId>`，
链接 `role='group'`、`routeKey=group:<groupId>`。`partner-` 前缀不进会话列表（web 端过滤）。
**群会话不参与记忆引擎**（召回与抽取都跳过，判定 = 链接表存在 `role='group'` 行）；
群内连续性靠会话历史 + 群时间线。

| 端点 | 说明 |
|---|---|
| `POST /api/v1/groups` | `{name, memberIds[2–6], responderKind?, responderPartnerId?, notice?}` → 201 `{ok, group}`。`responderKind` 默认 `member`（值日制）；kind=member 时值日执事必填且必须是成员；重名成员 400（@ 歧义拒绝不猜） |
| `GET /api/v1/groups` | `{ok, groups[]}`（含成员投影） |
| `GET /api/v1/groups/:id` | `{ok, group}`；未知 404 |
| `PATCH /api/v1/groups/:id` | `{name?, notice?, responderKind?, responderPartnerId?, addMemberIds?, removeMemberIds?}`；增删成员后人数仍须 2–6，值日被移除 → 400 要求先换值日 |
| `DELETE /api/v1/groups/:id` | **硬删**：群 + 成员关系 + 消息；成员群会话遗留无害（不进列表） |
| `GET /api/v1/groups/:id/messages?beforeSeq=&limit=` | 时间线升序（默认最后 100 条）；`{ok, messages[], lastSeq}` |
| `POST /api/v1/groups/:id/chat` | `{text≤8000字}` → **SSE**（见下）。running 中再发 → 409（v1 不排队，UI 发送键变停止键） |
| `POST /api/v1/groups/:id/stop` | 停当前发言成员（复用会话 stop 链）+ 作废本轮剩余队列，finishReason=aborted |

**发言路由（纯函数 `resolveGroupSpeakers`）**：解析 @（最长标签优先、词边界、
重名歧义 → 400 拒绝不猜）→ @点名 ≥1 按正文出现顺序串行去重 → @所有人 全员按 position →
无 @ 按 `responderKind`：`member`=值日 / `everyone`=全员 / `mentions`=无人回（落 system 行）。

**@ 唯一长标签（2026-11-08 扫尾批 5，D16 底线不动）**：`@名字·<domain>`（`·` 为中文间隔号，
domain = 成员执事的领域，全局唯一）。解析规则：

- 名字后紧跟 `·` 且后面是领域 token（小写字母/数字/连字符）时按**长标签**解析，
  只认 domain 恰好等于该成员领域的那个；
- 长标签**打错域** → 不命中，按普通文本处理（不回退短名、不猜）；成员没有 domain 时同理；
- 重名成员：**只有正文真的用了那个短名才 400**（没写这个名字时不拦，照常走值日），
  400 载荷为 `{error:"bad_request", message, candidates:[{name, domain}]}`，
  `candidates` 是该重名组的全部成员（前端据此展示「名字（领域）」并插入长标签）；
- 无重名时短名照旧；`@所有人` 优先级不变。

**投影（2026-11-08 扫尾批 5，纯增量）**：`group.members[]` 除 `partnerId/name/status` 外补
`avatar`（档案头像 data URL 或 null，界面用来拼 2×2 复合头像）与 `domain`（领域或 null，
长标签消歧用）；两者都是**实时 join 档案表**得出，`group_members` 不落这两列。
`group.round = {running: boolean, speaker: {partnerId, name} | null}`
（群会话「谁在忙」胶囊读这一段；成员间隙 `speaker=null`，如实不显示）。

**SSE（纯增量，老客户端零感知）**：`start` 加可选
`sender?: {kind: "partner"|"user", id?, name?}`——一轮一个 start，整轮帧归属该 sender；
新事件 `{type:"notice", text}`（成员被跳过 / mentions 无人回 / 岔路说明），同一行落
`group_messages(kind='system')`。逐成员串行；他人消息在成员视角是 user 角色带说话人标签
（`主人: …`），自己的历史回复仍是 assistant。增量投递 = 只喂该成员上次发言之后的新消息
（首建带最近 30 条窗口）。**断线 ≠ 取消**：客户端断开回合照跑完落库，重连拉 messages 补。
执事互聊 **0 跳**：成员回复里 @ 别人不触发。v1 群流不做 seq 断点重放（回读走 REST 补）。
手机端零改动：新端点老客户端不用，SSE 增量可忽略。

**模型侧工具 `group_manage`（2026-11-07 群组入口统一）**：总管在对话里建群 / 看群。
之前只有界面按钮能建群，模型侧没有对应的手——总管说「建个群」只能干看着，与 `partner_manage`
（总管能建/停执事）的能力面不对称。

- 动作只有 `create` 与 `list`：**改名 / 加减人 / 删群不做**（低频、歧义大、删群不可恢复，
  留在界面由人点）。
- 成员与值日都按**名字**指定（`members: string[]`、`responder?: string`），不按 uuid —
  对外 id 一律 uuid 这条口径不破，也避免模型拿着 uuid 乱拼。值日缺省取第一位成员。
- 重名 / 查无此人一律拒并列出可选执事（与群端点的 @ 歧义拒绝同源）。
- 权限与 `partner_manage` 逐字一致：只有总管 / 主对话能调；执事自己的会话返回「只有总管可以建群」。
- 开关=`GROUPS_ENABLED` ∧ `COMPANIONS_ENABLED`（与端点同一个），关掉即不注册（一行回滚）。
- 进 `WRITE_TOOLS` 与自主轮风险表（`new_task`）：建群是"新建常驻多成员会话"，
  会改"谁跟谁在一起"，与 `partner_manage` 同档。
- 核心实现 `group-manage.ts` 的 `createGroupChecked()`：**HTTP 端点与工具共用一份**，
  端点只做形状映射（400 文案逐字未变，groups 探针 21 项回归全绿）。

**刻意没有**（方案 §六）：执事互聊接力、自动选人路由、群内长期记忆、群级人格 prompt、
互发消息/分工编排、排队、群流 seq 重放、删群可恢复、群级超时看门狗、手机端群聊 UI；
模型侧的改群 / 删群 / 按 uuid 指定成员（2026-11-07 补记）。

### 2.15 记忆管理（2026-11-06，设置页用；2026-11-08 扫尾批 6 补整理与导入）

**人对自己的记忆的五个动作**：看 / 删 / 标过时 / 整理（只出建议）/ 导入（只增不改）。
写入在 `memory-api.ts`（路由只做形状映射），语义在 `agent.ts` 的 `memoryOverview` /
`forgetMemory` / `supersedeMemory` 与 `memory-consolidate.ts` 的
`reviewScope` / `applyProposal` / `importMemory`。

> **路径口径（2026-11-08 验收时统一）**：记忆管理全部端点（含整理与导入）统一在
> `/api/v1/agent/memory/*`——实现初版按方案原文落在 `/api/v1/memory/*`，验收时对齐既有
> 记忆端点族前缀（同一模块挂载、同一套鉴权与错误口径）。

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/memory?scope=global&limit=300` | `{ok, enabled, extract, total, byKind, items[], canConsolidate, canImport}`；`scope` 缺省 `global`（偏好与日记摄入都在这里），执事传 `partner:<uuid>`；`limit` 上限 2000 |
| `DELETE /api/v1/agent/memory/:id` | 硬删一条 → `{ok, deleted}`；不存在 → 404 `not_found` |
| `POST /api/v1/agent/memory/:id/supersede` | `{byId?: string \| null}` → `{ok, superseded, byId}`；把这条标为"已被取代"，之后不再进召回候选，历史链仍可查（`includeSuperseded`）。`byId` 为空 = 仅下线；替代者不存在 / 自指 / 目标不存在 → 404 `not_found` |
| `POST /api/v1/agent/memory/consolidate/review` | §2.15.1：让模型出整理建议（**只建议、不执行**）；成功后另跑一次确定性审计并落 diff |
| `POST /api/v1/agent/memory/consolidate/apply` | §2.15.1：逐条应用一条建议（幂等 supersede） |
| `POST /api/v1/agent/memory/consolidate/pass` | §2.15.3：跑一次确定性巩固审计 `{scope}` → `{ok, scope, generatedAt, kept, merged[], retired[]}`；**只出建议、不删** |
| `GET /api/v1/agent/memory/consolidate/diff` | §2.15.3：读上次审计结果（`{ok, scope, generatedAt, kept, merged, retired}`）；没跑过 → 404 `not_found` |
| `POST /api/v1/agent/memory/import` | §2.15.2：把旧记忆只增不改地并进来 |

`items[]` 一条的形状：`{id, kind, scope, content, importance, veracity, source, createdAt,
recallCount, supersededBy}`。`kind` ∈ `preference` / `fact` / `episode` /
`entity` / `intention` / `experience` / `work`（`work` 是履历台账，档案页专用；2026-11-10 批 17 加
`experience`）。`usageCount` / `lastUsedAt` 目前只进巩固审计 diff，不在本列表回吐。

**`canConsolidate` / `canImport`（2026-11-08，纯增量能力位）**：分别由
`MEMORY_CONSOLIDATE_LLM` / `MEMORY_IMPORT` 下发；前端据此决定渲不渲染「整理记忆」「导入记忆」。
关着时对应端点 404。老客户端忽略这两个字段即可（与 `GET /agent/policy` 的 `attachments` 同口径）。

**列表口径**：默认只列 `global`、**不含已被取代的**、不含 `session` scope 的原始沉淀
（那是对话正文的副产品，清理走删会话）。排序 = `preference → fact → entity → episode`，
组内按 `createdAt` 倒序；`byKind` 是当前返回集内的分项计数。
`importance` 是库里的**当前值**（召回命中会 +0.05、久未想起会按 `MEMORY_DECAY_DAILY` 衰减，
下限 0.1 / 上限 10）。

`extract` 是**实际生效**的抽取档：`llm` = 偏好走一次独立模型调用、其余走规则；
`rule` = 全规则（也包含"模型不可用"的降级结果）。取值来源见 §6 的 `MEMORY_EXTRACT`。

**错误口径**（与其它管理端点一致）：
- 记忆未启用（`MEMORY_ENABLED=false` 或初始化失败）→ **404 `memory_disabled`**（不是 503：
  这不是"依赖暂时不可用"，是这个能力在这台机器上没开）；
- id 为空 → 400；`byId` 不是字符串 → 400；`scope` 不是 `global` / `partner:<id>` → 400；
- 鉴权失败仍是 403 空体（§1，中间件统一处理）。

#### 2.15.1 整理记忆（2026-11-08 扫尾批 6 §二，`MEMORY_CONSOLIDATE_LLM`）

**语义（D18 底线）**：模型**只产出建议**，一条都不自动执行。应用必须由人在设置页逐条点
「应用」，走既有 `supersede()`（旧记录保留、可追溯）。**没有"全部应用"**。

`POST /api/v1/agent/memory/consolidate/review`

- 请求 `{"scope":"global"}`（或 `partner:<uuid>`）。
- 取该 scope **最近 ≤200 条**（不含已被取代的）喂给一次独立模型调用（默认模型链、不进主会话），
  超时 30s，最多 50 条建议。
- 响应：

  ```json
  {
    "ok": true, "scope": "global", "total": 42, "generatedAt": "2026-11-08T…",
    "proposals": [
      { "keepId": "…", "dropId": "…", "reason": "后一条已过时",
        "keep": {"id":"…","kind":"fact","content":"我搬到上海了","importance":0.72,"createdAt":"…"},
        "drop": {"id":"…","kind":"fact","content":"我住在北京","importance":0.5,"createdAt":"…"} }
    ]
  }
  ```

- `keep` / `drop` 是两端正文（前端不必再反查列表）；`keepId` / `dropId` 必须来自本次清单——
  模型编造的 id、自指、重复对一律丢弃（宁可少建议）。
- 少于 2 条记忆 → `proposals: []`，**不打模型调用**。
- 待决建议落 `.data/memory-proposals.json`（按 scope 存，可用 `MEMORY_PROPOSALS_PATH` 覆盖；
  原子写，坏文件当空账）。它只是"上次生成了什么"，刷新不回放，重新整理会覆盖。
- 失败口径**如实 5xx，不假装**：未配置可用模型 / `LLM_PROVIDER=faux` → 503
  `llm_not_configured`；调用失败 / 超时 / 输出解析不了 → 502 `llm_failed`。
- `MEMORY_CONSOLIDATE_LLM=false`（或 `0` / `off`）→ 本组两个端点 **404**（同"未启用"口径）。

`POST /api/v1/agent/memory/consolidate/apply`

- 请求 `{"scope":"global","keepId":"…","dropId":"…"}` → `{ok, scope, keepId, dropId, alreadyApplied}`。
- **幂等**：`dropId` 已经指向同一个 `keepId` → 200 `alreadyApplied: true`，不再写一次；
  指向别的记录 → 400 `already_superseded`。
- `keepId` / `dropId` 不存在或不属于该 scope → 404 `not_found`；两者相同 → 400。
- 成功应用后从待决文件摘掉这一条（刷新再点整理不会重复弹同一张卡）。

#### 2.15.2 导入记忆（2026-11-08 扫尾批 6 §三，`MEMORY_IMPORT`）

`POST /api/v1/agent/memory/import`

- 请求：

  ```json
  {
    "scope": "global",
    "items": [
      { "text": "我住在上海", "kind": "fact", "createdAt": "2023-05-01T00:00:00.000Z", "importance": 0.7 }
    ]
  }
  ```

  - `scope`：`global` 或 `partner:<uuid>`；
  - `items`：数组，单次上限 5000 条；
  - `text`：必填，非空、≤2000 字；
  - `kind`：可选，`fact`（缺省）/ `episode` / `preference` / `entity`；认不出的值整条跳过；
  - `createdAt`：可选，合法 ISO 就保留；非法或缺省 = now；**未来时间裁到 now**；
  - `importance`：可选，缺省 `0.5`，夹到 `[0.1, 1]`。
- 响应 `{ok, scope, added, skipped, total}`（只报条数，不回显正文）。
- **只增不改**：绝不覆盖 / 删除 / 修改已有记录（不提升 importance、不改正文）。
  规范化等价（同 scope + 同 kind，trim / 空白折叠 / 全半角统一 / 句末标点剥除后相等）→
  **跳过并计数**；同一批内的重复同样跳过；**已被取代的记录也算"已经存在"**
  （不把用户明确标过时的内容重新捞回来）。
- 导入记录 `source="imported"`、`veracity="imported"`，照常参与召回；
  **不参与"重复收敛"去重别人**（不提升别人、不取代别人），只会被别人收敛（后续真实对话撞上它时照常 +0.1）。
- 文件格式（设置页「导入记忆」）：**裸数组**，或 `{"items":[...]}`；条目字段同上。
  前端只解析 + 数条数，不预检内容；确认后整份交给服务端逐条校验。
- `MEMORY_IMPORT=false`（或 `0` / `off`）→ 端点 **404**、按钮不渲染。

#### 2.15.3 巩固审计（2026-11-10 批 17 §三，`MEMORY_USAGE_RANKING` 默认开）

**确定性、只读**：算一份「可合并 / 建议淘汰 / 留下几条」的差异摘要，落
`.data/memory-consolidate-diff.json`（可用 `MEMORY_CONSOLIDATE_DIFF_PATH` 覆盖；原子写）。
**淘汰只出建议，绝不自动删**——没有"应用淘汰"端点；删一条仍走 `DELETE /memory/:id`。

`POST /api/v1/agent/memory/consolidate/pass`，请求 `{"scope":"global"}`（或 `partner:<uuid>`）：

```json
{
  "ok": true, "scope": "global", "generatedAt": "2026-11-10T…", "kept": 41,
  "merged": [{ "keepId": "…", "dropId": "…", "summary": "≤40 字" }],
  "retired": [{ "id": "…", "kind": "fact", "summary": "≤40 字" }]
}
```

- **保留优先级**：`usageCount` 降序 → `lastUsedAt` 降序 → `createdAt` 降序。`usageCount` /
  `lastUsedAt` 在召回命中时 +1 / 置为 now（与 `recallCount` 同点），只服务巩固排序。
- **合并建议**：同 scope + 同 kind + 规范化等价（work / intention 除外），保留优先级最高的那条。
- **淘汰建议**：距 `lastUsedAt ?? lastRecalledAt ?? createdAt` > 90 天、`importance < 0.5`、
  kind 不是 `preference` / `experience` / `work` / `intention`（有效打算不淘汰）。已被列为合并 drop 的不再重复列。
- `kept` = 总数 − 合并建议数 − 淘汰建议数。文件里只记 id、kind 与 ≤40 字摘要，**不记正文**。
- `GET /api/v1/agent/memory/consolidate/diff` 读同一份；没跑过 → 404 `not_found`。
- `MEMORY_USAGE_RANKING=false`（或 `0`）：保留优先级回到 `createdAt` 倒序、**不给淘汰建议**（`retired: []`），diff 形状不变（一行回滚）。
- `POST /consolidate/review` 成功后自动跑一次本审计（模型失败则不落快照）。

**刻意没有**：编辑（改记忆等于让它变成第二个人格，删了重说更干净）、全文搜索、
导出、跨设备同步、**语义自动去重 / 自动冲突消解 / 自动删除**（`supersede` 只做显式取代，
模型只出建议、人拍板；理由见架构 D18）、后台巩固 cron、embedding、**"全部应用"按钮**。

### 2.18 权限策略（`/api/v1/agent/policy`，2026-11-03 访问档 / 2026-11-08 扫尾批 10-C 审批三档）

界面「权限档」三档（能力边界）与「审批档」三档（确认策略）的读写端点，与 §2.5 审批端点、§4 闸门同源
（`ts/apps/server/src/agent/policy.ts` 的 `getPolicy` / `setPolicy` / `readOnlyBlockReason`，
路由 `ts/apps/server/src/index.ts:422/424`）。`beforeTool` 每次调用都重判策略，
**改完立刻生效、不用重启**；选择落 `.data/policy.json`，下次启动沿用，env 只是初值
（`AGENT_TOOL_POLICY` → `access`、`AGENT_BLOCKED_TOOLS` → `blocked`、
`AGENT_CONFIRM_WRITES` → `approvalLevel` 的旧布尔映射，见 §6）。两轴独立：三档是能力边界，
`approvalLevel` 是确认策略；被档位拦下时不问直接拒（拦优先，`approval-policy.ts`）。

#### `GET /api/v1/agent/policy` —— 当前策略

```json
{ "access": "full", "blocked": [], "approvalLevel": "none", "confirmWrites": false, "label": "完全访问", "approvalMode": "async", "attachments": true, "editResend": true }
```

- `access`：`full` / `read-only` / `no-shell`；`read-only` 拦 `WRITE_TOOLS`（写/改/跑/派活/建群等），
  `no-shell` 只拦 `bash` / `powershell`，`blocked` 黑名单命中即「工具 X 已被禁用」（优先级最高）。
- `label`：`access` 的中文展示名（「完全访问」/「只读」/「不跑命令」），前端直接显示。
- **`approvalLevel`（2026-11-08 扫尾批 10-C）**：审批三档——`ask-all`（全部问我：`WRITE_TOOLS` ∪ 高危清单全问，
  旧 `confirmWrites:true`）/ `ask-critical`（只问重要的：只问高危清单）/ `none`（全不问，旧 `confirmWrites:false`）。
  高危清单缺省 `bash` / `powershell` / `delegate` / `partner_manage` / `send_to_agent` / `routine_manage`，
  `AGENT_APPROVAL_CRITICAL_TOOLS` 可整体覆盖（§6）。
- **`confirmWrites`（派生字段，兼容旧客户端）**：`approvalLevel !== "none"` 时为 `true`。
  新客户端读 `approvalLevel`；旧客户端只认布尔，语义是"是否至少有一部分操作会问"。
- **`approvalMode`（2026-11-08 扫尾批 8c，纯增量只读投影）**：`async`（缺省，等待态落库、答复触发续跑）
  或 `blocking`（旧的 120s 阻塞形态）。来自环境变量 `AGENT_APPROVAL_MODE`（§6），**不落
  `.data/policy.json`、不可通过 `POST` 修改**。前端据此决定审批卡显示倒计时（blocking）还是
  「等待处理」（async）。
- **`attachments` / `editResend`（2026-11-08 扫尾批 4a，纯增量只读投影）**：
  两个**环境变量**开关（`AGENT_ATTACHMENTS` / `AGENT_EDIT_RESEND`，§6）的当前值，前端据此
  决定渲染不渲染附件按钮 / 编辑入口。它们不可通过 `POST` 修改（改的是 env），
  `POST` 的响应也带这两个字段（形状同 `GET`，仍不含 `label`）。

#### `POST /api/v1/agent/policy` —— 改策略（部分更新）

请求体字段都可选，只更新给出的；`blocked` 非数组时该字段忽略：

```json
{ "access": "read-only", "blocked": ["bash", "powershell"], "approvalLevel": "ask-critical" }
```

旧布尔仍收：`{ "confirmWrites": true }` → `ask-all`、`false` → `none`；同一请求里
`approvalLevel` 优先于 `confirmWrites`。成功回更新后的完整策略（**不含 `label`**，带审批形态与两个能力开关）：

```json
{ "ok": true, "access": "read-only", "blocked": ["bash", "powershell"], "approvalLevel": "ask-critical", "confirmWrites": true, "approvalMode": "async", "attachments": true, "editResend": true }
```

| 情形 | 返回 |
|---|---|
| `access` 不是 `full` / `read-only` / `no-shell` | `400 {"error":"bad_request","message":"access 只能是 full / read-only / no-shell"}` |
| `approvalLevel` 不是 `ask-all` / `ask-critical` / `none` | `400 {"error":"bad_request","message":"approvalLevel 只能是 ask-all / ask-critical / none"}` |
| 带 `confirmWrites` 但不是布尔值 | `400 {"error":"bad_request","message":"confirmWrites 只能是布尔值"}` |
| body 非 JSON / 空体 | 各字段都不更新，返回当前策略（`{ok:true, …}`） |
| 写 `.data/policy.json` 失败 | 仍 200，本次内存态生效（服务端日志告警；重启回落旧值） |

**落盘与读档兼容**：`policy.json` 存 `approvalLevel`（不再写 `confirmWrites`）；读档时新字段优先，
老文件只有 `confirmWrites` 就按 `true→ask-all / false→none` 映射，两者都没有才回落 env 初值。

**权限**：与其他 `/api/v1/*` 同——`Authorization: Bearer <AGENT_TOKEN>` 或本机页面 cookie（§1），
失败一律 **403 空体**。端点不回显任何密钥。前端调用：`web/app.js` 的 `loadPolicy()`
（全屏设置页 `#policy-switch` / `#policy-approval-level`）与抽屉版 `cs-policy-*`（`GET` 读档、`POST` 回写）。

### 2.19 技能管理（2026-11-08 扫尾批 9-S；2026-11-08 批 10-A 加标准用户目录与两种形态；`SKILLS_ADMIN` 默认开）

技能 = 给模型的操作手册，两种文件形态都认：

- **扁平 `<name>.md`**（本仓库原生形态）：**第 1 行 = 索引用摘要，其余 = 正文**；`name` 即文件名。

`name` 受管理面白名单约束（小写字母 / 数字 / 短横线 / 下划线，1-64 字符，不能以 `-`/`_` 开头，

1. `AGENT_SKILLS_DIR` 显式指定（部署自选目录，不替用户创建；显式时**取代**用户目录槽位，不再建 `.lifediary\skills`）；
2. 用户目录 `%USERPROFILE%\.lifediary\skills`——**不存在则首次访问自动 mkdir**（管理界面写这里）；
3. 标准用户技能目录 `%USERPROFILE%\.agents\skills`——跨工具共享的 agent skills，**只读**（不存在就跳过）；

- **增删改与启停只影响下一个会话**（D5 既有取舍：技能索引按会话冻结，首轮渲染后不再变；
  `skill` 工具取手册不受此限——启停即时）；设置页文案如实说明。

### 2.20 高级开关（2026-11-09 界面细节批二；`AGENT_FLAGS_UI` 默认开）

把散在 env 里的**用户行为开关**搬进设置 → 服务 → 「高级开关」。机制（`flags.ts`）：
`.data/agent-flags.json`（`AGENT_FLAGS_PATH`）存界面覆盖值，**启动时覆盖写进 process.env**（在
loadEnvFile / injectProviderKeys 之后、路由挂载之前），`setFlag` 落盘并同步写 env——消费代码全是
函数内懒读 env（2026-11-09 逐处核对），热开关当场生效；启动期冻结类（路由挂载 / 工具注册 / 模块常量）
标 `hot:false`，界面如实报「重启服务后生效」。env 仍是缺省来源：文件里没写的键完全回到 env 行为
（**回滚 = 删文件**）。

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/flags` | `{flags:[{key, value, defaultValue, hot, overridden}]}`——`value` = 当前生效值（env 现值，缺省回落 defaultValue）；`overridden` = 界面文件里改过 |
| `PUT /api/v1/agent/flags/:key` | body `{value}`；key 必须在白名单、value 必须合法，否则 400/404。成功 `{ok, key, value, hot}` |

白名单 17 项（`flags.ts` FLAG_DEFS）：`AUTONOMY_ENABLED`（true/false/observe 三值，2026-11-09 T2）/ `AGENT_ATTACHMENTS` / `AGENT_EDIT_RESEND` /
`CURRENT_PROJECT` / `MEMORY_ENABLED` / `MEMORY_EXTRACT`（auto/llm/rule）/ `MINISTER_DISPATCH_AUTHORITY` /
`DEVICE_AUTO_DISPATCH` / `PARTNER_WORK_RECORD` / `PERSONA_MEMORY_ENABLED` / `PERSONA_EXPORT_ENABLED`
（persona 记忆库接入 2026-11-09：查 = `persona_recall` 的显式关闸、送 = 主对话导出，两项都即时生效；
查询还要求 `PERSONA_MEMORY_ASK` 配了 ask.py 路径才上架——路径类 env 刻意不进界面，开关文案里写明）
（以上即时生效）+ `SKILLS_ADMIN` / `ROUTINE_SELF_SERVICE` /
`COMPANIONS_ENABLED` / `GROUPS_ENABLED` / `CHANCELLOR_ENABLED` / `TOPICS_ENABLED`（重启生效）。
**刻意不收**：路径、令牌、密钥类 env。
**已知缺陷修复（2026-11-09 persona 接入批三顺手修）**：`app.js` 的 `toggleFlag` 原写
`String(value === "true")`——布尔拨杆路径传 boolean，严格比较恒 false，导致**所有布尔拨杆**点击后
服务端已保存但 UI 不翻（分段控件传字符串不受影响）。修为 `String(String(value) === "true")`。

### 2.21 bash 后台任务管理（2026-11-10 批 21 §二；`AGENT_BASH_BG_TIMEOUT` 开时才挂）

批 11 只做了"超时转后台 + 结果回灌"；这一节补管理面。**三个端点都在 `AGENT_BASH_BG_TIMEOUT`
关着时整组不挂（404）**，索引落点 `AGENT_BG_JOBS_DIR`（默认 `.data/bg-jobs`，探针隔离用）。

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/bg-jobs` | `{ok, jobs:[{id, commandSummary, startedAt, endedAt\|null, exitCode\|null, status}]}`，index 顺序；索引读失败 → 503 |
| `GET /api/v1/agent/bg-jobs/:id/log` | `{ok, id, lines, log}`：`lines` = 整份日志行数，`log` = **最后 ≤200 行**（末尾换行不算一行）。未知 / 非法 id → 404 |
| `POST /api/v1/agent/bg-jobs/:id/kill` | 只杀**本进程起的、仍在跑**的任务（POSIX 杀进程组、Windows `taskkill /T`）。成功 `{ok,id,status:"killed"}`；未知 id → 404；不是本进程起的 / 已结束 → 409（`not_owned_process` / `not_running`） |

- 进程归属只看本进程内存表：重启后 index 里的 `running` 一律当"没有活进程"，**绝不按 pid 杀**（pid 会复用）。
- 启动时裁剪：`index.json` 超过 200 条 → 从最旧的**已结束**任务开始删索引条目；在跑的不删，
  **日志文件一个都不删**（按 id 仍能找回原始输出）。
- 日志正文只进响应体；服务端日志只记条数 / 耗时 / 枚举。
- `AGENT_BG_JOBS_DIR` 只是测试 / 探针的落点隔离（同 `.data/*` 的既有 `*_PATH` 口径），不是部署换目录的开关。

  旧库启动时 ALTER 补列；`null` = 该版本没有契约快照）。
- 会话种类 / 首次问候状态：durable 的 conversation/session doc（`lifediary.chat-kinds`、
  `lifediary.partner-greeting`，2026-11-06 B2/B3）。身份与去重跟会话同在，不放前端存储。
- 执事家目录：`PARTNER_HOMES_ROOT`（默认 `.data/partner-homes/<uuid>/`；单槽 64KB、原子写、播种幂等）。
  文件：`SOUL.md`（人格当前值）/ `CONTRACT.md`（岗位契约当前值，2026-11-08 刀一 E1；新建执事播种
  四节空模板，存量不补）/ `memories/USER.md` / `workspace/` / `skills/`。
- 例行任务执行账：`ROUTINES_STATE_PATH`（默认 `.data/routines.json`，原子写；回执去重 24h 滑窗 + runs ≤50 条）。
- 课题账：`TOPICS_STATE_PATH`（默认 `.data/topics.json`，原子写；课题与提议同文件，提议 72h 过期，findings 每课题一份、不进记忆引擎）。
- 派单死信：`delegations.sqlite` 内 `delegation_dead_letters` 表（批次A A2；父单终态后子单结果无处并入的记账）。
- **主对话导出（2026-11-09 persona 接入批二）**：`PERSONA_EXPORT_ENABLED=true` 时，每轮真正收尾
  （settled done）向 `PERSONA_EXPORT_DIR`（默认 `.data/persona-export/`）的 `<yyyy-mm>.jsonl` 追加一行；
  一行一轮、UTF-8、`\n` 结尾。行格式（**契约只有一份**，voicevault 的
  `experiments/import_lifediary.py` 照此解析）：
  `{"v":1,"conversationId":"<对外 uuid>","turnId":"<durable 轮 id>","ts":"2026-11-09T20:15:03+08:00","userText":"…","assistantText":"…","model":"…"}`。
  `ts` 是带本地时区偏移的 ISO 8601；`assistantText` 只含本轮最终回复（不含工具过程、不含图片）；
  user / assistant **至少一个非空**，全空轮不写；`model` 拿不到写空串。只导主人主对话：
  `task-` 前缀、群会话、执事会话一律不写。幂等链由导入方负责
  （voicevault `uid=sha1("lifediary"|sid|ts|user_text)[:20]` + INSERT OR IGNORE）。
  导出文件是隐私产物，只落 `.data`（git 忽略）；日志只记轮数 / 字数 / 文件名，不记原文。
- 防打转守卫状态：进程内存（一轮一实例，崩溃即失，护栏不是账本）。
- **对外 `conversationId` = 服务端生成的 uuid**；durable 内部是自增整数，通过 session 文档 `lifediary.chats` 的
  `byExternal` 映射转换，**整数不暴露**（猜得到就能读别人的历史）。

- **中途播报 `report_progress`（2026-11-10 批 13 §三，默认上架；`AGENT_PROGRESS_REPORT=false` 一行回滚）**：
  参数 `{message ≤200 字}`。语义 = **长任务中途对主人说一句，不结束本轮**；与 steer 正交（那是人→agent）。
  送达 = 向**正在流式的那条会话**发一条 `notice` 帧（`【进度】…`，`delegation.ts` 的 emitDelegation 通道），
  若当前会话正好是任务专线再镜像一条。**不落盘，没开流就收不到**（不伪造主人的时间线）。
  频率闸：同一会话**每轮最多 3 条**，第 4 条起返回"合并成一条再说"的引导话术（不是错误）。
  上架范围：只有**执事轮与任务专线**；主人（总管）对话 / 群会话由 beforeTool 结构性拦下。
  **不进 `WRITE_TOOLS` / 高危清单**（不写盘、不起进程），只登记能力声明（`sideEffectScope:"none"`,
  `riskLevel:"low"`），一致性守卫单测覆盖。
- **执事汇报卡三规则（2026-11-10 批 15 §二，`BRIEF_CARD_RULES` 默认开）**：
  在**普通执事**的纪律段注入一段固定文案 `BRIEF_CARD_RULES`：①没有值得报的就不发（宁可安静，
  不要"今天一切正常"）；②同一件事有更新就改原来那条，不新开；③只在"今天第一次打开"或
  "离开三小时以上回来"时出现，永不抢屏（不弹窗、不打断）。本批**只落文案与纪律**，
  触发时机由宿主决定（不做推送通道）。总管纪律段不变（界面时间线自承载）。
  `BRIEF_CARD_RULES=false`/`0`/`off` → 纪律段回到改动前（逐字节一致）。
- **无人值守权限语义（2026-11-10 批 13 §一/§二，`AGENT_UNATTENDED_POLICY` 默认 **false**）**：
  判定"这一轮没人看着" = 例行任务轮 / `task-` 前缀会话 / `AGENT_UNATTENDED=1` 任一成立。
  开关打开后，beforeTool **先于一切审批判定**把工具收口成**三态，绝不落 pending 等人**：
  - `allow`：纯读 / 只写内部状态（`read` / `recall` / `remember` / `web_search` 等），
    **执行且不再走审批**（避免自定义 `AGENT_APPROVAL_CRITICAL_TOOLS` 仍把它问成 pending）；
    显式 block（黑名单 / 只读档）仍优先；
  - `skip`：需要花钱或需要人批准（`write` / `edit` / `bash` / `powershell` / `delegate` /
    `propose_project` / `partner_skill_write` / `persona_recall` / `ask_user` / `set_reminder`
    等）——**不执行**，回固定话术 `UNATTENDED_SKIP_MESSAGE`
    （"这一步需要花钱 / 需要人批准，已跳过…最后在结果里明确写出"），并记入本轮跳过账；
  - `deny`：会给自己扩权 / 影响系统（`partner_manage` / `group_manage` / `routine_manage` /
    `send_to_agent` / 删除类）——显式拒绝并给原因。
  例行 run 记录 `skipped:true` + `skipReason`（只记工具名枚举，不记参数与正文），`outcome="skipped"`。
  开关关着时这一整块不执行，行为与改动前逐字节一致（探针 `gate` 两档照常）。
- **执事间递话（2026-11-08 扫尾批 8d，`send_to_agent`）**：A 给 B 递一条话。
  送达 = 向**目标执事主会话**提交一条 user 输入（durable `submit`，`whenBusy=followUp`）——
  目标忙就排队到本轮收尾、空闲就直接起一轮；**零新增存储**（没有信箱表，消息本体就是对方
  transcript 里那句话）。送达正文 = `[relay hop=1][来自执事 A（域）] <message>\n（这是执事间
  递话，主人看不到原文；需要主人知情或回话请用汇报或主人对话。）`。
  **防乒乓三条（结构保证，不是提示词）**：
  1. **hop 恒为 1** —— 递话触发的目标轮次里 `send_to_agent` 被 beforeTool 结构性摘掉
     （进程内 run 标记，`beforeRequest` 认领）；B 要回 A 只能用自己的话新起。
  2. **每 run 最多 3 条** —— 第 4 条起回引导话术（"合并成一条"），不是错误、本轮可继续。
  3. **转述拒绝** —— `message` 里含 `[relay hop=1]` 标记（贴别人的递话原文）一律拒绝。
  **可用范围**：只有执事自己的会话能调；主人对话 / 总管 / 群成员会话 / 例行任务轮
  （autonomy）一律在 beforeTool 拦下（各有一句说明）。目标必须是 active 执事且**已经建过会话**
  （`partner_session_links` 的 canonical 链接）；重名不猜、返回 `名字·领域` 候选；查无此人列出
  现有执事；指向自己 / 总管直接拒绝。
  **主人知情**：递话成功时向**正在流式的主对话**发一条 `notice` 帧
  （`执事「A」→「B」：递了一条话（正文不在这里…）`），不展示正文。与派单进度同款——
  进程内轻事件，没开流就收不到、不落盘（不伪造主人的时间线）。
  **两态回执（2026-11-10 批 15 §五，`PARTNER_RELAY_RECEIPT` 默认开）**：`send_to_agent` 的返回
  明确 `queued`（已投递到对方会话，不代表已处理）；对方那一轮**真的结算**后，一条 `notice` 帧
  回流到**发送方正在流式的会话**（`「B」处理完了你递的那条话：<一句话结果>`，≤160 字），

  `data.receipt="settled"`）。没开流时 notice 收不到，但 transcript 那条照写。
  `PARTNER_RELAY_RECEIPT=false`/`0`/`off` → 只保留旧的"已递给"文案，不订阅结算、不回流、不写留言。
  **仍不做多跳**（hop 恒为 1 不变）、不做 bot_loop_guard（那是开两跳时才需要的）。
  已知边界：目标会话正被 `/stop` 或撞回合上限**硬停**时，排队的 followUp 会被内核
  abort 一并撤回（内核语义，不是本功能丢）；主对话没开流时收不到那条 notice。完整口径见
  `系统架构.md` D21。

| `POST /api/v1/pair/redeem` | **免** | **单段 / 回滚通道**：`{code, deviceName}` → `{deviceToken, deviceId, fingerprint?, name, version}`（`deviceId` / `fingerprint` 2026-11-10 批 26 §四 增，纯增量）；错误见下表。**`PAIR_TWO_STEP=true`（默认）时本端点收紧关闭 → `410 {"error":"two_step_required"}`**，否则"只扫码拿到 code 就能兑凭据"会让两段式形同虚设；`PAIR_TWO_STEP=false` 才逐字节回到旧单段行为 |
| `POST /api/v1/pairing/begin` | 需 | **两段式第一段（2026-11-10 批 28 §一）**：电脑端起一枚两段式码 → `{code, expiresAt, confirmToken}`。`code` 给手机扫（进二维码），`confirmToken` 只回电脑端确认用、**不随二维码下发**。`PAIR_TWO_STEP=false` → `404` |
| `POST /api/v1/pairing/confirm` | **免** | **两段式第二段**：body `{code, confirmToken, deviceName?}` → 才真正发 `{deviceToken, deviceId, fingerprint?, name, version}`。**只给 code 不能完成**——必须有人在电脑端把 `confirmToken` 输进去（手机绝不代确认）；错误见下表。`PAIR_TWO_STEP=false` → `404` |
| `GET /api/v1/pair/devices` | 需 | → `{devices:[{id, name, createdAt, lastSeenAt?, revokedAt?, fingerprint?, keyChanged?, keyChangedAt?}]}`（**不含 tokenHash**；指纹与键变更位见下） |
| `POST /api/v1/pair/devices/:id/revoke` | 需 | → `{ok:true}`；撤销后该 deviceToken **立即 403** |
| `GET /api/v1/agent/chats` | 需 | 会话索引：`{chats:[{conversationId, createdAt, lastAt, firstText, turns, pinned, chatKind}]}`，**只元数据不含正文**，按 `lastAt` 倒序（`pinned` 2026-11-04 批次一；`chatKind` 2026-11-06 B2 = `chief`/`worker`/`partner`，前端据此筛总管入口） |

`redeem` 错误口径：

| 场景 | 状态码 | body |
|---|---|---|
| 缺 code | 400 | `{"error":"bad_request"}` |
| 码不存在/错 | 404 | `{"error":"unknown_code"}`（同一码错 5 次后转 429） |
| 已用过 | 409 | `{"error":"code_used"}` |
| 已过期 | 410 | `{"error":"code_expired"}` |
| 同一 IP 每分钟 >10 次，或该码错满 5 次 | 429 | `{"error":"too_many_attempts"}` |

**两段式 `confirm` 错误口径（2026-11-10 批 28 §一）**：

| 场景 | 状态码 | body |
|---|---|---|
| 缺 code | 400 | `{"error":"bad_request"}` |
| 只给 code、没给 `confirmToken`（只有扫码） | 400 | `{"error":"confirm_required"}` |
| `confirmToken` 错 | 400 | `{"error":"bad_confirm"}` |
| 不是待确认的两段式码 / 码不存在 | 404 | `{"error":"unknown_code"}` |
| 重放（code / `confirmToken` 一次性，成功即作废） | 409 | `{"error":"code_used"}` |
| 已过期（code 与 `confirmToken` 同生共死） | 410 | `{"error":"code_expired"}` |
| 同 IP 每分钟 >10 次，或该码错满 5 次 | 429 | `{"error":"too_many_attempts"}` |

`confirmToken` 一次性、随 `code` 一起 5 分钟过期（默认 `PAIR_CODE_TTL_SECONDS=300`）、与 `code` 绑定（同一记录）；
**尝试次数计入既有 `attempts` 限流**（与 `redeem` 共用一个计数器、共用 5 次上限）。两段式码带 `confirmHash`，
从单段 `redeem` 视角不是可兑的码（store 层也兜了一层 `unknown_code`）。回滚：`PAIR_TWO_STEP=false` →
`begin` / `confirm` 整组 `404`，`redeem` 恢复单段。**诚实登记**：默认 `true` 下旧的 `/pair` 扫码页 / 旧手机端
单段流程因 `redeem` 收紧而不再能完成配对，需 `PAIR_TWO_STEP=false` 回滚或后续接两段式 UI（手机端另说）；
本批只交付服务端契约与端点（接口先行）。

鉴权扩展（`auth.ts`）：`Bearer` 现在接受 **`AGENT_TOKEN` ∪ 有效 deviceToken**；撤销即失效。
未配 `AGENT_TOKEN` 时 loopback 仍直通、局域网访问必须持有效 deviceToken。

存储（`pairing.ts`）：`.data/pairing.json`（`PAIRING_STORE_PATH` 可改）——**码、confirmToken 与设备令牌都只存 sha256**
（2026-11-10 批 28 §一：`confirmHash` 只在 `begin()` 签发的码上），明文只在签发那一刻返回；
设备上限 32 台（超出按最久未用淘汰）。

**设备指纹与键变更 fail-closed（2026-11-10 批 26 §四）**：

- `fingerprint = 前 12 位十六进制(sha256("lifediary-device-v1|<deviceId>|<tokenHash>"))`，按 `XXXX-XXXX-XXXX` 分组。
  用途只有一个：**人眼核对**（电脑 `/pair?token=…` 设备面板与手机端显示的字符串逐字符比对）；
  48 bit 不可反推令牌，**不当凭据**（鉴权仍只认 deviceToken 的 sha256）。
- 配对成功时随 `redeem` 下发，设备清单里同值；老记录（没有指纹）在服务启动时**补算写入**，不算键变更。
- **键变更 = fail-closed**：文件里的 `tokenHash` 与已存指纹对不上（文件被改 / 从别的机器搬来）→
  该设备标记 `keyChangedAt`，`verifyDeviceToken` 一律拒绝，直到主人撤销 / 重新配对。
  标记持久化，不因重启消失；**不静默按新键认**（否则等于把别人换进来的键当成主人）。
- 回滚：`PAIR_DEVICE_FINGERPRINT=false` → 不生成 / 不下发指纹，也不做键变更判定（恢复 2026-11-10 之前形态）。

已知代价（如实登记）：`GET /agent/chats` 为了拿首句与时间会逐会话读一遍 context，会话很多时会变慢；
真到那时应改用 durable 的 entries 分页 + 单独维护索引。
