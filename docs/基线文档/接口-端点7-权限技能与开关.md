### 2.18 权限策略（`/api/v1/agent/policy`，2026-11-03 访问档 / 2026-11-08 扫尾批 10-C 审批三档）

界面「权限档」三档（能力边界）与「审批档」三档（确认策略）的读写端点，与 §2.5 审批端点、§4 闸门同源
（`ts/apps/server/src/agent/policy.ts` 的 `getPolicy` / `setPolicy` / `readOnlyBlockReason`，
路由 `ts/apps/server/src/index.ts:422/424`）。`beforeTool` 每次调用都重判策略，
**改完立刻生效、不用重启**；选择落 `.data/policy.json`，下次启动沿用，env 只是初值
（`AGENT_TOOL_POLICY` → `access`、`AGENT_BLOCKED_TOOLS` → `blocked`、
`AGENT_CONFIRM_WRITES` → `approvalLevel` 的旧布尔映射，见 §6）。两轴独立：三档是能力边界，
`approvalLevel` 是确认策略；被档位拦下时不问直接拒（拦优先，`approval-policy.ts`）。

#### `GET /api/v1/agent/policy` —— 当前策略

```json
{ "access": "full", "blocked": [], "approvalLevel": "none", "confirmWrites": false, "label": "完全访问", "approvalMode": "async", "attachments": true, "fileAttachments": true, "editResend": true, "flagCascade": true, "pluginSurfaces": true }
```

- `access`：`full` / `read-only` / `no-shell`；`read-only` 拦 `WRITE_TOOLS`（写/改/跑/派活/建群等），
  `no-shell` 只拦 `bash` / `powershell`，`blocked` 黑名单命中即「工具 X 已被禁用」（优先级最高）。
  2026-11-14 起两档都先试一次**查看命令**判定（`isViewOnlyShellCommand`：词表只有
  `cat`/`type`/`head`/`tail`/`ls`/`dir`/`grep`/`rg`/`find`/`wc`/`stat`/`file`，看旗标，
  路径必须落在已登记根集合内）——命中则放行，其余照旧拦。`AGENT_READ_VIEW_COMMANDS=0` 关掉回旧形态。
  **2026-11-20 权限三档收口**：`full` 下 `write` / `edit` / `read` 都**不再过**路径闸门
  （`AGENT_FULL_ACCESS_PATH_GUARD=1` 可回滚到旧的限根形态）；`read-only` / `no-shell` 两档
  把 `read` 也纳入 root 校验（`AGENT_READ_PATH_GUARD=0` 可回滚），用户在本会话附上来的文件
  （`FilePart.path`）对 `read` 例外放行，`write` / `edit` 不享受这个例外。
  `bash` / `powershell` 在 `full` 下仍不扫命令文本——这是既有已知边界（`系统架构.md`）。
- `label`：`access` 的中文展示名（「完全访问」/「只读」/「在工作区内修改」），前端直接显示。
  2026-11-14 起 `no-shell` 的对外名字改成「在工作区内修改」（值不变，老客户端照旧）；界面上三档
  从左到右 = 只读 → 在工作区内修改 → 完全访问，完全访问恒在最右端。
  三档的副文与语义：只读 = 能看能查（ls / cat / grep 这类查看命令），不改文件，查看也限工作区和项目里；
  在工作区内修改 = 文件读写和查看都限工作区和项目里，命令只放行查看类；
  完全访问 = 文件读写和命令都不受工作区限制。
- **`approvalLevel`（2026-11-08 扫尾批 10-C）**：审批三档——`ask-all`（全部问我：`WRITE_TOOLS` ∪ 高危清单全问，
  旧 `confirmWrites:true`）/ `ask-critical`（只问重要的：只问高危清单）/ `none`（全不问，旧 `confirmWrites:false`）。
  高危清单缺省 `bash` / `powershell` / `delegate` / `partner_manage` / `send_to_agent` / `routine_manage`，
  `AGENT_APPROVAL_CRITICAL_TOOLS` 可整体覆盖（§6）。
- **`confirmWrites`（派生字段，兼容旧客户端）**：`approvalLevel !== "none"` 时为 `true`。
  新客户端读 `approvalLevel`；旧客户端只认布尔，语义是"是否至少有一部分操作会问"。
- **`approvalMode`（2026-11-08 扫尾批 8c，纯增量只读投影）**：`async`（缺省，等待态落库、答复触发续跑）
  或 `blocking`（旧的 120s 阻塞形态）。来自环境变量 `AGENT_APPROVAL_MODE`（§6），**不落
  `.data/policy.json`、不可通过 `POST` 修改**。前端据此决定审批卡显示倒计时（blocking）还是
  「等待处理」（async）。
- **`attachments` / `fileAttachments` / `editResend`（纯增量只读投影）**：
  三个**环境变量**开关（`AGENT_ATTACHMENTS` / `AGENT_FILE_ATTACHMENTS` / `AGENT_EDIT_RESEND`，§6）
  的当前值，前端据此决定渲染不渲染附件按钮 / 任意文件入口 / 编辑入口。它们不可通过 `POST` 修改
  （改的是 env），`POST` 的响应也带这三个字段（形状同 `GET`，仍不含 `label`）。
  `fileAttachments` 是 2026-11-13 附件走路径新增：`false` 时上传端点 404、前端只留图片内联。
- **`flagCascade` / `pluginSurfaces`（2026-11-25，纯增量只读投影）**：
  两个**环境变量**开关（`FLAG_CASCADE_ENABLE` / `PLUGIN_SURFACE_HIDE`，§6）的当前值，`POST` 不可修改、不落
  `.data/policy.json`。
  - `flagCascade`：§2.20 那四条「前置连开 / 父项连带关」端点是否可用；`FLAG_CASCADE_ENABLE=false` 时
    回 `false`，同时四个端点整组 404。
  - `pluginSurfaces`：前端声明式显隐注册表的总闸；`PLUGIN_SURFACE_HIDE=false` 时回 `false`，
    前端不隐藏任何面（回到「关了照旧显示、点了才 404」的旧形态）。
  - **两个门都与 `AGENT_FLAGS_UI` 合取**：`AGENT_FLAGS_UI=false`（插件页整组不挂）时也回 `false`，
    契约字段不撒谎（2026-11-25 核对 `index.ts:1285/1287`）。

#### `POST /api/v1/agent/policy` —— 改策略（部分更新）

请求体字段都可选，只更新给出的；`blocked` 非数组时该字段忽略：

```json
{ "access": "read-only", "blocked": ["bash", "powershell"], "approvalLevel": "ask-critical" }
```

旧布尔仍收：`{ "confirmWrites": true }` → `ask-all`、`false` → `none`；同一请求里
`approvalLevel` 优先于 `confirmWrites`。成功回更新后的完整策略（**不含 `label`**，带审批形态与两个能力开关）：

```json
{ "ok": true, "access": "read-only", "blocked": ["bash", "powershell"], "approvalLevel": "ask-critical", "confirmWrites": true, "approvalMode": "async", "attachments": true, "fileAttachments": true, "editResend": true }
```

| 情形 | 返回 |
|---|---|
| `access` 不是 `full` / `read-only` / `no-shell` | `400 {"error":"bad_request","message":"access 只能是 full / read-only / no-shell"}` |
| `approvalLevel` 不是 `ask-all` / `ask-critical` / `none` | `400 {"error":"bad_request","message":"approvalLevel 只能是 ask-all / ask-critical / none"}` |
| 带 `confirmWrites` 但不是布尔值 | `400 {"error":"bad_request","message":"confirmWrites 只能是布尔值"}` |
| body 非 JSON / 空体 | 各字段都不更新，返回当前策略（`{ok:true, …}`） |
| 写 `.data/policy.json` 失败 | 仍 200，本次内存态生效（服务端日志告警；重启回落旧值） |

**落盘与读档兼容**：`policy.json` 存 `approvalLevel`（不再写 `confirmWrites`）；读档时新字段优先，
老文件只有 `confirmWrites` 就按 `true→ask-all / false→none` 映射，两者都没有才回落 env 初值。

**权限**：与其他 `/api/v1/*` 同——`Authorization: Bearer <AGENT_TOKEN>` 或本机页面 cookie（§1），
失败一律 **403 空体**。端点不回显任何密钥。前端调用：`web/app.js` 的 `loadPolicy()`
（全屏设置页 `#policy-switch` / `#policy-approval-level`）与抽屉版 `cs-policy-*`（`GET` 读档、`POST` 回写）。

### 2.19 技能管理（2026-11-08 扫尾批 9-S；2026-11-08 批 10-A 加标准用户目录与两种形态；2026-11-23 多位置；2026-11-24 内置来源可移除；`SKILLS_ADMIN` 默认开）

技能 = 给模型的操作手册，两种文件形态都认：

- **扁平 `<name>.md`**（本仓库原生形态）：**第 1 行 = 索引用摘要，其余 = 正文**；`name` 即文件名。
- **目录 `<name>/SKILL.md`**（标准 agent skill 形态）：`name` = 目录名，摘要 = frontmatter 的 `description`，
  正文 = frontmatter 之后的内容；frontmatter 其余字段**忽略**（只解析单行 `key: value`，不解析多行块）。
  同一目录里两种形态同名时**扁平优先**。

`name` 受管理面白名单约束（小写字母 / 数字 / 短横线 / 下划线，1-64 字符，不能以 `-`/`_` 开头，
与 `partner_skill_write` 的 slug 同一条正则）；白名单外的名字（含 `.agents` 里的点号名）模型侧照常加载，
只是不出现在管理列表里。

**读取链**（`ts/apps/server/src/skills.ts` 的 `resolveSkillsDir()`，**先到先得**，同名只有第一个来源生效）：

1. `AGENT_SKILLS_DIR` 显式指定（部署自选目录，不替用户创建；显式时**取代**用户目录槽位，不再建 `.lifediary\skills`）；
2. 用户目录 `%USERPROFILE%\.lifediary\skills`——**不存在则首次访问自动 mkdir**（管理界面写这里）；
3. **自加位置**（2026-11-23）：`POST /api/v1/agent/skill-dirs` 登记的目录，**按登记顺序**逐个排在链里；
   **可写、可移除登记**；目录不存在时仍留在链里（`exists=false`，加载器跳过，界面如实标「目录不存在」）；
4. 标准用户技能目录 `%USERPROFILE%\.agents\skills`——跨工具共享的 agent skills，**只读**（不存在就跳过）；
5. 应用目录 `apps/server/skills/` 兜底（内置手册）。

**排除名单**（2026-11-24）：`.data/skills-dirs.json` 的 `excluded:[路径]` 里记了的来源（自加位置 / `.agents` / 内置目录）
**不进读取链**——界面上的「移除」就是这个。主目录（1 / 2，含用户目录建不出来时的 5 兜底主位）不能移除：
它是新建技能的落点，接口返回 400。重新登记同一路径（`addCustomSkillDir`）会顺手解排除。

管理端点的**默认写/删仍落主目录**（1 / 2，用户目录建不出来时才是 5）；带 `dir` 时可指向任一**可写**来源
（主目录 / 自加位置）。`GET` 列表合并全链并给每个 item 标来源目录；`GET :name` 任意来源都可读（带 `dir` 只读那一个）；
`.agents` 里的技能**不提供写/删**（连"在主目录写一份同名影子副本"也拒绝，否则用户会以为改的是那一份）；
应用目录的内置手册仍允许被主目录同名覆盖（9-S 就有的合并语义）。
`SKILLS_ADMIN=false` 时本节端点全部不挂（404 = 未启用）；`SKILLS_EXTRA_DIRS=false` 时只关多位置这一层（见下）。

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/skills` | `{ok, dir, origin, extraDirs, dirs:[{dir,origin,writable,exists,removable,label?}], items:[{name, summary, size, updatedAt, origin, dir, writable, form, core, enabled, usageCount?, lastUsedAt?, stale}]}`；`dir`/`origin` = 主目录（默认写目标），`items` 按读取链合并；`form` = `flat` / `dir`；`origin` = `env` / `user` / `custom` / `agents` / `app`，`writable=false` 即只读来源；`dir`（**2026-11-23**）= 该条实际来自哪个目录；`removable` = 该行能否移除（**2026-11-24**：除主目录外全为 `true`；`label` 仍只对自加位置有意义）；`extraDirs` = 多位置能力是否开着；`core`（**2026-11-16 工具裁剪 A**）= 是否代码内置技能，`core=true` 时 `enabled` 恒为 `true`（即使启停位里没有）；`enabled` = 启停位（2026-11-09，见下）；`usageCount` / `lastUsedAt` / `stale` = 技能用量账（2026-11-10 批 17，见下）。**2026-11-15** 可带 `?partnerId=<id>`：每项追加 `partnerEnabled`（该人实际可用 = 全局开 或 该人覆盖开；`core=true` 时恒 `true`）与 `partnerOverride`（全局没开、该人独开；`core=true` 时恒 `false`）；不带参数时形状不变 |

- **多位置（2026-11-23 用户口径：技能库能添加多个位置，建 / 改技能时选位置）**：登记表落
  `.data/skills-dirs.json`（`AGENT_SKILLS_DIRS_PATH` 可换）＝`{dirs:[{path,label?}], excluded?:[路径]}`；只登记目录，
  不替用户建（路径打错不该生成空目录）、移除不删文件。自加位置排在主目录之后、`.agents` 之前，
  **按登记顺序先到先得**；写入 / 删除的 `dir` 必须是链里的可写来源。位置或技能文件变动后服务端
  就地重扫技能库（`refreshSkillStore`：换「有哪些技能」，不动已冻结索引）——**已在跑的会话索引仍按
  首轮快照**，新会话按新链渲染。`SKILLS_EXTRA_DIRS=false/0/off` = 读取链忽略自加位置与排除名单 +
  `/agent/skill-dirs` 两端点 404（已存登记表保留，重开即恢复）。
- **内置来源可移除（2026-11-24 用户口径）**：技能页「技能库位置」里 `.agents/skills`、内置目录与自加位置每行都有
  「移除」；主目录保留（新建技能写在这里，不提供移除）。移除 = 只改读取清单（登记表 / 排除名单），
  磁盘文件一个不动；想恢复就「添加位置」把同一路径加回来（以自加位置身份、可写）。
- **启停位（2026-11-09 用户拍板：技能默认全关）**：状态存 `.data/skills-state.json`（`AGENT_SKILLS_STATE_PATH`  可换）＝`{enabled:{name:true}, partners:{partnerId:{enabled:{name:true}}}}`，**名单外一律视为关**；`SKILL_STATE=false` 逃生门 = 回到全部进索引的旧行为（此时列表的 `enabled` / `partnerEnabled` 也按全开显示）。
  注入侧（`assist.ts` 的 skillStore filter）索引 / `names()` / `manual()` 三处同源过滤——关了的技能
  不进索引、`skill` 工具也取不到（工具侧即时，索引按会话冻结）。`SKILLS_ADMIN=false` 时启停端点随整组不挂。
- **内置技能 core（2026-11-16 工具裁剪 A）**：`ts/apps/server/src/core-skills.ts` 的 `CORE_SKILL_NAMES`
  是唯一名单（当前只有 `delegate`），`isCoreSkill(name)` 判定；**只认代码常量，不认技能文件 frontmatter 自封**。
  core 技能始终进索引、始终能被 `skill(name)` 取到，**不受启停位（默认全关）与按人可见性影响**——
  工具政策手册（如 `skills/delegate.md`）关掉就等于让工具描述失去配套说明。实现上 `createSkillStore`

#### 前置连开 / 父项连带关（2026-11-25）

动机：父子门落地后，点到被锁的子项只有一句「随总闸关闭」，用户得自己回插件页逐个找父键。这次给两条路：
**开**时先只读列出缺的前置，确认后按拓扑序一次打开；**关**父项时先把会被连带关掉的子项列出来，再确认。
四个端点都在 `/api/v1/agent/flags` 下，鉴权与其他 `/api/v1/*` 同（失败 403 空体）。写值走 `setFlag`：
**plugin 键只落 `.data/agent-flags.json`；core 键沿用 `setFlag` 历史行为，落 JSON 并同步写
`process.env`（重启后仍保持）**（2026-11-25 核对 `flags.ts:506-551`）。旧 `PUT` 语义一个字节不动
（单键、无确认、不自动开父）。

| 端点 | 请求 | 成功响应 |
|---|---|---|
| `GET /api/v1/agent/flags/:key/enable-plan` | — | `{key,label,missing:[{key,label,value,hot,willWrite}],revive:[{key,label,value,hot,willWrite:false}],needsValue:[{key,label,choices}],target:{key,label,value,hot,willWrite}}` |
| `POST /api/v1/agent/flags/:key/enable` | `{confirm:true, values?:{KEY:value}}` | `{ok,changed:[{key,value,hot}],revived:[…]}`；目标已开 → `{ok:true,alreadyOn:true}` |
| `GET /api/v1/agent/flags/:key/disable-plan` | — | `{key,label,disableable,offValue,affected:[{key,label}]}` |
| `POST /api/v1/agent/flags/:key/disable` | `{confirm:true}` | `{ok,changed:[{key,value,hot}]}`；目标已关（含被父锁）→ `{ok:true,alreadyOff:true}`，不写值 |

- `missing`：从目标键沿 `requires` 递归收集、**计划写之前** `effectiveValue` 为关的祖先（不含目标自身），
  **拓扑序**（最深祖先在前）。父「存储值本来是开、只是被它自己的父锁着」同样列出来并继续上溯。
  `willWrite` = 该键**自己的存储值就是关值**，必须写；存储值本来是开、只是被父锁着 → `false`（父一开它
  自动恢复，本轮不写它自己的值）。`hot` = 该键是否即时生效。
  `target` 是目标自身的存储值 / `hot` / `willWrite`，前端据此算「打开 N 项、其中 M 项连带恢复」。
- `needsValue`：前置（含目标）里有枚举 / 数值键、这次请求没带（或带了非法）值时列出该键与 `choices`，界面补选后随
  `values` 一起回传；缺了就是 400 `{error:"needs_value", keys: [{key,label,choices}]}`（**错误体字段名是 `keys`**；
  `needsValue` 只用作 `GET enable-plan` 成功响应里的 plan 字段，两者不要混）。
- `POST enable` **不信客户端算的结果**：`values` **只对 `plan.needsValue` 列出的键生效**——实现逐项读
  `needsValue` 再取 `values`（`flags.ts:875-889`），清单里不存在的键、这次不需要选值的键传了也**不生效、不报错**；
  填好后服务端**重新推演一遍**，再按拓扑序逐键写。
  `changed` = 真写了的键（含目标），`revived` = 因这批写入从关变开的其它键。幂等：目标已开 → `alreadyOn`，不重复写。
- `revive` 口径：候选 = 清单里**排除 `missing ∪ {key}`** 之后的键；每项 `willWrite: false`（复活是父开了自己恢复，
  本轮不写它的值）。判据按「计划写完后」的状态推演（不是按现在的值）：计划内按计划值，计划外按**存储值 + 递归父**
  （存储值本来开、只被更上层锁着的中间父，会随父一起恢复，它的孩子也跟着恢复）；多父键必须所有父按这套推演都算开。
  排序按清单顺序。
- `disable-plan`：`disableable` = 这个键能不能被关；`offValue` = 将要写的关值；`affected` = `requires` 闭包含
  目标、且当前 `effectiveValue` 为开的全部后代。子项**存储值保留**，父重开自动恢复——弹窗必须写明，否则用户
  以为子项设置被清了。
- **关值规则**：`offValue ?? (布尔键 ? "false" : null)`。布尔键（`values` 只有 `true` / `false`）**一律可关**，
  不需要清单逐条配 `offValue`；枚举 / 数值键没配 `offValue` = 没有「关」这一档 → 400 `flag_not_disableable`
  （数值键如 `AGENT_COMPACT_TRIGGER_PERCENT` 同样命中，`disable-plan` 回 `disableable:false` 且不带 `offValue`）。
- 错误码：未知键 404 `flag_not_found`（**旧 `PUT` 对未知键同为 404，但 `error` 仍是 `bad_request`——本次不改 `PUT`**）；
  缺 `confirm` / 不是 `true` → 400 `needs_confirm`；缺打开值（`needsValue` 非空却没给合法 `values`）→ 400
  `{error:"needs_value", keys: [{key,label,choices}]}`；门关（`FLAG_CASCADE_ENABLE=false/0/off`）
  → 四端点整组 404（门在**挂载时**读一次，改 `FLAG_CASCADE_ENABLE` 需重启生效，关掉后插件页退回
  「点一下 → 400 `flag_locked`」的旧形态）。
- **原子性**：**逐键写 JSON，不是事务**。中途失败 → 500 `partial`，响应里如实带已写成功的 `changed` 前缀；
  前端据此重拉 `GET /agent/flags` 收口，不假装整体成功。
- 前端入口按 `GET /api/v1/agent/policy` 的 `flagCascade` 显隐（§2.18）：`false` 时不画「打开这些前置」/「确认关闭」按钮。

### 2.21 bash 后台任务管理（2026-11-10 批 21 §二；`AGENT_BASH_BG_TIMEOUT` 开或策略选了 background 时才挂）

批 11 只做了"超时转后台 + 结果回灌"；这一节补管理面。**挂载条件（2026-11-24 放宽）**：
`AGENT_BASH_BG_TIMEOUT` 开 **或** 工具超时策略（`TOOL_TIMEOUT_POLICY` 开 + 任一工具解析为
`onTimeout:"background"`，见 §2.24）。都为假时整组不挂（404）；索引落点 `AGENT_BG_JOBS_DIR`
（默认 `.data/bg-jobs`，探针隔离用）。挂载判断发生在服务启动时，**运行期新开策略要重启后管理面才出现**。

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/bg-jobs` | `{ok, jobs:[{id, commandSummary, startedAt, endedAt\|null, exitCode\|null, status, kind, tool\|null, conversationId\|null}], limit}`，index 顺序；索引读失败 → 503。**2026-11-24 起**每条带 `kind`（旧记录缺省 `shell`）、`tool`（发起它的工具名，如 `bash` / `powershell`；旧记录 null）、`conversationId`（旧记录 null）；可选 `?conversationId=<数字>` 只回该会话发起的任务（旧记录无该字段，不命中；非数字 → 400 `bad_request`） |
| `GET /api/v1/agent/bg-jobs/:id/log` | `{ok, id, lines, log}`：`lines` = 整份日志行数，`log` = **最后 ≤200 行**（末尾换行不算一行）。未知 / 非法 id → 404 |
| `POST /api/v1/agent/bg-jobs/:id/kill` | 只杀**本进程起的、仍在跑**的任务（POSIX 杀进程组、Windows `taskkill /T`）。成功 `{ok,id,status:"killed"}`；未知 id → 404；不是本进程起的 / 已结束 → 409（`not_owned_process` / `not_running`） |

- 进程归属只看本进程内存表：重启后 index 里的 `running` 一律当"没有活进程"，**绝不按 pid 杀**（pid 会复用）。
- 启动时裁剪：`index.json` 超过 200 条 → 从最旧的**已结束**任务开始删索引条目；在跑的不删，
  **日志文件一个都不删**（按 id 仍能找回原始输出）。
- 策略驱动转后台时，`notify:false` 只写 index / log，不写会话、不投唤醒（`notify:true` 才回灌）。
- 日志正文只进响应体；服务端日志只记条数 / 耗时 / 枚举。
- `AGENT_BG_JOBS_DIR` 只是测试 / 探针的落点隔离（同 `.data/*` 的既有 `*_PATH` 口径），不是部署换目录的开关。

  ∪ 已加载 ∪ **按人提升**，再减取消名单；写 `modelTools` 时把本会话已加载 / 已提升的 deferred
  带回 `add`，被取消的进 `remove`。**只要有被取消的 deferred 就必须写一次**
  （即使集合没变）——否则它留在 deferred 里，既能被加载又出现在清单里。运行时一律认注册对象上的
  `tool.deferred`（不读配置文件），避免"配置已改、Harness 还没重开"时口径漂移。
- **能力声明**（`tool-capability.ts`）：`readOnly:true` / `destructive:false` /
  `sideEffectScope:"none"` / `riskLevel:"low"` / `needsApproval:"never"` / `concurrentSafe:true`，
  说明「只把已注册的延迟工具加载进本会话工具面；不动工作区、不起进程、不写盘」。
  **不进 `WRITE_TOOLS`**（与 `approval-policy.ts` 正交：它只改会话工具面，不写盘、不起进程）。
- **全量常驻**：想在按需池之外全量常驻，走「设置 → 工具」把名单清空（`tool-pool.json` 的
  `deferred:[]`，重启生效）——这是正当机制，回滚开关已退役。
  与 `PARTNER_TOOLS_ENABLED` 正交：后者管"勾选屏蔽"，前者管"按需名单内容"。

#### 2.22.1 全局工具池端点（2026-11-17 设置 → 注入 → 工具）

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/tool-pool` | `{ok, enabled, deferred:[…], defaults:[…], applied:[…]\|null, restartPending, tools:[{name,summary,description,parameters,chars,tokens,deferred}]}`。`deferred` = 配置文件里的按需名单；`defaults` = 代码默认 9 个（「恢复默认」用）；`applied` = 当前运行的 Harness 实际用的名单（null = 还没装配过）；`restartPending` = 两者不同（已保存待重启）。`tools` 从 `modelToolCatalog()` 现取（含 deferred），`deferred` 按**配置**算；`summary` = 截断摘要（列表行），**`description` = 描述原文、`parameters` = 参数 JSON Schema 原文（2026-11-17 补，展开行看完整定义）**；`chars/tokens` = 工具名 + 描述 + 参数精简 JSON 的估算（口径同设置→上下文，`token-estimate.ts`）。**不返回分组**（2026-11-17 用户拍板：这页不展示硬编码分组，看完整定义就够；分组仍只用于人设页勾选目录）。`enabled` 恒 `true`（AGENT_TOOL_INDEX 回滚开关 2026-11-21 退役，字段留给旧客户端）；`cache-control: no-store`。鉴权同 `/api/v1/*` |

### 2.24 工具超时策略（2026-11-24 M0–M2，方案 `docs/设计方案/2026-11-24-工具异常处理与超时转后台.md`）

服务端内部设置端点，**不进 `ts/packages/shared/index.ts` 契约，手机端不需要适配**。
落点 `.data/tool-policy.json`（`TOOL_POLICY_PATH` 可覆盖；同目录临时文件 + rename 原子写，
mtime + size 缓存现读，**保存后下一轮生效**，不需要重启）。总开关 `TOOL_TIMEOUT_POLICY`
（插件页，`hot:true`）：**关 = 两个端点都 404**（handler 现读开关，打开 / 关闭下一轮生效）。

#### 文件形状

```json
{
  "v": 1,
  "tools": { "bash": { "timeoutMs": 900000, "onTimeout": "background", "notify": true } },
  "groups": { "memory": { "timeoutMs": 12000 } },
  "injections": { "memoryLight": { "timeoutMs": 6000 } }
}
```

优先级（每层只覆盖显式给了的字段）：`tools.<name>` > `groups.<id>` > legacy
（`AGENT_BASH_TIMEOUT_S` / `memory-bank.json` 的 `timeouts.askMs` / `lightMs`）> 代码默认。
`groups` 只对组内**可配**工具生效；锁定工具忽略。`injections` 不是工具调用（当前只有
`memoryLight`）：master 开时由 `injections.memoryLight.timeoutMs` 覆盖
`memory-bank.json` 的 `timeouts.lightMs`（消费点 = lifecycle 的轻召回接线，`memoryLightTimeoutMs()`）；
master 关仍只读旧 `lightMs`。

| 项 | 范围（ms） | 代码默认 |
|---|---|---|
| `bash` / `powershell` | 5_000 .. 3_600_000 | 900_000 |
| `recall`（外部记忆库） | 1_000 .. 120_000 | 15_000 |
| `web_search` | 5_000 .. 120_000 | 20_000（整次调用；每源仍是 20s 上限） |
| `injections.memoryLight` | 500 .. 30_000 | 8_000 |

`onTimeout` 的本批结算范围：`bash` / `powershell` = `fail` / `background` / `cancel`；
`recall` / `web_search` **只允许 `fail`**（`background` / `cancel` 在 PUT 时 400）。
`notify` 只对 `background` 有意义：默认 true；false = 只写 index / log，不写会话、不投唤醒。

#### `GET /api/v1/agent/tool-policy`

```json
{
  "ok": true,
  "enabled": true,
  "groups": [{ "id": "memory", "title": "记忆", "desc": "…" }],
  "tools": [
    {
      "name": "recall",
      "label": "记忆检索",
      "group": "memory",
      "category": "evidence",
      "capabilities": { "abortable": true, "backgroundable": false, "configurable": true },
      "lockedReason": null,
      "effective": { "timeoutMs": 15000, "onTimeout": "fail", "notify": false, "source": "legacy" },
      "ranges": { "min": 1000, "max": 120000 }
    },
    {
      "name": "read",
      "label": "读取文件",
      "group": "shell",
      "category": "evidence",
      "capabilities": { "abortable": false, "backgroundable": false, "configurable": false },
      "lockedReason": "本地同步读：加超时只能不再等，文件读仍会跑完。",
      "effective": null,
      "ranges": null
    }
  ],
  "injections": [
    {
      "name": "memoryLight",
      "label": "每轮记忆轻召回（不是工具调用）",
      "desc": "…",
      "effective": { "timeoutMs": 8000, "onTimeout": "fail", "notify": false, "source": "legacy" },
      "ranges": { "min": 500, "max": 30000 }
    }
  ],
  "backgroundJobs": { "indexLimit": 200 }
}
```

- `tools` 按 catalog 顺序返回**全部**工具行：4 个可配（`bash` / `powershell` / `recall` /
  `web_search`）+ 锁定行（只读 / 写 / 交互 / 派活等，带 `lockedReason`）。
  锁定行的 `effective` / `ranges` 为 `null`（没有可解析的输入面）。
- `effective.source` 指 **timeoutMs** 的来源：`tool` / `group` / `legacy` / `default`
  （`injections` 的显式条目同样标 `tool` =「你配的这条」）。`onTimeout` / `notify` 没有 legacy 层。
- `effective.timeoutMs = null` 只出现在一种情况：`AGENT_BASH_TIMEOUT_S=0`（显式不设默认超时）且
  policy 没给 `bash.timeoutMs`。
- `cache-control: no-store`。鉴权同 `/api/v1/*`（鉴权失败仍 403 空体）。

#### `PUT /api/v1/agent/tool-policy`（局部更新；`null` = 删除该条，回继承）

```json
{
  "tools": { "bash": { "timeoutMs": 900000, "onTimeout": "background", "notify": true }, "recall": null },
  "groups": { "memory": { "timeoutMs": 12000 } },
  "injections": { "memoryLight": { "timeoutMs": 6000 } }
}
```

- 只处理出现了的命名空间 / 名字；工具条目是**替换**（不是深合并）——卡片保存总是发完整三字段。
- 成功返回与 GET 同形（含 `ok:true`），并原子写文件。`null` 删除该条 → 回继承。
- 越界 `timeoutMs` 按范围 **clamp**（不报错），小数取整；三个字段都空 = 删除该条。

| 情况 | 状态码 | 错误码 |
|---|---|---|
| body 不是对象 / 三个命名空间都缺 / 命名空间不是对象 / 条目不是对象 | 400 | `bad_request` |
| 未知工具名 / 组名 / 注入名 | 400 | `unknown_tool` / `unknown_group` / `unknown_injection` |
| 不可配工具（`read` / `write` / `ask_user` 等）给了 policy | 400 | `tool_locked` |
| 组里没有可配工具（如 `collaborate`） | 400 | `bad_request` |
| 不可后台写 `background` / 本工具不支持 `cancel` / 不认识的 `onTimeout` | 400 | `on_timeout_unsupported` |
| `timeoutMs` 非数字 / 非有限数 | 400 | `bad_timeout` |
| `notify` 非布尔 | 400 | `bad_notify` |

#### 与旧开关的关系（只做兜底，不双写）

- `AGENT_BASH_TIMEOUT_S`：policy 没给 `bash.timeoutMs` 时仍按它（legacy 层）；有 policy 以 policy 为准。
  它是模块级常量，改 env 仍需重启；policy 是现读，下一轮生效。
- `AGENT_BASH_BG_TIMEOUT`：**master 关时行为逐字节不变**（只认这个旧开关）。master 开且
  `bash.onTimeout="background"` 时以 policy 为准（无需再开旧 env）；**旧开关在 master 开时不再参与**。
- `memory-bank.json` 的 `timeouts.askMs` / `lightMs`：兼容读一代。`recall` 工具按 policy
  `tools.recall.timeoutMs` 覆盖 `askMs`；`PUT /memory/bank {timeouts}` 仍照旧写旧文件。
- `tools.bash.timeoutMs` 是**默认注入值**，不是硬上限：模型显式传了更长的 `timeout` 时不覆盖，
  后台触发时点 = 内核实际超时的时点（方案 §3.4）。
- `bg-jobs` 管理面的挂载条件见 §2.21。
