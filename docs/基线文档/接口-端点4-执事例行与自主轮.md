### 2.11 执事（2026-11-05 批次B）

长期身份 = 档案（`partners.sqlite`）+ 磁盘家（`partner-homes/<uuid>/`：SOUL.md / memories/USER.md / workspace/ / skills/）。
`COMPANIONS_ENABLED=false` 时本节全部端点不挂载（404 语义 = 未启用）。

| 端点 | 说明 |
|---|---|
| `POST /api/v1/partners` | 建（必填 `name` ≤40 字）。创建即建家 + 身份计数置 1。可选 `domain`（小写 ASCII，正则同 chancellor `DOMAIN_PATTERN`）：带则 = **执事**，见下。可选 `soul`（E2 #0，纯增量）：建档成功后 `bumpSoul` 一次把正文覆盖成自定义（保存计数推进到 2），把前端「建完补 PATCH」两段式收敛成一段；400 校验照 PATCH 的 64KB 槽位上限（`PARTNER_SLOT_LIMIT`），超上限在建档前就拦；不带 `soul` 行为零变化。可选 `tagline`（2026-11-12 口头禅，纯增量）：与 PATCH **同一份校验**（trim 后按 Unicode code point ≤40 字；`null` / 空串 = 不设；省略 = 不设）；非法类型 / 超长在建档前 400，不留半建档案；响应投影带 `tagline` |

- **写入点**：harness 侧派单**终态结算**（`delegation.ts` 的 `settle` / `fail`，`settled` 守卫保证一次）落一条到**发起执事**的 `partner:<id>` scope（按 `originConversationId` 用 `partnerIdOfSession` 认执事，刀一同款判据；主人 / 总管会话不落账）。`kind=work`、`source="work"`、`id=work:<票号>`（稳定 id，终态重入是 upsert 不重复）。content 一行：`单号 ｜ 任务一句话摘要 ｜ 终态=<状态> ｜ 结果一行 ｜（产物目录，有则带）`；产物只记 `TicketResult.tasks[].dir` 目录路径，**不透传文件清单**（8e 之前不阻塞）。写失败只 warn，不影响结算主流程。
- **终态口径**：`done` / `failed` / `aborted` / `canceled`（取消）落账；`needs_you` / `idle` 是"等回答 / 等子单"的**中间态不写**（续跑会再 settle，写了就重复）。取消 / 中止 / 派单跑挂也照实结算。
- **ledger 语义**：巩固不合并（同正文也是另一单）、时间衰减不作用、**召回默认排除**（`WeightedRetriever` 候选集过滤 `kind!=="work"`，work 因此也不参与 `touchRecall` 写回）、模型侧语义整理建议剔除 work、`applyProposal` 另有 400 守卫；模型 `remember` 工具的 kind 枚举**不含** work（履历只由结算落，模型不可伪造）；导入通道不接受 work。
- **封顶**：每 scope 上限 **200 条**、超出删最旧，在写入点用 `store.pruneOldest(scope, 200, {kinds:["work"]})` 现算（`PruneOptions.kinds` 是本次给既有修剪机制加的 kind 规则；不传 kinds 与改动前逐字节一致）。与 `MEMORY_SESSION_CAP` 的整体封顶取严。
- **读取**：执事轮装配与周期盘点用 `store.search({scopes, kinds:["work"], limit})` 的**结构化查询**，不走语义召回。`agent/partner-context.ts` 在【当前在办】段末尾挂一行「近 10 单：完成 X、失败 Y、中止 Z」（零记录不加）；在办 = 现在时（runs 扫描），履历 = 过去时（work 记录），两层互补别混。
- **回滚**：`PARTNER_WORK_RECORD=false`（§6）→ 一个字节都不写，回到刀二之前的形态；`MEMORY_ENABLED=false` 同样旁路。

**经验层（`kind=experience`，2026-11-10 批 17 §一）**：与 `work` 的分工是「下次怎么做」vs「这单发生过什么」。

- **写入点**：同一处结算（`work-record.ts` 的 `recordWorkSettlement`），只在 `status=done` 且过门槛时写一条到同一 `partner:<id>` scope；`id=experience:<票号>`（稳定 id，重入不重复）。
- **价值门槛（确定性，不调模型）**：结果行 ≥40 字且至少含一个具体动作词（改 / 写 / 读 / 跑 / 查 / 整理 / 合并 / 删除 / 替换 / 核对 / 回滚等）；不过门槛**一条都不写**（宁缺毋滥）。内容 = `下次同类活可以这样做：<结果行>`。
- **语义**：进召回（与 fact 同组、权重 ×1.08）、**不参与时间衰减**、**参与巩固合并**（同 scope 规范化等价的经验合并并强化——与 work 相反）、会话封顶修剪受保护；`list` 排在 fact 之后。
- **回滚**：`PARTNER_EXPERIENCE=false` / `0` → 只落 work 履历，一个字节经验都不写（§6）。

**当前目标（E4）**：`partners` 表加 `current_goal TEXT`（旧库 `PRAGMA` + `ALTER TABLE` 补列，老行读 `null`）。只进 detail 端点与 PATCH，**列表形状不变**、不进 shared（刀三）。**不版本化**：目标不是身份，改完不动 SOUL / 契约、不推身份计数，现取现用。注入走刀一**同一装配点**：【岗位契约】段之后加一行「【当前目标】…」（有目标才出现），顺序固定为 契约 → 目标 → 在办。

**目标模式（2026-11-25 落地，默认关；方案 `docs/设计方案/2026-11-25-目标模式（参考ZCode与Codex）.md`，落地记 `变更记录/2026-11-25-目标模式.md`）**：`GOAL_MODE=false`（缺省）时下面这些**一个都不出现**，目标仍只是上面那一行文本；状态表 `partner_goals` 保留不清。

- **存储**：新表 `partner_goals`，`partner_id` 主键（一个执事最多一行）：`status / reason / rounds_used / max_rounds / token_budget（可空）/ tokens_used / no_progress_streak / updated_at`。目标正文仍是 `partners.current_goal`，注入不变、不进 shared。
- **状态**：`active / paused / budget_limited / done` 四态 + `reason`（`not_started / user / stopped / no_progress / blocked / rounds / tokens / self_report`）。"需要主人介入"不单设状态：模型写 `[[goal-blocked: …]]` → `paused` + `reason=blocked`。
- **详情** `GET /api/v1/partners/:id`：多一个 `goal` 对象 `{status, reason, roundsUsed, maxRounds, tokensUsed, tokenBudget}`；还没有状态行时 = `null`（例如开关关着时设的目标正文，点 `start` 会补建）。**列表端点形状不变**。
- **`PATCH /api/v1/partners/:id` 带 `currentGoal`**：非空 = 照旧写文本，并（没有状态行时）建一行 `paused / not_started`，零工具连击清零、状态不变；空 / `null` = 清除目标，**同一事务**里删状态行。返回体带 `goal`。
- **动作端点** `POST /api/v1/partners/:id/goal`，请求 `{action, maxRounds?, tokenBudget?}`：

  | action | 要求 | 结果 |
  |---|---|---|
  | `start` / `resume` | 目标是 `paused` 或 `budget_limited` | 置 `active`、连击清零，并立刻排一轮续跑 |
  | `pause` | 目标是 `active` | 置 `paused`，`reason=user` |
  | `reopen` | 目标是 `done` | 置 `active`、连击清零，并排一轮续跑 |
  | `clear` | 任意 | 删状态行 + `current_goal` 置空（同一事务） |

  `maxRounds`（整数 1–200）、`tokenBudget`（整数 ≥ 10000；`null` = 清除）可选，任何 action 都能带，**先落上限再判状态**。成功 200 `{ok: true, goal}`。
- **错误码**：鉴权失败 403 空体（与其它端点同）；`GOAL_MODE=false` 或执事不存在 → 404 `{ok:false, error:"not_found"}`；业务拒绝 400 `{error:"bad_request", message}`，状态一行不动。业务拒绝的五种：没设目标文本、状态与 action 不配（已在推进 / 没在推进 / 已完成要用 reopen）、`maxRounds` / `tokenBudget` 不合法、续跑轮数已用满且没上调、token 预算已用满且没上调。
- **结算**（服务端内部，无端点）：目标 `active` 的会话每轮收尾结算一次，顺序 = 末行标记 → 记账 → 轮数 / token 上限 → 零工具连击 → 排续跑。只数**续跑轮**的零工具；连击 3 次暂停。续跑是 durable 任务（`lifediary.goal-continue`），身份 `autonomous`，重启不自动重放。细则见 `系统架构.md` §7。
- **回滚**：`GOAL_MODE=false` → 不结算、不排续跑、动作端点 404、详情与 PATCH 都不带 `goal`。
- **探针**：`pnpm --filter @lifediary/server goal`（`scripts/goal-mode-probe.ts`，真起服务 + 真 HTTP + faux 模型）——两种开关形态、上面的错误码、状态机与结算全链路都走一遍；改这条链路要重跑并看输出。

**口头禅（2026-11-12 手机对话身份方案 §四）**：`partners` 表加 `tagline TEXT`（旧库 `PRAGMA` + `ALTER TABLE` 补列，老行读 `null`，不补数据）。**列表与详情投影都带**（未设置给 `null`，首页 / 空态零额外请求）；`POST /partners` 建档时可直接带（与 PATCH 同一份校验，非法在建档前 400）；≤40 字（按 Unicode code point、trim 后判）、`null` / 空串 = 清除、省略 = 不改；**不版本化**（不动 SOUL / 契约、不推身份计数）。shared `PartnerProfileSchema` 带可选 `tagline`。

**项目记忆挂载（2026-11-15 跟人走立项、同日多挂载方案扩化；方案 `docs/设计方案/2026-11-15-项目记忆多挂载（执事跨项目）.md`）**：`partners` 表 `project_ids TEXT`（JSON 数组）。上线首日是单值列 `project_id`（uuid|null），同日改多数组——旧库 `migrate()` 补列并一次性搬数据（单值 → `[旧值]`），旧列保留不读不写。`PATCH /partners/:id` 带 `projectIds`：**数组 = 整体替换**（去重，每个都必须命中已登记项目（含归档——记忆还在，只是项目不再活跃））、空数组 = 清空、省略 = 不改；有不认识的 uuid → 业务 400 且整批不写；**不版本化**（不动 SOUL / 契约、不推身份计数）。列表与详情投影都带 `projectIds`（未挂给 `[]`）；（PARTNER_PROJECT_MEMORY 回滚开关 2026-11-21 退役：字段恒投影；旧客户端忽略未知字段即可。）**挂载 = 可达性，不是"每轮整包搬进上下文"**：挂载项目 `recall` 全部可查、聊到的经闸门自动浮出（其余挂载项目走 `RecallQuery.gatedScopes` 字面命中才进候选）、`remember scope=project` 落到绑定项目 / 唯一挂载 / 按 `project` 参数指名（多挂载未指名报错列清单）；执事自己的 `partner:<id>` 键空间照旧。挂载跟人走、不跟会话走——worker 干活会话跟文件夹走（`ChatProjects`，另一层，互不干扰），解析在 `agent/project-scope.ts`（含 `project_index` 一行负责项目索引注入）。项目登记删除时 `detachProject` 从数组里摘掉该项（`2026-11-15 删除项目界面入口恢复`的连带解除）。shared `PartnerProfileSchema` 带可选 `projectIds`（uuid 数组）。

**印象（`impression`）**：记忆库新增 `MemoryKind = "impression"`，**带对象维度**。

- 正文 JSON（`shared` 的 `PartnerImpressionSchema`）：`{id, subject, text, at, source, event?, tierChange?}`；
  `subject` = `owner` 或群成员对外 id；`event` = `thanks` / `correction`；`tierChange` = 这一条就是跨档事件。
- **写入点只有两路**：会话结算钩子（`source="generated"`）与 persona 端点手改（`source="manual"`）。
  `remember` 工具的 kind 枚举不含 impression，模型不可伪造。
- **结算钩子**（`agent/settled.ts` → `partner-living.ts`）：只认执事的 **canonical 主会话**（例行专线
  跑的是提示词不是人在说话；群成员会话另有钩子）；只读**最后一条用户消息**——出现明确致谢词 → 一条
  `thanks` 印象；出现明确纠正词 → 一条 `correction` 印象（引原话 ≤40 字）。判不出来一条都不写。
- **群成员印象**：`group-runtime.ts` 在成员轮结束后，只记「本回合别人点名了我」这一种事件
  （`subject` = 那位成员的 id）；同一天同名事件不重复记。
- **温度**：五档文字，初始 `生疏`。**档内微调** = 每次致谢加一条印象，不换档；**跨档**必须有可解释事件：
  自上次跨档以来累计致谢达到阈值（`生疏→认识` 3 次、`认识→熟络` 5、`熟络→亲近` 8、`亲近→像家人` 12；
  到顶不再升），写一条带 `tierChange` 的印象账并落当前档。**不做自动降档**（避免隐形扣分）；手改温度
  同样写一条 `manual + tierChange` 的账。
- **封顶**：单对象总条数 ≤20（`shared` 的 `PARTNER_LIVING_LIMITS.impressionsPerSubject`），超出淘汰最旧；
  带 `tierChange` 的记录**永不淘汰**（跨档可追溯的唯一凭据）。
- **记忆层语义**（与 `work` 同待遇）：append-only、**不进语义召回**、不时间衰减、不参与巩固合并、
  会话封顶修剪受保护；记忆管理端点 `ALL_MEMORY_KINDS` 收 `impression`（可在记忆页看 / 删）。
- **日志纪律**：只记条数与枚举（`thanks` / `correction` / `group`），不记印象正文。

**心情（`mood`）**：三种可见规则，规则常量在 `partner-living.ts`（改规则 = 改行为，须同步变更记录）。

| 触发 | 结果 | 说明 |
|---|---|---|
| 结算轮被明确致谢 | `愉悦`（"刚被主人谢过"） | 与印象同一个结算钩子 |
| 连续 2 单失败 / 中止（`MOOD_FAIL_STREAK`） | `低落`（"连续两单没成"） | 派单结算点调 `noteWorkSettlement`，从 work 履历结构化查询数 |
| 72 小时没有新单落账（`MOOD_IDLE_HOURS`） | `平静`（"这阵子没什么活儿在办"） | 结算轮里判；没有 work 记录按建档时间算 |
| 低落中有一单成了 | `平静`（"手上的活办成了"） | 只从低落里捞回来，不覆盖愉悦 |

- 值没变就不写（保住 `mood_updated_at` 的可读性）；**手改随时覆盖**（`mood_source="manual"`），
  下一次规则事件仍可再改——手改不是永久锁，否则规则名存实亡。
- `烦躁` / `疲惫` **规则不生成**，只作手改选项（不模拟生理状态）。
- 子开关 `moodAffectTone`（`persona_switches.moodAffectTone`）：开 = 心情块多一行口吻提示
  （"说话可以带一点这种状态的口吻，但别演"）；关 = 只有状态，不给口吻指令。

**内心生活（`heart`）**：伙伴家目录三份文件，**SOUL.md 一个字节都不动**。

- `persona/diary.jsonl`：一行一条 `{id, at, text, source, liked?}`，正文 ≤300 字，最多 500 条
  （另有 512KB 文件护栏）；`liked` 只影响展示排序，不做算法。
- `persona/growth.md`：每周盘点追加一节 `## M月D日` + ≤400 字反思（最多留 40 节），是 **SOUL 的附注层**，
  永不回写 SOUL 正文。
- `persona/wishes.json`：字符串数组，≤10 条 × 每条 ≤40 字。
- **生成挂在既有盘点例行上**（不新造调度）：`routines.ts` 的 `runOnce` 在 `heart` 开、且规则名 / 指令里带
  盘点关键词（`盘点` / `回顾` / `周报` / `周总结`，常量 `REVIEW_ROUTINE_WORDS`）时，给这轮提示词末尾追加
  `PERSONA_DIGEST_INSTRUCTION`；模型按 `[[日记]]` / `[[成长]]` / `[[周报]]` 三段收尾。服务端
  `applyRoutineDigest` 把日记 / 成长摘出来落盘，**`[[周报]]` 那一句留在可见正文末尾**（"周报末尾他自己的话"）。
  日记 / 成长正文不进例行 run 的 200 字摘要。
- **注入**：`【心里话】` = 愿望 + 成长笔记最近一节；两样都空整段不出现。日记本身**不注入**（是他的私密记录）。

**注入顺序（每轮 system，`buildPartnerTurnContext`）**：契约 → 目标 → 纪律 → 在办 →
**印象（310）→ 心情（320）→ 心里话（330）**。三个 provider 各自按模块开关裁剪；`PARTNER_PERSONA_MODULES=false`
或模块关 → 整段不出现。`INJECTION_ORDER` 新增三个 id（缓存前缀资产，变更已记 `docs/变更记录/`）。

**端点（`GET/PUT /api/v1/partners/:id/persona` 扩展）**：

- GET 响应新增 `switches: {moodAffectTone}`、`living`（见下）、`limits.living`；`enabled=false` 时 `living = null`。
- `living` = `{ownerTier, tierNote, mood:{mood,reason,nearby,updatedAt,source},
  impressions:[{...条目, subjectName}], diary:{count, latestAt, latestText, entries(最近 50 条)},
  growth(最近一节), wishes}`。
- PUT body 新增 `switches?` 与 `living?`（`shared` 的 `PartnerLivingPatchSchema`，`.strict()`）：
  `ownerTier` / `nearby` / `mood` / `moodReason` / `wishes`（整份替换）/
  `impression: {add|update|remove}` / `diary: {add|edit|like|unlike|remove}`。全量过 zod，
  任一不合法 400 且一个字节都不写；手改的印象 / 日记写 `source="manual"`，温度写 `manual + tierChange` 账。
  找不到要改 / 删的条目 → 400 带说明。
- 系统更新与手改走**同一条服务端路径**（`partner-living.ts` 的写入口），端点只做形状映射。

**回滚**：模块开关（`impression` / `mood` / `heart`）关 = 停更 + 不注 + 内容保留；
`PARTNER_PERSONA_MODULES=false` = 端点整段回默认（`living=null`）+ 不注入 + 不更新。本批无新增 env。

**已知边界（未做 / 未验证，2026-11-15）**：

- 日记生成只挂在**自动触发**的盘点轮（`runOnce`）；`runNow`（手动试跑）不落账（手跑不该产生"这周"的记录）。
- 盘点识别按规则名 / 指令里的关键词（常量 `REVIEW_ROUTINE_WORDS`），没有关键词的自建盘点不挂生成。
- 印象提炼是**确定性字符串匹配**，不做模型总结（宁缺毋滥）；因此只认致谢 / 纠正两类事件，
  不会自动生成"他喜欢先看结论"这类判断（这类只能手写）。
- 群成员印象只覆盖"被点名"，不覆盖读发言 / 争论 / 协作。
- 手机端不做（批3）；团队包不搬运活内容（与人格模块同口径）。
- 成长笔记 / 日记的生成质量只做长度与结构校验，**不做内容事实核查**（模型仍可能写得不像）。

**刻意不做**（已在 `系统架构.md` §七登记，复核无新增）：数值好感度（五档文字替代）、
假装身体的生理状态（烦躁 / 疲惫只作手改选项）、agent 回写 SOUL 本体（成长笔记是独立附注层）。

**刻意不碰**：工具描述与注册顺序（缓存前缀资产）、skills、relay、手机端。

#### 人格模块 · 学习 / 主动性 / 人设库（2026-11-15，批3）

**1. 学习（`learning`，默认关）**：学主人说话风格与黑话，落伙伴家目录 `persona/voice.json`。

- **只落提炼后的规则与短例句（≤40 字），不存整段对话原文**；日志只记条数 / 枚举。

- `voice.json` 形状（服务端内部）：`{version, updatedAt, samples:[{text,at}], stats:{...}, rules:[{kind,text,example?,at}]}`；
  `kind` = `sentenceLength` / `address` / `interjection` / `jargon`。
- **注入**：`learning` 开且 `rules` 非空时，`buildPartnerTurnContext` 在在办段之后加一小节
  `【表达习惯】`（规则 + 可选短例句），注入 id `partner_learning`（顺序 305）。
- `MEMORY_ENABLED=false`、总开关 false 或模块关 → 整模块停（不读、不更新、不注入；内容保留）。

**2. 主动性（`proactivity`，默认关）**：追问指引 + 挂念提醒。

  （注入 id `partner_proactivity`，顺序 306）：回答末尾可以自然带一句追问，但不每轮都问、不打扰赶活。
- **主动开口时机**：本批**不新造调度器**，只挂两处既有唤醒：
  ① 派活完成即唤醒（`delegation-wake.ts`）成功一轮之后；
  ② 既有周盘点例行（`routines.ts` 的 `runOnce`）成功之后。
  没有这两类事件的执事不会自己找上门——这是本批的**已知边界**，不是保证每天一条。
- **挂念提醒**（子开关 `persona_switches.nudgeEnabled`，默认关）：在既有提醒链路下发
  （`ReminderTask` → `setReminderDeliverer` → `sayInConversation`），**必须带执事身份**：
  正文固定前缀 `【<执事名>】`，不允许无感知自动化。**2026-11-17 起**（`SCHEDULED_TASK_MODEL_RUN` 默认开）
  挂念随 ReminderTask 一起改为"到点跑模型 + 触发指令隐藏"：正文经 `runPartnerTurn(authority:autonomous)`
  现场生成、不再写死；`【<执事名>】` 身份前缀留在（已隐藏的）触发指令里。**已知边界**：模型现场回复是否
  复述这个身份前缀不保证（不再像旧形态那样逐字节写死）——但回复落在对应执事自己的会话里，用户仍可辨认来源。
  回滚开关关时回到写死消息（身份前缀逐字节保留）。

  取最新一条、引 ≤40 字；没有就不发。**一天最多一条**（本地日期落 `persona/nudge.json`）。
  不主动搭话打扰正在跑的会话（排提醒前查 `conversationIsBusy`）。

### 2.12 例行任务（2026-11-05 批次B）

触发层是 durable 任务（`sleepUntil` 落库），不是扫描定时器（系统架构 §3 口径）。

| 端点 | 说明 |
|---|---|
| `POST /api/v1/routines` | 建（`partnerId/name/prompt≤100k/triggers/sessionMode/enabled`），启用时自动排定时链 |
| `GET /api/v1/routines?partnerId=` / `GET /api/v1/routines/:id/runs` | 列表（**2026-11-17 起投影含 `prompt` 全文**）/ 执行历史（≤50 条有界） |
| `PATCH /api/v1/routines/:id` | 改即 `revision+1`：在飞任务醒来对不上号自动作废，还开着就重排。**2026-11-17 定时任务重做**：`name` / `prompt` 补校验（非空、≤40 / ≤100k），前端编辑内容与简单触发的时间都走这里；复杂触发（interval / event / 多触发器）不在界面改，保存内容时不动 `triggers` |
| `DELETE /api/v1/routines/:id` | 删定义；在飞任务醒来作废（没有取消 API 的替代机制） |
| `POST /api/v1/routines/:id/run_now` | 手动跑一次（entrusted，不占定时链） |

triggers 四型：`cron`（5 段：分 时 日 月 周）/ `interval`（seconds ≥60）/ `once`（ISO at）/ `event`
（kind = delegation/tool/phase + match 字段等值过滤；执事自己会话发出的事件不触发——防自环）。
执行铁律：同规则串行（上一轮没跑完下一次 deferred 30s）；终态落盘失败期间后续触发只排队不执行；
重启时 running 一律 interrupted **不自动重放**。例行轮是自主轮（`turnAuthority: autonomous`，
批次C 的高危审批只对它生效）。

**事件触发器三件门（2026-11-10 批 15 §一，`ROUTINE_TRIGGER_GATES` 默认开）**：`event` 触发器可选加
`baseline?: {key, delta}`（比上次观测值变化**超过** delta 才触发；首次记基线那次不受限）、
`edge?: true`（只从假变真那一下触发）、`cooldownSec?: number`（触发后 N 秒内不再触发）。
判定顺序固定 **cooldown → edge → baseline → 原 match**；三者可组合。门状态按
`<规则id>:<触发器序号>` 落 `routines.json` 的 `gates`，坏值/非数字观测值一律不触发
（宁可漏一次，不拿脏值硬比）。`ROUTINE_TRIGGER_GATES=false`/`0`/`off` → 三个字段全部被忽略，
行为回到改动前；纯函数在 `routine-conditions.ts`（`evaluateTriggerGate`）。

**看护单例交接（2026-11-10 批 15 §四，`ROUTINE_WATCH_SINGLETON` 默认开）**：
带 `until` 的"盯到条件达成"类规则，**同一执事同一时刻最多一个在看**。新一轮开始时若已有
别的看护在盯 → 旧规则只暂停（`enabled=false`，`revision+1` 让在飞闹钟作废），
**不删除**；交接账落 `.data/routine-watch.json`（`ROUTINE_WATCH_PATH` 可改）：
`{version:1, watches:{<partnerId>:{routineId,name,since}}, handedTo:{<旧id>:<新id>}}`。
同一对 old→new **只记一次** `handedTo`；规则置停（until 达成 / 跑满 maxRuns）时从 `watches`
摘除（`handedTo` 保留）。删除规则不额外清账——残留条目只是"指向一条不存在的规则"，
下一次同 key 认领会把它当作旧看护一次性交接掉（不删数据、不挡执行）。
`ROUTINE_WATCH_SINGLETON=false` → 不读不写此文件。

**触发来源 `runSource`（2026-11-10 批 15 §三，`RUN_SOURCE` 默认开）**：run 记录新增可空
`runSource`——定时/事件触发 = `routine`；执事 `routine_manage` 自建规则的**首轮** = `routine_self`；
`POST .../run_now` = `script`。`RUN_SOURCE=false`/`0`/`off` → 不写，行为回到改动前。
（派单回执的来源列见 §2.9。）

**条件门控（2026-11-10 批 13 §四；回滚开关 2026-11-21 退役，恒生效）**：`RoutineDef` 新增两个**可选**
字段——`until?: {note}`（一句文字完成条件；每轮跑完由模型判断，达成时回复末行写
`[[routine-done]]`，服务端把规则 `enabled=false`（**不删**，保留历史））与 `maxRuns?: number`
（自动跑满 N 次即停；手动 `run_now` 不计入）。run 记录新增结构化 `outcome`
（`success|quiet|skipped|failed|done`，`skipped` = 无人值守跳过过步骤）；下一次触发把
"上一次的结果是 X"带给模型。（2026-11-21 退役后字段与 `outcome`
全部被忽略，提示词与 run 记录回到改动前（一行回滚）。HTTP 端点本批仍只接受老字段
（`until`/`maxRuns` 目前经 `routine_manage` 工具设置，端点透出为已知边界）。

**触发器 `if` / `ends`（2026-11-10 批 21 §三）**：任一触发器可带
- `if?: {note}`：触发前**先问一次模型**"这句条件此刻成立吗"（独立 `completeSimple` 调用，
  走 `AUX_MODEL_REVIEW` 可 pin 的小模型，超时 15s，maxTokens 4）。**失败即跳过**：没配模型 /
  faux / 超时 / 报错 / 答案不是明确的 YES/NO → 当"不成立"，记一条 `status:"skipped"`、
  `outcome:"skipped"`、`skipReason:"condition_not_met"` 的 run（不跑模型、不推进游标、
  不消耗 `maxRuns`/`ends.after` 额度）。多个触发器各带 `if` 时**全部成立才跑**；`note` ≤200 字。
- `ends?: {at?, after?}`：`at` = ISO 时间点，到点后该触发器不再被定时/事件唤醒（在飞的 durable
  闹钟到点仍会响一次——它排在 `at` 之前才可能被创建）；`after` = 跑满 N 次停，是 `maxRuns` 的
  别名，两者同时存在取**更小**。`ends` 至少要给一个；非法值在 `validateTriggers` 直接 400。
  运行态判定在 `routine-conditions.ts`（`triggerEndedAt` / `effectiveMaxRuns` / `routineConditionNotes`），
  模型调用在 `routine-gate.ts`。

**游标推进时机（2026-11-10 批 21 §六，沿用 `ROUTINE_QUIET`）**：`routines.json` 新增
`cursors: {<规则id>: ISO}`——"上次看到哪里"的时间水位 = 上一轮**产出被保留**的 `run.endedAt`。
只有 `ok && !quiet && 没跳步` 才推进；quiet（没事）、skipped（跳步）、failed（含读失败）
一律原地不动，下一轮仍从同一处看。有游标时提示词在原文前加
`[上次看到这里] <ISO>；这一轮只看这之后的新内容。`；首次运行没有这一段。
`ROUTINE_QUIET=false` → 不读不写游标（回到"每轮从头看"）。**边界**：宿主只能按 run 终态判，
模型"读失败但照样回了 `[[no-update]]`"这一层无法区分——那是模型自报，不是宿主事实。

**安静契约（2026-11-09 T2）**：例行轮的产出"没有实质内容"时不写汇报——模型侧提示词尾部会要求
"没内容就回 `[[no-update]]`"；服务端再按确定性规则兜底（去空白后 < `ROUTINE_QUIET_MIN_CHARS`（默认 40）
且不含数字/链接/日期 → quiet）。quiet 时 run 记录 `summary:"quiet"`，`[[no-update]]` 标记从产出中剔除，
日志只记"本轮无更新"不记正文。`ROUTINE_QUIET=false` 一行回滚。**边界**：模型这一轮的 assistant
条目由 durable 内核落盘，服务端没有撤回 API，quiet 保证的是"服务端不再写第二遍汇报"，
不是"transcript 里绝对无痕迹"。

**自建巡逻 `routine_manage`（2026-11-08 刀二 E4）**：此前只有 HTTP `POST /api/v1/routines` 能建规则，
现在给**带派发权的执事**一只模型侧的手（工具参数与端点校验共用 `routine-manage.ts` 一份核心实现）：

- `action=create|disable|enable|delete`；create 带 `name` / `prompt` / `triggers` / `sessionMode`，其余带 `id`。
- **只能动自己的**：`partnerId` 由调用者会话认出后绑定，动别人的规则一律 `not_found`（找不到与"不是自己的"同一句话，**不泄存在性**）；主人 / 总管会话明确拒绝。
- **上限**：每执事活动（`enabled`）规则 ≤ **10 条**，create / enable 都先数，超了带说明拒绝。
- **走既有引擎**：create / enable 后由装配层 `routineEngine().ensureScheduled` 排 durable 闹钟；disable / 改期靠 `updateRoutine` 的 `revision+1` 让在飞闹钟作废；delete 直接删定义，在飞闹钟醒来查不到规则自然作废；事件触发的"自我事件不触发自我"防自环原样生效。
- 进 `WRITE_TOOLS` 过闸门；10-C 三档里与 `partner_manage` **同档高危**（`DEFAULT_CRITICAL_TOOLS`，自主轮强制 ask、禁"记住"绕过）。
- 回滚 `ROUTINE_SELF_SERVICE=false`（§6）→ 工具不上架，回到"只有 HTTP 能建规则"的形态。
- **不自动建周回顾规则**；盘点口径见 §2.11「工作履历与当前目标」。

### 2.11.1 自主轮审批（2026-11-05 批次C C2）

`approval` 事件与 `POST /agent/approvals/:callId` 的记录多一个可选字段 `origin: "autonomous"`

答复端点的 `remember` 参数对自主轮记录忽略。普通轮的审批行为完全不变（审批档口径不动，§2.18）。

开启后把「卡住 / 等你 / 出错 /
用量受限」写成会话内一行（`【需要你】…`，≤140 字，枚举化，不经模型），手机拉 transcript 可见。

#### 2.11.2 副会话（2026-11-17 一人多会话批1）

**总口径**：每个执事 = 1 条主会话（canonical，`partner-<id>`）+ N 条副会话（side，
`partner-<id>-side-<8位hex>`）；总管不建链接，它的"多会话"就是现成的多条 `chatKind=chief`
会话。副会话与主会话共用同一份人设 / 记忆 / 项目，但**不被派活唤醒、不接定时主动轮、
不涨人格**——三条自动流程仍只认 canonical（路由规则表与取舍见设计方案/系统架构 D29）。
开关 `PARTNER_SIDE_SESSIONS` 默认开、hot；关掉 = 不列、不建；已存在的副会话历史仍可按 id 读，
但不能继续发消息（续话 409，见分册1 §2.1）。

**1. `GET /api/v1/partners/:id/sessions` —— 列会话（给选择器用）**

- 开关关 → `400 {"error":"side_sessions_disabled"}`。
- `id === "chief"`：列最近 `chatKind === "chief"` 且**不以 `partner-` 开头**的会话，
  按 `lastAt` 倒序；返回 `{ok:true, partnerId:"chief", kind:"chief", sessionManage, sessions:[…]}`，
  每条 `role: "chief"`（界面把第一条**没有 `origin` 来源**的当主对话，身份不变）。
- 其他执事：不存在 → `404 {"error":"not_found"}`；非 `active` → `409 {"error":"partner_inactive"}`。
  会话 = canonical（`sessionIdOfPartner` 换成对外 id）+ 全部 side 链接的 `routeKey`；
  canonical 永远第一，其余按 `lastAt` 倒序；**已归档的不返回**（`chat-meta` 过滤）。
  返回 `{ok:true, partnerId, kind:"partner", sessionManage, sessions:[…]}`，每条形如：
  `{conversationId, role: "canonical"|"side", title?, firstText, lastAt, turns, pinned?, origin?, deletable}`。
- 列表一次取 `sessionLinksMap()` 快照批量标注，不逐条查链接表（避免 N+1）。
- 2026-11-18 补两个派生字段（方案《2026-11-18-分支会话删除与选择器二级菜单》）：
  - `origin`：分支副本的来源，直接取 `ChatOrigins.byExternal`；没有分叉就不出现；
  - `deletable`：选择器里能不能直接删——执事 `role=side` 或总管带 `origin` 的副本，
    且该会话没有**未归档**子分支；主对话 / 总管无来源会话恒为 `false`；
  - 顶层 `sessionManage`：开关生效值，前端据此决定缩进还是平铺旧列表。

**2. `POST /api/v1/partners/:id/sessions` —— 新建会话**

- body 可选 `{ "title": "装修那摊事" }`（≤80 字，超了 `400 {"error":"bad_title"}`）；
  给了就用 `renameChat` 写进 `chat-meta.titles`。
- `id === "chief"`：建一条普通 `chatKind=chief` 会话、不登记任何链接，返回 `role: "chief"`。
- 其他执事：`createPartnerSideSession` 建 `partner-<id>-side-<token>`（token = 8 位小写 hex），
  登记 `role='side'`、按当前身份装配 `instructions`，并把工作目录钉到主工作区（与 canonical 同口径）；
  返回 `role: "side"`。不存在 → 404；暂停 / 归档 → 409；会话建不出来 → 503。
- 返回 `{ok:true, conversationId, role}`。**不发送问候语、不写任何消息**
  （与 `/partners/:id/open` 的首次问候行为刻意不同）。
- 开关关 → `400 {"error":"side_sessions_disabled"}`。

**3. `POST /api/v1/partners/:id/sessions/:conversationId/delete` —— 删除分支/副会话（2026-11-18）**

- 永久删除，**不走归档**：删掉这条会话的对话记录（conversations / entries / tasks /
  submissions / 该会话的 documents），并清 `Chats` / `ChatKinds` / `ChatProjects` /
  `ChatOrigins`、`chat-meta` 痕迹与 `partner_session_links` 的 side 链接。
  记忆、附件文件、磁盘目录不动。
- 范围：执事 `role='side'` 的副会话；总管带 `ChatOrigins` 的分支副本。
  **canonical 主对话、总管无来源的主对话、普通 worker 会话不走这个端点**（worker 仍走归档 → 永久删除）。
- 有**未归档**子分支（`ChatOrigins` 里还有以它为 source 的会话）→ `400 {"error":"has_branches"}`，
  文案带数量；不做级联。已归档的子分支不挡（恢复后成为一条独立副会话）。
  忙（`pi.live.run`）→ `400 {"error":"conversation_busy"}`。
  `400 chat_hard_delete_disabled` / `503 llm_unconfigured`（复用永久删除总闸）、
  `404 unknown_session`、`409 not_side_session`。
- 返回 `{ok:true, conversationId, deleted:{conversations, entries, tasks, submissions}}`。

**不包含**：canonical 主对话的删除、级联删除子分支、批量删除、会话级人设 / 项目挂载 / 工具名单。
