### 2.15 记忆管理（2026-11-06，设置页用；2026-11-08 扫尾批 6 补整理与导入）

**人对自己的记忆的五个动作**：看 / 删 / 标过时 / 整理（只出建议）/ 导入（只增不改）。
写入在 `memory-api.ts`（路由只做形状映射），语义在 `agent.ts` 的 `memoryOverview` /
`forgetMemory` / `supersedeMemory` 与 `memory-consolidate.ts` 的
`reviewScope` / `applyProposal` / `importMemory`。

> **路径口径（2026-11-08 验收时统一）**：记忆管理全部端点（含整理与导入）统一在
> `/api/v1/agent/memory/*`——实现初版按方案原文落在 `/api/v1/memory/*`，验收时对齐既有
> 记忆端点族前缀（同一模块挂载、同一套鉴权与错误口径）。

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/memory?scope=global&limit=300` | `{ok, enabled, extract, total, byKind, items[], canConsolidate, canImport}`；`scope` 缺省 `global`（偏好与日记摄入都在这里），执事传 `partner:<uuid>`；`limit` 上限 2000 |
| `DELETE /api/v1/agent/memory/:id` | 硬删一条 → `{ok, deleted}`；不存在 → 404 `not_found` |
| `POST /api/v1/agent/memory/:id/supersede` | `{byId?: string \| null}` → `{ok, superseded, byId}`；把这条标为"已被取代"，之后不再进召回候选，历史链仍可查（`includeSuperseded`）。`byId` 为空 = 仅下线；替代者不存在 / 自指 / 目标不存在 → 404 `not_found` |
| `POST /api/v1/agent/memory/consolidate/review` | §2.15.1：让模型出整理建议（**只建议、不执行**）；成功后另跑一次确定性审计并落 diff |
| `POST /api/v1/agent/memory/consolidate/apply` | §2.15.1：逐条应用一条建议（幂等 supersede） |
| `POST /api/v1/agent/memory/consolidate/pass` | §2.15.3：跑一次确定性巩固审计 `{scope}` → `{ok, scope, generatedAt, kept, merged[], retired[]}`；**只出建议、不删** |
| `GET /api/v1/agent/memory/consolidate/diff` | §2.15.3：读上次审计结果（`{ok, scope, generatedAt, kept, merged, retired}`）；没跑过 → 404 `not_found` |
| `POST /api/v1/agent/memory/import` | §2.15.2：把旧记忆只增不改地并进来 |

`items[]` 一条的形状：`{id, kind, scope, content, importance, veracity, source, createdAt,
recallCount, supersededBy}`。`kind` ∈ `preference` / `fact` / `episode` /
`entity` / `intention` / `experience` / `work`（`work` 是履历台账，档案页专用；2026-11-10 批 17 加
`experience`）。`usageCount` / `lastUsedAt` 目前只进巩固审计 diff，不在本列表回吐。

**`canConsolidate` / `canImport`（2026-11-08，纯增量能力位）**：分别由
`MEMORY_CONSOLIDATE_LLM` / `MEMORY_IMPORT` 下发；前端据此决定渲不渲染「整理记忆」「导入记忆」。
关着时对应端点 404。老客户端忽略这两个字段即可（与 `GET /agent/policy` 的 `attachments` 同口径）。

**列表口径**：默认只列 `global`、**不含已被取代的**、不含 `session` scope 的原始沉淀
（那是对话正文的副产品，清理走删会话）。排序 = `preference → fact → entity → episode`，
组内按 `createdAt` 倒序；`byKind` 是当前返回集内的分项计数。
`importance` 是库里的**当前值**（召回命中会 +0.05、久未想起会按 `MEMORY_DECAY_DAILY` 衰减，
下限 0.1 / 上限 10）。

`extract` 是**实际生效**的抽取档：`llm` = 偏好走一次独立模型调用、其余走规则；
`rule` = 全规则（也包含"模型不可用"的降级结果）。取值来源见 §6 的 `MEMORY_EXTRACT`。

**错误口径**（与其它管理端点一致）：
- 记忆未启用（`MEMORY_ENABLED=false` 或初始化失败）→ **404 `memory_disabled`**（不是 503：
  这不是"依赖暂时不可用"，是这个能力在这台机器上没开）；
- id 为空 → 400；`byId` 不是字符串 → 400；`scope` 不是 `global` / `partner:<id>` → 400；
- 鉴权失败仍是 403 空体（§1，中间件统一处理）。

#### 2.15.1 整理记忆（2026-11-08 扫尾批 6 §二，`MEMORY_CONSOLIDATE_LLM`）

**语义（D18 底线）**：模型**只产出建议**，一条都不自动执行。应用必须由人在设置页逐条点
「应用」，走既有 `supersede()`（旧记录保留、可追溯）。**没有"全部应用"**。

`POST /api/v1/agent/memory/consolidate/review`

- 请求 `{"scope":"global"}`（或 `partner:<uuid>`）。
- 取该 scope **最近 ≤200 条**（不含已被取代的）喂给一次独立模型调用（默认模型链、不进主会话），
  超时 30s，最多 50 条建议。
- 响应：

  ```json
  {
    "ok": true, "scope": "global", "total": 42, "generatedAt": "2026-11-08T…",
    "proposals": [
      { "keepId": "…", "dropId": "…", "reason": "后一条已过时",
        "keep": {"id":"…","kind":"fact","content":"我搬到上海了","importance":0.72,"createdAt":"…"},
        "drop": {"id":"…","kind":"fact","content":"我住在北京","importance":0.5,"createdAt":"…"},
        "evidence": {"conversationId":"…","at":1699…,"role":"user","text":"…我一直住北京，通勤方便…"} }
    ]
  }
  ```

- `keep` / `drop` 是两端正文（前端不必再反查列表）；`keepId` / `dropId` 必须来自本次清单——
  模型编造的 id、自指、重复对一律丢弃（宁可少建议）。
- **`evidence`（2026-11-10 对标 Anthropic「做梦」§一，`MEMORY_REVIEW_EVIDENCE`）**：drop 端正文在
  **原始会话记录**里的命中片段（归一化锚点 4~12 字匹配、摘原文 ±40/80 字，正文首行为准、
  Why/How 不参与匹配）。**只建议、不执行的原则不变**：证据只是摆到人眼前供核对，
  查不到 = `null`（卡片提示"未找到原始出处"，**不挡应用**）；开关关着时字段整个不下发。
  查找在模型成功之后、单遍扫 ≤200 会话（任务专线与隐藏会话天然不在内），全部命中即早停；
  查找失败降级为全部 null（建议照常返回）。引文**过凭据打码**（与记忆正文同一政策）；
  **不落待决文件**（`.data/memory-proposals.json` 仍只存 id / 理由 / 两端正文快照），
  evidence 只随本次响应下发。前端：命中渲染成可点回原对话的引文块
  （`openConversation` 单入口跳转）。
- 少于 2 条记忆 → `proposals: []`，**不打模型调用**。
- 待决建议落 `.data/memory-proposals.json`（按 scope 存，可用 `MEMORY_PROPOSALS_PATH` 覆盖；
  原子写，坏文件当空账）。它只是"上次生成了什么"，刷新不回放，重新整理会覆盖。
- 失败口径**如实 5xx，不假装**：未配置可用模型 / `LLM_PROVIDER=faux` → 503
  `llm_not_configured`；调用失败 / 超时 / 输出解析不了 → 502 `llm_failed`。
- `MEMORY_CONSOLIDATE_LLM=false`（或 `0` / `off`）→ 本组两个端点 **404**（同"未启用"口径）。

`POST /api/v1/agent/memory/consolidate/apply`

- 请求 `{"scope":"global","keepId":"…","dropId":"…"}` → `{ok, scope, keepId, dropId, alreadyApplied}`。
- **幂等**：`dropId` 已经指向同一个 `keepId` → 200 `alreadyApplied: true`，不再写一次；
  指向别的记录 → 400 `already_superseded`。
- `keepId` / `dropId` 不存在或不属于该 scope → 404 `not_found`；两者相同 → 400。
- 成功应用后从待决文件摘掉这一条（刷新再点整理不会重复弹同一张卡）。

#### 2.15.2 导入记忆（2026-11-08 扫尾批 6 §三，`MEMORY_IMPORT`）

`POST /api/v1/agent/memory/import`

- 请求：

  ```json
  {
    "scope": "global",
    "items": [
      { "text": "我住在上海", "kind": "fact", "createdAt": "2023-05-01T00:00:00.000Z", "importance": 0.7 }
    ]
  }
  ```

  - `scope`：`global` 或 `partner:<uuid>`；
  - `items`：数组，单次上限 5000 条；
  - `text`：必填，非空、≤2000 字；
  - `kind`：可选，`fact`（缺省）/ `episode` / `preference` / `entity`；认不出的值整条跳过；
  - `createdAt`：可选，合法 ISO 就保留；非法或缺省 = now；**未来时间裁到 now**；
  - `importance`：可选，缺省 `0.5`，夹到 `[0.1, 1]`。
- 响应 `{ok, scope, added, skipped, total}`（只报条数，不回显正文）。
- **只增不改**：绝不覆盖 / 删除 / 修改已有记录（不提升 importance、不改正文）。
  规范化等价（同 scope + 同 kind，trim / 空白折叠 / 全半角统一 / 句末标点剥除后相等）→
  **跳过并计数**；同一批内的重复同样跳过；**已被取代的记录也算"已经存在"**
  （不把用户明确标过时的内容重新捞回来）。
- 导入记录 `source="imported"`、`veracity="imported"`，照常参与召回；
  **不参与"重复收敛"去重别人**（不提升别人、不取代别人），只会被别人收敛（后续真实对话撞上它时照常 +0.1）。
- 文件格式（设置页「导入记忆」）：**裸数组**，或 `{"items":[...]}`；条目字段同上。
  前端只解析 + 数条数，不预检内容；确认后整份交给服务端逐条校验。
- `MEMORY_IMPORT=false`（或 `0` / `off`）→ 端点 **404**、按钮不渲染。

#### 2.15.3 巩固审计（2026-11-10 批 17 §三，`MEMORY_USAGE_RANKING` 默认开）

**确定性、只读**：算一份「可合并 / 建议淘汰 / 留下几条」的差异摘要，落
`.data/memory-consolidate-diff.json`（可用 `MEMORY_CONSOLIDATE_DIFF_PATH` 覆盖；原子写）。
**淘汰只出建议，绝不自动删**——没有"应用淘汰"端点；删一条仍走 `DELETE /memory/:id`。

`POST /api/v1/agent/memory/consolidate/pass`，请求 `{"scope":"global"}`（或 `partner:<uuid>`）：

```json
{
  "ok": true, "scope": "global", "generatedAt": "2026-11-10T…", "kept": 41,
  "merged": [{ "keepId": "…", "dropId": "…", "summary": "≤40 字" }],
  "retired": [{ "id": "…", "kind": "fact", "summary": "≤40 字" }]
}
```

- **保留优先级**：`usageCount` 降序 → `lastUsedAt` 降序 → `createdAt` 降序。`usageCount` /
  `lastUsedAt` 在召回命中时 +1 / 置为 now（与 `recallCount` 同点），只服务巩固排序。
- **合并建议**：同 scope + 同 kind + 规范化等价（work / intention 除外），保留优先级最高的那条。
- **淘汰建议**：距 `lastUsedAt ?? lastRecalledAt ?? createdAt` > 90 天、`importance < 0.5`、
  kind 不是 `preference` / `experience` / `work` / `intention`（有效打算不淘汰）。已被列为合并 drop 的不再重复列。
- `kept` = 总数 − 合并建议数 − 淘汰建议数。文件里只记 id、kind 与 ≤40 字摘要，**不记正文**。
- `GET /api/v1/agent/memory/consolidate/diff` 读同一份；没跑过 → 404 `not_found`。
- `MEMORY_USAGE_RANKING=false`（或 `0`）：保留优先级回到 `createdAt` 倒序、**不给淘汰建议**（`retired: []`），diff 形状不变（一行回滚）。
- `POST /consolidate/review` 成功后自动跑一次本审计（模型失败则不落快照）。

**刻意没有**：编辑（改记忆等于让它变成第二个人格，删了重说更干净）、全文搜索、
导出、跨设备同步、**语义自动去重 / 自动冲突消解 / 自动删除**（`supersede` 只做显式取代，
模型只出建议、人拍板；理由见架构 D18）、后台巩固 cron、embedding、**"全部应用"按钮**。

### 2.16 长期课题（2026-11-07 长期课题跟进落地；`TOPICS_ENABLED` 默认开）

`TOPICS_ENABLED=false`：本节端点全部不挂载（404 语义 = 未启用）、`web_search` / `propose_topic` 不上架、TopicTask 不排。

课题实体存 `.data/topics.json`（原子写，§3）：`{ id(uuid), question, flavor("watch"盯梢型|"dig"啃题型), cron, status(active|paused|closed), revision, origin(user|proposal), findings[{id,date,summary,body,noNew,runConversationId?}], pendingPush, noNewStreak, … }`；提议 `{ id, question, flavor, cron, origin, status(pending|accepted|declined|expired), expiresAt(72h) }`。

| 端点 | 说明 |
|---|---|
| `GET /api/v1/topics` | 列表 + `activeCount`（findings 只带最新 summary，不展开正文） |
| `GET /api/v1/topics/:id` | 详情，findings 全量倒序 |
| `PATCH /api/v1/topics/:id` | `{ cron?, status? }`：改节奏重排闹钟、active⇄暂停；`revision` +1 |
| `POST /api/v1/topics/:id/close` | `{ reason? }` 关闭（数据保留不删） |
| `POST /api/v1/topics/:id/run_now` | 立即研究一次（后台专线对话；探针与界面用） |
| `GET /api/v1/topics/proposals/:id` | 提议状态（确认卡刷新用） |
| `POST /api/v1/topics/proposals/:id/accept` | 确认 → 建课题 + 排闹钟；400：`search_not_configured`（搜索没配，§2.17）/ `topic_limit`（进行中 ≥ 5）/ `exists`（同题已在跟，带已有课题 id）/ `expired` / `not_found` |
| `POST /api/v1/topics/proposals/:id/decline` | 谢绝 |

- **表达口只有两个**：用户直说（总管调 `propose_topic`，同样只出确认卡）/ 总管嗅探（判据在 chief 系统提示，从严：开放性问题 + 今天给不了定论 + 值得隔几天回头看 + 用户显出兴趣）。**只提议，永不自动建**。
- **研究回合**：`TopicTask`（durable 闹钟，范式 = RoutineTask：sleepUntil + revision 对号 + 同事务排下一次）到点或 `run_now` 触发 → 后台专线对话（`task-topic-` 前缀，不进侧栏对话列表、**不出任务中心卡**），系统提示注入课题问题 + findings 全量（接着上次往下查）；工具面只读 + `web_search`；结束**确定性**取最后一条 assistant 消息为 finding，末行按「相比上次：无新进展」解析 `noNew`。研究回合无模型不重放（重启 interrupted 不自动跑，同例行任务铁律）。
- **感知推送**：研究产出 → `pendingPush` → 总管 chief 对话下一轮 section 注入简报块，**渲染即标记已推送**（每课题每次活跃只报一次）；worker 对话（网页普通对话 `chatKind=worker`）与群会话不注入，按设计课题上下文只跟总管。
- watch 型连续 3 次 `noNew` → 随下次简报提议"饱和关闭"（仍是提议，不自动关）。

### 2.17 搜索源配置（2026-11-07 单一 DeepSeek；2026-11-12 多供应商，课题研究的硬前提）

> **2026-11-07 路径更正**：本节端点原误与 §2.6 内容搜索同占 `/api/v1/agent/search`（Hono 先注册者胜，
> 内容搜索自课题批次起实际被遮不可用——http 探针 §12 抓出）。搜索源管理整体挪到
> **`/api/v1/agent/search-provider`**；内容搜索留在原路径（§2.6，网页搜索框在用）。
>
> **2026-11-12 多供应商**：路径不变，语义从「一个 DeepSeek key」扩成「有序搜索源列表」。
> 源清单落 `.data/search.json`（只存 vendor / 顺序 / 地址覆盖），key 仍落
> `.data/provider-keys.json`（按各源 `keyEnv` 取 env）。旧字段 `keyEnv` / `hasKey` 保留兼容。
> 界面落点从「设置 → 服务」搬到「设置 → 模型 → 搜索」。

- `GET /api/v1/agent/search-provider` →
  `{ ok, configured, keyEnv, hasKey, sources[], vendors[] }`。
  `sources[]` = 已配置的源，按尝试顺序：`{ vendor, name, keyEnv, hasKey, baseUrl, usable, keyOptional, needsUrl, keyUrl, note }`；
  `vendors[]` = 可添加的目录（同上字段 + `configured`）。只回变量名，**绝不回显值**。
  旧客户端字段：`keyEnv` = 首个源的变量名，`hasKey` = 是否有任一可用源。
- `PUT /api/v1/agent/search-provider` `{ vendor?, apiKey?, baseUrl? }`：新增 / 更新一个源（按 vendor 去重）。
  `vendor` 缺省 `deepseek`（旧客户端兼容）；`apiKey` 有值才写密钥文件并热注入，空 / 缺省表示沿用已有 env；
  `baseUrl` 只在传了才改，空串清掉覆盖；返回同 GET 的完整投影。错误：
  `secrets_disabled`（`PROVIDER_SECRETS=false` 且带 apiKey）/ `missing_key`（该源需要 key 但 env 也没有）/
  `missing_url`（SearXNG 没地址）/ `unknown_vendor` / `bad_base_url`（非 http(s) 或带账号密码）。
- `DELETE /api/v1/agent/search-provider?vendor=`：移除源；`vendor` 缺省 `deepseek`（旧行为）。
  同时清密钥文件条目与运行期 env（`.env` 手写的值重启后仍在，但 `search.json` 已不含该源，不会被使用）。
- `PUT /api/v1/agent/search-provider/order` `{ vendors: string[] }`：按传入顺序重排；只认现有源，未列到的接在后面。
- `POST /api/v1/agent/search-provider/test` `{ vendor? }`：真调一次搜索（count=1）；
  不传 vendor 测第一个可用源 → `{ ok, vendor, hits, message }` 或枚举错误
  （`search_not_configured` / `upstream_error` / `bad_response`），message 为引导文案。
- **源目录（2026-11-12）**：DeepSeek / Tavily / Exa / 百度搜索（千帆 `POST /v2/ai_search/web_search`）/
  元宝搜索（腾讯云 WSA `POST /SearchPro`）/ Brave Search / Firecrawl / 豆包搜索（火山引擎
  `POST /search_api/web_search`）/ TinyFish / SearXNG（自建，免 key）。请求与回包映射在
  `search-vendors.ts`；失败或零命中按列表顺序回退，第一个有结果的生效。
- 兼容：没有 `.data/search.json` 时从 env 里的 key 反推源（`DEEPSEEK_SEARCH_API_KEY` 继续有效）；
  `SEARCH_BASE_URL` 仅对 deepseek 源生效（探针把请求指向本地 stub 用）。
- 回滚：`SEARCH_MULTI_VENDOR=false`/`0`/`off` → 只读 deepseek 一条源，GET 目录只剩 DeepSeek，
