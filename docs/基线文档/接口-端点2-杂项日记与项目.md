| `GET /api/v1/agent/approvals?conversationId=<uuid>&limit=50` | 待批审批（2026-11-04 批次二；批次六加全局形态；E2 #0 加 origin；2026-11-08 批三按会话形态也带 `conversationId`；8c 起 pending 跨重启保留） | **`conversationId` 可选**：带 = 只查该会话（原语义不变，2026-11-08 起投影也带同一个对外 `conversationId`，前端据此给审批卡标「来自 …」：`{ok,approvals:[{conversationId, callId,tool,args,deadlineAt,createdAt,origin?}]}`）；**不带或空串 = 全局待办**（跨会话、只回 pending、按 `createdAt` 升序，`limit` 默认 50）：`{ok:true, approvals:[{conversationId, chatTitle?, callId, tool, args, deadlineAt, createdAt, origin?}], limit}`。**两种形态都可选带 `origin:"autonomous"`**（E2 #0，从 `ApprovalRecord.origin` 纯增量透出）：例行任务/事件唤醒的自主轮审批才有，普通轮**不带该键**（老客户端按字段忽略）；前端据此把卡片标「例行任务」。全局项的 `conversationId` 是**对外 uuid**；`chatTitle` 取 `.data/chat-meta.json` 的改名表 `titles[uuid]`，取不到就**省略该字段**（界面显示「未命名会话」），不会逐会话 `openChat`。群成员会话的对外 id 形如 `partner-<partnerId>-group-<groupId>`，前端按它反查群名 + 成员名。`deadlineAt` 在 async 形态（缺省）下**只是展示字段**，不据此结算（见下方形态说明）。未知会话 → 404；未配置模型 → 503 |
| `POST /api/v1/agent/approvals/:callId` | 答复审批（2026-11-04 批次二；2026-11-08 扫尾批 8c 加续跑；2026-11-09 加 `feedback`） | body `{decision:"approve"\|"reject", remember?:boolean, feedback?:string}`；`decision` 非两值 → 400；`feedback` > 500 字 → 400；未知 `callId` → 404；**已决 → 200 返原决定（幂等）**；成功 `{ok:true, status}`（`approved` / `rejected`）。`remember` 只在批准时生效，进程内记住「本会话 + 该工具」，重启失效。**`feedback` 只在 reject 时生效**：带了就把回给模型的拒绝理由换成「你拒绝了这次 `<tool>` 调用。主人的要求：`<feedback>`」；不带**逐字节等于**旧文案。**ask_user 的 pending 不能用这个端点答复**（400 `ask_user_answer_required`，走 `/answer`）。**async 形态（缺省）下，真正从 pending 结算的那一次答复会自动向该会话提交一条 followUp**（批准 → 让模型立即原样重发该调用；拒绝 → 让模型继续其余工作；带 feedback 时拒绝指令就是上面那句「主人的要求」）；幂等重发不再触发。blocking 形态（`AGENT_APPROVAL_MODE=blocking`）不提交 followUp，由钩子里的等待自己醒，拒绝理由同样带 feedback |
| `POST /api/v1/agent/approvals/:callId/answer` | 答复 `ask_user` 提问（2026-11-09 §3/§4.4） | body `{answer:string}`（≤1000 字，空/超长 → 400）；未知 `callId` → 404；记录不是 `kind:"ask_user"` → 400 `not_a_question`；成功 `{ok:true, status:"answered"}`（幂等，重复答复不重复续跑）。答复正文作为 followUp 提交给会话；模型下一轮从这条用户消息里读到答复 |
| `GET /` | 界面（静态 UI） | 不受 `/api/v1` 鉴权影响，但数据接口都受 |

**会话索引字段（2026-11-12 归档模块）**：`GET /api/v1/agent/chats` 的响应从 `{chats, removed}` 改为
`{chats, archived}`——`archived` 是归档计数（原 `removed` 字段删除；手机端只读 `chats`，已核对不断）。
归档清单的独立端点是上表的 `/chats/archived`；响应字段口径见 §5。

**手机 worker 通道（2026-11-02 契约；2026-11-10 批 26 §一 加执行前重验）**：
`POST /api/v1/worker/poll`（要活，没活挂起后 204，同设备新 poll 顶掉旧的）、
`POST /api/v1/worker/model`（服务端 key 代理）、`POST /api/v1/worker/result`（交结果）。
服务端的保证只有两条：① **已取消 / 已超时的单不再交给 poll**（队列里跳过，收尾交各自的
计时器 / abort 监听）；② **已取消 / 已超时的单交回结果时不写回**——返回
`200 {"ok":true,"applied":false,"reason":"canceled"|"expired"}`（本批之前是 `404 unknown_task`；
正常路径仍是 `{"ok":true}`），并记一条只含单号的日志。取消墓碑在内存保留 10 分钟、上限 200 条。
回滚：`PHONE_ENSURE_ACTIVE=false`（§6）。
**已知边界（如实登记）**：手机拿到单之后、真正开始执行之前的那一段在手机侧，服务端无法代查——
本批不新增 preflight 端点，也不改手机端契约；取消只有发生在交付窗口内才保证"不产生副作用"。

审批（2026-11-04 批次二；2026-11-08 扫尾批 8c 改缺省形态、10-C 改三档）只在审批档不是 `none`
时产生（`ask-all` = 写类工具 ∪ 高危清单全问；`ask-critical` = 只问 `AGENT_APPROVAL_CRITICAL_TOOLS` 清单，
缺省 `bash` / `powershell` / `delegate` / `partner_manage` / `send_to_agent` / `routine_manage`）；
`none`（默认）时零行为变化，`GET .../approvals` 没有 pending（未配置模型时回 `503`，同 `/stop`）。

**缺省形态 = 等待态落库（async）**：被拦的写类工具**不阻塞本轮**——落一条 pending 记录（带工具名、
参数摘要与参数指纹）后，把「该操作在等用户批准」作为工具结果回给模型，本轮照常收尾（零挂起、零等待）。
人答复后服务端向该会话**自动提交一条 followUp**：批准 → 「用户已批准 X，立即原样重发这个调用」；
拒绝 → 「用户拒绝了 X，请继续其余工作」。模型重发同一个调用时，闸门按**一次性放行清单**
（工具 + 参数指纹，命中即核销）放行，不再问；换参数重发不会命中（防「批了 A 执行 B」），重新挂一条待批。
**pending 永不自动过期**：重启后仍保留可答（`load()` 不再置 `timeout`）；同一会话里同工具 + 同参数的
pending 只挂一条（模型重试不重复弹卡）。`/stop` 仍把该会话的 pending 按 `aborted` 结算，并作废该会话
未核销的放行。

**续跑轮进记忆（2026-11-08 批 10-A）**：自动 followUp 驱动的这一轮与普通轮走**同一个**收尾 handler
（观察层 / 记忆抽取 / 会话记忆修剪），不再有"审批续跑不进记忆"的缺口；任务专线（`task-` 前缀）照旧不进记忆。
代价是审批指令本身（服务端生成的文本）也会作为用户侧内容被抽取，属如实记账。

**回滚形态 = blocking**（`AGENT_APPROVAL_MODE=blocking`，见 §6）：完整回到 2026-11-04 的行为——工具回合
挂起等待，`AGENT_APPROVAL_TIMEOUT_S`（默认 120 秒）超时按拒绝；启动时遗留 pending 一律置 `timeout`。
两种形态的契约字段相同（`approval` 帧、GET 投影、POST 答复），前端按 `GET /agent/policy` 的
`approvalMode` 决定审批卡显示倒计时还是「等待处理」。

**已知边界（8c 登记）**：不做「工具结果回填」——pi-durable 1.4.0 没有向已收尾 run 回填工具结果的入口，
所以选「模型重发调用」（每次批准多一轮模型调用，但零内核改动、可靠）。

**全局待办的数据边界（2026-11-04 批次六）**：不带 `conversationId` 时，列表把**所有会话**的待批工具参数
（`args`，截断 1200 字符）返回给任一已配对设备（deviceToken 与共享令牌同权限）。这与 `GET /api/v1/agent/chats`
的既有边界一致——持令牌者本来就能列出全部会话并按 id 回读正文，**不是新增提权**。任务会话（`task-` 前缀）
天然没有工具、不产生审批；已「移除」的会话仍可能出现（标题可能为空）。列表不返回正文，只有审批所需的工具名与参数摘要。

**结构化提问（`ask_user`，2026-11-09 §3）**：它借审批 pending 管线，`GET .../approvals` 的每一项额外带
`kind:"ask_user"`（普通审批**不带该键**），`args` 是问题 JSON：`{question, options?, recommended?}`
（question ≤200 字；options 2-3 个、每个 ≤60 字；recommended 是建议项下标）。客户端据此渲染问题卡，
答复走 `POST .../approvals/:callId/answer`；`/stop`、重启保留、全局待办等语义与普通审批完全一致。
**答案沉淀（2026-11-10 批 19 §二）**：答复成功后额外把 `{question, answer}` 写成一条
`kind=fact`、`source=verified_answer` 的记忆（scope = 发起会话），下次同类问题不必再问；
群会话不落，`AGENT_VERIFIED_ANSWER=false` 关闭。只改记忆，不改答复与续跑语义。
手机端零改动（当前只会把它当普通审批卡；请走 `/answer` 的客户端才可答复）。

**审批的作用半径（2026-11-10 批 16 §三）**：审批档按"谁能改、多久生效"分三类，客户端文案与产品说明都按这个口径讲，
不要混成一句"关闭审批"：**即时生效**——API 引擎的 `AGENT_APPROVAL_*` 环境变量与界面开关，改完**下一轮**的工具调用
就按新档判（已在跑的那一轮里判过的调用不回改）；**turn 锁定**——自带模式的引擎（qoder / codebuddy 这类 CLI，
`--permission-mode` 在起子进程时写死）一个 turn / 一单内不变，换档只能重开一单；**代答型**——`ask_user` 的答复
与审批 pending 的答复，**立即生效、只作用于这一次调用**（批准 = 工具 + 参数指纹核销一次，问题答复 = 交回原单的一次输入），
不是"以后都放行"。三类都**不提升能力边界**：只读 / 黑名单的 `block` 永远优先于任何答复。

### 2.6 `POST /api/v1/diary/sync` —— 日记成稿镜像同步（2026-10-29）

手机是日记的**权威**，这里只是**镜像**：唯一写入路径就是这个端点，**没有任何"在 harness 改日记"的入口**
（不提供 PATCH/DELETE）。设计与合并规则见 App 仓库
`docs/设计方案/2026-10-29-对话正文归位Harness（手机只留索引）.md` §7.1。

请求：

```json
{ "since": 1761700000000,
  "entries": [{ "id": "01j…", "status": "CONFIRMED", "source": "MANUAL", "localSource": "MANUAL",
                "entryDate": "2026-10-29", "finalText": "…", "rawSnapshot": "…",
                "types": ["NOTE"], "mood": null, "createdAt": 1761700000000,
                "updatedAt": 1761700000000, "deleted": false, "conversationId": null }] }
```

响应：

```json
{ "entries": [ …同结构… ], "serverTime": 1761700005000 }
```

| 项 | 口径 |
|---|---|
| 鉴权 | 与其他 `/api/v1/*` 相同（共享令牌 ∪ 设备凭据；失败 403 空体） |
| `since` | **闭区间**（`updated_at >= since`）：同一毫秒的行宁可重复下发，客户端按 `updatedAt` 幂等跳过 |
| 上限 | 上行不限（客户端 200 条/页）；下行单次 ≤ 200 行，按 `updated_at` 升序 |
| 截断 | 单条 `finalText` / `rawSnapshot` 各 **8KB 字节**（按 UTF-8 逐码点截断） |
| `deleted` | **软标记**，永不物理删除；软删时**保留已有正文**（后期分析"写过又删了"） |
| 合并 | 见下表 |
| 幂等 | 按 `id` 对齐，重发不产生第二行 |

合并规则（服务端看到的视角）：

| 场景 | 处理 |
|---|---|
| 镜像无该 id | 插入 |
| 上行 `updatedAt` 更新 | 覆盖（手机赢） |
| 两边 `updatedAt` 相同且内容一致 | 跳过 |
| 两边 `updatedAt` 相同但内容不同 | 手机赢 + 日志一行（单用户单设备，正常不会发生） |
| 上行 `updatedAt` 更旧 | 镜像保留，**把胜出的那行塞回响应**（客户端据此覆盖本地） |
| 上行 `deleted=true` | **只置标记与 `updated_at`，其余字段一律不动**（无论 `updatedAt` 是新是旧）。墓碑是最小形状（只带 id + 删除时刻），走"整体覆盖"会把已镜像的正文抹成空 —— 2026-10-30 真机踩过 |

`GET /api/v1/diary/status`（只读自检）：`{count, items:[{id,status,source,localSource,entryDate,updatedAt,deleted,chars}]}` ——
**不含正文**（避免被随手当接口读全文）。

存储：`.data/diary.sqlite`（`DIARY_DB_PATH` 可改），**独立库、不混进 pi-durable 的表**；
写入只在收到推送时发生，进程启动不碰盘（懒建）。

端到端探针：`pnpm --filter @lifediary/server diary`（真起服务 + 真实 HTTP，覆盖上表全部行）。

#### 2.7.0a 项目内的文件夹（项目容器，2026-11-13）

一个项目 = 一个名字 + 一组文件夹，其中**恰好一个主文件夹**（`role="primary"`）。主文件夹决定
`rootPath` 缓存列、相对路径基准、以及「这个项目新建的会话落哪」。附加文件夹只是「同一项目里
还能去哪些目录」，不改变相对路径基准。

| 端点 | 行为 |
|---|---|
| `POST /api/v1/projects/:id/roots` | body `{path, label?}`。加一个附加文件夹：`path` 绝对、已存在、可写，且不能与**任意项目任意根**同路径或互相包含。`label` 缺省取目录名；重名 → `400 duplicate_label`；同路径 → `400 duplicate_root`；落在已有根内部/包含已有根 → `400 inside_existing_project` / `root_overlaps_root`；等于/包含工作区根 → `400 bad_path`。成功 `{ok, project}` |
| `PATCH /api/v1/projects/:id/roots/:rootId` | body `{path?, label?}`（至少一个）。改这个文件夹的路径或显示名；改主文件夹的路径会同步 `projects.root_path` 缓存列并重测 `vcs`/`head`。只改登记，不动磁盘。错误码同上 |
| `POST /api/v1/projects/:id/roots/:rootId/promote` | 设为项目主文件夹：把这条改成 `primary`、原主降为 `extra`，同步缓存列。**只影响之后新建的会话**；老会话的 `pi.agent.cwd` 是创建时快照，不会跟着换。成功 `{ok, project}` |
| `DELETE /api/v1/projects/:id/roots/:rootId` | 移除一个**附加**文件夹的登记：磁盘目录和文件不动、历史会话不受影响。主文件夹 → `409 root_is_primary`；只剩一个根 → `409 last_root`（最后一个不给入口）。成功 `{ok, project}` |

历史库（只有 `projects.root_path`、没有 `project_roots` 表）在服务启动时自动补一条
`primary` 根（`label=目录名`、路径取原 `root_path`），幂等；见 `projects.test.ts`
「旧库（只有 projects.root_path）自动补一条 primary 根」。

#### 2.7.1 文件浏览入口（2026-11-06，方案 `docs/设计方案/2026-11-06-文件浏览入口（桌面资源管理器与手机端）.md`）

三个只读端点；契约 schema 在 `ts/packages/shared/src/index.ts`（`OpenExplorerRequestSchema` / `FileEntrySchema` / `FileListResponseSchema` / `FileContentResponseSchema`）。全部走 `/api/v1/*` 鉴权（失败 403 空体），业务拒绝 400 带说明。手机端本次不动，契约落 shared 即可。

| 端点 | 行为 |
|---|---|
| `POST /api/v1/workspaces/open-explorer` | body `{projectId?: string, rootId?: string}`（不收任意路径）：缺省打开工作区根；带 `projectId` 对**该项目的主文件夹**起系统资源管理器（按项目直达——侧栏入口用）；带 `rootId`（须配合 `projectId`）直达该项目里的**那个文件夹**（2026-11-13 项目容器；找不到 → `400 root_not_found`，目录不在 → `400 root_missing`）。Windows 走「Shell COM 开窗 + SwitchToThisWindow 切前台」（2026-11-11 起，窗口直弹顶层；`EXPLORER_FOCUS=false` 退回裸 spawn），mac/Linux 仍 explorer/open/xdg-open。项目复核与派单同口径（已登记、未移除、realpath；2026-11-12 起不要求在工作区内，回滚开关下仍要求），失败 `400 bad_project`；未设工作区 `400 no_workspace`；`EXPLORER_OPEN=false`（回滚开关）→ `400 explorer_disabled`。实现：`ts/apps/server/src/files.ts`，实现位置集中、`2026-11-06 全量审计确认` |
| `GET /api/v1/files?path=<相对路径>&projectId=<可选>&rootId=<可选>` | 目录列表 `{ok, path, entries:[{name,type:"file"\|"dir",size,updatedAt}]}`；`path` 相对**所选根**（`rootId` 指定的文件夹 > `projectId` 的主文件夹 > 工作区根）。`FILE_BROWSE=false` → 404 |
| `GET /api/v1/files/content?path=…&projectId=<可选>&rootId=<可选>` | 文本内容 `{ok, path, size, truncated, content}`；UTF-8 可解码且 ≤512KB 才回正文，二进制/超大 `content=null、truncated=true`。`FILE_BROWSE=false` → 404 |

安全口径：只收**所选根（工作区根或 `projectId` 的项目根）内的相对路径**（绝对路径 `400 bad_path`；`..` 与 realpath 落在根外 `400 outside_workspace`，含符号链接祖先逃逸，与 `path-guard.ts` 同口径）；**每个根的第一段 `.data` 屏蔽**（`400 blocked_path`，列表里也不出现；根内嵌套 .data 不拦）；日志只记路径与字节数，不记内容。验证：`pnpm --filter @lifediary/server files` 探针 + `files.test.ts` 单测（开启路径用注入 opener，不真弹窗口）。

校验口径：

| 场景 | 结果 |
|---|---|
| 未选工作区就提交新建 | `400 {"error":"no_workspace"}` |
| `path` 是绝对路径 / 含 `..` / 解析后在工作区外 | `400 {"error":"outside_workspace"}`（绝对路径报 `bad_path`） |
| 路径已经落在某个已登记项目内 | `400 {"error":"inside_existing_project"}`（属于项目内子目录，不登记新项目） |
| 加文件夹时和已有根嵌套 | `400 {"error":"inside_existing_project"}`（落在某个根里面）或 `400 {"error":"root_overlaps_root"}`（反过来包含了某个根） |
| 加文件夹时同路径 / 同显示名 | `400 {"error":"duplicate_root"}` / `400 {"error":"duplicate_label"}` |
| 移除主文件夹 / 移除最后一个 | `409 {"error":"root_is_primary"}` / `409 {"error":"last_root"}` |
| 项目名重复 | `400 {"error":"duplicate_project"}` |
| 路径经 realpath 解析后落在工作区外（含符号链接祖先逃逸） | `400 {"error":"outside_workspace"}`；**提交阶段就拒绝，不会先 mkdir 到工作区外** |
| 确认一条已处理过的请求 | `409 {"error":"already_decided"}` |

- 项目根目录**不要求位于工作区内**（2026-11-12 起平级；回滚开关 `PROJECT_OUTSIDE_WORKSPACE=false` 时恢复旧口径）。但它不能等于/包含工作区根，也不能与任意项目的任意文件夹同路径或互相嵌套——一个目录只属于一个项目。
- 2026-11-13 起，**一个项目可以带多个文件夹**（一个主 + 若干附加），但"一个目录只属于一个项目"这条没变：附加文件夹同样过 `assertRootPathAllowed`，与其他项目/其他根重叠一律拒绝。
- 登记时记录 `vcs`（有 `.git` 即 `git`）与当前 HEAD（读不到则 `head=null`）。
- 工作区变更不迁移已有项目：派单时按**当前**工作区复核，落在外面的项目会被拒绝。
- `delegate` 新派单必须带已登记 `project`；否则工具返回
  `{"ok":true,"data":{"error":"needs_project","message":…,"projects":[{id,name}]}}`
  （2026-11-10 批 23b 起工具结果统一包 `ToolResult`；`needs_project` 是业务分支，仍放在 `data` 里），
  **不建单、不建目录、不写文件**。
- **设备活豁免（2026-11-08 扫尾批 3-H B3）**：执行体为设备 worker 时 `project` 可省，按无项目单
  受理，不进 worktree/租约、也不进 `resolveDelegationProject` 的 `realpath` / 工作区复核。设备
  worker = 手机 worker（`CHANCELLOR_EMPLOYEE=phone`，chancellor `WorkerKind`）或带明确
  `targetDevice` 的设备派发；本机执行体（codebuddy/qoder/native 等）照旧必须带项目。
