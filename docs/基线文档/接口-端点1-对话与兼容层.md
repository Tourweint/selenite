### 2.1 `POST /api/v1/agent/chat` —— 对话（SSE，自有协议）

请求：

```json
{ "conversationId": "uuid（可选，不带=新建）", "messages": [{ "role": "user", "content": "…" }], "requestId": "可选，重试幂等", "chatKind": "chief | worker（可选）", "whenBusy": "steer | followUp（可选）", "model": { "providerId": "…", "modelId": "…", "thinking": "off | low | medium | high（可选）" } }
```

- `messages`：**实际只取最后一条 user**；更早的历史在服务端（durable 的会话里）。
- **`content`（2026-11-08 扫尾批 4a 图片；2026-11-13 附件走路径）**：从 `string` 扩成 **union**
  `string | ContentPart[]`，`ContentPart = {type:"text",text} | {type:"image",mimeType,data} | {type:"file",path,name,mimeType?,bytes?}`。
  - `image.data` 是**裸 base64**（不带 `data:` 前缀，形状对齐内核 pi-ai 的 `ImageContent`）；
  - `file` **只带绝对路径，不带内容**：壳里由原生选择器给出（零拷贝），浏览器里先调
    `POST /api/v1/agent/attachments` 落盘拿服务端路径（§2.3.3）。服务端只 `stat` 校验
    （必须是已存在的普通文件），**不读取、不内联**；
  - 纯字符串的老调用方（手机、OpenAI 兼容层、旧脚本）**逐字节不变**；
  - 服务端把文本 parts 用 `\n` 拼成 `text`（与 pi-ai `contentText` 同口径）、图片 parts 原样
    随 `submit` 下传；文件列表写成正文第一行清单（见下）；**纯附件无文本允许**；
  - 限制：**单图解码后 ≤8MB、单条 ≤4 张、单条 ≤8 个文件**，超限
    `400 {"error":"bad_request","message":"…"}`；
  - 回滚 `AGENT_ATTACHMENTS=false`：分段请求 → `400 {"error":"attachments_disabled","message":"…"}`，
    纯字符串照常（§6）；
  - **图片仍内联**：base64 直接进 durable 条目（粘贴截图没有路径，且模型直接看最快）；
    **文件内容不进 durable**，只在 durable 里留一段清单：
    `[附件] 用户附上了以下文件，需要时用 read 工具按路径读取：[{name,path,mimeType?,bytes?}]`
    （固定一行；回读时剥掉并还原成 `files` 字段）。图片是**输入侧**，不进任何 SSE 帧。
- `conversationId`：**必须是服务端发过的 id**；不认识的 id → `404 {"error":"unknown_conversation"}`（不会偷偷新建）。
- `requestId`：同一条用户消息重发时带同一个值 → 认成同一轮，不重复扣 token、不重复写记忆。
- **`whenBusy`（2026-11-07 消息即引导，纯增量；2026-11-19 插话统一 批1 改缺省）**：这一轮正在跑时，这句话怎么进。
  - `steer`（缺省，2026-11-19 起）：请求插进**当前这一轮**，模型在下一个边界（工具轮之后 / 收尾前）就能看到；
    多条插话全部生效（内核 `steeringMode="all"`，回滚 `AGENT_STEERING_MODE=one-at-a-time` 回单条）；
    忙时 steer 的提交正文第一行带 `[插话]` 标记（模型可见、历史可见；前端渲染成「插话」徽标）。
  - `followUp`：排到本轮结束，作为下一轮（改动前缺省；现降级为插件卡"忙时消息"档，关=排队）。
  - 它是**请求不是保证**：内核按"下一次边界"消费，没赶上就是下一轮的第一句。服务端会先发一帧
    `notice` 说明实际落点（见下表），不把"受理"说成"已插入"。不带该字段 = 跟随服务端缺省
    （回滚 `AGENT_STEER_DEFAULT=false` 时缺省回 `followUp`）。
- **`model`（2026-11-19 会话级模型切换，纯增量）**：新建会话的初始模型，
  形状 `{providerId, modelId, thinking?}`，**只在不带 `conversationId` 时采用**；
  不传 = 服务端读当前全局默认。已有会话带这个字段会被忽略（要换模型走
  `POST /agent/chat/:conversationId/model`，只影响那一条）。模型不在目录 → `400 {"error":"bad_model"}`。
- **`chatKind`（2026-11-06 侧栏调整 B2，纯增量）**：新会话种类，`chief` / `worker`，**只在不带 `conversationId` 时采用**；
  缺省仍 `chief`（手机与旧调用方零改动）。身份落在 durable 的 `lifediary.chat-kinds`（内部会话 id → 种类）：
  - 续话时带**不匹配**的值 → `400 {"error":"chat_kind_mismatch"}`，不隐式改身份；
  - 续话时不带 → 沿用已存种类；
  - 执事的 canonical 会话种类由 `partner_session_links` 判定为 `partner`，客户端不能自报；
  - `WORKER_CHAT_ENABLED` **2026-11-23 起默认关**（普通助手会话退役）：新建 worker →
    `400 {"error":"worker_chat_disabled"}`；已落盘的 worker 保持原身份（不会被重解释成总管），
    照常可续话。前端新建入口只剩「新建任务」（派给池），不再发 `chatKind=worker`。

  身份提示词也按种类分流（2026-11-06 B2）：`worker` 用独立的普通任务助手提示，**不读总管 SOUL**；
  执事 canonical 会话不注入总管 persona（身份来自其 `configure` instructions）；无记录旧会话仍走总管 SOUL。
  工具闸门 / 审批 / 工作区边界不因种类变化。

- **续话角色分流（2026-11-17 一人多会话批1）**：`kind === "partner"` 的续话按链接表
  `partner_session_links.role` 分流，不再只看 `chatKind`（完整口径见分册4 §2.11.2）：

  | 链接角色 | 续话行为 |
  |---|---|
  | `canonical` / `group` / `routine` / `topic` / `delegation` / 无链接 | 保持原行为：折回该执事 canonical |
  | `side`（副会话，`PARTNER_SIDE_SESSIONS` 开） | **不折回 canonical**：对齐这条副会话的身份后继续 |
  | `side`（`PARTNER_SIDE_SESSIONS=false`） | `409 {"error":"side_session_disabled","message":"副会话已关闭"}` |

- **`GET /api/v1/agent/chats` 增量字段（2026-11-17 批1，只增不改）**：每条会话多带
  `partnerId`（归属执事 id；无链接的总管 / worker 会话不返回）、`sessionRole`
  （`canonical` / `side` / `group` / `routine` / `topic` / `delegation`）、
  `isCanonical`（仅 canonical 为 `true`）。老客户端 / 手机端忽略未知字段即可；
  权威字段表见 `接口-存储工具与配对.md` 的 `GET /api/v1/agent/chats` 端点行。

响应（SSE，`data:` 行，JSON 依次为）：

所有事件帧都可带 **`seq`**（2026-11-04，SSE seq 与断点重放方案）：**会话内**从 1 单调递增的事件序号，
服务端先落库再外发。断线重连后带 `sinceSeq`（本地已收最大 seq）到 §2.2 的 `/messages` 精确补缺帧。
`AGENT_SSE_SEQ=off` 回滚后帧不带 seq，客户端按"没有重放可用"对待。老客户端忽略该字段，行为不变。

| type | 字段 | 说明 |
|---|---|---|
| `start` | `id`, `conversationId` | 首帧；**客户端必须存下 `conversationId`**（之后回读/停止都用它） |
| `thinking` | `text` | 思考正文**增量**（2026-11-04 批次一，deep 档才有内容）。客户端累计成段，折叠展示；老客户端忽略 |
| `delta` | `text` | 文本增量 |
| `progress` | `phase` | `thinking` / `working`：这一轮在想还是在动手 |
| `tool` | `name`, `status`, `label?`, `ok?`, `output?`, `args?`, `diff?` | 工具调用起止；start / end 成对，客户端按 `name` 归并。`diff?`（2026-11-10 批 33，纯增量）= 编辑类工具的 unified diff，只在 `end` 上有，截断 2000 字符（与 §2.2 `steps[].diff` 同口径）——以前只有历史 steps 带 diff、现场工具行画不出改动，两边不一致；现在 `edit` 这类带 `details.diff` 的工具两边同一份事实，前端靠它汇总「改了 N 个文件」 |
| `delegate` | `ticketId`, `domain`, `phase`, `done`, `total`, `current`, `message?`, `project?`, `lastAction?`, `lastHeartbeat?`, `waitingOn?` | 派单进度与终态（2026-11-03）。`phase` 见下方 `DelegationPhase`；`done/total` 是单内已办件数/总件数。2026-11-04 补齐：`project` 项目名、`lastAction` 最近动作、`lastHeartbeat` 事件心跳（ISO，同一份也落进 `ticket.json`，§2.9）、`waitingOn` 卡在哪个文件租约 |
| `attention` | `ticketId`, `domain`, `kind`, `question` | 任务单要人回答；`kind` = `need_input` / `need_decision` / `need_action` |
| `escalation` | `ticketId`, `domain`, `escalationId`, `question`, `context`, `options?`, `urgency` | **打手决策上报（2026-11-19 批2，契约先行改 `shared`）**：本机池 worker 执行中调 `escalate` 工具上报决策/问题，投到**派活方会话**出上报卡（两个动作：总管代答 / 升级给用户，走 `POST /agent/escalations/:ticketId/route`，§2.9）。`urgency` = `low` / `normal` / `high`；`escalationId` 是 uuid。答复经打手插话通道（steer）投回 worker 续跑；谁答的（总管/主人）进任务台账。限流：每单同时 1 条活跃、每单上限 `ESCALATION_MAX_PER_TASK`（超限直达用户）。（ESCALATION_CHAIN_ENABLED 回滚开关 2026-11-21 退役，上报链恒开。）老客户端按 `type` 忽略；手机不进 SSE 聊天流、openai 兼容层跳过该帧 |
| `approval` | `callId`, `tool`, `args`, `deadlineAt` | **写类工具要你确认**（2026-11-04 批次二；审批档不是 `none` 时才发：`ask-all` 写类全问、`ask-critical` 只问高危清单，§2.18）。`args` 是工具参数 JSON（截断 1200 字符）；`deadlineAt` 是 ISO 截止时间，blocking 形态下过了按拒绝处理（fail-closed）。答复走 `POST /api/v1/agent/approvals/:callId`（§2.5）。**手机不进这条聊天流**：手机不进 SSE 聊天流，审批走全局待办 `GET /api/v1/agent/approvals`（不带 `conversationId`）轮询（建议 20–30 秒，或拉任务页时顺带），答复用同一个 POST，与传输协议无关。`lifediary_approval` 非标字段保留但手机不再依赖；老客户端按 `type` 忽略即可 |
| `notice` | `text`, `steer?` | 系统提示行（2026-11-07 消息即引导）：`whenBusy=steer` 的诚实回执（"下一个边界带上它" / "这一轮刚好收尾，已作为新的一轮开始"）。不是模型正文，也不是错误；客户端渲染成中性一行即可，老客户端按 `type` 忽略。`steer`（2026-11-07 补，纯增量）是机器可读落点：`inserted` = 插进了正在跑的这轮，正文由原来那条流继续画；`new-turn` = 刚好收尾、成了新的一轮——这条短连接就是唯一正文来源，客户端只收回执的话必须在轮收尾后回读一次 `GET .../messages`，否则新一轮的回答没人画。判断只认 `steer`，不要匹配 `text` 文案。2026-11-10 批 13 起，执事的 `report_progress` 也发同一形状的 `notice`（`text` = `【进度】…`，≤200 字，无 `steer`）；不落盘，没开流就收不到 |
| `done` | `id`, `finishReason`, `usage?` | `stop` / `length` / `aborted` / `error`（表示"这条流怎么结束的"，不是"这一轮怎么结束的"）。`usage`（2026-11-04 批次一）= 本轮最后一条 assistant 消息的 token 用量 `{input, output, cacheRead}`，faux/mock 也给（数字仅供链路验证） |
| `error` | `message`, `code?`, `detail?` | 这条流出错（工具回合撞上限 / 一轮没给出回答 / 服务端生成异常，2026-11-10 批 32 起三类都发这帧）。`message` 是给人看的中文短句，**客户端不要解析文案**；`code`（纯增量）是稳定类别 `rate_limited` / `auth` / `timeout` / `network` / `context_overflow` / `model_error` / `unknown`（工具回合撞上限无 `code`），客户端按它决定动作（限流等待、密钥去设置页……）；`detail`（纯增量）是**服务端已脱敏**的细节摘要——凭据打码（`«redacted»`）、上游地址剥掉主机只留路径、截断到 400 字符，供「详情」小窗展示。**原始上游错误绝不下发**（可能带 key 片段），只进服务端日志；`message` 的措辞由 `apps/server/src/stream-error.ts` 按类别统一给出。前端呈现 = composer 容器卡顶部一张错误卡（一行摘要 + 详情/复制/重试/×，切会话或发新消息退场），不再往消息流里插红字行（批 32） |

`DelegationPhase`（对外的"在等谁"）：`accepted` / `planning` / `running` / `reviewing` / `done` / `needs_you` / `failed` / `aborted`。

- `delegate` 的进度帧**只在拿到 `ticketId` 之后才发**（前端靠它归并），所以第一帧一定是 `accepted` 或 `planning`。
- 终态帧（`done` / `needs_you` / `failed` / `aborted`）之后如果还有一条问题，会再发一个 `attention`。
- `approval` 的答复等待**不计入工具回合上限**；并行工具各自有独立的 `callId`，互不阻塞。
- 老客户端按 `type` 分发，认不出的类型直接忽略即可（这些都是**纯增量**事件）。

**关键语义：客户端断开 ≠ 取消。** 那一轮会在服务端跑完并落库；记忆抽取挂在"这一轮真正结束"上，不会因为关界面而漏写。
真要停请用 §2.3。

未配置模型（`LLM_API_KEY` 缺失）时：返回 mock 流（逐字回显 + 固定文案），**不建会话、不写库**。

### 2.2 `GET /api/v1/agent/chat/:conversationId/messages?limit=50&sinceSeq=0&page=1&before=<游标>`

回读该会话的历史（每轮的正文 + 该轮的工作步骤）：

```json
{ "conversationId": "…", "messages": [ { "role": "user", "text": "…", "at": 1761234567890 } ], "chatKind": "worker",
  "chatWorkdir": { "kind": "project", "name": "lifediary-harness", "path": "D:\\Projects\\projects\\lifediary-harness", "projectId": "…" } }
```

- 存在理由：一轮可以在客户端关掉之后继续跑完，客户端下次打开必须能把结果拉回来。
- **`id` / `images` / `files`（2026-11-08 扫尾批 4a；`files` 为 2026-11-13 纯增量，只出现在 user 消息上）**：
  - **`id` 现在 user 与 assistant 都给**（2026-11-17 批3a）：user 的 id 供编辑重发定位，
    assistant 的 id 供 `POST .../branches` 指定从哪条回答分叉；**带 `author` 的来信仍不给 id**。
    只有步骤、正文为空的兜底 assistant 也有 id，但不能作为分叉点（见 §2.2.7）。
  - `id` 是**可寻址 messageId**（uuid 形状，编辑重发用它定位）；**不是** durable 内部自增条目 id——
    由 `(会话 uuid, 条目 id)` 哈希得到（`agent.ts` 的 `messageIdOf`），离开会话 id 没有意义；
  - `images: [{mimeType, data}]` 是这条用户消息带的图片（base64 原样回读）；文字仍走 `text`，
    **纯图消息 `text` 可能是空串**；
  - `files: [{path, name, mimeType?, bytes?}]` 是这条用户消息带的文件（**只有路径，没有内容**）；
    durable 里的清单行在这里被剥掉还原，不会出现在 `text` 里；**纯文件消息 `text` 可能是空串**；
  - 老客户端忽略这三个字段即可；手机端现行只读 `role`/`text`/`at`，零改动。
- **`author`（2026-11-15 作者标记，纯增量）**：**非主人来源**的 user 消息带这个对象
  （目前只有执事间递话 `send_to_agent`）：`{ kind: "partner", id, name, domain?, hop? }`。

  - 带头 = 这条不是主人本人输入；**同时没有 `id`**——编辑重发要靠 `id` 定位，
    所以同事的话在界面上"能看不能改"（服务端 `forkForEdit` 也只认 `pi.user`）。
  - 没有这个字段就代表主人自己说的（不另标"主人"，对齐 cindy「本机输入不盖章」）。
  - `text` 里**不含**模型侧那三段说明（`[relay hop=1][来自执事 X（域）]`、末尾的
    "主人看不到原文"括注）：它们是给模型看的，回读时已剥掉，由 `author` 说"谁发来的"。
  - 手机端忽略即可（仍按 `user` 渲染，只是会看到剥过前缀的正文）。
- **`origin`（2026-11-17 批3b，纯增量；画板批加 `atMessageId`）**：**只有分支副本才有**：
  `{ source: "<来源会话 id>", sourceTitle?: "<来源标题>", at: <分叉时间 epoch ms>, atMessageId?: "<分叉点 assistant 消息 id>" }`。
  `sourceTitle` 取源会话当时的标题（没有就不带）；`at` 是创建副本的时间；
  `atMessageId` 是画板批之后新建副本才有的分叉点，老副本没有该字段（画板按时间戳兜底）。
  **分页与全量两个响应都带**（补帧响应同样带），老客户端忽略未知字段即可。
  只用于展示来源行与回跳原会话，不参与历史解析。
- **`steps` / `workMs`（2026-11-07，纯增量）**：`assistant` 条目上多这两个字段，回答"这一轮具体做了什么"。
  流式期间的 `tool` 事件只在当轮界面上活过一次，刷新/切会话就没了；而步骤本来就躺在 durable 里
  （`pi.assistant` 的 `toolCall` + `pi.tool-result`），服务端按调用顺序配成对下发，**没有新增存储**。

  ```json
  {
    "role": "assistant", "text": "…", "at": 1761234567890,
    "workMs": 41230,
    "steps": [
      { "name": "edit", "label": "ts/apps/server/web/app.js", "args": "{\"path\":\"…\"}",
        "output": "Successfully replaced 2 block(s) in …", "diff": "-12 +12 …", "ok": true, "ms": 18 },
      { "name": "bash", "label": "pnpm typecheck", "ok": false, "output": "error TS2339…", "ms": 9042 }
    ]
  }
  ```

  - 字段口径与 SSE 的 `tool` 事件一致（`args` 1200 字符、`output` 2000 字符，均截断后带"还有 N 字符"），
    「现场看到的」与「回头翻到的」是同一份事实。`diff` 只有 `edit` 这类带 `details.diff` 的工具才有。
  - `ok=false` 覆盖两种情形：工具真的失败，以及**这一轮被中断、始终没等到结果**的调用——
    后者不能画成成功（判据是"有没有配到 `tool-result`"，不是"有没有输出"）。
  - 只挂在**带正文的那条回答**上；中间的工具回合（正文为空）不会变成独立的"回答"。
    被中断且始终没等到回答的那一轮没有挂靠点，历史里不回放它的步骤。
  - **`think` 步（2026-11-19；2026-11-21 扩到无正文轮）**：模型的思考段作为一步
    `{"name":"think","ok":true,"output":"…"}` 挂进 `steps`，排在其工具 / 说话之前。
    模型没吐思考正文（思考关着 / 只有连接期）也记一步**不带 `output` 的 `think`**——
    现场的转圈占位不再撤掉，历史必须留给同一枚，否则重读一次就把这一步擦掉
    （2026-11-21 用户口径「思考过程也要显示出来」）。整轮至多补一条空壳（已有思考的轮不再补）；
    `think` 不写 `ms`，空壳不编 `output`——客户端如实显示"这段没留下正文"。
    因此裸回答轮现在带 `[think]` 一步，不再是无 steps。
  - **`say` 步（2026-11-10 批 32，纯增量）**：模型动手前说过的话（带工具调用的中间回合里
    `toolCall` 之外的正文块）作为一步 `{"name":"say","ok":true,"format":"md","output":"…"}` 挂进 `steps`，
    位置跟真实发生顺序一致（说话在工具前）。`format:"md"` 表示 `output` 是模型写给人的正文、按
    markdown 渲染；`name` 是其它值的步没有 `format`，`output` 按工具输出纯文本渲染。前端把它画成
    正文里的一个普通段落（2026-11-13 E1 灰块）：话 → 灰块 → 话 → 灰块，不再折进"工作过程"面板——
    「现场看到」与「回头翻到」仍是同一顺序、同一份内容。
  - `workMs` = 提问时间 → 收尾时间（`assistant.timestamp + durationMs`）；读不到 `durationMs` 的旧记录
    退回 `timestamp`，可能偏小，不编数。
  - 手机端：手工解析 `messages` 只取 `role` / `text` / `at`，Kotlin 零改动。
- **`endedAt`（2026-11-17，纯增量）**：`assistant` 条目上的**收尾时刻**（epoch 毫秒）。
  `at` 是"这次请求开始"，界面上"几点答完"要的是它：服务端按 `at + durationMs` 算，
  与 `workMs` 的收尾同源；读不到 `durationMs` 的旧记录退回 `at`（可能偏早，不编数）；
  只有步骤、没有正文的收尾轮用最后一条的时间。只挂在 assistant 上，`user` 条目不出现；
  老客户端 / 手机端忽略即可（界面按 `endedAt || at` 显示）。
- 未配置模型 → `{ "messages": [] }`；未知 id → 404。
- **`chatKind`（2026-11-06 B2，纯增量）**：`chief` / `worker` / `partner`。续话/刷新时前端据此恢复身份，
  不按 id 猜。旧客户端忽略该字段即可。
- **`chatWorkdir`（2026-11-18，纯增量）**：**只有 `chatKind === "worker"` 且 `CHAT_PROJECT_LABEL` 开时才有**，
  给输入框左下角的只读工作归属标签用：`{ kind: "project" | "workspace" | "dir", name, path, projectId? }`。
  `project` = `ChatProjects` 有绑定且项目还在（项目名按服务端当前登记，归档项目也返回）；`workspace` = 没绑项目、
  cwd 是主工作区根（或完全没有 cwd），`name` 固定「工作区」；`dir` = 只选了目录 / 项目被硬删，`name` 取目录 basename。
  分页、全量与 `sinceSeq` 补帧三个响应都带；总管 / 执事 / task 专线不带。老客户端忽略未知键即可。
- **`sinceSeq`（2026-11-04，SSE seq 与断点重放方案，可选）**：带上后响应多一个 `events` 数组——
  该会话落库事件里 seq > `sinceSeq` 的部分（完整 `ChatEvent` 帧，含 seq），用于断线补帧；
  不带 `sinceSeq` 时无 `events` 字段，行为与改动前完全一致。落库窗口每会话只留最近 500 条，
  所以响应带 `fromSeq`（重放第一条的真实 seq）：若 `fromSeq > sinceSeq + 1`，说明窗口已滑过，
  客户端不能只补帧，要按 `messages` 全量重建。`AGENT_SSE_SEQ=off` 时 `sinceSeq` 被忽略。
- **历史分页 `page=1` / `before`（2026-11-13 方案「按天分组·上滑加载」，纯增量）**：
  `page=1` 或带 `before` 时走**倒序游标分页**，服务端只读这一页涉及的 entry，不再每次把整段
  活跃上下文读进内存。响应多 `hasMore`（还有更早？）与 `nextBefore`（下一页**不透明游标**；
  没有更早时不带）。一页最多 `limit` 条（默认 50，取值 1–200，非法 → `400`）；页边界落在
  **"轮"**（`user` 提问开头）上，不会把一轮和它的工具步骤切两半；累计 ≥20 条后优先在自然日
  边界收页，某一天特别长就当天分段。日期分隔条由客户端按消息的 `at` 渲染，契约里不加日期字段。
  游标跨会话 / 被改 / 服务端换过 `AGENT_TOKEN` 一律 `400`（客户端应回落重开，不要重试同一游标）。
  **不带 `page` / `before` 时响应形状与改动前逐字一致**（手机端零改动）。
  时带了也忽略，退回老形态。
- 手机端：契约纯增量，Kotlin 零改动（适配说明加一行"可忽略 `seq` / `events` / `hasMore` / `nextBefore`"）。

### 2.2.1 `GET /api/v1/agent/chat/:conversationId/export?format=handoff&limit=30` —— 会话导出「接续文件」（2026-11-10 批 20 §一）

把一个会话导出成**能直接粘给任何 AI 继续聊**的 markdown（不是数据备份）。响应体是文件本身：

- `Content-Type: text/markdown; charset=utf-8`；`Content-Disposition: attachment; filename="lifediary-handoff-<会话 uuid 前 8 位>.md"`；
- **一次性响应，不落服务端磁盘**（隐私口径）：不写 `.data`、不排队、不加缓存（`Cache-Control: no-store`），
  请求结束即丢。要留存由客户端自己保存；
- 文件四块：角色说明（`chief` / `worker` / `partner` 各一句）+ 读取说明（"可以直接粘给任何 AI 继续聊"）+
  记忆摘要 + 最近 N 轮原文。标题取 `chat-meta.json` 的改名表，没有标题就写「会话 <前 8 位>」；
- **记忆摘要**：该会话**作用域**的 `preference` + `experience`，最多 20 条（主对话 = `global`，
  执事会话 = `partner:<uuid>`，与偏好落点同口径 `preferenceScopeOf`）。不导 `session:` 原始沉淀；
- **最近 N 轮**：`limit` 默认 30、取值 1–200（非整数 / 越界 → `400`），一轮从一条 user 消息起算，
  回答与工作步骤跟着走，不会把某轮回答切一半。更早的消息不进文件。
- 回滚：`CHAT_EXPORT_HANDOFF=false` → 端点 `404`（未启用，与其它能力端点同口径）。
- 错误：`format` 不是 `handoff` → `400`；未知会话 → `404`；未配置模型 → `503 {"ok":false,"reason":"llm_not_configured"}`。

**状态如实（三条口径，写进文案与产品说明）**：

1. **部分可读要标注原因，不冒充完整**：被 `limit` 截断时文里写「更早的 N 条消息未包含」；
   记忆未启用 / 读取失败 / 池子为空各有明确一句，不静默省略。
2. **导出成功 ≠ 对方已接收**：文件头明写这一句；服务端不知道也不追踪对方是否收到。
3. **默认不保存正文**：导出是一次性文件，服务端不落盘（见上）；这不影响服务端本来就会持久化的会话历史。

**探针**：`pnpm --filter @lifediary/server http` §28——200 + markdown + 附件头、四块文案、
`limit=2` 只含 2 轮、坏 `format` / 坏 `limit` / 未知会话各自的状态码。

### 2.2.2 `GET /api/v1/agent/chat/:conversationId/context?aroundIndex=<n>&radius=5` —— 旧会话定点找回（2026-11-10 批 20 §四）

从旧会话的某一处往回看（只做后端能力，不做界面、不做 fork）。

- **`aroundIndex` 是消息数组下标（从 0 开始）**，不是 seq——transcript 没有 seq 字段，不为这个改内核。
  必填；缺 / 负数 / 非整数 → `400`；
- `radius` 默认 5、取值 0–50（前后各取几条）；越界 / 非整数 → `400`；
- 返回：

```json
{
  "conversationId": "…", "total": 11, "aroundIndex": 5, "radius": 1,
  "from": 4, "to": 6,
  "messages": [ { "role": "user", "text": "…", "at": 1761234567890, "index": 4, "id": "…" } ]
}
```

  - `total` = 该会话消息总数，客户端据此知道边界；`from` / `to` 是窗口两端的**绝对下标**（含）；
  - 每条带 `index`（绝对下标）；user 消息另带可寻址 `id`（与 §2.2 同源）；
  - **不回放图片与工作步骤**（`images` / `steps` 不在这里出现）；纯图消息的 `text` 可能是空串；
- `aroundIndex >= total` → `400 {"error":"bad_request","message":"aroundIndex 超出范围（共 N 条）","total":N}`；
  会话为空 → 200，`total:0`、`from:0`、`to:-1`、`messages:[]`；
- **与同路径旧端点共存**：不带 `aroundIndex` 时仍是 §2.5 的「上下文占用」`{used, window}`（旧客户端零影响）；
  带 `aroundIndex` 才走本语义。
- 回滚：`CHAT_CONTEXT_LOOKUP=false` → **带 `aroundIndex`** 的请求 `404`；旧「上下文占用」不受影响。

**探针**：`pnpm --filter @lifediary/server http` §28——`total` 与 §2.2 一致、窗口两端与绝对下标、
越界带 `total`、`radius` / `aroundIndex` 非法各自 400。

### 2.2.3 `GET /api/v1/agent/chat/:conversationId/injections` —— 注入审计（2026-11-10 批 26b §二；批 27 §四扩到全部注入）

返回注入框架**当前接管**的注入清单，**只回元数据、不回正文**：

```json
[ { "id": "persona", "source": "lifecycle", "scope": "session", "channel": "system", "length": 412 } ]
```

- 字段固定五个：`id` / `source`（来源模块：`lifecycle` / `assist` / `partner-context`）/
  `scope`（`session|once|turn`）/ `channel`（`system|message`）/ `length`（正文字符数）；
  **没有 `text`，也没有任何正文片段** —— 审计端点不会泄露提示词实文。
- 批 27 起 B/C/D 全部注入都已接管，数组是**多条**（lifecycle 的 section、assist 的记忆、
  partner-context 的执事纪律各按段列出）。`AGENT_INJECTION_GUARD` 关时 `injection_guard` 行不列。
- `:conversationId` 会尽量解析成内部 id / 会话种类 / 执事，好让 persona、执事纪律与真实一轮一致；
  解析不到（未配置 LLM / 会话不存在）就按原始 id 出静态清单，**绝不 500**。
- **审计是只读的（`dryRun`）**，两条边界如实写下：
  1. 技能不冻结索引（`skills` 条目不列——按会话冻结属于首轮渲染的副作用）；
  2. 任务近况不跑（`task_memory` 会先摄入日记镜像，写库）；
     执事「当前在办」（`partner_status`）不列（要扫 chancellor `runs/` + 开 SQLite）。
  消息流里的 `memory_recall` / `skill_slash` / `turn_limit` 需要一轮的真实请求（用户正文 / 回合数），
  会话静置时同样不列。
- 回滚：`AGENT_INJECTION_AUDIT=false`（§6，默认开）→ 端点 `404`。
- 逐字节约束：接管后每一处注入的正文与位置与改造前一致（`src/agent/injection.test.ts` 钉住）；
  唯一有意变化是 `injection_guard` 的重复合并（原来 system 段与执事尾巴各一份，同 id 同正文）。

**探针**：`pnpm --filter @lifediary/server http` §4.5——200、多条、`{id,source,scope,channel,length}` 形状齐、无正文。

### 2.2.4 `GET /api/v1/agent/chat/:conversationId/context-inspect` —— 设置页「上下文」检查（2026-11-16，2026-11-17 重画；2026-11-21 页面可就地改可编辑段）

给「设置 → 注入 → 上下文」一页用：**看这一条请求到底装了什么**——固定前缀 + 已经进请求的每一条消息与工具调用，
不做请求历史、不做最近 N 条。端点本身仍是只读重放；页面上的「改这一节」写回各自的源头（人设 / 关于我 /
岗位契约 / 当前目标 / 纪律），不经过这个端点。

```json
{
  "conversationId": "…", "title": null, "chatKind": "worker",
  "usage": { "used": 8480, "window": 158000 },
  "system": { "content": "", "chars": 837, "tokens": 590, "sections": [
    { "key": "persona", "label": "人设", "stability": "fixed", "chars": 216, "tokens": 150, "text": "<persona>…" }
  ] },
  "tools": { "count": 21, "chars": 15667, "tokens": 7680, "items": [
    { "name": "read", "description": "…", "chars": 648, "tokens": 162, "schema": "{…pretty JSON…}" }
  ] },
  "skills": { "count": 19, "chars": 2040, "tokens": 727, "text": "<skills>…" },
  "memory": { "enabled": true, "limit": 16, "maxChars": 2000, "last": {
    "at": 1794760694967, "items": 9, "chars": 1504, "tokens": 1180, "text": "…",
    "others": [ { "id": "turn_limit", "label": "回合上限", "chars": 28, "tokens": 24, "text": "…" } ]
  } },
  "changing": {
    "messages": { "count": 2, "chars": 38, "tokens": 30 },
    "toolCalls": { "count": 1, "chars": 52, "tokens": 20 },
    "toolResults": { "count": 1, "chars": 1042, "tokens": 300 }
  },
  "entries": [
    { "kind": "user", "label": "用户", "index": 1, "chars": 12, "tokens": 12, "text": "…" },
    { "kind": "assistant", "label": "助手", "index": 2, "chars": 8, "tokens": 8, "text": "…" },
    { "kind": "toolCall", "label": "read", "index": 2, "chars": 52, "tokens": 20, "text": "{\n  \"path\": …\n}" },
    { "kind": "toolResult", "label": "read", "index": 3, "chars": 1042, "tokens": 300, "text": "…", "truncated": true }
  ],
  "updatedAt": 1794760710591
}
```

- **数据来源**：`conversation.context(CTX)` 的 `ContextView` 只读重放（`content` 追加、`sections` 按名覆盖、`tools` 增删），再用 `getCurrentSystemMessage(view.messages)` 取当前真正会发出去的那份；**不重跑 provider、不重跑记忆召回**（`recall()` 会回写 `lastRecalledAt` / `usageCount`）。
- `system.sections`：`stability` = `fixed`（人设 / 验证铁律 / 开工前问清 / 注入防线）/ `session`（当前项目的固定部分 / 技能）；`skills` 从系统段单拎成独立块。**2026-11-19 前缀锁定**：当前项目的动态一半（`current_project_live`）不再进 system，改走消息尾部；`memory.last.others` 里能看到它。
- `tools.chars` / 每项 `chars`：`JSON.stringify({name,description,parameters}).length`；`schema` 是同一对象的 pretty JSON。
- **`tokens`（2026-11-16 续，纯增量）**：同层级的 token 估算，页面主数字。口径 = CJK 1 token/字 + 其它 1 token/4 字符，向上取整（`token-estimate.ts`）；对 cl100k 实测合计约 -5%。`chars` 全部保留，供排查 / 兼容。页面数字带 `≈`，不冒充精确计费。
- `skills.count`：技能索引里 `- ` / `* ` 条目行数；没有条目行但有正文时算 1。
- `memory.last` **只来自进程内记录**：`beforeRequest` 在一轮**第一次模型请求**（`used === 1`）把 `collectInjections(...).message` 的 `{id,text}` 记进进程内表；每个会话只留最新一轮，最多 64 个会话 LRU，**不落盘、不进日志**。三种语义：
  - `null`：当前进程还没跑过这个会话的一轮请求（重启后首次打开也会是 `null`）；
  - `{text:"",items:0,chars:0}`：记过，但这一轮没有召回；
  - 有 `text`：这一轮实际注入的 `memory_recall` 实文；`others` 是同一轮里其它临时注入的 `{id,label,chars,tokens,text}`（2026-11-19 起带可读 `label`；超过 4000 字截断并标 `truncated`）。2026-11-19 前缀锁定后这些条目以 **user 角色**追加在请求尾部，不再并入 system。
- `changing` **只报条数与字数 / token 估算**：user/assistant 文本、assistant `toolCall`、`toolResult`。
- **`entries`（2026-11-17 重画，纯增量）**：已经进请求的每一条，页面按真实顺序逐条列出并能读原文——`kind` = `user` / `assistant` / `toolCall` / `toolResult`；`label` 是行名（用户 / 助手 / 工具名）；`index` 是它在 `view.messages` 里的下标（页面序号另按条目数从 1 数）；`text` 是正文或 pretty 参数；`chars` / `tokens` **按全文算**，单条正文超过 `MAX_CONTEXT_ENTRY_CHARS = 4000` 字时截断并标 `truncated`。
  - 只取 `user` / `assistant` / `toolResult`；system 消息属于“系统提示词”，不进条目。
  - assistant 的文本与它发出的每个 `toolCall` 各成一条（调用排在文本之后，保住原序）；工具调用的 token 口径与 `changing.toolCalls` 一致（紧凑 `JSON.stringify({name, arguments})`），因此组内各行相加 = Hero 的「对话」段。
  - `toolCall.text` 给 pretty 参数供人读，`chars` / `tokens` 仍按紧凑 JSON 算——两者词法不同，不要用 `text.length` 反推 token。
  - **`system.content` 字段保留但不渲染**：真实请求里它恒为空（页面 2026-11-17 起不再有「系统底稿」这一行）。
- 错误：开关关 → `404`（`CHAT_CONTEXT_INSPECT=false`，默认开）；会话不存在 → `404 {"error":"unknown_conversation"}`；`conversation.context` 读失败 → `503 {"error":"context_unavailable"}`。响应带 `cache-control: no-store`。
- 明确不做：离线编辑、按模型词表精确分词、手机端页面。**请求历史**已由 §2.2.6 / §2.2.7 单独提供（2026-11-19），本端点仍只画当前这一条。
- 验证：`pnpm exec tsx --test src/context-inspect.test.ts` 12/12（开关默认、section 覆盖与 skills 单拎、会变计数 + 条目顺序、4000 字截断、注入记录最新一轮 / 空覆盖 / 64 会话 LRU、payload 记忆三种语义）；`node --check` 三个 web JS。

### 2.2.5 `GET /api/v1/agent/context-defaults?role=chief|dispatch-worker|partner:<id>` —— 设置页「注入 → 上下文 · 默认开销」（2026-11-16 续；2026-11-22 加池工人；2026-11-24 普通 worker 档退役）

同一页的第二种视图：**不创建会话、不读聊天记录**，按角色显式装配一份“全新会话会读到的固定前缀”，
用来回答“我没有上下文、不聊天时，默认要花多少”。这不是请求历史，也不是第二个模型请求。

```json
{
  "default": true,
```

### 2.2.7 `POST /api/v1/agent/chat/:conversationId/branches` —— 从某条回答另开一支（2026-11-17 批3a）

请求：`{ "atMessageId": "<assistant 消息的 id>", "title?:": "≤80 字" }`；成功
`200 { "ok": true, "conversationId": "<新会话 id>", "entries": <复制条数> }`。

**语义**：从一条**带正文的 assistant 回答**复制出一条新会话。复制源会话从 1 到该回答的全部
条目（不挑 kind，未知 kind 照抄，保住上下文一致性），按原顺序 append 到新会话；
**时间戳 / durationMs 保留原值**，历史 `usage` 全 0 同形（账单不翻倍）；`edits[].target` 重映射到
新会话里的真实条目 id（目标不在复制范围就丢该条 edit）；`pi.compaction` 的 `head`：后向引用
（历史 / 合成数据）回填真实 id，真实数据的前向 head（指向 compaction 之后的 first kept entry）
在副本里退化为普通摘要条目（上下文等价，未来再压缩会重新折叠），映射不到则丢该条并记日志。
上限 400 条 / 64MB，
超过直接拒绝、不悄悄截断。**不设 durable `parent`**，来源只写 `lifediary.chat-origins`
（`{source, sourceTitle?, at, atMessageId?}`，仅用于展示、回跳与画板分叉点，不参与历史解析）；
**源会话只读、不改**。新会话不写消息、不跑模型——分叉点就是最后一条。

**目标会话**：
- 执事会话（链接 role = canonical / side）：新分支 = 同一人设下的 **side 会话**
  （走 `createPartnerSideSession`，新 id 含 `-side-`，人设 / 记忆 / 项目照旧，身份对齐 + 钉工作目录）；
- worker / chief：新建独立会话，继承种类、项目归属、工作目录与**当前模型（含思考档后缀）**。

**错误码**：`404 unknown_conversation`；`409 conversation_busy`（源会话在跑，照 `/edit` 口径）；
`400 bad_request`（缺 `atMessageId`）；`400 branch_point_not_found`（找不到该 assistant / 分叉点不是 assistant）；
`400 branch_point_empty`（该回答正文为空，含"只有步骤、正文为空"的兜底 assistant）；
`400 branch_too_large`（「这条太长了，先压缩再复制」）；
`400 branch_not_supported`（群成员 / 例行等带非 canonical/side 链接的会话不能分支——
落到 worker/chief 会把身份复制丢）；执事会话分支但 `PARTNER_SIDE_SESSIONS=false` 时
`400 side_sessions_disabled`（副会话已关闭）；执事不可用（暂停 / 归档）时 `409 partner_inactive`。
分叉是纯复制能力，**不接替主线**：canonical 仍只有一条，不做 retired / 冻结（有 side 不需要）。

### 2.2.8 `GET /api/v1/agent/chat/:conversationId/map` —— 会话画板（2026-11-17 画板批；2026-11-19 窗口化）

只读投影：把**一条会话及其全部分支**画成"回合卡 + 分支树"。作用域写死在路径里——
只接受一个会话 id，不接受工作区 / 会话列表。不写布局、不改会话、不跑模型。
2026-11-19 起每个节点只回**最近 N 轮**（`?turns=`），更早的另走 2.2.10 逐段展开。

响应 `200`：

```json

  "rootId": "<最顶层来源会话 id>",
  "truncated": false,
  "window": 10,
  "nodes": [
    {
      "id": "<会话 id>",
      "title": "<标题>",
      "chatKind": "chief | worker | partner | unknown",
      "sessionRole": "canonical | side | null",
      "root": true,
      "branchable": true,
      "archived": false,
      "missing": false,
      "origin": { "source": "<母会话>", "sourceTitle": "…", "at": 1700000000000, "atMessageId": "…" },
      "branchFrom": { "conversationId": "<母会话>", "turnIndex": 0 },
      "startTurn": 1,
      "windowStart": 1,
      "totalTurns": 12,
      "hasEarlier": false,
      "updatedAt": 1700000000000,
      "turns": [
        {
          "index": 1,
          "question": { "id": "…", "text": "…", "at": 1700000000000, "hidden": false, "hasAttachments": false },
```

- **节点顺序**：根在最前，其后按分叉时间 BFS；`rootId` 从请求的会话沿 `origin.source`
  向上走到顶（防环，最多 64 跳）。
- **`turns[].index` 是会话内绝对轮次**（从 0 起）。分支节点只回**分叉点之后**的轮次，
  序号保持绝对，前端据此把第一张问卡挂回母会话 `branchFrom.turnIndex` 那张答卡。
  `startTurn` = 分叉点之后第一轮（根节点为 0），也是 2.2.10 的 `floor`。
- **窗口（2026-11-19）**：查询参数 `turns` 指定每个节点回最近多少轮（缺省 10，夹在 1–100）；
  响应 `window` 回显实际值。每个节点带 `totalTurns`（会话总轮次，含复制前缀）、

  `turns` 只含 `[windowStart, totalTurns)`。
- **分叉点**：优先 `origin.atMessageId` 在母会话回合里找答卡；老副本没有该字段时，
  按"提问时间 ≤ `origin.at` 的回合都是复制前缀"兜底；两条都读不出来时**不猜**，
  返回空的 `turns`（前端画空分支占位卡）。
- **隐藏轮**：定时主动轮的触发指令在会话正文里不显示；画板把它保留成一轮
  （`question.hidden: true`、`text: ""`、**不给 id**），回答挂在这一轮下面，
  避免它被并进上一轮。`/messages` 的形状不变，隐藏轮仍不下发。
- **预览与上限**：问句 400 字、回答 1200 字（超出带 `…`）；节点 ≤ 24。
  `truncated` 只在节点数超 24 时为 true；回合窗口是正常视图，不算截断。
  详情另走 2.2.9 取全文，更早的回合走 2.2.10。
- **`branchable`** 与分支端点同一套判据（见 2.2.7）；`missing: true` = 会话在 durable 里
  已打不开（删了 / 对不上），节点仍保留，`turns` 为空、`branchable` false。
- **回滚**：`CHAT_MAP_ENABLED=false`（缺省开）→ 本端点 404
  `{ "error": "chat_map_disabled", "message": "会话地图已关闭" }`；
  `GET /api/v1/agent/policy` 的 `chatMap` 同步为 false，前端据此收起入口。

错误：`404 unknown_conversation`（请求的会话不存在）；`404 chat_map_disabled`。

### 2.2.10 `GET /api/v1/agent/chat/:conversationId/map/turns` —— 画板逐段展开（2026-11-19 折叠批）

查询参数：

| 参数 | 缺省 | 含义 |
|---|---|---|
| `before` | 会话末尾 | 取这个绝对轮次之前的一段（不含 `before`）；越界夹到 `[floor, totalTurns]` |
| `limit` | 10 | 单次条数，夹在 1–100 |
| `floor` | 0 | 这条会话自己的回合起点；画板传节点的 `startTurn`（分支不会展开到复制前缀）。服务端只夹到 `[0, totalTurns]`，不重新解分叉 |

响应 `200`：

```json
{
  "nodeId": "<会话 id>",
  "startTurn": 0,
  "totalTurns": 25,
  "windowStart": 15,
  "hasEarlier": true,
  "turns": [
    {
      "index": 15,
      "question": { "id": "…", "text": "…", "at": 1700000000000 },
      "answer": { "id": "…", "text": "…", "at": 1700000000000, "tools": 2 }
    }
  ]
}
```

- `turns` 是 `[windowStart, before)` 的最后 `limit` 轮；`windowStart` 是这段的第一轮绝对轮次。
- `hasEarlier` = `windowStart > startTurn`，即再往前还有。
- 与 `/map` 同受 `CHAT_MAP_ENABLED` 管；会话不存在 404 `unknown_conversation`。
- `floor` 由前端提供是**省一次母会话全文读取**的取舍，不是数据边界：

```json
      "inputTokens": 45818, "outputTokens": 231, "cacheReadTokens": 128,
      "cacheWriteTokens": 0, "promptTokens": 45946, "hitRate": 0.0028, "seq": 69,
      "systemChanged": true, "toolsChanged": false, "prefixChanged": true,
      "systemPatches": 1, "drop": true, "flag": "prefix_change_drop" }
  ]
}
```

- **请求口径**：`pi.assistant` entry 且 `usage` 存在、`promptTokens > 0`；本地合成消息
  （提醒 / `[[no-update]]` 那类 0 token assistant）不算请求。
- **保留窗口**：最新 500 条（`CACHE_STATS_MAX_REQUESTS`）；`truncated=true` = 还有更早的没列。
  每页固定上限 100 条（`pageSize` 传更大的值也会夹到 100）；`page` 从 1 起，越界夹到最后一页。
- **命中率**：`cacheRead / (input + cacheRead + cacheWrite)`，0–1；汇总按 token 加权
  （ΣcacheRead / Σprompt），不是各条命中率的平均。`fullMisses` = 命中率 < 5% 的请求数。
- **顺序**：`items` 新 → 旧；`seq` 是整条会话里按时间从旧到新的序号（1 = 最早一条请求，
  不再只数保留窗口）；页面直接用这个号。
- **骤降定位（2026-11-19，本端点最重要的字段）**：扫描时按 entry id 升序**增量重放**
  `pi.system`（content 追加、sections 按名覆盖、tools 先 remove 再 add），给每条请求算
  system / tools 指纹，从而在不读整份 ContextView 的情况下知道「这条请求的前缀是不是变了」：
  - `systemChanged` / `toolsChanged` / `prefixChanged`：相对**上一条模型请求**；
  - `systemPatches`：两条请求之间新增了几条 `pi.system`（首条 = 1 条 baseline）；
  - `drop`：命中率从 ≥50% 掉到 <20%（0% 命中可能是缓存过期，`drop` 只表示"掉了"，不表示"前缀坏了"）；
  - `flag` 是给页面的一结论：
    - `prefix_change_drop`：**骤降 + system 前缀同时变了**——这就是「正常运行中突然掉到个位数」，
      页面红色 `!` 并弹红色横幅；
    - `prefix_change`：system 前缀变了但没骤降（可能缓存已经过期过）；
    - `tools_change` / `tools_change_drop`：工具面变了（`tool_search` 加载；用户接受的一次性代价）；
    - `drop_unchanged`：骤降但 system / 工具面都没变——大概率缓存过期或上游不稳定；
    - `compacted`：压缩 / 重置后的第一条，前缀必然重写，不算事故。
  - 汇总里的 `drops` / `suspects` / `prefixChanges` 与上面同口径。
- 错误：`CHAT_CACHE_STATS=false` / `CHAT_CONTEXT_INSPECT=false` → 404 `{"error":"not_found"}`；
  会话不存在 → 404 `unknown_conversation`；响应带 `cache-control: no-store`。

### 2.2.12 `GET /api/v1/agent/chat/:conversationId/requests/:entryId/context` —— 某条请求的上下文（2026-11-19）

点开 2.2.11 的一行时用：`conversation.context({ at: entryId })` 重放**那一条请求当时**的
固定前缀与已存档消息，并与上一条模型请求做对比——直接回答「前缀是不是变了、变在哪个 section」。

```json
{
  "conversationId": "…",
  "request": { "entryId": 3404, "at": 1794838561000, "model": "auto/deepseek-v4.1-flash", "…": "同 2.2.11 的一行" },
  "context": {
    "system": { "content": "", "chars": 812, "tokens": 570, "sections": [ "…同 2.2.4…" ] },
    "tools": { "count": 14, "chars": 9120, "tokens": 4400, "items": [ "…" ] },
    "skills": { "…": "…" },
    "changing": { "…": "…" },
    "entries": [ "…" ],
    "entriesTotal": 86, "entriesOmitted": 0
  },
  "system": {
    "chars": 988, "tokens": 690, "hash": "9f2c1a7b3d4e",
    "sections": [ { "key": "persona", "label": "人设", "chars": 699, "tokens": 690 } ],
    "tools": 14
  },
  "compare": {
    "entryId": 3398, "at": 1794838557000,
    "systemChanged": true,
    "changedSections": ["topics"], "addedSections": [], "removedSections": [],
    "orderChanged": false,
    "toolsChanged": false, "toolsAdded": [], "toolsRemoved": [],
    "messages": { "shared": 84, "replaced": 0, "appended": 2 }
  },
  "note": "请求时的临时注入（记忆召回 / 当前项目 / 执事上下文）不写进对话存档，这里只能看到固定前缀与已存档消息。"
}
```

- `context.entries` 只带**最后 200 条**（`entriesOmitted` = 没带的数量）；`changing` 计数仍按全量。
- `system.hash` = system 正文 + 工具声明的指纹；`compare.systemChanged` 只看 system 正文
  （工具面另报 `toolsChanged` / `toolsAdded` / `toolsRemoved`）。
- `compare.messages`（2026-11-21）：**消息层**的前缀对比——把两条请求当时的非 system 消息
  逐条做指纹、取最长公共前缀：`shared` = 与上一条逐条一致的消息条数（= 可缓存的消息前缀长度）；
  `appended` = 这一条比上一条多出来的条数（**追加不改前缀，不背未命中的锅**）；
  `replaced` = 上一条有、这一条被换掉的条数，**>0 才是真的前缀断裂**（正常只有压缩 / 改写会这样）。
  system / 工具面都没变 + `replaced=0` 的 0% 命中，前端据此直接写「锅在上游（过期 / 淘汰 / 上游不稳）」。
- **诚实边界**：请求时临时拼装的注入不落 durable，历史详情里看不到；它们现在是尾部 user 消息，
  改它们只会让尾部那几百 token 不命中，不再作废固定前缀。`compare.messages` 同样只覆盖已存档消息。
- 边界：`entryId` 不是带 usage 的 `pi.assistant` → 404 `{"error":"unknown_request"}`；
  非正整数 → 400 `{"error":"bad_request"}`；开关 / 会话错误同 2.2.11。

### 2.3 `POST /api/v1/agent/chat/:conversationId/stop`

人工停止当前这一轮（走 `abort()`：排队的输入撤回、当前任务撤销）。之后再说一句话就是新一轮。
`{"ok":true,"conversationId":"…"}`；未配置模型 → `503 {"ok":false,"reason":"llm_not_configured"}`。

### 2.3.1 `POST /api/v1/agent/chat/:conversationId/say` —— 让助手说一句（2026-11-01）

手机端回顾页的钩子问题（"新版本装好之后的回读，结果跟预期一样吗？"）本来就是**助手要问的话**。
点卡片应该由助手说出来、然后等用户接，而不是塞进用户输入框（自问自答）。

- 请求 `{"text":"…"}`（必填，空 → `400 {"error":"bad_request"}`）；成功 `201 {"ok":true,"conversationId":"…"}`；
- **不调模型**：只在会话里追加一条 `pi.assistant` entry（走 `submit` 的 write，带 `model` 所以也进模型上下文，
  以后再聊时它知道自己问过这句）；会话忙时由 durable 排队到下一个边界落地，不打断正在进行的一轮；
- 之后 `GET .../messages` 就能读到这条（`role: "assistant"`）；
- 未配置模型 → `503`；未知会话 → `404`。

**探针**：`pnpm --filter @lifediary/server http` 里补一段——`POST /say` 后立刻回读，断言最后一条是 `assistant` 且文本一致。

### 2.3.2 `POST /api/v1/agent/chat/:conversationId/edit` —— 编辑重发（2026-11-08 扫尾批 4a）

改一句话并重说。语义决策见 `docs/设计方案/2026-11-08-扫尾批4方案（附件·编辑重发·壳发布）.md` §二：
内核 append-only、没有 truncate/edit，所以**不是就地改写**，而是
**fork 到那条消息之前 + 在新会话里提交新文本**。老会话完整保留（列表里会多一条分叉前的
旧会话，是方案登记的已知边界；不做删除）。

请求：

```json
{ "messageId": "GET .../messages 里 user 消息的 id", "text": "改过的话" }
```

- 校验：`messageId` 属于本会话且是 user 消息；`text` 去空白后非空。
- 分叉点：目标条目的**前一条**（fork 的 `at` 含该条目）；编辑会话第一条时没有"之前"，
  按同样形态（同模型、同种类）开一个空会话。
- 新会话的提交走 `chatStream` 主链路（SSE/用量/记忆全继承），在服务端后台跑完并落库；
  客户端拿到 id 后 `GET .../messages` 回读即可（与"关掉界面它照样跑完"同一语义）。
- 会话在跑 → `409 {"error":"conversation_busy"}`（与插话同口径，不排队）；消息不属于本会话 /
  不是 user → `400 {"error":"message_not_found"}`；未知会话 → 404；未配置模型 → 503。
- 回滚 `AGENT_EDIT_RESEND=false` → 端点 **404**（未启用，与其它能力端点同口径；§6）。
- 前端（web）：最后一条 user 消息 hover「编辑」→ 行内输入框 → 提交 → 用返回的新 id
  走 `openConversation()` 切换；更早的历史消息不提供编辑（方案登记的刻意没有）。
  现场刚发出的消息没有 messageId（SSE 契约未动），点编辑时按"从末尾对齐"拉一次历史补齐。

成功：`202 {"ok":true,"conversationId":"<新 uuid>"}`。

**探针**：`pnpm --filter @lifediary/server http` §21/§22——老会话完好、新会话 id 不同、
分叉点前历史完整、新文本在最末、跑着编辑 409、开关关闭 404。

### 2.3.3 `POST /api/v1/agent/attachments` —— 浏览器附件上传（2026-11-13）

浏览器出于安全拿不到用户选文件的真实路径，所以这条端点负责"收字节、落盘、回路径"。
壳里不走它（`Shell.SelectFiles` 直接给绝对路径，零拷贝）；上传后的路径再由
`POST /api/v1/agent/chat` 的 `{type:"file", path, name}` 带回去。

请求：

```json
{ "name": "报告.pdf", "mimeType": "application/pdf（可选）", "data": "<裸 base64>" }
```

成功：`200 {"ok":true,"file":{"path":"<服务端绝对路径>","name":"报告.pdf","mimeType":"…","bytes":1234}}`

- 单文件解码后 ≤ **32MB**；`data` 不是合法 base64 → 400；
- 落盘：`.data/attachments/`（`ATTACHMENTS_DIR` 可覆盖），文件名 = 内容 sha256 前 16 位 +
  `basename(原文件名)`；同内容同名复用同一路径；目录总量超过 `ATTACHMENTS_MAX_MB`
  （缺省 512）按 mtime 从旧到新删，只删这个目录；
- 日志只记数量/字节/耗时，不记文件名与完整路径；
- 回滚 `AGENT_FILE_ATTACHMENTS=false` → 端点 **404**，`GET /agent/policy` 的
  `fileAttachments` 为 `false`，前端只留图片内联入口（§2.9）。
- 鉴权走全局中间件：失败 403 空体；业务拒绝 400 `{error,message}`。

**探针**：`pnpm --filter @lifediary/server http` §20b——上传 200 + 路径可读 + 字节一致、
带 file 消息受理、回读 `files`、坏路径 400、开关关着 404。

### 2.4 `POST /api/v1/llm/chat/completions` —— OpenAI 兼容层

给"已经在说 OpenAI 协议"的客户端（现有手机 App）用。**分两路**（2026-10-30 增 `X-Task` 任务通道；2026-10-31 直通分支已删除，带 `system` 一律 400）：

- 请求体：OpenAI Chat Completions 原样 JSON；`stream: true` 时按 OpenAI chunk 形状逐块回写，最后补 `data: [DONE]`。
  `messages[].content` 支持纯文本或分段数组：`text` 段与旧行为逐字一致；`image_url` 段（2026-11-16，见 §2.4.1）支持 `data:image/*;base64,` 内联图片。
- 非流式：返回标准 `chat.completion` 对象（**无 `usage`**；Agent 路径 `finish_reason` 恒 `stop`）。
- 错误：`400`（messages 空 / 无可用内容；图片形状非法、超限、外部 URL、附件开关关闭）、`503`（服务端未配 `LLM_API_KEY`；**流式也回 503**）、`502`（仅非流式，上游失败）。

#### 2.4.1 两条路径的分流（客户端必须知道；2026-10-31 直通已删除）

| 请求特征 | 路径 | 行为 |
|---|---|---|
| **带 `X-Task`** | **任务**（2026-10-30） | 服务端按任务名渲染模板 → 走 **Agent 会话**（建会话、落库、可回读）；**不判快/深档**，一律深档 + 客户端采样参数；`system` 被忽略；详见 §2.4.4 |
| **有非空 `system`** | **400 拒绝**（2026-10-31 直通已删除） | `400 system_prompt_not_supported`。直通分支（整套 system 原样转发、不建会话）已删除：生产端 12 个任务全部走任务通道、聊天从不带 `system`，它已无调用方。**故意不静默降级**——降级会让旧客户端的模板被当普通消息丢掉，产出看着成功、其实残废 |
| **没有 `task`、没有 `system`** | **聊天** | durable 会话：历史在服务端、有记忆与工具；**只取最后一条 `user`** 作为本轮输入；`model`/`temperature`/`max_tokens`/`response_format`/`reasoning_effort` **全部忽略**（归服务端配置，模型级 `maxTokens`）；会话 id 优先 `X-Conversation-Id`，否则"首条 user 内容" sha256 前 32 位（`oa-<hash>`；纯图消息没有正文，改用图片指纹当种子）；**未见过的 id 直接新建同 id 会话**（不返回 404，与 §2.1 自有端点语义不同） |

**图片输入（2026-11-16，修复"image_url 被静默丢弃"）**：`messages[].content` 里的
`{ "type": "image_url", "image_url": { "url": "…" } }` 不再被压成空串丢掉（改动前：模型收不到图、也不报错）。
两条分流（`X-Task` 任务 / 普通聊天）都在同一处解析，行为一致；`system` 仍一律 400，与图片无关。

| 输入 | 行为 |
|---|---|
| `data:image/*;base64,<数据>` | 拆出 mimeType + 裸 base64，转成内部 image part 交给 Agent；**上限与开关复用 `/agent/chat` 附件那一套**，不另写一份 |
| 外部 `http(s)://…` | **400 `unsupported_image_url`**：兼容层不做下载转发（拉取 / 防 SSRF / 落临时文件是另一件事），但**必须报错、不静默丢** |
| 其它形状（缺少 `url` / 相对路径 / 非 base64 data URL / 非 `image/*` / 空数据） | **400 `bad_image`**，`error.message` 写明原因 |
| `AGENT_ATTACHMENTS=false` 时带图 | **400 `attachments_disabled`**；纯文本请求不受影响（与改动前一致） |

上限：单图解码后 ≤8MB、单条消息 ≤4 张（超限同样 400 `bad_image`）。`detail` 字段忽略。
纯图消息（没有文字、只有图）允许，不再被当"空消息"丢掉。**只有最后一条 `user` 的图片进入本轮**——
兼容层本来只取最后一条 `user`（历史文本同样不转发）；前几轮的图片已落在会话 transcript 里，续话时模型仍能回读。
支持范围只到 Chat Completions 的 `image_url` 段；Responses API 的 `input_image` 不支持（按未知分段忽略）。

**Agent 路径的思考强度档（2026-11-04 起替代快/深两档；方案见 `docs/设计方案/2026-11-04-思考强度档位.md`）**：
`Conversation.configure({ model })` 支持**会话中途换模型**，所以档位是**每轮**决定的，不是开局锁死：

| 来源 | 优先级 | 规则 |
|---|---|---|
| 请求头 `X-Mode: off\|low\|medium\|high` | 最高 | 说了就听（当轮生效）；旧值别名 `fast`→`off`、`deep`→`high`；越界档位（该模型未声明）按支持域落回 ≤ 该档的最高档（与 §2.8 换模型回退同规，2026-11-04 实施补充） |
| 已按 D3 切过非 off | 次高 | 保持切后的档（切一次就保持，不中途降档） |
| `JEV_ROUTE=gate` | 中 | 问 Jev（`deep_think` → `high`；`reply_direct` → `off`；confidence < 0.6 保守 `high`）；超时 `JEV_TIMEOUT_MS`（默认 1200）→ 直接 `off` |
| 默认 | 最低 | **off**（思考关变体，首字 0.8~0.9s） |

**档位 = 同模型 + 思考变体（2026-11-04 档位方案 D1/D3，替代 2026-10-31 的两变体）**：档位不靠换模型
（换模型 = 上游缓存清零），而是**同一模型的四条思考变体**
（派生模型 `#think-off` / `#think-low` / `#think-medium` / `#think-high`；旧后缀 `#think-on` 读兼容 = `high`）：
`off → enable_thinking:false`；`low / medium / high → reasoning_effort:<档>`。全部经 `samplingParams` 最后合并注入，
`model` 字段盖回真实模型名。**档位按模型支持域校验**：providers.json 每模型可选 `thinkingLevels`
（缺省 `["off","low","high"]`；`medium` 对 glm-5.3 实测 400，故只对声明支持的模型开放，见 §2.8）。
传未声明档位 → `400 bad_request`。换模型时当前档不在新模型支持域内 → 自动落回支持域内 **≤ 当前档的最高档**（`off` 兜底）。
两条变体链头块不同，缓存互不命中 —— 切档 = 当前前缀整段重算，所以默认**按会话定档、中途不切**。

**首次工具调用切一次（D3，2026-11-04 起目标档 = `AGENT_THINK_TOOL_LEVEL`，默认 `low`）**：模型发起第一次工具调用时（`beforeTool`），服务端看该会话
**上一轮的 `usage.input`**（D3a：客户端不知道前缀大小，harness 的 usage 是唯一可靠来源）：
`< 4000`（`AGENT_THINK_TOKEN_LIMIT` 可调）→ 切到目标档并保持；`≥ 4000` → 不切（长会话切一次就是整段重算）；
首轮无 usage → 视为短会话。`AGENT_THINK_ON_TOOL=off` 是总开关。
实测（2026-10-31，默认 deepseek-v4.1-flash）：聊天第 1 轮 2.31s（冷，思考关）→ 第 2 轮 1.20s（命中 1536）→ 首次调工具触发切思考（日志「首次工具调用 → 思考开（prompt≈126 < 4000）」）。

**`POST /api/v1/agent/chat/:conversationId/mode`（2026-11-04 登记进契约）**：body
`{ "thinking": "off"|"low"|"medium"|"high" }`，旧 `{ "mode": "fast"|"deep" }` 兼容映射（fast→off、deep→high）。
按当前模型支持域校验：未知值或未声明档位 → `400 {"error":"bad_request"}`；成功 `{ "ok":true, "thinking":"<档>" }`；
503 `llm_not_configured`；404 `unknown_conversation`；`LLM_PROVIDER=faux` 下空操作仍返回 ok。
写入即 `configure` 持久化（durable 会话模型引用，重启保留）。UI 选择器见 §2.8 `thinkingLevels`。

**`POST /api/v1/agent/chat/:conversationId/compact`（2026-11-07 扫尾批 1 B1）**：手动压缩。body
`{ "instructions"?: string }`；可选 `?wait=1`。内核 `Conversation.compact` 本就是**受理即返回**，
端点照实：受理即回 `200 {"ok":true,"taskId":<数字>}`（压缩在后台做、在空闲/边界落摘要）。
`?wait=1` 时再 `harness.waitForTask` 至多 `AGENT_COMPACT_WAIT_MS`（默认 60000）：完成
`200 {"ok":true,"compacted":true}`；超时 `200 {"ok":true,"waited":false,"taskId"}`（受理仍有效，
客户端可走 SSE / 刷新看结果）。404 `unknown_conversation`、503 `llm_not_configured` 与 `/mode` 同口径。
压缩事件（`compaction_start/end`）内核本就发，SSE 透传不动。
前端 composer：输入 trim 后匹配 `/^\/compact\b/i` → 不作为消息发送、不进历史，调本端点（剩余文字作
`instructions`、wait=1），完成后气泡提示；其余 `/xxx` 原样发送。**刻意不做通用斜杠命令系统**（登记防扩散）。

任务通道**一律思考开**（一次性会话无历史包袱）；每轮在 settle 时打一行
`[usage] 会话 N input=… cacheRead=… cacheWrite=… output=…`（验收口径见 App 仓库方案 §7）。

深档实测（历史，换模型语义时代）：同一收敛任务 `qwen-flash` 1.47s/157 tokens vs
`deepseek-v4.1-flash` 10.17s/1591 tokens，质量差距远小于时间差（App 仓库
`docs/设计方案/2026-10-29-聊天通道与思考模式.md` §5.3–§5.5）。

为什么要有直通：客户端把 prompt 模板放在 `system` 里（收敛 / 周报 / 分段 / 记忆策展 / 题目 / 深挖 / 回忆）。
修复前这些请求会被压成"只喂最后一条 user"，实测同一条收敛请求跑了 **129 秒、产出为空**；
修复后同一条 **2.5 秒**返回合规草稿（详见 App 仓库 `docs/基线文档/接口契约.md` §6 与 §7）。

#### 2.4.2 进度帧（2026-10-29）：让界面能显示"正在思考 / 正在动手"

工具回合可能几十秒没有正文。Agent 路径会额外下发**不带正文的进度帧**（非标准 OpenAI 字段，
只认 `choices[].delta.content` 的客户端会安全忽略）：

```json
data: {"object":"chat.completion.chunk","lifediary_progress":"working"}
data: {"object":"chat.completion.chunk","lifediary_progress":"thinking"}
```

- `working` = 工具正在执行（`beforeTool` 触发时发）；`thinking` = 工具返回后重新思考（`afterTool`）；
- 一次工具调用会成对出现 `working → thinking`，可能多次；
- 帧里**没有 `id`**（不是正文帧），客户端解析时要先判这个字段再判 delta；
- 只在 Agent 路径发；直通路径（带 `system`）没有工具，不发。
- 客户端意义：拿它把"空白等待"变成"正在动手…/正在思考…"，并且**它同时充当心跳**
  （工具跑几十秒也不会被判成读超时）。

#### 2.4.3 出错的呈现（不发独立 error 帧）

- Agent 路径一轮跑完却没有内容（上游 key 错、模型报错）→ 先吐 `delta.content = "这次没能生成回复，请再试一次。"`
  （`chatStream` 的 `unanswered` 事件）；
- 直通路径上游失败 / 一个字都没吐 → 吐 `"生成失败，请稍后重试"`；
- 两种情况都以 `finish_reason: "stop"` + `[DONE]` 收尾。
- **不再写 `{"error":{…}}` 帧**：只认 `choices[0].delta.content` 的客户端会把它当噪音丢掉，最后留下空气泡。
  客户端若自带 `error` 帧解析（旧版兼容），留着无害。

#### 2.4.4 任务通道 `X-Task`（2026-10-30，模板上移）

**为什么有**：日记任务（周报 / 分段 / 题目 / 回忆）原先由客户端把整份 prompt 塞进 `system` 走直通，
直通不建会话 ⇒ 那段对话**过完即弃**。"手机只留索引、正文归位 harness"要求这部分也落库，
所以模板搬到服务端、任务改走 Agent 会话。设计来源：App 仓库
`docs/设计方案/2026-10-29-对话正文归位Harness（手机只留索引）.md` §4（方案 A）。
收敛任务（`converge`）已于 2026-11-13 随旧整理链路退役（日记 v2：原文归档，不再整理）。

请求（`X-Task` 大小写不敏感，同时忽略 `system`）：

```http
POST /api/v1/llm/chat/completions
X-Task: weekly
Content-Type: application/json

{
  "messages": [{ "role": "user", "content": "请按上面的约束写这一周的回顾" }],
  "task_vars": { "positive_facts": "- 本周聊了 5 天", "profile_markdown": "（画像）", "previous_week_context": "上周回顾…" },
  "temperature": 0.5,
  "max_tokens": 4000
}
```

| 项 | 口径 |
|---|---|
| 任务名 | `weekly` / `segment` / `question` / `entry_view_polish` / `entry_view_digest` / `memory_curation` / `memory_merge` / `diary_review`；未知 → **400 `{"error":{"code":"unknown_task"}}`**（`interview` / `chapter` 于 2026-11-17 随回忆模式退役删除） |
| 模板 | 服务端 `apps/server/prompts/<name>_v<N>.md`，**与 App `core/ai/src/main/assets/prompts/` 同名同字节**；版本号 = 文件名去 `.md` |
| 变量 | `task_vars` 的键必须**齐**（缺一个或值不是字符串 → **500 `task_render_failed`，且不落半条会话**）；占位符是 `{{key}}`，与 App 的渲染算法相同 |
| system | 由服务端渲染后作为会话 `instructions` 段写入并**持久化**（进程重启仍是同一份 prompt）；客户端给的 `system` 一律忽略 |
| 人格 / 记忆 / 工具 | **全部摘掉**：任务会话不选我们的扩展（无人格、无记忆注入），`tools: []`（不给 pi 自带的读写改跑） |
| 档位 | 不参与思考档判定，**一律思考开**（`enable_thinking:true`，不带 effort 档；`LLM_MODEL`） |
| 参数透传 | `temperature` / `max_tokens` / `response_format` 照抄上游 —— 实现方式是按参数派生一个模型 id（`<model>#t0.4m4000r<8 位哈希>`），把参数挂在 `samplingParams` 上（pi-ai 最后写入、覆盖同名请求字段）；同参数复用同一个派生模型 |
| 会话 id | **一次调用一个新会话**（2026-10-31）：优先 `X-Conversation-Id`，没带就生成 `task-<uuid>`。任务之间没有对话关系，复用哈希 id 会把同一任务的多次调用挤成一条（实测三次收敛滚进同一条，token 越滚越长）；要续跑就显式带 `X-Conversation-Id`。**非流式回的 `id` / 流式 chunk 的 `id` 就是这个 id**，客户端拿它回读 |
| 落库内容 | transcript 里是**那句固定输入**（如「请按上面的约束写这一周的回顾」）+ 模型输出；整份 prompt 不进 transcript（否则回读是一堵规则墙） |

**任务会话不进"历史对话"（2026-10-31）**：`task-` 前缀的会话被 `GET /api/v1/agent/chats` 过滤掉——
它们的首句是"请按上面的约束写这一周的回顾"这类**指令**，不是用户说过的话，混进列表只会让人莫名其妙。
正文照旧可以按 id 回读（`GET /api/v1/agent/chat/:id/messages`），只是不露头。

**探针**：`pnpm --filter @lifediary/server tasks`（假上游记账，断言参数真的进了请求体、模板逐字节等于 App 现版、
三个任务都能回读、未知任务 400、渲染失败 500 且不留会话、通用聊天回归，
以及"同任务两次调用 → 两条 `task-` 会话、列表里 0 条任务会话"）。

**客户端接入状态（2026-10-31，两批；2026-11-17 更新）**：App 现用 **6** 个任务——segment / weekly
（第一批；`converge` 随旧整理链路退役）+ entry_view_polish / entry_view_digest / memory_curation / memory_merge（第二批，
模板逐字节复制自 App 资产，探针黄金用例守住）。`interview` / `chapter` 于 2026-11-17 随手机端回忆模式退役
（任务表与模板一并删除，App 不再有 RECALL 会话入口）。`emotion_deep_dive` 于 2026-11-12 随手机端深挖模块删除（任务项与模板一并退役）。
**仍未切**：`question`——本模板只有 `tone/question_length/depth`，App 现在的 system 还拼了人格 + 画像 + 近三天摘要，
切过去会丢上下文；要切得先给模板加 `profile_markdown` / `recent_summaries` / `today_captured` 并升版
（上下文走记忆块还是 App 拼，方案 §9.1 待定）；`diary_review` 是新任务，模板与 App UI 都未开始。
