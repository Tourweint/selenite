# 夜间任务模板 ·「阴间班表」

> 这是几份**拿来就能贴**的夜间定时任务模板（文案，不是功能）：定一个半夜的时间挂上去，晚上自己跑，早上只见一份晨报。
> 机制口径与挂法限制按 **2026-11-17** 代码核对（`index.ts:2252` 提醒建单、`reminder.ts:158` 到点跑模型闸、`scheduled-run-handler.ts` 隐藏触发、`settings-reminders.js:621` 手填上限、`tools.ts:719` set_reminder）。
> 状态：**模板已立、零任务挂上**。生效前提是 2026-11-17 那批改动（定时主动轮）提交/重启——生产服务还在跑旧代码，旧代码到点只写死消息、不调模型。

## 1. 机制口径：两路一班机器

「定时任务」和「主动轮」不是两个东西，底层都汇到同一个 `runPartnerTurn`；区别只有**触发指令隐不隐藏**（2026-11-17 核对）：

| 路 | 入口 | 触发指令 | 用户看到什么 |
|---|---|---|---|
| 定时任务（提醒路） | `POST /agent/reminders`、提醒页、执事 `set_reminder` 工具 | **隐藏**（带 `PROACTIVE_HIDDEN_MARKER`，`scheduled-run-handler.ts:28`） | 只有执事到点主动冒的那句晨报 |
| 例行任务（执事例行规则） | 执事例行任务引擎（`companion-api.ts:998` 起） | **可见**（指令本身就是任务内容） | 任务与指令都在例行会话里可见 |

夜间班全部走**提醒路**：早上最干净，醒来只有对面主动说的一句话。

## 2. 挂法（2026-11-17 核对）

| 挂法 | 长模板塞得下吗 | 说明 |
|---|---|---|
| 提醒页手填 | ✗ 单行 200 字上限（`settings-reminders.js:621`） | 只适合短指令 |
| 对话里让执事自建（`set_reminder` 工具） | ✓ 无长度闸（`tools.ts:719`） | 最省事：「每天 02:30 给自己安排巡检任务，指令如下：〈贴模板〉」 |
| 直接 `POST /api/v1/agent/reminders` | ✓ 服务端不限长（`index.ts:2252` 只 trim） | 批量挂用这条；多行文本注意 JSON `\n` 转义 |

- **挂给谁**：`partnerId` 指谁就在谁的会话跑；不指则取建任务会话的执事、兜底总管（`scheduled-run-handler.ts:16`）。要动手的模板挂总管（能派活）或有文件工具的执事；纯陪伴执事挂了只能出报告。
- **重复档**：`none / daily / weekly(+weekdays) / monthly(+dayOfMonth)`，可加 `until` 封顶。每周二/四 = `weekly` + `weekdays:[2,4]`。

**挂之前的三件事**（都是硬前提）：

1. **先重启**。生产还跑着旧代码（2026-11-17 核对：11-16/17 两批未提交未重启），重启前挂上去也只会写死消息。开关 `SCHEDULED_TASK_MODEL_RUN` 默认开、热生效，关 = 回旧闹钟。
2. **电脑半夜得醒着**。进程睡过头就跳过错过的那次、**不补发**（`reminder.ts:124` 注释明说），Windows 睡眠设置要对应调，否则阴间时间白定。
3. **动手修复会撞审批闸**。按你的审批档位来：夜间没人批的动作停在审批卡上，durable 不丢、早上批了续跑——别指望无人值守全自动修完，这是设计不是缺陷。

## 3. 阴间班表建议

| 时间 | 模板 | 频率建议 |
|---|---|---|
| 02:30 | 一 · 工程巡检 | 试点期每周 2 晚（如二/四），跑顺再加密 |
| 03:15 | 二 · 文档口径核对 | 每天 |
| 03:45 | 三 · 测试体检 | 每周 1 晚 |
| 04:15 | 四 · 依赖巡检 | 每周 1 晚（如周五） |

**试点口径**：先只挂 1–2 个，跑一周看晨报质量再加。每次到点都是一轮真模型（巡检还会派活、补测试，token 是真金）；晨报质量优先于任务数量。错开半小时以上，避免两个任务同时跑抢资源。

## 4. 模板一 · 夜间自主工程巡检（可动手）

```text
夜间自主工程巡检

长期目标：持续提升本仓库的代码质量、可靠性、可维护性和数据一致性。

开工守卫（先于一切）：
0. 先看 git status：工作区有未提交改动（说明有别人的在途工作）→ 本轮降级为「只巡检、只报告」，不做任何修改。
1. 读仓库自己的说明（README、AGENTS.md 或等价的代理说明、基线文档），按它说的技术栈、模块边界、验证方式来；它和本模板冲突时以它为准。

工作步骤：
2. 检查各业务模块的实现与文档口径是否一致。
3. 检查存储层：表结构、实体映射、索引、约束、迁移脚本。
4. 检查前后端与跨端接口的一致性（契约定义 vs 两端实现）。
5. 检查测试覆盖：关键路径有没有测试、仓库自己的探针还能不能过。
6. 识别潜在 Bug、异常处理缺陷、并发问题和数据一致性风险。
7. 按「严重程度 × 修复成本」排序。
8. 最多挑 3 个低风险、可独立验证的问题修复；修不完就记账，不硬修。
9. 为修复内容补测试。
10. 按仓库自己的验证说明跑「最小充分」验证，不只看退出码；检查 git diff。

约束：
- 不修改核心业务规则，不做大规模重构，不改无关文件。
- 不动对外契约与存储结构——这类发现记进报告，留给白天走仓库的方案流程。
- 不允许删测试或改断言来让测试通过。
- 不读、不抄、不外传任何密钥与环境变量真实值。
- 无法确定正确行为时不猜，记录问题。
- 所有修改留在工作区、不自行 commit / push（仓库说明另有规矩除外）；报告里列清修改清单和回滚方式。
- 测试失败如实报告。

最终交付：
对话里给 ≤3 行总结（做了什么、发现几件、改了几件）；完整报告落盘到仓库内固定位置（没有惯例就 docs/patrol/YYYY-MM-DD.md），若当前执行者没有写文件能力就直接把完整报告发在对话里。报告包含：巡检结论 / 问题与证据 / 实际修改清单 / 测试结果 / 未解决问题 / 下一轮建议（按优先级）。
```

## 5. 模板二 · 夜间文档口径核对（只报告）

```text
夜间文档口径核对（只报告，不动手）

长期目标：契约文档与代码不漂移——文档滞后按缺陷对待。

工作步骤：
1. 读仓库自己的说明（README / AGENTS.md / 基线文档），列出它自己声明的「文档必须跟代码一致」的清单：接口与契约、环境变量与开关表、模块结构、现状表。
2. 逐项对照代码：每个声明的字段 / 端点 / 开关 / 默认值，代码里是否真存在、语义是否一致；反向找「代码有、文档没写」的。
3. 检查最近几天的提交（或变更记录）有没有漏回写的文档。
4. 每个发现写清：文件与位置、文档现状、代码现状、建议改哪边、影响面。
5. 按「误导程度 × 修复成本」排序。

约束：
- 本轮只写报告，不改任何文件（包括文档本身——文档怎么改也要走白天的口径）。
- 不确定的一律算「待核对」，不算「不一致」，不猜。

最终交付：
对话里 ≤3 行总结；完整报告落盘（惯例同巡检），包含排序后的漂移清单 + 每条一句话修法建议。
```

## 6. 模板三 · 夜间测试体检（可补测试）

```text
夜间测试体检（最多补 3 个测试）

工作步骤：
1. 按仓库自己的验证说明跑全量测试与探针；没跑的部分如实写「没跑」，不用「暂不支持」含糊带过。
2. 标出 flaky 测试（重复跑两遍对比）、慢测试、被跳过的测试。
3. 找覆盖缺口：最近提交改动最多的模块 × 测试最少的模块，取交集。
4. 最多补 3 个确定性测试（不依赖网络、不依赖执行顺序、可重复）。
5. 重跑验证全绿才算完；绿不了就如实记录并回退新测试。

约束：
- 不改产品代码；不许改旧断言凑绿；不许删测试。
- 工作区有未提交改动 → 降级为只报告。
- 新测试不自行 commit。

最终交付：
对话里 ≤3 行总结；完整报告落盘（惯例同巡检），包含 flaky 清单 / 缺口清单 / 新增测试 / 执行结果。
```

## 7. 模板四 · 夜间依赖巡检（只报告）

```text
夜间依赖巡检（只报告，建议每周一次）

工作步骤：
1. 清点直接依赖的过期情况（按仓库生态用官方工具，如 pnpm outdated / npm audit / gradle versions）。
2. 已知漏洞扫描结果分级：能被本仓库实际触达的才升严重度，光在依赖树里挂着的不算。
3. 代码里是否有已废弃 API 的使用迹象（编译警告、deprecation 提示）。
4. 每项给结论：建议升 / 观望 / 不动，各配一句话理由。

约束：不真正升级、不改锁文件、不改任何文件，只报告。

最终交付：
对话里 ≤3 行总结；完整报告落盘（惯例同巡检），包含分级清单。
```

## 8. 顺手发现的滞后点（未动，待立项）

- `set_reminder` 工具描述还是旧闹钟口径：「到点要让执事做的事（它会据此现场说一句，不是照念这段）」（`tools.ts:719`）。新形态下这段 text 是**完整的隐藏触发指令**、跑的是一整轮模型，描述该跟着改。改工具描述 = 动缓存前缀资产，按仓库规矩必须进变更记录，故此处只登记不动手。
