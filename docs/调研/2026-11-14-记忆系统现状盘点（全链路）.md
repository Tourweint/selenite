# 记忆系统现状盘点（全链路）

> 一句话：现在的"记忆"不是一个库，是三层库各管一段——本地短记忆（`memory.db`）、日记事实源（`diary.sqlite`）、外部一生记忆库（`persona.db`），中间用 `voice.db` 当中转。短记忆已经跑通"抽取→巩固→召回→注入"四层；外部库只接通了"读"和"台账"，"写"默认关着，"自动介入"没做。

盘点时间：2026-11-14。口径以代码和实际库为准，设计文档只作旁证；两者不一致处以代码为准。

## 0. 结论先行

| 问题 | 一句话答案 | 状态 |
|---|---|---|
| 组织结构 | 一个记忆引擎四层（抽取/巩固/召回/注入），存储是一张 SQLite 表 + FTS5 镜像；外面套着"日记事实源"和"外部一生库"两圈 | 已跑通 |
| 记忆从哪来 | 六条写入路径：对话自动抽、`remember` 工具、日记镜像、派单结算、导入接口、外部库检索 | 前五条已跑，第六条只读 |
| 外部记忆库 | 读路径（`persona_recall` + 库边界页脚）已落地并已配置；写路径（每轮导出→voicevault→persona）代码有、开关默认关；每轮自动注入、通用 provider 化没做 | 半条 |
| 从其他软件导入 | 产品内的"导入记忆"只有接口、没有统一格式（前端是占位按钮）；真正在干活的是 voicevault——26 个来源、官方导出、Trae 解密库、723 个 Agent 记忆文件、551 篇知识库 | 分离的两套 |
| 整理记忆 | 自动化只做"强化/衰减/封顶/打码"这类确定性动作；语义合并一律"模型只出建议、人逐条点应用"，从不自动删 | 已跑通 |

一句话纠偏：你说"外部记忆库的介入还没做"——**不是完全没做，是只做了半条**。读的一只脚 11-13 已经落地（`.env` 配了 `PERSONA_MEMORY_ASK`，14 日进程重启后工具应当已注册），写的那只手默认关着，而"每轮自动把一生库带进上下文"确实没做。

## 1. 物理分布：三个库，各管一段

| 库 | 路径 | 角色 | 实测体量 |
|---|---|---|---|
| `memory.db` | `ts/apps/server/.data/memory.db` | 本地短记忆，模型每轮能想起的东西 | 122,880 B / **73 条**（episode 64、work 4、fact 2、entity 2、preference 1） |
| `diary.sqlite` | `ts/apps/server/.data/diary.sqlite` | 日记成稿的**事实源**（App 同步进来） | 16,384 B，摄入最近 3 天、≤50 条 |
| `voice.db` | `voicevault/data/voice.db` | 跨软件原始对话的**中转与归档** | **13,167 轮 / 26 个 source** |
| `persona.db` | `persona-metric/data/persona.db` | 外部"一生记忆库"，只读证据检索 | **245 MB / 121,989 原件 / 9,621 片 / 1,536 条记忆 / 100 事件 / 294 人** |
| 导出落点 | `ts/apps/server/.data/persona-export/2026-11.jsonl` | 主对话逐轮导出给 voicevault | 15 行（测试数据） |

数据流是单向的：

```
主对话 ──抽取──▶ memory.db ──召回──▶ prompt
   │
   └─(开关默认关)─▶ persona-export/*.jsonl ──手动跑脚本──▶ voice.db ──persona 入库──▶ persona.db
                                                                                  │
                                                                persona_recall ◀──┘（只读、按需）
```

注意两个"看起来像 bug"的事实：

1. **73 条里只有 6 条在 `global`**，其余散在 `session:*`（最多的一个 7 条）和 `partner:*`（7 条）。记忆页默认 scope 是 `global`，所以打开页面只看到 6 条——不是库空了，是作用域分开了。
2. **外部库已经有两跳的痕迹，但没接上第三跳**：导出文件有 15 行、voice.db 里有 4 轮 `source=lifediary`，而 persona 的 `catalog` 来源仍是 `ai_dialog+browser+clipboard+diary+voice_input+wechat_self`，没有 lifediary。也就是说"导出→中转"通了，"中转→一生库"这一段还没实际跑过。

## 2. 本地短记忆：四层结构

引擎装在 `ts/packages/memory/src/engine.ts`，只做编排，不含策略：

```
        ┌─────────┐   会话边界（done）
对话 ──▶│ Extract │──────────┐
        └─────────┘            ▼
                        ┌─────────────┐    ┌───────┐
                        │ Consolidate │───▶│ Store │
                        └─────────────┘    └───────┘
                                               ▲
        ┌─────────┐   每轮开头                  │
prompt◀─│ Inject  │◀── Recall ◀───────────────┘
        └─────────┘
```

### 2.1 记录模型：7 种 kind × 5 种 scope

`kind` 决定"怎么被想起、会不会过期、能不能合并"（`types.ts` L48–81）：

| kind | 中文 | 谁写 | 进召回 | 时间衰减 | 参与合并 | 封顶保护 |
|---|---|---|---|---|---|---|
| `preference` | 偏好 | LLM 抽取 / `remember` | ✅ 单独成组排最前 | ✅ | ✅ | ✅ |
| `intention` | 打算 | `remember(kind=intention)` | ✅ 单独成组 | ❌ | ❌ | ✅ |
| `fact` | 事实 | 导入 / 意图过期降级 | ✅ | ✅ | ✅ | ❌ |
| `experience` | 经验 | 派单 `done` 抽出 | ✅ 权重 ×1.08 | ❌ | ✅ | ✅ |
| `entity` | 人事物 | 导入 | ✅ | ✅ | ✅ | ❌ |
| `episode` | 经历 | 规则抽取 / 日记 | ✅ | ✅ | ✅ | ❌ |
| `work` | 履历 | 派单结算 | ❌ 排除 | ❌ | ❌（append-only） | ✅ |

`scope`（`types.ts` L15–30）：`global`（跨会话）、`session:<id>`、`partner:<id>`（执事独立键空间）、`day`、`topic`。**`day` 和 `topic` 只有类型定义，全仓库没有写入路径**——属于预留概念，不是现状。

每条记录的 15 个字段（`store-memory-store.ts` L88–104）：正文、重要性（0 起、上限 10）、可信度（`stated/inferred/tool/imported/unknown`）、来源、创建/失效时间、被谁取代、召回次数与时间、使用次数与时间、意图过期时间。

关键设计：

- **不软删**。用户点删除是物理删除（`MemoryStore.remove` 注释 L57–63）；要保留演化链就走 `supersededBy`（旧记录还在，只是不再被召回）。
- **越用越牢**。召回命中一次 `importance +0.05`，同时 `usageCount +1`；上限 10，下限 0.1，衰减永远不会把一条记忆降到 0。
- **意图有过期**。`intention` 带 `expiresAt`，过期后在**读取路径**原地降级成 `fact`（不建定时器、不删记录，`engine.ts` L231–243）。

### 2.2 抽取层：规则兜底 + 窄口径 LLM

两套实现共用一个 `Extractor` 接口，装配层按 `MEMORY_EXTRACT`（`auto/llm/rule`）选择（`memory-extract.ts` L35–49）。

**规则版**（`HeuristicExtractor`，`extract.ts` L111–154）：

- 只取 **user** 说的话，助手的话不记（防止自我强化的回声）；
- 按句切分，短于 6 字、寒暄、重复句丢掉；
- 一轮最多 5 条；
- `importance = min(1, 字数/60) × 0.6 + 0.2`；
- 一律记成 `episode`，来源 `extract:heuristic`。

**2026-11-13 加的噪声过滤**（默认开，`MEMORY_EXTRACT_NOISE` 可关）：

- 合成指令：`用户已批准…`、`用户拒绝…`、`主人回答了你刚才的问题…`、`本轮工具调用已达上限…` 等固定前缀，整条跳过；
- 命令句：`请/帮我/给我/不要/写/改/查/跑/生成/总结/翻译…` 开头，不算经历；
- 问句：问号结尾，或 `吗/呢/怎么样/为什么/是不是/能不能…` 结尾；
- 还要有"我/今天/最近/家里/喜欢/打算/过敏…"这类生活锚点，否则不记。

**LLM 版**（`DialogueExtractor`，`extract.ts` L505–579）只判两类：

- `preference`：对以后也成立的偏好，**最多 5 条**；
- `experience`：用户纠正过并说明原因、或验证过有效的做法，**最多 3 条**；
- 置信度低于 **0.6** 丢弃；每条正文上限 **400 字**，格式是 `偏好\nWhy: …\nHow: …`；
- **引文校验**：归一化后必须在用户原话里找到连续 **4 个字**（纯西文按 ≥4 字母整词），找不到就拒收，宁缺勿滥（`extract.ts` L301–317）；
- 输入只给模型 **6000 字**、单条 user 最多 600 字、助手只留首行，从最新往前取；
- 一次单独模型调用，超时 **20s**，`temperature=0`、`maxTokens=600`，走 `auxiliaryModel("extract")`（可单独 pin 小模型）。

两套并行跑、产出的 kind 不相交：`auto` 的语义是"在旧规则之上**增加**偏好/经验"，不是替换规则。

### 2.3 巩固层：写时只做确定性的事

`BasicConsolidator`（`consolidate.ts` L64–130）只做两件事：

1. **规范化**：全角→半角 → 空白折叠 → 首尾去空 → 剥句末标点（`normalizeContent` L49–58）；
2. **同 scope + 同 kind + 规范化全等** → 不新增，只把 `importance +0.1`（上限 10）。

例外说清楚：

- `work` / `intention` 不查重，直接按 id upsert / append——同文的另一单是另一段历史，合并等于篡改；
- `experience` 反过来，同一套做法再次出现算"确认"，照常合并强化。

**刻意不做**：语义去重、自动冲突消解、自动删除。语义合并全部走"模型建议 + 人拍板"。

### 2.4 存储层：一张表 + 一个 FTS 镜像

`memories` 表 15 列，`kind/scope/created_at` 建索引（`store-memory-store.ts` L128–148）。镜像表：

```sql
CREATE VIRTUAL TABLE memory_fts USING fts5(
  content, content_id UNINDEXED, tokenize='trigram'
);
```

- 写入时 `delete + insert` 维护镜像；构造时如果行数对不上就整表重灌（个人量级，几毫秒）；
- FTS5 不可用 / 查询切不出 3-gram → **静默回落窗口 SQL**，记忆检索不会让服务起不来；
- 查询走 trigram 词袋 `OR`，最多 24 个 gram（`buildFtsMatch` L160–177）。

**凭据打码收口在 `put()` / `patch(content)`**（`store-sqlite` L80–83、L275–278）：API key、Bearer、`sk-/ghp_/xoxb-`、JWT、≥32 位随机串、Luhn 通过的银行卡、MOD 11-2 通过的身份证，一律换成 `«redacted»`；手机号、生日、地址、人名**故意放行**（`redact.ts` 头注 L9–13）。所有写入方（工具、抽取、导入、巩固、日记、履历）都走这里，没有第二条漏口。

### 2.5 召回层：三路加权，可解释优先

`WeightedRetriever.recall`（`recall.ts` L53–117）：

1. **候选集** = FTS 命中 ∪ 最近窗口，窗口 `max(limit×5, 200)`；`work` 在候选集这一层就排除；
2. **过滤**：`validUntil` 已过的不进；已被取代的（`superseded_by` 非空）由 store 层过滤；
3. **打分**：

```
score = (importance×0.45 + recency×0.3 + keyword×0.2 + timesRecalled×0.05) × kindBoost
```

- `recency`：21 天半衰期（`exp(-ln2 × 天数/21)`）；
- `keyword`：中文退化为"双字片段"，命中比例封顶 1；
- `timesRecalled = min(1, recallCount/10)`；
- `kindBoost`：`experience` ×1.08，其余 ×1；
- `importance` 用的是**衰减到此刻**的值（`0.99^天数`，锚点 `lastRecalledAt ?? createdAt`），但 `intention` / `experience` 不衰减；
4. 排序取前 `limit`，默认 8。

命中后的写回（`touchRecall` L182–203）顺序不能换：先衰减到此刻 → 再加 `+0.05` → 最后把 `lastRecalledAt` 推到 now。锚点跟着值走，不会把衰减重复乘。

**已知 TODO（代码里明写）**：语义召回（embedding）、MMR 去冗余、相对时间感知。现在只有 FTS trigram + 双字关键词。

### 2.6 注入层：每轮现算，1200 字预算

`recallContext`（`assist.ts` L204–231）在每次模型请求前跑：

- scope = `global` + 执事的 `partner:<id>` + 本会话 `session:<id>`；
- 群会话直接返回空串（不读不写，防串台）；
- 异常只 warn，本轮不用记忆，绝不打断对话。

`buildContext`（`engine.ts` L254–339）分组渲染，预算 **1200 字**：

```
【用户偏好】    ← preference，排最前
【打算】        ← 未过期 intention
【其它】        ← [kind] 正文
【也许值得提起】 ← 主动提起，固定放最后
```

"也许值得提起"是**主动开口**类能力：`MEMORY_PROACTIVE` 默认关；开也只挑 `importance ≥ 0.7`、超过 7 天没被召回、与当前话题**零关键词交集**的旧记忆，最多 2 条、每条 ≤80 字；执事轮一律不注入（`memory-proactive.ts`）。

注入点在 `memory_recall` provider（`INJECTION_ORDER.memory_recall = 100`），`scope: "turn"`、`channel: "message"`。

另有一条**任务近况**通道（`taskMemoryBlock`，`assist.ts` L243–274）：给 `question` / `diary_review` 类任务用的最近 3 天日记，拼在 instructions **尾部**（不动前缀缓存），先 `syncDiaryToMemory` 再从记忆里按日期取，不再直读 `diary.sqlite`。

**边界：上下文压缩不是记忆。** `pi-durable` 在超 50% 上下文时做的 L1 压缩/摘要，不进 L2，也不参与召回；否则等于把"临时摘要"变成了长期人格。

### 2.8 记忆页 A 版（UI）

`MEMORY_PAGE_A` 默认开，关掉整套回旧页（`memory-page.js` L21）。结构：

- 首屏只拉计数（`limit=0&excludeKinds=work`），再按分组懒加载，每页 20 条；
- 7 个分组：偏好 / 打算 / 事实 / 经验 / 人事物 / 经历 / 履历；**默认展开偏好与打算**，经历默认收起；
- 每条显示 kind、来源标签（`用户/抽取/日记/履历/导入`）、状态、时间、召回/使用次数；操作是"删掉 / 标过时"；
- 顶部有整理按钮与"在跑 / 上次整理时间 / 失败原因"状态；建议以卡片呈现，带**证据引文**，逐条"应用 / 忽略"；
- 底部是"一生记忆库"页脚，只显示库边界，**不提供查询入口**；
- "导入"按钮是**占位**：点开提示"目前还没有统一的记忆格式，等格式定了再做"（`memory-page.js` L304–307）。

## 3. 记忆从哪来：六条写入路径

| # | 来源 | 触发 | 落点 | 落什么 | 开关/上限 |
|---|---|---|---|---|---|
| 1 | 对话自动抽取 | 每轮 `done` 收尾 | 本会话；偏好/经验改挂 global 或 partner | 规则 episode + LLM preference/experience | `MEMORY_ENABLED`；`MEMORY_EXTRACT` |
| 2 | `remember` 工具 | 模型主动调用 | 本会话（或由工具决定） | 指定 kind | 群聊拒绝；写完修剪 |
| 3 | 日记镜像 | 任务近况读取时 | `global`，`id=diary:<entryId>` | `episode`，正文前 200 字，`importance 0.6` | 30s 节流；最近 3 天、≤50 条；upsert 幂等 |
| 4 | 派单结算 | 任务终态 | 发起执事的 `partner:<id>` | `work` 履历 +（done 时）`experience` | work 每 scope 200 条；经验门槛 40 字 + 动作词 |
| 5 | 导入接口 | `POST /memory/import` | 指定 scope（global / partner） | 仅 `fact/episode/preference/entity`，`veracity=imported` | 单次 ≤5000 条；单条 ≤2000 字；规范化等价跳过 |
| 6 | 外部库 | `persona_recall` 工具 | **不写入** | 只返回证据条目 | 条件注册；只读 |

实测来源分布（73 条）：`extract:heuristic` 57、`diary` 6、`user` 5、`work` 4、`taught` 1。**没有一条 `extract:preference`**——说明偏好抽取在产出这批数据的进程里没生效或没命中。这是"为什么库里 64/73 都是 episode"的直接原因，也意味着 kind 统计现在更接近"规则抽取器的统计"，不是"人的记忆结构统计"。

路径 3 的细节值得单独记：日记摄入**不复用 `engine.remember()`**，因为那会每次生成随机 id、重复同步堆一串；它直接用 `store.put()` + `diary:<entryId>` 稳定 id 做 upsert（`memory-ingest.ts` L10–14）。

路径 4 的经验门槛是确定性的，不调模型（`work-record.ts` L75–80）：

```
结果行 ≥40 字 且 含至少一个动作词（改/写/读/跑/查/整理/合并/删除/替换/核对/重试/迁移/拆分/回滚/验证/补/建/装/配）
→ "下次同类活可以这样做：<结果行，≤160 字>"
```

不过门槛就一条都不写——宁缺毋滥。

## 4. 外部记忆库：persona-metric

### 4.1 它是什么

`persona-metric` 不是"另一个记忆插件"，是一套**证据库**：把散在六类来源的个人记录切成片、打好标签、连成事件，做到"问一句话就能翻出原话，每条结论都能追到具体哪一段"。

入库五步（`persona-metric/docs/项目说明.md`）：

```
六个来源 → 原件（raw_source，sha256 + 只许 INSERT）→ 片（segment，9,621）
        → 锚点（行为/情绪/对象/人物）→ 四层记忆 → 索引
```

四层与六套表：

| 层/表 | 一条是什么 | 体量 |
|---|---|---|
| `segment` | 一段可独立读懂的原文，100–1500 字 | 9,621 |
| `memory`（level=day） | 「某年某月某日 某主题的一天（N 片）」 | 1,536（日 + 事实同表，用 level 分） |
| `memory`（level=fact） | 跨多天反复出现的稳定倾向 | 同上 |
| `event` | 跨天的一件事 + 带逐字原话的弧线 | 100 |
| `entity` | 人 / 角色 / AI | 294 |
| `tension_pair` | 「某稳定倾向 vs 另一个｜触发：某类情境」 | — |
| `catalog` | 库里有什么（100 事件 / 294 人 / 74 个月 / 277 对象） | — |
| `time_axis` | 每月活跃度 | 74 个月 |

检索五条路线：A 只搜词（BM25）、B 只比意思（向量）、C 词+意思融合（默认）、D 先摘要再搜（**已弃用**，专名保留率只有 45.8%）、E 搜完再让模型重排（精度最高，3 次模型调用）。

边界很硬：`ask.py` 只读（`mode=ro`）、0.7 秒、不调模型；`answer.py` 的生成层要过四道校验（逐字/覆盖/依据/反向检索），过不了就降级成"证据里没有直接回答"。日常建议只看证据，不看生成结论。

### 4.2 读路径：已落地

`persona-ask.ts` 的设计是"唯一入口 + 只读契约"：

- 只 spawn `python ask.py <question> --json --limit N`，**argv 数组、不用 shell**，模型只能影响 question 文本，没有注入面；
- 超时 15s；失败一律 `ok:false`，绝不抛、不打断裂对话轮；
- 解析六组：`memory_day / event / fact / segment / entity / tension`，每组默认 5 条、上限 20；
- 带 `unknown` 与 `coverage`（`not_searched / not_indexed / gaps / gap_months`）——**查不到 ≠ 没有这回事**，工具描述里明写"照转述，不要编"；
- 日志只记字数/耗时/组数，不记问题原文与正文。

双闸注册（`lifecycle-harness.ts` L472–478）：

```
PERSONA_MEMORY_ASK 配置 = 启用；PERSONA_MEMORY_ENABLED=false = 显式关
两个都过 → 注入 deps.personaAsk → persona_recall 才注册
否则工具不上架（模型侧 tool_unavailable，一行回滚）
```

现状：`.env` 在 **2026-11-13 22:06** 写入 `PERSONA_MEMORY_ASK=<persona-metric>\analysis\ask.py` 与 `PERSONA_PYTHON=python`；本机 node 进程启动于 **2026-11-14 14:31 之后**。按启动读取顺序，当前进程应已注册该工具——这一点没有做实机调用验证（调用会起 python 子进程并触达个人库，超出本次只读盘点范围）。

库边界页脚（`GET /api/v1/agent/memory/external`）：

- `MEMORY_EXTERNAL=false` 时整块 404；
- 未配置 → `ready:false, reason:not_configured`；配了但关 → `reason:disabled`；
- 配好 → 跑 `ask.py --catalog-only`，只取前 20 行，缓存 10 分钟；
- provider 目前**硬编码一个** `{id:"persona", name:"一生记忆库"}`，没有 provider 注册表。

### 4.3 写路径：代码有，默认关

`persona-export.ts` 在每轮 `done` 后追加一行 JSONL：

```json
{"v":1,"conversationId":"…","turnId":"…","ts":"2026-11-06T02:41:44+08:00","userText":"…","assistantText":"…","model":"…"}
```

- 只导**主人主对话**：`task-` 专线、群会话、执事会话一律不导（混进主人语料会串人格）；
- 按本地月份轮转文件，`appendFile`，失败只 warn，**不 await**；
- `PERSONA_EXPORT_ENABLED` 默认关，只有显式 `true/1/on` 才写。

现状：`persona-export/2026-11.jsonl` 有 15 行（探针/测试），voice.db 里 `source=lifediary` 4 轮 / 2 会话，persona 侧还没有 lifediary 来源。

### 4.4 "介入"到底缺什么

| 能力 | 现状 |
|---|---|
| 按需检索（模型主动查一生库） | ✅ 代码 + 配置都已就位（待实机验证） |
| 每轮自动把相关一生记忆带进上下文 | ❌ 没做（本批明确"只走按需工具，不进 recallContext/buildContext"） |
| 通用外部记忆库 provider（可插多个库） | ❌ 没做，单点硬编码 persona |
| 主对话持续回流到一生库 | ⚠️ 代码有，开关关；且需要手动跑 `import_lifediary.py` |
| 一生库→本地短记忆的回写（把人提炼成偏好/事实） | ❌ 没做 |
| 删除/遗忘在两侧传播 | ❌ 没做 |
| 外部库的写入鉴权与脱敏边界 | ⚠️ 只读天然安全；写路径只有会话过滤，没有内容分级 |

所以更准确的说法是：**外部库已经"接上了"，但还没有"介入"**——介入意味着它主动参与每一轮，现在只是"你想查就能查"。

## 5. 从其他软件导入：三条完全不同的路

先把三个"导入"分开，它们经常被混为一谈：

| 场景 | 入口 | 单位 | 现状 |
|---|---|---|---|
| A. 把**别的 AI 的记忆条目**并进本地短记忆 | `POST /api/v1/agent/memory/import` | 一条一句 | 后端可用，前端占位，**没有统一格式** |
| B. 把**别的软件的原始对话/记录**收进归档 | `voicevault` 的扫描器与定制导入器 | 一轮对话 / 一个文件 | 大量已入库，26 个 source |
| C. 把 **voicevault 的归档**做成一生记忆库 | persona 的五步入库 | 片 → 四层 | 已跑通（121,989 原件） |

### 5.1 A：产品内导入（壳已搭好，格式未定）

契约在 `memory-consolidate-review-scope.ts` L200–242：

- `items: [{text, kind?, createdAt?, importance?}]`；
- 只认 `fact / episode / preference / entity`；单条 ≤2000 字；单次 ≤5000 条；
- **只增不改**：规范化等价跳过并计数，不提升 importance、不覆盖、不删除；已被取代的旧记录也算"已存在"；
- `source` / `veracity` 一律 `imported`；未来时间裁到 now（防止 2099 年的记忆把新近度打分打爆）。

它没有做的是**格式适配**：ChatGPT 的 memory、Claude 的 memory、各家导出的 JSON，都没有映射层。前端按钮因此是占位——"等格式定了再做"。

### 5.2 B：voicevault（真正在干活的导入枢纽）

26 个来源、13,167 轮，覆盖面从编码 Agent 到浏览器、微信、剪贴板、语音、账单、知识库：

| 类别 | 代表来源 | 状态 |
|---|---|---|
| Agent 会话 | Claude Code、Codex、OpenCode、Z Code、Cursor、CodeBuddy、豆包 agent、通义灵码、Gemini CLI、Cherry Studio、VS Code Copilot… | ✅ 直接扫本地库/JSONL |
| 网页对话 | ChatGPT 官方导出、DeepSeek 官方导出、conversation-export | ✅ 只读官方导出，不做在线抓取 |
| 加密库 | Trae CN `database.db`（SQLCipher 4） | ✅ 先解密再读，113 会话 / 594 轮 |
| Agent 自己的记忆 | 16 个 agent 群、**723 个记忆文件 / 1,869 条** | ✅ 但 `generated_by=agent, retrievable=0`，只作 L3 旁证 |
| 知识库原件 | Obsidian **551 篇 / 6,528 段** | ✅ 全文逐字留存 |
| 被动来源 | 微信 309,769 条、剪贴板 441、浏览器 8,909、语音输入 295、支付 3,498 笔 | ✅ 各有 `retrievable` 开关 |

它的分层纪律是关键：**L0 原文只增不改、L1/L2 必须能用代码重算、L3 判断（释义/结局/话题命名）不进稳定契约**。判据只有一条："这个值能不能用代码重算出一样的结果？"

对我们的意义：

- **"从其他软件导入外部记忆"其实早就做了，只是做在归档层**，不是做在 `memory.db`；
- Agent 记忆文件**故意不变成我的记忆**（`retrievable=0`）——别人的画像不等于我的人格，这是刻意的边界，不是漏做；
- 微信里别人的话也只留角色标签、不进检索（"只有自己那一半"）。

### 5.3 C：persona 消费 voicevault

persona 不自己扫本机原始文件，只读 voice.db（`mode=ro`），并遵守稳定契约（`turn/session` 的列名与语义、`uid` 生成规则、原文永不清洗）。浏览器数据也从 voicevault 同步脱敏后的日锚，`collect_browser.py` 已废弃。

这就是"上游唯一真相源 + 下游只同步派生视图"的口径——否则口径分叉、脱敏失效、覆盖不全必然同时发生。

## 6. 整理记忆：自动化只做确定性的事

### 6.1 十种整理手段

| # | 手段 | 时机 | 是否自动 | 会不会删数据 |
|---|---|---|---|---|
| 1 | 规范化去重 + 强化 | 写入 | ✅ | 不删，只 +0.1 |
| 2 | 时间衰减 | 召回打分/写回 | ✅ | 不删，下限 0.1 |
| 3 | 召回强化 | 每次命中 | ✅ | 不删，+0.05 |
| 4 | 会话/执事封顶修剪 | 写入末尾 | ✅ | **会删**，只删 `session:`/`partner:` 最旧，`global` 永不修剪 |
| 5 | 意图过期降级 | 读取 | ✅ | 不删，`intention → fact` |
| 6 | 凭据打码 | 落盘 | ✅ | 改写正文中的敏感串 |
| 7 | 噪声过滤 | 抽取 | ✅ | 不落库 |
| 8 | 模型建议整理 | 人点"整理" | ⚠️ 只出建议 | 不执行 |
| 9 | 确定性审计 | 整理成功后 | ✅ 只算 | 不执行，只写 diff |
| 10 | 应用/忽略 | 人逐条点 | ❌ 必须人点 | 应用 = `supersede`（旧记录保留） |

封顶的细节：`MEMORY_SESSION_CAP` 默认 200，`0/负数/非法 = 关闭`；保护 `preference / intention / experience / work`，以及被 `supersededBy` 引用的行（避免悬空引用）；`global` 在 store 层直接抛错拒绝修剪（"偏好与长期事实永不淘汰"）。

### 6.2 模型建议整理（A 版"整理任务"）的完整流程

```
POST /consolidate/review?background=1
  → 202 + 后台任务（同 scope 去重，已在跑返回 alreadyRunning）
  → 取 scope 内 ≤200 条，剔除 work
  → < 2 条直接返回空（不打模型）
  → 模型：30s 超时、temperature=0、maxTokens=2000、≤50 条建议
  → id 复核：模型编造的 id 一律丢；同对去重
  → 证据引文：拿 drop 端正文回扫最近 200 会话 × 200 条，找最早命中，
     摘 ±40/80 字，再过一遍打码；查不到 = null（不挡应用）
  → 写 .data/memory-proposals.json（剥掉 evidence，避免多存一份对话片段）
  → GET /consolidate/state 给页面轮询：running / 上次结果 / 失败原因
  → 人逐条 apply → supersede(dropId, keepId)，幂等；或 dismiss → 从待决文件摘掉
  → 成功后跑确定性审计，写 .data/memory-consolidate-diff.json
```

提示词只有 6 条规则，核心是"只在语义确实重复、或后者是前者的更正时才提；措辞接近但讲的是不同事情，不要提"。

D18 底线写死在两处代码注释里：**自动化只做强化/衰减/确定性同义收敛；模型调用只产出建议；没有"全部应用"。**

### 6.3 确定性审计（只读）

`consolidateScope`（`consolidate.ts` L342–393）：

- **合并建议**：同 kind + 规范化等价，保留 `usageCount` 更高的一条；`work/intention` 豁免；
- **淘汰建议**：>90 天没被使用、`importance < 0.5`、kind 不在 `preference/experience/work/intention`；已被合并的条目不重复列；
- 上限刻意不设（截断会让人误以为"剩下的都没问题"）；
- 只写 diff，**从不调用 `remove()` / `supersede()`**。

现状：global 6 条 → `kept 6 / merged 0 / retired 0`；另有一条待决建议（10-30 两条"同步链路"日记重复，保留细节更全的那条），说明"建议制"确实在工作，但还没人点。

### 6.4 一生库的"整理"是另一回事

persona 不合并记忆，它做的是：切片（一篇 3000 字日记不切，查"天洋广场"会返回整篇）→ 打锚点（行为/情绪/对象/人物，规则+词典为主）→ 聚合成日/事实/事件/张力 → 建四套索引。原文用 sha256 + 数据库触发器保证"只许 INSERT"，任何时候都能证明没被改过。

它明确弃用了"先摘要再搜"：摘要会把 `Vue3+SpringBoot` 洗成"确定技术栈"，术语保留率只有 45.8%——所以摘要只当给人看的缩放版，检索永远走原文。

## 8. 边界与风险（这条会怎么错）

1. **kind 分布失真**：规则抽取把几乎所有话都记成 `episode`（64/73），偏好/事实/人物的比例被压低。按 kind 做的统计、按 kind 做的注入分组，现在更像"抽取器日志"，不是"人的记忆结构"。
2. **4 字引文校验是双刃**：能挡住"模型把常识安到用户头上"，但也会误杀改写幅度大的真实偏好；短偏好（归一化后 <4 字）走的是"整段出现"兜底，等于放宽。
3. **1200 字预算 + 无 MMR**：召回 10 条里 8 条说同一件事时，预算会被重复条目吃掉；代码 TODO 里已写明，但还没做。
4. **中文关键词是双字切片**：`Kimi199`、`<VPS_IP>` 这类词靠 FTS trigram 能搜到，但纯关键词打分对英文/数字不友好；短查询（<3 字符）直接走窗口，不走向量。
5. **外部库"接入但未介入"**：用户感知不到"一生记忆"，除非主动问"去年""2024 年"；而且工具描述要求"先 recall 再 persona_recall"，模型不一定遵守。
6. **数据流断在第二跳**：导出默认关、voicevault 导入要手动跑、persona 摄入也要手动跑——任何一跳没跑，主对话就永远进不了一生库。现在实际只有 15 行导出、4 轮进 voice、0 条进 persona。
7. **一生库的空月不是空白**：74 个月里 20 个空月（其中 2021 全年 12 个），"查不到"只代表没记录，不代表没发生。工具已经把 `coverage.gap_months` 带出来，但模型可能不复述。
8. **删除不传播**：本地删一条记忆，不会影响 voicevault 里的原文，也不会影响 persona 里已提炼的片；反过来也一样。这是当前最大的"隐私一致性"缺口。
9. **`work` 履历是 append-only**：不召回、不衰减、不合并，只按 scope 封顶 200；整理时被剔除。它不是"记忆"，是台账，混在同一个表里只是复用了存储。
10. **`day` / `topic` scope 是空概念**：类型里有、代码里没有写入路径，读文档的人容易误以为"按天/按主题存"已经实现。

## 9. 如果要往前推，最小三步

按"投入小、闭环短"排序，不建议一次做通用记忆平台：

1. **把写路径打通**：`PERSONA_EXPORT_ENABLED=true` → 定时跑 `import_lifediary.py` → persona 侧增量入库；先验证"主对话能进一生库"，再谈自动注入。
2. **给外部库一个"低置信自动一次"**：不是每轮注入，而是在 `recall` 空结果 / 用户问"以前/去年/很久以前"时自动补一次 `persona_recall`；仍不改变"按需"的架构。
3. **定义记忆交换格式 v1**：`{text, kind, createdAt, source, evidence?}` + 各家导出映射（ChatGPT/Claude 先做两家），把前端占位按钮变成真导入；否则 A 路径永远只有接口没有用户。

通用 provider 注册表、删除传播、embedding 召回都可以往后放——它们重要，但不是当前最短的闭环。
