## 零、先说结论（按性价比排序）

| 优先级 | 做什么 | 为什么值 | 代价 |
|---|---|---|---|
| **P0** | 让 `user_statement` 进检索面（FTS + 向量） | 现在它只有 `LIKE`，是「亲口说的话反而最难召回」的直接原因 | 小：一张表进两个索引 |
| **P0** | 补「这库没什么」的机器可读边界 | 现在边界靠 20 行 catalog 文本，模型只能看到月度密度，看不到「哪类事根本没采」 | 小：catalog 加几行 |
| **P1** | `segment` 粒度对齐「一句话能回答的单元」 | 平均 513 字、最长 9.9 万字，一条命中里 90% 与问题无关 | 中：切分策略 + 重建索引 |
| **P1** | 空的 20 个月显式标注 | 74 个月里 20 个整月无片，模型容易把「没采到」说成「没发生」 | 小 |
| **P2** | 链接层扩类型 | 现在只有 `same_day_object` / `same_utterance` 两种，事件链、因果链都没建 | 中 |
| **P2** | 事件与长期事实层扩容 | `event` 100 条、`memory.fact` 160 条，对 9621 片来说太薄 | 中 |

## 一、召回质量：真正的问题在哪

### 1.1 亲口说的话召不回（P0）

实测：

- `user_statement` 只有 10 条，`ask.py:306-323` 的 `g_statement` **只用 `LIKE`** 匹配 `body/about/tag`。
- 它**不在** `segment_fts`、**不在** `rag_unit`、**没有向量**（`rag_unit` 只有 `summary` / `question` 两类单元）。
- `search_rag.py` 完全不查它。

后果：用户亲口纠正过的事实（"我妈没住过院，住院的是我姥姥"），
在语义召回里是**不可见的**，只有问题里恰好出现「姥姥」「住院」这类原词才 `LIKE` 得到。
这恰恰是最高证据等级的一层，却排在检索能力的最后。

**建议**：

1. 把 `user_statement` 建成一张检索单元（`rag_unit.unit_type = 'statement'` 或独立 FTS 表），
   `text` 用 `body`，`qtype` 留空。
2. 向量侧同批入库（bge/qwen 都行，和 `rag_unit` 同一套 `vec_off` 机制）。
3. `ask.py` 的 `fact` 组继续把它排在**最前面**（现在就是），但改成从索引取而不是 `LIKE`。
4. 每写入一条就增量更新索引（`repair.py` 写完顺手 upsert），不要等全量重建。

### 1.2 片太长（P1）

实测：`segment` 9621 条，平均 513 字，最长 99,724 字；`readable_alone=0` 的有 2246 条。

一条 500 字的片被 `ask.py` 截成 200 字展示、被 harness 再截成 160 字，**命中理由与正文经常不是一回事**。
而 `rag_unit` 的 `summary` 单元（3981 条）其实是更好的召回粒度——但 `ask.py` 的主路径
（`g_segment`）走的是 `segment_fts`，不是 `rag_unit`。

**建议**：

- 召回层优先用「`rag_unit` 的 summary 单元」，`segment` 只作为回原文的落点（`get` 用）。
- 或者把超长片在入库时按「一个话题一段」切开（不是按字数硬切），`readable_alone=1` 作为切分门槛。
- 长片保留 `parent_seg_id` 链，回原文时能拼回去。

### 1.3 空月与覆盖缺口（P1）

实测：`catalog` 里 `section='time'` 共 74 个月，**20 个整月无片**（2021 全年几乎空），
2020-09 到 2021-04 每月只有 3–23 片（note 写着"记录极少，结论不稳"）。

`ask.py` 的 `coverage.gaps` / `gap_months` 会带出来，harness 也会显示成
「记忆库在这些时段没有记录」，这是对的。但有两个缺口：

- **没采的模态**：`coverage.not_indexed` 现在硬编码 `["audio（未采集）"]`。
  实际没采的可能还有：微信他人的原话（`raw_wechat_other` 有但 `retrievable=0`）、
  浏览器历史、剪贴板里的非文本。建议改成从 `raw_source` 统计出来的真实清单。
- **密度差**：2026-10 有 1771 片，2026-11 只有 2 片。模型看到「最近没什么」时，
  分不清是"真没事"还是"还没采进来"。建议 catalog 里加一行「最后采集时间」。

### 1.4 catalog 太薄（P0）

现在 `--catalog-only` 输出的是**月度密度 + 人物/对象计数**。它能让模型知道"大概有什么"，
但答不了三个关键问题：

1. 这个库**覆盖哪些模态**（AI 对话 / 微信 / 剪贴板 / 语音 / 日记）；
2. 这个库**不覆盖什么**（比如"没有别人说的话的原文"）；
3. 这个库**哪些结论不可靠**（`confidence='low'` 的 511 条占 33%）。

**建议** catalog 固定四段（仍 ≤20 行）：

```
范围：2020-09 ~ 2026-11（74 个月，20 个月无记录）
模态：AI 对话 5221 / 微信本人 3546 / 剪贴板 329 / 语音 292 / 日记 233
可信：high 876 / medium 149 / low 511（low = 模型推断，别当事实）
不覆盖：他人原话原文、音频本体、2021 年
```

这段会进模型每轮前缀（裁到 600 字），比月度列表有用得多。

## 二、写入面：现在这条链是干净的，别急着扩

### 2.1 写一张表是对的

`repair.py` 的 `ALLOWED` 白名单（`user_statement` / `object_synonym` / `entity` /
`memory` 降权 / `segment_anchor` / `tension_pair`）这个设计很好：**写面小、每刀留痕、不许删**。
继续保持。

### 2.2 但 `user_statement` 混了两种语义（P2）

现在 `source` 统一 `user_oral`、`built_by` 区分是 `record_user_statements.py` 还是 `repair.py`。
外部写入进来之后，你分不清：

- 用户当面口述（最高优先，压过一切推断）；
- 从别处导入的"用户说过的话"（比如聊天记录里他自己说的）；
- 助手判断该记的（**不应该进这一层**）。

**建议**：`source` 加前缀（`user_oral:lifediary` / `user_oral:import`），
或加一列 `source_ref`（会话/消息 id）。别加 `kind` / `scope`——那会让这层变成杂货铺。

### 2.3 助手推断要有自己的表（P2，可选）

如果以后要接"助手觉得值得记"（偏好、打算、项目事实），别塞进 `user_statement`。
单开一张候选表，带 `status = pending/accepted/rejected` 和 `confidence ≤ medium`，
`ask.py` 用低优先组读。这样"人说的"和"机器猜的"永远分得开。

## 三、内化：拆分规则比内化频率重要

### 3.1 拆分应该在写入时做，不是在内化时

现在的链条是：写入 → 攒着 → 内化 → 拆进派生表。
问题：内化时再拆，规则改了要重跑全部历史；而且内化失败时，原话还是一条大块头。

**建议**：写入时就切到「原子粒度」（一句话一件事），内化只做**关系**（人物、事件、时间轴、冲突、链接）。
这样：

- 内化可以随便重跑，因为源已经是原子的；
- 内化失败不影响召回（原子已经能查）；
- 规则迭代只影响"关系"，不影响"能不能查到"。

### 3.2 内化幂等键

用 `note_id + rev`，旧 rev 标 `superseded` 而不是删。这与 `repair.py` 的
"降权不删、留证据"是同一套纪律。

### 3.3 派生表随便重建，源表别动

`build_*` 系列现在会 `DELETE FROM memory WHERE level='fact'`、`DROP TABLE rag_unit` 等。
这没问题——只要 staging / `user_statement` 不在 `build_*` 的清理范围内。
建议在 `pm_status.py` 里加一条断言：重建后 `user_statement` 行数不减。

## 四、检索层：几个具体的调优点

### 4.1 `ask.py` 不走向量，`search_rag.py` 走向量，但两者不共享结果

- `ask.py`：六组表 + 关键词/时间锁，**没有向量**（`--no-vector` 参数注释写"本门本就不走向量"）。
- `search_rag.py`：BM25 + 向量 + RRF，五字段，**但不查 `user_statement`**。

用户问"我妈住院那阵子"，`ask.py` 靠 `LIKE`/FTS 能中；问"我是不是一直很怕麻烦别人"，
`ask.py` 基本无解，`search_rag.py` 有可能中。

**建议**：`ask.py` 至少对 `segment` 一路加向量（复用 `seg_vec` + `rag_embeddings.npy`），
或者干脆把 `search_rag.py` 作为 `ask.py` 的 `--vector` 模式接进去。
不需要重写，两个脚本共用同一个 `.npy`。

### 4.2 六组并行查是对的，但组的权重可以调

`ask.py` 按题型选入口（`pick_qtype` 八类）。实测 `event` 只有 100 条、`tension` 更少，
这两组对大多数问题贡献很小，却和 `segment`（9621 条）平起平坐。

**建议**：按题型给组配额，而不是每组同 `--limit`。比如事实题：`segment` 占 60%，
`memory_day` 20%，`fact` 20%，`event/entity/tension` 只在题型命中时才查。

### 4.3 `dist` 字段现在没被消费

`ask.py` 输出 `dist.by_month` / `by_module` / `by_group`，但 harness 只解析
`groups` / `coverage` / `unknown`。这是**没问题的**——但如果你希望模型知道
"这个结论覆盖了哪些月份"，把它折进 `unknown` 一句话更有效（模型只读文本）。

### 4.4 内容词门槛这件事，harness 已经做了，库这边也该做

harness 的轻召回有个 `hasInformativeMatch`（虚词剥离后再比），是 2026-11-22 冒烟校准出来的。
库这边的 `LIKE` 匹配没有这个门槛——搜「怎么样了」这种虚词会命中一堆片。

**建议**：`ask.py` 的 `LIKE` 分支加同样的虚词剥离（或干脆全部走 FTS/BM25，不用 `LIKE`）。

## 五、数据质量：值得定期看的三件事

1. **`confidence='low'`**：`memory` 里 511/1536（33%）、`segment` 里 89/9621（0.9%）。
   前者是模型推断、后者是切分不确定，`ask.py` 都照样当事实返回。
   建议 `ask.py` 命中 `low` 时在 `why` 里标出来，让模型知道"这是推断"。
2. **`readable_alone=0` 占 23%**（2246/9621）。这些片离开上下文读不懂，
   但照样进检索。建议检索时降权，或只作为"回原文"的落点。
3. **重复片**：按 `text` 前 100 字 hash 实测，`segment` 里有 **431 组、510 条多余重复片**
   （占 5.3%）。这些会挤占召回名额、也会让「同一个事说了两遍」看起来像两件事。
   建议入库时按 hash 去重（保留最早一条 + `dup_of` 标记），检索时直接跳过。

## 六、和 harness 的接口：现在够用，别为了"完美"改契约

- 两个入口文件（读 `ask` / 写 `repair`）的形状已经够 harness 用了。
- `groups` 组名不固定这件事，harness 已经按扁平 `hits` 处理（2026-11-23 改的）。
- 真要加字段就**只增不改名**：`hits[].text` 换成 `hits[].body` 会让 harness 丢内容。
- 如果以后要支持 `get`（按 id 回原文），加一个 `--get <id>` 子命令即可，
  harness 侧再接，不影响现在的读写。

## 七、明确不建议做的

- **不要为召回建向量库/FAISS**：9621 片 + 1.6 万单元，numpy 点积够快，`.npy` 可重建可解释。
- **不要把派生表当源**：`memory` / `event` / `rag_unit` 都能重建，别让外部写入直接进这些表。
- **不要在一张表里混 stated / inferred**：这是"以后说不清哪句话是谁说的"的起点。
- **不要为了让 harness 好用而改 JSON 字段名**：改名的收益是零，代价是两边都得改。

## 八、如果只做三件事

1. **`user_statement` 进 FTS + 向量**（亲口说的话必须能召回）。
2. **catalog 换成四段式**（范围 / 模态 / 可信度 / 不覆盖）。
3. **`ask.py` 的 `segment` 一路接上向量**（语义问题现在基本查不到）。

这三件都是小改动，收益直接体现在"模型能不能答对"上。
