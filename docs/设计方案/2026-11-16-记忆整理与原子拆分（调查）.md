## 0. 一句话结论

**现在的问题不是"Agent 记性太啰嗦"，而是把别家的整篇记忆文档当成了"一条记忆"导进来。**

实测：记忆库 268 条 / 17.5 万字，其中 **193 条是导入、占 98% 的字数**；84 条超过 1000 字，**全部是导入**；
Agent 自己写的 75 条平均 **39 字**，最长 173 字。也就是说，记忆四层本身没有坏，坏在导入的口径。

`persona-metric`（"一生的记忆库"）已经把这类问题解过一遍。可以借它三条，不必搬它六张表：

1. **一条记忆 = 一个能独立成立的断言**（它的事实层正文 ≤80 字）。
2. **每条断言必须能指回原文**（它用 `seg_ids` + 逐字引文）。
3. **长文不是记忆，是原文档案**：默认不进召回，需要时再查。

### 0.1 目标形态：两层三件事

先给一个能一直朝前走的目标，后面的方案都是为它服务的。

**两层**：

```
原文档案层（memory_documents）
  长文原样存：导入的记忆文件、项目 changelog、一次长对话的整理稿
  默认不进每轮召回；可查看、可核对、可重新拆

原子记忆层（memories）
  一条 = 一个能独立成立的断言（事实 ≤80 字，经历 ≤200 字，偏好 ≤400 字）
  每条带出处：doc_id + quote（原文逐字子串）或会话轮次
  召回只召回这一层
```

**三件事（都归在“整理记忆”一个入口下）**：

| 事 | 方向 | 输入 | 输出 | 人怎么点 |
|---|---|---|---|---|
| **拆** | 纵向：一条内部 | 一条长记录 / 一份原文 | N 条原子事实 + 每条引文 | 一条长记忆点一次 |
| **合** | 横向：多条之间 | 多条重复/近义 | 保留一条，其余标过时 | 一对建议点一次 |
| **退** | 横向：多条之间 | 过时、冲突、被更正 | 标过时（不删） | 一对建议点一次 |

现在的“整理记忆”只做了**合 + 退**；之前说的“原子拆分”是**拆**。它不是“整理”的替代品，而是整理缺的第三条腿。三者共用一个入口，人看到的是同一份“整理报告”，只是分三栏。

### 0.2 你看到的“整理记忆”和“拆成原子”差在哪

| | 现在的“整理记忆”（consolidation） | 之前说的“拆成原子”（atomize） |
|---|---|---|
| 解决什么 | 库**脏**：重复、过时、说法冲突 | 库**胖**：一条 = 半屏文档 |
| 看几条 | 一次看一个 scope 里多条（最近 ≤200 条） | 一次看一条长记录 / 一份原文 |
| 找什么 | “这两条是不是同一件事？哪条更新？” | “这一条里混着几个独立断言？” |
| 输出 | `keepId` / `dropId`（保留谁、下线谁） | N 条原子事实 + 每条 `quote` |
| 对原文 | **不改写、不压缩**，只标过时 | 原文进档案，原子是新记录 |
| 应用后 | 旧记录保留但不再召回 | 长记录归档，N 条原子进召回 |
| 当前代码 | `CONSOLIDATE_PROMPT` 只写 keep/drop | **没有**（这正是缺口） |

拿你库里一条真实记录举例（`ts/apps/server/.data/memory.db`，1985 字，项目 scope）：

> “2026-11-12 桌面端 设置 → 项目 重做为**多根平级模型**……工作区根 = 默认目录；项目 = 平级的附加根……助手物理边界 = 所有已登记且未移除的根之并集……「完全访问」只是审批档，不绕过边界……回滚开关 `PROJECT_OUTSIDE_WORKSPACE=false`……移除项目不连带批量归档普通会话……”

- **现在的“整理”**：如果另有一条讲同一件事，它只会建议“留新的、把旧的标过时”。这条 1985 字的记录本身不会被改变，下一轮还是只能装半条。
- **“拆成原子”**：会拆成 5–8 条，每条 30–80 字、各带原文引文：
  - 工作区根与项目平级，项目可以在任意位置；
  - 助手物理边界 = 所有已登记且未移除的根之并集；
  - “完全访问”只是审批档，不绕过边界；
  - 回滚开关 `PROJECT_OUTSIDE_WORKSPACE=false` 恢复单根；
  - 移除项目不连带归档普通会话；
  - ……
  原文 1985 字进“原文档案”，不再每轮抢预算；召回只拿这 5–8 条短句。

**所以两者不是一回事，也不冲突**：整理管“多条之间的关系”，拆分管“一条内部的结构”。目标形态是让“整理”同时拥有这两把刀。

### 1.2 三个直接结论

1. **"事实类平均 951 字"不是事实层的问题，是导入文档的问题**：155 条 fact 里只有 2 条是原生，正文都是 20 字；
   其余 153 条全是导入的整篇项目记忆。
2. **原生记忆已经是原子的**：75 条非导入记录平均 39 字，最长 173 字（而且最长的是 impression 的 JSON），
   没有一条需要"拆"。`remember` / 抽取链路不需要推倒重来。
3. **导入是唯一的主要矛盾**：193 条导入占 98% 的字数，其中 84 条 ≥1000 字。把导入修好，
   库的体积问题就解决了约 95%。

> **你实际点过的“整理记忆”，现场是这样的**（2026-11-16 核对 `.data/`）：
> `memory-nightly.json` 显示当天 `global` 那次整理 `ok:false, error:llm_failed`；
> `memory-proposals.json` 里唯一待处理建议是某个执事的一条 impression 温度变更（“熟络”→“生疏”）。
> 也就是说：当前整理跑得动的时候，产出也主要是“两条之间保留谁”；84 条长导入从来没有被拆过。
> 这不是你的错觉——“整理”和“拆原子”确实是两件事。

## 2. 根因：导入解析器把"正文"当成了"记忆"

### 2.1 直接原因（一行代码）

`ts/apps/server/src/memory-import-sources.ts:1185`：

```ts
const text = body.trim() || (meta["description"] ?? "").trim();
```

含义：**只要文件有正文，就整篇当一条记忆；frontmatter 里的 `description` 只在正文为空时兜底。**

而 ZCode 记忆文件恰好是"frontmatter 有一句摘要 + 正文是完整说明"的结构。实测本机
`~/.zcode/cli/memories/projects/*/memory/*.md`：

| 指标 | 实测 |
|---|---|
| 源文件数 | 234 |
| 有 `description` 的文件 | **234 / 234** |
| `description` 长度 | 平均 **70.7** 字，中位 65，最长 225；≤80 字的有 186 条，≤120 字的有 217 条 |
| 正文字数 | 平均 **1,857.6** 字，最长 43,284 字 |
| 正文 > 2,000 字（被 `IMPORT_MAX_CHARS` 整份跳过） | **63 个文件** |
| 已被导入的 ZCode 记录 | 154 条 |
| 其中能与源文件正文精确对上的 | **131 条** |
| 这 131 条如果改用 `description` | 合计 **8,528 字**（现在 163,076 字，约 **19 倍**压缩） |

也就是说：同一批源文件，摘要一直在文件头上，导入器没看；63 个更长的文件连导入都没进来。
**改这一处，既能把库缩小约 19 倍，又能多收 63 条来源。**

### 2.2 为什么"整理"救不了

`ts/apps/server/src/memory-consolidate-parse-proposal-json.ts:150` 的整理提示词，任务只有一件事：

> "找出**说的是同一件事、且其中一条明显更完整或更新**的条目对。"

输出只有 `{keepId, dropId, reason}`。所以现在的"整理"只能做**合并/下线**，不能做**拆分/压缩/改类型**。
而且它取的是该 scope **最近 ≤200 条**，最多 50 条建议；84 条长导入里很多是老的，根本轮不到。

### 2.3 为什么"召回预算"装不进去

`ts/apps/server/src/memory-inject.ts` 的默认预算是 **16 条 / 2,000 字**。
一条 951 字的 fact 就吃掉近一半预算，实际一轮只能装 2 条左右。于是出现：

- 库里有 17.5 万字，但每轮只带得动几百字；
- 召回按关键词命中整篇长文，命中"项目"两个字就把整篇 changelog 拉进来；
- 记忆页看起来"很多"，真正能被用上的很少。

### 2.4 为什么拆分现在做不了

`MemoryRecord`（`ts/packages/memory/src/types.ts`）只有 `source: string`，没有"这条记忆来自哪个文件/哪句话"的指针。
模型就算把一条长文拆成 10 条短事实，也无法证明每条来自原文；人也没法核对。
`persona-metric` 的 `seg_ids` + 引文就是为解决这个而存在的。

## 3. `persona-metric` 怎么解的（可借 / 不借）

### 3.1 它的三层

`docs/设计/数据结构设计.md` 与 `db/schema.sql`：

```
L0 原件层（不可变）      L1 片层（唯一工作单元）        L2 要素/事件层
日记 / 对话 / 录音  ──→  segment（片）             ──→  memory（day / event / fact）
                            │                          ├─ entity（人/项目/组织）
                            │                          ├─ event（title + arc + outcome）
                            └─ 每条都能回指原文          └─ tension_pair（张力对）
```

关键口径：

| 层 | 口径 | 实测/出处 |
|---|---|---|
| **L1 片** | 最小可判断单元；只准剪切拼接原文，不得改写；一句话可复述 | 233 篇日记 → 1,351 片，单片中位 **44 字**；纯度 91.7% |
| **L2 事实** | 正文 **≤80 字**；主语是"我"；时间跨度放 `date_start/date_end`，不塞进正文；至少 1 个 `seg_ids`；"拿不准就不写" | `analysis/build_fact_memory.py` |
| **L2 事件** | title + `arc`（立场→触发→新立场），arc 每一条都带 `seg_id/quote`；outcome | `db/schema.sql` 的 `event` |
| **记录类型** | fact / inference / quote / reflection 分开；**推断不能当证据** | `record_claim` |
| **时间真实性** | `event_date`（发生）/ `recorded_at`（写下）/ `ingested_at`（进库）三件事分开；`record_kind = contemporaneous / recalled / reconstructed` | `docs/设计/记忆的时间真实性.md` |
| **检索门** | `ask.py` 只做纯检索，不调模型；按六组返回证据包，并明确说"没查什么 / 没入库什么 / 缺哪几个月 / 不确定什么" | `analysis/ask.py` |
| **生成层** | `answer.py` 四道校验：逐字 / 覆盖 / 依据 / 反向检索 | `analysis/answer.py` |

### 3.2 能搬的三条（也正是当前缺的）

1. **原子单位**：一条记忆只回答一个问题，不把"背景 + 决策 + 实现 + 验证 + 刻意没做"塞进一条。
2. **证据指针**：每条原子记忆带 `quote`（必须是原文的逐字子串）和来源（文件 + 偏移 / 会话 + 轮次）。
   模型拆出来的东西如果找不到原文，就不准落库。
3. **文档与记忆分层**：长文进"原文档案"，不参与每轮召回；原子事实进记忆层，参与召回。
   召回装不下时，牺牲的是细节的自动出现，不是细节本身。

### 3.3 不搬的（刻意）

| 不搬 | 原因 |
|---|---|
| 六套表全量（segment / event / entity / catalog / tension_pair / time_axis） | 那是**离线人生档案分析**的模型，不是每轮对话的 hot memory；harness 里重建等于把 persona-metric 抄一遍 |
| 向量 / FTS + RRF / LLM 重排 | persona 的检索门是"批量取证据 + 分组统计"，harness 的召回是"这一轮该想起哪几条"，目标不同 |
| 事件 arc / 张力对 / 月度时间轴 | 当前没有产品入口消费它们；先不做，避免"看不懂的表" |
| 把 harness 记忆写进 persona.db | persona 没有 partner/project 的键空间隔离，跨仓库写还会破坏隐私边界；现状是单向导出（`persona-export`）+ 只读查询（`persona_recall`），这个分工保持不变 |
| 自动应用 / 自动删除 | D18 不变：模型只出建议，人逐条应用 |

> 补充：harness 已经有 `persona_recall`（`ts/apps/server/src/persona-ask.ts`）作为"一生库"的只读入口。
> 它是**冷库**；本次要修的是**热记忆**，两者不是替代关系。

## 4. 方案对比

### 方案 A：只改导入映射（零 schema）

**做法**：导入文件有 frontmatter `description` 时，用 `description` 当记忆正文；正文留在源文件里（或存路径）。
`IMPORT_MAX_CHARS` 从"正文上限"改成"摘要上限"。

| 优点 | 缺点 |
|---|---|
| 半天到一天；无 schema、无迁移框架 | 原文细节不在记忆库里，Agent 查不到；只能靠源文件 |
| 立刻把 154 条 × 1,059 字降到约 70 字/条 | 对不上源文件的 23 条无法处理；未来非 frontmatter 来源仍可能进来长文 |
| 63 个被 2,000 字上限挡掉的文件可以进来 | 没有证据指针，无法做"语义拆分" |

**定位**：止血，不是完整方案。

### 方案 B：两层存储（推荐）

**做法**：
- 新增 `memory_documents`：存长文原文（title / content / source / source_ref / sha256 / scope）。
- `memories` 增列：`doc_id`（指向原文）、`quote`（逐字证据）、`quote_start/quote_end`、`archived_at`。
- 导入：**摘要进 memories，正文进 documents**；摘要优先用 frontmatter `description`，没有才用正文首句/标题。
- 整理：新增"拆分"建议——模型把长文拆成 1–6 条原子事实，每条带 `quote`；人逐条应用（按"一条长记忆"为单位，不是按每个原子）。
- 召回：只召回原子记忆；documents 默认不进注入，记忆页可查看原文。

| 优点 | 缺点 |
|---|---|
| 借到 persona 的核心（原子 + 证据 + 文档分层），不搬六张表 | 比 A 多 2–4 天；要加表和 UI |
| 不丢细节；可核对、可回退、可重新拆 | 迁移 154 条要做一次 dry-run 和确认 |
| 未来任何长文导入都有统一落点 | 拆分建议仍要人点（D18），不能一键全应用 |

### 方案 C：全量三层（照搬 persona-metric）

加 segment / event / entity / tension / time_axis / 向量检索。

| 优点 | 缺点 |
|---|---|
| 能力最全，能回答"那段时间发生了什么" | 1–2 周以上；与 persona-metric 重复；harness 当前没有消费入口 |
| | 会把"记忆整理"变成"重建一个人生档案库"，偏离当前需求 |

**不推荐**。

### 方案 D：外接 persona-metric 当冷库

harness 只留热原子记忆；旧事/长文走 `persona_recall`。

| 优点 | 缺点 |
|---|---|
| 复用现成的一生库；不重复建 | persona 没有 partner/project 隔离；`ask.py` 是本地 Python 子进程（约 0.7s）；不能替代作用域记忆 |
| 已有 `persona_recall` 通道 | 解决不了导入把项目文档塞进 memory.db 的问题 |

**定位**：作为补充保留，不作为主方案。

## 5. 推荐：方案 B，分三步落地

### 5.1 第一步：停血（导入改口径）

- 文件类来源，若 frontmatter 有 `description`：
  - `memories.content = description`（≤200 字；preference 可放宽到 400 字，保留 `Why / How`）；
  - `memory_documents.content = body`（完整正文，过同一套打码）；
  - `source_ref = 源文件绝对路径`，`sha256 = 正文哈希`。
- 没有 `description` 的来源：
  - 已经是 `section / headings / index` 切分的，按切分单元照旧；
  - 单个单元 >300 字时，用标题/首行当摘要，正文进 documents。
- `IMPORT_MAX_CHARS` 只管摘要；正文进 documents 不受这个上限限制（但仍受 `MAX_SOURCE_BYTES` 文件大小保护）。
- 开关：`MEMORY_IMPORT_ATOMIC`（默认开）；`false` = 逐字节回到"正文即记忆"的旧行为。

### 5.2 项目 changelog 的特殊处理（用户已拍板：项目记忆要进，但特殊处理）

项目记忆要不要进，不按“导入来源”一刀切，按**员工/负责项目的勾选**走——现有的项目匹配规则不变。
但“项目 changelog”不能整篇当原子记忆，因为它混着两类东西：

| 内容 | 例子 | 去处 |
|---|---|---|
| **可复用口径** | 怎么构建 / 怎么部署 / 踩过的坑 / 约束 / 用户拍板的决定 | **原子记忆**（项目 scope） |
| **发生过什么** | “2026-11-12 完成 X，改了 12 个文件，测试 783/783” | **原文档案**（项目 scope） |

ZCode 的记忆文件恰好自带这个分层：

```markdown
---
name: ...
description: 一句话摘要（平均 70 字）
metadata:
  type: project | feedback | reference
---
正文：背景 / 做了什么 / 为什么 / 怎么应用
```

所以项目 changelog 的导入按这个映射，**机械解析、不调模型**：

- **原子** = `description` + 正文里的 `**Why:**` / `**How to apply:**`（有就带，没有就只用 description）；
- **原文** = 完整正文（含 changelog 叙事），进 `memory_documents`；
- **scope** = 沿用现有项目匹配结果（命中登记项目 → `project:<uuid>`；否则 global +【项目名】）；
- 一条文件默认产 **1 条原子**；如果 `description` 本身超过 120 字或含多个 `；` 分句，再走“拆分”把它拆成 2–4 条（这一步才需要模型/人工确认）。

这样既满足“项目记忆要进”，又不会把 changelog 叙事塞进每轮召回。
`feedback` / `user` 类型的文件（偏好/教诲）走同一套：原子保留规矩 + Why/How，正文进档案。

### 5.3 第二步：迁移现有 154 条

这是**机械迁移**，不是模型建议，所以不需要走 D18 的"逐条应用模型建议"：

1. 备份 `.data/memory.db`（时间戳副本）。
2. dry-run：按规范化正文匹配源文件（实测 131/154 能精确对上）。
3. 匹配上的：
   - 建 document（正文 + 路径 + sha256）；
   - 把 memory 的 `content` 换成 `description`，写 `doc_id`；
   - 保留原 `createdAt / importance / recallCount`。
4. 对不上的 23 条：列清单，不自动动；人可以手工标过时或后续单独处理。
5. 63 个曾被 2,000 字上限挡掉的文件：用同一套导入重新收一遍（摘要进 memories，正文进 documents）。
6. 成果预览给用户确认一次（"131 条换摘要 + 131 份原文档案；23 条待处理；新增 63 条"），确认后执行。
7. 可回退：documents 保留原文；备份可整库恢复。

> 如果用户不接受"一次确认"，退化做法：只改未来导入，旧的 154 条逐条人工处理。效果会慢很多。

### 5.4 第三步：整理里加"拆分"（语义）

只对 **>200 字** 的记录（未来主要是异常长文；当前迁移后应剩很少）出拆分建议：

- 模型输出 1–6 条：`{content, quote, kind?}`。
- 硬校验（照 persona 的引文校验）：
  - `quote` 必须是原文的逐字子串（归一化后匹配，记录 `quote_start/quote_end`）；
  - `content` 上限：fact ≤80 字、episode ≤200 字、preference ≤400 字（含 Why/How）；
  - 原文里没有依据的断言直接丢弃；"拿不准就不写"；
  - 不允许把推断写成 fact（`veracity` 保持 `imported` / `inferred`，不升 `stated`）。
- 应用粒度：**一条长记忆 = 一次确认**。预览左边原文、右边 N 条原子；点"应用这条拆分"后：
  - 建 document（原文）；
  - 建 N 条原子记忆（带 `doc_id` + `quote`）；
  - 原长记录 `archived_at`（不删，可回滚）。
- 合并建议保持现状（keep/drop），和拆分并列显示。
- 夜间整理也可以生成拆分建议，但仍只出建议，不自动应用。

### 5.5 可选：结构字段（不阻塞主线）

- `event_date / date_start / date_end`：如果以后要回答"这事什么时候发生的"，再把时间从正文里拿出来；
  当前项目记忆的正文里日期是重要的，先保留在 `content` 里，不强行拆。
- `subject / entities`：先不做；等有"按人/项目查记忆"的明确需求再立项。
- `catalog / coverage`：记忆页可以先加一个"库的边界"统计（多少条、多少字、最长几条），
  不做完整的目录表。

## 6. Schema / API 草案

### 6.1 存储

```sql
CREATE TABLE IF NOT EXISTS memory_documents (
  id          TEXT PRIMARY KEY,
  scope       TEXT NOT NULL,
  title       TEXT,
  content     TEXT NOT NULL,
  source      TEXT NOT NULL,      -- import:zcode-projects / conversation / manual
  source_ref  TEXT,               -- 文件路径 / 会话 id / 轮次
  sha256      TEXT,
  chars       INTEGER,
  created_at  TEXT NOT NULL,
  updated_at  TEXT
);
CREATE INDEX IF NOT EXISTS idx_memory_documents_scope ON memory_documents(scope, created_at);

ALTER TABLE memories ADD COLUMN doc_id TEXT;
ALTER TABLE memories ADD COLUMN quote TEXT;
ALTER TABLE memories ADD COLUMN quote_start INTEGER;
ALTER TABLE memories ADD COLUMN quote_end INTEGER;
ALTER TABLE memories ADD COLUMN archived_at TEXT;
```

迁移沿用 `store-sqlite-memory-store.ts` 的 `ensureColumns()` 模式（`PRAGMA table_info` + 缺列才 `ALTER`），
不引入迁移框架。

### 6.2 接口

- `GET /api/v1/agent/memory`：形状不变；`items[]` 增加可选 `docId`、`archivedAt`（老客户端忽略）。
- 新增 `GET /api/v1/agent/memory/documents?scope=&limit=&offset=`：只读原文档案列表（不含 content 全文，列表给 title/chars）。
- 新增 `GET /api/v1/agent/memory/documents/:id`：读一份原文。
- 整理：`POST /api/v1/agent/memory/consolidate/review` 响应增加可选 `splits[]`；
  新增 `POST /api/v1/agent/memory/consolidate/split/apply`（一次应用一条拆分）。
  老字段 `proposals[]` 不变，旧页不受影响。

### 6.3 开关与回滚

| 开关 | 默认 | 作用 |
|---|---|---|
| `MEMORY_IMPORT_ATOMIC` | 开 | 导入时摘要进 memories、正文进 documents；`false` 回旧行为 |
| `MEMORY_SPLIT_REVIEW` | 开 | 整理时额外生成拆分建议；`false` 只剩合并/下线 |
| `MEMORY_DOCUMENTS` | 开 | 原文档案的读写端点；`false` 404，记忆层不受影响 |
| `MEMORY_ATOMIC_MAX_CHARS` | 200 | 导入摘要上限；`0` = 不截断（回旧形态） |

### 6.4 召回与注入

- `recall()` 候选只收 `archived_at IS NULL` 的原子记忆。
- documents 不进候选、不进注入。
- 维持 16 条 / 2,000 字预算；原子化后同样的预算能装 10–20 条，而不是 2 条。
- `recall` 工具的输出格式不变（仍是一行一条），不新增工具、不改工具描述，避免打掉缓存前缀。

## 8. 刻意不做

- **不自动应用拆分、不自动删除**（D18）。语义拆分永远人点；机械迁移只做一次确认。
- **不在 harness 里重建 persona-metric 六张表**；`persona_recall` 继续当冷库入口。
- **不引入向量 / LLM 重排**；当前召回问题不是排序，是条目太长。
- **不改造原生 `remember` / 抽取**：实测原生记忆平均 39 字，已经是原子的；最多在工具描述里补一句"一次记一条"。
- **不做事件层 / 实体层 / 张力对**：没有消费入口，先不立。
- **不碰 partner / project 的隔离边界**：导入只按现有项目匹配规则落 scope。
- **不做"全部应用"**：拆分按"一条长记忆"应用，仍不是按整库。

## 9. 已拍板与剩余问题

### 已拍板（2026-11-16）

1. **路线 B**：原文档案 + 原子事实两层，整理入口下同时有“拆 / 合 / 退”。
2. **迁移**：dry-run 预览后一次确认，不逐条点；对不上的 23 条列清单不动。
3. **项目 changelog**：仍然进项目记忆（按员工/负责项目勾选走），但特殊处理——摘要 + Why/How 进原子，完整正文进原文档案。

### 剩余问题（实施前定）

1. **原文档案要不要给 Agent 查？** 推荐先只给人看（记忆页），Agent 仍只吃原子事实；以后需要再加只读工具。
2. **对不上的那 23 条怎么处理？** 推荐先列清单、不自动动；人可以单独标过时或手工补摘要。
3. **拆分用哪个模型、什么预算？** 复用 `AUX_MODEL_REVIEW` / 当前整理模型；一次只喂一条长文，单次超时 30s，失败不落库。
4. **“全部应用”是否永远不做？** 保持 D18：拆按“一条长记忆”应用，合/退按“一对”应用；没有整库一键应用。
