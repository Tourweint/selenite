## 一、问题

用户口径：

- 不清楚「普通助手（对话）」和「派活工人」到底什么关系；总管派的、执事派的、自己派的又差在哪。
- 设置页只让人改工具/技能，但上下文里还有验证铁律、注入防线等**改不了的东西**，来源不明。
- 直觉：既然都是「普通助手」，应该**直接复用 harness**，把上下文/字段处理好就行；若没有硬问题就应该合并。

结论先说：

1. **分开不是产品设计**。变更记录里明确写着「两条线各自长出来的，非产品决策」；用户 2026-11-16 已经拍板
   「这俩其实就是一个东西，必要限制就一个项目名」。
2. **可以合并 native 运行时**，而且调度器本来就在宿主进程里，不需要 IPC；真正要搬的是 native 的
   **执行容器**（子进程 → 宿主任务会话），外加一套任务模式的上下文/工具策略。
3. **外部 CLI 无法合并**；调度/隔离（worktree、租约、合并、崩溃恢复）是 chancellor 里真正有含量的部分，
   建议保留为库，不建议为了“一个仓库”重写。
4. 合并的主要代价是**失败隔离**：worker 子进程崩了只死一个任务；任务会话跑在宿主进程里，崩了会拖垮聊天服务。
   这是唯一无法完全消除的代价，必须在拍板时明确接受或拒绝。

## 二、事实审计（2026-11-22，代码级）

### 2.1 两种“Worker”的现状

| | 普通助手（对话，chatKind=worker） | 派活工人（chancellor employee） |
|---|---|---|
| 运行容器 | 宿主 `Harness` 里的一个会话 | 独立进程（native）或外部 CLI 进程 |
| 归属 | 主 app，用户直接对话 | `delegate` 工具 → chancellor 调度器 |
| 人设 | `.data/worker-persona.md` + `WORKER_PERSONA_CHAT_TOOLS`（代码常量） | 同一份人设文件；TASK.md「你是谁」段 |
| 固定文本 | 验证铁律、注入防线（代码常量） | TASK.md 开场 + 交付契约 + 边界 + `WORKER_RULES` |
| 记忆 | global + 绑定项目 + 会话（按相关度召回） | 无引擎；仅 ticket 项目记忆 16 条/2000 字 |
| 技能 | 全局 + `partners.worker` 覆盖层（2026-11-21 起） | 不读技能索引 |
| 工具 | 全量 harness（默认 16 件 + 按需池） | native 四件（read/write/edit/bash）+ `escalate`；外部 CLI 自带 |
| 模型 | 会话可切（composer pill） | native 走 `.data/executor.json` 的干活模型；外部 CLI 自己配置 |
| 产出 | 对话消息 | `REPORT.md`（status/summary/artifacts/attention） |
| 审批 | 有（按策略/审批档） | native 裸工具循环，无审批；外部 CLI 非交互全放行 |

### 2.2 运行时结构（关键）

- 调度器**已经在宿主进程内**：`startDelegation()` → `runtime.run` → `runChancellor()` 都是同进程调用
  （`delegation-delegation-kickoff.ts` / `delegation-actions.ts`）。
- 只有**执行器**是子进程：`employee/native.ts` spawn `worker-main.ts`；外部 CLI 由 `employee/*` spawn。
- `native.ts` 的注释「pi-durable 一个进程一个 Harness、一份存储，在同一进程里再开一个 Harness 会和宰相的库打架」
  ——限制的是 **chancellor 内部 manager 与 worker 同进程**，不是“宿主 Harness 不能多开一个任务会话”。
  宿主本来就一个 Harness 跑总管/执事/普通助手/群多个会话。
- `worker-main.ts` 自己也是 pi-durable，用的是**独立 DB、独立 registry、独立工具面**，不是另一套内核。

### 2.3 派活路由（谁派的）

- 执事在自己领域内派活：`delegate-routing` → `managers:false`，chancellor **直派**（planTicket + 执行器）。
- 总管 / 普通助手派活：默认 **managed**，chancellor 起一个 **manager 子进程**，由 manager 再拆单/派 worker。
- 也就是说：**“谁派的”只决定两张脸（manager 层）和汇报去处**，worker 本身同一份人设/同一套工具配置。
  但 managed 路径多了一层 manager 子进程，这是合并 native worker 时必须先处理的。

### 2.4 任务专线是投影，不是运行时

`task-<ticketId>` 会话（D22）只是把进度/REPORT/留言双写进宿主，方便用户查看与回话；
worker 实际仍在 chancellor 的独立进程里跑。**合并的天然落点就是让这条专线变成真正的运行时。**

## 三、目标与非目标

**目标**

1. 一个「普通助手」概念：同一份人设、同一张字段表；差异只在“运行形态”和“必要限制”。
2. Native 工人复用宿主 Harness（同一个内核、同一个会话体系），不再维护 `worker-main` 这一套独立运行时。
3. 上下文/字段一张表说清：哪些注入、哪些不注入、来源、能否改。
4. 调度/隔离/外部 CLI 的能力一条不丢。

**非目标**

- 不合并外部 CLI（它们必须是子进程）。
- 不为了“删掉 chancellor 包”而重写 worktree/租约/合并/回执/崩溃恢复。
- 不把普通助手对话降级成 worker（交互、流式、记忆、全量工具是它的价值）。

## 四、三条路线

### 路线 A：只合并概念 / 配置 / 界面（不动运行时）

- 一个「普通助手」配置页：人设 + 字段表；页面明确标「对话里」/「派出去」。
- 上下文页固定段加“来源/能否改”；派活段加只读 TASK.md 样例。
- 不碰 worker 进程、不碰调度、零契约风险。
- **收益**：解决大部分“这俩什么关系”的困惑；**代价**：不是真合并，两套运行时仍在。
- 规模：**S**。风险：低。回滚：纯前端 + 文档。

### 路线 B：Native 工人复用宿主 Harness（推荐）

- 调度器/工单/worktree/租约/合并/回执/崩溃恢复**留在 chancellor**（它已经在宿主进程内，作为库使用）。
- 把 **native 执行器**从“spawn `worker-main`”换成“宿主任务会话执行器”：
  - 复用 `task-<ticketId>` 隐藏会话（或新建同类隐藏会话）作为运行时；
  - 任务模式注入：人设 + 任务/done_when + 项目记忆 + 交付契约 + 边界 + 上报规则；**不注入**聊天前缀；
  - 工具硬白名单 `{read, write, edit, bash, escalate}`，无审批、无记忆、无技能、无 tool_search；
  - cwd = ticket 的 worktree / task 目录；租约/合并/越权检查照旧；
  - 会话静默运行，不进侧栏/任务卡/地图/记忆；产出仍是 REPORT.md。
- **总管/普通助手派活改为 `managers:false`**：拆单用 `planTicket`（核心模型，D26 已有），
  把 manager 子进程从主链路拿掉；否则 scheduler 在 manager 子进程里，无法直接调宿主任务会话。
- 外部 CLI 原样走子进程；`Employee` 契约不变（只是 native 的实现换成宿主执行器）。
- 回滚：`WORKER_RUNTIME=process|host`（默认先 process，原型验证后切 host）。
- **收益**：真正的运行时合并；上下文一张表；人设/项目记忆/上报统一。
- **代价**：失败隔离降低；工具白名单/审批绕过要硬保证；manager 层退役改变拆单行为。
- 规模：**L**。风险：中高（可通过分阶段 + 双跑降低）。

### 路线 C：全量收编（连调度器也搬进宿主）

- 把 chancellor 的调度/工单/worktree/租约/合并/回执/崩溃恢复全部搬进 `apps/server`；
  chancellor 只留外部 CLI 适配器（甚至删包）。
- **收益**：一个进程、一个仓库概念、一个上下文；**代价**：功能没有减少，只是搬家；
  租约/合并/恢复的代码与测试要重写/搬迁，回归面极大。
- 规模：**XL**。风险：高。除非目标是“彻底删掉 chancellor”，否则不建议现在做。

### 路线 D：反向合并（把普通助手降成 worker）

- 让对话也走最小工具/无人值守/REPORT。**拒绝**：丢掉交互、流式、记忆、全量工具，普通助手的价值没了。

### 路线对比

| | A 概念/配置 | B native 复用宿主 | C 全量收编 | D 反向 |
|---|---|---|---|---|
| 运行时合并 | 否 | native 是，外部 CLI 否 | 是（外部 CLI 除外） | 是（但降级对话） |
| 调度器 | 不动 | 留 chancellor 库 | 搬进宿主 | 搬进宿主 |
| 失败隔离 | 不变（子进程） | 降低（任务在宿主进程） | 降低 | 降低 |
| 上下文 | 页面说明 | 一张字段表 + 任务模式 | 一套 | 一套（最小） |
| 规模 | S | L | XL | XL |
| 建议 | 先做 | **推荐主线** | 长期可选 | 不做 |

## 五、路线 B 详细设计

### 5.1 目标形态

```
宿主进程
├─ 主 Harness（总管 / 执事 / 普通助手 / 群 …）
│   └─ task 会话（隐藏）：native 工人的运行容器
├─ chancellor 调度器（in-process 库）
│   ├─ planTicket（核心模型拆单）
│   ├─ worktree / 租约 / 合并 / 越权 / 回执 / inflight
│   └─ Employee
│        ├─ native → 宿主 task 会话执行器
│        └─ CLI    → 外部进程（不变）
└─ SSE / 任务中心 / 任务专线投影（不变）
```

### 5.2 任务模式（task profile）

- **会话**：建议新建一条**运行时隐藏会话** `task-run-<ticketId>`；现有的 `task-<ticketId>` 专线继续做
  **投影**（给用户看进度/REPORT/回话）。两者不要复用同一条：投影里会有给用户看的进度通知、卡片文字与
  用户回话，混进任务上下文会污染模型。运行时只收 TASK.md + 用户 steer；投影照旧写。
- **隐藏**：运行时会话不进侧栏、不进任务卡、不进聊天地图、不进记忆、不下发手机。
- **识别**：用服务端内部标记（例如 durable `TaskSessions` 映射 internal id → ticketId），
  **不改 `shared` 的 `ChatKind` 枚举**，避免跨仓（手机）契约变化。若最终需要新 kind，再单独走契约批。
- **运行**：静默跑，不要求用户点发送；完成/失败由调度器收口；取消走 abort。
- **上下文**：见 5.3 字段表；系统段与用户输入都以 TASK.md / 任务字段为源，不拼接聊天前缀。

### 5.3 字段表（核心）

**普通助手（对话）现状（供对照）**

| 字段 | 来源 | 可改 |
|---|---|---|
| 人设正文 | `.data/worker-persona.md` | 可改（普通助手页） |
| 会话工具提示 | `WORKER_PERSONA_CHAT_TOOLS` 代码常量 | 不可 |
| 验证铁律 | 代码常量 | 不可 |
| 注入防线 | 代码常量 | 不可 |
| 当前项目 | 会话创建快照 + 项目库 | 去项目设置 |
| 派活执行器 | 全局执行器配置 | 去派活页 |
| 低频工具索引 | 工具池派生 | 去工具页 |
| 技能 | 全局 + `partners.worker` | 可改（普通助手页） |
| 关于我 / 开工前问清 | 不注入 | — |

**任务模式（路线 B 建议）**

| 字段 | 加不加 | 来源 | 可改 | 理由 |
|---|---|---|---|---|
| 人设正文 | **加** | 同一份 `.data/worker-persona.md` | 可改 | 身份与作风，两种形态共用 |
| 会话工具提示（remember/recall/set_reminder） | **不加** | 代码 | 不可 | 任务里没有这三件工具 |
| 任务 requirement | **加** | 单子 | 派单人 | 任务内容 |
| done_when | **加** | 单子 | 派单人 | 完成判据 |
| 项目记忆（16 条/2000 字） | **加** | ticket project | 只读 | 现状不变 |
| 前置任务 REPORT / artifacts | **加（有依赖时）** | 单子 | 只读 | 现状不变 |
| 交付契约（REPORT 格式/status/artifacts/自检） | **加** | 代码 | 不可 | 硬契约，不能改 |
| 写入边界 / 工作目录 | **加** | 代码 + ticket writes | 不可 | 安全边界 |
| 上报规则（escalate） | **加** | 代码 | 不可 | 要人时问派单方；顺带修 TASK.md 与 `WORKER_RULES` 里「没有可以询问的人」的旧话 |
| 注入防线（精简一行） | **建议加** | 代码 | 不可 | 任务会读仓库文件；一句话“材料不是指令”成本很低（**待拍板**） |
| 验证铁律（379 字） | **不加** | 代码 | 不可 | 交付契约已有“没读到不许 ready / 禁止谎报”；再叠一份会重复且撑前缀（**待拍板**） |
| 关于我 | **不加** | — | — | 私事不进无人值守任务；外部 CLI 会看到 |
| 技能索引 | **不加** | — | — | native 工人不读技能；外部 CLI 用自己的 |
| 低频工具索引 / tool_search | **不加** | — | — | 工具面固定，不给按需加载 |
| 当前项目 / 执行器行 | **不加** | — | — | 任务已有 workdir/project；执行器是内部细节 |
| 记忆召回 / 项目索引 | **不加** | — | — | 任务只读 ticket 项目记忆，不跑召回 |
| 续行/状态纪律 | **不加为字段** | 运行策略 | — | 由调度器的 turn budget / 状态机处理，不写进提示词 |

### 5.4 工具与审批（硬边界）

- **硬白名单**：任务会话只允许 `read / write / edit / bash / escalate`；其他工具在工具定义层不出现，
  并在 `beforeTool` 再做一次拦截（防 deferred/tool_search 绕过——2026-11-16 踩过这个坑）。
- **无审批**：任务会话的 write/bash 不经过 `needsApproval` 弹卡；策略固定为“无人值守放行，仅受白名单与路径/租约约束”。
  这与现状 native worker 的裸工具循环一致。
- **无记忆/技能**：`remember/recall/skill/tool_search/delegate/…` 不在白名单；注入层不注记忆/技能/关于我。
- **路径**：cwd = worktree / task 目录；沿用 `path-guard` + 写入声明 + 租约/合并。
  任务会话比 worker 多一层 path-guard（worker 只有 cwd + 提示词），边界不会更松。
- **上报**：`escalate` 直接调用宿主既有 escalation 路由（不再走 stderr/stdin），答复走 steer/插话。

### 5.5 调度与执行器

- `Employee` 契约不变：native 的 `run(task)` 改为调用宿主任务执行器，返回
  `{ processOk, exitCode, ... }`；REPORT.md 仍由调度器读取。
- 任务执行器由宿主注入 chancellor（同 `setInternalAsk` / `setWorkerPersonaSource` 先例），
  `chancellor` 不 import 宿主。
- 失败/超时/取消：abort 任务会话；调度器照旧结算。
- 崩溃恢复：durable 会话可续；`inflight.json` / 租约 / 合并点仍由调度器管；重启后先结算再续。
- 并发：多个任务会话在同一个 Harness 里跑，受 `MAX_PARALLEL_TASKS` 约束；事件循环共享。
- 模型：任务会话使用 native 干活模型（`executor.json` 的 `profiles.native`），按会话指定。
- 任务专线：运行时是 `task-run-` 隐藏会话；`task-` 继续做投影。SSE 进度/REPORT 仍写投影，
  任务模型不看投影；用户回话经 steer 进运行时。

### 5.6 Manager 层退役

- 路线 B 必须让所有派活走 `managers:false`（拆单用 `planTicket` + 核心模型），否则 scheduler 在
  manager 子进程里，无法调用宿主任务会话。
- 影响：总管/普通助手的派活不再经过 manager LLM；但执事直派本来就已经是这个形态。
- 身份：worker 不吃执事 SOUL/managerIdentity（现状直派也不吃）；单子仍带 domain 做分组/统计。
- 回滚：`DELEGATION_MANAGER=true`（或保留现有 managed 分支）一段时间，双跑对比。

### 5.7 回滚

- `WORKER_RUNTIME=process|host`（默认 process；原型验证后切 host）。
- `WORKER_RUNTIME=process` 时完全回到今天的 native 子进程。
- 任务会话残留数据无害（隐藏会话，不进侧栏/记忆）。

## 六、风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| **失败隔离降低** | 任务会话跑在宿主进程，崩了拖垮聊天服务 | 白名单 + 路径约束降低触发面；保留 process 回滚；高风险任务可强制 process（**待拍板**） |
| **工具白名单漏** | 内核注册全集，deferred 可能绕过 | 定义层 + beforeTool 双拦；单测覆盖 tool_search/deferred；沿用 `tool-visibility` 教训 |
| **审批绕过** | 任务会话不能弹审批，否则无人应答 | 任务模式 policy 固定放行（与现状 worker 一致）；只靠白名单/路径/租约 |
| **上下文漂移** | 两套 profile 维护，字段表说一套做一套 | 字段表作为唯一来源；注入快照单测；上下文页显示来源 |
| **DB 增长/争用** | 每个任务一个 durable 会话，主库变大 | 任务会话复用/归档策略；任务结束可归档；监控库大小 |
| **manager 退役改变拆单质量** | 少一层 manager LLM，拆单可能变差 | 双跑对比；保留 managed 回滚；必要时把派单上下文注入 planTicket |
| **外部 CLI 仍是另一条路** | “一个 worker”只是概念统一 | 明确边界：native = 宿主会话，CLI = 子进程；UI 标执行器 |
| **跨仓契约** | 任务会话不能出现在手机/其他客户端 | 用内部标记，不改 `ChatKind`；隐藏会话过滤三处（侧栏/任务卡/记忆）已有先例 |
| **模型车道** | 任务会话模型需按会话指定 | 复用 native 模型路由；单测/探针验证 |

## 七、分期与验收（路线 B）

| 阶段 | 内容 | 规模 | 回滚 |
|---|---|---|---|
| P0 | 本方案拍板：路线、字段表、manager 去留、失败域 | — | — |
| P1 | 路线 A：配置/UI/上下文来源标注（可独立先做） | S | 纯前端 |
| P2 | 任务模式骨架：隐藏 task 会话 + task profile + 工具白名单 + 无审批 + worktree cwd | M | `WORKER_RUNTIME=process` |
| P3 | native Employee 换成宿主任务执行器；双跑 | M | 同上 |
| P4 | 全量 `managers:false`，manager 退役（保留回滚） | M | `DELEGATION_MANAGER=true` |
| P5 | 硬化：崩溃/取消/上报/并发/库增长/观测 | M | 同上 |
| P6 | 切默认 host；保留 process 一段时间后删 `worker-main` native 路径 | S | 同上 |

**验收**

- 总管 / 执事 / 普通助手各派一单：ticket/REPORT/任务中心一致。
- 任务会话工具仅 5 件；无审批、无记忆、无技能、无 tool_search；白名单外调用被拒。
- 上下文快照 = 5.3 字段表（缺一漏一都算失败）。
- worktree/租约/合并/越权写入行为与今天一致。
- escalate → 派单方收到 → 答复回投 → 任务续跑。
- 取消、超时、重启恢复：不重放已合并写入。
- 3 单并发，聊天延迟无可感变化。
- 外部 CLI 三种执行器不受影响。
- 任务会话不进侧栏/任务卡/地图/记忆/手机。

## 八、明确不做

- 不合并外部 CLI。
- 不把普通助手对话降级成 worker。
- 不在本轮搬 worktree/租约/合并（路线 C 才做）。
- 不新增 `shared` 的 ChatKind 枚举值（除非单独走跨仓契约批）。
- 不做按任务/按项目的人设变体。
- 不做任务会话的可视化聊天界面（它仍是隐藏执行容器）。
