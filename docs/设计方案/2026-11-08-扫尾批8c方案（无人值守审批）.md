# 扫尾批 8c 方案：无人值守审批（等待态落库，答复触发续跑）

> 状态：**方案设计完成，待批 8b（agent.ts 拆分）落地后实施（动同一批文件）**。上位：扫尾计划 A12（用户拍板做）。
> 形态出处：批次二细化 §六升级路径（登记在案）——"等待态落库成一行记录，本轮正常收尾、零进程零 token；答复作为事件触发续跑"。

## 一、现状与痛点

`confirmWrites` 开启时，写工具执行前挂起审批：**当前工具回合阻塞等待** 120s（`AGENT_APPROVAL_TIMEOUT_S`），超时默认拒绝。人不在场 = 全部拒绝；等待期还占着一个活着的 run（进程与 token 都在）。

## 二、新形态（答复触发续跑）

1. **遇审批不再阻塞**：beforeTool 拦到需审批工具 → 落 pending 审批记录（approvals.json 既有设施：callId/toolName/args 摘要/conversationId）→ **对该工具调用回拒绝性答复**（"该操作等待用户批准，批准后我会继续"）→ 本轮照常收尾（run 结束，零挂起）。
2. **pending 永不过期**：等待态落库的本意就是"人随时回来批"。启动遗留 pending 不再置 timeout（保留可答）；审批卡 UI 去掉倒计时、显示"等待处理"。旧 120s 行为整体退役为回滚形态。
3. **approve → 触发续跑**：服务端向该会话自动提交一条 followUp 指令（"用户已批准 `<tool>`：`<args摘要>`——立即重新发起同一个工具调用"），模型下一轮重发该调用 → 闸门查**一次性放行清单**（`approved:{callId}` → tool+args 哈希，命中即放行并核销）不再拦。
4. **reject → 同样触发续跑**：followUp 指令告知"用户拒绝了 `<tool>`：请继续其余工作"——模型不卡死，转做能做的。
5. **防骗**：放行清单按 callId 核销、只对同 tool+args 哈希生效；模型换个 args 重发 = 重新走审批（不许"批了 A 执行 B"）。

## 三、权衡与决策（写明取舍）

- **"模型重发调用"而非"工具结果回填"**：后者要内核支持向已收尾的 run 回填工具结果（1.4.0 无此口）；前者零内核改动、可靠，代价是每次批准多一轮模型调用（重发+继续）。选前者——ZCode 的答复续跑同款形态。
- **pending 无限等待 vs 保留超时**：等待态落库的前提就是"人不在场"，无限是语义必然；积压风险由"待批列表永远可见 + 用户可批量拒绝"兜住。回滚开关 `AGENT_APPROVAL_MODE=blocking` 回到 120s 阻塞形态（默认即新形态）。
- **手机端零改动**：答复链路（轮询+弹窗）原样复用；弹窗倒计时文案随投影自适应。

## 四、验证

- 探针（approval 探针扩展）：①审批不再阻塞本轮（本轮正常收尾、pending 落库）；②approve → followUp 自动提交 → 模型重发 → 放行清单核销放行 → 执行落地；③换 args 重发 → 重新审批（防骗）；④reject → 模型继续别的工作；⑤重启后 pending 仍在且可答（不再 timeout）；⑥`blocking` 回滚形态全绿（旧行为一字不变）。
- 单测：放行清单核销/哈希匹配/幂等。
- 真模型手验（派单人）：真跑一轮带写工具的对话，网页批准后看续跑。
