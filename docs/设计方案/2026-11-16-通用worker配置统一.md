# 方案：通用 worker 配置统一（派活工人与普通助手同源）

**状态**：设计期 → 2026-11-16 批1–3 + 2026-11-17 批4 已全部落地；结论下沉 `系统架构.md` D27、接口文档主册 env 表与分册4 §2.11 / 分册7 §2.23，冲突以长期文档为准。
**批4 增补（2026-11-17 用户翻案）**：原「明确不做」里的 worker 工具勾选被翻案——做，但只限**本机 native 工人**（canonical 四件、取消名单、`--tools` 下发；外部 CLI 不碰，用户拍板"人家自己带记忆，把任务发好就行"）；「派单时指定工具」（per-dispatch）仍刻意没有，理由与未来扩展点（`EmployeeProfile.tools`）记在 D27。
**审计基准**：2026-11-16 全量代码核实（worker-persona.ts / delegation-project-memory.ts / worker-main.ts / worker-prompt.ts / executor-config.ts / project-scope.ts / session-open.ts）。

## 背景与现状

系统里有两个"worker"，配置面完全不同：

| | 普通助手会话（chatKind=worker） | 派活的 native worker / 外部 CLI |
|---|---|---|
| 归属 | 主 app，用户直接对话 | chancellor 派活（delegate 工具） |
| 人设 | `.data/worker-persona.md` 全局一份，每轮现读 | **无**。native 写死 `WORKER_RULES` 8 条；TASK.md 首句「你是 chancellor 派出的独立 worker」 |
| 记忆 | 自动召回 global + 绑定项目 + 会话 | 无引擎；唯一入口是 requirement 尾部项目记忆段（16 条/2000 字，经拆单器转述） |
| 工具 | 全量 harness 工具 | native 写死 4 个（read/write/edit/bash）；外部 CLI 各自的内置工具 |
| 模型 | 每会话可切（composer pill） | 启动 env（`CHANCELLOR_LLM_MODEL`/`LLM_MODEL`），界面不可调 |
| 独立可设置字段 | 1（全局人设，不按会话存） | **0** |

**为什么当初分开（如实回答，非产品决策）**：两条线各自长出来的。普通助手会话来自主 app 的"开发会话"需求；native worker 来自 chancellor 的"无人值守一次性工人"需求，当时刻意做成无状态、无记忆、最小工具面——干完就退场，不需要身份。2026-11-16 用户拍板"普通对话就是 worker"已合并了**身份**（会话归属、人设跟随项目），但**配置面**从未合并。本方案第一次把它当产品问题统一。

## 目标

**一个 worker 概念**：设置里那份「普通助手」就是所有 worker（会话里的 + 派活出去的）的共用配置。可调项默认关（worker 只干活），机制尽量复用执事的（flags / persona_switches / 注入 provider），页面保留专属小页、不上执事那套 44 字段。

## 决策点

### D1 人设共享：派活工人也吃 `.data/worker-persona.md`

- **注入位置**：chancellor `buildWorkerPrompt` 生成的 TASK.md 增「## 你是谁」段（首句身份行之后、任务正文之前）。
- **数据来源**：chancellor 开注入口（`setInternalAsk` 同款先例）：`setWorkerPersonaSource(fn)`，server 装配时装 `() => readWorkerPersona()`。chancellor **不读** server 的文件（依赖方向：server 推、chancellor 收）。
- **覆盖面**：native 与外部 CLI 同吃——TASK.md 是两边唯一的上下文，与 `delegation-project-memory` 同一个"一个方法覆盖两边"的位置。
- **备选被否**：
  - 拼进 requirement（同项目记忆的路径）→ 人设会被拆单器改写/截断，身份不是任务内容，否；
  - `EmployeeProfile` 加 persona 字段传进 ticket.json → 每张单存一份人设，且 profile 语义是"执行参数"不是"身份"，否。
- **默认文案拆分**：现默认正文末句「需要长期记住的事用 remember…set_reminder」是 worker **会话**的工具提示，派活工人没有这些工具，照抄会教它调不存在的工具。拆成「人设正文（共享）」+「会话工具提示（仅 chatKind=worker 注入，代码常量）」，文件里不再混工具行。改默认文案 = 打掉 worker 会话一次上游缓存前缀，进变更记录说明（硬约束）。
- **回滚**：`WORKER_PERSONA_DISPATCH=false` → TASK.md 不注人设，native 回到纯 `WORKER_RULES`（行为与今天逐字一致）。
- **刻意不做**：按任务/按项目的人设变体；外部 CLI 单独一套人设。

### D2 native 模型可调

- `EmployeeProfile.model` 已存在且已流到 native（`dispatch.ts` 把 settings 全量传进 employeeTask），只是 `employee/native.ts` spawn 时忽略。落地 = spawn env 带上 `CHANCELLOR_LLM_MODEL=<task.settings.model>`（非空时）。
- `executor-config`：native 档放开 model 输入（留空 = 启动 env，即今天的行为）；`executorForDelegation` 不再给 native 硬回 `{}`，model 非空才带进快照。
- 探测：native **不做**「检测」按钮（真调要走百炼兼容端点，另接不划算），保留提示行。
- **备选被否**：让 native"跟随运行时主选"——worker-main 只会 OpenAI 兼容单供应商栈，主选可能是 Anthropic 协议/别的 baseUrl+key，给 worker 子进程搬整套 provider 栈收益低风险高。**登记"刻意没有"**（系统架构.md）。
- 回滚：输入框留空即回 env。

### D3 设置页：保留专属 worker 页

- 位置不动（`#/settings/partners/worker`），字段两块：① 人设正文（现有）② 「派活带项目记忆」子开关（父闸 `DELEGATION_PROJECT_MEMORY`，卡片 tip 必须标父闸名——开关父子规则）。
- D2 的 native 模型框在设置→派活 native 卡，不进本页。
- 执事的模块化字段（人格模块 44 字段/情感/学习/主动性/履历/目标/纪律）**不进 worker 页**：后期上下文优化要挑哪几个给 worker，到时单独立项再挂（挂的时候走现有 persona_switches 机制，默认关——符合"默认都关掉、可以开"的口径）。
- **worker 不设项目挂载**（2026-11-16 用户拍板）：派活项目按单指定（delegate `project` 参数，不填回 needs_project），普通助手会话沿用建会话绑定当前项目的现行口径。worker 设置里不出现项目区。

### D4 记忆边界不变

- 派活注入仍只取单子项目的 project scope（16 条/2000 字，`DELEGATION_PROJECT_MEMORY` 总闸）；
- global / partner 记忆**不进派活**（防私事落 runs/ 盘、防泄给外部 CLI——既有硬口径不变，登记"刻意没有"）；
- worker 会话记忆召回维持现状（global + 绑定项目 + 会话）。

## 明确不做

- 按 任务/项目/执行者档位 的人设变体；
- worker 页上执事全套模块；
- native 的「检测」按钮；
- native 跟随运行时主选（provider 栈原因，见 D2）；
- 外部 CLI 的模型走 server 统一下发（各 CLI 自己的配置是它的地盘，model 框只填名）。

## 验证

- chancellor 侧：buildWorkerPrompt 注入段单测（有人设 / 无人设 / 开关关三态）；
- server 侧：executor-config 单测（native model 快照带与不带）、worker-persona 单测扩展；
- `pnpm probe`（内核回归）+ `pnpm --filter @lifediary/server http`（executor 端点视图）；
- 浏览器：设置→派活 native 卡模型框保存回读；真派一单看 TASK.md 首段人设（补上 2026-11-16 项目记忆"真 TASK.md 端到端未验"的欠账，一并核对）。
