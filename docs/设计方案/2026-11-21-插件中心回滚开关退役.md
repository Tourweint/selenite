## 背景与目标

插件中心（`src/plugins.json`，2026-11-21 全量审计：99 项 = 插件页 7 组 93 + 设置页专属 6）里有一类开关的"关"分支是**改动前的旧形态**，旧代码路径纯为回滚保留。功能早已落地验收、口径已定，回滚路径成了死重量：

- 前端旧版整套还活在前端里，只等开关拨 false；
- 服务端每处旧分支都要随新形态一起维护、测试；
- `CHANCELLOR_INTERNAL` 的卡片文案（"拆单/验收/目标核对"）在验收层 11-19 退役后已经失真。

目标：把这 24 项退役——**删卡片（plugins.json 行）+ 删旧代码（off 分支）+ 删开关（辅助函数 / env 读法 / .env.example 行 / 接口文档 §6 行）**。退役后语义 = 原"开"形态成为唯一形态。

## 判据

一个开关值得退役，当且仅当：

1. **"关"分支 = 旧形态**（代码注释或接口文档自称"回滚开关 / 回滚形态 / 旧行为"），不是正当的替代形态或能力关停；
2. 功能已落地验收、口径已定（变更记录可查）、无未决翻案；
3. 删除后"开"形态自洽，不依赖被删的分支。

对照：**能力关停型**（关=端点 404/工具不上架，没有旧代码）与**偏好/成本型**（插话 vs 排队、缓存 vs 新鲜）不在退役范围——那些"关"是正当形态，没有旧代码可删。

## 关键顺序（不照做就是静默事故）

`flagEnabled()` 对不在清单里的 key 返回 false（flags.ts:326）——**先删清单行会让对应功能静默全关**。每项退役必须按：

1. 删消费分支旧代码（off 分支整体退役，功能恒为"开"）；
2. 删 `plugins.json` 行（卡片即消失，清单热装载不用重启）；
3. 删辅助函数 / env 直读 / flags.ts 便捷封装；
4. 删 `.env.example` 注释行 + 接口文档 §6 行与正文引用；
5. 改受影响的测试与探针（见下）。

`requires` 图已核对：**没有任何保留开关 require 被退役开关**，删行不会产生悬空引用。

## 备选与取舍

- **备选A：只藏卡片、留代码**——否。本需求核心是删死代码；只删卡片会让 off 分支变成无开关保护的盲肠，比现在更糟。
- **备选B：一次性全删**——否。三档风险不同（前端旧版 / 服务端单点 / 核心机制），分批让每档的验证范围清晰，第三档（尤其 PARTNER_PROJECT_MEMORY）出问题可单独 revert。
- **本批自身的回滚 = git revert**。退役后单个功能不再有 env 退路——这是本批的明示代价，换来的是代码面干净；若某功能要翻案，按新能力重新立项（照旧给回滚开关）。

## 风险

- 最大单点：批3 `PARTNER_PROJECT_MEMORY`——跟人走模型已是地基，删除时要确保只删"off 分支"，不碰在用链路；先跑 memtest + projects/partners 相关单测再收。
- `PROMPT_TAIL_INJECTION` 删除后，若上游缓存行为异常将失去"退回 system 前缀"的排查手段——接受（备选：临时 revert 本项提交）。
- 探针中依赖"关开关"做隔离的场景（wake 两处）改法要保守：宁可断言收窄，不引入新开关。
