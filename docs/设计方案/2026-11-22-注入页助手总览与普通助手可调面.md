# 注入页助手总览与普通助手可调面

> 状态：**展示卡部分已退役**（2026-11-23，见 `docs/变更记录/2026-11-23-注入页人设顶部总览卡退役（只留总管与执事列表）.md`）；
> 普通助手可调面部分仍有效。
>
> 目标：设置 → 注入里能**一眼看到所有助手的人设与工具**，并知道派活工人（池）
> 这一档“能调什么、什么是固定的”。本批只做**展示 + 已有可调项的入口**；
> 新增行为（普通助手会话工具勾选）留给下一批，避免把工具面改动混进展示层。

## 一、现状审计（2026-11-22，代码级）

### 1.1 注入分区

`设置 → 注入` 六个 tab：人设 / 工具 / 关于我 / 索引 / 技能 / 上下文（`web/settings-base.js` 的 `INJECT_TABS`）。

- **人设**：总管与执事列表 + 置顶的「普通助手」卡（`web/partner-modals.js` 的 `renderPartnerList`），
  点进去是 `#/settings/partners/<id>` / `#/settings/partners/worker`。
- **工具**：全局工具池（常驻/按需，`.data/tool-pool.json`，改完重启）。
- **上下文**：当前会话 / 默认开销两种视图；默认开销的角色下拉由服务端
  `contextDefaultRoles()` 给：总管 → 活跃执事 → 普通 worker。可编辑段走
  `settings-context-edit.js`，写回人设 / 关于我 / 契约 / 目标 / 纪律。
- 普通助手页（`web/worker-profile.js`）：人设正文、会话技能、派活工具（canonical 四件 + escalate）。

### 1.2 普通助手（会话，`chatKind=worker`）

| 可调 | 入口 | 实现 |
|---|---|---|
| 人设正文 | 普通助手页 / 上下文页 persona 段 | `PUT /api/v1/agent/worker-persona` |
| 会话技能 | 普通助手页「会话 → 技能」 | `GET /api/v1/agent/skills?partnerId=worker` + 覆盖层 |
| 派活工具 | 普通助手页「派活 → 工具」 | `GET/PUT /api/v1/agent/worker-tools`（canonical 四件；escalate 恒开） |
| 模型 | 会话 pill / 设置 → 模型 | 全局默认 / 会话级 |
| 全量会话工具 | **不可按 worker 逐件勾选** | 走全局工具池 + harness 默认工具面；`applyPartnerToolSelection` 明确跳过 worker |

固定/不适用的：关于我（worker 固定不读）、记忆召回开关（会话侧没有按 worker 的开关）、
审批（会话内按策略）。

### 1.3 派活工人（池，第二套运行时）

池进程的系统提示由 `pool/task-profile.ts` 的 `buildTaskProfile()` 拼，工具由
`pool/pool-tools.ts` 的 `buildPoolRegistry()` 给五件。逐项：

| 段 | 内容 | 可调？ |
|---|---|---|
| 工人纪律 | 只在任务目录/工作目录干活；需要拍板用 escalate 上报 | **代码固定** |
| 注入防线 | 与宿主同一份 `INJECTION_GUARD` | **代码固定** |
| 验证铁律 | 与宿主同一份 `VERIFICATION_IRON_LAW` | **代码固定** |
| 人设 | `readWorkerPersona()` 的「你是谁」段 | **可调**：与普通助手共用 `.data/worker-persona.md` |
| 任务 / 完成标准 | 单子写入的 instruction / done_when | 建单时由需求决定，不在设置页改 |
| 项目记忆 | 按单子 `project` 召回的 16 条 / 2000 字 | 自动，不单独调 |
| 前置任务结果 | 上游产物 | 自动 |
| 交付契约 | REPORT.md 的 JSON / status 五值 / artifacts 自检 | **代码固定** |
| 工作边界 | 任务目录、工作目录、声明写入路径 | **代码固定**（路径由单子/项目决定） |
| 工具 | read / write / edit / bash + escalate | 前四件按「普通助手 → 派活 → 工具」勾选；**escalate 恒开** |
| 模型 | 设置 → 派活 → 底层 worker 运行时（`profiles.pool`） | **可调** |

**池工人不读**：记忆召回、技能索引、低频工具索引、关于我、当前项目、审批、会话级模型。
这就是“另一套运行时和宿主不一样”的部分；不是遗漏。

### 1.4 总管 / 执事

- 人设：SOUL（`#/settings/partners/<id>` / `chief`）。
- 工具：人设详情页「能用的工具」（按人取消名单 + 按需/常驻提升），写 `partners.disabled_tools`。
- 上下文段：`context-defaults` 已按角色装配，可编辑段写回各自源头。

## 二、本批做什么

1. **服务端加一个只读汇总端点** `GET /api/v1/agent/assistant-surfaces`：
   返回总管、每个活跃执事、普通助手、派活工人（池）的
   `{ id, label, kind, persona{preview,chars,editable,hash}, tools{count,names,editable,hash,note}, adjustable[], fixed[], contextHash }`。
   不返回全文正文、不返回密钥；只给预览与入口。
2. **服务端给 `context-defaults` 加 `dispatch-worker` 角色**：
   用池任务 profile 的真实段与五件工具生成一份默认上下文；角色下拉里出现
   「派活工人（池）」。人设段可编辑（写回 `worker-persona`）；固定段只展示。
3. **前端在注入 → 人设顶部加「助手的人设与工具」卡**：
   按汇总端点渲染每档的：人设预览、工具 chips、可调/固定标签、动作
   「改人设 / 调工具 / 模型 / 看上下文」。空/失败只显示一行，不挡原来的总管与执事列表。
4. **上下文页支持 `?role=<id>` 深链**：卡片「看上下文」直接落到对应角色的默认开销；
   旧入口（无 query）行为不变。

## 三、明确不做

- **不给普通助手会话加逐件工具勾选**（需要改 `tool-visibility` / `applyPartnerToolSelection` /
  新的存储与依赖闸；单独一批，避免和展示层一起回归）。
- **不给池工人单独一份人设**：本批如实标“与普通助手共用”；要拆再立项。
- **不给池工人单独一份工具勾选**：当前四件与 native 共用同一份 `worker-tools.json`；
  本批只展示“共用”，不新造第二张名单。
- **不改任何固定段文字**（工人纪律 / 注入防线 / 验证铁律 / 交付契约 / 工作边界）。
- **不新 tab**：卡片放在现有「人设」tab 顶部，不增加第七个注入 tab。

## 四、接口形状（前端/服务端共同遵守）

```json
GET /api/v1/agent/assistant-surfaces
{
  "ok": true,
  "surfaces": [
    {
      "id": "dispatch-worker",
      "label": "派活工人（池）",
      "kind": "dispatch",
      "persona": { "chars": 203, "preview": "你是一个普通任务助手……", "editable": true, "hash": "#/settings/partners/worker" },
      "tools": { "count": 5, "names": ["read","write","edit","bash","escalate"], "editable": true, "hash": "#/settings/partners/worker", "note": "前四件与 native 共用勾选；escalate 恒开" },
      "adjustable": ["人设（与普通助手共用）", "工具四件", "模型"],
      "fixed": ["工人纪律", "注入防线", "验证铁律", "交付契约", "工作边界"],
      "contextHash": "#/settings/context?role=dispatch-worker",
      "modelHash": "#/settings/agent"
    }
  ]
}
```

- `preview` 最多 160 字；没有的字段不出现。
- `hash` 只给站内 hash，不给绝对地址。
- 排序：总管 → 活跃执事（按原顺序）→ 普通助手 → 派活工人（池）。

## 五、验收

1. `GET /api/v1/agent/context-defaults?role=dispatch-worker` 200；sections 含
   `worker_rules / injection_guard / verification_iron_law / persona / task / delivery_contract / boundary`；
   tools 为五件（或按当前 worker-tools 勾选后的四件 + escalate）。
2. `GET /api/v1/agent/assistant-surfaces` 200；至少 4 类 surface；派活工人的 fixed/adjustable 与 §1.3 一致。
3. 浏览器：注入 → 人设顶部出现「助手的人设与工具」卡；点「看上下文」落到
   `#/settings/context?role=dispatch-worker`，默认开销显示派活工人（池）；点「改人设」到普通助手页；
   点「调工具」到普通助手页；点「模型」到派活页。
4. `pnpm typecheck`；相关单测（context-defaults / task-profile / pool-tools）全绿；`web-imports` 绿。
5. 现有总管 / 执事 / 普通 worker 的上下文默认页行为不变（原有测试全绿）。

## 五之二、落地结果（2026-11-22）

- 服务端：`context-defaults` 加 `dispatch-worker`（九段 + 五件工具，人设段可编辑）；
  `assistant-surfaces.ts` + `/api/v1/agent/assistant-surfaces`；`poolToolCatalog()`。
- 前端：注入 → 人设顶部「助手的人设与工具」卡（总管 / 执事 / 普通助手 / 派活工人）；
  `#/settings/context?role=...` 深链；上下文页 persona 段对 `dispatch-worker` 也写回
  `worker-persona`。
- 验证：`pnpm typecheck`；`context-defaults` / `pool-tools` / `task-profile` / `web-imports`
  28/28；真 HTTP 两个端点；浏览器实测卡片四行、工具 chips、可调/固定标签；
  点「看上下文」落到 `?role=dispatch-worker`，页面显示「系统 9 个字段 · 工具 5 个 · 技能 0 个」。
- **派活实施备注**：服务端票 `t-20261122-222902-1hbl` 的第 1 个任务成功；第 2 个任务
  pool `stream_closed` 失败；前端票 `t-20261122-222931-cs01` 的 1/2/3 任务报告 ready，
  但调度器的 worktree 合并没有把 **tracked 文件** 的改动落回主工作区（新文件能落），
  验证任务因此 blocked。最后是人工把两个 worktree 的 patch 应用到主仓、补齐缺失的
  `poolToolCatalog` 与服务端汇总端点后验收。**教训**：脏工作区上派发多文件任务，
  不能假设 worktree diff 会自动合并；派完要核对主仓是否有改动。

## 六、回滚

本批只加只读端点、默认角色与展示卡，不改执行链路。
`context-defaults` 新角色只在 `?role=dispatch-worker` 时使用；前端卡片读不到端点时静默不显示。
无新行为开关；要整体隐藏卡片可删 `#assistant-surfaces` 卡（一行）。
