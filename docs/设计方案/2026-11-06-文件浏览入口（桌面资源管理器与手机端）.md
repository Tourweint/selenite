- 来源：用户原话转达（经 Cindy）——桌面端加一个「从文件资源管理器打开」的入口看本地文件；手机端（lifediary）也想要一种能看文件的方式。
- 下沉落点（落地后）：契约 → `docs/基线文档/接口文档.md`；模块 → `docs/基线文档/系统架构.md`。

## 1. 需求与边界

两件事，性质不同：

1. **桌面端「从文件资源管理器打开」**：本机服务本就在用户电脑上跑，缺的只是一个按钮，点了在当前工作区/当前项目的根目录弹出系统资源管理器。这不是"远程看文件"，是本机便利入口。
2. **手机端看文件**：手机读不到电脑磁盘，必须由服务端出文件浏览接口。这是**跨端契约改动**（`ts/packages/shared` + 手机端 Kotlin），按仓库规矩必须先写方案。

共同的安全底线：无论哪端，能看到的范围都**锁在最大工作区内**，复用 `path-guard.ts` 的 realpath 判定口径（含符号链接祖先逃逸识别）；越界一律拒绝，不区分原因（沿用"鉴权失败 403 空体、业务拒绝 400 带说明"的既有风格）。

## 2. 桌面端：资源管理器入口

### 备选

- **A. 服务端端点 + Web 界面按钮（已采纳）**：新增 `POST /api/v1/workspaces/open-explorer`，服务端收到后用 `explorer.exe <root>`（Windows）/ `open`（macOS）/ `xdg-open`（Linux）打开目录；Web 界面在侧边栏项目小窗口里加入口（2026-11-06 用户调整，原设计为右上角按钮）。浏览器和 MyGo 壳（壳本就加载 `http://127.0.0.1:39847/` 的 Web UI）都能用，一份实现两端生效。
- **B. MyGo 壳原生按钮**：Go 侧直接 `exec.Command("explorer", root)`。缺点：只在壳里可用，浏览器打开没有；Go 壳要多一份"知道工作区在哪"的逻辑（要新增一次服务端查询），改动面反而更大。

### 推荐理由（一句话）

A 一份代码同时覆盖浏览器和桌面壳，且路径判定、鉴权、回滚开关都落在服务端已有的体系里。

### 设计要点

- 请求 body `{projectId?: string}`（不收任意路径）：缺省打开工作区根；带 `projectId` 打开该项目自己的根（复用派单同一套复核：已登记、未归档、realpath 在当前工作区内，失败 400 `bad_project`）。
- 路径先 realpath 复核在工作区内、且是已存在目录，再起进程。**不收绝对路径参数**——没有"打开任意目录"的需求，也就没有越权面。
- 打开目录不是写操作、不是 agent 工具，不进 `WRITE_TOOLS`；但按硬约束给回滚开关：`EXPLORER_OPEN=false` 一行回到无此端点形态（端点返回 400）。
- 鉴权与其他 `/api/v1/*` 相同；失败 403 空体。
- 手机端不提供此入口（手机上"打开资源管理器"无意义），契约上此端点手机零改动。

## 3. 手机端：文件浏览

### 备选

- **A. 工作区只读浏览接口（推荐）**：契约进 `shared`，两个只读端点：
- `GET /api/v1/files?path=<工作区内相对路径>` → 目录列表 `{ok, path, entries:[{name,type:"file"|"dir",size,updatedAt}]}`（`path` 缺省 = 工作区根）。
  - `GET /api/v1/files/content?path=…` → 文本内容（`{ok, path, size, truncated, content}`），二进制与超大文件（>512KB）`content=null、truncated=true`，只给元信息。
  - 路径处理：只收相对路径，`..`/绝对路径直接 400；解析后 realpath 判定必须落在工作区根内（口径与 `path-guard.ts` 的 `realTarget`/`insideOrEqual` 一致，符号链接逃逸拦住）。全部走 `/api/v1/*` 鉴权，失败 403 空体。**只读，无任何写/删/改名端点**。
  - 回滚开关：`FILE_BROWSE=false` 端点整体下线（404）。
- **B. 走 agent 工具通道**：手机端不新增契约，让用户在聊天里说"帮我看下 xx 文件"，由 agent 用 read 工具读回来。零契约改动，但每次都要跑一轮模型、慢、耗 token，且看到的内容混在对话流里，谈不上"浏览"。可作为兜底说明，不作为功能。
- **C. 完整文件管理 API（列表 + 下载任意文件 + 上传/删除）**：能力最全，但把"看一眼"扩成了"远程文件管理器"，鉴权面、下载面、误删面全都要设计，远超需求。

### 推荐理由（一句话）

A 用最小契约（两个只读端点）满足"能看"，边界直接抄工作区既有物理边界口径，手机端按 JSON 读写即可、纯增量。

### 设计要点

- 契约改动顺序照 §7：先改 `ts/packages/shared/src/index.ts`（Zod schema：请求参数、目录项、内容响应）+ `接口文档.md`，再改两端实现。
- 大文件/二进制：正文只回文本（UTF-8 可解码）且 ≤512KB，超出只给元信息并标 `truncated`——手机端渲染文本即可，不做图片/视频预览（见"明确不做"）。
- 隐藏文件照常列出（工作区本来就是用户自己的）；`.data/` 含令牌哈希与 providers.json 等配置，**在根层屏蔽 `.data` 目录**（密钥不进日志/不下发客户端的延伸口径）。
- 日志只记访问路径与字节数，不记内容。

## 4. 明确不做

- **不收任意绝对路径**：桌面端入口不收路径参数，手机端只收工作区内相对路径。"看工作区外的文件"请调整工作区设置，或直接在电脑上操作。
- **不做写操作**：手机端不能新建/修改/删除文件。写文件走既有派活/agent 链路（有闸门与审批），浏览器不做第二套写通道。
- **不做二进制预览**（图片/视频/PDF 在手机端渲染）与**不做下载**：先满足"看文本、看目录结构"；确有需要再单独立项。
- **不做搜索/排序/收藏**等文件管理器增强，第一版就是"列目录 + 看文本"。
- **不做实时监听**（文件变更推送）：看的时候刷新即可。
