## 1. 问题：213,804 token 的 prompt 里约一半（51%）可以直接省掉；另 43% 是 bash 结果与工具参数，本次不动

审计对象是同一会话的 58 次请求（数据来自 durable 的 usage 与观测，未改存储、未复现）：

| 块 | 估算 token | 占比 | 问题 |
|---|---:|---:|---|
| `web_search` 结果 | 78,737 | 37% | 10 次搜索、66 条命中、22.2 万字符；`message` 把 hits 又抄一遍（10.9 万字符纯重复） |
| bash 结果 | 53,987 | 25% | 本次不动（结果本身是事实，无重复结构） |
| 工具调用参数（heredoc） | 39,400 | 18% | 本次不动（历史必须逐字节一致） |
| 被回放的 thinking | 29,346 | 14% | 58 条 assistant 全带 `thinkingSignature:"reasoning_content"`，适配层每轮重发 |
| system + 工具声明 | ~7,600 | 3.6% | 固定前缀资产，本次不动 |

逐请求增量回归确认：去掉 thinking block 后 prompt 估算与 usage 对不上；加回去完全对上——
说明 `reasoning_content` 确实在每一轮被重发，而不是只存不读。

## 2. 决策

### 2.1 `web_search` 只回结构化结果，并给整次结果封顶

- 正常命中返回 `{ count, hits }`，删掉与 `hits` 重复的 `message`；0 命中仍返回
  `{ count: 0, message: "没有找到相关结果。" }`（引导文案是独立价值，不是重复）。
- `WEB_SEARCH_MAX_RESULT_CHARS = 32_000`：按 `hits` 序列化后的字符数算，超了从排名最后的
  命中开始丢，至少保留 1 条。每条 `title / url / summary` 的结构与内容不动。
- `count` 取**裁剪后**的条数，与 `hits.length` 恒等（调用方不必自己再算）。
- 取舍：不改搜索适配层的 2000 字单条截断——单条摘要的质量边界是另一个话题；这里只治
  「一次搜索塞满上下文」和「同一事实写两遍」。
- 为什么不是开关：这是输出瘦身，没有语义变化（模型拿到的仍是同一批命中、同构字段）；
  回滚 = revert 本次提交。工具 name / description / 注册顺序一个字未动，不构成契约变更。

### 2.2 历史 assistant 的 thinking 默认不回放

- 新增 `agent/reasoning-replay.ts`：`replayThinkingEnabled()`（缺省假）+
  `stripReplayedThinking()`（不改原数组 / 原对象，只去掉 assistant 的 thinking block 与
  多余的 `reasoning_content` 字段）。
- `lifecycle-harness.ts` 的 `beforeRequest` 最前面应用，后续 `lastUser`、注入拼接与返回值
  一律用剥离后的视图；**durable 里的 assistant entry 不动**（UI 的步骤展示仍要 thinking）。
- 依据：DeepSeek 官方回传历史时不建议带 `reasoning_content`；pi-ai 的 openai-completions
  适配层对要求该字段的供应商会自动补空 `reasoning_content`
  （`requiresReasoningContentOnAssistantMessages`），所以剥离不影响工具调用。
- 取舍：模型可能依赖上一轮思考的细节。若实测模型行为变差（重复推导、答非所问），
  `CHAT_REPLAY_THINKING=true` 一行回到旧形态；代价是每轮多背一份思考。
- 明确不碰：pi-ai / pi-durable 依赖、provider 适配层、durable 存储。

### 2.3 压缩触发点窗口上限：2026-11-25 晚撤回

- 原问题仍然成立：默认 `percent=70` 时，网关自报 1,000,000 窗口 → `trigger = window × 70% = 700,000`，
  213K 完全不触发；用户口径是**1M 窗口的模型不该滚到 20 万还不压**。
- 原方案（已撤）：`CompactionConfig` 增加 `windowCapTokens`，env `AGENT_COMPACT_WINDOW_CAP_K`
  （默认 200K）；`percent` 档先算 `effectiveWindow = min(window, cap)` 再乘百分比，
  1M + 默认 → 140K 压；小窗口（131,072）仍是 91,750。
- 撤回原因：
  - 用户实际用的是 `tokens` 档（`AGENT_COMPACT_TRIGGER_K=300` = 307,200）；cap 只作用于
    `percent` 档，对用户是死配置。
  - 同一份 `percent` 值在 cap 下会悄悄换语义：25% × 1M = 250K，但 25% × 200K 上限 = 50K；
    调一个"上限"会让没动过的百分比变成另一种行为。
  - 已有 `tokens` 档就是绝对触发点，不需要再叠一层窗口上限。
- 结论改为：需要绝对触发点时用现有 `tokens` 档；看不清哪一档生效、换算成多少 token 时，
  由设置页在单位后缀的悬停提示里显示「当前生效」（2026-11-25 晚加）。**不新增算法上限**。
- 撤回后 `triggerOf` 的 percent 分支恢复为 `Math.round(window × percent / 100)`，
  `AGENT_COMPACT_WINDOW_CAP_K` 删除。撤回只影响之后的触发；已经发生的压缩不可逆。

## 3. 明确不做

- 不改任何工具的 name / description / 注册顺序（缓存前缀资产）。
- 不改搜索适配层（`search*.ts`）的 2000 字单条截断。
- 不改内核压缩策略：`keepRecentTokens` / `backgroundTokens` 仍吃内核默认（20000 / 32768）。
- 不动 bash 结果与工具调用参数（历史必须逐字节一致）。
- 不动 `.data/` 与 durable 存储；测试只写临时目录。
