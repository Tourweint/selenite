## 件③ 面向总管/执事 + 对话内看产出文件（主件，最大）

### 3a. 对话流里的"工作区文件"卡片（抄 ZCode + cindy 双蓝本）

**调研结论**（三路 agent 已核对，cindy 修正版 2026-11-10）：
- ZCode：`tool` 事件（`status:"end"`、`name ∈ {write,edit}`）带 `label`（路径）与 `diff`；前端把每轮的写文件步骤聚成"本次修改的文件"列表（文件名 + 增删行数 + 状态点），**轮尾默认折叠、点开才展开**；事件通道就是 SSE `tool` 事件，无独立端点。
- cindy 桌面端：`GeneratedFilesCard` 同样挂在 turn 末尾，**从 tool_use 结构化派生**（不靠正文链接）；关键产品口径有三条值得抄：
  1. **"可点必存在"**：渲染前先验证文件存在才出可点 chip（我们用 `GET /api/v1/files` 的 stat 换算实现），不存在只显示纯文本路径；
  2. **>6 个折叠**"前 6 个 + 再显示 N 个"；
  3. 点开是**全屏 Lightbox 不是 sheet**，MD 用与聊天气泡同一个渲染器（观感一致）+ "查看源码"切换。
- cindy 移动端没有产出卡，走正文路径 chip + 全屏 Markdown 阅读器（`MarkdownFileReader`，标题/列表/表格/代码块，WebView 滚动）——验证了"移动端全屏预览页"是成熟形态。
- 手机端现状：`ChatScreen` 已有 `LdMarkdownText`（极简 md 渲染：标题/列表/引用/代码块/粗斜体）；SSE `tool` 事件手机端**已解析**（步骤行在用），只是没把 write/edit 单独拎出来做卡片；历史回读 `steps[]` 字段同形状（含 `diff`），刷新后也能重建。

**设计**（ZCode 调研深挖后回填，2026-11-10）：
1. **数据源零契约改动**：服务端 `tool` 事件与 `TranscriptStep.steps[]` 都已带 `name/label/diff/ok`。手机端在 `ChatViewModel` 加一层"写文件步骤收集器"：`name∈{write,edit}` 的 end 事件 → 按 `label`（路径）去重聚合成本轮"产出文件"。（ZCode 的对应物是 turn 结束事件带聚合数+懒加载明细；我们量级小，SSE end 事件里 `diff` 现成，不用做二级拉取。）
2. **UI**（ZCode v4 交互骨架 + cindy 产品口径）：一轮回答末尾**默认折叠**的一条——「本次产出 · N 个文件 · +X -Y」（增删行数从 `diff` 文本按 `+`/`-` 行数现算，ZCode 同款口径）；点开展开文件行列表（文件图标 + 相对路径 + "新建/修改"徽标 + 增删数；**超 6 个折叠"前 6 + 再显示 N 个"**，cindy 口径；**可点前先验证文件存在**——`GET /api/v1/files` 探一下，不存在的只显示灰字路径不可点，cindy"可点必存在"口径）；再点某文件 = **全屏预览页**（cindy 移动端同款形态，不是半截 sheet）：
   - md 文件 → `LdMarkdownText` 渲染（与聊天气泡同渲染器，观感一致）；
   - 代码/文本 → 等宽纯文本 + 行号；
   - edit 且 `diff` 有值 → 顶部 tab 切"文件/改动"，diff **自绘逐行染色**（LazyColumn，`+`绿/`-`红/上下文灰——ZCode 移动端同款轻量方案，不用重型高亮库）。
   - 大文件（>200KB）只给"去电脑看"提示（手机屏不宜预览超长文）。
3. **文件内容拉取**：复用既有 `GET /api/v1/files/content?path=…`（P1 批次已在用），零新端点。`label` 是绝对路径时需换算成工作区相对路径——服务端 files 端点只收工作区内相对路径；`write/edit` 的 label 实测多为工作区内相对/绝对路径，实施时做一次换算，工作区外的文件卡片只显示不可点。
4. **历史回读同样生效**：`steps[]` 里有同一份事实，打开旧会话也能重建卡片（ZCode 同款"现场与回放一致"）。
5. **不做**：ZCode 的"从回答正文正则提取文件路径出预览卡"（`AssistantPreviewCards` 那路）——误报面大，且服务端事件源已够准；登记"刻意没有"。ZCode 的"撤销文件回退"（rewind）是另一套 checkpoint 机制，桌面必备批次二已有挂项，不在本方案。

### 3c. 右上角会话设置（思考档搬进去 + 模型等归拢）

**调研**（cindy 深挖后修正）：cindy 桌面端**没有**右上角 ⚙——模型/思考强度收在 **composer 底部模型 pill → 弹层**（`ModelConfigFlyout`：强度滑杆/Fast 开关，档位<2 不画滑杆不做假按钮）；会话管理（重命名/置顶/归档）在标题"…"菜单。cindy 移动端：头部右侧固定「远程桌面、文件、更多」三键，"更多"开底部 `SessionMenuSheet`（会话管理类），**模型/强度也不在这里**，而是 composer 模型药丸 → `ModelPickerSheet`（列表+选中模型的 effort 子页+权限模式，选行=原子切"来源+模型+effort"）。

## 件④ 手机 / 电脑对话同步

**调研结论**（agent 深挖后修正版，2026-11-10）：
- 服务端会话正文全在 pi-durable（`.data/agent.sqlite`）；回读 `GET /agent/chat/:id/messages` 带 `limit`（默认 50）与 `sinceSeq`，**但 sinceSeq 只覆盖"HTTP 发起轮次 + 最近 500 条"的滑窗**（`chat-events.sqlite` 重放库，`AGENT_SSE_SEQ_KEEP`），且手机走的 OpenAI 兼容端点不写重放库——所以**增量游标救不了历史同步，历史同步只能全量拉**（`session.ts:1182` readTranscript / `index.ts:1116-1138`）。
- `GET /agent/chats` 只收 `limit`，无 after/lastAt 游标；每条带 `chatKind`（chief/worker/partner）与 `lastAt`——**抽屉分组与"刚刚活跃"标记的数据全是现成的**（`session.ts:1654-1711`）。
- web 电脑端同样是"切会话才全量拉"（`web/app.js:4846`），没有跨设备实时感知。
- **中继侧推送骨架其实已存在**：`events/subscribe` 通道按 conversationId 订阅、`push/session:<uuid>` 推送（`relay-channels.ts:158-230`）——将来要做实时感知是"加白名单项+补齐写库入口"，不是从零搭。但重放库只收 HTTP 轮次、群聊/兼容层/中继发起的轮次都不写（`index.ts:1086-1101` 等），补齐面较大，**首批仍不做实时，登记"刻意没有"**。

**设计**（不做双向合并，服务端唯一真相 + 拉取式同步）：
1. **会话清单同步**：手机抽屉会话列表改为每次打开抽屉时全量拉 `/agent/chats`（现在就有端点），并按 `lastAt` 排序显示"电脑上聊的"会话——手机本地已有的会话清单仅作离线兜底。`chatKind` 已在清单里（chief/worker/partner），3b 抽屉分组直接用同一份数据，不用第二拉。
2. **正文拉取**：点开任何会话（不管哪台设备发起）都走 `/agent/chat/:id/messages` 全量拉——已有行为，无需改。手机不存正文是既定架构，天然无冲突。
3. **"正在聊"提示（零契约）**：清单行对 `lastAt < 60s` 的会话标"刚刚活跃"——数据已有，纯展示。
4. **明确不做**：
   - `after=<at>` 增量参数——调研证实 `sinceSeq` 滑窗（500 条、只收 HTTP 轮次）救不了历史同步，全量 50 条量级够用，增量游标属过度设计；
   - 跨设备实时推送——中继 `events/subscribe` 骨架虽在，但重放库只收 HTTP 发起轮次（OpenAI 兼容层/群聊/中继发起的都不写），要补齐写库入口面太大，登记"刻意没有"，等真卡手再立项。

**一句话口径**：手机永远以服务端为准拉取，本地不存正文 → 天然同步，不需要"同步机制"，只需要"每次都拉"。
