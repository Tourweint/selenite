## 一句话

前端把已经做好的数据用起来（任务中心的阶段分段/证据/返工、执事的忙因胶囊、技能用量），
后端把只读工具迁到统一返回契约。

---

## 一、任务中心：阶段分段 + 验收证据 + 返工次数（七 #23）

1.1 任务详情页（`web/app.js` 的 `renderTicketDetail`）加一个**阶段条**：
   `受理 → 规划 → 执行 → 验收 → 完成`，当前阶段高亮；数据来自 `ticket.status` 与已有字段。
1.2 **验收证据块**：把 `reviews[]` 的逐条 verdict / reason / 改了哪些路径列出来（已有数据，只是没展示）。
1.3 **返工次数**：`repairRound > 0` 时在阶段条旁显示"返工 N 轮"（批 11 已有字段）。
1.4 **裁判结论**（批 14 的 `judge.json`）：若任务详情端点已下发就展示，没下发就**先不下发**——
   本批不新增端点，只展示已有字段。若发现 `judge.json` 没有投影到详情端点，**在变更记录里写清"裁判结论暂无界面"**，不要顺手加端点。

## 二、执事列表：忙因胶囊（七 #23 后半）

2.1 侧栏执事行的状态点旁边，忙时显示一个小胶囊说明**忙因**，优先级：
   **等审批 > 跑任务 > 等回答 > 空闲**。
2.2 数据来源：现有 `/api/v1/partners` 的字段 + 全局待办 `/api/v1/agent/approvals`（不带 conversationId）。
   若拿不到"某执事是否在等审批"，**降级为只显示"忙/空闲"**，并在变更记录写清。
2.3 只改 `web/app.js` 与 `style.css`，不动契约。

## 三、面板七原则评审（四 §十一#2）

3.1 对**任务中心看板**与**审批浮窗**做一轮对照评审，按 dsh-superagent 的七原则：
   ① 每个元素都要回答三问之一（有需要我的吗 / 系统健康吗 / 这活经历了什么），否则删；
   ② 数字必须等于它链接的列表长度；③ 标签说"在等谁、需要什么"，不露内部状态码；
   ④ 用领域词不用内部 id；⑤ 诚实状态（不得与另一处事实矛盾）；⑥ 默认安静（健康态不占空间）；
   ⑦ 控件一致。
3.2 **输出**：在 `docs/设计方案/` 写一份简短的评审结论（每条原则：符合 / 不符合 / 已改 / 暂不改+原因），
   并把**明显违背**的改掉（例如：看板数字与列表长度不一致、露了内部状态码）。
3.3 不要为了"符合原则"大改视觉；只修明显问题。

## 四、技能用量进界面（批 17 的收尾）

4.1 设置 → 技能页：每行显示 `usageCount` 与 `stale` 徽章（"90 天未用"）。
4.2 只加展示，不加操作（技能仍只能由人删，不给"归档"按钮）。

## 五、旧工具迁到统一返回契约（五 §八#1 的续）

5.1 按 `tool-result.ts` 文件头写的顺序，迁移**只读**工具：`recall`、`web_search`、`propose_topic`、`skill`。
5.2 迁移规则：**保持人读的 `message` 文案不变**，只把外层包成 `ToolResult`。
5.3 每迁一个，把对应的单测/探针断言一起改。
5.4 **写类工具本批不迁**（`delegate` / `work_*` / `partner_*` 的结果被回执与恢复链路读取，要单独一批）。
5.5 在 `tool-result.ts` 的注释里更新"还剩哪些没迁"的清单。
