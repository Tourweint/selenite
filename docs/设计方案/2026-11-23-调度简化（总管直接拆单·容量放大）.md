# 调度简化：总管直接拆单 + 容量放大

> **状态：已落地（2026-11-23）。**
> 下沉落点：拆单所有权 → `接口文档.md` §7 / `系统架构.md` D37 与模块表；容量默认值 → `接口文档.md` §6 环境变量表；
> 落地记录 → `docs/变更记录/2026-11-23-调度简化（总管直接拆单·容量放大）.md`。
> 与长期文档冲突时，以落地后的基线文档为准。

## 零、人话版

1. **删掉拆单器**。现在每张单收下后，chancellor 还要调一次内部模型把需求拆成 1–5 个 task；
   用户拍板：这一步没用，慢且多一次模型调用。改成**总管/领域经理在 `delegate` 时直接把 tasks 给出来**。
   没给 tasks 的入口（前端直派、手机、远端设备）退化成**一个任务**，照样能跑。
2. **容量放大**。同时活跃单 3 → **8**；同领域准入 1 → **4**；池进程 4 → **8**；
   外部 CLI 车道 Claude/Codex 2 → 4，OpenCode/Qoder/CodeBuddy 1 → 2。
3. **同领域 manager 仍串行（1）**。用户说“并行也没关系”，但 manager 是**长期会话 + 单份 SQLite**，
   两个进程会抢同一个 `conversation_id`，这是状态冲突，不是文件冲突。总管拆单解决不了。
   本方案只放大“同领域准入到 4”（单可以同时活着、在领域闸排队），不放开 manager 进程并发。
4. **隔离不新增机制**。worktree + 文件租约 + 越权检查保留；无计划单用 `writes:["**"]`（整项目）兜底，
   两单撞同一文件是小概率，worktree 合并冲突检查仍是最后一道闸。
5. **终止回执第二批做**。失败分类已有；先把“结构化终止回执交给派活人”单独立项（见 §七）。

## 一、现状与问题（2026-11-23 代码核对）

- `runChancellor` 收单后走 `planTicket()`（`packages/chancellor/src/plan.ts`）：
  一次 `askInternal` 模型调用，最多重试 3 次，把 requirement 拆成 1–5 个 `PlannedTask`。
- 总管 `delegate` 只能给 `requirement` / `steps` / 项目 / 工作目录，**不能直接给任务拆分**；
  拆单器是唯一的分配者。用户认为这次模型调用低效，且总管本来就能拆。
- 容量默认值偏小：`CHANCELLOR_MAX_ACTIVE_TICKETS=3`、`CHANCELLOR_MAX_ACTIVE_PER_DOMAIN=1`、
  `SUPERVISOR_POOL_SIZE=4`、外部 CLI 车道 2/2/1/1/1。
- 失败/终止信息目前只以一句话 `line` 回报，结构化字段（failureClass / 是否可重试 / 是否合并）
  没有稳定地交给派活人。

## 二、拆单所有权转移

### 2.1 契约：`tasks` 进 delegate

`delegate`（宿主侧 `ts/apps/server/src/tools.ts`）与 manager 的 `delegate`
（`ts/packages/chancellor/src/worker-main.ts`）增加可选参数：

```ts
tasks?: Array<{
  title: string;
  slug: string;          // 小写字母/数字/连字符
  instruction: string;
  done_when: string;     // 与 plan.json 同名字段，直接复用校验
  dependsOn: number[];   // 1-based seq，只能依赖更小的 seq
  writes: string[];      // 项目内相对路径；只读给 []
}>
```

- 传了：代码校验后直接落 `plan.json`，**不再调用任何拆单模型**。
- 没传：生成**单个任务**兜底：
  - `slug: "task"`，`title: "整单任务"`；
  - `instruction = requirement`（若带 `steps`，按现有 `appendPlanSteps()` 追加步骤段）；
  - `done_when = "完成用户交代的事；有产物时在 REPORT.md 的 artifacts 里列出，并逐个读回自检"`；
  - `writes = ["**"]`（整项目，见 §四）。
- 校验失败：不建 task，票转 `needs_you`，`line` 写清哪个字段不合法（复用 `renderPlanFailureLine`）。
  不做“模型重试”，让派活人下一条消息修正。

`ChancellorRequest` 增加 `tasks?: unknown`；`DelegationKickoff` 增加 `tasks?: unknown`；
`delegation-start-delegation.ts` 在**新派**（含回退重派）时透传，续跑不带（沿用 `plan.json`）。

**项目记忆不能丢**：原来项目记忆拼进 `requirement`，由拆单器分发到各 task；拆单器删掉后，
宿主 `delegate` 在 `tasks` 非空时把同一段项目记忆追加到**每个 task 的 instruction 尾部**
（只影响交给 chancellor 的 tasks，不参与幂等指纹）。单任务兜底仍走 `appendDelegationProjectMemory` 后的 requirement。

### 2.2 谁负责拆

| 入口 | 是否必须给 tasks | 没给时的行为 |
|---|---|---|
| 总管 `delegate` | 多步活必须（技能手册要求） | 单任务兜底 |
| 领域经理 `delegate` | 多步活必须（manager prompt 改写） | 单任务兜底 |
| 前端「新建任务」 | 否（弹窗只有一句话） | 单任务兜底 |
| 手机 / 远端设备 / HTTP 派活 | 否 | 单任务兜底 |
| 崩溃恢复 / 续跑 | 不适用 | 读 `plan.json`，行为不变 |

### 2.3 `plan.json`

- 形状保持兼容：`{ticket, employee, ok, tasks, droppedDeps, error, attempts, created_at}`。
- 新增 `source: "dispatcher" | "single"`；`attempts` 恒为 `[]`（没有模型重试了）。
- 校验失败时仍写 `ok:false` + `error`，`tasks: []`，供任务详情看原因。
- `steps` 保留：老单仍能展示；新单不再喂给拆单器（没有拆单器了），只在单任务兜底时拼进 instruction。
  `delegate` 的 `steps` 参数**保留但降级**为“任务详情里的核对序列”；技能手册改成“多步活直接给 tasks”。

### 2.4 要删的

- `planTicket()`、`buildPlanPrompt()`、`PLAN_TIMEOUT_MS` 的使用、`internal-plan.test.ts`。
- manager 的 `installManagerInternalAsk`（只为拆单注入）**本批不删**，留作后续清理；先保证不调用。
- `applyEmployeePlanPolicy()` 保留（phone 清空 writes 的口径不变）。

### 3.1 为什么同领域 manager 不并行

- manager 是**长期会话**：`managers/<domain>/meta.json` 里只有一个 `conversation_id`，
  两个 manager 进程会同时 resume 同一个 pi-durable 会话，抢同一份 `.agent.sqlite`。
- 这跟“两单改同一个文件”不是一类问题；用户说“总管会拆好任务”解决的是文件冲突，解决不了会话冲突。
- 本方案：准入层同领域放到 4（单可以同时活着，不挡别的领域），领域闸保持 1（manager 进程串行）。
  如果以后要并行，必须先做“一单一会话”的领域会话分片，单独立项。

## 四、写集 `**`（整项目）

- `paths.ts` 的 `writeCovers()` 增加：`declared === "**"` → 覆盖任意路径。
- 兜底单任务 `writes: ["**"]`；租约按字面量 `"**"` 建锁，两个兜底任务之间会串行。
- 已知小风险：`"**"` 与具体路径租约不互斥（比如另一单声明 `src/a.ts`）。worktree 隔离 +
  合并前的 `hasConflict()` 仍是最后一道闸；非 git 项目没有 worktree，两单同时写同一文件时
  以“后合并者冲突、不写”收场，不静默覆盖。用户已接受这是小概率。
- 边界文案：`task-profile.ts` 的「工作边界」与 `worker-prompt.ts` 的 TASK.md 边界，
  在 writes 含 `"**"` 时显示“项目内任意路径”，不要打印裸 `**`。
- 池的 `writes` 链路（2026-11-23 收口补）：`EmployeeTask.writes` → `dispatch.ts` →
  `employee/pool.ts` → `QueuedRun` / `/run` / `bridge` / `supervisor` → `buildTaskProfile({writes})`。
  不传 = 池按只读渲染边界；`["**"]` 显示“项目内任意路径（**）”。

## 五、明确不做

- 不做“总管给完整 plan 之外再调一个模型校验/补全”。校验只做确定性规则。
- 不做 manager 进程并行（理由见 §3.1）。
- 不做队列 UI / 排队详情；`GET /api/v1/scheduler` 的计数投影不变。
- 不做新的隔离机制、不做 per-task 隔离开关；worktree 默认不变。
- 不删 `steps` 的存储与任务详情展示；不删 manager 的 internal ask 基建（后续清理）。
- 不改手机端 / shared 契约；`tasks` 只走服务端内部派活链路。

## 七、第二批：终止回执（2026-11-23 已落地基础版）

目标：每个 task 结束（完成 / 失败 / 中止 / 超时 / 崩溃）都给派活人一份结构化回执，而不是只有一句话。

建议字段（基础版只落了 `failure` 四项；`status` 已在 `TicketResult`，`attempts` / `merged` 留后续）：

```ts
failure?: {
  class: string;      // FailureClass
  retryable: boolean; // 复用 retryDecision 的口径
  canceled?: boolean;
  timedOut?: boolean;
}
```

落点：`TicketResult.failure` 聚合 → `DelegationReport.failure?` → `buildWakePrompt()` 渲染
“终止：class（可重试/不可重试，超时，已中止）”；直派任务的专线汇报尾部也追加同一句。
进程崩溃 / 超时由 `classifyRunFailure()` + 池 supervisor 的 timeout 判定兜底，保证有终态回执。
