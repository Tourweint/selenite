# SSE 事件流 seq 与断点重放（调研方案建议③）

> 2026-11-04 立项。**状态：已落地（2026-11-04，落地偏差见文末）**。契约改动，按接口文档 §7 顺序执行完毕。
> 来源：`2026-11-04-参考项目架构调研（agent-autoloop与Kun）.md` 建议③。

## 〇、一句话

给聊天 SSE 流的每一帧加单调递增 `seq`，客户端重连时带 `Last-Event-ID`（或 query `since`），
服务端从**落库的会话记录**补发缺帧——目标是"弱网/锁屏重连不丢事件，也不用全量重拉 transcript"。

## 一、为什么现在做（前提修正）

调研时把这条排成"等批次二/四"，前提已失效：**批次二（审批）与批次四（回灌）2026-11-04 均已落地**。
事件种类已到位（`start/delta/thinking/progress/tool/delegate/attention/approval/done/error` 十种），
丢事件的代价不再是"少看一行 delta"，而是**丢一帧 `approval` 就少批一次、丢一帧 `attention` 就漏答一单**。

当前现实（2026-11-04 核对代码）：

- 服务端 `index.ts:436` `streamSSE` 逐帧 `writeSSE`，**无 seq、无重放**；断线后客户端唯一的恢复手段是
  `GET /messages` 全量回读 + 重新发起对话（web 端 `app.js:2151` 的 `getReader()` 手写流读取，无 EventSource，
  无重连逻辑）。
- 审批有兜底：全局待办 `GET /api/v1/agent/approvals` 轮询（接口文档 §2.1 approval 行），丢帧不致命但体验降级；
  attention/delegate 依赖"任务中心"页面拉取。**所以今天不是正确性漏洞，是体验与一致性缺口**——这决定了下面的规模控制。

## 二、设计

### 2.1 契约改动（先改 shared + 接口文档）

1. **`ChatEvent` 联合加可选 `seq?: number`**：每帧一个整数，**单条 SSE 连接内从 1 单调递增**。
   可选 = 老客户端零感知；新客户端拿它判断"我断线时缺了哪段"。
2. **`GET /api/v1/agent/chat/:conversationId/messages` 加 query `sinceSeq`**（可选，默认 0）：
   响应改为 `{ conversationId, messages, events: ChatEvent[] }`——`events` 是该会话**跨轮**的事件重放
   （从 `sinceSeq+1` 起），这是"重连补帧"的正式通道。
3. 接口文档 §2.1 事件表加 `seq` 说明 + §2.2 加 `sinceSeq`；§7 顺序走完再动代码。

**关键取舍：seq 挂在"会话"而不是"单条 HTTP 连接"上。** 单连接内编号的话，重连后两边对不齐；
挂会话则要求服务端把事件**先落库再发**（Kun 的 "persist-before-publish is load-bearing"）。

### 2.2 服务端机制

- **落库**：durable 的会话记录（`agent.sqlite`）目前只存 transcript 消息，不存事件帧。
  新增**事件日志**存放：`agent.sqlite` 加一张 `chat_events(internal_id, seq, event_json, at)`，
  或复用 delegation-receipts 的"独立小库"先例开 `events.sqlite`。**倾向前者**（同库同事务）。
  保留窗口：每会话只留最近 N 条（建议 N=500，够覆盖一次长跑轮 + 审批等待），**不追求全量审计**——
  审计是另一件事，别混进来。
- **先落库再发**：`send()` 改为 `seq = nextSeq(chat); await persist(chat, seq, event); await stream.writeSSE(...)`。
  落库失败的帧不外发（宁可客户端重拉，也不发"承诺过却补不回来"的帧）。
- **重放**：`/messages` 的 `events` 从 `chat_events` 按 seq 排序取出。断线重连的客户端流程：
  重连 → 发 `GET /messages?sinceSeq=<本地最大 seq>` → 收 `events` 补帧 → 若返回里 `messages` 的最后一条
  user 没有对应 done（轮还在跑），重新 `POST /chat` 续着看新帧。
- **不做**（明确边界）：`Last-Event-ID` 请求头方式（我们的客户端是 fetch 流读取不是 EventSource，
  query 参数更直接，两者不兼容也不必兼容）；OpenAI 兼容层不动（手机端轮询全局待办已覆盖审批，
  不走这条流）；全局心跳帧（当前无此需求）。

### 2.3 客户端

- web `app.js`：记录本地最大 `seq`；重连（页面刷新/`send()` 建流前）先 `GET /messages?sinceSeq=` 补帧再续流。
- 手机端：本轮**零改动**（契约纯增量，Kotlin 不动），适配说明文档加一行"可忽略 `seq`"。

## 三、验证计划

- 单测：seq 单调性、落库失败不外发、重放边界（sinceSeq=0 / 中段 / 超出窗口）。
- 探针（真起服务）：建流收 N 帧 → 断开 → 落几帧 → `sinceSeq` 重放精确补齐 → 旧客户端（不带 seq）行为不变。
- 老客户端回归：web 界面 + OpenAI 兼容层探针照跑。

## 四、规模与不做

预计：`shared` +10 行、`index.ts` send 链改造 + `chat_events` 表 + `/messages` 扩展 ≈ 150–250 行、
web 端 ≈ 50 行、文档三处。**一个批次内做完**，不拆多批。
明确不做：全量事件审计、跨会话事件总线、`Last-Event-ID` 头、手机端消费 seq。
回滚开关：`AGENT_SSE_SEQ=off` 时 send 链跳过落库、响应不带 `events`（回到现状）。
