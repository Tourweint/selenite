## 零、一句话

上下文环时有时无不是"加载失败"：**`lifediary.say` 播报条目以 `pi.assistant` 落地、usage 全 0，
被当成了"最后一次真实用量"**，`used=0` 时接口回 `null`、前端按旧口径整块隐藏。
修法两层：服务端跳过零用量条目（找不到真实测量就回 `used:null` 但**照样带上窗口**）；
前端只要有窗口就画环（没测量画虚线空环 + 卡里写「尚未统计」），读失败不撤已有画面。

## 一、现象与证据

用户口径（2026-11-24）：对话框右下角的上下文小圆圈"有时候不显示，有时候就显示"，
怀疑"每次都重新加载、有加载失误"，要求**每次固定显示**。

审计结论（证据级：查过代码 + 查过库）：

| 事实 | 位置 / 证据 |
|---|---|
| 环的显隐完全由 `GET .../chat/:id/context` 的 `{used, window}` 决定；任一为假就 `hidden` | `web/chat-notice.js` `syncCtxMeter()`（改前 `if (!data.used || !data.window)`） |
| `used` 取"从末尾往前第一条带 usage 的 `pi.assistant`"，**不区分 0 用量** | `src/agent/session-transcript.ts` `lastTurnUsageOf()`（改前） |
| 播报条目就是 `pi.assistant` + `usage` 全 0 | `lifecycle-thinking.ts` `sayInChat()`、`partner-runtime-do-open-partner-conversation.ts` 问候、`task-conversation.ts` `buildEntry()` |
| 派活上报 / 进度回写都走 `sayInChat`，落在主会话末尾 | 同上；`.data/agent.sqlite` 最近 60 条条目里 48 条是 `api=lifediary.say` |
| 实测序列：3884 会话最后 8 条全是 `lifediary.say`（used=0），之前才有真实 `openai-completions` 用量 | 2026-11-24 直接读库（`entries` 按 `conversation_id` 升序打印） |

所以时间线是：**真回复后环出现 → 一条上报/进度播报落地 → 下次打开会话时 `/context` 回 `null` → 环消失
→ 再发一句真回复 → 环回来**。用户看到的是"随机失败"，实际是数据源被播报条目遮住。

另有两处会让它在正常链路上继续缺位：

1. **新会话第一轮**：还没有任何 assistant 用量，旧实现连 `window` 都不给，环一直隐藏到第一轮结束。
2. **一次读取失败**：`syncCtxMeter` 的 `catch` 无条件隐藏；网络抖动 / 服务刚起时的 404
   会让已经画好的环直接消失，直到下一次 send/open。

## 二、拍板（实现取舍）

| # | 决定 | 理由 | 代价 / 备选 |
|---|---|---|---|
| D1 | `lastTurnUsageOf` **跳过 prompt 用量为 0 的 assistant 条目**，继续往前找 | `lifediary.say` 不是模型请求，上一条真实请求的用量才是"最后一次用量"；老会话不会因为尾巴上一条播报就丢环 | 若上游某轮真没回 usage，会回落到更早一轮（略旧但真实）；备选"客户端缓存最后值"会在重启/换设备后丢，且更不诚实 |
| D2 | 没有真实测量时 **`used:null` 但 `window` 照给**（形状不变） | 前端能画空环并说明"尚未统计"，而不是靠 0 假装测过；窗口来自会话模型，与用量无关 | 老客户端若把 `used:null` 当"整块隐藏"仍按旧行为（向后兼容）；**不把 used 改成 0**，避免"用量 0%"的误导 |
| D3 | 前端 **有窗口就显示**；`measured=false` 时空环 + 虚线轨道 + 卡里「尚未统计 / 窗口」 | 用户口径"每次都固定显示"；虚线区分"没测过"与"真的 0%" | 新会话第一轮期间就能看到环（0 填充） |
| D4 | 读取失败 **不撤已有画面**：同一会话已有环就保留；换会话后的首拉失败才隐藏；网络错误重试一次（700ms） | 直接对应用户"加载失误"的怀疑；404/500 走正常隐藏分支，不进重试 | 极端情况下可能短暂显示上一轮数值（同会话内），比整块消失可接受 |
| D5 | 新会话 `start` 帧到达即拉一次 `/context` | 不用等第一轮 `done` 才有环；`start` 前会话已落盘（`openOrCreateChat` 先建后流） | 每轮多一次只读请求；已有 `done` 那次，量级可忽略 |

## 四、明确不做

- **不做轮询 / 定时刷新**：环的语义是"最后一次真实请求的 prompt"，只在 open / start / done 时更新足够；
  轮询只增加空转请求。
- **不把 `used` 缺失变成 0**：会让"没测过"和"用量 0%"混为一谈。
- **不在前端本地缓存用量 / 自己算窗口**：窗口的唯一事实源在服务端模型目录，双份数据会漂。
- **不改 mock（未配置 LLM）口径**：`readLlmConfig()` 为空时窗口确实不存在，环继续隐藏
  （`接口-端点2` 已写"mock 下两者皆 null"）。
- **不新增回滚开关**：这是缺陷修复 + 显示口径，不是新能力；回退方式就是回退这三处改动。
- **不动 `lifecycle-thinking.ts` 的 `lastTurnInputTokens`**：它有同款"零用量播报遮最后一轮"的问题
  （影响首次工具调用时是否升思考档），但属于另一条链路的行为，**本次不改**，已登记给用户决定。
