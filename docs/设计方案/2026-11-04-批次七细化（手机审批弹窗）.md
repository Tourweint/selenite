## 〇、一句话（传输按审查改定）

**主链路 = 轮询 `GET /api/v1/agent/approvals`（全局形态，不带 conversationId）**：App 前台每 20–30s 轮一次 + 回前台/冷启动补拉——这样**桌面触发的审批手机也收得到**（这正是主要用途），且与批次六契约（"手机不进聊天流、走全局待办轮询"）一致，harness 零改动成立。SSE 的 `lifediary_approval` 事件只作**加速提示**（收到就立刻触发一次刷新，不做解析主链路的依赖）。App 内弹窗逐条展示，点「允许/拒绝」→ `POST /api/v1/agent/approvals/:callId`。

## 一、解析与答复（审查订正后的事实）

1. **答复 body 是 `{decision:"approve"|"reject"}`**（服务端 `approval-api.ts:72-73` 只认这两个词，`approved/rejected` 是返回的 `status`——第五轮审查抓的错）。
2. **返回 status 分支**：`approved/rejected` → 提示"已处理"；`timeout/aborted` → 提示"已超时/已中止（可能在电脑上处理过了）"；HTTP 404 → 视为"已失效"，静默关弹窗；其他错误 → 中文 toast。**不能只判 isSuccessful**（幂等 200 + 原 status 会让人误以为批准成功）。
3. `lifediary_approval` 加速解析照 attention 四步（`approvalOf` Client:417-426 范式 / Wire.kt / StreamEvent / 分派链），但作用仅 = 触发 `coordinator.refresh()`。
4. 契约登记：App `接口契约.md` §0 调用点计数更新（新增 approvals GET/POST + policy GET/POST，按该文档现有粒度）；**§3.3 一并修正**——现文"只读 delta.content 与 [DONE]"与代码不符（早已读 progress/delegate/attention，本批再加 approval）。

## 二、状态与弹窗

1. **新建 `feature/chat/ApprovalCoordinator.kt`**（app 作用域状态持有者，不放 ChatViewModel——审批不属于聊天流生命周期）：持有 `StateFlow<List<ApprovalPrompt>>`；`start()` 注册 LifecycleObserver——**前台每 25s 轮询 + ON_RESUME/冷启动即拉**；`answer(callId, decision)` 调 API 后从列表移除并刷新；`deadlineAt` 到点自动从列表移除（弹窗自动收口，审查 S4）。
2. **新建 `feature/chat/ApprovalDialog.kt`**（M3 AlertDialog，照 ChatScreen.kt:347-365 范式）：挂 `MainActivity` 根 Box（:649）**一行**（既有文件 1062 行，新代码一律进新文件，审查 A2）；每次只弹列表最早一条，`onDismiss` = 只关弹窗不改服务端（条目留在列表，下次轮询还在）；正文 = 工具名 + args 摘要 + 剩余时间。
3. **并行审批**：列表天然支持多条（审查 S3，不用单字段）；弹窗逐条处理。
