# web/app.js 按职责拆分（78 个平铺模块）

> 一次性的结构整理：把 25,467 行的单文件界面层，按职责拆成同目录的兄弟模块，不碰行为。

## 结论

| 项 | 结果 |
|---|---|
| 拆分前 | `ts/apps/server/web/app.js` 25,467 行 / 1,103 KB / 1,050 个顶层语句 |
| 拆分后 | 78 个兄弟模块 + 入口 `app.js` + 无依赖叶子 `icons.js`，共 80 个文件，同目录平铺 |
| 最大文件 | `settings-router.js` 670 行（含 import，正文 634 行，只有 `renderSettings` 一个函数） |
| 超过 500 行 / 超过 1000 行 | 9 个 / 0 个 |
| 代码改动 | 正文逐行原文搬运，函数体一字未改；只有 3 处结构性调整（见「三处不得不动的地方」） |
| 页面入口 | `index.html` 不动：仍是 `<script type="module" src="/assets/app.js">`；app.js 变成「side-effect import 78 个兄弟 + 文末启动代码」 |
| 服务端 | `src/web.ts` 不动：`/assets/:file` 只认单段文件名，所以模块只能平铺在 `web/`，不能建 `modules/` 子目录 |

「尽量不要超过 500 行、最多不超过 1000 行」的落点：正文超 500 行的 9 个（634 / 572 / 554 / 544 / 526 / 522 / 515 / 515 / 513），最大 634 行；没有任何一个超过 1000 行。

## 边界是怎么定的

- 以文件里作者手写的 97 条 `/* ── 分区 ── */` 横幅当天然职责边界，再按耦合簇把大分区切开（每分区行数 / 语句数 / 跨区引用统计）。
- 切分用 TypeScript 编译器 API 读 AST，以「顶层语句」为最小单元：区间起点和终点必须落在语句边界上，绝不切在语句中间。
- 发射时按**连续行区间原文搬运**，不是只搬语句 `getStart()`~`getEnd()`——只搬语句会丢掉语句前面的说明性注释。区间切分保住注释、原始顺序和空行节奏。
- 80 个文件的区间**无缝覆盖**原文件 9–25467 行（1–8 行是原文件头注释，已移入新 app.js 的头注释；第 9 行 `import { createStreamRevealer }` 交给需要它的模块各自 import）。
- 每个模块的 `export { … }` 追加在文件末尾，`import { … }` 按「这个模块引用了谁、谁声明在哪个模块」自动生成；不做 `export` 前缀手术。

## 三处不得不动的地方

原文件只有一个作用域，拆开后 ESM 导入的绑定**不能赋值**，所以下面三处做了最小结构改动（其余全部原文）：

| 位置 | 原状 | 现在 | 为什么 |
|---|---|---|---|
| 快捷设置抽屉的 10 个 `let cs*`（原 L8667–8676） | 10 个平行的 `let`，被 partner-roster / settings-employee / -persona / -contract / -model / -permission 六个模块赋值 | 收成 `const cs = { page, archiveTab, timer, catalog, policy, target, detail, providers, archive, archiveJob }`，引用改写成 `cs.page` | 跨 6 个模块写，只能靠对象属性共享。标识符替换是 AST 级的，只动代码、不动注释与字符串 |
| 花名册领域缓存（原 L4267–4270） | `let rosterDomainActive` / `let rosterDomainRows`，一个被 loadRoster 写、一个被 renderRoster 写 | 收成 `const rosterDomain = { active, rows }` | 同上：两个模块各写一个字段 |
| `const CS_ICONS`（原 L8837–8858） | 抽屉图标表，被 `groups-settings.js` 在**顶层求值时**读（`chevron: CS_ICONS.chevron`） | 单独成 `icons.js`（零 import 的叶子模块） | 环里「谁先求值」不确定；叶子模块永远先于引用方求值，从根上没有 TDZ |

另有几处「声明在 A、赋值在 B」的单个 `let`（`approvalPopKnown`、`pairTimer`、`connPhoneCount`、`projectAnchor` / `projectLoading` / `projectOpenToken`），处理办法是把**声明区间划给写入方**，读的一方 import 只读——没有引入新形态。

## 循环 import 是预期内的

原文件里函数互调没有方向（`el` 413 次、`state` 297 次、`groups` 136 次是全局枢纽），按职责切完，模块之间必然互相 import（实测 75 个模块在环上）。ESM 允许环，前提是**模块顶层求值时不向别的模块取 const**：

- 各模块顶层只做声明、常量表、事件监听注册；
- 全文件的启动代码（原 L25397–25467 的 `void (async () => {})()`）原样留在入口 `app.js` 文末，等 78 个模块都求值完才跑；
- `dom.js`（`el` + `KEY_*`）和 `icons.js` 必须保持**叶子**（不 import 任何模块），因为它们被十来个模块在顶层求值时读。

后续新增模块要守住这条：**模块顶层不许 `const X = 别的模块的 const`**（要读就放进函数体里）。

## 明确不做

- 不改任何行为：函数体、常量、正则、模板串一字未改；也不顺手修 bug（见「遗留」）。
- 不拆单个函数内部：`renderSettings`（634 行）、`renderCsPersonaPage`（276 行）、`createWorkPanel`（238 行）等按原样整块归属某个模块。
- 不引入构建 / 打包 / TS：这一层继续「原生 ESM，改完刷新就见效」。
- 不建子目录：服务端 `/assets/:file` 白名单只认单段文件名。
- 不动 `index.html` / `style.css` / 服务端代码。

## 遗留的两个 bug（拆分时原样保留，同日单独修掉）

- `createToolChips` 在 `tool-flow.js` 里被调用两次，但没人 import 它（`web/tool-chips.js` 导出了同名函数、全仓库零引用）。拆分时按「不改行为」原样留着，随后补 `import { createToolChips } from "./tool-chips.js"`，引用不再悬空。这条线（`createToolFlow` / `toolFlowFromSteps`）现在**没有任何调用方**，E1 的「话→灰块→话」形态还没接进渲染路径（`style.css` 里也没有 `.tchips` 样式），现行渲染走 `work-panel.js` + `workPanelFromSteps`；接上还是删掉是独立的一次决定。
- `settings-reminders.js` 里 `notify("定时任务", …)` 的 `notify` 全文件无定义（同行附近有 `maybeNotify`）。已改成 `maybeNotify("定时任务", …, null, "attention")`，走桌面通知的统一闸（开关 / 时机 / 可见性），提醒到点现在真会弹。
- `scripts/memory-qa/render-smoke.mjs` 在拆分**之前**就已经是红的（旧版记忆页函数早改名为 `memorySettingsMarkupLegacy`，脚本还按 `memorySettingsMarkup` 取，切出来的源码直接语法错）；本次顺手重指 + 补一个 `attr` 桩，恢复绿灯。
