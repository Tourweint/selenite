## 现状审计（2026-11-13，两路调查员实读）

## 关键实现事实（2026-11-13 核实）

- **durable 内核（@earendil-works/pi-durable 1.4.0）没有删除 API**：`Storage` 接口零 delete，注释明确 "immutable conversation/entry creation"。存储是 SQLite（`.data/agent.sqlite`）：`conversations / entries / tasks / submissions / documents / documentRevisions / recordIds`。
- **fork 是引用不是复制**：`ConversationRecord.parent = {conversationId, at}`，读取实时沿父链回放（`sqlite/storage.js readEntries`）；fork 时只有文档被复制。**物理删父会话会坏子会话**，且 parent 边只存在 `conversations.record` JSON 里、无反向索引（找子会话需全表扫）。
- **运行中判定现成**：`conversationIsBusy()`（`agent/session.ts:713`）读 `pi.live` 文档的 `run` 字段（内核注释 "present exactly while busy"）。现 archive 端点不判忙；`forkForEdit` 已有 409 先例。
- **搜索零索引**：三路内容搜索全部实时重放 durable，枚举面是 `Chats` 文档映射。删除时同步清映射，搜索自动不含它，无需清索引。
- **lastAt 不持久化**：`readChatStats` 现场重放算（`max(pi.user/pi.assistant 的 timestamp)`）。`listChats` 会按 limit 截断，**自动归档不能走活跃清单**（要收的恰是旧会话），须全量枚举 `Chats.byExternal`。
- **后台定时器范式**：autonomy.ts 的 `syncSweepTimer`（按需开关 + `unref`）已在生产接线，照此写。
- **flags 机制**：`.data/agent-flags.json` 覆盖 env、懒读热生效（`flags.ts FLAG_DEFS`，`hot: true` = 消费处函数内读）。

## 决策

### 1. 归档页重做成"归档管理"形态（批 B）

- 「已归档的会话」卡重做：**按项目分组**（有 projectName 的按项目一组；有 projectId 但查不到项目的归「项目已删除」组；无 projectId 的归「未归类」组），每组一张折叠卡 + 计数，默认折叠、展开显示 50 条 + "显示更多"。
- 顶部筛选区：标题搜索（现有）+ **排序下拉**（归档时间 / 最后活跃，倒序）+ **项目下拉**。
- 行内动作：**恢复** + **永久删除**（新增，见第 4 条）；组头动作：**全部取消归档**（组内逐条串行调 `/unarchive`）。
- **页级"全部恢复"按钮退役**（ZCode 无此物，组级恢复取代之）；`POST /chats/restore` 端点保留不删（兼容与回滚）。
- 「已归档的项目目录」卡保持现状（恢复不删项目、不动磁盘），不参与本次重做。
- 空态三态区分：没有归档 / 筛选无结果 / 加载失败+重试（后两者已有）。

### 2. 归档防误触（批 A + 批 B）

- **服务端**：`POST /chat/:id/archive`（含 `/hide` 别名）先过 `conversationIsBusy`，忙则 400 带说明「会话正在运行，请先停止再归档」（业务拒绝 400 带说明，与 `forkForEdit` 409 同款思路）。归档仍不中断运行——是"先停止再归"，不是"归档即停止"。
- **前端**：会话行归档图标点击后**行内二次确认**（行内出现「确认归档 / 取消」小条，不做弹窗；ZCode 同款）；当前正在流式输出的会话图标禁用态 + 悬停提示（其余行 UI 不知忙态，由服务端 400 兜底，toast 显示服务端说明）。
- 项目归档已有确认弹窗，不动。

### 3. 自动归档（批 A + 批 B）

- **开关与天数**：flags 新增 `ARCHIVE_AUTO_ENABLED`（默认 `false`，hot）与 `ARCHIVE_AUTO_DAYS`（默认 `30`，最小 1，hot）；env 同名键兜底，flags 文件覆盖 env；设置 → 会话页加开关 + 天数输入（走 `PUT /agent/flags/:key`）。
- **调度器** `agent/auto-archive.ts`：照 autonomy.ts 范式——启动后首轮延迟 5 分钟，之后每小时一轮；`unref`；开关关闭时定时器不开。**不走 durable sleepUntil**：这是低频清扫型任务，不需要"到点必响"的可靠性，错过一轮下轮补上（差异在方案里说明，不动系统架构 §3 的口径——那说的是触发型提醒）。
- **判定**：全量枚举 `Chats.byExternal`（不走 `listChats`，防截断漏旧会话）→ 只取 `chatKind=worker` 的普通会话（chief 是主对话、`partner-`/`task-` 有自己的生命周期，都不收）→ `lastAt < now - days` → 跳过已归档、跳过置顶（`chat-meta.pins`）、跳过 `conversationIsBusy`。**每轮上限 50 条**，防长阻塞；剩余下轮继续。
- 归档动作复用 `archiveChat()`（记 `archivedAt`），日志只记条数与 id 数量，不含内容。
- **已知边界（如实登记）**：不做"归档事件广播"——当前打开的会话被自动归档后，界面要等下次 `loadChats` 才反映；该会话仍可继续聊（归档不影响正文读写）。ZCode 有事件广播关侧栏 tab，咱们的会话页没有对应的"tab"概念，第一版不做。

### 4. 永久删除协议（批 A + 批 B）

**范围（硬边界）**：只允许普通会话（`chatKind=worker`）；chief / `partner-`（执事与群）/ `task-`（任务）拒绝删除。只删 durable 数据 + 三张映射 + chat-meta 条目；**不删**：文件与附件、记忆四层、派活回执、磁盘目录。

**门槛**：只允许删除**已在归档里**的会话（未归档 → `blockedReason: "not-archived"`，ZCode 同款）。UI 也只在归档页行内给按钮。

**分叉以子树为单位连根删**（与 ZCode"保留独立分叉"不同，这是咱们存储决定的，见备选表）：预检扫 `conversations` 全表找 `record.parent.conversationId` 落在目标集合内的子孙（BFS 逐层），**整条子树一起删**（从叶到根），不产生悬挂父链。确认弹窗必须列全子树名单。

**端点**：

- `GET /api/v1/agent/chat/:id/deletion-preview` → `{ conversationId, title, rounds, lastAt, archivedAt, blocked?: { reason: "not-archived" | "kind" | "busy" | "chief" | "task" | "partner", detail }, subtree: [{ conversationId, title, rounds, lastAt }], estimate: { conversations, entries, tasks, submissions } }`（blocked 时 subtree 为空数组；estimate 用 SQL COUNT，不逐条读 context）。
- `POST /api/v1/agent/chat/:id/delete` → 执行前**重跑一遍预检**（预检与执行之间状态可能变化：被恢复、变忙、多了分叉），任一 blocked 拒绝 400；成功 → `{ ok, deleted: { conversations, entries, tasks, submissions } }`。

**执行时序**（durable 无删除 API，走裸 SQL，安全顺序）：

1. 复用 `discardHarness()`（`lifecycle.ts:231`）关闭 Harness（同一进程独占 storage，先关门防并发读写）。
2. 拿一把**删除互斥**挡住 `getHarness()`（删除期间新请求排队等待而不是重开 Harness），并再次全量 busy 复核。
3. 临时打开 SQLite 连接，按子树叶→根顺序删：`documentRevisions`（按 document_id）→ `documents`（`scope_kind='conversation' AND owner_id` 子树 + 子树 tasks 的 task 作用域文档）→ `entries` → `tasks` → `submissions` → `conversations`。`recordIds` **刻意不删**（孤儿行只服务全局 id 唯一性，无害；清理它收益为零风险高）。
4. 清服务端映射：`Chats` / `ChatKinds` / `ChatProjects` 文档里子树的条目（走服务端既有文档写路径）+ `chat-meta.json` 的 `titles/archived/archivedAt/pins` 条目（顺手把 chat-meta 写路径补成原子写，参照 flags.ts）。
5. 放互斥，`getHarness()` 重开；响应带删除计数。

**回滚开关**：`CHAT_HARD_DELETE`（默认 `true`；`false` 时两个端点 400「永久删除已关闭」）。flags + env 双落点。

## 备选与为什么不选

| 备选 | 为什么不选 |
|---|---|
| 分叉保留（ZCode 式）：删父会话、子会话历史物化（复制 entries 进子会话） | durable 的 entry 全局 id 单调递增、context 按 id 序回放——复制进来的父历史只能排到子会话已有条目**之后**，时序错乱；手工改 id 是对内核表做非法手术，风险不可控。 |
| 等上游 pi-durable 提供删除 API | 版本 1.4.0 无此路线图迹象；个人规模等不起。 |
| 永久删除范围扩到执事/群/任务会话 | 执事会话承载人格连续性、任务会话与派活回执/审计关联，删了账就断了；先收普通会话，扩范围另立方案。 |
| 删除时连附件文件一起清 | 附件可能被记忆/其他会话引用，引用关系没有账；ZCode 也保留被引用附件。磁盘清理另立项。 |
| 自动归档走 durable sleepUntil（范式 3） | 清扫任务不需要到点必响；每小时定时器 + 错过补扫够了，不给系统添"重启唤醒链"。 |
| 自动归档默认开 | ZCode 默认关；翻案的是"有这个能力"，不是"替用户做主"。 |
| 保留页级"全部恢复" | 组级恢复已经覆盖"批量恢复"意图；页级一键恢复全部会把刚归档的也全放回来，与"归档是清理动作"的心智冲突。 |
| 删除前要求输入标题确认 vs 三清单确认 | 咱们的删除对象是"会话+它的编辑分叉"，清单天然比 ZCode（跨附件/跨引用）短；名单 + 标题确认足够，别把确认做成流水账。 |

## 安全与回滚

- 删除互斥期间新请求排队不重开 Harness，杜绝"删到一半有人写"；执行前全量 busy 复核。
- 预检与执行之间的状态漂移靠"执行前重跑预检"收口，不做事务级 CAS（SQLite 单文件 + 单进程，够了）。
- 回滚开关三个：`CHAT_HARD_DELETE=false`（端点 400）、`ARCHIVE_AUTO_ENABLED=false`（调度器不开）、归档页 UI 回退 = 组卡退化为平铺卡不做（纯前端，回滚即 revert）。
- `POST /chats/restore` 保留：即使 UI 退役，旧客户端/探针不 404。
- 删除操作日志只记计数与 id 枚举，不含标题/正文（密钥与内容不进日志的既有口径）。

## 明确不做

- 不删执事/群/任务会话、chief；不做项目目录的磁盘删除；项目登记的删除（连登记一起）不做。
- 不清 `recordIds` 孤儿行；不清附件文件；不动记忆四层与派活回执。
- 不做归档事件广播（SSE 推"某会话被归档了"）——打开中的会话被自动归档后靠下次 loadChats 反映。
- 不做归档对象的导出/备份前置（删除不可逆，弹窗写明；要备份走既有全量导出）。
- 不做 ZCode 的"未归档直接删"路径——门槛只有归档一条。
- 不做自动归档的天数分档/白名单（一个天数全局生效）。

## 验证计划

- 单测：busy 拒绝归档（400）、预检 blocked 各 reason（not-archived / kind / chief / busy）、子树 BFS（父→子→孙）、删除计数、删除后 `Chats/ChatKinds/ChatProjects` 与 chat-meta 无残留、flags 三键热读、自动归档判定（置顶/忙/非 worker 跳过、上限 50、开关关不动）。
- `pnpm typecheck`；`pnpm --filter @lifediary/server test`。
- `pnpm --filter @lifediary/server http`：§14.8 覆盖归档→预检→删除→列表/搜索不含它；busy 400；`CHAT_HARD_DELETE=false` 400。
- 隔离实例（独立 DB + env 隔离）+ 真 HTTP + 浏览器：分组折叠、排序、项目筛选、组级恢复、永久删除弹窗全流程；自动归档开关打开 + 天数调小 → 等一轮 → 旧会话进归档。
- `pnpm probe` 不跑：不动内核提交/流式/闸门（如实记录）。
