# 扫尾批 8a 方案：插话队列服务端化（刷新不再丢话）

> 状态：**方案随批实施（2026-11-08）**。上位：扫尾计划 A3（用户拍板做）。
> 关键事实（2026-11-08 读码核实）：服务端 `whenBusy: followUp|steer` 已落地（shared:114-120，2026-11-07 消息即引导批），忙时提交走 `conversation.submit()` **落 durable 持久化**，http 探针 §19 已验"三次合法投递都落库"。丢话的根源是**前端**：`web/app.js:580` 起"忙时发的消息先在本地数组排队，本轮结束后依次真发"——队列只存在浏览器内存里。

## 一、修法（纯前端消费既有服务端能力）

1. **忙时 Enter → 立即提交**：`whenBusy:"followUp"`（保持"这条是下一轮指令"的既有排队语义不变），提交即落库——刷新/断线后回读 transcript 就能看到这条话，不再依赖本地队列。
2. **既有插话快速路（steer）不动**：那是"插进当前轮"语义，与本项正交。
3. **本地队列退役**：删掉 app.js 的本地排队数组与轮末补发逻辑；乐观显示保留（发出即上屏，followUp/steer 帧回流后归位——两帧已有渲染路径）。
4. **多条插话**：每条 Enter 都立即提交，durable 按提交顺序排队，天然有序；无需前端排序逻辑。
5. **语义不变承诺**：唯一行为变化 = 刷新不再丢；插话出现的轮次时机与改前一致（followUp=下一轮）。

## 二、明确不做

- 不加服务端开关（服务端零改动；回滚 = 前端一处 revert，不造开关通胀）。
- 不改 steer 语义、不做"选这条插进当前轮/下一轮"的 UI 选择器（要的话将来单提）。
- 不动手机端（手机无本地队列问题，其插话路径本就走服务端）。

## 三、验证

- 探针/单测：忙时连续三条 followUp 提交→落库有序；刷新（重开页面）后回读含这三条；steer 快速路回归。
- 浏览器手验（派单人）：打字→AI 回答中插话→**当场刷新**→插话还在并按序被消费。
