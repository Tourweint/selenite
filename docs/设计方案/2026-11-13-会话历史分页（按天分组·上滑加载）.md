> 状态：**已落地**（2026-11-13）。下沉落点：契约 → `docs/基线文档/接口-端点1-对话与兼容层.md` §2.2；
> 机制与边界 → `docs/基线文档/系统架构.md` §7；开关 → 主册 §6 + 分册7 §2.20；
> 落地细节 → `docs/变更记录/2026-11-13-会话历史按天分组与上滑加载.md`。
> 与长期文档冲突时，以长期文档为准。
>
> 上位：用户口径「主管的对话太多了……应该按天存。往上滑加载时，按照每天加载，往上滑一段就加载当天的一段，
> 避免主管说的话过多」。

## 结论

| 项 | 结论 |
|---|---|
| 存储 | **不按天拆会话**。消息自带时间戳，SQLite 有 `(conversation_id, id DESC)` 索引；按天只是"看"的方式 |
| 读 | `/messages` 新增可选 `page=1` / `before=<不透明游标>`，用 durable 的 `Conversation.entries()` 倒扫，只读一页 |
| 页边界 | 以"轮"（`pi.user` 开头）为最小单位；累计 ≥20 条后优先在自然日边界收页；一天太长则当天分几段 |
| 前端 | 打开只拉一页；滚到顶自动前插上一页；按天插"今天 / 昨天 / M月D日"分隔条；滚动位置不跳 |
| 回滚 | `CHAT_HISTORY_PAGING_ENABLED=false`：服务端忽略分页参数，前端回到一次 200 条、无日期条 |
| 手机 | 契约纯增量，手机端零改动（仍发 `?limit=N`，拿到最近 N 条） |

## 现状审计（2026-11-13 实读）

- 电脑端 `openChat` 一次 `GET /messages?limit=200`（`ts/apps/server/web/app.js`），**没有上滑加载**；
  也没有任何日期分隔（时间戳只挂在消息 `title` 上）。
- 服务端 `readTranscript()`（`ts/apps/server/src/agent/session.ts`）每次 `conversation.context()` 把
  **整段活跃上下文读进内存**再 `slice(-limit)`。对话越长，每次打开越慢——不只是界面显示多。
- `Conversation.entries(query, limit, cursor)`（pi-durable 1.4.0）是现成的倒序游标分页：
  `maxEntryId` 含边界、cursor 排他、`(conversation_id, id DESC)` 索引命中；本仓库此前零调用。
- 会话/任务/用量都落在同一个 `AGENT_DB_PATH` SQLite；`messageIdOf` 的下发 id 是
  `sha256(会话 uuid:条目 id)` 的 uuid 形状——**durable 自增整数不外泄**是硬约束，新游标不能直接把 entry id 摆到 URL 里。
- `context()` 的"活跃上下文"从最新 `head` 标记（reset / compaction）之后开始；`entries()` 是
  fork-aware 全历史，会带出 head 之前的旧段。两者不能混用。
- 检索的既有口径：`searchTranscripts` / `recall_sessions` 只读每个会话**最近 200 条**
  （`agent/session.ts:searchTranscripts`），更早的话搜不到。这是独立缺口，本批不碰。

## 为什么不"按天存"

1. **主管会话是一条连续上下文**：模型每轮要看到前面在聊什么；按天拆成新会话 = 每天让总管"失忆"，
   跨天的派活、记忆抽取、任务专线、群组路由都要重新挂接。
2. **存储层不需要**：时间戳本来就在每条消息里；SQLite 的倒序索引 + durable 的 cursor 分页足够。
   按天拆文件/拆表只会把"读一页"变成"先找天、再找会话、再拼上下文"。
3. **检索也不会因此变好**：拆开后要跨 N 个会话搜，反而更慢；检索要修的是索引/扫描口径，另立一批。

## 决策

1. **契约（纯增量）**：`GET /messages` 增加可选 `page=1` + `before`。响应在分页模式多
   `hasMore` / `nextBefore`。**不带新参数时逐字保持旧形状**（手机端零改动）。
2. **游标不透明**：AES-256-GCM 加密 `{c: 会话对外 uuid, m: entry 上界}`，key 由 `AGENT_TOKEN` 派生。
   跨会话 / 被改 / 换过令牌一律 400；客户端回落重开，不猜。
3. **页装配**：`readTranscriptPage()` 倒扫 `entries()`，按 `pi.user` 切轮，每轮用与
   `readTranscript` 同一个 `foldTranscriptEntries()` 折叠（工具步骤、`say` 步、`workMs`、`files` 全部一致）。
   - 不切轮：一页的第一条通常是 user；工具步骤不会跨页丢。
   - 累计 ≥ `min(20, limit)` 条后，遇到上一天就收页；`limit` 是硬上限（默认 50，夹 1..200）。
   - 遇到最新 `head` 标记就停：与 `context()` 的活跃历史同语义，压缩前的旧段不翻出来。
   - 单页扫描 4000 条 entry 的保险丝：一轮里几千个工具结果时宁可少收几轮，不拖死请求。
4. **前端**：初始 `?page=1&limit=50`；顶部状态条（加载中 / 加载更早 / 已到最早）；
   滚到 120px 内或点按钮→`loadOlderMessages()`；前插进 `DocumentFragment`，按
   `scrollHeight` 差恢复 `scrollTop`。**不复用 `openChat`/`clearThread`**，不重置 `maxSeq`，
   流式补帧、审批卡、编辑入口不受影响。
5. **日期条**：前端按消息 `at` 用本地日历日分组；群聊已有的 `groupDayOf/groupDayLabel`
   抽成通用 `dayKeyOfAt/dayLabelOf` 后两处共用（"不能 `slice(0,10)`"的踩坑注释保留）。
6. **回滚开关**：`CHAT_HISTORY_PAGING_ENABLED`（缺省开，`hot:true`）。false 时服务端忽略
   `page`/`before`，web 回到旧的 `limit=200` 路径（日期条与顶部条都不渲染）。

## 备选与否决

| 备选 | 为什么不选 |
|---|---|
| 按天拆 durable 会话 | 主管失忆；任务/记忆/搜索/派活全要重接线；不是"看不到"的问题 |
| offset 分页（`?offset=N`） | 越翻越慢（SQLite 仍要跳过前 N 条），且新消息插入会让 offset 漂移 |
| 把 entry id 直接当 `before` | 违反"durable 内部自增整数不外泄"；猜 id 就能定位别人的历史 |
| 前端只拿 `limit=200` 本地切片 | 服务端还是要整段读；对话再长一点就回到原问题 |
| 整页/整屏虚拟列表 | 一页 50 条的 DOM 量可控；先解决数据面，虚拟化等真卡再立项 |

## 契约变更清单

- 新增查询参数：`page=1`、`before`（不透明串）；分页模式 `limit` 默认 50、取值 1–200、非法 400。
- 新增响应字段（仅分页模式）：`hasMore: boolean`、`nextBefore?: string`。
- 错误：`400 {"error":"bad_request","message":"before 游标无效" | "limit 必须是 1..200 的整数"}`。
- 旧行为不变：不带 `page` / `before` 时 `limit` 解析（含 `limit=0` 全量）与 `sinceSeq` 补帧逐字不变。
- 开关：`CHAT_HISTORY_PAGING_ENABLED`。

## 明确不做

- **不按天拆会话、不改存储结构**。
- **不改检索**：`recall_sessions` 与会话列表搜索的"最近 200 条"上限只登记（系统架构 §7），
  搜索页全量扫描也不动——另立一批。
- **手机端不做上滑加载**：接口向后兼容即可，手机本次零改动。
- **不动 pi-durable 的 compaction / 模型上下文压缩**；本批只管"看历史"，不管"模型记得多少"。
- 不做消息级虚拟列表/窗口回收。

## 回滚与安全

- `CHAT_HISTORY_PAGING_ENABLED=false` 一行回滚（服务端 + web 两侧都认这个键）。
- 游标含加密串，不含明文 durable 自增 id；`AGENT_TOKEN` 轮换 → 旧游标 400，客户端提示刷新。
- 分页只读、无新写入；删除/归档/永久删除的既有闸门与路径不变。
