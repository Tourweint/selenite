# 派活的回头路：回答能回到原单

> 2026-11-02。chancellor 有了 resume（v1.2），但 harness 这头还没把「用户的回答」路由回那张单。

## 结论

三条：

1. `delegate` 加一个可选参数 `resume`：`true` = 接着上一张单跑，不重新派。
2. harness 按会话记「最后一张单」，只记 id，不记内容。
3. 模型看到用户回答了问题，自己决定用 `resume: true`——**不猜、不自动**。

## 一、现在的断点

链路上有一环是断的：

```
worker 卡住 → 单子进 needs_you → 「⚠ 需要你：验证码是啥？」回到对话
                                        ↓
                              用户回「1234」
                                        ↓
                    ✗ 断在这里：这句话变成一条普通消息
                      模型只能重新派一张新单
                      → Mika 那边的老 task 还在跑，两个任务抢同一个屏幕
```

**这不是小问题**：重开一张单，Mika 会从头再来一遍，可能重复操作。

## 二、改法

### 2.1 `delegate` 加 `resume`

```ts
parameters: Type.Object({
  requirement: Type.String({...}),
  resume: Type.Optional(Type.Boolean({
    description: "接着上一张单跑（用户回答了你刚才问的问题时用这个）。不填 = 新派一件。"
  })),
})
```

工具描述里要写清：

> 上一轮你派出去的活卡住了、并且你问了用户一个问题，用户回答了 —— 这时用 `resume: true`，
> `requirement` 里只写用户的那句回答（比如「验证码 1234」），不要重述整个任务。
> **不要重新派**：重派会让对方从头再做一遍。

### 2.2 harness 记住"最后一张单"

按会话记 `lastTicketId`：

| 存哪 | 为什么 |
|---|---|
| 内存 Map（conversationId → ticketId） | 够用：resume 只可能发生在同一轮对话里 |
| **不落库** | 落库要改表结构；而且进程重启后老单子也没法 resume（chancellor 那边 task_id 还在，但会话已经断了） |

**代价（要写清）**：进程重启后 `resume` 失效，只能重新派。这是可接受的——重启是低频事件，
而落库带来的复杂度（迁移、清理、过期）是常态成本。

### 2.3 没单可 resume 时怎么办

用户可能在根本没有卡住的单时说了句"1234"。这时：

```
resume: true 但会话没有 lastTicketId
  → 不报错，当成普通派活（等价于 resume: false）
  → 但在返回里加一句：「（没有可续的单，已按新活派）」
```

**不报错**，因为模型判断失误不该让用户看到一条红色错误。但**必须告诉它**，否则它会以为续上了。

## 三、验收标准

| # | 验收项 | 怎么算过 |
|---|---|---|
| 1 | `resume: false` 行为不变 | 不带 resume 连派两次 → 两张单 |
| 2 | `resume: true` 接上原单 | 造一个 needs_you → 回答 → 同一张单继续，**ticket 数不变** |
| 3 | 没单可续时不报错 | 空会话里 `resume: true` → 正常派新活，返回里带说明 |
| 4 | 会话隔离 | A 会话的单不会被 B 会话 resume |
| 5 | 重启后行为明确 | 重启后 `resume: true` → 走"没单可续"分支，不崩 |
| 6 | 回归 | 派活进度帧、attention 帧、闸门、tasks/http/diary 全过 |

第 2 条是核心。

## 四、这条会怎么错

1. **如果自动判断"这句像回答就 resume"**，会把新需求当成回答塞进老单。必须模型显式说 `resume: true`。
2. **如果 resume 时把整个任务重述一遍**，worker 会以为要重做。`requirement` 只放用户那句回答。
3. **如果 lastTicketId 落库**，要处理迁移、过期、清理，而且重启后照样接不上（会话已断）——白付复杂度。
4. **如果没有"没单可续"的兜底**，模型判断失误就会给用户一条错误提示。
5. **如果跨会话共享 lastTicketId**，A 会话能把活续到 B 会话的单上，这是串单。
6. **如果这头不做**，v1.2 的 resume 只是个库能力，手机上永远用不到。
