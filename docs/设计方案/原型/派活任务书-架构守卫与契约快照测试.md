## 任务一：架构守卫测试（新文件 `apps/server/src/arch-guard.test.ts`）

背景：AGENTS.md 硬约束"新工具要进闸门"目前只靠人肉审查，要把它变成测试断言。三组断言：

### 1.1 闸门完整性（核心）

事实（已核实）：
- `apps/server/src/tools.ts` 的 `createTools()` 返回 `ToolRegistration[]`：固定含 `remember` / `recall` / `remind`（注意：提醒工具的 name 是 **`remind`**，不是 `set_reminder`）；`deps.skills` 存在时追加 `skill`；`deps.delegate !== false` 时追加 `delegate` / `propose_project`。
- 内核五件来自 `@earendil-works/pi-durable/tools` 的 `CodingTools`：`read` / `write` / `edit` / `bash` / `powershell`（在 `node_modules/@earendil-works/pi-durable/dist/tools/*.js` 里 grep 核实过）。
- `WRITE_TOOLS`（`apps/server/src/approval-policy.ts:16`）= `{"write","edit","bash","powershell","delegate","propose_project"}`，是 `Set<string>`。

要求：**对每一个实际会注册进 harness 的工具名做穷举断言**——它要么不在 `WRITE_TOOLS` 里（读类，无需闸门），要么在（写类，被闸门覆盖）。断言清单：

1. `createTools({ memory: undefined, skills: undefined, delegate: false })` 返回的工具名集合 ⊇ `{remember, recall, remind}`，且**每一个都不在 WRITE_TOOLS 里**（这三个是纯读/记忆类；若未来有人给它加了会写的东西，这条先红）。
2. 全量装配（`createTools({ delegate: true })` + 模拟 skills）∪ 内核五件 `{read, write, edit, bash, powershell}` 的并集，对并集里每个名字断言 `WRITE_TOOLS.has(name) || isReadOnlySafe(name)`——写法建议：维护一个显式的**读类白名单常量** `READ_TOOLS = new Set(["remember","recall","remind","skill","read"])`，断言"全集 = WRITE_TOOLS ∪ READ_TOOLS"，多出或缺少任何一个名字都让测试失败并打印出错的工具名。这样将来加新工具没进闸门，测试直接红。
3. `WRITE_TOOLS` 至少包含六个已知写类工具（防有人误删）。

注意：`createTools` 不会自己连库——它只收 `deps` 构造闭包，不会在 import/构造时产生 IO（`memory: undefined` 时 `requireMemory` 只在工具执行时抛错）。直接调用是安全的。若构造时确实抛错，允许只对"名字清单"做静态断言（把两个来源的工具名硬编码进测试并注明出处），但优先尝试真实调用。

### 1.2 依赖方向

- `packages/shared/src/index.ts` 的 import 只允许来自 `zod`（读文件、正则抽 `import ... from "..."`，任何相对导入或 `@lifediary/*` 导入都算违规）。
- `packages/memory/src/` 下所有 `.ts` 文件不得 import `@lifediary/server` 或 `apps/server`（含相对路径逃出包的写法，如 `../../apps/...`）。

用 `node:fs` 递归扫文件 + 正则实现即可，不需要 ast 库。

### 1.3 只读闸门行为回归（已存在的保证，别让它退化）

- `readOnlyBlockReason`（从 `./approval-policy.ts` 同目录 import，实际定义在 `approval-policy.ts`）：对 `WRITE_TOOLS` 六件在 `read-only` 档都返回非 undefined；对 `READ_TOOLS` 五件都返回 undefined。`policy.blocked` 命中的名字优先返回禁用理由。
- 注意 `readOnlyBlockReason` 读的是模块级 `policy` 状态（`approval-policy.ts` 里有 `loadPolicy`/持久化），直接调用时用默认策略即可，**不要**在测试里写 policy 文件。

## 任务二：契约快照测试（新文件 `packages/shared/src/snapshot.test.ts`）

背景：shared 是服务端与手机端共用的契约单文件，接口文档 §7 口径"文档滞后即 bug"。快照测试让任何字段增删改在 review 里显形。

### 2.1 快照什么

对以下 schema 断言"字段形状"（不是值）：`ChatRequestSchema`、`ChatMessageSchema`、`TranscriptMessageSchema`、`ChatTranscriptSchema`、`RoleSchema`、`FinishReasonSchema`。

形状提取器自己写（不要引入新依赖）：对每个 schema 序列化出一个确定性的 JSON——包含 `kind`（object/enum/…）、每个字段的 `type`（string/number/array/object/enum/optional 标记）、enum 成员列表、嵌套 schema 递归。建议实现：写一个 `shapeOf(schema)` 纯函数（测试文件内），按 zod 的 `_def.typeName` / `_def.shape()` / `values` 走；输出做 key 排序，保证跨平台稳定。zod 是 3.25（`_def` 可用；不要用 `zod-to-json-schema` 包，node_modules 里没有）。

快照值直接**内联写在测试文件里**（一个 `const EXPECTED = {...}`），不落单独 `.snap` 文件——理由：文件少一个是一，diff 时形状改动一目了然。若你觉得内联太大可改用 `__snapshots__` 目录，二选一并说明。

### 2.2 SSE 编解码行为回归（顺手钉死）

- `encodeSseEvent({type:"delta",text:"hi"})` === `"data: {\"type\":\"delta\",\"text\":\"hi\"}\n\n"`（只写 data 行、无 event: 行——注释说这是"避免同一件事两份真相"）。
- `createSseDecoder()` 边界行为三例：帧被任意切分（逐字符喂）能完整解出；两个事件粘在一个 chunk 里能解出；畸形 JSON 帧被跳过且后续帧不受影响。

### 2.3 ChatEvent 联合成员清单

`ChatEvent` 是手写 TS 联合（不是 zod），无法运行时反射。用类型级断言钉住成员清单（9 个：start/delta/thinking/progress/tool/done/error/delegate/attention/approval——共 10 个，以 `index.ts:82` 起的实际清单为准），写法：

```ts
// 编译期断言：ChatEvent 的 type 字面量全集。加新成员时这里必须显式追加，
// 否则 never 检查失败 —— 这是"契约改动必须过 review"的类型级版本。
type ChatEventType = ChatEvent["type"];
const ALL_EVENT_TYPES: readonly ChatEventType[] = ["start","delta","thinking","progress","tool","done","error","delegate","attention","approval"];
// 再补一个反向检查：ALL_EVENT_TYPES 少写成员时编译不过（exhaustiveness 手法）。
```

并在测试里断言 `encodeSseEvent` 对每个成员的代表性样例编码后 `JSON.parse` 回来 `type` 值都在清单里。类型错了 `pnpm typecheck` 会红，这正是想要的。
