# 员工人格化设计：从「一份文档」到「一个人」

> **状态**：提案已接续——由 2026-11-14《员工人格模块（开关化拟人）》重做并于 2026-11-14 三批落地；本文留档。冲突以长期文档为准。
> **来源**：用户两篇 ChatGPT 分享对话（简单 harness vs 企业流程 / 多 Agent 组织设计）+ 2026-11-08 当日讨论「如果员工真正像一个人，应该怎么设计」。
> **落地后下沉落点**：契约字段 → `接口文档.md`；成长与档案机制 → `系统架构.md`；本方案保留「当时怎么想的」。
> 前置讨论与代码核对结论见同日讨论（边界对照、缺口清单 A/B/C），本文是它的收拢与推进。

## 一、问题：员工现在是什么

编辑执事 = 编辑 `SOUL.md` 文本；调教 = 写技能手册、靠记忆引擎从对话里碰运气抽偏好；派下去的工人连文本都没有。

执事家目录（`partners.ts`，2026-11-08 核对）：

```text
.data/partner-homes/<uuid>/
  SOUL.md        身份（人格 + 职责混写在一个文本里）
  memories/USER.md  主人画像
  workspace/     唯一默认可写区
  memories/      记忆落点
  skills/        技能落点
```

记忆引擎的形态只有四种：`fact / episode / preference / entity`（`packages/memory/src/types.ts:48`）——**没有"工作记录"形态**。派活履历散在 chancellor `runs/<ticket>/`，不挂在执事头上。

结论：**咱们有的是"一份会说话的岗位说明书"**。边界那半（闸门/审批/领域派发/不越级/审批不阻塞）已经齐了，2026-11-08 核对无缺口；缺的是让"人"成立的那几样东西。

## 二、真员工 vs 文档：五个落差

| # | 落差 | 真员工的样子 | 咱们现状 |
|---|------|-------------|---------|
| 1 | 岗位和人混写 | 岗位契约稳定（调岗低频慎重），人在日常里成长 | SOUL 一改全改：改职责顺手把人格也动了 |
| 2 | 没有履历 | 有 track record：干过什么、成几单、产物在哪 | 履历散在 chancellor；记忆里只有聊天流水 |
| 3 | 不会被教 | 纠正一次，下次同类活就变了 | 靠记忆抽取碰运气，权重与召回都不保证 |
| 4 | 没有目标与周期 | 有当前目标，有周期盘点 | 只有一次性任务 + 用户配的闹钟 |
| 5 | 没有状态感 | 知道自己在办什么、卡在哪 | 任务中心知道，他自己的输入里没有 |

## 三、设计（E1–E5）

### E1 岗位契约与人格分离

**改动**：家目录新增 `CONTRACT.md`（独立文件，与 SOUL 并列），固定四个小节：

- **职责范围**：管什么、不管什么（与 domain 派发边界一致口径）；
- **决策分级**：哪些自己定 / 哪些办完通知 / 哪些必须先申请（对应"通知/协商/申请/汇报"四类通道的执事侧）；
- **验收标准**：交给他的活"怎么算好"；
- **汇报对象**：向谁汇报、周期是什么。

**存储**：沿用 `partner_versions` 版本化机制（`soulSource` 旁加 `contractSource` 快照），改契约=调岗，低频、版本化、下一轮生效（与 SOUL 的"下一轮生效"契约同款，不即时变身）。

**消费两处**：
1. 执事轮输入组装 = SOUL（人格）+ CONTRACT（岗位）+ 状态/履历摘要（E2/E5）；
2. 派活任务书组装自动带上契约的"决策分级 + 验收标准"——前轮缺口清单里的 **A1（任务书四段）就是它的落点**，不再单独做。

**界面**：9-P 角色管理屏（在跑）落地后加"岗位契约"编辑区，与"人格（SOUL）"区分开。服务端字段与注入可先行，不等界面。

**取舍**：
- 独立文件 vs SOUL 内分节 → 选独立文件：改岗位不该牵动人格文本，diff 与版本化都干净。
- per-partner 硬权限档 → **刻意不做**（见 §五.2）：契约只写"哪些要申请"的条款，执行仍靠全局闸门，一套执行机制。
- shared 契约影响：`PartnerRow` 若经 `GET /api/v1/partners` 暴露契约/目标字段，动 shared schema，手机端角色管理（9-P 同域）需同步——**先在本仓服务端与提示词层落地，字段暴露挪到与 9-P/手机端联动的那一批**。

**回滚**：`PARTNER_CONTRACT=false` → 不建文件、不注入，回到纯 SOUL 形态。

### E2 工作档案（履历回灌）

**改动**：给"工作记录"一个记忆形态。记忆引擎 `MemoryKind` 新增 `"work"`：

- 写入点：派单结算处（delegation 回执落账时）写一条 `work` 记忆到该执事 scope——单摘要、结果状态、产物路径、耗时；返工/取消也记（带原因枚举）。
- 产物路径：依赖 8e（A25 chancellor v0.5 产物透传）。8e 之前先落"状态 + 一句话结果"，产物列留空——**不阻塞，不等待**。
- 消费点：执事轮输入注入"履历摘要"（近 N 单、成功率、在办、最近教训）；巩固层天然获得去重/强化/衰减；召回口径沿用现有 recall。

**取舍**：
- 入记忆引擎 vs 独立 partner-records 文件 → 选记忆引擎：独立文件等于造第二套记忆，失去巩固与召回，两套"他记的事"还得互相解释。
- `work` 是新 kind，**只增不改**：现有 fact/episode/preference/entity 语义零变动，手机端与既有数据天然兼容（kind 枚举是开放判断处需逐一核对，实现时列清单）。

### E3 教员工（显式教诲沉淀）

**改动**（最便宜，两层）：
- **偏好层（本批可做）**：手册与提示词口径——用户用"以后 / 记住 / 下次"句式纠正执事时，执事必须调 `remember` 落一条 `preference`（来源标记 taught）。偏好层已有"永不删"保护（`store.ts` protectKinds），教过的话不会在巩固里被衰减掉。
- **技能层（依赖 9-S）**：9-S 技能管理落地后，"这类活怎么做"的方法论沉淀为该执事的技能文件（`skills/` 家目录与 `partner_skill_write` 接口已有底子），同类任务书自动挂对应技能。

### E4 目标与周期回顾（含自建巡逻）

**改动**：
- `PartnerRow` 加 `currentGoal` 字段（用户/总管可改；改目标=动目标管理权，界面提示"下一轮生效"）。
- **回顾例行模板**（每周一条）：盘点本周单据（数据源 = E2 的 work 记忆）→ 一段自然语言总结写回档案 → 向主人汇报。**不打分、不搞 KPI 数字**（见 §五.5）。
- **自建巡逻**（前轮缺口 B3 的落点）：给带派发权的执事一个"自建例行规则"工具，进 `WRITE_TOOLS` 过闸门；防自环已有（`routines.ts`：自我事件不触发自我）。E4 的回顾规则本身可由执事自建，也可由用户配模板。

**回滚**：`ROUTINE_SELF_SERVICE=false` 关自建工具；回顾模板不建就不跑，天然无行为变化。

### E5 状态感

**改动**（最便宜，纯装配）：执事轮输入加"当前在办"一段——durable 在跑单、待审批 pending（含等待了多久）、最近完成一单。数据全在服务端（任务中心与审批队列同源），不改任何存储。

## 五、明确不做

1. **工人身份化/建档**。工人默认一次性（用完即弃），这是刻意设计：成本低、无残留、无身份泄露面。"人"的成长全部记在执事头上。**复用不走建档，走"续链"**（2026-11-08 用户口径：普通员工用完即弃，可复用但少见）：执事派后单时把前单的产物与结论作为输入交给新单，等效"同一个员工接着干"；该能力归 chancellor v0.5 链式任务方向（8e / A25），harness 侧只需任务书组装能带上前单产物引用（E1 消费点 2 自然覆盖）。持久的工人身份（跨单同会话、工人档案）仍不做。
2. **per-partner 硬权限档**。闸门保持全局一套；契约写条款，执行归闸门。两套权限判断的维护成本与不一致风险远大于收益。
3. **情感/人格拟真**（情绪状态、性格发展、拟人闲聊强化）。超出"员工"语义，不做。
4. **网状通信 / 工人互聊**。8d（A21）排的是执事间通道；工人层网状不做，规模没到。
5. **考核打分 / KPI 数字**。回顾用自然语言总结；给员工打分既不可靠也不必要。

## 六、回滚开关汇总

| 开关 | 关掉后 |
|---|---|
| `PARTNER_CONTRACT=false` | E1：不建 CONTRACT.md、不注入，回纯 SOUL |
| `ROUTINE_SELF_SERVICE=false` | E4：自建例行工具下线 |
| E2 新 kind | 只增不改，无需开关；写入点用 `PARTNER_WORK_RECORD=false` 可单独停 |
| E3 / E5 | 口径与装配层，随手册与注入自然退回 |

## 七、验证

- `pnpm typecheck` + 单测（partners / routines / memory 写入与巩固）；
- `pnpm memtest`：`work` kind 的写入、巩固（去重/强化/不误删）、召回；
- 探针：执事轮输入装配（SOUL + CONTRACT + 履历摘要 + 当前在办）四段各有一断言；
- 真模型走查三条线：教一次 → 同类活行为变化（E3）；派一单 → 履历可见且摘要正确（E2）；建一条周回顾 → 跑一轮产出总结并汇报（E4）。
