## 二、先给结论

1. **领域负责人不是从零做。** chancellor v0.4（2026-11-02 落地）已有领域注册表、独立进程的长期会话、
   `done/blocked/failed` 结论契约、自己的 `delegate`（递归断在参数层）。
   **缺的是助理侧从不传 `domain`，以及整条链路仍是同步阻塞。**
2. **非交互能力：本机三个 CLI 都可用，项目只接了 Qoder 国际版。**
   harness 自身没有任何外部 AI CLI 调用；chancellor 的雇佣兵只调 Qoder 国际版单发。
   三个适配器、`permission_denials` 判定、`-r` 续接、`--max-turns` 都要补（§5.6）。
3. **异步是这次的结构性改动。** 派单工具立刻返回；负责人在后台进程干活，单内并行多个执行者；
   完成/失败/待你处理时把结果回灌会话（会话空闲才自动汇报，忙则排队）。
4. **文件抢占用租约强制。** 任务单计划必须声明"要写哪些路径"；调度器按路径发独占租约，
   并用 git worktree 隔离执行、按租约合并。冲突进"等待文件"状态，不并发写同一个文件。
5. **领域和项目是两件事，别混。** 领域 = 一块分工（前端 / 桌面壳 / 文档 / 数据），由一位负责人管；
   项目 = 磁盘上真实存在的目录或仓库，记在任务单上。**没有已登记的项目目录就不能干活**；
   **只有新起一个项目（新项目根目录）才要用户确认**，且必须建在事先选定的工作区内；
   **项目内部子目录随便建**，越出工作区一律拒绝（§5.5）。

## 五、方案

### 5.1 职责边界

| 角色 | 管什么 | 不管什么 |
|---|---|---|
| **助理**（harness 主 agent） | 跟用户对话、记忆、判断"要不要派、归哪个领域"、**新增领域（自行决定，无需用户确认）**、发起新建目录（**必须用户确认**） | 不拆单、不选执行者、不验收、不碰项目文件、不自作主张建目录 |
| **领域负责人**（chancellor manager） | 领域上下文（长期会话）、拆单、选执行者、控并发、验收、给一行结论 | 不跟用户说话、不建领域、不建目录、不建项目、不写 `REPORT.md` |
| **执行者**（本机/工具/手机） | 在自己的隔离目录里干完一段，交 `REPORT.md` | 不派单、不跨任务、不跨目录、不新建项目目录 |
| **外部执行**（CLI） | 作为执行者的一种，执行同一份任务契约 | 不参与拆单、不验收、不跟用户对话 |

**建目录的唯一入口**：助理代为发起 → 用户确认 → 才执行。**只对"新起一个项目根目录"生效**；
项目内部（含产物目录、嵌套子目录）由负责人/执行者自由创建，不需要确认。
负责人与执行者不能在工作区内新起项目根目录，也不能碰工作区以外的任何路径（harness 自身 `data/` 除外，§5.5）。

**分工一句话**：助理管"做不做、归谁"；负责人管"怎么拆、谁去干、干成没有"；
执行者只拿自己被派的那一段，干完即回收。**持久上下文只在负责人手里。**

**记忆边界**：负责人没有 `remember/recall`（`MANAGER_ALLOWED_TOOLS` 只有 `read/write/edit/bash/delegate`）。
跨领域共享事实仍由助理侧记忆承担，需要时写进 `requirement`。**不做负责人与助理共享记忆库。**

### 5.2 通信：异步派单

**唯一通道仍是 `delegate` 工具，但语义改为"立刻受理、后台执行、结果回灌"。**

```
助理 --delegate(requirement, domain, project)--> 受理，立刻返回 { ticketId, domain, project }
                                                        │
                                                        ├─ 后台进程：负责人拆单 → 并行执行者
                                                        │
        <-- 事件 delegation(phase/progress) ------------┤
        <-- 系统记录 delegation_result(一行结论) <------┘
```

| 项 | 决定 |
|---|---|
| 传什么 | `requirement` + `domain`（必填）+ `project`（必填）+ 可选 `resumeTicketId` / `answer` / `requestId` |
| 返回什么 | 立刻返回 `{ ticketId, domain, project, accepted: true }`；不返回结论；同一 `requestId` 返回既有 `ticketId` |
| 负责人怎么收 | 后台 `startDelegation()`；同一领域同时只跑一个负责人进程（SQLite 单写者），其余任务单排队 |
| 单内并行 | 负责人的拆单结果带 `files` / `writes`；调度器并行起多个执行者，`MAX_PARALLEL_TASKS` 默认 3 |
| 结果怎么回 | 1) **终态且子任务全部收口**才写入会话的系统记录（折叠展示）；2) 会话空闲时把多张终态任务单**合并成一轮**汇报，只输出一行结论（≤80 字，长文落 `data/projects/<id>/tickets/<ticketId>/`）；会话忙则排队到本轮结束 |
| 重复派单 | `delegate` 支持可选 `requestId`；受理**先落回执再入队**；同一 `requestId` 返回原任务单，不新建；结果不确定（发送中崩溃）不自动重派，卡片提示"先确认"（借 DS-Bot `request_id`，见 §11.2） |
| "待你处理" | 沿用 `attention` 事件 + 会话卡片，事件带 `kind: approval \| question`；用户回复后仍由助理调 `delegate(resumeTicketId, answer)` |
| 回滚开关 | `DELEGATION_ASYNC=false` → 退回同步等待（旧行为）；`DELEGATION_AUTO_REPORT` **默认 `true`**（完成 / 失败 / 待你处理都冒一条），设 `false` 则只发事件不自动汇报 |

**任务单状态机**：

```
排队 → 拆单中 → 执行中（含 等待文件） → 验收中 → 完成
                                   ↘ 待你处理 / 失败 / 中断 / 已取消
```

- `parentTicketId`：子任务未全部终态时，父任务单不得进入 `完成`、不得汇报（借 DS-Bot 派活树，见 §11.2）。
- `resumeCount`：同一次中断最多自动续一次，防止"重启—续跑—再中断"的循环。

**为什么这样回灌**：异步不等于"静默"。用户继续聊天时，结果必须自己冒出来一次；
但只在会话空闲时冒，避免打断正在进行的对话。自动汇报只讲一行结论，细节在卡片里。

**明确不做**：负责人直接给用户发消息；助理与负责人共享同一个 durable 会话；两个负责人进程同时开同一领域库。

### 5.3 并发模型

| 层级 | 规则 |
|---|---|
| 跨领域 | 并行。不同领域目录、不同 SQLite、不同进程 |
| 同领域 | **串行任务单**（默认 `MAX_ACTIVE_TICKETS_PER_DOMAIN=1`），后到的排队；负责人可在单内并行多个执行者 |
| 单内任务 | 并行，受 `MAX_PARALLEL_TASKS`（默认 3）与文件租约约束 |
| 执行者超时 | 本机/外部 10 分钟；手机/工具按原预算 |
| 停止 | `abortSignal` → 杀进程树；任务单终态 `已取消`；租约释放 |

负责人"调控并发"的具体抓手：计划里的 `files`、`dependsOn`、`parallel` 上限，
以及租约冲突时选择"串行 / 重拆 / 换执行者"。

### 5.4 文件抢占：路径租约 + 隔离执行 + 按租约合并

**原则：不并发写同一路径；执行时的写入不直接落项目；靠租约合并。**

1. **计划必须声明写集。** 每个任务带 `writes: [相对路径]`（新增/修改/删除都要列）。
   没声明写集的任务按只读处理；一旦检出写入即判 `失败：越权写入`。
2. **执行隔离。** 项目是 git 仓库时，每个任务用 `git worktree` 起一份独立副本（基线 = 任务单的 `baseRevision`）；
   非 git 项目不允许并行写，任务串行直写项目目录。
3. **路径租约（调度器强制，不靠提示词）。**
   - 键：`(projectId, 规范化相对路径)`；值：`{ ticketId, taskId, pid, acquiredAt, heartbeatAt }`。
   - 合并前申请**独占租约**；已有人持有 → 任务进 `等待文件`，不启动、不写。
   - 心跳 30 秒；两次丢失 + 5 分钟宽限判 `stale`，可被重新申请。
   - 租约随任务结束/失败/取消释放；进程崩溃由启动扫描回收（§5.7）。
4. **合并。** 持租约后把任务副本的 diff 应用到项目目录；冲突 → 任务 `失败：合并冲突`，
   原副本保留供负责人查看，**不自动重试**。
5. **越权检测。** diff 里出现未声明路径 → 拒绝合并，任务 `失败：越权写入`；改动留在隔离副本，不污染项目。
6. **删除/重命名**：租约同时覆盖旧路径与新路径，避免"改名的同时别人在读"。
7. **可关闭**：`TASK_ISOLATION=worktree|direct`（默认 worktree）；`direct` 仅用于非 git 项目或明确串行场景。

**为什么不是"负责人判断"**：负责人是模型，判断会漏；租约与越权检测在调度器里，漏不掉。

### 5.5 项目与工作区：派单的硬前置

**先把三个概念分开，避免以后再混。**

| 概念 | 定义 | 谁决定 | 记在哪 |
|---|---|---|---|
| **领域** | 一块分工（前端 / 桌面壳 / 文档 / 数据…），一个领域一位负责人 | 只有助理能新增；**助理自行决定，不需要用户确认** | `managers/<domain>/` |
| **项目** | 磁盘上真实存在的目录或仓库，是干活的落点 | **新项目根目录必须用户确认** | 项目登记表；任务单记 `projectId` |
| **工作区** | 用户事先选定的根目录，**所有新项目只能建在它下面** | 用户（设置页选一次） | `workspaces` 表 |

**四条硬规则：**

1. **没有项目目录就不能干活。** 派单必填 `project`；无项目返回 `{ error: "needs_project" }`，
   前端显示"还没有项目，先建一个"，**不创建目录、不写文件、不建任务单**。
2. **只在新起一个项目时问用户。** 判定标准是"新的项目根目录"，不是"任何 mkdir"。
   流程：助理在对话里提出 `项目名 + 工作区内的相对路径` → 用户点确认 →
   才创建目录、写入项目登记表、允许派单；用户拒绝 → 什么都不建，任务单不落地。
3. **项目内部目录自由。** 项目根之内的子目录、产物目录、嵌套目录，负责人/执行者随便建，
   不需要问用户，也不登记为新项目。**但仍要写进任务计划的 `writes`（可用 `dir/**` 形式）**，
   供租约与合并使用；没声明的路径按越权处理（§5.4）。
4. **越界即拒。** 读写路径都必须解析到已登记项目的 `root_path` 内（`realpath` 校验，防 `..` 与符号链接逃逸）；
   工作区之外的路径**一律不碰**；跨项目写入一律拒绝。**唯一例外是 harness 自己的数据目录 `data/`**
   （任务单元数据、worktree、日志），它由 harness 管理，不属于用户工作区。外部执行以 worktree/项目目录为 `cwd`，
   权限模式再收紧一层。

**实现口径：**

- **项目登记表**（harness 侧 SQLite）：`id(uuid) / workspace_id / name / root_path / vcs(git|none) / created_at / archived`。
- **工作区**：用户在设置页「项目」分区选定一个根目录；未选工作区时不能新建项目，已有项目不受影响。
- **谁能建项目**：只有"助理发起 + 用户确认"这一条路；负责人的工具里没有建项目、也没有建领域。
- **目录校验**：必须在工作区根下、必须是绝对路径；拒绝盘符根、用户主目录、系统目录；
  `realpath` 归一后仍须在工作区内；启动时检查可写；记录是否 git 仓库与当前 `HEAD`。
- **产物位置**：改动直接落 `root_path` 内（含任意子目录）；任务单元数据、隔离副本、日志放 harness 数据目录
  `data/projects/<id>/`，不往项目里塞隐藏目录。
- **领域与项目的关系**：项目是"在哪改"，领域是"谁来管"。一个领域可服务多个项目；
  一个项目可被多个领域服务。任务单同时记录 `projectId` 与 `domain`。
- **非 git 项目**：接受"串行直写 + 租约"，不强制所有项目必须 git；同项目不并行写（§5.4 第 2、7 条）。
- **只读审查**：项目存在但任务只读时，不申请租约、不建 worktree，直接读项目目录（仍限项目根内）。

### 5.6 外部执行：三个 CLI 接入

统一适配接口 `CliAdapter`：`buildArgs()` / `parse()` / `preflight()`，负责人的计划里用逻辑名选：
`codebuddy` / `qoder-intl` / `qoder-cn`。

| 逻辑名 | 二进制 | 关键参数（2026-11-03 实测口径） | 已知坑 |
|---|---|---|---|
| `codebuddy`（默认第一） | `codebuddy` | `-p <prompt> --output-format json -y --model deepseek-v4.1-flash [--allowedTools "Bash,Read,Write,Edit,Grep"]` | `-p` 必须带 `-y`；`-m` 短参报错，必须 `--model` 全拼；目录首次要信任；清掉 `CODEBUDDY_*` / `WORKBUDDY_*` 宿主变量，否则会挂起 |
| `qoder-intl`（第二） | `C:/Users/<user>/.qoder/bin/qodercli/qodercli.exe` | `-p <prompt> -w <dir> -m DeepSeek-Flash --permission-mode <mode> -o json [--tools ...] [--max-turns N]` | 用全路径，绕过分发器 |
| `qoder-cn`（第三） | `C:/Users/<user>/.qoder-cn/bin/qoderclicn/qoderclicn.exe`（真身是带版本号的可执行文件，PATH 里的 0 字节符号链接不可靠） | 同上：`-p ... -m DeepSeek-Flash -o json` | 登录态独立（`~/.qoder-cn/.auth`）；**首次调用约 100 秒**，超时要放宽 |

**统一判定（三个都一样）**：

```
ok = exit 0  &&  result 非空  &&  is_error=false  &&  permission_denials 为空
```

- 输出字段：`type=result`、`result`、`is_error`、`session_id`、`num_turns`、`duration_ms`、`permission_denials`。
- 多轮：`-r <session_id>`；只在同一任务的"继续改"里用。
- 长提示词：`TASK.md` > 8K 字符改 stdin；不要同时加 `< /dev/null`。
- 超时：默认 10 分钟；Qoder CN 首调放宽到 180 秒起步。
- 选择顺序（已定）：**`codebuddy` → `qoder-intl` → `qoder-cn`**。
  理由：CodeBuddy 按用户指定排第一；Qoder 国际版是当前 `mercenary.ts` 已验证在用的链路，稳定性和登录态最熟，排第二；
  Qoder CN 登录态独立、首次调用约 100 秒，放第三，只在前两档不可用时兜底。
  负责人可按任务改；失败/登录过期则换下一档，同一任务**不并行两档**。
- 启动时做一次健康检查（`status` / `--version`），结果缓存；不可用档位不参与选择。
- 外部执行是**执行者的一种**，仍受租约与隔离约束（在 worktree 里跑，不直写项目）。

**刻意不接**：Claude / Codex / OpenCode（magpie 已停）。

### 5.7 生命周期与崩溃恢复（默认方案，可调策略）

| 阶段 | 行为 |
|---|---|
| 受理 | 校验 `domain`（只能选既有领域）、`project`；建任务单（`排队`）；立刻返回 |
| 启动 | 同领域无活跃任务单 → 起负责人进程；有 → 排队 |
| 上下文 | `managers/<domain>/meta.json` 的 `conversation_id` + `.agent.sqlite` 常驻；当上下文用量到窗口 **60%**（`MANAGER_CONTEXT_ROTATE_RATIO`，默认 `0.60`，可配置）自动处理：活告一段落 → `rotate`（写交接笔记换新段，旧段归档可查）；没告一段落 → `compact` 原地压缩。**绝不弹给用户问**（借 DS-Bot 管家，见 §11.2-3） |
| 空闲 | 进程退出；状态保留；不做进程守护 |
| 超时 | 负责人 30 分钟 `killTree`；任务单转 `待你处理：超时` |
| 崩溃/重启 | 启动分四类结算（借 DS-Bot `inflight.json` 口径）：`still_running`（pid 活）/ `finished_with_result`（只补发汇报）/ `cut_off`（`resumeCount=0` 才从 worktree 快照续跑）/ `unknown`（判 `中断`，写明未知）。**只有跨过"合并进项目目录"这一步的任务单需要人工确认**；未跨过的可安全重跑。释放租约（宽限 5 分钟），保留 worktree |
| 取消 | 杀进程树、释放租约、删 worktree、任务单 `已取消` |

**可调策略**：崩溃恢复默认"未合并前自动续一次；跨过合并点人工确认"，目标是尽量少占用户注意力；
参数与开关（`DELEGATION_RESUME_POLICY=auto-before-merge|always-ask|never`）留一行，便于按实际噪声调整。
**已实测（2026-11-08，探针在 `ts/apps/server/scripts/`，结论详见
`docs/变更记录/2026-11-08-宰相层四项验证结论.md`）**：

- **pid 存活**：`process.kill(pid, 0)` + EPERM 当活，在 Windows 上对活/死/无权限/非法 pid 均判断正确；
  唯一误判面是 **pid 被回收复用**——恢复只看 pid，会把原单永久判成 `still_running`（租约侧有 5 分钟心跳兜底，不受影响）。
- **`harness.resume()` 与未收尾提交**：两种顺序（先 resume 再输入 / 先输入再 resume）实测新输入都按
  `followUp` 排队，旧提交保持 `placed` 并最终 `done`，上下文顺序不变。**不会被顶掉。**
- **worktree 清理**：成功即删；进程失败**刻意保留**副本，同 seq 下次开工先清再检出；崩溃保留副本 + `inflight.json`，
  自动续跑成功后再删。三条路均无设计外残留。崩溃留下的半成品也必须在 `writes` 里声明，否则续跑按越权写入判失败。
- **60% 阈值判定**：正常收尾 → 换段（`handoff.md` + `rotations+1`）连续 5 轮全中，第 6 轮短回复不再触发；
  非正常收尾 → 压缩方向正确。**偏离**：`conversation.compact()` 只完成入队，进程随即退出，
  本轮内压缩任务不会跑（日志却已写"已压缩"），下一次负责人启动才真正压下去；不丢数据，但日志口径不实。

### 5.8 失败与超时

| 情形 | 原则 | 对外 |
|---|---|---|
| 负责人超时 | 不判失败，判"没给结论" | `待你处理` |
| 执行者超时 | 任务级 `失败：超时` | 结论带"第几件卡住" |
| 外部执行被拒 | `permission_denials` 非空 → `失败：权限拒绝` | 不冒充完成 |
| 合并冲突 | 任务 `失败：合并冲突` | 保留副本，不自动重试 |
| 越权写入 | 任务 `失败：越权写入` | 拒绝合并 |
| 结论格式错 | 不算完成 | `待你处理` |
| 审批后重启 | 原审批失效，不假装还在等 | 清审批，写"审批已失效，请重新允许" |
| 失败 | 不自动重试；重派 = 新任务单 | 需要人决定 |

### 5.9 前端：任务中心 + 对话内提示（已定）

**主形态：独立任务中心（原型 03）。**

- **定位**：独立整页，路由 `#/tasks`，与设置页（`#/settings`）同级；不是弹窗、不是抽屉、不嵌在对话里。
- **默认视图**：当前项目、全部领域、按状态分列（排队 / 执行中 / 待你处理 / 已完成）；
  顶部可切项目、领域、排序；列内按最近更新排序。
- **任务卡详情**：点开看任务列表、执行者、文件占用、一行结论、取消与"回复"入口。
- **深链**：`#/tasks?ticket=<id>`（可选 `project=<id>`）。进入后定位并高亮该任务单；
  任务单不存在或已归档 → 显示"任务单不存在"，不静默跳回列表。
- **多任务单多项目**：看板同时展示多个领域/项目的任务单；默认聚焦当前项目，可切"全部项目"。

**对话内提示（两件一起做，互为补充）。**

1. **会话任务卡片**（订阅 SSE，随状态实时更新）：

| 项 | 规则 |

| 任务单状态 | 徽标 | 卡片内容 | 按钮 |

2. **助理固定提示句**（回复末尾单独一行，不加装饰、不加表情）：

| 完成 | `任务已完成，去任务中心查看结果。` |
| 待你处理 | `有一项需要你处理，去任务中心回复。` |
| 失败 / 中断 | `任务未完成，去任务中心查看原因。` |

- 任务单号与领域已经在卡片里，提示句**不重复**这些信息。
- 提示句里的"任务中心"是可点链接，目标与卡片按钮相同（`#/tasks?ticket=<id>`）。
- 若禁用了自动汇报（`DELEGATION_AUTO_REPORT=false`），提示句随事件生成，不额外起一轮对话。

- 侧栏在"对话列表"上方加一条固定项「任务中心」，右侧带进行中任务单数徽标（如 `3`）。
- **理由**：任务中心是跨对话的资产，用户离开对话后还会回来查；侧栏本来就是导航区。

## 八、拍板结果（无未决项）

| # | 事项 | 结论 |
|---|---|---|
| 1 | 新增领域 | 只有助理能新增；**助理自行决定，不需用户确认**；负责人不能建 |
| 2 | 新建项目 | **只在新起一个项目根目录时问用户**，必须先确认；项目内子目录自由，不问 |
| 3 | 工作区 | 用户在设置页先选定；新项目只能建在工作区内；越界一律拒绝（读写都不碰） |
| 4 | 外部执行顺序 | **CodeBuddy → Qoder 国际版 → Qoder CN**；失败/登录过期换下一档，同一任务不并行 |
| 5 | 常驻入口 | 侧栏固定项「任务中心」+ 折叠态收进顶栏「功能菜单」 |
| 6 | 非 git 项目 | 接受"串行直写 + 租约"，不强制所有项目必须 git |
| 7 | 自动汇报 | 默认开启（完成 / 失败 / 待你处理都冒一条） |
| 8 | 崩溃恢复 | 未合并前自动续一次，跨过合并点人工确认；标为可调策略 |
| 9 | 越权写入 | 直接判失败，拒绝合并，不警告后放行 |
| 10 | 上下文阈值 | 窗口 60%，自动 `compact`/`rotate`，绝不弹给用户问；阈值可配置 |

**运行时可调参数（不是未决项）**：`DELEGATION_AUTO_REPORT`、`DELEGATION_RESUME_POLICY`、
`MANAGER_CONTEXT_ROTATE_RATIO`、`MAX_PARALLEL_TASKS`、`MAX_ACTIVE_TICKETS_PER_DOMAIN`。

## 九、这条会怎么错

1. **领域自由命名** → 助理自造 `code` / `coding` / `dev`，上下文碎掉。
2. **只靠提示词约束并发** → 两个执行者改同一个文件，后写的覆盖先写的。
3. **直接在项目目录并行写** → 半成品互相污染，出了问题无法回滚。
4. **没有项目就开干** → 产物散落在 `runs/`，用户找不到，也不敢删。
5. **异步不回灌** → 用户以为派丢了，反复派单，越派越乱。
6. **自动汇报打断对话** → 用户正在说话，助理突然插一段结论；所以只在空闲时汇报。
7. **外部执行假成功** → 旧 `REPORT.md` 还在 + 写入被拒，验收直接放行。
8. **负责人做成常驻进程** → 守护、IPC、心跳、重启全来了，只为省几百毫秒。
9. **跨领域借执行者** → 产物边界消失，两个领域写同一项目却没有仲裁。
10. **卡片与任务中心各自维护状态** → 两处显示不一致；卡片必须只读任务单接口，由同一事件驱动。
11. **固定提示句每轮都冒** → 用户被同一句话反复打扰；同一轮只出现一次，且只在该轮有派单/结果时出现。
12. **深链指向已删任务单** → 跳过去一片空白；必须先校验存在性，再给"任务单不存在"的明确页。
13. **工作区外建目录/写文件** → 执行者用绝对路径绕开项目根；必须 `realpath` 校验 + 调度器拒绝，
    不能只靠提示词"不要越界"。

## 十一、参考 DS-Bot 的可取之处

> 审计日期：2026-11-03。读的是 `<reference>\DS-Bot` 的 `README.zh.md`、`AGENTS.md`、
> `docs/plans/2026-10-10-bot-runtime.md`、`2026-10-16-bot-handoffs.md`、`2026-10-09-context-and-memory.md`、
> `2026-10-07-roles-and-permissions.md`，以及 `ds-bot/src/host/` 下的 `handoffs.js`、`turns.js`、
> `resume.js`、`delivery.js`、`requests.js`、`approvals.js`、`permissions.js`、`tools.js`、`store.js`。
> 它是 DSH 插件（JavaScript，跑在 DSH 会话里）；我们是 Node/Hono + durable + Go 桌面壳，
> 只借机制，不搬代码。

### 11.1 先对齐概念

| DS-Bot | 对应我们 | 边界 |
|---|---|---|
| Main Bot（团队管理员） | 助理 | 建/改/停其他角色；对用户说话 |
| 群管理员 / 普通 Bot | 领域负责人 | 长期身份；在领域内接活、拆活、派活 |
| DSH Session（一个 Bot 的私聊会话、每个群一个、上下文满了换新段） | 负责人会话 / 执行者进程 | 真正跑模型与工具的单元 |
| 派活（`message_bot`，活是一棵树） | 派单（`delegate`，任务单） | 上层等下层交回，结果自动上浮 |
| Bot 状态（等批准 / 换段 / 在干活 / 在等别的 Bot / 空闲） | 任务单状态 + 执行者状态 | 给人和给模型看同一份事实 |

**结论：它的"主控—下级—执行单元"与我们的"助理—领域负责人—执行者"是同一形状。**
差别在于它由会话内消息驱动，我们由跨进程任务单驱动。

### 11.2 可直接借鉴（按价值排序，每条都落到具体章节）

1. **派活树：子活没交回，父就不交回；结果自己往上走。**
   - 它怎么做：`handoffs.js` 每件活记 `parent / open / results`；回复回合结束时若子活未回，
     先 `hold()` 住自己的话；子活回来后再拼成一条往上交（`answerText()`）；
     并明确拒绝"发给正在等这件活结果的上游"（防绕圈）。
   - 我们怎么落：任务单增加 `parentTicketId`；**任务单只有在所有子任务均为终态时才允许进 `完成`
     并触发自动汇报**；部分结果只更新卡片，不汇报。
   - 落点：§5.2 状态机与回灌规则、`shared` 的任务单字段。
   - 要改什么：把"结果怎么回"从"终态就汇报"改成"终态且子树收口才汇报"；汇报文案注明"还有 N 件在跑"。

2. **幂等回执（`request_id`）：先写回执再发；结果不确定就不重发。**
   - 它怎么做：`requests.js` 以 `(调用者, 场合, 名字)` 为键存请求指纹与回执；
     回执在消息发出前落盘；同名字同内容 → 返回原回执；同名字不同内容 → 拒绝；
     发送途中失败或重启 → 标 `uncertain`，**不重发**，让调用方先确认对方收没收到。
   - 我们怎么落：`delegate` 增加可选 `requestId`（缺省由服务端按 `conversationId + 本轮 + requirement 指纹` 生成）；
     受理时先落一条 `delegation_receipts(requestId, ticketId, fingerprint, outcome)`，再入队；
     重启后收到同一 `requestId` 只返回原 `ticketId`；`outcome=uncertain` 时不自动重派，
     卡片提示"结果未知，先确认是否已经派出去"。
   - 落点：§5.2 受理、§5.7 崩溃恢复、`接口文档` §2.1。
   - 要改什么：`delegate` 的返回从"每次新建任务单"改为"可能返回既有任务单"；前端卡片按 `ticketId` 去重。

3. **负责人上下文的分段与交接（我们方案里缺的一整块）。**
   - 它怎么做：不硬切也不无限压缩。到预判线（`checkRatio` 默认 0.8）由"上下文管家"看最近消息，
     判断"活告一段落"就写交接笔记换新段，没告一段落就原地压缩；旧段整份归档、可全文搜；
     新段开头是"交接包 = 笔记 + 最近原文 + 其余内容在哪"；判断时核对"有没有问了用户还没答的问题"。
   - 我们怎么落：负责人除 `conversation_id` 外增加 `segments[]`；到阈值（我们取窗口 **60%**，
     `MANAGER_CONTEXT_ROTATE_RATIO` 可配）自动做一次轻量判断
     （用负责人自己的模型，单独小请求），二选一：`compact`（原地压缩）或 `rotate`（写交接笔记换新会话）。
     全程不弹给用户问。
     交接笔记固定字段：做到哪、已否决的方案、用户约束、剩余步骤、必须原样保留的事实。
     旧段归档可查（任务单详情给"历史段"入口）。
   - 落点：§5.7 生命周期、`系统架构.md`「领域负责人」。
   - 要改什么：原方案只写了"会话常驻"，没写"上下文满了怎么办"；补这条，并明确
     **不做负责人自动重置**（避免丢领域上下文）。

4. **重启结算：按持久记录判定，读不出来就明说"未知"，绝不重放副作用。**
   - 它怎么做：`inflight.json` 记在跑的回合与未取走的投递；启动延迟 3 秒；分三种结算：
     仍在跑 → 继续记；回合已结束 → 读会话持久日志，把答案交给等它的人；被切断 → 只续跑一次
     （`resumed` 标记防重启循环）；日志读不出 → 告诉上游"结果未知，别重跑"。
     等待关系存在 `state.json`，重启后接着等。
   - 我们怎么落：任务单表增加 `assistantConversationId / assistantRoundId / startedAt / resumeCount`；
     启动扫描分四类：`still_running`（pid 活）/ `finished_with_result`（结果已落库，只补发汇报）/
     `cut_off`（`resumeCount=0` 才允许续，且从 worktree 快照续，不重做已合并改动）/
     `unknown`（判 `中断`，写明未知）。**合并进项目目录是唯一不可逆动作**：它之前崩溃重跑安全，
     它之后只能查、不能重做。
   - 落点：§5.7（替换"默认不自动续跑"为分档结算）、§5.8。
   - 要改什么：把"人工确认再续"收窄为"只有跨过合并点的任务单才要人工确认"。

5. **状态是"给人看的一句话"，不是布尔值。**
   - 它怎么做：`statusOf()` 输出"在哪个场合、干了多久、正在跑什么工具/哪份文件、为谁做"；
     状态优先级明确（等批准 > 换段 > 在干活 > 在等别人 > 空闲）；状态不进系统提示（保住前缀缓存）。
   - 我们怎么落：任务卡片的"进度"不只用百分比，固定显示
     `正在做什么（当前任务/文件）· 已多久 · 执行者 n/m · 为谁（哪个任务单）`；
     超过心跳阈值显示"可能已卡住"。状态只走接口/事件，不写进负责人或助理的系统提示。
   - 落点：§5.9 卡片字段、§5.2 回灌。
   - 要改什么：卡片字段表补 `lastAction / lastHeartbeat / waitingOn`。

6. **审批要出现在"能回答的地方"，且重启后不能假装还在等。**
   - 它怎么做：`approvals.js` 把隐藏会话的审批请求转到群聊卡片（allow/reject），另记一份
     "谁在等批准"给团队视图；重启时把审批记进 `record.approval`，续跑时提示"那次审批已失效，
     需要再申请"。
   - 我们怎么落：执行者的权限请求统一进任务中心「待你处理」，卡片给"允许一次 / 拒绝"；
     任务单被重启恢复时，若原来在等审批，直接清掉审批并写"审批已失效"，不让它等一个不存在的按钮。
   - 落点：§5.8、§5.9「待你处理」。
   - 要改什么：`attention` 事件增加 `kind: approval | question`；取消/重启必须写终态。

7. **长内容不塞会话：只给开头 + 长度 + 文件位置。**
   - 它怎么做：`handoff-results/` 存整份结果，`state.json` 只存开头与长度；回复附文件；
     重启不会把已完成的结果截短。
   - 我们怎么落：执行者 `REPORT.md`、完整日志、完整结论落
     `data/projects/<id>/tickets/<ticketId>/`；会话与卡片只放一行结论 + 链接；
     自动汇报永远不粘贴长文。
   - 落点：§5.2 回灌、§5.9 卡片。
   - 要改什么：明确"一行结论"上限（建议 80 字），超出截断并给链接。

8. **同一位收件人的未读消息合并成一条。**
   - 它怎么做：对方没读时，同一件活的第二条合成到第一条，一次回复答两条；不留未读上限。
   - 我们怎么落：同一会话在"空闲待汇报"窗口里攒了多张任务单终态 → **合成一轮汇报**
     （每张任务单列一行），不连续起多轮；用户正在对话时不插话。
   - 落点：§5.2 自动汇报。
   - 要改什么：`DELEGATION_AUTO_REPORT` 从"每单一次"改为"每窗口合并一次"。

### 11.3 不适用（不是不好，是约束不同）

| # | DS-Bot 的做法 | 为什么不适用 |
|---|---|---|
| 1 | **不做任务对象，活只活在会话消息里**（它的设计文档明确"不做看板式任务对象"） | 我们的执行者跨进程、跨重启、带文件租约与合并；必须有独立任务单做事实源，消息只是视图 |
| 2 | **平级 Bot 互发 `message_bot`、群聊 @ 接力** | 我们是层级派单：助理 → 负责人 → 执行者；允许平级互派会绕过领域边界与租约仲裁 |
| 3 | **不设超时/上限，靠用户手动停** | 外部 CLI 会挂、会烧额度、可能停在交互提示上；我们保留 10 分钟超时、`--max-turns`、`permission_denials` 判定 |
| 4 | **状态只在内存、由事件重建**（它自己也承认"重启后从新的事件重建"） | 执行者在独立进程里，harness 重启后拿不到实时事件；必须持久化心跳与最后动作 |
| 5 | **单写者 `state.json` + 第二个宿主只读** | 我们的存储是 SQLite，同领域串行已由数据库锁解决；照搬文件锁只会多一套状态 |
| 6 | **每个 Bot 自己的模型 / 思考强度 / 能力包面板** | 与"领域负责人"这一层无关，属于后续执行者配置，不并入本次 |
| 7 | **DSH 的 `agent.steer/followup`、`sessionController.inspect`、审批事件** | 平台 API 不同；我们只能实现等价语义（消息入队/插话、读 durable 事件、审批表） |

### 11.4 它是坑（看起来好，照抄会出事）

1. **"异步"其实是会话内异步。** 它的结果是"以后作为一条新消息到"，没有跨进程持久队列；
   进程一停，在途的活靠 `inflight.json` + 会话日志兜。只学"稍后回一条消息"，崩溃就真丢了。
   → 我们必须有任务单账本，消息只是投影。
2. **无超时 + 无上限。** 它把链长/未读/轮数上限全删了，并承认"下面的活一直不交回，上面就一直等，
   DSH 没有超时"。聊天机器人可以靠用户停；会花钱的外部 CLI 上就是事故。
   → 保留超时与轮数上限，且"等待"本身要有 stale 判定。
3. **自动续跑会重放副作用。** 它续跑被切断的回合，靠提示词让模型"先检查已经做了什么"。
   模型检查不可靠；对我们就是重复写文件、重复合并。
   → 只在"未合并"阶段允许自动续；跨过合并点一律人工确认。
4. **幂等回执永不淘汰。** 它明确保留所有 `request_id` 回执（"否则旧重试会重复副作用"），
   代价是状态只增不减，且内容改一个字就冲突。→ 我们的回执跟任务单生命周期绑定（终态 + 保留期），
   键用 `requestId` 而不是正文指纹。
5. **状态只给模型不给界面，模型不看就瞎。** 它把状态放在 `list_bots` 返回值里，靠模型主动查；
   不查就不知道队友在等谁。我们已有任务中心，不要退化成"只有模型知道"。
   → 状态必须同时进接口与界面，模型只是消费者之一。
6. **群聊/多 Bot 社交结构会带来费用与绕圈。** 它为此写了合并未读、拒绝发给上游、派活树一整套；
   我们若引入平级互派，等于把这些一起引进。→ 维持严格层级。
