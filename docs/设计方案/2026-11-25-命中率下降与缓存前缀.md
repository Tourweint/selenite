## 1. 问题：一次会话里的四次命中率坍塌

审计对象是会话 `3971` 的四条请求（数据来自 durable 的 `pi.assistant` usage 与
`request-stats.ts` 的重放，未改存储）：

| # | entry | prompt tokens | 命中率 | 触发点 | 当时的具体变化 |
|---|---|---:|---:|---|---|
| 7 | 4016 | 33,043 | 6% | `tool_search` 加载 `routine_manage` | `tool_index` 段 698 → 621 字符；工具面 12 → 13 |
| 11 | 4035 | 35,666 | 5% | `tool_search` 加载 `propose_project` | `tool_index` 段 621 → 577 字符；工具面 13 → 14 |
| 33 | 4140 | 141,295 | 0% | 上游 502 后切换网关 | **前缀未变**（缓存过期 / 上游路由，客户端无从修复） |
| 58 | 4247 | 213,804 | 2% | `delegate` 描述被改 | 工具面 14 个全部 remove + add（本次**不处理**） |

结论分三类：

1. **#7 / #11 是设计选择的代价，不是事故**：按需工具一旦被 `tool_search` 加载，
   `tool_index` 段（写在 system 里）和工具声明会同时变化，前缀必然断一次。原设计认为
   「用户明确接受的一次性代价」，但审计显示它在真实使用里**反复发生**：低频工具被加载
   是常态，每次都要重算整段 history。
2. **#33 是上游，不该用代码「修」**：前缀没变，命中率为 0 只能归因缓存过期 / 网关切换。
   硬把这段写进代码统计反而会掩盖真实故障。
3. **#58 是工具描述变更**：`delegate` 的描述属于缓存前缀资产，改动必然全量失效。本次
   任务边界明确不处理（描述冻结是独立议题，见 §4）。

另有一个**报告 bug**：同一批比较里有 57 处相邻请求的正文对比 `replaced = 0`（纯追加），
但 `RequestMessageDiff` 在「工具调用 → 下一请求带结果」这种步骤上会报 `replaced: 1`。
根因是旧口径直接对比**两条请求 entry 自己的** `context({at})` 视图：上一条请求的视图里
含着内核补的 `Tool result unavailable: history ends before this call completed.` 占位，
下一条请求的视图里这个占位被真实工具结果替换，于是被算成「正文被改写」。实际 prompt
前缀并没有断，是**统计口径**的问题，不是缓存问题。

## 2. 决策

### 2.1 按需工具默认常驻（改默认，不删机制）

`DEFAULT_DEFERRED_TOOL_NAMES` 从 9 个改为 `[]`：**所有工具默认每轮都带完整定义**。
按需池变成显式 opt-in——部署方在 `.data/tool-pool.json` 写 `{"deferred":[...]}`
（重启生效）才启用某几个工具走 `tool_search` 加载。

代价是固定前缀大约多出 ~2.6k token（任务书口径：原 9 个低频工具的名字 + 描述）。
之所以接受：

- **前缀缓存让这份代价摊薄**：多出来的部分在请求之间不变，首次 miss 之后会被缓存命中；
  而旧形态里每次加载一个低频工具都要重算整段 history（#7 是 33k、#11 是 35k，
  长会话里是 14 万、21 万级别），长期更贵。
- **工具面稳定**：工具声明不再因为一次 `tool_search` 而在会话中途增删，缓存前缀
  的断点从「每加载一次断一次」变成「只在用户改配置时断一次」。
- **工具名 / 描述 / 注册顺序一律不动**：`tool_search` 与 `markDeferred` 的机制原样保留，
  只是默认清单为空；启用后行为与改造前完全一致。

选择**改默认值**而不是删除按需机制，是因为某些部署（手机端、低预算模型）仍可能需要
裁剪工具面；opt-in 保留这条路径，同时默认行为回到「稳定」这一侧。

### 2.2 `tool_index` 从 system 段改走尾部注入

按需机制保留后，`tool_index` 不能继续待在 system 里：它列的是「已启用、尚未加载」的
工具，一加载就变。2026-11-19 的前缀不变量已经规定「动态的东西走请求尾部 user 消息」，
`tool_index` 本来就属于这一类，之前只是被当成了 system section。

落地：`toolIndexProvider` 的 `channel` 从 `"system"` 改为 `"message"`、`scope` 改为
`"turn"`，从 `LIFECYCLE_SECTION_PROVIDERS` 挪到 `LIFECYCLE_MESSAGE_PROVIDERS`；
`INJECTION_ORDER.tool_index = 70` 的值不变（框架内排序稳定）。lifecycle 里删掉
`key:"tool_index"` 的 system section，`beforeRequest` 把当前会话可加载的 deferred
（已启用、未加载、未被按人取消）放进注入上下文。默认清单为空时没有任何 deferred，
整段照旧省略——零字节，也没有 `tool_search` 工具。

这样即使部署方启用按需池，加载工具时变的只有**尾部本轮上下文**与工具声明，system
前缀的指纹不变（验收见 §3）。

### 2.3 修正 `RequestMessageDiff` 的 `replaced` 假阳性

消息层对比改为比较两条请求各自**发出去之前**的 prompt 视图：

- 当前 prompt = `context({at: 当前请求 entry 的前一条})`
- 上一条 prompt = `context({at: 上一条请求 entry 的前一条})`
- 展示用的 `context` / `system` 仍取 `context({at: entryId})`，不受影响

拿不到「前一条」或视图重放失败时退回旧视图，宁可多一点噪音也不让详情空掉。
`replaced > 0` 从此只在真正的压缩 / 正文改写时出现，与「追加」彻底分开。

## 3. 验收口径

1. **system 指纹不变**：构造「上一条请求刚 `tool_search` 加载一个 deferred 工具」的场景，
   `systemChanged = false`（system 段与工具声明分开看；工具声明本身会变，见第 2 条）。
2. **工具声明变了**：同上场景 `toolsChanged = true`（一次性的、用户加载动作触发的代价）。
3. **`tool_index` 在尾部**：`collectInjections(...).message` 含 `tool_index`，
   `.system` 不含；默认空清单时整段省略。
4. **消息对比只算追加**：工具调用链（assistant toolCall → toolResult → 下一请求）
   在新口径下 `replaced: 0`，`appended` = 上一条回答 + 工具结果；压缩 / 正文改写
   仍报表 `replaced > 0`。

## 4. 明确不做

- **pi-durable 的 `planTools`**：上游内核的新工具规划能力不属于本仓库契约，本次不接入。
- **上游网关的路由分组**：#33 的 0% 是网关切换，属于上游运维，不在客户端代码里绕。
- **工具描述冻结**：#58 的根因是 `delegate` 描述变更；把描述锁成常量、或给描述加版本
  指纹，都是独立议题（涉及缓存前缀资产的长期治理），本次不顺手改。
- 不改任何工具的 name / description / 注册顺序；不改 `ts/packages/shared`；不改 HTTP
  端点形状；不加新工具。

## 5. 回滚

- **按需工具常驻**：在 `.data/tool-pool.json` 写回原 9 个名字
  `routine_manage` / `partner_manage` / `group_manage` / `save_skill_advice` /
  `partner_skill_write` / `propose_project` / `send_to_agent` / `respond_escalation` /
  `save_reminder_advice`，重启服务即回到旧形态（机制原样保留）。
- **`tool_index` 尾部注入**：若需回退，把 provider 的 channel / scope 与注册表位置改回
  system、并在 lifecycle 恢复 `key:"tool_index"` section；属于代码回滚，没有独立 env 开关
  （默认空清单下这段本来就不出现，风险面为零）。
- **报告口径**：纯统计修正，无需回滚；旧口径不影响任何存储。
