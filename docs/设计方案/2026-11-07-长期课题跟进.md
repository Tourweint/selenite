## 〇、一句话定位

不是造一台新机器：**钟**（durable sleepUntil 闹钟，范式见 reminder.ts / routines.ts）和**界面骨架**（会话内卡照 approvalCards、提议-确认照 propose_project）都是现成的。真正新建的是三样：

1. **课题户口本**——一个比单次运行活得久、会越攒越厚的实体（问题、节奏、发现日志、状态）；
2. **两个表达口**——用户直说 / 总管提议弹卡，都只落到"确认才建"；
3. **搜索底座**——设置页配 DeepSeek 搜索 key + 服务端 web_search 适配层（课题研究的硬前提）。

## 一、搜索底座（课题的硬前提，先做）

### 决策 S1：上游固定 DeepSeek，不做多供应商抽象

`POST https://api.deepseek.com/v1/tools/search`，Bearer 认证，入参 `query / count / need_content`，出参 `results[]`（title / url / summary）。
**明确不做**：搜索供应商抽象层。要换/加搜索源是二期立项，别提前造接口。

### 决策 S2：key 落点照密钥既有两路，变量名 `DEEPSEEK_SEARCH_API_KEY`

- 主落点：`.env` 手写（`loadEnvFile` 启动首行加载，已有值优先）；
- 界面直填：设置页 → 服务页新增「搜索」区块，`writeProviderKey("DEEPSEEK_SEARCH_API_KEY", …)` 走 `.data/provider-keys.json` 热注入（provider-secrets.ts 原样复用，不新造存储）；
- providers.json / 文档 / 日志只出现变量名，不出现值；值不进任何响应。
- 区块带「测试连接」：真实调一次搜索（count=1），成功显示返回条数，失败显示枚举原因（未配置 / 上游报错），不显示 key。

### 决策 S3：`web_search` 工具，只读，不进 WRITE_TOOLS

- 在 tools.ts 注册模型工具 `web_search`（query 必填，count 默认 5 上限 10）；服务端发 HTTP，返回 title/url/summary 列表。网络读，不写文件不起进程，**不过闸门白名单**，但照常受只读策略约束。
- 未配置 key 时工具返回结构化引导错误（"先去设置里配搜索"），**不许空转、不许造假结果**（mock 纪律）。
- 探针需要假上游：`SEARCH_BASE_URL` env 允许覆盖端点（默认 DeepSeek 官方），探针指向本地 stub——这是测试开关，不是绕过校验。
- 可用面：总管主对话与研究回合都有；执事/工人不给（他们走 chancellor，课题研究不走那条路）。

### 决策 S4：搜索未配置 = 开不了课题

提议确认与手动建课题（若未来有）在服务端硬校验：`DEEPSEEK_SEARCH_API_KEY` 不存在 → 拒绝，错误码 `search_not_configured`，提议卡上明示「先去设置里配搜索」。没有搜索的"每周研究"就是纯推理瞎说，这是把"必须配"落成硬约束。

## 二、课题实体

### 决策 T1：存储 `.data/topics.json`，单文件原子写，照 routines.json 的先例

```text
Topic {
  id: uuid（对外一律 uuid，内部无自增外泄）
  question: 一句话问题（≤200 字）
  flavor: "watch" | "dig"        # 盯梢型 / 啃题型
  trigger: { cron }              # 例 "0 9 * * 1"（每周一 09:00）
  status: "active" | "paused" | "closed"
  revision: number               # 改动即 +1，醒来对号用（RoutineTask 同款）
  origin: "user" | "proposal"    # 用户直说 / 提议确认
  findings: [ { id, date, summary(≤200字), body, runConversationId } ]
  pendingPush: boolean           # 有发现攒着等感知推送
  noNewStreak: number            # 连续无新进展计数（饱和提议用）
  createdAt / lastRunAt / closedAt? / closeReason?
}
```

- **课题不进记忆引擎**（照"群会话不进记忆"先例）：发现日志是课题私产，总管引用靠系统提示里的清单摘要，不污染个人记忆召回。
- 进行中课题上限 **5 个**（常量），超限时提议确认与建课题返回 `topic_limit`。
- 运行历史不另设表：每次研究回合 = 一条后台专线对话（见 R2，不出卡）；课题只留 findings + runConversationId 存档。

### 决策 T2：口味两种，v1 就分（用户已拍板）

- **watch 盯梢型**（盯政策/价格/论文/动态）：研究提示词强调"和上次比变了什么"；没有新进展要明说。
- **dig 啃题型**（搞懂一个大问题）：研究提示词强调"接着上次往下啃一小块"；发现日志就是进度。
- 两者提示词只差一段，共用同一执行链路。建课题时默认 watch，提议卡上由总管按语境给建议口味。

## 三、表达口（两个，都只到"确认才建"）

### 决策 E1：口 1 —— 用户直说 → `propose_topic` 工具（带确认）

用户说"这个长期帮我盯着""每周一给我讲讲这块"→ 总管调 `propose_topic(question, flavor, cron?)` → 与 propose_project 同语义：**只提交待确认请求，不建实体**。会话底部出确认卡（同口 2 的卡），用户点「开课题」才真建。
服务端校验（工具执行时先查）：同题未完结课题已存在 → 返回已有课题 id 与"已在跟"提示；搜索未配置 → `search_not_configured`；超上限 → `topic_limit`。

### 决策 E2：口 2 —— 总管当场嗅探 → 对话底部的提议卡（用户已拍板"当场判"）

- **判据放总管系统提示**（agent.ts 系统提示装配处加一段）：开放性问题 + 今天给不了定论 + 值得回头查 + 用户显出兴趣；判据从严，宁可少提。同一话题单会话内最多提一次。
- 总管判到就调 `propose_topic`（origin=proposal）。**永不自动建课题**——误判的代价是烦人，不是出错；所以自动提不自动建。
- 巩固层"事后看跨天兴趣再提"**二期观望**，一期不做（明确不做）。

### 决策 E3：提议卡 = 会话内卡片，前端认工具结果，零契约改动

- 渲染照 approvalCards 的路子：`propose_topic` 的工具结果 JSON 里带 proposalId / question / flavor / cron / 预设节奏，前端识别后在该条工具消息位置渲染「课题提议」卡（图钉在对话流的末尾，自然满足"对话结束放底下"），按钮「开课题 / 不用了」打 REST。
- 卡片状态可查：`GET /api/v1/topics/proposals/:id`（pending / accepted / declined / expired），刷新页面后卡片仍能按 transcript 里的工具结果重渲、按查询结果定状态，不靠内存。
- 提议 72h 未理 = expired（防僵尸卡）。

## 四、执行链路

### 决策 R1：`TopicTask` 照 RoutineTask 范式起新任务，不动例行任务

- `defineTask`：wait = `sleepUntil(cron 下次触发)`；deliver = 先排下一个（同一事务，断链自续），再 fire-and-forget 触发研究引擎；醒来先对 `revision`，对不上作废（课题被改/停/删）。
- ownership 挂总管主会话（照 RoutineTask 的 conversation 写法，落地时对齐 durable 细节）。
- **不**复用 routines.ts 的执行体——那是执事会话轮；课题是自己的研究回合。复用的是范式（闹钟 + revision + 串行 defer），不是代码。
- 同一课题串行：上一轮没跑完，下一次标 deferred（30s 重试，照抄例行任务铁律）；重启后 running → interrupted，不自动重放。

### 决策 R2：研究回合 = 一条后台专线对话（不出卡）

- 到点起一条后台专线对话（task- 前缀，照例行任务 fresh 会话先例，不进侧栏对话列表；**任务中心不出卡**——那里的卡是 chancellor 派活单，课题不走 chancellor，2026-11-07 核实）。系统提示 = 课题研究提示词（按 flavor 选段）+ **课题问题 + 全部发现日志**注入——这是课题和普通例行任务的本质区别：**接着上周往下查，不是每周从零开始**。
- 工具面只给只读：`web_search` / `recall` / `read`，不派活、不写文件、不过 chancellor。
- 结束时系统**确定性**取最后一条 assistant 消息存为 finding（不靠模型调工具落盘）；要求模型按约定格式收尾两行：「结论：…」「相比上次：…」（watch 型允许"无新进展"）。
- runConversationId 仅存档备用，一期不做跳转（专线对话不进对话列表，侧栏时间线直接展示发现摘要与正文）。
- 模型用当前默认模型；**不给课题单独配模型**（明确不做，二期再看）。

### 决策 R3：感知推送 —— 不炸屏，用户来了才报，一次清空（用户已拍板）

- 研究回合产出 finding → `pendingPush = true`，**不主动往主对话塞消息**。
- 感知点：**主对话收到用户消息**时（agent.ts 用户消息入口），检查有 pendingPush 的课题 → 把简报块注入当轮系统提示（课题名 + 最新发现摘要，合并多条课题一次报），总管随回复自然带出；注入即标记已推送（每课题每次活跃只报一次）。
- 用户长时间不来，简报就攒着；侧栏课题时间线随时可看，不等推送。

## 五、收口

- 用户说"不用跟了" / 侧栏点关闭 → closed（留 closeReason），数据不删。
- **饱和提议**：watch 型连续 3 次"无新进展" → 在下一次感知推送里附带提议「这题饱和了，关掉？」（仍是提议，不是自动关）。
- 课题可暂停（paused：不排下一次闹钟，恢复时重排）。
- 上限 5 个 + 提议 72h 过期，两道闸防堆积。

## 七、硬约束对齐

- **回滚开关**：`TOPICS_ENABLED=false` → 不注册 propose_topic / web_search 不对课题开放、不排 TopicTask、提议卡不再出；已有课题数据保留不跑。搜索本身以 key 为天然开关（没 key 工具报引导错误），不另设 env。
- **密钥**：S2 全程照既有纪律；测试连接的响应不含 key。
- **日志**：研究回合日志只记条数 / 耗时 / 结果枚举；发现正文只进课题文件与会话，不进服务端日志。
- **对外 id**：课题 / 提议 / finding 全 uuid。
- **闸门**：研究回合工具面只读，不进 WRITE_TOOLS；不新增会写文件的工具。
- **契约顺序（接口文档 §7）**：一期不动 `shared`（SSE 无新帧，卡片前端认工具结果；REST 为本仓 web 专用）。**手机端要看课题/收简报 = 二期，动 shared + 接口文档再开工**（用户已拍板二期写在文档上）。
- **回写落点**：端点与 env → `接口文档.md`（§2 新增课题端点组、§6 增 TOPICS_ENABLED / SEARCH_BASE_URL）；模块机制（TopicTask 范式、感知推送、课题不进记忆引擎）→ `系统架构.md`；"刻意没有"清单补：不做搜索供应商抽象 / 不做手动建课题 UI / 不给课题单独配模型 / 不做巩固层事后嗅探。

## 十一、明确不做（一期）

- 搜索供应商抽象（固定 DeepSeek）
- 手动建课题 UI（口只有两个）
- 手机端看到课题 / 收简报（二期，动契约时一起）
- 巩固层事后嗅探（二期观望）
- 课题单独配模型
- 研究产出自动写文件（发现只进课题日志）

- 研究回合出任务中心卡（卡=派活单，课题不出卡，可见性走侧栏时间线）
