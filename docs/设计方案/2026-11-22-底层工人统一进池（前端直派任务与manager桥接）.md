# 底层工人统一进池（前端直派任务与 manager 桥接）

> 状态：已落地（2026-11-22；真 HTTP 直派 / 真 manager→池子单已跑通；manager 子上报与工具勾选真跑未验）
>
> 本文是《派活工人执行器池（独立进程复用宿主运行时）》与《调度层与执行器池的合并方案》
> 的续篇，只解决一件事：**“新派出去的最底层 worker 一律在第二套运行时（池）里跑”**。
> 与长期文档冲突时，以 `docs/基线文档/系统架构.md` / `接口文档.md` 为准；本文只记录
> “当时为什么这么切、哪些刻意没做”。

## 一、问题

池已经落地并成为默认（`executorForDelegation()` 缺省 `pool`），但还漏两类入口：

1. **前端没有“直接派一件底层活”的入口。** 侧栏「任务」只有“新建对话”（宿主里的
   普通助手会话）。用户想派一件活，必须先跟助手说一句，由模型决定调 `delegate`。
   用户口径（2026-11-22）：「前端新建一个普通对话任务……应该是另一套运行时，
   不是复用旧进程」。
2. **manager 路径的子单仍回落 native。** 总管 / 普通助手带领域派活 → chancellor 起
   `worker-main.ts --role manager` 子进程 → 子单 `createEmployee("pool")` 在 manager
   进程里找不到宿主注入的 `PoolClient`，于是回落 native。用户口径：「无论是谁，
   只要派一个活儿，是一个最底层的 worker，它都应该是另一套运行时」。

另外三个已核实的小洞：

- **池的取消路由打错**：`supervisor.postAbort()` 打 `/abort`，池服务端是
  `/run/:ticketId/abort` → 404；取消只能等 10 秒后断流杀进程。
- **池不吃 worker 工具面勾选**：`run.tools` 一路传到 `pool-main` 却没被使用；
  `createPoolEmployee` 也没读 `workerAllowedTools()`。
- **manager 子单的取消 / 上报没有宿主入口**：子单在 manager 进程里创建，宿主
  没有它的 `AbortController`；上报也只回到 manager 进程（manager 的 `delegate`
  工具没有 `onEvent`），用户看不到。

## 二、拍板与范围

| # | 决定 | 理由 |
|---|---|---|
| 1 | 前端「新建任务」= **直接建票 + 强制 pool**，不走宿主助手回合 | 用户要的是“派活”，不是“再开一个助手会话”。直派也避开模型先理解再转述的一层损耗 |
| 2 | 任务的可视线程 = 既有 `task-<ticketId>` 专线；用户发话写**真 `pi.user` 条目**，不再触发宿主投影模型 | 线程是显示层；执行在池。投影模型跑一轮就是“复用旧进程”，与口径冲突 |
| 3 | 任务会话的输入按票状态分流：跑动中 → `POST /agent/delegations/:ticketId/message`（steer）；等回答 / 空闲 → `POST /tickets/:id/say`（续跑） | 复用已有的插话 / 回话通道，不另造协议 |
| 4 | manager 子单进池：宿主开一个**仅 loopback 的池桥**（HTTP + SSE），只把 endpoint + token 经 env 交给 manager 子进程 | manager 进程不能 import 宿主；池桥与池进程的 IPC 同形，chancellor 侧只多一个 HTTP 客户端。token 不进日志、不过公网 |
| 5 | manager 子单的上报转发回**父单来源会话**：池桥收到 escalation，读子单 `originConversationId`，走既有 `emitDelegation` → 上报路由 | 复用现有“总管/执事代答 → 升级用户 → 答复回 worker”的链路，不新建一套 |
| 6 | 宿主取消 manager 子单：没有票级控制器时，按 `ticket.employee=pool` 回落 `poolControl.abort()` | 池桥里的票在宿主 supervisor 的槽位表里，取消入口本来就有，只是没接 |
| 7 | 池吃 worker 工具面：canonical 四件按勾选过滤，`escalate` 恒开 | 与 native 的 `--tools` 同口径；上报是池工人的通信手段，不能被勾掉 |
| 8 | 新入口 / 新桥各留一行 env 回滚 | `DIRECT_TASK_POOL=false`、`POOL_MANAGER_BRIDGE=false`；池本身仍可 `CHANCELLOR_EMPLOYEE=native` 整体回滚 |

## 三、接口与数据流

### 3.1 前端直派任务

```text
侧栏「任务」⋯ → 新建任务
  → POST /api/v1/agent/tasks { requirement, project? }
  → 分配单号（预分配，先建专线）
  → ensureTaskConversation(ticketId) 写一条真 pi.user（不跑模型）
  → startDelegation({ ticketId, conversationId: 专线内部 id, executor: pool })
  → 返回 { ticketId, conversationId: "task-<ticketId>" }
前端 → 打开会话；进度 / 汇报 / 上报由 mirror 写进专线
用户再说话 → 跑动中 steer；否则 /tickets/:id/say 续跑
```

**新增接口**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/agent/tasks` | 直派一件底层活；body `{ requirement, project? }`；强制 pool（可回滚） |

**契约变化**

- `ChancellorRequest.ticketId?`：预分配单号（只给直派任务用；不传 = chancellor 自生成）。
- `DelegationKickoff.ticketId?` / `executor?`：宿主侧装配缝，不跨仓。
- 任务专线的 `submitTaskReply()` 从“写 input 触发投影模型”改为“写 `pi.user` 条目”，
  不触发宿主回合。

### 3.2 manager 子单进池（宿主池桥）

```text
宿主 index.ts
  ├─ WorkerPoolSupervisor（已有，管池进程）
  ├─ startPoolBridge(supervisor) → { endpoint, token }（仅 127.0.0.1，随机端口）
  └─ setManagerPoolBridge({ endpoint, token })
        ↓ runManager spawn 时注入 env
manager 子进程（worker-main --role manager）
  ├─ createEmployee("pool") 发现 CHANCELLOR_POOL_ENDPOINT
  ├─ 子单 → HTTP POST /run → 宿主池桥 → supervisor.run → 池进程
  └─ SSE /run/:id/events ← 池事件（progress / escalation / settled）
```

**池桥端点**（与池进程的 `pool-server.ts` 同形，便于 chancellor 复用一套客户端语义）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/run` | 收票，立即 202；事件走 SSE |
| GET | `/run/:id/events` | 事件流（先回放后实时） |
| POST | `/run/:id/say` | 插话 / 上报答复 |
| POST | `/run/:id/abort` | 中止 |
| GET | `/health` | 槽位快照 |

**安全边界**：只 bind `127.0.0.1`；除 `/health` 外一律 `Authorization: Bearer <token>`，
失败 403 空体；token 每次宿主启动随机生成，只进 manager 子进程 env，不写文件、不进日志。

**manager 内部模型（实测补洞）**：manager 子进程没有宿主的 `installInternalAsk()`，
子单拆单走 `askInternal()` 时旧兜底会去 spawn Qoder CLI；本机没配 Qoder → 子单
`needs_you`（`qoder-intl 子进程 ENOENT`）。落地时在 `worker-main.ts` 的 manager 角色
用自己刚建好的 `models` / `model` 装了一份 `installManagerInternalAsk`（纯文本完成、
不挂工具），拆单不再依赖外部 CLI。

### 3.3 上报与取消

- **上报**：池桥把 `escalation` 事件同时（a）推给 manager 的 SSE 客户端（manager 忽略），
  （b）读子单 `ticket.json.originConversationId`，走 `emitDelegation` → 既有上报路由。
  用户在任务卡 / 派活会话里答复 → `forwardWorkerMessageAction` → `sayWorker` →
  `supervisor.say` → 池进程续跑。
- **取消**：`cancelTicketAction` 先试票级 `AbortController`；没有且 `employee=pool` 时
  调 `poolControl.abort(ticketId)`。池进程收到 `/run/:id/abort`，runner 的 signal 触发，
  `run-queue` 结算为 `aborted`，不杀槽位。

## 四、刻意不做

1. **不把普通助手会话的完整模型循环搬进池。** 历史读、记忆引擎、审批、流式 delta、
   逐句交互仍是宿主硬依赖（详见池方案 §三）。本批的“会话进池”指**任务线程**：
   线程是显示层，执行在池；不是把 `chatKind=worker` 的宿主 Harness 会话整体搬走。
2. **不动外部 CLI 打手**（CodeBuddy / Qoder / Claude / Codex / OpenCode）。它们的
   调度与登录态不在本批语义里。
3. **不做“等上报让出槽位”、池崩溃按票重派、池队列可见性**（合并方案 M2/M4 的其余项）。
4. **dist 产物仍不支持池**（池入口是源码 `.ts`）；`available()=false` 时照旧回落 native
   并告警。
5. **不做按任务选择执行器**；池 / native 仍是全局默认 + 回滚 env。
6. **不把密钥值送进池桥**；`modelRoute` 仍只传 `baseUrl + keyEnv` 变量名。

## 五、回滚

| 开关 | 缺省 | 关掉后的形态 |
|---|---|---|
| `CHANCELLOR_EMPLOYEE=native` | — | 所有新单回到 native（每票子进程），池不参与 |
| `DIRECT_TASK_POOL=false` | 开 | 前端直派任务仍可用，但执行器跟随设置（可能是 native / 外部 CLI） |
| `POOL_MANAGER_BRIDGE=false` | 开 | 不起池桥；manager 子单回落 native（改动前形态） |
| `WORKER_TOOLS_DISPATCH=false` | 开 | 池 / native 都不按勾选过滤，工具全开 |

## 六、验收

1. 侧栏「新建任务」→ 写一句话 → 直接出现任务线程；任务中心该单 `employee=pool`，
   宿主 `worker-pool` 日志有 dispatch / settle 行。
2. 任务线程里再说话：跑动中走 steer，等回答时走 `/tickets/:id/say`；池 worker 上下文
   能看到这句话（探针或任务详情留言）。
3. 带领域的派活（manager 路径）：子单 `ticket.employee=pool`；池桥日志 / 观测 jsonl
   能看到该票；宿主没有新的 native 进程。
4. manager 子单上报：任务卡出现上报；答复后池 worker 续跑并结算。
5. 取消 manager 子单：5 秒内槽位 `activeTicket` 变空，进程不崩。
6. 池 worker 工具面：勾掉 `bash` 后新票的工具列表没有 bash（仍保留 escalate）。
7. `CHANCELLOR_EMPLOYEE=native` / `POOL_MANAGER_BRIDGE=false` 两个回滚路径行为与改动前一致。

## 七、已知边界（如实写）

- manager 子单的 `modelRoute` 只继承 `baseUrl + keyEnv` 变量名；若该供应商的 key
  没有出现在宿主 pool 进程 env 里，池内模型调用会失败，需要在宿主 `.env` 提供该变量。
- 任务线程的“等回答”依赖票状态；票在 `planning`（还没起 worker）时发话只能提示稍后
  再发，不做队列缓冲。
- 任务线程不做附件 / 图片输入（先只收文字）。
- `task-` 专线仍由宿主存储承载（显示层）；如果将来把线程存储也搬走，属于另一个方案。
