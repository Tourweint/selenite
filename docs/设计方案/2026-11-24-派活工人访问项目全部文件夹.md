# 2026-11-24 派活工人访问项目全部文件夹

状态：**已落地**（2026-11-24）。实施记录见
`docs/变更记录/2026-11-24-派活工人访问项目全部文件夹与项目索引文案.md`；
结论已下沉到 `docs/基线文档/系统架构.md` §7 与 `docs/基线文档/接口文档.md` §6（env 表）。

> 一句话：派活按**项目**下发，项目下的每个文件夹都进工人的可见 / 可写范围；
> 主文件夹仍是唯一的 worktree / 合并 / 租约单位，其他文件夹共享读写（沿用 2026-11-13 项目容器方案已登记的边界）。

## 起因（用户口径 2026-11-24）

- "派活的这个工人（pool）肯定是能够进入他的这个项目的，而不是说定死了文件夹。"
- "我们发这个消息的时候，肯定是按照项目，而不是按照文件夹。"
- "不只是主文件夹，别的其他的也都要进入。"

## 现状（2026-11-24 代码核对）

2026-11-13《项目容器：一个项目 = 一个名字 + 一组文件夹》已经定了语义：`ProjectRef.roots[]`
下发派活侧，`worktree / 验收基线只认 primary`，**附加根是共享读写**（不进 worktree、不合并、
不独立租约），登记为已知边界。但落地时只有前一半接上了：

| 层 | 现在 | 结果 |
|---|---|---|
| `project-store.resolveForUse` | 返回 `roots[]` | 服务端有 |
| chancellor `normalizeProject` | 只保留 id/name/rootPath/vcs/head/dataDir | `roots` 被剥掉 |
| `dispatchTask` / `buildWorkerPrompt` | 只认 `workDir` | TASK.md 只有主文件夹 |
| `scheduler` worktree / 合并 / 租约 | 只认 `project.rootPath` | 其他文件夹不在隔离范围 |
| 池 run payload | 只有 workDir / instruction / doneWhen / writes | 池不知道其他文件夹 |
| 池 `pathBlockReason` | `[taskDir, workDir]` | read / write / edit 被挡在主文件夹之外 |
| 池 `buildTaskProfile` | 边界只写任务目录 + 工作目录 | 工人不知道项目还有别的文件夹 |

于是产品上"派活按项目"只兑现了主文件夹这一半。

## 决策

### D1 主文件夹仍是唯一隔离单位（不变）

- `worktree` 只从主文件夹拉；越权检查、合并、租约只对主文件夹的改动生效。
- 主文件夹在隔离模式下对工人呈现为 worktree 副本（`workDir`），**真实主文件夹不进池的路径边界**
  （否则工人绕过副本直接写项目）。

### D2 其他文件夹直接读写真实目录（沿用 13 日方案）

- 不进 worktree、不复制、不合并、不租约、不参与越权检查。
- 并发写冲突不在本次解决范围——这是 2026-11-13 方案已登记的已知边界，本次只是把它接线。
- 工人可以用绝对路径读写这些文件夹；相对路径基准仍是 `workDir`。

### D3 下发链路

```text
server ProjectRef.roots
  → chancellor normalizeProject 保留 roots
  → scheduler 按隔离形态过滤：
      worktree（主文件夹有副本）→ 只下发 role=extra
      非隔离                     → 下发全部 roots
  → dispatchTask
      ├─ TASK.md（外部 CLI）列出这些文件夹
      └─ 池 run payload.roots
            ├─ task profile 的「工作边界」列出路径
            └─ pool-tools pathBlockReason 的目录集合加入这些路径
```

- 提示文案按 roots 列表判定：含 `role=primary` = 非隔离（列全部根）；只有 extra = 隔离（"不在副本里"）。
- 池的管理进程（manager）提示词同样列出 project roots；经理子进程派活时靠
  `--project-roots`（JSON）把 roots 带进自己的 `project`，否则子单会退回只给主文件夹。
- 单根项目 / 回滚开关关掉时：下发行为与今天一致（只给主文件夹）；工人纪律措辞改为
  「任务目录 / 工作目录 / 项目文件夹（精确路径见工作边界）」，边界段内容不变。

### D4 回滚开关

`DELEGATION_PROJECT_ROOTS=0/false/off` → 不下发 roots，回到"只给主文件夹"。
默认开。开关在 chancellor 侧读 env，宿主与 manager / 池进程自然一致。

### D5 外部记忆库槽位的项目索引文案（顺带修口径漂移）

外部库槽位下 `recallContext` 整条不注入，项目记忆不会"自动想起"；但
`projectIndexProvider` 仍注「聊到哪个项目，相关的项目记忆会自动想起」，
且多挂载时提示"用 remember 的 project 参数指名写"——两件事在该槽位都不成立。

按用户 2026-11-24 口径"按照行为来"：external 槽位改成
「项目记忆不会自动带进上下文；要查用 recall（当前接的是外部记忆库）」，
不再提示 remember 的 project 参数。builtin 槽位文案不变。

## 明确不做

- 其他文件夹的 worktree / 复制 / 合并 / 独立租约 / 冲突检测。
- 外部 CLI 厂商沙箱的强制放行：TASK.md 会给出路径，能否真的写到 cwd 之外由各 CLI 原生沙箱决定。
- 删除 `delegate` 的 `workdir` 参数 / 会话 cwd 快照：本次只保证"项目内其它文件夹可达"，不改选目录能力。
- 项目记忆写入在 external 槽位下的行为：现状是只写原话进外部库、`scope=project` 不生效；
  用户 2026-11-24 已确认接受，本次不接 A 方案。
