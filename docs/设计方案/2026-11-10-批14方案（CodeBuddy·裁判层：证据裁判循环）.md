## 〇、为什么这三条要合并

三条都是"完成由第三方证据定义，而不是由执行者自报"，但形态不同：

| 条 | 形态 | 时机 |
|---|---|---|
| 七 #14 /goal judge | **过程证据**：会话空闲时独立 reviewer 按目标判 done/continue/blocked/wait | 持续 |
| 七 #22 codex review | **验收证据**：起 one-shot 独立评审 agent 看 diff，findings 回写 | 一次 |
| 七 #36 dim evaluator | **裁判会自己读文件跑检查**，不靠报告 | 一次（但带工具） |

**我们的现状（2026-11-10 勘察）**：
- 已有 **D13 验收快照**（结果核对，确定性）+ 批 11 的**核对-修复循环**（不合格自动返工 N 轮）。
- chancellor 已有 `checkTicketGoal()`（`chancellor/src/goal.ts:29`）——**一次 LLM 调用**判整体目标是否达成，
  `buildGoalPrompt()`（`:104`）的提示词已经写了"材料不足就判 satisfied=false""假成功最常见"这些纪律，
  但**它没有工具**（`:133` 明写"你没有工具，不能读文件、不能执行命令"）——只能读宿主喂给它的材料。

所以缺的不是"要不要裁判"，而是**裁判能不能自己去查**。这就是本批要做的唯一一件事。

## 一、目标（一句话）

把 `checkTicketGoal` 从"看材料下判断"升级成**"能自己读文件、跑只读检查，再下判断"的证据裁判**，
并把它的结论接进已有的核对-修复循环里——不合格继续返工，而不是交人。

## 二、设计

### 2.1 裁判形态：read-only 子会话（不是子进程）

复用现有"研究专线"的收敛方式（`configureResearchChat`：只给 `read` + 明确白名单），
新建 `configureJudgeChat`：**工具面 = `read` + `bash(只读白名单)`**，无写、无 edit、无派活。

理由（写进代码注释）：裁判一旦能写，就能"自己把活干了再宣布通过"，证据就没了。

### 2.2 裁判输入（四样，都有出处）

1. **用户原话**（`ticket.prompt`）——用 `<untrusted_objective>` 包裹（照批 11 的注入防线）。
2. **任务单的 steps 与 writes**（批 11 已落）。
3. **落盘事实**：`review.json` 的逐条 verdict + 快照比对的 changed 列表。
4. **执行者自报**（worker 的 result.line）——**明确标注"这是自报，不是证据"**。

### 2.3 裁判结论（四态，与 opencode 对齐后裁剪）

`{ verdict: "done" | "continue" | "blocked" | "wait", evidence: string[], reason: string }`

- `done`：目标达成，且 `evidence` 里**至少一条**是它自己查到的（读了哪个文件 / 跑了什么检查看到什么）。
- `continue`：还没做完但**有明确下一步**——`reason` 必须写出下一步是什么、要改哪里。
- `blocked`：缺信息或缺授权，人才能推进（→ 走 attention）。
- `wait`：等外部条件（→ 走 needs_you 但文案不同）。

**铁律（写进提示词）**："执行者说完成了不是证据。"结论里没有自己查到的证据，就不许给 `done`。

### 2.4 防打转三判据（照 opencode）

- `MAX_JUDGE_ROUNDS = 3`（与 `DELEGATION_ACCEPT_ROUNDS` 正交：那是"返工几轮"，这是"裁判最多来看几次"）。
- 同一个 `reason` 连续出现 2 次 → 判 `blocked`（不是 continue），交人。
- 裁判这一轮**没调用任何工具**却给了 `done` → 降级为 `continue` 并记一条 warning（"没查就给通过"）。

### 2.5 接进既有循环

`runChancellor` 的返工循环里，**返工前先问裁判**：

```
验收 fail → 判裁判
  裁判 done      → 说明验收判太严 → 记 warning，按 done 收（人工可查这条 warning）
  裁判 continue  → 用裁判的 reason 作为修复要求（比机械的"0 个变更"具体得多）→ 返工
  裁判 blocked   → needs_you，带裁判给的问题
  裁判 wait      → needs_you，文案"在等外部条件"
```

**验收 pass 时不叫裁判**（快路径不变，省钱）。

### 2.6 开关与成本

- `DELEGATION_JUDGE`（默认 **false**）：开了才叫裁判。理由：裁判 = 额外一次带工具的模型调用，
  个人机器上默认关、按需开更诚实。
- `DELEGATION_JUDGE_MAX_ROUNDS`（默认 3）。
- 一次裁判的调用数上限：`DELEGATION_JUDGE_MAX_TOOLS`（默认 8）。

## 三、明确不做

- **不做常驻 /goal 循环**（opencode 那种"会话一空闲就判一次"）：我们没有长跑目标会话，
  收益 < 成本。只做"派单收尾时判一次"。
- **不做裁判写代码**：read-only 是这条设计的立身之本。
- **不替换 D13 验收快照**：快照是确定性底线，裁判是它不够用时的补充。
- **不上多模型互相评（LLM-as-judge 的评审团）**：单人自用没必要。

## 四、验证

- 裁判是 read-only：单测断言它的工具面只有 `read` + 白名单 bash（写类被结构性摘掉）。
- 四态结论解析：`done` 无证据 → 降级 `continue`；同 reason 两次 → `blocked`。
- 接进循环：验收 fail + 裁判 continue → 返工要求 = 裁判 reason；裁判 blocked → needs_you。
- 开关 false：行为与今天逐字节一致。
- 真模型手验归派单人（这条必须真跑，mock 验不出裁判好不好使）。

## 五、风险

1. **裁判可能比执行者更贵**（带工具多轮）。缓解：默认关 + 只在验收 fail 时才叫 + 工具数与轮数双上限。
2. **裁判可能"和稀泥"给 done**。缓解：无证据不许 done 的降级规则 + 记 warning 可查。
3. **裁判自己读到的可能是执行者刚写的错文件**（同一工作区）。缓解：裁判读的是**worktree 合并后**的状态，
   且要求它在 evidence 里点名路径，人可复核。
