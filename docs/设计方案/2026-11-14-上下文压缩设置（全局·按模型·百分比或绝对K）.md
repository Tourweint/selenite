# 上下文压缩设置（只两档 · 默认 70%）
> 状态：已落地（2026-11-14）。本文留"当时怎么想的"；冲突以长期文档（接口文档.md / 系统架构.md）为准。


> 一句话：把"什么时候自动压上下文"从内核写死的「窗口减 16384」改成界面上能选的一档——
> 按窗口百分比（默认 70%）或按绝对 token（K）。2026-11-14 用户两次拍板：**只留这两档、默认 70%**，
> 保留原文与后台提前不进界面。

## 结论

| 项 | 决定 |
|---|---|
| 落点 | 全局（Harness 级）＋ 按模型覆盖（`modelOverrides`），**不做每会话一份**——内核没有这个粒度 |
| 界面 | 设置 → 会话 → 「上下文压缩」：三行——自动压缩（开关）／按什么算（按百分比 · 按 token）／到多少压一次 |
| 档位 | `percent`（默认 **70**）／`tokens`（填 K，1K = 1024）；**没有"跟随内核"这一档** |
| 生效 | 改完**下一轮**生效，不重启。`Harness.open` 的 `settings` 传函数、内核每次使用现读（`harness.js:100-123`） |
| 删掉的旋钮 | 保留最近原文（`keepRecentTokens`）、后台提前压（`backgroundTokens`）——一律吃内核默认 20000 / 32768 |
| 回滚 | `AGENT_COMPACT_ENABLED=false` 关掉自动压缩（手动 `/compact` 仍可用）；或把档位拨回 70% |

## 为什么是"按模型"而不是"按会话"

内核的压缩判据是 `估算 token > contextWindow - reserveTokens`（`generation.js:236-246` 实读），
`contextWindow` 是**模型的属性**；策略解析 `compactionPolicy(settings, model)` 只按
`${provider}/${modelId}` 查 `modelOverrides`（`compaction.js:194-203`）。

- `Conversation.configure(AgentChange)` 收 model / tools / instructions / cwd，**不收 compaction**；
- `HarnessOptions.settings` 是 `HarnessSettings | (() => HarnessSettings)`，那个函数**没有会话参数**。

所以"每会话一份"只能靠宿主自己估 token、自己调 `compact()`：
`compact()` 是"受理后到下一个边界落地"，不是阻塞压缩（`types.d.ts:689-693`），
等于把"这一轮已经装不下"交给上游报 `context_overflow` 去兜——代价比收益大。本批不做。

按模型则天然成立：百分比必须按各模型的窗口换算，正好落在 `modelOverrides` 上。

## 口径（env / flags 四个键）

| 键 | 默认 | 语义 |
|---|---|---|
| `AGENT_COMPACT_ENABLED` | `true` | 自动压缩总闸（阈值 + overflow 兜底）。`false` = 只剩手动 `POST .../compact` |
| `AGENT_COMPACT_TRIGGER_MODE` | `percent` | `percent` 按窗口占比／`tokens` 按绝对量。旧值 `default` 回落 `percent` |
| `AGENT_COMPACT_TRIGGER_PERCENT` | `70` | 窗口用到多少百分比就压（整数 5–95，越界夹回）。**默认即生效** |
| `AGENT_COMPACT_TRIGGER_K` | （空） | 绝对触发点，单位 K；空 = 该档不生效、回落内核默认白 |

换算（`compaction-settings.ts`）：

```text
trigger = 用户说的"到多少压"          // percent → round(window × p / 100)；tokens → K × 1024
reserve = window - trigger            // 内核吃的是"给回答留的白"，我们吃的是"用到多少就压"
reserve 夹在 [1024, window - 1024]    // 两头都留一点，避免 0 / 负数把判据顶穿
```

用户的口径（原话）：**窗口 100K、按 token 填 70 → 到 70K 就自动压一次、压完再接着执行任务。**
换算后 `trigger = 71680`、`reserve = 30720`，内核判据 `tokens > 102400 - 30720` 正好就是"到 70K"。

## 明确不做

- **不做每会话策略**（内核不给这条路；要做等于自建压缩，需另立方案）。
- **不做"跟随内核"档**（用户否掉：那一档的意义就是"别动"，而他要的就是调）。
- **不做保留原文 / 后台提前的可调界面**（用户否掉：不是能凭直觉调的量；内核默认可用）。
- **不改压缩提示词与摘要结构**（`compact(instructions)` 的 instructions 仍是手动命令那条口）。
- **不保证"一定压得动"**：保留原文 ≥ 触发点时 `selectCut` 找不到切点，就是不压。那是内核默认值下的行为，不假装它一定发生。
- **不在界面实时预估"当前会话离触发还有多远"**：判据是 `estimateContext` 的估算值，不含系统提示与工具描述，
  报一个假精确的数字比不报更坏。

## 这条会怎么错

| 风险 | 兜底 |
|---|---|
| 百分比按模型覆盖，模型不在 `providers.json`（faux / 未登记派生）时回落内核 16384 | 属于预期：那类模型没有可信窗口。启动日志打印实际档位与覆盖数 |
| 按 token 填得超过窗口 | `reserve` 夹到 1024，即"几乎每轮都压"，界面 hint 写明 |
| 绝对 K 对所有模型一视同仁，小窗口模型会被压得很勤 | 用户口径就是要绝对量；要按比例就拨回百分比档 |
| 关掉自动压缩后上游仍报 `context_overflow` | `stream-error.ts` 的既有兜底话术照旧；`/compact` 仍能手动压 |
