## 〇、一句话

A1 给 agent 的工具调用循环装"防原地打转"守卫（纯函数类 + beforeTool/afterTool 两个现成钩子，
v1 疑似只告警、铁证才中断）；A2 给派单回执补两个洞（pending 跨进程一律 uncertain；
父单终态后迟到的子单结果落死信不丢）。两件互不依赖，都不碰契约对外形状的既有语义。

## 一、目标与明确不做

**做**：模型连续重复调用同一工具空转时，能被检测、被告警、（铁证时）被拦下；
崩溃/重启后回执判定不出现"上个进程的受理被本进程默认放行"的口子；迟到的子单结果有账可查。

**不做（v1 明确砍掉）**：
- 辅助模型复核（cindy 的 ToolLoopMonitor）——需要挑便宜模型的口径，单独立项；
- 每模型/每会话的阈值配置面——只留 env 常量；
- chancellor 仓库内改动（pid 判活加启动时间比对属 chancellor 自身的恢复加固，另行登记，不混进本批）；
- A2 不改 `begin()` 四分支的既有语义，只**收紧**判定条件（新增 boot 代号维度）。

## 三、A1 设计：防打转守卫

### 3.1 新文件 `ts/apps/server/src/loop-guard.ts`（纯类，零依赖零 IO）

从 cindy `loop-guard.ts` 裁剪移植，判定阈值照抄（踩坑调出的数值不改）：

| 级别 | 判据（按序检查，命中即返回） | 处置 |
|---|---|---|
| 铁证 1 | 同一指纹连续 ≥30 次完全相同 | 中断 |
| 铁证 2 | 同一指纹的结果持续 ≥60 分钟且仍在重复 | 中断 |
| 铁证 3 | 最近 128 次读类调用中 distinct 指纹 ≤32 且最大重复 ≥4 次（长读轮转） | 中断 |
| 疑似 1 | 同一指纹连续 4 次（name+args+结果都相同） | 告警 |
| 疑似 2 | 12 次滑窗内 distinct ≤2（pingpong） | 告警 |
| 疑似 3 | 16 次滑窗内 distinct ≤4（轮转） | 告警 |

- **指纹** = `name + 归一化 args JSON（键排序）+ 结果摘要（isError + 输出前 N 字符）`，sha256 前 16 位；
- **豁免**：距上次调用 ≥30s 的"节奏轮询"不计入重复判据（照抄 cindy）；豁免工具清单 v1 为空
  （我们没有 sleep/TaskOutput 类等待工具；`set_reminder` 是提交不是轮询）——清单留成常量，后续要加工具再补；
- 每个会话每轮一个实例（挂 `Map<conversationId, LoopGuard>`，轮结束由 `onSettled` 清理，
  与 `runTurns`/`toolsBlocked` 同款进程内 Map 纪律，agent.ts:287-315 现成范式）；
- 只统计顶层调用（`call.parent === undefined`），嵌套调用不喂（防嵌套放大误判）。

### 3.2 接线（只动 `agent.ts` 两处 + 一个事件）

1. `beforeTool`（agent.ts:552 附近，闸门之后、`emitPhase("working")` 之前）：
   `guard.before(call.name, call.arguments)` → 若返回 `interrupt`（铁证）：
   `return { block: LOOP_GUARD_BLOCK_MESSAGE }`（文案对齐 `TURN_LIMIT_INSTRUCTION` 口径：
   "你已连续重复相同的工具调用没有进展，请停止调用工具，直接用已有信息回答"），
   同时 `console.warn` 记枚举（会话号/工具名/命中判据，**不含参数内容**，对齐 D8）；
2. `afterTool`（agent.ts:629）：`guard.after(call.name, call.arguments, result)`；
3. **疑似告警**：新内部事件 `{ type: "loopGuard", pattern: "repeat|pingpong|rotation", count }`
   进 `ChatStreamEvent` 联合（agent.ts:1232-1321）——对外转发策略照 `turnLimit` 先例：
   v1 **只进服务端日志 + 不对外发帧**（客户端无消费场景；等有 UI 需求再放行对外事件，
   届时按"纯增量事件"口径加进 shared）。这样本批对 shared **零改动**。

### 3.3 回滚开关与验证

- 开关：`TOOL_LOOP_GUARD`，读法照 `envFlag`（tools.ts:88-93）惯例：不设 = 开，
  `false/0` = 关（关 = `beforeTool`/`afterTool` 不喂守卫，行为与改动前完全一致）；
- `.env.example` 补登记（注释段对齐现有"审批 ask 流"格式）。
- **验证**：
  - 新单测 `ts/apps/server/src/loop-guard.test.ts`（纯类不碰 IO）：各阈值边界（3/4 次、
    29/30 次）、pingpong/轮转窗口、≥30s 豁免、嵌套调用不统计、开关关闭零判定；
    挂进现有 `pnpm --filter @lifediary/server test`；
  - `pnpm typecheck`；`pnpm --filter @lifediary/server durable` + `http` 探针回归
    （faux 链路正常多轮不误伤——faux 固定文本不会触发指纹重复）。

## 四、A2 设计：回执补差

### 4.1 补差 1：pending 跨进程一律 uncertain（boot 代号）

- `delegation_receipts` 表加列 `boot_id TEXT`（照现有 `migrate()` 的
  `ALTER TABLE ... ADD COLUMN` 惯例，delegation-receipts.ts:65-75；旧行 NULL）；
- 模块内新 boot 代号：`bootId = crypto.randomUUID()`（模块加载期定一次，进程内不变——
  与 DS-Bot `requests.js` 的 run 记录同语义）；
- `accept()` 写 `boot_id = 当前 bootId`；`insert()`（new 分支）同样写入；
- `begin()` 判定收紧（delegation-receipts.ts:123-127 处）：
  - 现状：`accepting && ticketId===''` → uncertain；
  - 收紧为：`accepting && (ticketId==='' || boot_id !== 当前 bootId)` → uncertain——
    **上个进程留下的"受理中"，本进程无法确认它发没发出去，一律按结果未知，不自动重派**
    （fail-closed，宁可让人重提不可重复副作用）；
  - `accepted` 行不动（accepted+终态单已有 recovery 回灌链路，recovery-report.ts:58-89）。
- 单测扩 `delegation-receipts.test.ts`：跨 boot 的 accepting → uncertain
  （测试里直接 `setOutcome` 构造 accepting 行 + 伪造旧 boot_id 后调 `begin()`）；
  旧行 `boot_id IS NULL` 的 accepting 也按 uncertain（NULL ≠ 当前 boot）。

### 4.2 补差 2：迟到子单结果死信（启动恢复路径）

- **场景**：父单已终态（含 aborted）后，子单才在自己 runs_dir 落终态——现状
  `enforceChildClosure` 只在父单收口那一刻读一次 children，之后无人看（§二 已核实）；
- **插桩点选在 server 启动恢复，不动 chancellor**（跨仓改动单独立项原则）：
  `recovery-report.ts` 的恢复扫描流程（reportRecoveredTickets 一带）扩一步：
  对本次扫到的每个**终态**父单，调 chancellor 已导出的 `childTickets(runs_dir, ticketId)`
  （chancellor index.ts:1507-1514），凡存在"父单终态时刻之后才终态 / 仍未终态"的子单，
  逐条写**死信记录**：
- **死信落点**：`delegations.sqlite` 新表 `delegation_dead_letters`：
  `parent_ticket_id / child_ticket_id / child_status / note / created_at`，主键
  `(parent_ticket_id, child_ticket_id)`（重复扫描幂等，`INSERT OR IGNORE`）；
- **可见性**：`GET /api/v1/tickets/:id` 投影（delegation-api.ts:146-151）的 `children` 旁
  补 `deadLetters` 只读投影；不写回会话（避免"已经结算过的事又打扰人"——但探针要断言落库）；
  汇总计数进启动恢复日志（`[恢复]` 前缀，枚举口径）；
- **不做**：不自动重派、不自动并结果（与"中断不自动重放"原则一致）；不给子单补 inflight。

### 4.3 验证

- `recovery.test.ts` 扩两用例：① 父单 done + 子单迟终态 → 死信表有一行、二次扫描不重复；
  ② 父单 aborted + 子单未终态 → 死信表有一行（helper `makeTicket`/`childTickets` 现成）；
- `delegation-receipts.test.ts` 扩 boot 判定用例（§4.1）；
- `delegate-chain-probe` 不动（其断言面向派活帧，与本批无交）；`pnpm typecheck` +
  全量 `pnpm --filter @lifediary/server test`。

## 五、安全与纪律自查

- 日志：守卫与死信日志只记 会话号/单号/工具名/枚举/计数，**不含参数与对话内容**（D8）；
- 对外契约：shared 零改动、`ChatEvent` 零新增（v1 告警不对外）、`/tickets/:id` 投影为纯增量字段；
- 死信表只增不删，无外泄 id（ticket id 本就对外）；
- 两件都不新增工具，闸门无涉。
