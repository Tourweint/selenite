## 零、人话版

现在有两套记忆，互不搭理：

- **小库**（`ts/packages/memory`，`.data/memory.db`）：每轮自动打分召回，16 条 / 2000 字，
  但只覆盖最近与偏好——问"去年"它没有。
- **大库**（persona-metric，60 张表，rag_unit 1.6 万条）：只有 `persona_recall` 工具，
  赌模型每轮"记得去查"。模型不想起来，大库等于不存在。

本方案把大库接进**每轮自动召回**，但不是把 1.6 万条塞进小库打分池（不同构、也没必要），
而是**分层**：小库照旧第一级，大库命中行做第二级（独立预算、独立分组），
再加一段**库目录常驻**让模型知道大库里有什么。中间件放 server，大库保持只读外挂。

## 二、设计

### 2.1 分层（核心拍板）

```
第一级  小库自动召回（照旧）：16 条 / 2000 字，四组渲染，预算不动
第二级  大库轻召回（新增）：≤3 条 / 800 字，独立分组【更早的记录】，不与小库抢预算
常驻    大库目录（新增）：~600 字进静态前缀，模型每轮知道大库有什么
深查    persona_recall 工具（照旧）：证据包级，模型看着目录点名查
```

**大库条目不进小库打分池。** 理由：两库条目不同构（rag_unit 是"证据片"，没有小库的
kind/importance 语义）；16,325 条先过 FTS 才配进池，打分意义不大；分层配额（auto-memory
实测教训：单层 77 条能吃光 800 token 全部预算，"分层"退化成单层）比统一打分干净。

### 2.2 中间件（`ts/apps/server/src/persona-inject.ts`，新文件）

放 **server** 不放 memory 包。理由：依赖方向单向 `shared ← memory ← server`，
memory 包不该 import persona-ask（spawn python 是 server 的装配事）；
memory 包新增窄接口让"外挂源"概念立住，persona.db 只是第一个实现者。

```ts
/** 每轮轻召回：给定本轮 user 文本，返回大库命中行（已过相关性门槛、已限条数）。 */
export async function personaLightRecall(text: string): Promise<string[]>
```

流程（全在中间件内）：

1. **触发判据**：`askPersonaAvailable() && personaAskEnabled()` 之外，新增总闸
   `PERSONA_MEMORY_INJECT`（默认**开**——ASK 已配置即有库，注入是它的自然延伸；
   `false` 一行回退到"只有工具"的今日形态）。
2. **前置过滤**（0 成本，不 spawn）：本轮文本 < 6 个有效汉字 → 直接返回空
   （"嗯""哈哈"这类不值得起 python）。含明显时间疑问词（去年/以前/那时候/之前）
   或直接相关词才继续——判定复用 `directlyRelevant` 的双字片段口径。
3. **spawn `ask.py --json --limit 2`**（每组限 2，总耗时 ~0.8s）：复用 persona-ask 的
   spawn 骨架（argv 数组、不用 shell、15s 超时、stderr 只留 4KB）。
4. **相关性门槛**：`why` 含"关键词命中"的条目，正文必须与 query 有双字交集且
   交集长度 ≥2 字——闲聊（"今天天气不错"）拦在这层。`why` 是其它理由
   （时间锁/类型命中/用户亲口确认）的放行。
5. **去重**：对返回条目正文跑现有 `dedupeRecallHits` 同款 bigram-Jaccard（阈值 0.8），
   同一件事多种说法只留一条。**echo trap 防线**：query 与条目正文近重复
   （Jaccard ≥0.8 或正文包含 query）→ 该条抑制（用户在复述旧事，不是在问）。
6. **限额截断**：≤3 条、每条 ≤120 字（`text` 超长截断带省略号）、总预算 800 字。
7. **渲染**：

```
【更早的记录】（来自主人一生的记忆库，背景不是话题；查不到 ≠ 没有这回事）
- 2026-10-27 答辩老师认为课题偏普通系统设计…（segment · diary）
- 2026-09 毕设被说「太简」不止一次（用户亲口确认）
```

   格式与 buildContext 的行格式对齐：`- [日期] 正文（组 · 来源）`；
   `fact` 组带"用户亲口确认"时原文标注。
8. **并发节流**：同一会话 60s 内不重复轻召回（in-flight 单飞 + 上次时间戳，
   措施与 executor-model-cache 同款）；失败静默返回空（与 recallContext 同口径，
   记忆永远不能把对话卡住）。
9. **日志纪律**：只记 `字数 ok 组数 条数 耗时`，不记 query 原文与条目正文
   （persona-ask 既有纪律，沿用）。

### 2.3 库目录常驻段（`persona_catalog` 注入）

- **内容**：`ask.py --catalog-only` 输出裁剪到 ≤600 字（现有输出 ~4 行数百字，
  超长时空月行砍掉）；复用 `askPersonaCatalog` 的 10 分钟缓存。
- **位置**：注入框架 `INJECTION_ORDER.persona_catalog = 46`，channel **"system"**、
  scope "session"——紧跟 `current_project`(40) 之后、`skills`(50) 之前，
  **进静态前缀**（与 user_profile 同款：净增一段固定前缀，缓存前缀变化一次，预期内）。
- **触发**：与轻召回同一个总闸；只有配置了大库的部署才有这段，未配置 = 零字节。
- **标题行**：`以下是主人一生记忆库的边界（可用 persona_recall 工具查询，查不到 ≠ 没有）：`
- **catalog 缓存失败**：不注入（目录是"锦上添花"段，失败不该留下空标题）。

### 2.4 引用回流（P2，本批不做实现）

轻召回 / persona_recall 命中的条目 id 记进中间件账本
（`.data/persona-recall-usage.json`：`{id, count, lastUsedAt}`），
**不回写 persona.db**（只读契约不动）。用途：攒出"高频证据"清单，
将来按它优化 catalog 排序 / 决定哪些证据值得 prewarm。本批只落账本 + 用量页不加卡。

### 2.5 memory 包窄接口（P2，本批不做实现）

本批先在 server 内部把中间件写扎实；`RecallSource` 抽象接口等第二个外挂源
（voicevault 或别家）真要接时再立——**不预先抽象**（YAGNI；现在只有一个实现者，
接口是想象出来的形状）。

## 三、契约与环境变量

| env | 默认 | 语义 |
|---|---|---|
| `PERSONA_MEMORY_INJECT` | 开 | 轻召回 + catalog 常驻的总闸；`false` = 回到"只有 persona_recall 工具"的今日形态。父闸 = `PERSONA_MEMORY_ASK` 已配置 + `PERSONA_MEMORY_ENABLED`≠关（双闸不过时本闸无意义） |

契约变化：**每轮 system 段净增一段 `persona_catalog`（≤600 字）+ 消息尾部净增一组
【更早的记录】（≤800 字）**。上下文页注入清单会多出 `persona_catalog` 条目
（审计投影自动覆盖）。手机端无感（注入是服务端行为）。

## 四、明确不做（本批拍板）

- **不做向量 / 语义召回**：大库 FTS + 八类判型已够轻召回用；向量等真出现"FTS 捞不回"
  的实测案例再立（小库的 TODO(语义召回) 同样留白）。
- **不大库全量进打分池**：见 2.1。
- **不回写 persona.db**：只读契约（D-甲/D-丙）不破；引用账本只记中间件侧。
- **不做逐轮 Delta / 消息层对比**（dsh-context 那套）：上下文页已有缓存统计，
  够用，不扩。
- **不做 catalog 预热派活**：catalog 就是给模型看的目录，不做别的。
- **群聊**：轻召回与工具同口径整段跳过（群聊不走个人记忆）。
- **执事会话**：轻召回照进（执事也该记得主人的旧事）；catalog 只进总管/普通会话
  （执事轮已有大量 partner_context 注入，再加目录段收益低）。
- **nightly 整理不碰大库**：整理只管 global+partner（既有拍板）。

## 五、回滚

一行 env：`PERSONA_MEMORY_INJECT=false` → 两处净增（catalog 段 + 轻召回组）
全部消失，`persona_recall` 工具照旧，逐字节回到今日形态。
注入框架按 id 收集，不注册 = 零痕迹。

## 六、验收口径

1. `pnpm typecheck` 绿。
2. `pnpm memtest`（memory 包全测）绿——本批不改 memory 包语义，红了=无关红要指出。
3. `pnpm --filter @lifediary/server test` 新增单测绿：
   - 前置过滤（短文本/纯符号不 spawn——用假 spawnFn 断言未调用）
   - 相关性门槛（闲聊 query → 0 条；含直接相关词 → 放行）
   - echo 抑制（query 与命中正文近重复 → 0 条）
   - 限额（>3 条截 3、单条 >120 字截断、总预算 800）
   - catalog 注入（配置了才注、失败不注、空月行裁剪）
   - 节流（60s 内第二次不 spawn）
   - 总闸关闭 → 两处净增消失
4. `pnpm --filter @lifediary/server http`：`persona_catalog` 出现在注入清单、
   未配置环境（隔离实例）不出现。
5. 真库冒烟（配置了 PERSONA_MEMORY_ASK 的本机）：问"毕设答辩那阵子怎样"→
   消息尾部出现【更早的记录】≤3 条；问"今天天气不错"→ 不出现。
6. 日志抽查：无 query 原文、无条目正文。
