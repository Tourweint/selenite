# 设计方案 · 执事招聘模板 + 改人设页交互重构

- 日期：2026-11-15
- 状态：**已落地（当日）**——拍板走了推荐项（六卡照单做 + 9 卡折叠）；落地记
  [变更记录 2026-11-15-执事招聘模板与改人设页卡片化](../变更记录/2026-11-15-执事招聘模板与改人设页卡片化.md)。
  验收时抓到并修复"弹窗流程 SOUL 占位符未替换"一坑。落地形态与本文一致，冲突以变更记录为准。
- 需求方口径：终端用户"不太会用、不知道该建什么样的执事"——要给模板，让他快捷建出一个。
  默认带总管、执事 0 个（现状即如此），空花名册 = 招聘大厅。
- 范围：**电脑端前端为主，零契约改动**（全程走现有端点）；新建弹窗的内部重构后期再说，本轮只做"选模板预填"。

## 一、问题

1. 新手面对「新建执事」三个空格（名字/领域/一句话身份）不知道填什么；建出来的是个空白的人。
2. 档案页（`#/settings/partners/<id>`，2026-11-14 C 版）是"设置式长表单"：
   人设 / 人格模块 / 岗位 / 能力四段从上到下，其中「人格模块」= 预设三选一 + **14 行开关平铺**——
   对懂的人是控制台，对新手是仪表盘恐惧。术语（口吻/里子/处境/印象/心情/内心/学习/主动性/人设库/
   契约/纪律/目标/履历/在办）没有一个解释"关掉会怎样"。
3. 模板文案已落一份（`docs/员工模板-我的执事.md`，2026-11-15），但那是"照着抄"，
   不是"点一下就建出来"。

## 二、"皇帝需要什么手下"——分类与模板清单

分类的尺子不是"会什么技能"，而是**"你让他管什么"**（技能是能力，职责是编制）。
系统真实能力挂载决定每张卡长什么样：

| 卡 | 管什么 | 系统能力挂载 | 预设 | 建议名 |
|---|---|---|---|---|
| **大管家** | 家里杂事：查、整、写、盯 | 普通执事 + 杂事契约 | work + 开口吻/里子/处境 | 小安 |
| **监工** | 一个领域的活，带工人办完 | 领域标签 + 接派单 | work（岗位默认） | 按领域起（建时必填领域） |
| **巡官** | 定时盯一件事，没新信不吵你 | 例行任务（引导建，不自动建） | work | 小巡 |
| **日记官** | 日记、周报、原文归档 | 日记执事开 + 晚间例行引导 | work + diary | 墨墨 |
| **书童** | 读书、资料、笔记整理 | 普通执事 + 整理契约 | work + 开口吻/里子/处境 | 小卷 |
| **知心** | 陪聊，有内心生活 | companion 预设 + 印象/心情/内心 | companion | 阿暖 |

总管**不进模板墙**：他是默认自带的贴身大总管，不是"招聘"来的（每台一个，只跟他说话）。

每张模板卡携带：建议名 / 一句话身份（SOUL 种子）/ 预设 / 开关组合 / 契约种子（四节）/ 口吻里子处境内容 / 岗位开关（diary、dispatch）。内容来源 = `docs/员工模板-我的执事.md` + 各形态变式，巡官/日记官的契约按各自职责改写。

## 三、模板数据与建档链路（零契约）

- 模板 = **前端常量**（新文件 `web/partner-templates.js`）：文案性质，不进 shared、不进存储；
  改模板 = 改前端刷新即生效。
- 建档链路全走现有端点（2026-11-15 核对 companion-api.ts）：
  1. `POST /api/v1/partners` `{name, soul, domain?}` — 建档 + SOUL；
  2. `PUT /api/v1/partners/:id/persona` `{preset, contents}` — 部分合并（预设铺默认表 → contents 按字段合并）；
  3. `PUT /api/v1/partners/:id/contract` `{contract}` — 契约（版本化）；
  4. `PATCH /api/v1/partners/:id` — `diary`（日记官）/ `dispatchAuthority`（监工）。
- 三步失败中断即停、toast 报哪步没成（不留半人：SOUL 建成后 persona 失败会得到"有身份没里子"的执事，
  可接受——档案页补得回来，提示里说明）。
- **巡官/日记官不自动建例行任务**：例行触发器绑这台机器的会话与时钟，模板卡只写建议
  （"建好后到能力 → 例行任务加一条"），建档 toast 带引导。

## 四、招聘大厅与新建入口

1. **空花名册**（执事 0，只有总管）：列表空态从"一句提示 + 新建按钮"改成**模板卡墙**——
   六张卡（名字 + 一句管什么 + 类型点），点卡 → 建档流程（见 §三）；
   卡墙末尾保留"自己捏一个"走原新建弹窗。
2. **非空列表**：侧栏 ⋯ →「新建执事」弹窗**顶部加一条横向模板快捷条**
   （六个小卡，点选预填弹窗的名字/领域/一句话身份；"空白开始"默认选中）。
   弹窗本体字段（新建表单内部）**本轮不动**——需求方明确后期再说。
3. 档案页**不提供**"给现有执事套模板"：模板只管出生；已建的人换人格走人设库快照
   （快照应用=整份覆盖，2026-11-15 口径）。要给老人换模板，先存快照备份再手改。

## 五、改人设页交互重构（主要交付）

保持 C 版"一页从上往下"的定位，**不推翻页面骨架，重组信息**：

1. **Hero / ①人设 / ②岗位 / ③能力**：保持现有结构与保存逻辑，不动数据流。
2. **「人格模块」段重做**（`pfWirePersona` 一带，1828 行文件里改动最重的一块）：
   - 预设三选一保留在段顶（一键填开关的既有语义：切预设=重填开关表）。
   - 14 行平铺开关 → **9 张模块行卡 + 1 个高级折叠**：
     - 可编辑的做成行卡：口吻 / 里子 / 处境 / 印象 / 心情 / 内心生活 / 学习 / 主动性 / 人设库；
       每张卡 = 名字 + **状态摘要**（"已填：风格、忌语" / "没填" / "3 条印象"）+ 卡头快捷开关；
       点卡 = 打开现有编辑层（`pfOpenPersonaEditor` / living 三弹层全部复用，不重写编辑器）。
     - 岗位类注入开关（契约 / 纪律 / 目标 / 履历 / 在办）——对新手是噪声，收进「注入细节」折叠
       （默认收起，解释文字照旧 data-tip 悬停）；岗位卡上契约/目标本来就各自有实体编辑处。
   - 状态摘要数据全部来自现有 persona GET，不加端点。
3. **文案降维**：卡片标题保留现名（口吻/里子/处境…，与既有口径一致），解释进悬停。
4. 样式照档案页现有 pf-* 卡片语言，不引新组件库（三端同源手写 web 三件套路线不变）。

## 六、明确不做

- 新建弹窗内部字段重构（需求方明确"后期再说"）。
- 手机端：模板建档是电脑端功能，手机档案页保持只读现状。
- 给现有执事套模板（§四.3 的口径）。
- 自动建例行任务（触发器绑机器，模板只引导）。
- 模板进 shared / 进存储 / 做成可编辑的"用户模板"——先做内置六卡，用户自建模板等人设库快照
  跨执事能力立项（另行方案）。

## 七、回滚

- 新增 flags 一行 `PARTNER_TEMPLATES`（默认开）：false → 空态回旧"新建执事"按钮、
  新建弹窗无模板条（模板墙是行为增量，按硬约束挂回滚）。
- 人设页卡片化是交互重构、不挂运行时开关（同技能页卡片墙惯例），回滚 = 回退提交。

## 八、验证
