## 一、工具能力声明接管判定（#8 的后半，最有价值）

1.1 现状：`tool-capability.ts` 有 19 条声明，但 `needsApproval()` 仍读老的 `WRITE_TOOLS` 集合，
   声明只是"登记"，没接管。
1.2 改成**读声明**：
   - `needsApproval()` 里 `WRITE_TOOLS.has(tool)` → 用 `capabilityOf(tool)?.destructive === true`；
   - `critical.has(tool)` → 优先用 `capabilityOf(tool)?.needsApproval === "critical"`，
     **`AGENT_APPROVAL_CRITICAL_TOOLS` 覆盖仍然优先**（人显式配的要盖过声明）。
1.3 **未登记的工具**（声明表里没有）→ 保守处理：当作 `destructive: true` + `needsApproval: "critical"`，
   并 `console.warn` 一次（"未登记的工具按最严处理，请补声明"）。
1.4 一致性守卫单测保留，并**加强**：断言"声明里的 destructive 集合 === WRITE_TOOLS 集合"、
   "声明里 needsApproval==='critical' 的集合 === DEFAULT_CRITICAL_TOOLS 集合"。
1.5 **行为必须完全不变**：改完后跑一遍现有全部测试，一条都不能红。这是本项唯一的验收标准。

## 三、例行条件门控补 `if` 与 `ends`（#19 的后半）

3.1 `RoutineTrigger` 再加两个可选字段：
   - `if?: { note: string }` —— 触发前**先问模型"这个条件成立吗"**（一次轻量调用），不成立就跳过本轮；
   - `ends?: { at?: string; after?: number }` —— `at` = 到某个时间点后不再触发；`after` = 跑满 N 次后停
     （与 `maxRuns` 同义，`ends.after` 是它的别名，两者同时存在时取更小的）。
3.2 `if` 的判定**必须失败即跳过**（模型调用失败/解析失败 → 当作"不成立"，记一条 run 记录 `skipped`）。
3.3 开关 `ROUTINE_CONDITIONAL`（沿用批 13 的）。

## 五、记忆敏感闸补 Luhn / 身份证（#31 的后半）

5.1 批 11 的 `redactSecrets` 只按"形状"打码（sk-/Bearer/key= 等）。补两条**校验位**规则：
   - **Luhn**：16 位连续数字且通过 Luhn 校验 → 当作银行卡号打码；
   - **身份证**：18 位（17 位数字 + X/x）且校验位正确 → 打码。
5.2 **故意放行**：手机号（11 位，1 开头）、生日、邮编、普通长数字（不过校验位的不打）。
5.3 单测：≥8 个正例（含边界）、≥8 个反例（手机号/生日/普通数字不能误伤）。
