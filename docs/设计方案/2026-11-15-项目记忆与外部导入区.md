## 背景与两个任务

上一批把别家 AI 的记忆导了 194 条进 global（项目级条目带【项目名】前缀）。用户两个决定：

1. **项目记忆要做**：关于某个项目的记忆该有自己的地方存，不混在 global（存哪由我定）。
2. **外部导入要有自己的区域**：导入的记忆在界面上新开一片"外部导入"，不让人在海里捞
   （形态由我定）。适配器就是现在这六个，不加会话蒸馏（用户明确说会话整理不需要）。

## 任务一：项目记忆

### 存哪（用户交给我定）

`MemoryScope` 新增 `{ type: "project"; id: string }`，`scopeKey = "project:<uuid>"`——
**id 是设置→项目页登记的项目的 uuid**。不建平行体系：项目记忆跟着已登记的项目走，
每个项目一个独立键空间，与 global/partner 同一套存储、索引、召回，key 不同互不可见
（与 partner scope 的隔离口径一致）。

- 项目软删（archived）记忆保留；项目从项目页移除后 scope 成孤儿——**不可见即无害**，
  要清理走记忆页删除（登记边界，不做删除联动）。
- 选择 uuid 而不是项目名：对外 id 一律 uuid（仓库硬约束），项目改名不搬家。

### 写路径（本批两条；不做会话自动抽取）

1. **`remember` 工具加可选参数 `scope: "auto" | "project"`**（默认 `auto` = 现行为）。
   会话归属项目时（durable 的 ChatProjects 绑定），模型可以 `scope="project"` 把项目相关的
   口径（这个项目怎么跑、构建、部署、踩过的坑）写进项目；会话不归属任何项目时如实回话。
2. **导入适配器**（见任务二）：能匹配到登记项目的项目级条目直接落 `project:<uuid>`。

### 读路径

- **recall 工具**与**每轮注入 `recallContext`**：会话归属项目时召回 scopes 插
  `project:<id>`，即 `[global, partner?, project?, session]`。项目记忆只在
  聊这个项目的会话里浮出来，别的会话零打扰。
- 抽取管线不动：偏好/经验照旧落 global/partner（`preferenceScopeOf` 口径不变）。

### 会话→项目的解析（实现要点）

会话归属项目来自 durable 的 `ChatProjects` 文档（internalId → projectId）+
`Chats.byExternal`（externalId → internalId），都要 `harness.snapshot`（async）。
而注入管线 `collectInjections` / `InjectionProvider` 是**同步契约**（6 处调用点），
本批不为它做 async 化重构——`recallContext` 改用 **TTL 缓存（30s）+ 后台刷新**：
命中缓存就用，过期就异步拉新快照。代价是重启后第一轮可能缺项目 scope，随即自愈，无感知。
工具路径（remember/recall 的 execute 本来就是 async）直接 await 快照，不走缓存。

## 任务二：外部导入的适配

### 来源记名（谁带来的要能查）

记忆包 `ImportEntry` 加可选 `source?: string`，`importMemories` 落
`entry.source ?? "imported"`（老调用零变化）。server 侧：

- 来源导入（六适配器）：`source = "import:<sourceId>"`（如 `import:zcode-projects`）；
- 手工文件导入：保持 `"imported"`。

### 项目匹配（项目级条目进项目 scope）

适配器给项目级条目带**匹配线索**，匹配发生在导入时刻（对着 `projectsStore().listProjects()`）：

| 来源 | 线索 | 匹配 |
| --- | --- | --- |
| zcode-projects | 目录名剥尾巴哈希 = 项目文件夹名 | `basename(rootPath)` 或项目 name 相等（大小写不敏感） |
| qoder-cli-projects | slug 重建路径（`d-GitWarehouse-konwlegdecard` → `<本地盘>\konwlegdecard`，首段单字母=盘符）+ 尾段名 | `rootPath` 路径相等（大小写不敏感）优先，尾段名兜底 |

- **匹配上** → 落 `project:<uuid>`，**不带**【项目名】前缀（scope 本身就是归属）；
- **匹配不上** → 回落 global +【项目名】前缀（现行为），出现在外部导入区。
- 想让某个没登记的项目的记忆住进项目 scope：先去项目页登记，再点一次导入
  （导入只增不改，重导会补进项目 scope；global 里遗留的带前缀旧条目手动删）。

### 外部导入区（UI 形态）

- **范围选择里新开一个 tab**："外部导入"（伪 scope `__imported__`，`kind: "external"`）。
  点进去看到的**全部是 veracity=imported 的条目**（来源导入 + 手工文件导入都算），
  **按来源分组**（ZCode / Qoder CLI / Qoder Work / Qwen Work / CodeBuddy / 文件导入…），
  组内带条数。项目 tab 里能看匹配进项目的，这里能看全部来历——两处视角不同，不冲突。
- 项目 tab（`kind: "project"`）与执事 tab 并列；**有记忆的项目才列**（免得空 tab 一排）。
- global 主列表保持现状：导入条目带着「· 导入」标签混排在 kind 分组里（它们本来就该
  被想起）。

### 服务端契约增量

- `GET /agent/memory/scopes`：加 `kind:"project"` 条目（label=项目名）与
  `kind:"external"` 条目；响应的 kind 枚举扩为 `"mine" | "partner" | "project" | "external"`。
- `GET /agent/memory` 加 `veracity=imported` 过滤参数：命中时走特支路径
  （全量拉回 → 按 veracity 过滤 → JS 分页，量级千内够用；真到万级再下沉 store 层），
  响应加 `bySource` 计数（纯增量）。过滤口径 = `veracity==="imported"`（source 前缀
  `import:` 的细分留给 `bySource`）。
- `POST /agent/memory/import`（手工）：`scope` 放行 `project:<uuid>`（uuid 必须是登记
  项目，否则 400）；本批前端不出项目选择器，能力先给 API。
- `POST /agent/memory/import/sources/:id`：行为升级为「匹配项目 → 项目 scope；否则
  global+前缀」，响应形状不变。

### 迁移（当天已导的 176 条带前缀条目）

导入只增不改，搬家=删除重导：删掉 global 里 veracity=imported 且正文以【开头的条目
（即今天的两个项目级来源），重跑 `qoder-cli-projects` / `zcode-projects` 导入——
匹配上登记项目的进项目 scope（无前缀），没匹配的原样回到 global+前缀。

## 明确不做

1. **会话蒸馏导入**（用户明确说不需要；Claude Code/Codex 会话提炼另说）。
2. **会话自动抽取进项目 scope**：抽取管线照旧只落 global/partner/session；项目记忆的
   产生走显式 remember（模型拍板 scope=project）与导入。自动化必须可见。
3. **注入管线 async 化**：波及 6 处调用点，TTL 缓存够用。
4. **项目删除联动清理记忆**、**前端项目选择器（手工导入）**：登记边界，后做。

## 备选与取舍

- 项目 scope 用 topic 伪造（`topic:project:<id>`）→ 否：topic 是自由文本，没有 uuid
  约束与类型区分，范围清单/匹配/清理都要靠字符串约定，不如加一个真正的 scope 类型。
- 外部导入区做成独立 scope（`import:*` 键空间）→ 否：召回装配就得带上它，等于给每轮
  注入加一路；现在召回本来就是相关性打分，imported 留在 global/项目 scope 里自然参与，
  UI 分区即可。
- 项目匹配放适配器层 → 否：登记项目是 server 的知识（projects store），适配器只给线索，
  匹配决策收在 server 一处（换匹配策略不用改六个适配器）。
