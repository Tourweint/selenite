# 豆包 CLI 执行器适配（2026-11-23）

**状态**：已落地（2026-11-23）。
**冲突口径**：落地后以 `docs/基线文档/接口文档.md`、`docs/基线文档/系统架构.md` 为准；
本文保留"当时怎么想的"。

## 1. 背景与目标

本机已安装字节官方 `@bytedance/doubao-cli`（v2.37.2，`doubao` PATH 直达，已登录）。
用户要求把豆包 CLI 接进派活，作为与 CodeBuddy / Qoder / Claude Code / Codex / OpenCode
并列的一档执行器；模型用 DeepSeek 就行。

目标只有一个：**设置 → 派活 能选「豆包 CLI」，新单能真的派给它干、能续跑、能检测模型可用性。**

## 2. 调查结论（2026-11-23 本机实测）

### 2.1 非交互入口与输出

```bash
doubao -C <dir> --model <id> --permission-mode <mode> -p "<任务>" --output-format json
```

- 成功时 **stdout 只有一行** `{"type":"result","subtype":"success","is_error":false,
  "session_id":"...","result":{"type":"text","content":"..."},"tool_calls":[]}`；
  `[cli-chat]` 进度日志全在 stderr。正文取 `.result.content`，会话号取顶层 `.session_id`。
- 失败时 exit 1，stdout 常为空或 `internal_error:` 文本；不能只看 exit 0。
- `--output-format` 只接受 `text|json|stream-json`；Text 模式的会话行在 **stderr**，
  正文在 stdout，不适合结构化解析——统一用 `json`。

### 2.2 Windows 硬坑：stdout 不能接匿名管道

`doubao -p ... | cat` 稳定报 `internal_error: 无法启动主任务。请稍后重试。`（exit 1）；
同一命令 `> file` 就成功。原生日志给出的真因：

```
Cannot duplicate CLI output for Worker: overlapped output handles are not supported
```

Windows 匿名管道不支持重叠句柄，CLI 起内部 worker 时复制 stdout 句柄失败。
**`spawn(..., { stdio: ['ignore','pipe','pipe'] })` 捕获 stdout 会踩同一个坑**，
所以豆包适配器必须把 stdout 重定向到文件，跑完再读文件。

### 2.3 模型池（聚合多厂，默认就是 DeepSeek）

`doubao model list --output-format json` 实测 14 个模型，`is_default: true` 的是：

- `person-deepseek-v4-1-flash-261017` — DeepSeek V4.1 Flash（默认，efforts 到 max）
- `person-deepseek-v4-pro-ga-260813` — DeepSeek V4 Pro
- 另有 Kimi K3/K3.1、GLM 5.3、Qwen 4 Max/3.8、Doubao 2.1 Pro/Turbo/Lite、Auto

模型名必须用 `id`（`name` 与 `id` 不一致，例如 id 带 `person-` 前缀）。

### 2.4 权限档

只有 `ask_always` / `ask_risky`（默认）/ `always_allow` 三档，
`--dangerously-bypass-approvals-and-sandbox` 与 `--permission-mode` 互斥。

- `ask_risky` 下**普通写文件实测会直接执行**（不是拒绝，也不卡确认）。豆包没有"只读沙箱"。
- `always_allow` 下建文件正常。
- 所以三档只能这样映射：`read` → `ask_risky`，`edit` / `full` → `always_allow`。
  `read` 不是真正的只读，UI 的 note 要写清。

### 2.5 参数位置

- `-C` 必须是**第一个参数**：放在 `--permission-mode` 之后再传会报
  `invalid_arguments: 无法识别参数 -C`（实测）。
- `--model` / `--permission-mode` / `--effort` 须在 `-p` 之前，`--output-format` 可在 `-p` 之后。
- 长提示词走 `-p -` + stdin，stdout 仍落文件，可行。
- 续跑：`--resume <session_id> -p "..."`；裸 `--resume` 需要真终端，脚本禁用。

### 2.6 启动方式

`doubao` 是 npm 全局 shim：`%APPDATA%\npm\doubao.cmd` → `node .../@bytedance/doubao-cli/scripts/run.cjs`
→ 原生 `doubao.exe`（`stdio: inherit`）。复用 chancellor 已有的 `resolveCliLauncher` 解 shim，
用 node 起 `run.cjs` 即可；外层 stdout 文件句柄会被 `run.cjs` 原样继承（已用 Node spawn 链实测）。

## 3. 方案

### D1. 适配器沿用现有 Employee 契约，只加一种 kind

`EmployeeKind` / `EXECUTOR_KINDS` / `SELECTABLE_EXECUTOR_KINDS` 增加 `"doubao"`。
能力声明与 CodeBuddy 一致：`artifacts: "taskDir"`、`canWriteFiles: true`、`resumeWithSession: true`。
产物仍只认任务目录的 `REPORT.md`，不把 stdout 当交付物。

### D2. stdout 落文件，不接管道

`chancellor/src/employee/cli.ts` 的 `runCliProcess` 增加可选 `stdoutFile`：

- 传了：`fs.openSync(file,"w")` 作为 `stdio[1]`，spawn 后父进程立即关闭自己的 fd，
  子进程退出后读文件填充 `stdout`；
- 没传：保持原 `pipe` 行为，其它 CLI 零影响。

豆包适配器每次调用在系统临时目录建一个 `doubao-out-*.json`，`finally` 删除。
`stderr` 仍走 pipe（进度日志顺便续空闲超时）。

### D3. 参数与权限映射

```text
短提示：-C <cwd> [--model <id>] --permission-mode <mode> -p <prompt> --output-format json
长提示：-C <cwd> [--model <id>] --permission-mode <mode> -p - --output-format json  (stdin 写 prompt)
续跑：  -C <cwd> [--model <id>] --permission-mode <mode> --resume <id> -p <prompt> --output-format json
```

- 模型留空 = 不传 `--model`（跟随豆包账号默认）；填了就用 id。
- 权限：`read` → `ask_risky`，`edit` / `full` → `always_allow`，缺省 `full`。
- 提示词超过 8000 字符走 stdin，与 CodeBuddy/Qoder 同一条阈值。

### D4. 默认模型 = DeepSeek V4.1 Flash

`CHANCELLOR_DOUBAO_MODEL` 缺省值钉 `person-deepseek-v4-1-flash-261017`。
它本来就是豆包账号的默认模型，钉住是为了"同一份配置换机器也复现"。

### D5. 模型清单与检测

- 清单：`doubao model list --output-format json`，stdout 同样落临时文件再解析；
  只取 `models[].id`，排序去重。走服务端已有 24h 缓存与手动补刀文件。
- 检测：用 `runDoubao` 真跑一次 "只回复 OK"（`read` 档），失败分类沿用
  `classify()`（未安装 / 未登录 / 模型不可用 / 超时）。

### D6. 前端零改动

设置页的「默认派给谁」与各执行器卡片本来就是 `GET /agent/executor` 的 `kinds` 数据驱动；
后端 `EXECUTOR_KIND_INFO` 加豆包一项，卡片、下拉、权限三段、模型清单面板自动出现。

### D7. 配置与回滚

- `.data/executor.json` 增加 `profiles.doubao`（模型 / 权限），与其它档同一套读写。
- env 三个：`CHANCELLOR_DOUBAO_BIN` / `CHANCELLOR_DOUBAO_MODEL` / `CHANCELLOR_DOUBAO_PERMISSION`。
- 回滚：设置里换回原执行器；或 `EXECUTOR_CONFIG=false` 全部回 env；
  豆包档本身可只用 `CHANCELLOR_EMPLOYEE` 显式指定，不影响默认池。

## 4. 明确不做

- **不修改/汉化豆包 CLI 本身**，不绕它的更新检查（当前走 npm shim 即可）。
- **不做只读沙箱**：豆包没有只读档，`read` 只到 `ask_risky`，普通文件写入仍会执行。
- **不接 `--service-start` 远程任务服务**：本次只做"宿主派活给豆包"，不做豆包反向承接手机任务。
- **不做按单选择执行器**：沿用"全局默认 + 建单快照"的既有口径。
- **不解析 `stream-json`**：统一 `json` 单次结果，少一条要维护的流式解析。
- **不做交互式 TUI 桥**：与 Claude Code 同一结论，工程量不成比例。

## 5. 风险与已知边界

- 豆包 CLI 版本升级可能改动输出形状；解析器按"最后一条 `type=result`"宽松取，形状变了会判失败而不是误判成功。
- `ask_risky` 的"风险操作"边界由豆包服务端定义，本仓只能测到"普通写文件不拦"；
  真遇到确认类操作在 headless 下会空转到超时——这是没有只读档的代价。
- 临时输出文件在系统 tmp，进程被杀（SIGKILL）时可能残留；不影响任务判定。
- `run.cjs` 在发现新版本时会读 stdin 问是否更新；当前 2.37.2 为最新，暂不受影响。
  若未来升级窗口撞上，stdin 为 ignore 时 readline 会立即关闭并返回 130（表现为无输出失败），
  排障入口是 `doubao -v` 与 `doubao update`。
