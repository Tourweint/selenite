## 〇、一句话

三档按字面收口：**完全访问 = 文件工具不再过路径闸门**；**只读 / 在工作区内修改 = 读也限根**（用户给的附件除外）；**文件夹重叠按“根与根两两比”限定**，补上“恢复归档”这个唯一漏掉的入口。审批轴（`approvalLevel`）与工具黑名单（`blocked`）不动。

## 一、现状核对（2026-11-20）

- `path-guard.ts` 只守 `write` / `edit`，`GUARDED_TOOLS` 写死两项；`read` 完全不过闸门。
  `tool-capability.ts` 的注释也写着「读文件，纯读；工作区边界由 path-guard 之外的既有语义兜」——
  实际没有那道语义：内核 `read` 只做路径解析（`pi-durable/dist/tools/read.js`），不检查根集合。
- 完全访问档目前**仍然**过 `path-guard`：越界 write/edit 硬拒。这与用户要的“完全不受约束”相反。
- 两档受限档的 shell 查看命令（2026-11-14）已经限根；`read` 是唯一的缺口。
- 项目根的重叠校验（`assertRootPathAllowed`）已经是**跨项目、逐根**比对：`listProjects()` × `roots`，
  同项目内的两个根也按这条判。多文件夹项目不会削弱它，因为比较单位是“文件夹”，不是“项目”。
- 唯一漏掉的入口是**恢复归档**：`setArchived(id, false)` 只翻 `archived` 位，不复查；
  归档项目又不参与重叠校验，所以“归档父项目 → 登记子目录 → 恢复父项目”能造出嵌套的活跃项目。

## 二、决策

### D1：完全访问 = 文件工具不再过路径闸门

- `pathGuardBlockReason` 增加 `access` 入参；`access === "full"` 时 **write / edit / read 全部直接放行**。
- 边界**只**看文件工具；`bash` / `powershell` 本来就不扫命令文本，维持现状
  （cwd 在根内，命令里写绝对路径可逃逸——这条已知边界继续登记在 `系统架构.md`）。
- 不放宽的两样（刻意）：
  - `policy.blocked` 黑名单：那是“这个工具禁用”，不是“权限档”；
  - `approvalLevel` 审批轴：三档是能力边界，审批是确认策略，正交。
- 回滚：`AGENT_FULL_ACCESS_PATH_GUARD=1/true/on` → 完全访问也走原来的路径闸门
  （write/edit 限根、read 不限），一行回到 2026-11-20 前。

### D2：只读 / 在工作区内修改 = 读也限根

- `read` 进 `path-guard` 的受守工具集合，但**只在受限两档生效**：
  - `read-only`：`WRITE_TOOLS` 照旧全拦；`read` 的目标路径必须落在已登记根集合内。
  - `no-shell`：`write` / `edit` 照旧限根；`read` 同样限根；`bash` / `powershell` 仍只放行查看命令。
- 只读档的“写行为”一个字没改，只是把“看”收进同一套根集合；否则会出现
  “只读能看全盘、在工作区内修改反而只能看工作区”的非单调。
- **用户给的附件例外**：`read` 的目标等于本次会话里用户附上来的文件（`FilePart.path`）时放行。
  附件是“用户主动递给你看的”，不属于越界；否则受限档下附件直接读不了。
  - 允许清单 = 当前消息的 `assembled.value.files` + 客户端上行 `messages[].files`（最多 200 条）
    + 本进程内该会话此前记过的附件；服务重启后由下一次上行历史重新补齐。
  - 只对 `read` 生效，不给 `write` / `edit` 开口子；shell 查看命令仍只认根集合。
- 回滚：`AGENT_READ_PATH_GUARD=0/false/off` → `read` 恢复“不过闸门”（2026-11-20 前形态）。

### D3：文件夹重叠 = 根与根两两不重叠（多文件夹项目同样适用）

不变量（对所有**活跃**项目）：

1. 任取两个根，不能同路径、不能互相包含（祖先 / 后代都算）；
2. 根不能等于工作区根、不能包含工作区根；
3. 工作区根**可以**包含项目根（旧口径常态，不禁）。

比较单位是**根**，不是项目：项目 A 有 [X, Y]、项目 B 有 [Z]，只要 X/Y/Z 两两不重叠就合法；
A 的文件夹多并不产生“项目级重叠”这个额外概念，也不需要限制。反过来说，
一个文件夹不可能同时属于两个项目——同路径会命中 `duplicate_root`。

生效点：新建项目 / 追加根 / 改根路径 / 改主文件夹 / 合并项目（已有）；**恢复归档（本次补）**。

### D4：恢复归档前复核，冲突返回 409 `restore_conflict`

- `setArchived(id, false)` 在翻位之前，对项目的**每个根**跑一遍 `assertRootPathAllowed`
  （排除自己——此时它是归档态，本来就不在活跃名单里）。
- 命中重叠 / 工作区冲突 → `ProjectError("restore_conflict", "无法恢复项目「A」：文件夹「x」……", 409)`，
  文案直接说清跟哪个项目、哪个文件夹冲突；界面沿用 `doProjectAction` 的 toast 展示服务端 message。
- 目录不存在 / 不可达的根跳过校验（它本来就不进根集合，恢复后项目卡会显示“目录不在”），
  不因为盘符暂时离线就挡住恢复。
- 回滚：`PROJECT_RESTORE_OVERLAP_CHECK=0/false/off` → 恢复不复查（回到 2026-11-20 前）。

## 三、备选与为什么不选

- **只读档不改，只给 no-shell 加 read 限制**：会造成档位非单调（只读能看全盘、no-shell 不能），
  与“只读 ⊂ 在工作区内修改 ⊂ 完全访问”的既有口径冲突。
- **完全访问只放开 write/edit，不放开 read**：用户要的是“完全不受任何权限约束”，且 read 本来就不受限，
  只放开写会造成“能写不能读”的怪状态。
- **按项目整体判重叠**：多根项目没有单一“项目路径”，项目级包含关系无法定义；
  根级两两判是唯一可执行、可解释的口径。
- **恢复冲突时静默跳过冲突的根**：等于悄悄丢登记；宁可 409 让人先处理。
- **自动合并/自动删除重叠登记**：改用户数据，超出本需求，不做。

## 四、明确不做

- 不给 `bash` / `powershell` 在完全访问档加命令文本扫描（既有已知边界，见 `系统架构.md`）。
- 不改审批轴、不改工具黑名单、不改手机端。
- 不改文件浏览 / 会话目录选择的根限制（那是“入口”，不是工具权限）。
- 不自动清理历史脏数据（已经嵌套的活跃项目）；恢复入口之后不会再新增。
- 不做项目树 / 嵌套项目（2026-11-13 方案既定）。
