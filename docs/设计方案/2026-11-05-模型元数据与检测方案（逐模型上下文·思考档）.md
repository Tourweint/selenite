## 〇、一句话

把模型从「一个字符串」升级为「ID + 元数据（上下文 / 最大输出 / 思考档）」：
元数据落 `providers.json`，由服务端在构建内核模型时使用、在投影里下发；
新增**单模型检测端点**，用供应商自己的 `baseUrl + keyEnv` 真打一次上游，
把「能不能用 / 上下文多大 / 支持哪些思考档」一次说清，结果交给弹窗回填，用户确认后才保存。

## 一、现状与问题（2026-11-05 审计）

| 现状 | 位置 | 问题 |
|---|---|---|
| `models: string[]`，设置页用 textarea 一行一个 | `provider.ts` / `app.js` 供应商表单 | 没有逐模型配置；用户要手改一整段文本，增删一个模型像编辑配置文件 |
| 上下文窗口 / 最大输出硬编码 `131072 / 4096` | `provider.ts` `buildModel()` | 所有模型共用一个窗口；上下文环、裁剪都按错的值算 |
| 思考档已有 `modelThinkingLevels`，但设置页看不见、也不能改 | `provider.ts` | 只能靠后台自动探活或手改 JSON |
| 已有「保存并拉取清单」 | `app.js` | 拉全量清单噪音大，且没有逐模型的上下文/档位 |
| 已有切模型后的思考档后台探活 `scheduleThinkingProbe` | `provider.ts` | 只能在切换后异步发生，用户添加模型时看不到结果 |

## 二、数据形状

`providers.json` 的 provider 增加可选 `modelMeta`（与 `modelThinkingLevels` 并列，不改 `models[]` 形状）：

```json
{
  "id": "magpie",
  "models": ["glm-5.3-flash"],
  "modelMeta": {
    "glm-5.3-flash": { "contextWindow": 200000, "maxTokens": 8192 }
  },
  "modelThinkingLevels": { "glm-5.3-flash": ["off", "low", "high"] }
}
```

- `modelMeta`：键必须仍在 `models[]` 里；值只收正整数，非法值丢弃（与思考档同口径，
  一个脏字段不该让整份配置读不出来）。
- 缺省：`contextWindow = 131072`、`maxTokens = 4096`（沿用现硬编码，保持旧文件行为不变）。
- `modelThinkingLevels` 语义不变；缺省仍是 `["off","low","high"]`。
- **不持久化检测结果本身**：检测只返回建议值，用户确认后随保存写入。

## 三、接口增量

### 3.1 投影扩展（纯增量）

- `GET /agent/model` 的 `models[]` 每行增加 `contextWindow` / `maxTokens`（已解析的生效值）。
- `GET /agent/providers` 每项增加 `modelMeta`（稀疏）与 `modelThinkingLevels`（每模型生效档位）。
- `POST /agent/providers` 接受可选 `modelMeta` / `modelThinkingLevels`；不传 = 保留旧值。
- `POST /agent/providers` 允许 `models: []`（新 UI 先建供应商、再逐个加模型）。
  `models` 缺省且是编辑态时仍沿用旧清单，不清空。

### 3.2 `POST /api/v1/agent/providers/:id/models/detect`

body `{ "modelId": "..." }`。**只读**：不写 `providers.json`、不改密钥。

服务端并行做四件事：
1. **连通性 ping**：`POST {baseUrl}/chat/completions`，不带思考参数，`max_tokens=8`；
   拿到任何 HTTP 响应 = 端点可达，2xx = 请求可用。
2. **上下文/输出上限**：`GET {baseUrl}/models`（匹配该模型），兼容
   `context_length` / `context_window` / `max_model_len` / `max_input_tokens` / `inputTokenLimit`
   与 `max_output_tokens` / `max_completion_tokens` / `outputTokenLimit` 等常见字段；
   列表里没有该模型时再试 `GET {baseUrl}/models/{modelId}`。
3. **思考档探测**：沿用现有 `probeLevel` 对 `low / medium / high` 各打一枪；
   `off` 视为兼容基线始终可用。
4. 汇总：返回 `reachable / status / latencyMs / contextWindow / maxTokens /
   thinkingLevels / levels / message`。

- 允许检测**尚未加入 `models[]`** 的模型 ID（添加流程本来就是先检测再添加）。
- 供应商不存在 → `404 unknown_provider`；`modelId` 空 → `400 bad_request`。
- 上游拿不到上下文 → `contextWindow: null`，不猜、不写死；UI 提示手填。
- 密钥纪律不变：只用 `process.env[keyEnv]`，日志只记 provider/model/状态码。

## 四、前端形态

供应商表单：
- 删除「模型清单（一行一个）」textarea 与「自动拉取清单」勾选。
- 换成模型卡片列表：每行 `模型 ID` + `上下文 / 最大输出 / 思考档` 摘要 + 编辑 / 移除。
- 区块右上角「添加模型」按钮（ZCode 同款位置）。
- 供应商保存只保存当前列表与元数据；不再有「保存并拉取」的第二段请求。

添加 / 编辑模型弹窗（复用 `.modal`）：
- 模型 ID（等宽输入）；
- 「检测」按钮：调 3.2，回填上下文、最大输出、思考档；提示连通耗时或失败原因；
- 上下文窗口 / 最大输出（数字输入，空 = 用默认）；
- 思考强度复选（关闭 / 低 / 中 / 高）；
- 保存 = 写入前端草稿列表，供应商表单再点「保存」才落盘。

未保存的新供应商：检测按钮禁用并提示「先保存供应商，再回来检测」。
（新供应商允许空清单保存，所以流程走得通。）

## 五、明确不做

- 不做全量模型目录的自动导入（噪音大；要批量仍可用 `modelsUrl` 的老接口）。
- 不做基于已知模型名的内置上下文表（容易过期，宁可由上游给或用户填）。
- 不做主动二分探测真实上下文上限（发大量 token 既慢又费钱）。
- 不改手机端：本次只涉及服务端设置页投影，手机端不读这两个字段。

**实施与方案的差异**：

- 方案 §3.1 写"允许 `models: []`"，落地改成**显式 `allowEmptyModels: true`**：默认仍 `400 bad_models`，
  保住老客户端与 `http-probe` 的既有断言；新 UI 显式带上开关。
- 方案 §3.2 的字段名对齐代码：上下文键还包括 `max_context_length` / `contextwindow`，
  输出键还包括 `max_output_length` / `output_token_limit`；`/models/{id}` 兜底照方案。
- 前端顺带在模型菜单里显示上下文（`contextWindow` 来自 §2.8 投影），设置页模型卡片显示
  `上下文 / 输出 / 思考档` 摘要；这不是方案新增，属于投影字段的自然使用。
