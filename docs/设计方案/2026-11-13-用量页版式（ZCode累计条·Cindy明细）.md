# 设计方案：2026-11-13 用量页版式（ZCode 累计条 + Cindy 明细表）

> 状态：已落地（2026-11-13）。
> 下沉落点：`docs/基线文档/系统架构.md`「设置页分区」段（页面构成与数据边界）；
> 落地细节与验证：`docs/变更记录/2026-11-13-用量页独立与鉴权文案（服务页二次瘦身）.md`。
> 与基线文档冲突时，以基线文档为准。

## 结论

数据只有一份「按模型累计」的量，决定了能抄哪一半：

- **抄 ZCode 的"终身条"**（`packages/ui/src/settings/usage-stats/AppUsagePanel.tsx`）——
  一个大数字 + 一格一数、发丝竖分隔、数字 tabular 的统计条。它不需要时间序列，正好对上我们只有累计的口径，
  而且"累计"这件事本身就是一次性的、不需要切换区间。
- **抄 Cindy 的"明细"**（`apps/desktop/src/renderer/components/settings/usage/UsageHistorySection.tsx`
  与 `UsageBreakdownTables.tsx`）—— 色点对图例、占比格里那条按 share 长度的小横条、数值右对齐的表格。
  这是唯一能把 11 个模型档位摆明白的形态。
- **不抄两家的时间轴**：ZCode 的 7d/30d/all 切换 + 堆叠日柱 + 模型饼图，Cindy 的年度热力图 + 30 天柱——
  两者都以"逐日流水"为前提，`pi.usage` 没有。硬画只能造假数据。

一句话：**结构学 ZCode（因为数据是快照），列表学 Cindy（因为对象多且要横向比）。**

## 两家各有什么，哪些能用

| 元素 | ZCode | Cindy | 我们用不用 | 理由 |
|---|---|---|---|---|
| 终身总量条 | 一格一数、竖发丝分隔、5 格 | 5 张独立 chip 卡 | **用**（ZCode 形态） | 我们只有一份累计快照；chip 卡片各自有底，读起来像 5 个并列指标，不如一条 strip 的"同一个数的拆解" |
| 区间切换（今日/7d/30d/全部） | 有 | 有（含任意日期） | 不用 | 没有逐日数据，切了也是同一个数 |
| 日柱 / 堆叠柱 | 有（按模型堆叠 + 轴 + tooltip） | 有（30 天按模型堆叠） | 不用 | 同上；且 11 个档位堆在一根 10px 柱里本来就不可读 |
| 热力图 | 有（整年） | 有（整年） | 不用 | 年度格子要 365 个日桶，零数据 |
| 占比条 | 无（有饼图） | 无（只有表内小条） | **自造**：一条 10px 堆叠条 + 图例行 | 3～5 个模型时，一条条比饼图读得快；条目多时自动并"其他" |
| 明细表 | 无 | 有（模型 / 执行方 / 合计 / 占比） | **用**（扩到 8 列） | 我们要的是 token 的四项拆解 + 单档命中率，Cindy 的"执行方"我们对应 provider（已含在 key 里） |
| 刷新 | 有 | 无 | 用（节标题右侧 ghost） | 数据是读接口来的，页开着时可能变 |

## 版式（1280×960 实测）

| 层 | 内容 | 实测 |
|---|---|---|
| 累计用量 | 34px 大数字 + tokens 单位；右侧一枚 11.5px 的"4 个模型 · 11 个档位" | 卡片 962×179，内边距 18 |
| 五格 | 输入 / 输出 / 缓存读 / 缓存写 / 缓存命中，格间 1px 发丝线 | 每格 185px，数值 14.5px tabular，标签 11.5px |
| 注脚 | 来源 + 不折算金额 + faux 说明 | 11.5px，顶部 1px 分隔 |
| 按模型 | 10px 堆叠条（top4 + 其他），图例行 48px：色点 8px / 名称 13px / provider+档位数 11px / 数值 13px / 占比 54px 右对齐 | 卡片 962×294 |
| 明细 | 8 列（模型 / 输入 / 输出 / 缓存读 / 缓存写 / 合计 / 占比 / 缓存命中） | 行高 38px、表宽 924、11 行卡片 521 |
| 节距 | 标题 → 卡片 14px | 三节全为 14（`.set-sec-head` 的 ghost 也要 `margin-block: -6px`） |

## 几个具体取舍

- **颜色不用第二套调色板**：第一名 `--accent`，2～5 名是 `--text` 与 `--card` 的 58/34/18/6% 混合。
  理由：主题色是用户自己选的（米黄 / 暖白 / 靛蓝夜 / 炭黑 × 5 种主题色），写死的七彩在某个组合下必翻车；
  灰阶段在深浅两套主题里都成立，而且"第一名最重、往后越轻"本身就是排序信息。
- **同模型的 think 档位并成一行**：11 个 key 里 5 个是 `glm-5.3-flash#think-*`，并完只剩 4 行，
  占比条才有意义；想看分档去明细表（原样保留 `#think-off` / `#t0.4m4000r-th1`）。
- **模型 key 用等宽字体**：`magpie/auto/glm-5.3-flash` 这种路径里斜杠与版本号要能对齐着看；
  provider 不在明细里单列一行——key 本身已含路径，单列是复读（初版这么干，11 行撑到 741px）。
- **faux 标注「模拟」而不是扣除**：当前总量 2,275,237 里 78% 是 `faux/faux`（`LLM_PROVIDER=faux` 的假回答）。
  扣掉会让数字突然变小、也没法解释；标注 + 注脚是"照实说"的解法。
- **口径写在卡片里**：删会话 → 那部分用量一起消失（账记在会话上）。这不是"充值账单"，
  用户拿它算钱之前应该先看到这句话。

## 这条会怎么错

| 可能的错 | 触发条件 | 现在怎么兜 |
|---|---|---|
| 灰阶段在某个主题下糊成一片 | 深色主题 + 主题色接近灰 | 靛蓝夜已实拍；炭黑没拍（`--card` 更暗，混合后段间差会更小，需补拍） |
| 五格又被截 | 617 级窗口（设置导航折成图标栏） | ≤900 已收字号；617 没拍，只有算术 |
| 明细表被以为"只有 5 列" | 窄窗口下右侧 3 列滚出视口 | `overflow-x: auto`；没有加渐隐提示，靠系统横向滚动条 |
| 分组掩盖了 think 档位的差异 | 某档位用量与同族其它档差一个量级 | 明细表保留原始 key 与单档命中率 |
| 点开是空页 | 全新库、`models[]` 为空 | 已写空态（"还没有用量"），未实拍 |
| 总数与四格对不上 | 上游 `totalTokens` 口径变化（如把 reasoning 单列） | 页面不做加总校验；四格只是拆解，合计以 `totalTokens` 为准 |

## 明确不做

- 按天/按周账本（要先有存储机制：每日快照或事件流水，另立项）。
- 金额换算（`cost` 恒 0）。
- 按会话 / 按任务维度的用量榜（要逐会话开 session，成本高）。
- 导出 CSV / 分享图（没有需求，也不该在"把页面做好看"里塞功能）。
