> 状态：**已落地**（2026-11-17）。本文件留的是"当时怎么想的"；长期口径已下沉到
> `docs/基线文档/接口-存储工具与配对.md` §5（新端点）、`接口-端点1-对话与兼容层.md`（任务表）、
> 以及 App 仓库 `docs/基线文档/数据模型.md` / `需求与边界.md` / `接口契约.md`。**冲突以长期文档为准。**

## 缘起

用户在同一次对话里提了两件事：

1. **"最近的对话我都删了呀，同步的时候就把它去掉就行了，也不用在本机存了。"**
   电脑端 `/agent/chats` 已返回 `chats: []`，但手机本地 `chat_thread` 仍有 9 条绑定着旧会话的测试行——
   现在的同步只"拉电脑清单给手机看"，**从不回收本地行**，所以电脑上删掉的对话在手机上一直留着。
2. **"你把这个回忆模式直接删了得了，反正我也没做呢，就是刚做了一个入口，到时候我就跟给我记日记的这个执事聊。"**
   抽屉「回忆」按钮 + RECALL 会话（开场白生成、`X-Task: interview` 模板、日记来源「回忆整理」）整条线退役。

用户对两个口径当场拍板：

- 本地清单**保留**（离线看、首轮落库的会话 id 映射是既有不变量），**同步时按电脑清单回收**；
- 回忆模式**连 harness 一起删干净**（任务模板、提示词资产、接口文档任务表）。

## 一、会话同步回收

### 为什么不做"列表只认电脑"

备选：最近对话每次直接渲染电脑清单，手机只留会话 id 映射。否掉的原因：

- App `AGENTS.md` 的硬规则是"会话清单存手机本地，**首轮就必须落库**，丢了只能新建会话"；
- 断网时最近对话会整段空掉，而本地日记、总管/小记入口还在，体验断档。

保留本地清单 + 同步回收，既守住既有不变量，又让"电脑上删了 = 手机上没了"成立。

### 为什么新增 `POST /agent/chats/check` 而不是复用 `GET /agent/chats`

`GET /agent/chats` 为了拿首句与时间**逐会话读一遍 context**（接口文档 §5 已登记的已知代价），
且带 `limit` 截断——拿它做回收判定，会话一多就会把"被截断"误判成"已删除"。
新增的核对端点先走便宜的会话表 / 归档表判定，再对剩下的 id 逐个读一次内容（见下），
手机每次只发本地清单条数（≤50），代价与开一次抽屉相近。

### 口径

- 请求 `{ids:[conversationId…]}`；响应 `{missing:[…]}`。
- **两段判定（与 `GET /agent/chats` 的可见性同口径）**：
  ① 便宜段：不在 durable 会话表 / 已归档 / `task-` 前缀；
  ② 可见性段：会话在表里但 `readChatStats` 为 null（`turns == 0` 的空会话）也算不在。
- 读取异常**不判死**（留给下一次同步）；非法或空请求 → `{missing:[]}`；LLM 未配置 → 也回空。
- 手机端只在**拿到确定答复**时软删本地行（`deleted=1`）；端点不存在 / 网络失败 = 不回收。
- **软删不硬删**：`diary_entry.source_thread_id` 是 I3 追溯线索，日记 / 成稿一律不动。
- 归档会话按"不在"处理（手机没有归档页）；电脑上取消归档后，它会重新以"电脑端会话"出现在最近对话里。

### 实机联调发现（2026-11-17）

第一版只按"会话表里有没有"判定，模拟器上 9 条应回收的只删掉 5 条：剩下 4 条对应的 durable 会话
**还在表里、但一条消息都没有**（首轮中断 / 旧客户端残留），`GET /agent/chats` 从来不显示它们。
手机侧存的却是"用户发过话"的行，于是这些行永远留在手机上——正是用户要清掉的那批。
补上第②段（`turns > 0` 才可见）后，9 条全部回收。这也说明"存活"必须按**列表可见性**定义，
不能按表里有没有行来定义。

### 明确不做

- 不做硬删除、不做墓碑表（durable 删掉就是删掉，核对时"查不到"已经够用）。
- 不在回收时同步改名 / 置顶 / 标题（那是另一个方向的问题，手机列表的标题仍以本地首句为准）。
- 不做分页全量对账（一次最多 500 个 id，个人使用量级足够；超了分多次也没意义）。

## 二、回忆模式退役

### 删了什么

| 层 | 删除内容 |
|---|---|
| App UI | 抽屉「回忆」宽按钮（顶部只剩「新建」）；`onOpenRecallThread` 回调 |
| App 状态机 | `startRecallThread` / `generateRecallOpening` / `recallSessionDigest` / `recallOpeningJob`；发送与回复里的 `isRecall` 分支；`ChatUiState.isRecall`；`RECALL_*` 常量 |
| App 提示词 | `recall_interview_v1.md` / `recall_interview_v2.md` / `recall_chapter_v1.md` / `recall_chapter_v2.md` 与 `PromptAssets` 常量、黄金用例 |
| App 任务名 | `LlmTask.INTERVIEW` / `LlmTask.CHAPTER`（及 wire 名对照测试） |
| harness | `tasks.ts` 的 `interview` / `chapter` 两张任务表；`prompts/` 下四份同名资产；task 探针里的 interview/chapter 用例（改测 weekly/segment/question） |
| 文档 | 接口文档任务名表与"客户端接入状态"；App 基线文档的需求行、数据模型、模块边界、体验与启动性能 |

### 保留了什么（兼容）

- `ThreadKind.RECALL` / `EntrySource.RECALL` 枚举值**保留**：Room 按名字映射，删值会让历史行解析失败；
  老 RECALL 会话仍能打开、按普通对话继续；老成稿的「回忆整理」来源标签照常显示。
- `recall_chapter` 相关的 `memory_fact.era` 标签字段与展示不动（那是数据模型的历史字段，不是模式入口）。

### 备选与取舍

- **只删入口、保留开场白逻辑**：用户明确说"整模式删了"，且只删入口会留下不可达代码与提示词资产（死重量），否。
- **连枚举值一起删**：历史数据存在解析崩溃风险，且迁移要清库；个人数据不该为此冒风险，否。
- **保留 harness 任务模板**（任务名是弱契约，留着不碍事）：用户选"连 harness 一起删干净"，否。
  删除后老客户端若仍发 `X-Task: interview` 会得到 400 `unknown_task`——App 已同步删掉发送方，可接受。

### 明确不做

- 不清理历史 RECALL 会话与成稿（用户没要求，且属于个人数据）。
- 不把"跟小记聊"做成新的回忆入口——用户的原话是"到时候我就跟这个人聊"，即直接进执事会话，不另造模式。

## 验证

- harness：`pnpm --filter @lifediary/server typecheck`；`chats-check.test.ts` 5/5；
  `pnpm --filter @lifediary/server test`（全量）；`pnpm --filter @lifediary/server tasks`（探针已改测 weekly/segment/question）。
- App：`:core:ai` / `:core:data` / `:core:database` / `:feature:chat` 单测 306 个全绿
  （含新增的 3 个同步回收用例：回收、核对不可用不回收、清单失败不回收）。
- 模拟器：删掉 9 条本地测试会话后验证「最近对话」为空；抽屉不再有「回忆」按钮。

## 回滚

- 同步回收：老服务端没有 `/chats/check` 时手机自动跳过回收（幂等、无本地迁移），
  真要回滚只需删掉 `ChatViewModel.refreshRemoteChats` 里那一段核对调用。
- 回忆模式：`git revert` 本批提交即可；harness 任务表与 App 入口同日删除，没有中间态兼容负担。
