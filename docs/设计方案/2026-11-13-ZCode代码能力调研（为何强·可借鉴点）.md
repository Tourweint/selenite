## 〇、人话版结论（先看这里）

**一句话：ZCode 代码能力强不是某个单点魔法，是四件工程习惯叠出来的——① 把"模型看到什么"当核心契约死磕；② 失败不截断、让模型自己纠偏；③ 编辑类工具先验证后写入的原子性；④ 全仓库机器守卫 + 1000+ 测试文件。**

| # | 为什么强 | 证据 | 我们抄什么 |
|---|---|---|---|
| 1 | **模型可见结果（model-visible projection）被当成一等契约设计**，不是把原始输出一股脑塞回去 | `docs/design/v2/tool/04-bash.md`：stdout 只采前 30000 字节、失败结果头尾各 5000 字符截断、大输出落盘只给预览+路径、`grep` 无匹配/diff 有差异这类"语义型非零退出"不算错误、中断固定追加 `<error>Command was aborted…</error>`、图片输出识别失败降级规则逐条枚举 | **最值得抄**。我们 bash/edit 工具的模型可见输出目前是粗放的；照它制定"每工具一份结果映射规则"，尤其是语义退出码与截断预算 |
| 2 | **失败不截断后续动作，模型先自纠偏**——工具失败不跳过后续调度组、不设全局 tool call 上限、malformed 调用先 repair | `docs/agent-tool-relaxed-execution-policy.md`（2026-06-29 放宽 TodoWrite 硬拒绝与调度组跳过）；`docs/design/v2/loop/model-anomaly-fallbacks.md`："tool call 数量不设硬停止条件……模型先自纠偏；资源边界才硬保护" | **抄原则**。我们已有 AGENT_MAX_TURNS=100 兜底，保留；但工具失败后的处理应对齐"不 skip、错误原文回给模型" |
| 3 | **编辑原子性：先全部验证、再统一写入** | `docs/design/v2/tool/14-apply-patch.md`："对所有文件先做 verification，不得边验证边写；任一 hunk 失败整次 patch 不产生任何文件副作用"；匹配策略阶梯 exact→trimEnd→trim→Unicode 归一化；写回保留原编码（GB2312/GBK） | **抄语义**。我们 edit 工具的 matchers 可对齐这个阶梯；多文件 patch 场景照它的"验证-审批-写入"三段 |
| 4 | **机器守卫 + 测试密度**：架构依赖关系写进 `architecture-policy.yaml` 用 `pnpm architecture:check --changed` 强制；`apps/zcode-cli` 下 1006 个 `*.test.ts`；bash 命令注册表由脚本生成并 `--check` | 根 `AGENTS.md`、`architecture-policy.yaml`、`apps/zcode-cli/package.json`（registry:check）、实测 test 文件数 1006（2026-11-13 find 统计） | 抄一成：我们的 arch-guard 已有 7 条，可加"工具注册表反射遍历"那条的强化版；1000 文件测试密度不抄 |

## 一、逐项证据细节

### 1.1 模型可见结果契约（第 1 强点的核心）

`apps/zcode-cli/docs/design/v2/tool/04-bash.md`（执行合同 2026-09-07）：

- **大输出不进上下文**：stdout 采集前 30000 字节；总长超限的失败正文"保留前 5000 和后 5000 字符，中间换成 `... [K characters truncated] ...`"；成功大输出落盘 tool-results artifact，模型只拿到 `<persisted-output>` 预览（前 2000 字符）+ 完整路径 + 原始大小——模型要细节自己 Read。
- **语义退出码**：`grep` 无匹配、`diff` 有差异、`test` 为 false 这类非零退出**不是** provider error；普通失败才标 error 并输出 `Exit code N`。避免模型把正常信号当崩溃。
- **中断可识别**：timeout/取消统一追加 `<error>Command was aborted before completion</error>`，模型能稳定区分"没跑完"与"跑完但失败"。
- **后台任务通知极短**：`<task-notification>` 只含 task-id、状态、摘要、输出文件路径，"不包含完整 stdout/stderr；模型需要读取日志时继续调用 Read"——防止后台任务完成瞬间把上下文灌爆。
- **tools 段固定字节**（`00-tool-change-chain.md`）：工具 schema/顺序/描述是固定字节（排序规则与语言设置解耦），保 prompt cache 前缀命中。
- `agent-tool-call-renderer.md`、`edit-tool-model-visible-result.md` 对 Edit/TUI 工具卡同套纪律：模型可见文本与 UI 投影分离，"App 不解析模型 envelope"。

### 1.2 宽松执行与异常兜底（第 2 强点）

- `agent-tool-relaxed-execution-policy.md`：真实事故驱动——schema 硬拒绝多个 in_progress todo + 前序失败跳过后续调度组，把模型排好的活截断。放宽后："某一组出现普通失败后，不再自动跳过后续组；后续工具能否运行仍由各自权限、取消信号、handler 错误和调度分组决定。"旧校验保留为注释可回滚。
- `model-anomaly-fallbacks.md`：连续相同工具相同 input 是 doom loop **信号**，交给权限确认或模型可见提示，不直接杀 turn；provider 返回 stop 但带 tool calls 时继续处理；malformed call 先 repair 再报错；网络 retry adapter 自己做（默认 10 次，指数退避+jitter+retry-after）。
- 调度元数据：`packages/core/src/tool/types.ts:85` 每个工具声明 `concurrentSafe`，`registry.ts:118` 透传给 scheduler 并行分组——读类工具天然并行。

### 1.3 编辑与补丁（第 3 强点）

- `14-apply-patch.md`：结构化 patch（非自由文本）；**verify-all-then-write** 原子性；hunk 匹配阶梯 exact→trimEnd→trim→Unicode 标点归一化，"不得进行跨文件搜索或开放式语义猜测"；失败给稳定错误码；TUI diff 预览与 Edit 共用同一套结构化 hunk 投影。
- `17-read-file-state-resume.md` + `tool/read-file-state.ts`：记录文件读取状态，Edit 前检测 stale read（模型基于旧内容改文件时给 `staleReadFileStateHint`）——防止"按记忆改文件"。

### 1.4 子代理（subagent）

`07-subagent.md`：`Agent` 是"小型 agent runtime 入口"，六形态分清：fresh / fork（继承历史保 prompt cache）/ background（完成 `<task-notification>` 唤醒主会话）/ worktree（隔离 git worktree）/ remote / teammate（独立概念不混）。关键边界写死："普通 subagent 不是 OS 子进程"。`docs/agent-background-subagent-join.md` 记录了 join 方案废弃史——"background 完成后自动唤醒，不许 main 干等"，与 cindy auto-bridge 结论同向。
失败续接（`00-tool-change-chain.md` 2026-11-09 条目）：同步失败的 Agent 结果给模型追加 `agentId` 行+部分报告——原设计只透传 provider 错误（429），父模型拿不到 agentId，跑了几十步的子代理无法续接；修复方式是"不可枚举属性挂在原错误上，不复制不包 wrapper（保 stack）"，UI/事件完全不变。**这是"给模型的交接信息"和"给系统的错误对象"分离的好例子。**

### 1.5 可靠性工程（第 4/5 强点）

- `architecture-policy.yaml`：每模块登记 `roots / requires / publicEntrypoints / layers / owner`，`pnpm architecture:check --changed` 只查改动模块——依赖方向违规直接红。
- 测试：`apps/zcode-cli/packages/**` 下 `*.test.ts` 共 1006 个（2026-11-13 统计）；`registry:check` 由脚本生成 bash 命令注册表并核对漂移。
- `session-control`（`packages/session-control/src/CONTRACT.md`）：会话控制 20 个方法收敛为 contract/domain/app 三层独立包，**requestId 由工具层注入（`retryOf ?? toolCallId`）而不是模型提供**、回执必带 requestId 供对账、wait 带严格递增 revision 的 feed。幂等与授权边界写得极细。
- `formal-proof`：对话场景 compact/fork/goal/队列组合的状态空间枚举器（Web UI）——用穷举验证产品状态机组合，属于罕见投入。

## 二、对我们（lifediary-harness）的落点

**值得抄（按性价比）：**
1. **每工具一份"模型结果映射规则"**（bash 先行）：语义退出码白名单、失败头尾截断预算、大输出落盘给预览+路径、中断标记统一。改动面：`apps/server/src/agent.ts` 的工具闸门层 + 工具实现，无契约破坏。
2. **工具失败不 skip 后续调用**：核对我们 executor 是否存在"前序失败即跳过"逻辑，对齐"错误原文回模型、后续由各自权限决定"。
3. **Edit 匹配阶梯 + stale read 提示**：exact→trimEnd→trim→Unicode 归一化四档；read-file-state 记录最近读取视图，Edit 时检测旧内容。
4. **子代理失败带 agentId 续接**：我们 delegation-receipts 已有 requestId 体系；补"失败回执带可续接的子会话 id + 部分报告"。
5. **架构守卫升级方向**：学 architecture-policy.yaml 把"模块 requires + publicEntrypoints"登记成数据文件而不是散在测试里（保留我们现有 7 条测试，形状向数据化靠）。
6. **幂等技巧**：requestId 工具层注入（`retryOf ?? toolCallId`）、模型不可伪造——比"让模型自己传 request_id"可靠。

**不建议抄（体量不符）：**
- formal-proof 状态空间枚举、session-control 20 方法双 facade 合同包——我们单机个人、20 个方法级别，合同包纯增负。
- 1000+ 测试文件密度、SEA 打装、TUI 全套——工程形态差异。
- "不设全局 tool call 上限"整段照搬——他们的模型纪律强且有 doom loop 提示兜底；我们保留 AGENT_MAX_TURNS=100 作为个人无人值守的保险，只把"撞上限前先给模型可见提示"学过来。
