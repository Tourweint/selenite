## 问题

用户当天三条反馈，指向同一个缺口：**界面没有把「还在跑 / 跑完了 / 没派成」说清楚。**

1. 一轮在跑时刷新前端：历史只回读到已落盘的部分，流不会自动重接，屏幕看起来像卡住；
   用户不知道服务端其实还在跑。
2. 派活失败（最常见是 `needs_project`：没有可派项目）时，工具返回的 JSON 仍是
   `{ ok: true, data: { error: "needs_project", ... } }`，聊天灰块按 `isError` 判定，
   于是「没派出去」画成一个绿勾；任务中心也没有这张单（根本没建单）。
3. 一轮里出现多组工具时，每组各报各的「工作 N 步」（例如先「工作 1 步」再「工作 7 步」），
   同一轮的开合也要点好几处；跑动中收起后看不出还在跑。

## 取舍

### A. 刷新后续看：轮询，不新开实时订阅端点

- 采用：`/messages` 纯增量加 `running`（读 `LiveDoc.run`），前端在 `openChat` 时若
  `running=true` 挂一行说明，每 2 秒查一次 `limit=1`；跑完自动 `openChat` 重建。
- 不做：`GET .../live` 的 SSE 重接端点。它要新造一条广播 / 会话订阅契约、
  还要处理多客户端、断线、seq 归并；本轮要解决的是「不知道还在跑」，
  轮询已足够，且最坏代价是 2 秒一次单条查询。
- 客户端本地还有流在画（`state.sending`）时不轮询，避免和主流抢屏幕。

### B. 派活回执：业务数据不动，外层补 `isError`

- 采用：`delegate` 的所有「没受理」分支（`needs_project` / `invalid_*` /
  `delegate_rejected` / 设备矩阵不可用 / `bad_workdir` / `uncertain` / 派单异常）
  仍返回原来的 JSON（模型要拿 `projects` 等字段），但工具结果加 `isError: true`；
  聊天灰块与同类失败连击据此认失败。
- 消息文案统一加上「派活成功：」「派活失败：」「派活已提交：」开头，
  让模型和用户都能从工具返回第一句看出结果；工具 description 同步要求模型
  先看第一句再向用户汇报。
- 不把 `needs_project` 改成 `err`：`ToolError` 没有 `data`，项目候选清单会丢，
  模型就没法问用户选哪个项目。这是 2026-11-10 批23b 定下的口径，本轮不翻案。

### C. 任务中心：补「没有来源对话」的在跑 / 出错单

- 旧视图只渲染 `conversationId` 能解析出来的对话卡；`delegate` 的 SSE 临时单
  （还没有会话映射）在「在跑」区完全不可见。补一类小卡，点开走任务详情。
- 不做：新增「已完结」区。完成单的展示是另一件事，本轮只保证「刚派出去的单看得见」。

### D. 工作步骤：一轮一份状态

- 采用：`tool-chips.js` 加 `createTurnWork()`，同一轮的所有组共享
  `collapsed / expanded / finished` 与总步数；只有第一组画折叠条，文案报整轮总数。
- 收起时整轮所有组一起藏（跑动中也允许收起），折叠条自己在 `[data-running]`
  下带扫光；收起顺手关掉已展开的详情卡。
- 排布保证「最多一行」：运行中的块优先保留，但多个运行块放不下时只留最新的，
  不允许折成第二行。

## 明确没做

- 不做断流后自动重接 SSE；刷新期间的增量正文不实时补，跑完整体重读。
- 不做任务中心「已完结」区。
- 不改 `/messages` 的既有字段形状；`running` 只是纯增量。
- 不动手机端：它忽略未知字段即可。
