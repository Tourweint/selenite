# 人设停存版本快照（留上一份可回滚）

**状态**：设计定稿，当日落地。
**下沉落点**：机制 → `系统架构.md`；新端点 → `接口文档.md`；落地记 → `变更记录/2026-11-15-人设停存版本快照.md`。冲突以长期文档为准。

## 背景与核实结论

用户拍板（2026-11-15）：人设不要每次保存都存版本；保存的版本没人用。核实（2026-11-15 全量消费方核对）：

- 每次保存 SOUL / 契约 / 切模型候选链都往 `partner_versions` 插一整份快照（soul + contract + capabilities）。
- **快照历史零读取**：没有历史页、没有回滚端点、没有列表接口；`getVersion` 只被 `currentVersion` 调（且只取最新一行）。历史快照是只写不读的死重量。
- 版本号（`partners.current_version`）真正承担的活只有三件：
  1. 「下一轮生效」记账：会话侧比对 `applied_version ≠ current_version` 才重配 instructions（`partner-runtime-run-partner-turn.ts` / `group-runtime.ts`）；
  2. UI 展示（「人设 v14」徽章、「已保存为 v15」提示、「v14·N 字」）；
  3. 模型候选链寄存在版本行 `capabilities` 列（`getModelChain` 只读最新行）。

## 决定

1. **停存版本快照**：`bumpSoul` / `bumpContract` / `setModelChain` / 建档 / 总管播种不再 INSERT `partner_versions`，表整个退役（启动迁移 DROP）。
2. **计数器保留**：`partners.current_version` 照旧自增，继续当「下一轮生效」的记账位；契约字段 `soulVersion` / `contractVersion` 不动（值语义变为「保存计数」，前端不再展示）。
3. **磁盘成为当前值唯一事实源**：prompt 组装 / 身份对齐 / 导出 / 详情端点全部改「读盘」，删掉所有「版本行快照优先」的读法（其余路径本来就是盘优先，只是去掉死兜底）。
4. **留上一份可回滚**：`bumpSoul` 写盘前把当前 SOUL 存进家目录 `SOUL.prev.md`（单槽）；新端点
   `POST /api/v1/partners/:id/soul/rollback` 把 SOUL.md 与 SOUL.prev.md **交换**（交换语义天然支持「再按一次撤销回滚」），计数 +1 维持下一轮生效。前端保存成功提示「已保存，下一轮起用」并给「回到上一版」按钮。
5. **候选链搬家**：`modelChain` 从版本行 `capabilities` 迁到执事家目录 `model-chain.json`；启动迁移一次性搬运（幂等），随后 DROP 表。

**明确不做**：

- 不做版本历史列表、不做手动「存为新版本」、不做按版本号回滚（真有需求再立项）。
- 契约（CONTRACT）不做上一份/回滚：低频慎重操作、编辑有弹窗确认，SOUL 才是高频改错的地方。
- 不留 env 回滚开关：摘除的是只写不读的死数据，回滚开关等于把死重量接回来；当前值（SOUL/CONTRACT/候选链）全部还在盘上，没有数据丢失面。
- 手机端本轮只摘版本徽章展示，不做回滚按钮。
