## 零、人话版（先看这个）

**现在的派活，像一家没有前台的小饭馆。**
客人（总管/执事）直接冲进厨房点菜；厨房有几口锅，就同时开几口。
池已经把锅增加到了 4 口，但它不是前台——而且它只管 native 这口锅，
Claude / Codex / OpenCode 照样能直接冲进厨房。

所以调度优化不是把算法做复杂，而是**先补一个前台**：

1. **最要紧：限住同时开火的数量。**
   现在一次派 10 单，最坏是 30 个 CLI 同时跑。先做到“最多同时 3 单，其余排队”，
   再按 CLI 限并发（Claude 2、Codex 2、OpenCode 1、native 按池大小）。
   **光这一条就能挡住大部分机器卡死和额度打爆。**
2. **第二：取消要真的停。**
   现在取消只停 native；Claude/Codex/OpenCode 会继续跑，而且作废单的改动还会并进项目。
   改成“取消=杀进程+不合并+马上把位置让出来”。
3. **第三：同一个领域不要同时来两单。**
   原设计写过“同领域一次一单”，代码里没做；两个同领域单会共用一个 manager 数据库。
   补一把领域锁即可。

再往后才是“锦上添花”的三件：

4. 失败分类型：429/断网自动等一等再试，权限/冲突不瞎重试。
5. 外部 CLI 的 10 分钟一刀切，改成“10 分钟没动静才算卡死”。
6. 让任务中心能看见“在跑 3 / 排队 5”，不用猜。

**建议顺序**：先做 1+3（前台和领域锁），再做 2（真取消），最后做 4~6（重试和观测）。
**需要你拍的只有四个默认值**，都给了推荐：最多 3 单、取消不合并、额度恢复先不自动续、
同领域一次一单。你不需要逐项研究——说一句“按推荐做”就可以开工。

详细的代码依据、方案和验收在下面；看不懂可以只看这一节。

## 一、结论

1. **现在有“派活”，没有“调度”。** 每张 ticket 在自己的 `runScheduledTasks` 里跑，
   单票最多并行 3 个 task；跨 ticket 没有任何全局上限，也没有排队、优先级、重试与跨执行器的公平性。
   一次让总管连派 10 单，最坏是 10 张 ticket 各自起 3 个 worker。
2. **最该先补的不是“更复杂的算法”，是四道硬闸**：
   （a）ticket 准入上限；（b）按执行器分车道的并发上限（外部 CLI 也管）；
   （c）同领域串行（原方案承诺过、代码里没有）；（d）取消要真的停进程、释放槽位。
3. **重试只做“可分类的失败”**：额度/限流/传输类自动退避（能拿到 reset 就等 reset），
   权限拒绝、越权写入、合并冲突、报告格式错误一律不重试。不要把“失败”统一变成“再跑一遍”。
4. **排队可见性零契约成本**：任务中心已经把 `received` 显示成「排队中」
   （`web/tasks-model.js:29`）。排队原因先写进现有事件的 `message`（任务详情 `lastAction`
   直接可见），不新增状态、手机端零改动；要结构化队列位置时再给 `ticket` 事件加可选
   `waitingOn`（纯增量，老客户端忽略）。
5. **参考项目没有一个是“统一调度器”**：t3code 有 Run/Attempt 与 usage-limit 恢复，
   orca 有优先级信号量与 worktree 预热池，vibe-kanban 有“一 workspace 一执行进程”的闸，
   omnara 有机器池配额；但跨执行器、带优先级和重试的调度层，得我们自己补。

## 二、现状审计（2026-11-22，代码级）

### 2.1 一次派活实际怎么跑

```text
delegate 工具（tools.ts:1223）
  → startDelegation（delegation-start-delegation.ts:22）
  → runtime.run（tools.ts:1244）→ runChancellor（chancellor/src/index.ts:108）
  → intake 建 ticket（index.ts:165）
  → planTicket 拆 1–5 个 task（index.ts:232）
  → runScheduledTasks（index.ts:302）
      → 依赖就绪 + 本票槽位未满 + 写集租约拿到 → dispatchTask（scheduler.ts:124）
      → 执行器子进程（native / Claude / Codex / OpenCode / CodeBuddy / Qoder / phone / mcp）
      → 收集变更 → 按租约合并（scheduler.ts:367）
```

- **调度器在宿主进程内**，`startDelegation → runtime.run → runChancellor` 都是同进程调用；
  只有执行器是子进程。这一点池方案也已经确认（池方案 §2.2）。
- **单票并行上限 3**：`MAX_PARALLEL_TASKS`（`config.ts:266`）只在
  `TASK_ISOLATION=worktree` 且项目是 git 时生效；否则强制 1（`scheduler.ts:104-107`）。
- **租约是文件级**：`(project, 相对路径)` 独占，30s 心跳、5min 判死（`lease.ts`）；
  拿不到就进「等待文件」，1s 后再试（`scheduler.ts:184-202`）。
- **崩溃恢复**：`inflight.json` + 启动扫描（`index.ts:603`），未跨合并点最多自动续跑一次；
  已合并不自动续（`index.ts:683-706`）。
- **派单幂等**：回执库 requestId 去重（`delegation-receipts.ts`），先落回执再入队。

### 2.3 缺口（按影响排序）

| # | 缺口 | 事实 | 影响 |
|---|---|---|---|
| G1 | **跨 ticket 无全局并发上限** | `runScheduledTasks` 的 `maxParallel` 是每票的；宿主没有任何“在跑几单”的闸；`countActive()` 只给远程挑机用（`relay-matrix.ts:505`），本地从不查 | 一次连派 N 单 ≈ N×3 个 CLI 子进程；CPU、内存、供应商限流一起撞 |
| G2 | **外部 CLI 完全在池方案之外** | 池方案明确「外部 CLI 仍是子进程，不在本次范围」（池方案 §一.15） | 即使用 Claude Code/Codex，也没有任何并发上限或排队 |
| G3 | **同领域串行未实现** | 原方案 §5.3 写了 `MAX_ACTIVE_TICKETS_PER_DOMAIN=1`，代码里没有这个变量，也没有 domain 锁；两个同领域单会各起一个 manager 子进程，共用 `managers/<domain>/.agent.sqlite` | manager 会话/库并发写；原承诺落空 |
| G4 | **取消不杀外部 CLI** | `cancelTicketAction` 只对 native 发 stdin abort 帧（`delegation-actions.ts:123`、`employee/native.ts:90`） | 外部 CLI 取消后继续跑、继续占资源；作废单的产物仍会合并进项目（设计口径是“照常跑完、只是不搬结果”） |
| G5 | **外部 CLI 超时是墙钟 10 分钟** | `employee/cli.ts:174`；native 是“无活动 10 分钟”（`employee/native.ts:210-215`） | 正常长任务被误杀；挂死任务占满 10 分钟槽位 |
| G6 | **失败不分类、不重试** | `scheduler.ts:204-208` 任何 run 都算 completed；失败即终态，只能人工重派/续跑 | 429、5xx、CLI 瞬断都要人再点一次；没有退避，重派立刻又撞限流 |
| G7 | **没有额度/限流的车道级冷却** | provider 层没有 429 处理；worker 模型只有一份快照，没有候选链 | 一个执行器限流时，所有新单继续往同一车道塞 |
| G8 | **队列不可见** | ticket 没有排队位置/等待原因；`received` 只显示“排队中”，但实际立即开始拆单 | 用户不知道“在跑几单、前面还有几单、为什么不动” |
| G9 | **项目级 git 操作无互斥** | `prepareTaskWorktree` / `removeWorktree` / `git worktree prune` 可被不同票并发调用（`isolation.ts:62-65`、`isolation.ts:192-206`） | 并发 add/remove/prune 的 git 元数据竞争；**未复现**，属结构性风险，不是已观测 bug |
| G10 | **池方案只覆盖 native** | 池的队列/容量只服务 pool employee；manager 子进程里的 child ticket 也走自己的调度器 | 即使池落地，整体并发仍不是“一个数” |
| G11 | **启动判活只靠 PID** | `inflight.json` 存 `pid`，`recoverDelegations` 用 `isPidAlive` 判“还在跑”（`inflight.ts:21`、`index.ts:675`）；Windows 上 PID 会被复用 | 上一代孤儿可能被当成“还在跑”永远不结算；反过来也可能被误杀 |

## 三、参考项目结论（2026-11-22 拉取）

> 六个仓都在 `D:\Projects\reference\`，HEAD 以各仓 `git log -1` 为准；本节结论来自代码级阅读，
> 不是 README 宣传口径。**结论先行：没有一个仓同时做到“跨会话、跨执行器、有配额、有优先级、
> 有重试分类”的统一调度器。** 可抄的是原语，不是架构。

| 项目 | 与调度相关的真实做法 | 值得抄 | 不适合我们 |
|---|---|---|---|

| **orca**（stablyai/orca） | 没有进程内 fan-out 调度器；“fan-out”是手动建多个 worktree 粘贴同一提示，或 skill 建议一次约 4 个；代码层 **一个 Task 同时只允许一个 active Dispatch**（`task-start-claim.ts` 写事务抢占），重试必须 `--retry-of` 最新已结算的失败 Dispatch；Task / Dispatch / worker 三层状态机（`pending/ready/dispatched/...`、`start_unknown/stop_unknown`），SQLite WAL + savepoint + mutation receipt；**3 次失败熔断**（`dispatch-circuit-breaker.ts`），熔断后不自动绕过；有 `PrioritySemaphore`（函数优先级、abort、同优先级 FIFO）但主要用在探测/辅助任务，不是主 agent 并发；worktree 按需创建，另有一个 **worktree 创建预热池**（prepare/refresh，上限 3，`worktree-create-preparation-pool.ts`），不是任务 worktree 池 | Task/Dispatch/worker 三层 + 完成权威绑定（taskId+dispatchId+pane 身份）；显式 `--retry-of` + 失败计数沿重试链；熔断 3 次；`start_unknown/stop_unknown` 恢复语义；durable mailbox；worktree-per-dispatch；创建预热池 | 45 个 TUI 适配与粘贴时序启发式（我们非交互）；“用 agent 当调度器”的 skill 驱动；没有全局配额/排队；Electron+daemon+orcad 三态；人工选 merge winner 可保留，但别当自动仲裁 |

| **claude-squad**（smtg-ai/claude-squad） | tmux `new-session -d` + PTY attach，Title 即 tmux 名；输入直接写 PTY 字节 + Enter，输出 `capture-pane` 屏抓；审批靠内容哈希 + 子串命中后 `TapEnter`，无 Deny/reason/审计/超时，且只对 program 精确等于 `"claude"` 生效；硬上限 10 个实例，无队列/优先级；每实例一个 git worktree；state.json 恢复，tmux 死了标 Paused | 仅 worktree + Pause/Resume 的思路 | 交互式 PTY/tmux 与非交互路线冲突；屏抓+自动回车不可接受（不抄 AutoYes）；无远程/鉴权 |

**共同结论**：主流产品都在“单会话/单 workspace 内排队”，没有跨执行器的统一调度器。
t3code 的 per-thread 队列、orca 的 Task/Dispatch 熔断、vibe 的 process 级回滚、omnara 的租约式
wakeup 分别解决其中一段；我们要补的是把它们拼到一个**跨 ticket、跨执行器**的策略层：
**信号量（优先级/abort）、Run/Attempt、usage-limit 冷却、队列可见性、熔断**。

## 四、设计

### 4.1 原则

1. **一个调度层，所有执行器共用。** 车道（lane）= 执行器档（native / claude-code / codex /
   opencode / codebuddy / qoder-intl / qoder-cn / phone / mcp）。池只是 native 车道的执行容器。
2. **两级闸，不互相替代**：
   - **ticket 准入闸**：限制“同时在拆单/跑票的 ticket 数”，按领域/来源分配；
   - **task 车道闸**：限制“同时真正在跑的执行器子进程数”，按执行器分配。
3. **排队不是失败。** ticket 在队列里保持 `received`，任务在等槽位时保持 `pending`，
   都用 `waitingOn` 说明原因；不新增状态、不伪造进度。
4. **取消 = 停止 + 释放 + 不合并。** 作废/中止的单不再“照常跑完再合并”；
   半成品留在 worktree 里供人查看，但不进项目。
5. **失败分层**：可重试的（额度/限流/传输/超时）自动退避；不可重试的（权限、越权、冲突、报告格式）
   立即终态，交给人。
6. **所有新能力带一行回滚**：`CHANCELLOR_SCHEDULER=false` 回到今天的无闸行为。

### 4.2 ticket 准入闸

**落点**：`runChancellor` 的 intake 之后、`planTicket` 之前（`chancellor/src/index.ts:224` 附近）。
ticketId 已经产生、`ticket` 事件已经同步发出，所以 `delegate` 仍能立即返回单号。

```text
intake → emit ticket（单号已出）→ 申请 admission
  ├─ 拿到：正常 planning
  └─ 没拿到：ticket.status 保持 received
             emit message="排队：前面 N 单"（变化时才发；任务详情 lastAction 可见）
             被取消 → 立即出队，不占槽
```

- 默认上限 `CHANCELLOR_MAX_ACTIVE_TICKETS=3`（含 managed / direct；dry 不计）。
- 领域闸：`CHANCELLOR_MAX_ACTIVE_PER_DOMAIN=1`。同领域单在 host 侧排队；
  manager 子进程因此不会有两个同时写同一个 `.agent.sqlite`。
- 队列上限 `CHANCELLOR_QUEUE_MAX=64`；满了在 intake 后直接 `failed`，
  消息「排队已满，稍后再试」，不静默堆积。
- 恢复/重试也走同一入口：`resumeTicket` / `retryTicketAction` 必须先过 admission，
  否则重启恢复会绕过所有闸。
- **优先级**（先用已有的 `runSource`）：`human(0) > device(1) > routine(2) > test(9)`；
  同优先级 FIFO。`runSource` 目前只做簿记（`run-source.ts`），拿它做排序是语义变化，
  需要 host 把 `priority` 显式传给 chancellor（`ChancellorRequest.priority?`，可选，缺省 5；
  这是 chancellor 内部类型，不是 shared/手机契约）。
- **公平性**：ticket 准入先保证“每个 ticket 最多占 1 个准入位”；同一 ticket 的第 2、3 个 task
  走车道闸，不额外占 ticket 位。这样 10 单不会变成“第 1 单 3 个 worker 跑完才轮到第 2 单”。

### 4.3 task 车道闸

**落点**：`runScheduledTasks` 的 `executeTask` 开头（租约之前、spawn 之前）。
顺序必须是 **车道槽 → 租约 → spawn**：先拿租约再等槽会形成“持租约等槽、持槽等租约”的死锁。

- 默认车道帽（可用 `CHANCELLOR_LANE_CAPS` 覆盖，如 `native:4,claude-code:2,codex:2,opencode:1,phone:1,mcp:1`）：
  - native 4（= 已落地的 `SUPERVISOR_POOL_SIZE`，池进程数；回退 native 执行器时同容量）
  - claude-code 2、codex 2、opencode 1
  - phone 1、mcp 1
  - codebuddy / qoder 各 1（非交互全权，额度不可控）
- 等槽时 emit `task-waiting`，`waitingOn="执行器槽位（claude-code 2/2）"`；
  等超过 2s 才发，避免刷屏。
- 车道帽是**进程内**的；manager 子进程里有自己的一份。跨进程的精确总量由
  “同领域串行 + 每领域 child ticket 上限”兜住（见 4.4）。**这是有意的边界，不假装全局精确。**
- 池落地后：native 车道帽读池大小；池内队列只做“进程恰好被回收/重启”的兜底，
  不再承担业务排队（见 §5.7）。

### 4.4 manager 路径（不假装它不存在）

manager 是独立进程，里面的 child ticket 在 manager 进程内跑自己的 `runChancellor`，
宿主看不到、也管不到它的 task 槽。**不引入跨进程调度服务**，用两道结构闸：

1. 同领域串行（4.2）：一个领域同时只有一个 manager 进程；
2. manager 进程内 **`CHANCELLOR_MANAGER_MAX_ACTIVE_TICKETS=1`**（由 `runManager` 在 spawn 时
   显式写进子进程 env，不靠继承；否则会继承 host 的 3）：manager 的 child ticket
   一次只跑一单，单内仍可最多 3 个 task，但受 4.3 的车道帽约束。

代价：manager 路径的并发上限 = 领域数 × 1 票 × 3 task。对个人机器足够；
如果将来领域数也上去了，再考虑 manager 通过本地 HTTP 向宿主申请槽位（不在本次范围）。

### 4.5 取消、超时与合并

**取消**：
- host 在 `startDelegation` 时为每张 ticket 建一个 `AbortController`，把 signal 传进
  `runChancellor`（async 模式也传；这个 signal 只由 `cancelTicketAction` 触发，
  不受聊天轮次结束影响）。
- `cancelTicketAction` 依次：作废位落库 → `controller.abort()` → `abortEmployeeWorker(ticketId)`：
  - native：现有 stdin abort 帧；
  - pool：池的 `/run/:id/abort`；
  - **外部 CLI：新增进程注册表 + `killTree`**（`employee/cli.ts` 目前 spawn 后不留句柄）。
- 取消后：scheduler 停止启动新 task；正在跑的收到 abort → `run.aborted=true`；
  `executeTask` 在 `collectTaskChanges` 之前检查 `run.aborted || signal.aborted`，
  **跳过合并**，保留 worktree，记录 `changedPaths` 供人查看。
- 队列里的 ticket 取消：立即从 admission/车道队列移除，不占槽、不 spawn。

**超时**：
- 外部 CLI 从“墙钟 10 分钟”改为 **空闲超时**：stdout/stderr 有数据就重置计时；
  `CHANCELLOR_WORKER_IDLE_MS` 默认 10 分钟。
- 另加 `CHANCELLOR_WORKER_MAX_MS` 默认 60 分钟（0 = 不限）防无限输出。
- native 已经是活动超时，口径对齐即可。
- 超时按 G5 处理：kill tree，失败，不合并（保留副本）。

**合并互斥**：
- 在 `isolation.ts` 的 `prepareTaskWorktree` / `removeWorktree` / `mergeTaskChanges` 外加
  项目级进程内互斥（一个项目一把锁），避免并发 `git worktree add/remove/prune` 的元数据竞争。
- 这把锁不跨进程；跨进程的写冲突仍由路径租约负责。

### 4.6 重试与额度恢复

**Attempt 模型**（借 t3code 的 Run/RunAttempt 分层，最小化）：

```ts
TaskRun {
  ...现有字段,
  attempt: number;                 // 1 起
  failureClass?: FailureClass;     // 见下
  retryAfter?: string;             // ISO；额度类用 resetAt
}
```

- 每次重试在 task 目录留 `attempt-<n>.json`（只记枚举、退出码、时长、错误类，不记正文）。
- `REPORT.md` / `session.json` 按 attempt 分目录或加后缀，避免上一轮的旧报告被当成本轮结果。
- ticket 详情只多两个可选字段：`attempt`、`failureClass`；老客户端忽略。

**失败分类**（chancellor 内纯函数，不 import server；server 的 `model-chain.classifyUnanswered`
可以参考但不能反向依赖）：

| 类 | 例子 | 处置 |
|---|---|---|
| `usage_limit` | 429 / quota / "reset after 2h" | 车道冷却到 resetAt；到期自动续跑（可关）或转 needs_you |
| `rate_limit` | 429 无 reset、CLI 明确限流 | 指数退避 5s/30s/2min，最多 3 次 |
| `transient` | 5xx、ECONN、ETIMEDOUT、socket hang up | 退避重试，最多 2 次 |
| `timeout` | 空闲/墙钟超时 | 重试 1 次；仍超时 → failed |
| `permission` | permission_denials、401/403、登录过期 | 不重试；needs_you（要人重新登录/授权） |
| `unauthorized_write` | 越权写入 | 不重试 |
| `merge_conflict` | 合并冲突 | 不重试；保留副本 |
| `report_missing` | REPORT.md 缺失/JSON 不合法 | 不重试（重跑只会再缺）；needs_you |
| `unknown` | 认不出 | 不自动重试；如实标 unknown |

**车道熔断**（借 orca 的 `dispatch-circuit-breaker`，比 t3 的 usage-limit 更通用）：
- 同一车道连续 3 个**不同 task** 失败（权限/登录/CLI 损坏这类“重试也没用”的类），熔断 5 分钟；
- 熔断期间该车道的新 task 不 spawn、不逐个重试，排队并显示 `waitingOn="执行器不可用（冷却到 HH:mm）"`；
- 冷却结束进半开：只放 1 个探针 task；成功则闭合，失败再开 5 分钟；
- 熔断只由“不同 task 的失败”触发，同一 task 的重试不重复计数（orca 的失败计数只沿重试链）。

**额度冷却**（借 t3code `UsageLimitRecoveryWorker`）：
- 每条车道有 `cooldownUntil`；冷却期间该车道的新 task 直接排队，不 spawn。
- 从 Claude 的 result 文本解析 `API Error: 429 ... (reset after Xh Ym Zs)`；
  Codex/OpenCode 从各自的 JSONL error 事件取；拿不到 reset 就用退避上限。
- 到期后：`CHANCELLOR_USAGE_LIMIT_AUTO_RESUME`（默认建议 **false**，先观察）为 true 时
  自动重试一次；false 时把 ticket 转 `needs_you`，消息里写「额度预计 X 点恢复」。
- 自动续跑最多 3 次/票，防止“恢复→又 429→再恢复”的循环。

**重试的执行方式**：
- **显式重试链**：每次重试带 `retryOf=<上一次 run 的 id>`，失败计数只沿这条链继承；
  不允许“重新派一张新单”绕过熔断/次数（借 orca `--retry-of`）。
- 外部 CLI 有 sessionId → `--resume`，保留上下文；没有 → 重派新单，并在 TASK.md 里写明
  “上一轮因 X 失败，这是第 N 次尝试”，避免模型重复已经完成的步骤。
- native worker 自己已有续行/上报通道；重试仍走 `resumeEmployee`。
- 重试不重新拆单（plan 不变），只重跑失败的 task；已成功的 task 不重跑
  （scheduler 的 `completed` 集合按 seq 保留）。
- **写过的失败不要叠加**：每个 attempt 开工前记 worktree 的 `beforeRef`，结束时记 `afterRef`
  （借 vibe-kanban 的 `execution_process_repo_state`）。普通失败重试 = 清掉副本重新检出
  （与 `scheduler.ts` 现有“同 seq 下次开工先清”一致）；只有崩溃恢复的 `resumeWorktreePath`
  才复用半成品，两者不能混。

### 4.8 启动恢复与孤儿

- `inflight.json` 增 `bootId`（进程启动时生成，与回执库已有的 `boot_id` 同源/同口径）。
  启动扫描时 **bootId 不匹配 → 一律当上一代进程的孤儿**，不靠 `isPidAlive` 单独判活
  （PID 会被复用，Windows 上尤其不可靠）。
- 孤儿按现有 `DELEGATION_RESUME_POLICY` 处理：未跨合并点 auto-before-merge 续一次；
  已合并/续过 → `needs_you`；队列里未开跑的 → 重新入队（按原 `created_at` 排序）。
- 启动时把所有 `running` 的 task 行投影成 `waiting/blocked`，不允许界面出现“永远在跑”的僵尸行
  （借 vibe-kanban `cleanup_orphan_executions`）。
- 池进程的孤儿由 supervisor 的“票→进程绑定表 + 心跳”处理（池方案 §4.5），本文不重复。

### 4.7 观测

- `GET /api/v1/scheduler`（宿主，鉴权同其他 `/api/v1`）：
  ```json
  {
    "queuedTickets": 2, "runningTickets": 3,
    "lanes": [
      {"kind":"claude-code","cap":2,"running":2,"queued":4,"cooldownUntil":null},
      {"kind":"native","cap":2,"running":1,"queued":0,"cooldownUntil":null}
    ],
    "tickets": [{"ticketId":"...","priority":0,"queuedAt":"...","waitingOn":"执行器槽位（claude-code 2/2）"}],
    "recent": [{"ticketId":"...","event":"retry","failureClass":"rate_limit","attempt":2,"at":"..."}]
  }
  ```
  只给枚举、数字、相对时间；不含 prompt / 文件内容 / 密钥。
- 任务中心头部：`在跑 N / 排队 M`；单卡显示排队位置与等待原因（复用 `waitingOn`）。
- `.data/scheduler.jsonl`：每次 queued / started / finished / retry / cooldown 一行，
  只记 ticketId 前 12 位、executor、时长、结果类；滚动上限（如 5 万行）。
- 指标口径：queue wait（enqueuedAt→startedAt）、run duration、attempt 数、失败类分布、
  每车道利用率。**没有测量就不写“优化了”。**

## 五、与现有池方案的关系

### 5.1 池方案已经解决的问题（本文不重复）

| 问题 | 池方案的做法 |
|---|---|
| native 每票一进程的装配/开库成本 | 常驻池进程，串行复用 |
| native 并发上限 | `SUPERVISOR_POOL_SIZE=4`（池进程数）+ 内存/RSS 回收 |
| 等待上报/答复时占进程 | 让出进程，会话挂起 |
| 池进程崩溃 | supervisor 按票重派 |
| 池队列可见/可取消/背压 | `WORKER_POOL_QUEUE_MAX` + 任务中心 |

### 5.2 池方案没有解决、本文要补的

1. **外部 CLI 的车道**：Claude/Codex/OpenCode 不走池，池方案 §一.15 明确排除；
   它们仍会每票起子进程、3 路并行、无上限。车道闸必须覆盖它们。
2. **跨 ticket 的准入与公平**：池的队列是“池进程不够用”时的第二层；
   谁先进入池、10 单怎么排队，池方案没有定义。
3. **同领域串行**：池方案明确 manager 暂不动；两个同领域单仍会各起 manager。
4. **失败分类与额度冷却**：池方案只处理“进程崩溃重派”，不处理 429/5xx/权限拒绝。
5. **取消语义**：池方案有 abort 端点，但外部 CLI 没有；作废单仍会合并产物。
6. **观测口径**：池方案有 `worker-pool.jsonl`，但没有队列等待、车道利用率、重试分布。

### 5.3 两种落地顺序

```text
顺序 A（推荐）：先调度层，后池
  调度层先按进程内车道帽把 native / 外部 CLI 都管住
  → 池落地时只替换 native 执行容器，策略不变

顺序 B：先池，后调度层
  池先把 native 容量变成 N
  → 调度层再把外部 CLI 纳入同一套车道；native 车道帽 = WORKER_POOL_SIZE

两种顺序都不允许：池内一套队列 + 调度层一套队列同时做业务排队。
池内队列只允许做“进程被回收/重启”的短时兜底，且要有日志区分。
```

## 六、分期与回滚

| 阶段 | 内容 | 规模 | 回滚 |
|---|---|---|---|
| P0 | 拍板：默认并发数、取消语义、额度自动续跑默认值、是否先做池 | — | — |
| P1 | ticket 准入闸 + 同领域串行 + 队列可见（received/waitingOn，零契约） | M | `CHANCELLOR_SCHEDULER=false`；`CHANCELLOR_MAX_ACTIVE_TICKETS=999` 可退回无闸 |
| P2 | task 车道闸（覆盖外部 CLI） + 项目级 git 互斥 + 外部 CLI 取消/空闲超时 | M | `CHANCELLOR_LANE_CAPS=` 空 = 不限；`CHANCELLOR_WORKER_IDLE_MS=0` 回墙钟 |
| P3 | Attempt 模型 + 失败分类 + 退避重试 + 额度冷却/自动续跑 | L | `CHANCELLOR_RETRY_ENABLED=false`；`CHANCELLOR_USAGE_LIMIT_AUTO_RESUME=false` |
| P4 | 观测端点 + scheduler.jsonl + 任务中心「在跑/排队」 | S | 纯增量；端点不存在时前端不画 |
| P5（可选） | worktree 预热池、按成本/能力自动换执行器、设备矩阵用队列深度挑机 | M | 各自开关 |

**建议先做 P1+P2**：这两批不改共享契约、不碰池进程，直接把“一次派 10 单会打爆机器”
和“取消停不下来”两个真问题解决；P3 再处理失败恢复。

## 七、明确不做

- **不做多租户/账号配额/计费**：单人系统，车道帽是资源保护，不是商业配额。
- **不做分布式调度**（k8s / Temporal / Redis 队列）：单机、单宿主进程，文件/内存足够。
- **不做抢占式调度**：不为了跑新单去暂停/杀掉正在跑的 worker；CLI 会话不支持无损暂停。
- **不做 fan-out 同一提示到 N 个 agent 再挑赢家**（orca 的做法）：token 成本 ×N，个人场景不划算；
  要对比就人工重派。
- **不做交互式 PTY/tmux**（claude-squad 的路线）：非交互已经能跑；省额度的 TUI 桥是另一个量级的工程。
- **不新增 `queued` 对外状态**：`received` + `waitingOn` 已经够表达，手机端零改动。
- **不在本轮重写 manager**：manager 仍是独立进程；用“同领域串行 + 每领域 1 票”兜住。
- **不做按任务手动选执行器**（2026-11-16 已拍板不做）：自动回退可以有，手动选择不做。

## 八、验收（可独立复跑）

1. **准入**：一次连派 8 单，`GET /api/v1/scheduler` 显示 running=3、queued=5；
   任务中心头部「在跑 3 / 排队 5」；第 4 单开始前 `waitingOn` 有排队原因。
2. **领域串行**：同领域连派 2 单，任何时刻 `managers/<domain>` 只有一个 manager 进程；
   第二单在 host 队列里，不启动 manager。
3. **车道**：把 `CHANCELLOR_LANE_CAPS` 设成 `claude-code:1`，同票 3 个 task 同时就绪时，
   同一时刻只有一个 claude 子进程；另外两个显示“等执行器槽位”。
4. **取消**：起一个会跑 60s 的 Claude 任务，取消后 5s 内子进程树消失、ticket 为 canceled、
   worktree 保留、项目目录没有该任务的改动；队列里的单取消后不 spawn。
5. **超时**：外部 CLI 静默 10 分钟被杀；持续有输出的 15 分钟任务不被误杀；
   超时任务不合并、副本保留。
6. **重试**：mock 一个 429（带 reset 2s），任务自动退避并在 reset 后重跑一次；
   mock 一个 403，直接 failed/needs_you，不重试。
7. **恢复**：在排队/跑动中 kill 宿主，重启后队列按原顺序恢复；
   已合并的 ticket 不自动续跑。
8. **回滚**：`CHANCELLOR_SCHEDULER=false` 后行为与 2026-11-22 之前逐字节一致
   （无 admission、无车道帽、取消仍只停 native）。
9. **外部 CLI 不受池影响**：池开关切换前后，Claude/Codex/OpenCode 三条链路的输出与失败口径不变。
