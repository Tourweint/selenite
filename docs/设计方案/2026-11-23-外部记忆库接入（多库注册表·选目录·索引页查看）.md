## 零、人话版

现在这套东西**只认一个库，而且是写死在 `.env` 里的**：一个脚本路径、一个 Python、一套拼死的命令。
注入页底部那一行「一生记忆库」就是它的全部门面——看得到规模，看不到别的库，也加不了第二个。

要"查看我所有的外部记忆库"，缺的不是再写一个查询工具，是三件小事：

1. 把"库"从环境变量变成一个**可增删的清单**；
2. 选库的动作 = **选一个目录**，服务端认得出这是哪种库；
3. 索引页里**每个库一行**，点开能看边界、能搜。

工具层不用现在合并——今天外部库本来就只有 `persona_recall` 一个读工具；
等第二个库真接进来，把"一库一工具"改成"一个工具 + 选库参数"就够了。
本地小库（`remember` / `recall`）不并进去，理由在 §四。

## 二、结论（先看这六条）

1. **连接 = 注册表 + 适配器**。`memory-banks.json` 存库清单；每种库一个适配器（今天只有一个
   `persona-ask`）。不做"通用记忆平台"，只做"目录 → 认得 → 能问"。
2. **目录 = 库的根，不是入口文件**。用户选 `persona-metric/` 这样的项目根；服务端按固定形状
   推出入口（`analysis/ask.py`），入口路径不接受客户端上传。
3. **展示 = 索引页底部那一行升级成折叠区**，每库一行（名字 · 类型 · 规模 · 状态 · 主/按需）；
   「查看」弹层 = 库边界 + 一个搜索框 + 命中列表。不新开 tab、不做全量数据浏览。
4. **工具现在不动**。外部读工具保持 `persona_recall` 一个；P2 接第二个库时才合并成
   `memory_search {query, bank?}`。`remember` / `recall` 永久独立（写语义不同）。
5. **一个主源注入，其余按需查**。多条库同时每轮轻召回 = 0.8s × N 的延迟与预算膨胀，
   不值得；主源由清单标记，`inject` 唯一。
6. **`PERSONA_MEMORY_ASK` 降级为"首次播种"**。文件不存在时用它生成第一条库记录；
   文件一旦存在，它就是唯一事实源——用户删掉的库不会被 env 偷偷加回来。

## 三、三个问题

### 3.1 怎么连接

三条可选通道，P1 走第一条：

| 通道 | 长什么样 | 取舍 |
|---|---|---|
| **CLI 检索门**（选它） | 目录里有 `analysis/ask.py` 这类固定入口，argv 传 query，读 stdout JSON | 零耦合库内部结构；库自己保证只读；今天已经在跑 |
| MCP over stdio | 库里自带 MCP server（persona-metric 已有 `analysis/mcp_persona.py`） | 标准化、能发现能力；但多一套进程握手与工具语义，P1 不引 |
| 只读 SQLite | 服务端直接 `mode=ro` 开库跑 FTS | 最快；但把 harness 绑到别家的表结构上，违背"上游唯一真相源、下游只同步派生视图" |

适配器契约（形状，不是实现）：

```ts
type BankKind = "persona-ask" | "voicevault";   // P3 再加 "mcp" / "sqlite-fts"
interface BankTarget { root: string; entry: string; python?: string }
interface MemoryBank {
  id: string;            // 稳定短 id，入库即定
  name: string;          // 展示名，可改
  kind: BankKind;
  root: string;          // 库根（绝对路径）
  entry: string;         // 相对 root，由识别写入，用户不可改
  python?: string;       // 空 = 跟随 PERSONA_PYTHON / python
  enabled: boolean;      // 是否参与工具与注入
  primary: boolean;      // 唯一：每轮轻召回 + 目录常驻只认它
  origin: "env" | "manual";
  addedAt: string;
  lastProbe?: { at: string; ok: boolean; summary?: string; error?: string };
}
interface BankHit { date?: string; title?: string; text: string; group: string; ref?: string; why?: string }
```

每个适配器只做三件事：`probe(root)` 认库并给规模、`catalog(bank)` 给边界、`query(bank, text, opts)`
给统一命中形状（`BankHit[]` + 库自己那句"查不到≠没有"）。

### 3.2 怎么选目录

**识别顺序（只看用户选的这一层，不扫盘、不下钻）**：

| 目录里有什么 | 认成 | 状态 |
|---|---|---|
| `.lifediary-memory.json`（P3） | 按 manifest 的 `kind` / `entry` | 显式声明优先 |
| `analysis/ask.py` + `data/persona.db` | 一生记忆库（persona-ask） | P1 |
| `voicevault.py` + `data/voice.db` | 语音档案库（voicevault） | P2 |
| 其它 | **拒绝**：「这个目录里没找到可用的记忆库入口」 | 不猜 |

- 手势：壳里点「选择目录」走原生选择器；浏览器里手输绝对路径（与「项目」登记同一个退路）。
- 两步确认：选目录 → `POST /banks/probe` 只探测不落盘 → 页面显示"识别为：一生记忆库 ·
  60 表 / 1.6 万条 · 主注入" → 点「添加」才写清单。识别不了就不给添加按钮。
- 校验（服务端）：目录存在且是目录；`entry` 解析后必须仍在 `root` 内（realpath 比对，防 `..` 逃逸）；
  同一 canonical root 不能重复登记（409 + 指出现有那条）；路径长度上限 260；Windows 大小写不敏感比较。
- 安全边界：客户端只能传 `root`，**不能传 `entry` / `python` / 参数**；spawn 仍是 argv 数组、
  query 只占一个 argv 位、不经 shell；stderr 只截首行、不进日志。这条与"无密钥下发"同级，不放松。
- 删除：从清单移除即断开（不碰库本身、不删库里任何文件）。改名只改展示名。

### 3.3 怎么在前端展示

位置：**注入 → 索引**页底部，今天那一行原地升级为折叠区（默认展开，只有 1 个库时也是这个形态）。

```
外部记忆库                                    2 个已连接        [+ 添加]
● 一生记忆库   persona-metric · 60 表 / 1.6 万条   ● 主注入   [查看] [⋯]
○ 语音档案库   voicevault · 1.1 万轮 / 597 天     ○ 只按需   [查看] [⋯]
```

- 行首状态点：绿 = 可用；灰 = 未启用；黄 = 目录/入口/库文件缺失；红 = 探测失败（悬停给一句原因）。
- 「查看」弹层三段：**边界**（catalog 行，原样只读）→ **搜索**（输入框 + 结果，命中 ≤160 字，
  可展开）→ **连接信息**（root / entry / python / 上次探测；只读，改路径走「⋯ → 更换目录」）。
- 搜索是显式动作，不用每轮预取；单次 0.8s 量级，按钮给 loading。空结果说
  「这个库里没有查到相关记录」——沿用 `ask.py` 自己的 `unknown` 口径，不自己编。
- 命名要分开：persona-metric 叫 **一生记忆库（检索/证据）**，voicevault 叫 **语音档案库（原话归档）**。
  现在文档里两个库都出现过"一生记忆库"，再接第三个库就彻底说不清谁是谁。
- 为什么不做新 tab：注入分区已经是 6 个 tab 的三列两行卡片；第 7 个会破坏版式。
  而且"外部库"与"本地索引"回答的是同一个问题（哪些记忆在），同页不同区更顺。
- 为什么不做全量浏览（按天/按事件翻页）：库自己的浏览界面是它的职责
  （persona-metric 有月度报告，voicevault 有每日 Markdown）；harness 抄一份等于
  把别人的表结构变成自己的契约。这里只做**边界 + 搜索 + 证据**。

## 四、工具层评估：要不要"只留一个记忆库"

先按两种读法各答一遍。

**读法 A：工具只留一个（不要一库一工具）** —— 现在改是空转，第二个库出现再改：

| 工具 | 干什么 | 是否并入"一个记忆工具" |
|---|---|---|
| `remember` | 写本地库（kind / scope / 项目 / taught） | **不并**：写语义，且是"记一句"的即时动作 |
| `recall` | 读本地库（打分 + 最近窗口 + 预算） | **不并**：与外部库不同构，合并后描述讲不清打分口径 |
| `persona_recall` | 读外部库（证据包 + coverage） | **P2 扩成** `memory_search {query, bank?}` |
| `persona_write` | 写外部库（高危、审批、单表） | **不并**：写与读不同档，按库能力单独上架 |
| `recall_sessions` | 翻本机会话原文 | 不并：它不是"库"，是 transcript 检索 |

- 今天外部库只有 1 个，`persona_recall` 本来就已经是"一个记忆库一个工具"。现在合并 = 为一个
  不存在的第二个库付一次缓存前缀变更 + 一轮文档迁移，收益为零（与 2026-11-22 方案"不预先抽象"同一条纪律）。
- P2 合并的理由：N 个库各一工具会让工具面线性膨胀、描述互相重复、模型要学"哪类问题问哪个库"
  且容易漏查；一个工具 + `bank` 参数把"选库"降成参数。工具描述与注册顺序是缓存前缀资产，
  合并只允许发生一次，必须进 `变更记录`。

**读法 B：库只留一个（废掉本地小库）** —— 不建议：

- 本地库是**可写索引**（每轮抽取、偏好/打算、项目记忆、修剪、整理），外部库是**只读档案**。
- 废掉本地库 = 把"记住"变成跨库写：延迟（起 python）、失败面（脚本挂了就记不住）、
  隐私边界（每条都进大库）三样一起变差；而外部库的写面只有一个 `user_statement` 表，接不住这些。
- 正确形态是**对外一个入口，对内分层**：用户只看到一个"记忆"，工具面一个读工具，存储继续分两层。

## 五、存储与契约（P1 需要动的）

存储：`.data/memory-banks.json`（原子写；`MEMORY_BANKS_PATH` 可覆盖）。

```json
{ "v": 1, "banks": [ { "id": "bank_xxx", "name": "一生记忆库", "kind": "persona-ask",
  "root": "D:\\Projects\\projects\\persona-metric", "entry": "analysis/ask.py",
  "python": "", "enabled": true, "primary": true, "origin": "env",
  "addedAt": "2026-11-23T10:00:00+08:00",
  "lastProbe": { "at": "...", "ok": true, "summary": "60 表 / 1.6 万条" } } ] }
```

端点（新，挂在既有 memory 路由里；静态段要排在 `:id` 路由前）：

| 端点 | 行为 |
|---|---|
| `GET /api/v1/agent/memory/banks` | 清单 + 每库 `{status, summary}`（lastProbe 直读，后台刷新） |
| `POST /api/v1/agent/memory/banks/probe` | body `{root}` → 识别结果，**不落盘** |
| `POST /api/v1/agent/memory/banks` | body `{root, name?}` → 服务端再识别一次，写入清单 |
| `PATCH /api/v1/agent/memory/banks/:id` | `{name?, enabled?, primary?}`；`primary:true` 自动把别的置 false |
| `DELETE /api/v1/agent/memory/banks/:id` | 只删清单行，不碰库 |
| `GET /api/v1/agent/memory/banks/:id/catalog` | 边界（10 分钟缓存） |
| `POST /api/v1/agent/memory/banks/:id/query` | `{text, limit?}` → `BankHit[]` + notes |

兼容与开关：

- **旧 `GET /agent/memory/external` 保留**（返回主源，字段不变），旧页脚/老客户端不破。
- `MEMORY_EXTERNAL` 继续当整块的闸（false = 端点 404 + 页面不渲染）。
- `PERSONA_MEMORY_ASK` / `PERSONA_PYTHON` 保留为播种与回滚；`PERSONA_MEMORY_ENABLED` /
  `PERSONA_MEMORY_INJECT` 语义不变，但父闸从"env 配了"改成"主库存在且启用"。
- 注入只认 `primary`：轻召回与 `persona_catalog` 取主库的 target；其它库只出现在页面与
  （P2 的）工具参数里，不额外占每轮预算。
- 不新增插件开关：`plugins.json` 是静态登记表，`flagEnabled` 对未登记键恒 false——
  每库的开关必须放在清单里，放不进 flags（2026-11-22 落地坑，已踩过）。

## 七、明确不做

- **不做通用记忆平台 / 多 provider 注册表的"平台版"**：只登记"有检索门的库"，不做插件市场。
- **不做全盘自动发现**：不扫 `D:\Projects`，不猜用户想接哪个；只认用户点选的目录。
- **不做库内全量浏览**：见 §3.3。
- **不做多主源同时每轮注入**：延迟与预算不允许；多库只走按需。
- **不把外部库内容复制进本地小库**：那是"记忆导入"的职责（Qoder/CodeBuddy 那套），不是外部库。
- **不做云端 / HTTP 远程库**：P1/P2 只认本机目录；远程或 MCP 通道 P3 再议。
- **不改工具描述来"宣传"新库**：描述只改一次（P2 合并时），不随库数量抖动。

## 八、回滚

- 删 `.data/memory-banks.json` → 下次启动按 env 重新播种，逐字节回到"单库写死"形态。
- `MEMORY_EXTERNAL=false` → 页面整块不渲染、端点 404，注入按 `PERSONA_MEMORY_INJECT` 照旧。
- P2 工具合并留 `persona_recall` 别名一版，回滚 = 摘别名、回到旧工具名。

## 九、验收口径（P1）

1. `pnpm typecheck` 绿；`pnpm --filter @lifediary/server test` 全绿（新增注册表/适配器/端点单测）。
2. `pnpm --filter @lifediary/server http` 探针：`banks` 清单出现主源；未配 env 的隔离实例返回空清单、
   页面显示"未连接"；`external` 旧端点字段逐字不变。
3. 真库冒烟：索引页出现「一生记忆库」一行，点开能看到 catalog 原文；搜「毕设答辩」有命中，
   搜「今天天气不错」不命中；关 `MEMORY_EXTERNAL` 后整块消失。
4. 日志抽查：只有字数 / 组数 / 条数 / 耗时，无 query 原文、无条目正文、无完整路径。

## 十、待拍板（三条）

   但要多一套分段状态）。

   避免"加了新库就悄悄接管每轮注入"。

## 十一、这条会怎么错

- **把"目录"当成安全边界**：目录只是定位入口，不是"这个库可信"。用户选了一个带恶意脚本的目录，
  服务端就会起它——本机单用户 + 完全访问的量级下这是可接受的，但必须在文档里写明，
  不能当成"加了目录校验就安全了"。
- **多库后工具面重新膨胀**：P2 合并如果只换名字不换形状，`bank` 参数会让模型在"选哪个库"上犹豫；
  真正的判据是返回值统一形状 + 每库 notes，不是参数本身。
- **注入与页面看到的不一致**：页面显示三个库，注入只用主源——用户会以为"都注进去了"。
  所以行上必须直写「主注入 / 只按需」，不能只用一个绿点糊过去。
