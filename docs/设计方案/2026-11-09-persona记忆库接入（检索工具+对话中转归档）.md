# persona-metric 记忆库接入（检索工具 + 对话中转归档）

> 状态：**方案定稿（2026-11-09 用户四项拍板），批一实施中**。
> 下沉落点：契约（导出行格式）→ 批二落地后进 `接口文档.md`；模块与机制 → 批二落地后进 `系统架构.md`；
> 冲突以长期文档为准。

## 背景与目标

`<persona-metric>`（个人记忆库：六套表 + 检索门 `ask.py` + 生成层 `answer.py`，
纯本地 SQL，约 232 MB / raw_source 12 万条）要接进 lifediary：

- **读**：总管在"本地短记忆（`.data/memory.db`，1200 字符预算）没提到、或用户问很久以前的事、
  或要原文出处"时，按需查这个大库。
- **写**：lifediary 的主对话原文经 voicevault 中转归档进 persona，成为"一生记忆"的原料。

**用户拍板（2026-11-09）**：
1. 写入走 **voicevault 中转**（守 persona 侧 D-011 裁定"persona 不接新来源，一律进 voicevault"）；
2. 注入形态 = **按需查询工具**（不做每轮自动注入）；
3. 写入内容 = **只写对话原文**（lifediary 的提炼记忆条目不进 persona）；
4. 实施 = **全派 CodeBuddy 分批**，方案与验收归本会话。

## 调研结论（2026-11-09 三仓库核查）

### persona-metric（基本零改动）

- 读：`analysis/ask.py` 是"唯一检索门"——`mode=ro` 只读 URI 打开、纯本地 SQL ~0.7s、零模型零网络、
  `--json` 输出结构稳定（六组证据 + coverage + unknown）、支持 `--from/--to/--limit`、可子进程调用
  （`ask.py:719-744`）。AGENT.md 红线：ask.py 内不得出现模型/网络调用（已核实 grep 为 0）。
- 写：`analysis/gateway.py` 收 `data/inbox/<批次>/*.jsonl` 是唯一入库口，`module=ai_dialog`
  已注册（`gateway.py:66`）落 `raw_source` + `raw_ai_turn`，`source_id=ai_dialog-{external_id}`
  幂等（INSERT OR IGNORE），入库后文件移 `data/archive/`。库里已有 11,651 条 AI 对话来自
  voicevault 导出（`analysis/export_voicevault.py` 产出）。
- 铁律：raw 组 20 个 no-update/no-delete 触发器（INSERT 是唯一放行的写操作）；
  硬约束 5 要求 `memory.seg_ids_json` 非空 → **外部预生成摘要不能写 `memory` 表**
  （这也是"只写原文"拍板的另一个理由）；改完数据前后跑 `check_invariants.py` 须 5/5。
- 既有节奏：voicevault→persona 两跳（`export_voicevault.py` + `gateway.py`）都是**手动跑**，
  update-policy §7 裁定"只提醒不自动改库"。本方案**不改这个节奏**。

### voicevault（新增一个导入脚本，不改主体）

- `voicevault.py`（2844 行）主库 `data/voice.db`（295 MB），AI 对话在 `turn`/`session` 两表。
  一轮 = 一条用户消息 + 其后 assistant 全文；`uid=sha1(source|sid|ts|text)[:20]` 幂等；
  digest / reply_kind / seq / topic 全部由它自动生成，**来源方不用提供**。
- 现成先例：`experiments/import_qclaw_wechat.py`（83 行定制导入，构造 `vv.Turn` → `vv.ingest()`）。
- 既有入口不合适：`round2_ingest.py` 的 MAPPING 没有 ai_dialog（jsonl 路线对 AI 对话是死路）；
  `chat_import.py` 会强制 source=`lifediary-web` 且整文件级跳重。
- 既有缺口（接受，不改 voicevault 主体）：<2 字符用户消息被丢（"嗯""好"没有记忆价值，可接受）；
  命中 AUTO_MARKERS 的消息被丢；孤儿 assistant 回复被丢弃（导出器按 user-turn 锚定配对即可）。
- voice.db 无触发器——"只增不改"靠纪律（INSERT OR IGNORE + uid 主键），导入脚本自身只 insert。

### lifediary-harness（新代码全在这）

- 注入链：每轮 `beforeRequest`（`lifecycle.ts:621-634`）→ `recallContext`（`assist.ts:200-222`）
  → `buildContext`（1200 字符预算）→ system 消息插最前。这是本地短记忆，**不动它**。
- 按需工具先例：`recall`（`tools.ts:387-414`）、`skill`（`tools.ts:903-925`）。
- 外部写入记忆样板：`memory-ingest.ts`（稳定 id + upsert + 30s 节流 + 失败降级）——本方案
  **不写 lifediary 记忆库**（persona 是只读参照，见决策 D-丙），但失败降级、节流的姿势照这个抄。
- 闸门：`WRITE_TOOLS` / 高危清单在 `approval-policy.ts:26,56`。只读查询工具（recall）两个清单都不进。

## 关键决策

**D-甲：读取走子进程调 ask.py，不碰 persona 仓库代码。**
`spawn(python, [ask.py, query, "--json", ...])`，argv 数组传参不经 shell（无注入面，模型只能传
query 字符串）。备选：MCP（`analysis/mcp_persona.py` 现成）——但 lifediary 无 MCP 客户端设施，
为一条检索引一条协议栈不值；导入 `from ask import ask`——要常驻 Python 进程，运维面更大。
子进程每查一次 ~1s（含 Python 启动），按需调用频率下可接受。

**D-乙：persona_recall 进 WRITE_TOOLS（硬约束字面要求），不进高危清单。**
AGENTS.md 原文"会写文件 / **起进程** / 派活的工具必须加进 WRITE_TOOLS 并过 readOnlyBlockReason"——
persona_recall 起 python 子进程，属于"起进程"一类，按字面进闸门（read-only 档拦截），
不搞"它其实只读"的豁免。但**不进** `DEFAULT_CRITICAL_TOOLS`：命令是我们拼死的
（python + 固定脚本路径），模型唯一的自由度是 query 文本（作为 argv 元素传给 python，
不经 shell、不解释）——审批三档"只问重要的"不必为它打断用户。

**D-丙：persona 库对 lifediary 只读。** lifediary 侧一切新代码只 `mode=ro` 读 persona.db
（经 ask.py），不写 persona 的任何表；写入诉求全部经 voicevault 中转达成。这样"哪些表能改"
的复杂度完全不进 lifediary 代码库。

**D-丁：只导出主对话。** 范围 = 非 `task-` 前缀、非群会话、非执事会话的主对话（总管），
user + assistant 原文。理由：voicevault 的一轮模型是"一用户+多助手"，群聊多方发言会搅乱；
执事会话走执事记忆键空间（D15），混进主人语料会串人格。**刻意没有**：群会话/执事会话/
任务专线的对话不归档；lifediary 提炼的记忆条目不进 persona（persona 的记忆由它自己的
管线从原文长出来，摘要指不回 segment 会撞硬约束 5）。

**D-戊：导出器落盘 jsonl，voicevault 拉取。** lifediary 收尾钩子（`settled.ts` 现有的
turnSettledHandler 处）把本轮 user+assistant 追加写 `ts/apps/server/.data/persona-export/<yyyy-mm>.jsonl`
（按月轮转，一行一轮，见契约节）。voicevault 的 `import_lifediary.py` 读该目录增量导入。
边界：lifediary 只写自己 .data 下的文件；voicevault 只读那个目录；互不进对方进程。
备选：lifediary 直接 HTTP 推 voicevault——voicevault 无常驻服务（README 口径），为此起服务
破坏它"文件最不易丢"的设计，不取。

**D-己：回滚开关两条。** 读：`PERSONA_MEMORY_ASK` 未配置（或 `PERSONA_MEMORY_ENABLED=false`）
→ 工具不上架，零行为差异。写：`PERSONA_EXPORT_ENABLED=false` → 收尾钩子不写导出文件
（默认关——启用需要 .env 显式配，和技能默认全关同一拍板口径）。

## 契约：导出文件行格式（lifediary → voicevault，跨仓库）

文件：`ts/apps/server/.data/persona-export/<yyyy-mm>.jsonl`，UTF-8，一行一轮，按 settle 顺序追加。
**契约只有一份**：以本节为准，voicevault 侧 `import_lifediary.py` 与 lifediary 侧导出器都照此实现；
批二落地后本节下沉 `接口文档.md`。

```json
{
  "v": 1,
  "conversationId": "<对外 uuid，voicevault 用作 sid，前缀 ld- 由导入方拼>",
  "turnId": "<durable 轮 id，同一轮重导幂等>",
  "ts": "2026-11-09T20:15:03+08:00",
  "userText": "<用户原话，原文不截断>",
  "assistantText": "<本轮最终 assistant 文本，纯文本化（同 settled.ts 的 plain 转换）>",
  "model": "<模型名，可选>"
}
```

- 空串字段照写；`userText` 与 `assistantText` 至少一个非空，全空的轮不写。
- 幂等链：voicevault `uid=sha1("lifediary"|sid|ts|user_text)[:20]`，同一轮重导 INSERT OR IGNORE。
- **assistant 文本不含工具中间过程**（与 settled.ts 转纯文本同口径：只取最终回复）；
  图片丢弃。
- 导出器日志只记条数/字数，**不记对话内容**（硬约束：日志不含对话内容）。

## 明确不做

- 每轮自动注入 persona 检索（0.7s×每轮 + 挤预算，工具按需已覆盖）。
- persona 侧任何代码/schema 改动（含新表、新触发器）。
- lifediary 记忆条目、执事会话、群会话、任务专线对话进 voicevault/persona。
- 短消息（<2 字符）与 AUTO_MARKERS 命中消息的保留（voicevault 既有规则，"嗯"无记忆价值）。
- 自动定时触发 voicevault→persona 两跳（守 update-policy §7"只提醒不自动改库"，手动跑）。
- 向量检索路（ask.py 纯 BM25/FTS 是它自己的红线；要向量是 persona 仓库自己的课题）。

## 风险与既有坑登记

- **ask.py 的 `--db` 与 WAL**：只读打开 WAL 库会触 `-shm`，与 gateway 写入并发安全（WAL 多读单写），
  但 lifediary 侧必须用 `mode=ro`（ask.py 已内置）且不拷库。
- **persona 检索质量已知短板**：人眼 20 题约 6-7 题可答、经验迁移类 0 分（当前事实.md §5）——
  工具返回要带 coverage/unknown 原文透传，让总管知道"没查到"≠"没有这事"。
- **跨仓库坑**：voicevault session join 必须 `s.sid = t.source || ':' || t.sid`（裸 sid 陷阱，
  export_voicevault.py:30 注释原话）；无时间戳的轮会 day=NULL → 导出器必须保证 ts 非空。
- **agent.sqlite 是 pi-durable 领地**：导出器只读打开（`mode=ro`），不写它的任何表。
- **Windows Python**：`PERSONA_PYTHON` env 给命令名（默认 `python`）；ask.py 自行 reconfigure
  utf-8（ask.py:715-718），子进程 stdout 按 utf-8 解。
