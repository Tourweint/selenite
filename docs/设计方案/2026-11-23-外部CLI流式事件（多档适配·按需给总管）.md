## 1. 背景与用户口径

1. 用户要试**多档 CLI 的流式效果**：不只豆包，OpenCode / Claude Code / Codex 也一起；
   模型都已挂上，可以真跑。
2. **过程不进总管上下文**：用户原话「把过程交给总管，上下文一定会爆炸，相当于复制了两份上下文」。
   总管只需要知道「大概干了啥」，不需要工具结果全文和全部思考流程。
3. **按需读**：大部分单不需要把过程告诉总管；要查时能查到即可。
4. 「不用关注事件细节」：事件字段由实现按各 CLI 实际输出定，方案只定边界与落点。

## 2. 现状（2026-11-23 核对）

- Claude / Qoder / CodeBuddy：非交互单结果（`type=result`），没有过程。
- Codex / OpenCode：JSONL，已有各自解析器判完成 / 失败 / 会话号，但事件只用于判定，不喂 UI。
- 豆包：单结果 JSON 自带 `tool_calls`（工具名、input、result、is_error、`tool_calls_truncated`），
  已实测（Glob / Read 两件都能拿到）。但豆包 stdout 不能接匿名管道（Windows 重叠句柄），
  实时流式只能落文件再增量读。
- 总管拿到的结果 = `REPORT.md` + 产物摘要（2KB 截断）+ 派活人自己写的 `steps`。

## 3. 方案

### D1. 事件只走「任务事件 / 界面」，不注入模型上下文

统一事件（形状由实现定，建议至少 `tool` / `status` / `text` 三类）：

- 落点：任务事件流（任务中心步骤条 / 详情）与任务目录的 `steps.jsonl`（按需查）。
- **禁止**把工具结果全文、思考过程拼进总管 / 执事 / 用户的模型上下文。
- 回写结果时最多加**一行统计**，例如「读了 3 个文件、跑了 1 条命令、改了 2 个文件（1 次失败）」。

### D2. 各档实测先行，按真实形状适配

实现前先真机跑一遍，记录 stdout / stderr 的真实事件形状（命令模板）：

- Claude Code：`--output-format stream-json`（如需 `--verbose` 一并记录）
- Codex：`exec --json`
- OpenCode：`run --format json`
- 豆包：`-p ... --output-format stream-json`（stdout 落文件）

每档都记录：事件类型、工具名 / 参数 / 成败、会话号、结束标志、是否需要 `--verbose`。
**形状没验过的档不许凭文档写解析器**；验不通就退回「最终结果摘要」，不硬做。

### D3. 豆包的实时性按实测决定，优先用最终 `tool_calls`

- stdout 只能落文件（管道会 `internal_error`）。若 `stream-json` 能边写边读（tail 增量），
  就做增量事件；做不到就**只做结束后摘要**——`tool_calls` 已经够回答「大概干了啥」。
- 不为了实时性把豆包改回管道，也不引入 PTY。

### D4. 给总管「按需读」

- 默认：结果回写只带一行统计；完整事件落 `steps.jsonl` / 任务事件。
- 需要细节时：任务详情 / 端点按任务号读取，不主动进提示词。
- 不新增「过程自动摘要进上下文」的通道；要总结由派活人自己读文件后决定。

### D5. 回滚开关

`CHANCELLOR_CLI_STREAM_EVENTS=false/0/off` = 关闭所有 CLI 的流式事件采集与 UI 步骤，
回到「只有最终结果」的形态（一行 env 回滚）。

## 4. 明确不做

- 不做交互式 TUI 桥（用户确认不交互）。
- 不把过程事件当验收依据（验收层已删，终态只认退出码 + `REPORT.status`；语义验收由 Agent 另派 worker）。
- 不做「事件全量进总管上下文」，也不做自动过程总结。
- 不改各 CLI 的计费路径；不为了流式降级既有单结果解析。

## 5. 验证

- 四档各跑一次真机流式，记录形状与耗时（Claude / Codex / OpenCode / 豆包）。
- 单测：事件解析（成功 / 工具失败 / 截断 / 无事件）、回滚开关、结果统计一行。
- `pnpm typecheck`、全套 `pnpm --filter @lifediary/server test`。
- 前端：任务中心跑动中能看到步骤；结束后详情可查 `steps.jsonl`；总管上下文里没有事件全文。
