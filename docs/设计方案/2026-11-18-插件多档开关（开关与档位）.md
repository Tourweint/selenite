## 问题

2026-11-18 用户口径（第二批）：

1. 有些多档插件没有开关：`MEMORY_EXTRACT`（自动 / 模型 / 规则）、`PARTNER_LEARNING_FREQUENCY`（每周 / 结算）、
   `AGENT_TOOL_POLICY`（全部 / 禁命令行 / 只读）、`CHANCELLOR_INTERNAL`（核心 / 外部 CLI）。
2. 开关位置不对：`AUTONOMY_ENABLED` 的拨杆在左、档位在右；用户要求**开关固定在右下角，档位往左放**。

上一版把这 4 个当「纯档位」处理，理由是它们没有协议里的「关」档，硬映射到某一档等于骗人。
这次用户明确要求每个多档插件都有开关，处理方式不是造假开关，而是**把「关」定义清楚并落到协议**。

## 决策：`offValue` + 每个多档插件各自的关语义

清单字段新增可选 `offValue: string`（必须在 `values` 里）。前端读它决定：
- 该插件有没有开关（有 `offValue` 才有）；
- 开关关掉时写哪个值；
- 哪些档位属于「开」态，放在开关左边。

五个多档插件：

| key | 开档（放左边） | 关 = | 关的语义 | 后端行为 |
|---|---|---|---|---|
| `AUTONOMY_ENABLED` | 只观察 / 开 | `false` | 完全不跑 | 已有 |
| `MEMORY_EXTRACT` | 自动 / 模型 / 规则 | `off` | 不自动抽取新记忆 | **新增**：装配 no-op 抽取器；召回 / 手动 remember / 导入 / 记忆页仍可用 |
| `PARTNER_LEARNING_FREQUENCY` | 每周盘点时 / 结算时抽查 | `off` | 不做模型反思提炼 | **新增**：`learningFrequency()` 返回 `off`；句长 / 称呼等确定性统计照常记录，已有规则照常注入 |
| `CHANCELLOR_INTERNAL` | 核心模型 | `qoder` | 不用宿主核心模型，回到外部 CLI | 已有（`qoder` 本来就是回滚形态） |
| `AGENT_TOOL_POLICY` | 禁命令行 / 只读 | `full` | 完全访问（不限） | 已有（`full` 本来就是默认档）；卡片名称改「工具权限限制」，避免「关 = 不限」被读成「只读」 |

`MEMORY_EXTRACT` 同期改为 `hot: false`：抽取器在记忆引擎装配时取一次，改档实际要重启；
旧文案「下一轮生效」与实现不符，本次顺手修正（2026-11-18 核对 `assist.ts` 的 `memoryEngine` 是模块级常量）。

## 备选与否决

- **纯前端假开关**：把开关状态存 localStorage、不写服务端。否决——刷新/换端就丢，后端行为不变，
  与「开关」两个字不符。
- **把 4 个多档全部改成布尔**：否决——会丢掉「按什么方式做」的档位，等于把功能砍小。
- **每个插件新增 `<KEY>_ENABLED` 布尔键**：否决——多 4 个键、多 4 组父子关系，
  而且关掉后各自的「不做什么」仍要定义，收益更小。
- **内部质检关 = 完全不做质检**：否决——chancellor 的拆单 / 验收 / 目标核对必须有判官，
  没有注入时本来就回落到 Qoder；「关」只能定义成「不用核心模型，走外部 CLI」。
- **工具权限关 = 只读**：否决——默认档是 `full`，把「关」定义成更严的档会让用户以为关掉更安全，
  实际只是换了一种限制；关 = 不限才是与默认一致的语义。

## 明确不做

- 不动任何**非**多档插件的控件形态（布尔仍是单独拨杆）。
- 不新增端点、不改 `GET /agent/flags` 的既有字段语义（`offValue` 只是新增可选字段）。
- 不改手机端（手机不渲染插件页控件）。
- 不改 `MEMORY_EXTRACT=rule` 的逐字节回滚口径；`off` 是新增的第四档，不替换 `rule`。
- 不对单条记忆做「抽取来源」标记：`off` 期间只是不写新的，已有记忆原样保留。

## 回滚

- 单选层面：把开关拨回开（或把对应值改回原档）即可；`offValue` 只是界面语义，不设就回到旧控件。
- 代码层面：`MEMORY_EXTRACT=off` 的 no-op 抽取器只在值为 `off` 时启用，不影响 `auto/llm/rule`；
  `learningFrequency` 的 `off` 只在值为 `off` 时出现，原有 `weekly/settle` 行为不变。
