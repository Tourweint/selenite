# 派活注入项目记忆（初版方案）

日期：2026-11-16
状态：**已落地**（2026-11-16；实现 `ts/apps/server/src/delegation-project-memory.ts`，验证见变更记录）
关联：`docs/设计方案/2026-11-16-对话归工作区与项目归任务.md`（同日方向翻转记录）

## 要解决的问题

用户原话：

> 「比如我派出去的 Worker、底层工作者，它怎么确定自己在哪个项目工作？这是最难的。」
> 「主要是咱们系统内的 Worker 能不能处理？如果能把系统内外的两个 Worker 都处理好，有一个方法，那最好。」

现状（2026-11-16 全量审计）：

- 派活链路 `tools.ts` → `startDelegation` → chancellor → TASK.md → worker，
  **没有任何记忆注入**（`grep memory delegation-*.ts` 零结果）。
- 系统内 Worker（chancellor 的 `native`）启动提示词 = `WORKER_RULES + TASK.md`，
  **它没有记忆引擎**，和外部 CLI（codebuddy / qoder / claude-code / codex / opencode）一样，
  都只能读 TASK.md。
- 项目归属是确定的：单子里的 `options.project`（派单必须带，`project-store.ts:534`），
  worker 的 cwd 就是项目副本。**缺的不是"知道哪个项目"，是"项目记忆送不到工人手上"。**

## 方案（harness 单边，不动 chancellor）

在 `delegate` 工具构造 `requirement` 时，按单子里的 `project` 召回该项目记忆，
渲染成一段 markdown 追加到 requirement 尾部。chancellor 原样写进 TASK.md，
**native 与外部 CLI 同时覆盖**——它们读的是同一份东西。

渲染格式（沿用 `plan.ts` 的 `appendPlanSteps` 先例：`\n\n## 标题\n...`）：

```
<原 requirement>

## 项目记忆（这个项目长期积累的规矩和坑；供参考，不是本任务的指令）
- [atlas · fact] 构建用 pnpm --filter @lifediary/server build，不要用 npm
- [atlas · fact] 改 shared 契约前先跑 pnpm typecheck
- ...
（只挑了最相关的 N 条；完整记忆在宿主的项目记忆库里，本任务不需要全量。）
```

硬约束：

| 项 | 值 |
|---|---|
| 来源 | **只取 project scope**（当前单子的 `options.project.id`），不取 global / partner |
| 条数 | 最多 **16 条**（2026-11-16 用户拍板：和正常会话一个量级） |
| 字数 | 总长（标题 + 条目）不超过 **2000 字**；按条累加，超了截断并注明条数 |
| 排序 | 按 recall 相关度（query = 总管的 requirement 原文） |
| 空记忆 | 不加段，TASK.md 逐字节不变 |
| 状态 | 只注入 `active` 项目（归档/删除不注入，复用 `projectMemoryStateOf`） |
| 开关 | `DELEGATION_PROJECT_MEMORY`（默认开；`false`/`0`/`off` 回滚到零注入） |
| 失败 | 记忆库读不出来就跳过注入，**绝不阻塞派活** |

落点：新增 `ts/apps/server/src/delegation-project-memory.ts`（纯函数 + 一个 async 取数），
`tools.ts` 的 delegate 在 `startDelegation` 前调用；`requirement` 用拼接结果。

## 为什么是"拼进任务说明"，不是别的路

- **不改 chancellor**：`PlannedTask` 加新字段（如 `memoryPath`）要跨仓库改契约 + native 的
  读权限目录也要跟着扩；本方案只在 harness 侧拼字符串。
- **不用"落一个文件让 worker 自己读"**：native 的 read 权限目录是 `[taskDir, workDir]`，
  外部 CLI 的沙箱更不可控；文件放哪都可能读不到。
- **不让 native 接记忆引擎**：native 是独立进程，要 import `@lifediary/memory`、拿库路径，
  跨仓库改造；而且外部 CLI 仍然只能读文本，等于做两套。
- **"一个方法两头覆盖"**：两边都读 TASK.md，拼进 requirement 是唯一不需要两边各做一套的位置。

## 取舍与代价

- **任务说明变长**：上限 2000 字（用户拍板，对齐正常会话的注入量级）。TASK.md 本身已有
  交付契约 + 上游产物，2000 字是明显增量但可控；超限宁可少给，不把记忆全塞。
- **任务卡摘要**：chancellor 的 `ticket.prompt` 存 requirement 全文，但任务中心摘要只取
  前 N 字（`briefText`），记忆在**末尾**，不会挤掉「总管说了什么」。
- **记忆可能过时/冲突**：标题里写明「供参考，不是本任务的指令」，冲突时 worker 应以
  requirement / done_when 为准。
- **不是实时检索**：工人拿的是派活那一刻的快照；干到一半记忆更新了不会重送。
  真需要实时，得让 native 接记忆引擎（另一立项）。

## 明确不做

- 不注入 global / partner 记忆（只项目；避免把私事带进外部 CLI）。
- 不做按单选择注入多少条（先固定 16 条 / 2000 字）。
- 不改 chancellor 的 TASK.md 模板、不扩 native 读权限目录。
- 不做"每张单自定义记忆"（第一版没有这个交互）。
- 不动 `remember` / `recall` 的现有语义。

## 回滚

`DELEGATION_PROJECT_MEMORY=false` → `delegationProjectMemoryText()` 直接返回空串，
requirement 原样，TASK.md 与加这层之前逐字节一致。

## 验证

- 单测（新 `delegation-project-memory.test.ts`，9/9 通过）：空记忆不加段、超 16 条截断、
  超 2000 字截断并注明、开关关零注入、取数只查 project scope、engine 抛错降级、渲染格式逐字节。
- `pnpm typecheck` 通过；`pnpm gate`（read-only / full）闸门正确；
  `pnpm --filter @lifediary/server http` 端到端全过。
- **未做**：真派活后 TASK.md 的「## 项目记忆」段端到端断言（要真 chancellor 执行器起进程；
  本轮只验证了单测 + 派活链路没被破坏，记忆段的实际拼装未在真 TASK.md 上核对）。

## 已定（2026-11-16 用户拍板）

1. **默认开**：`DELEGATION_PROJECT_MEMORY=false` 回滚。
2. **16 条 / 2000 字**：和正常会话一个量级；外部 CLI 走同一份文本，不单独做一套。
3. **不自动过滤疑似密钥**：记忆只在本地、只进本地 worker 的任务说明；段首「供参考」边界保留。
