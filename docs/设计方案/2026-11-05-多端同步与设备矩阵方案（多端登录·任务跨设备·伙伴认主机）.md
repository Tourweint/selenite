## 〇、一句话

把"一台电脑 + N 个控制端"长成"N 台电脑互为矩阵"：**中继只当路由与在场名册，会话数据永远住在跑它的那台 harness，其他端全部是镜像**；手机发任务可以点名任何一台在线电脑，伙伴认一台主力电脑、CAS 换家随时搬家——全程没有账号服务器、没有云端正文。

## 一、目标与用户口径（2026-11-05 定）

1. **多端登录**：手机 / Windows / macOS / Linux 全支持。web 控制端天然跨平台；CLI 客户端另行立项（2026-11-05 已拍板"等需要时再做"）。
2. **手机发任务给"任何人"**：点名某台电脑直接派活；或发给某个伙伴——伙伴自动落到它的主力电脑执行。
3. **伙伴运行在哪台电脑上？**——认主力（home device），可一键换家；主力离线可从手机发起"在这台电脑继续"。
4. **分布式但不开云端**：中继是自建的"路由 + 名册"，看不见业务数据；不引入账号体系（架构 §"刻意没有"不动摇）。

## 三、cindy 的答案：两套体系，挑 30%

cindy 同时跑着两套跨设备体系，混着看会迷路：

- **IM 式（伙伴云）**：闭源 Chat Server 存伙伴 actor 与 `home_device_id`；手机发消息进伙伴的云端 1:1 房间（确定性房间 ID、`operationId` 幂等）；服务器转成 execution，**只有主力电脑能 `POST /executions/claim` 领取**；伙伴回复由主力电脑按 `sourceId` 去重**镜像回写**房间。离线 = 服务器排队、上线领取。
- **RPC 式（device-link）**：单一 WS 信封 `{v,kind,id,src,dst}`（src 由中继盖章防伪造）；控制端 invoke 被控端走**白名单默认拒绝**三道 gate（被控开关→逐设备撤权→通道白名单）；会话是"被控端唯一事实源 + 控制端镜像订阅"，断线靠全量 resync 补。

**必须抄的六件**（每件都省掉一轮踩坑）：

1. **信封协议与错误码表**：`device_offline / remote_disabled / version_mismatch / payload_too_large`，中继盖章 `src`；
2. **homeDeviceId CAS 换家**：`expected_home_device_id` 乐观锁，409 时**带回实际值**重读再试；空位先到先得；
3. **只路由给主力 + 持久降级名单**：非主力副本不领取、不执行、不发送（"边界写死"的跨设备版）；
4. **离线排队三件套**：发送端 durable outbox（`operationId` 幂等）→ 目标上线补投 → `sourceId` 去重回填；
5. **allowlist 三道 gate + 通道超时表 + 熔断**：安全骨架约 200 行可抄完；`CHANNEL_NOT_ALLOWED` 兼作能力探测（老端 fail-visible）；
6. **presence 双源纪元合并**：REST 快照 + WS 增量按纪元合并，治"快照落地晚于增量被打回离线"的竞态。

**明确砍掉的 70%**：P2P 直连与可靠传输层（seq ACK/拥塞/微批/文本快照修复帧）、自建中继的证书/媒体全套、40+ 通道白名单全集、Orca 远端 Worker 整套（只留"输入队列 clientId 幂等 + 轮询回报"这个模式）、任务整包复制。v1 一律"全量 resync 补齐"。

## 四、总体架构：三阶段

### 阶段一：中继与多控制端（前置 = 中继立项）

- **中继职责（对 §7 登记的升级，不是推翻）**：连接枢纽 + 在场名册（presence 广播 + `GET /devices` 快照）+ **伙伴→主机路由表**。中继存的是**路由元数据**（设备、在场、归属），不存会话正文 / 密钥 / 记忆——"哑"指看不见业务数据，cindy 自建中继同样存 presence 与凭证哈希。
- **多端登录**：配对令牌绑 `deviceId`（uuid）；hello 交换 `{deviceName, platform, version, capabilities}`；新连接顶替旧连接（同设备）。
- **镜像**：控制端订阅会话流，复用现有 SSE seq/`sinceSeq` 语义 over 中继；断线重连 = 全量 resync（列表 + 打开的会话）。v1 不做补发队列、不做文本快照修复帧。
- **回滚**：`RELAY_ENABLED=false` → 回局域网直连形态（手机存电脑地址，现状）。

### 阶段二：任务跨设备（设备矩阵）

- **设备模型升级**：`pairing` 表 → 设备注册（`deviceId`、`platform`、`capabilities[]`、`online`、`lastSeenAt`）；权威投影在中结名册，harness 自报能力。
- **派活**：`delegate` 扩 `targetDevice` 参数（或新工具，细化方案定；**必进 `WRITE_TOOLS` 过闸门**）。执行 = 经中继 invoke 目标 harness 的**会话输入队列**（`clientId` 幂等，学 cindy `maker:input:enqueue`）；目标机上是普通 chancellor 单。
- **回报（轮询制，不订阅）**：学 cindy §4.5——快 2s / 闲 15s，15 轮无回复判 error；`last_reported_id` 去重；同轮重复只送一次。汇报回流走中继 push 回发起端会话（`DELEGATION_AUTO_REPORT` 语义跨机延伸）。
- **回执两级**：发起端记"远端受理"（引用目标机回执 id），目标机记实际执行；`requestId` 全局 uuid 跨机幂等；与批次A2 的 `bootId` / 死信补差天然衔接。
- **离线语义 v1**：目标离线**直接失败不排队**，回执记 `device_offline`（学 cindy 首版）。发送端补投只做在手机 App 本地 outbox（排队在发送端，中继永远不存正文）。
- **超时/熔断**：每个通道一张执行预算表（学 `INVOKE_TIMEOUT_OVERRIDES_MS` 思想）；连续超时熔断快速失败，不占管道。
- **回滚**：`DEVICE_MATRIX_ENABLED=false` → 回本机 chancellor（现状）。

### 阶段三：伙伴认主机（依赖批次B partners 落地）

- **归属**：partners 表加 `home_device_id`（细化方案时预留）；**仲裁点在中继**——CAS `expected_home_device_id`，409 带回实际值；空位先到先得。
- **路由**：手机发消息给伙伴 → 中继按 `home_device_id` 转给主力 harness 的伙伴专线会话；只有主力能领取执行。
- **降级**：非主力副本不领取、不执行例行任务、不发送（持久化降级名单，中继不可达时也生效）。
- **换家顺序（照抄 cindy，一句不改）**：先写中继路由表 → 再动本机；本机全程降级，成功才解除；失败保持降级重试。主力离线时手机可发起"在这台电脑继续"→ 新主机 CAS 抢占 + 拉档案快照重建。
- **迁移内容**：SOUL / 记忆 / 技能 / 能力**引用**随行；**凭证不随行、权限档不随行**（蓝图判词原文引用）——每台 harness 各自 env 配 key，新主机用自己配的。v1 全量拉取式同步（档案本来就小），不做增量、不做墓碑。
- **历史**：canonical 会话随主机走；换家后新主机按档案快照开新会话，旧历史整包只读带走（对齐"会话数据住 harness"）。
- **回滚**：`COMPANION_HOME_ENABLED=false` → 回单机伙伴形态。

## 五、安全与故障半径

- 中继不可信三件套沿用（凭证只存哈希 / 令牌不过中继 / `src` 盖章防伪造）。
- **审批 fail-closed 不变**：审批状态住 harness；跨设备送达不了就拒绝（蓝图原则 2 的直接套用）。
- **故障半径按设备隔离**：一台设备抽风不许拖垮中继上其他设备（cindy 判例 #1187：一台休眠手机把全网打掉线）；per-peer 状态隔离 v1 就要做。
- 新派活工具过闸门（`WRITE_TOOLS` + `readOnlyBlockReason()`）；`AGENT_TOOL_POLICY=read-only` 语义不被矩阵绕过。
- 日志纪律不变：跨设备链路只记条数 / 枚举 / 耗时 / 设备 id，正文与参数不进日志。

## 六、备选与取舍

- **备选 A：现成 Tailscale/Headscale 代替自建中继信令**——保留为部署选项（架构 §7 已登记），协议仍按自建信封设计，随时可换底座。
- **备选 B：不做矩阵，多台电脑各跑各的**——现状即此形态，零成本但没有"发给任何人"；本方案的核心增量就在这。
- **为什么 v1 砍离线服务器排队**：排队要存正文，与"中继不碰业务数据"冲突；发送端 outbox + 上线补投已覆盖不丢消息，且 cindy 的服务器排队闭源不可考，只学语义不学实现。
- **为什么伙伴仲裁放中继**：CAS 需要单一仲裁点；中继本就是连接与在场的事实源，存一条"伙伴→设备"引用是元数据不是业务数据。备选是"各 harness 协商仲裁"——分布式 CAS 没必要自找。

## 七、明确不做（登记进"刻意没有"）

| 不做 | 理由 |
|---|---|
| 多端双向同步 | 唯一事实源 + 镜像 + 显式迁移；双向同步是复杂度无底洞（cindy 也不做） |
| 中继存会话正文 / 密钥 / 记忆 | 密钥纪律 + 中继不可信前提 |
| P2P 直连、可靠传输层、文本快照修复帧 | 弱网优化第二优先级；全量 resync 够用 |
| 任务整包复制（task-copy） | 产品层增量，与核心问题无关 |
| 伙伴多机并行 | 同一时刻只有一个主力；并行归属是另一条产品线 |
| 群聊接力 / 伙伴互发 | 蓝图后置池已有，不重复 |
| 云端账号体系 | "刻意没有"不动摇 |

## 八、契约影响与落地顺序

1. **shared 先行**（硬约束"契约只有一份"）：信封 Zod schema（`Envelope` / invoke / push / 错误码）、设备与伙伴路由 schema、SSE 事件扩展 → `接口文档.md` 新章节 → 手机端跟进。**手机端契约是跨仓改动，本方案即是其前置方案**。
2. **顺序**：中继（独立立项）→ 阶段一（多控制端镜像）→ 阶段二（设备矩阵）→ 批次B 伙伴落地 → 阶段三（伙伴认主机）。批次A/B/C 与本方案无阻塞关系，可交错。
3. **验证**（真起服务 + 真中继，不 mock 单测糊弄）：阶段一双控制端镜像（两浏览器 + 一手机：列表/流/审批/断线 resync）；阶段二双 harness 互派（含目标离线 → `device_offline` 回执、熔断）；阶段三换家探针（CAS 冲突、降级、离线接管、凭证不随行断言）。
4. **回滚开关汇总**：`RELAY_ENABLED` / `DEVICE_MATRIX_ENABLED` / `COMPANION_HOME_ENABLED`，逐层退回上一形态。
