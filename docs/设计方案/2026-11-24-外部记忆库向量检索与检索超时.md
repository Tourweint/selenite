## 二、目标与非目标

**目标**

1. 让**工具调用**可选用库侧的向量检索（今天 = 向量 + FTS 的 RRF），默认行为与今天逐字节一致。
2. 能力开关跟着**库**走：换库 = 换这个库的能力，不是改部署 env。
3. 轻召回有独立、更短的时间预算，且**永远不向量检索**（每轮延迟优先）。
4. 超时在界面上可调，两档分别管"每轮"和"工具"。
5. 旧形态清干净：只有一套 `recall` / `remember`，不留第二套工具与开关。

**非目标**

- 不给内置记忆库加向量 / 向量检索；不改 JSON 字段；不接 `search_rag.py`；不做后台检索（§十）。

## 三、向量检索：`--vector`

### 3.1 外部契约（库侧可见）

```
ask <question> --json --limit <N> [--vector]
```

- `--vector` 是**布尔开关，只出现在末尾**；不传 = 与今天逐字节相同的调用。
- 语义：**"愿意等更慢更强的检索"**，不承诺手段。persona-metric 的实现是向量 + FTS 的 RRF；
  换成 rerank、扩展组、二次召回都算合规，只要守住下面三条。
- `--catalog-only` **永不**带 `--vector`（目录是库边界文本，不是检索）。
- **JSON 输出形状一字不改**：`groups` / `id` / `date` / `title` / `text` / `body` / `name` / `why` /
  `coverage` / `unknown` 全部沿用；`parsePersonaAskOutput` 的 `anyGroups` 扁平化不动。
- 硬约束：`--limit` 仍是**每组硬上限**。工具层只按单条 160 字裁剪、不按条数减
  （`tools.ts:538`），向量检索命中变多会直接撑大工具返回。
- 旧库的两种表现（都写进接入手册）：
  - Python `argparse`（`ask.py` 即此形态）：未知参数 → 退出码 2 + usage 到 stderr → `ok:false`，
    **不会静默退化成浅检索**；
  - 手写 argv 解析的入口（`.js` / `.sh` 等）：可能**静默忽略**未知参数 → "勾了没效果"，不报错。
  因此"勾选向量检索"等于**声明这个库认识 `--vector`**，这是配置项的语义。
- 探测（`probeBank`）**不验证**向量检索能力：不检索就无法判断；勾选即声明，失败只在实际检索时暴露。

### 3.2 库接入配置 `external.vector`（默认 false）

`memory-bank.json`：

```json
{
  "v": 1,
  "active": "builtin",
  "external": {
    "id": "bank_xxxxxxxx",
    "name": "外部记忆库",
    "root": "D:\\Projects\\projects\\persona-metric",
    "ask": "analysis/ask.py",
    "repair": "analysis/repair.py",
    "python": "",
    "vector": false,
    "origin": "user",
    "addedAt": "2026-11-24T10:00:00+08:00"
  },
  "timeouts": { "lightMs": 8000, "askMs": 15000 }
}
```

- `vector` 是 `ExternalBankRecord` 的新字段，`false` = 不声明（也兼容老库）。
- 写入路径：接入页勾选 → `PUT /api/v1/agent/memory/bank/external` body 加 `vector?: boolean`。
  缺省 = `false`（本次接入不声明）；前端接入 / 更换表单**总是**带上复选框状态，不会意外丢。
- 读取消毒：非 boolean / 缺字段 → `false`；旧字段 `deep` 不做别名（直接忽略，按 `false`）。
- **不 bump `v`**：缺字段按默认补齐；旧版 harness 读到新文件会丢掉未知键（`vector` / `timeouts`），
  降级回旧版时重设一次即可，不会坏。
- 生效范围（检索类调用；轻召回除外）：
  - `recall`（外接槽）→ `bankAsk(question, {limit, vector})`，`vector` 读库接入配置 `external.vector`（缺省 false）；
  - `persona_recall`（`MEMORY_BANK=false` 旧路径；本批仍在，退役批才删）同样传；
  - **轻召回永远不传**（`personaLightRecall` 不设 `vector`，默认 `false` 由调用点保证，不看配置兜底）；
  - 页面搜索 `POST /bank/search` **与工具调用一致，跟随 `external.vector`**（同一条 `bankAsk` 读路径；召回只有一套口径）；
  - `--catalog-only` / 接入探测 / 目录刷新不传。
- 改已接入库的 `vector`：重新「接入」一次（探测会重跑一次 `--catalog-only`，代价已知）。
  本批**不做**"只改 vector"的独立端点（§十）。
- 开关跟着库走的好处：换库不会继承上一个库的能力声明；一处配置同时决定"这个库能不能深"和
  "工具要不要传"，不需要两个开关对齐。

### 3.3 密钥边界（单列）

- **API key 绝不进 harness**：embedding / 重排所需的 key 由库自己管（persona-metric 用自己的
  `DASHSCOPE_API_KEY`），harness **不读、不存、不传**任何 key。
- 接入配置里**只有布尔字段**（`vector`）；`memory-bank.json` 不出现 key、不出现 provider、不出现模型名。
- 子进程 env 也不额外注入密钥：`bankSpawnEnv` 只钉路径与三个开关，其余原样继承（库自己从环境里取）。
- 日志纪律不变：只记状态 / 条数 / 字数 / 耗时；不记 query 原文、库路径、stderr 全文。
- 因此"向量检索用哪个 provider / 哪个模型 / 维度多少"是**库的内部事实**，harness 不知道也不需要知道；
  换 provider 不需要改 harness。

### 3.4 通用适配

`--vector` 不绑外部库：将来内置记忆库实现向量检索（embedding provider + 索引 + 迁移，独立工程），
同一套语义可以复用——harness 只关心"这一路检索愿不愿意等更慢更强"，不关心底层手段。
本轮**不实现**内置库向量检索（§十）。

## 四、两档超时

### 4.1 存储与默认

`memory-bank.json` 顶层新增：

```json
"timeouts": { "lightMs": 8000, "askMs": 15000 }
```

| 字段 | 默认 | 作用点 | clamp |
|---|---|---|---|
| `timeouts.lightMs` | `8000` | **只**轻召回 `personaLightRecall` | `500..30000` |
| `timeouts.askMs` | `15000` | **只**工具调用的 `askPersona` | `1000..120000` |

- 读取：`bankTimeouts(env)`（`memory-bank.ts` 导出），缺字段 / 非数字 / 越界 → 回落默认并 `warn`
  一次（文件被手改坏不该让服务起不来）。
- **只对外接库生效**：内置 `recall` 是进程内引擎，没有子进程可超时；内置槽位下这两个值不参与任何判定。
  界面文案与小节标题都要写清这一点。
- `askPersonaCatalog`（`--catalog-only` / 接入探测）**不参与两档**，继续用 15s 常量：
  它不是工具调用、也不是每轮注入。
- 优先级：`deps.timeoutMs`（测试注入）> 库配置 > 常量默认
  （`PERSONA_ASK_TIMEOUT_MS = 15_000` 保留为 ask 兜底；新增 `PERSONA_LIGHT_TIMEOUT_MS = 8_000` 作轻召回兜底）。
- 超时文案动态化：`persona 检索超时（${Math.round(timeoutMs / 1000)}s）`
  （今天硬编码 15s，`persona-ask.ts:389`）。
- 传递链：`bankAsk` 读 `timeouts.askMs` 传给 `askPersona`；轻召回的 `lightMs` 由
  `lifecycle-harness` 读 `bankTimeouts()` 后沿现有 deps 传入 `personaRecallLightTextFor` →
  `personaLightRecall` → `askPersona`。**persona-inject 不 import memory-bank**
  （memory-bank 已 import persona-inject，反向会成环）。

### 4.2 HTTP 契约（变更，按接口文档 §7 顺序）

`GET /api/v1/agent/memory/bank` 响应扩展两个字段：

- `external.vector: boolean`（外接库存在时）
- `timeouts: {lightMs: number, askMs: number}`（顶层，恒在）

`PUT /api/v1/agent/memory/bank` 支持**局部更新**：

```json
{ "active": "external", "timeouts": { "lightMs": 8000, "askMs": 20000 } }
```

- 每个字段都可选；**至少给一个**，空 body / 未知字段 → `400 bad_request`。
- `active` 非法 → 400（沿用）；`timeouts` 的每个子字段独立可选，只改给了的。
- 值必须是整数且在 clamp 区内，**越界直接 400 并说明区间**（不静默改）；文件被手改坏才走"回落默认 + warn"。
- 一次调用只落一次盘（`active` + `timeouts` 同批写），响应沿用 `{ok, active, bank}`。
- 老客户端只发 `{active}` 仍然工作（向后兼容）。

`PUT /api/v1/agent/memory/bank/external` body 扩 `vector?: boolean`；非 boolean → 400（文案「vector 只能是 true 或 false」）。
响应里的 `external` 带 `vector`。

顺序（`接口文档.md` §7）：先改 `docs/基线文档/接口-端点6-记忆课题与搜索.md` §2.15.11 与
`docs/接入手册/外部记忆库接入（两个文件）.md` §2.1 → 再改代码。手机端与 chancellor 不涉及
（这两个端点只有本仓网页端在用，字段只增不改名）。

### 4.3 界面：插件中心一项「记忆工具时长」

- 位置：插件中心 → 记忆组。**不是 flag**（存 `memory-bank.json`，不走 `/agent/flags`），
  而是该组里一张自定义卡：卡面右侧摘要 `每轮 8s · 工具 15s`，整张卡点开（或「编辑」）弹层里
  两个数字输入 + 保存。
- 交互可复用两处现成模式：
  - 「整行点开就是编辑」：`web/settings-reminders.js:597`、`635` 的口径；
  - 数值输入的画法与保存：`settings-switches.js:555-625` 的「自动归档天数」（含 clamp、失败回滚、toast）。
- 读写：`GET /bank` 回填、`PUT /bank` 保存（与记忆页同一套端点）。
- 渲染条件：`GET /bank` 404（`MEMORY_ENABLED=false`）时该项不渲染。
- **退路（若该页结构插入自定义卡太脏）**：挪到记忆页「记忆库」卡里（`web/memory-page.js` 的
  `#mem-bank` 卡体，`memoryBankBankMarkup` 一带）。那一页本来就有 `handleBankAction` 的
  `GET/PUT /bank` 通路，不需要新接一层；代价是入口更偏"记忆库"而不是"插件"。
  二选一在落地时按实际改动量定，**默认先试插件中心**。
- 插件中心原来的「记忆库槽位」卡在退役批删除，这张卡正好接它的位置（记忆组不留空洞）。

### 4.4 超时后的行为

**工具调用**：

- `askPersona` 返回 `ok:false`、`error` = `persona 检索超时（Ns）`，并带内部标记 `timedOut: true`
  （`PersonaAskResult` 与 `tools.ts` 的结构孪生 `PersonaRecallResult` 各加一个可选字段，两边同步；
  不做字符串匹配）。
- 工具层在 `!ok` 分支里**只对 `timedOut` 透传**这句 error（`err(code, message, hint)` 的 message），
  hint：「告诉主人这次查得太慢、没查完；可以换更短的关键词再试一次，别连续重试同一个查询」。
- 其余失败维持现状（通用「暂时查不了（原因已记日志）」）：stderr / 退出码 / 本机路径仍只进服务端日志
  （现有 `memory-bank-tools.test.ts:111-119` 的断言因此仍然成立）。
- 不重试、不换库、不自动加长超时——一次超时就是"这轮没有库证据"。

**轻召回**：

- 静默 `[]`、本轮不注；照常写 60s 节流账本（`persona-inject.ts:238-242`），
  即"这个会话 60 秒内不再为轻召回起 python"。
- 8s 是"正常 0.8s 的十倍"；超过即认为库不正常，60s 内不再撞。

## 五、库侧降级要求（库主实现，harness 只依赖外部行为）

`--vector` 打开后，库侧必须在**任何一步失败**时退回浅检索（纯 FTS/BM25），且对 harness 完全透明：

| 失败 | 要求 |
|---|---|
| 无 `DASHSCOPE_API_KEY` | 退浅检索；stderr **一行**警告（不含 key）；退出码仍 `0` |
| npy / 索引缺失或损坏 | 同上 |
| 网络 / 超时 / HTTP 非 2xx | 同上（**新增 catch**：`encode_query` 的 `urlopen` 今天没有 try） |
| 向量矩阵与表不一致（越界 / 空） | 同上 |

- 降级后仍输出**完整合法 JSON**，退出码 `0`；**不许"半开"**（先返回部分结果再非零退出）。
- stderr 一行、进程内只警告一次（`VEC_WARNED` 已有先例），不记 query 原文。
- 库侧 `urlopen` 超时必须**显著小于** `timeouts.askMs`（建议 ≤3s，现在 60s）：否则永远是 harness
  先 `kill`，降级逻辑没机会跑，用户看到的永远是"检索超时"。
- 具体接哪几组、怎么融合由库主定（与调研 §4.1 建议一致：复用已有向量 + RRF）。

## 六、为什么不转后台

明确**不做**"超时转后台、完成后回填"：

1. **检索结果是当轮回答的证据**；后台返回时模型已答完，证据来晚等于没检索，塞进下一轮又说不清归属。
2. **该转后台的是写 / 整理类**（索引重建、内化、巩固），它们不参与当轮推理，且已有后台任务机制承接。
3. **超时本身是信息**：告诉模型"查不了"比让它编造好，也让主人知道库慢。
4. **后台不解决根因**：慢在库侧（embedding、全量点积、npy 冷读）。要"慢但完整"，正确形态是库侧
   预计算 / 缓存，那是库主的活。

## 七、成本

- **每次工具调用多 1 次 DashScope embedding 请求**（`qwen3.7-text-embedding-flash`，1024 维，
  输入是一条问题文本）。按量计费，单次极小（**未核价**，不写数字）。
- 轻召回 **0 次**；`--catalog-only` / 接入探测 **0 次**。
- 固定成本不变：每次工具调用仍起一次 python（实测 0.7s 检索 + 启动，见 `persona-ask.ts:21`）；
  向量检索版多 import numpy 与 mmap npy（未实测，见 §十五）。
- **不做 LLM rerank**：`search_rag.py` 的 `E`（D+rerank）要网关模型，超预算且今天未实现。
- 模型侧 token：条数上限仍由 `--limit` 决定（默认 5），单条 ≤160 字，不因向量检索变多。

## 八、回滚

| 想回到 | 一行操作 | 结果 |

## 九、备选方案与不选的理由

| 备选 | 不选的理由 |
|---|---|
| **甲：harness 改调 `search_rag.py`** | 入口契约是"ask / repair 两个文件"，改调第三个脚本等于改跨仓契约 + 改接入检测；`search_rag.py` 不查六组、不查 `user_statement`，输出是五字段而不是 `groups`，等于把解析、渲染、`coverage` 全部重做；一次工具调用要跑两套检索，成本与口径都翻倍 |
| **乙：`ask.py` 内部默认走向量检索** | 轻召回会被一起拖慢（无法按调用形态分档）；回滚要动库；库与 harness 的版本对应变隐式 |

| **庚：超时用 env** | 已拍板否掉：改一次要重启/碰 env；放库配置 + 插件页才能让"两档"落到界面上，且与 `vector` 同源 |

## 十、明确不做

1. 不把 `search_rag.py`（或任何第三个脚本）接进产品；harness 只认 `ask` / `repair` 两个入口。
2. 不改 JSON 字段名（`groups` / `id` / `text` / `body` / `name` / `date` / `why` / `unknown` / `coverage`）。
3. 不建向量库 / FAISS / 索引服务；向量文件归库侧，`.npy` 可重建。
4. **不给内置记忆库加向量 / 向量检索**：那需要 embedding provider（key、模型、配额）、索引构建与迁移、
   以及召回质量回归，是一整件工程；本轮只让**外部库**可选向量检索。内置库继续用现有的
   FTS + 打分召回。
5. 不给轻召回开向量检索。
6. 页面搜索与工具调用一致，跟随 `external.vector`（同一条 `bankAsk` 读路径；不做单独的页面搜索开关）。
7. 不做"只改 vector"的独立端点：改 vector 靠重新接入（探测重跑一次）。
8. 不做后台检索 / 超时转后台 / 迟到结果回填（§六）。
9. ~~不做能力探测（不"先试 `--vector`，失败再补一次浅检索"）：多一次超时级失败 + 一层缓存，
   而勾选语义已经说清"我声明这个库支持"。~~ **2026-11-24 命名统一批改口径**：只对
   **非超时失败 + 退出码 2 + stderr 命中 argparse 参数拒绝特征**自动退回普通检索一次
   （`vectorUnsupported:true` 留痕）；超时不重试，其余失败不重试。不做通用能力探测 / 缓存。
10. 不在 `memory-bank.json` 里存多库候选 / provider / 模型 / key。
11. 不引入 embedding 缓存（query 每次不同，命中率低，还要考虑隐私落盘）。
12. 不做 rerank、不做组配额调整（调研 §4.2 是库主的事）。

## 十一、已知边界与风险

- **旧库 + 勾了 vector**（Python argparse 退出码 2）：harness 会自动去掉 `--vector` 重试一次普通检索
  并留一行日志（「库不认识 --vector，已改用普通检索」）；重试结果正常返回，不再是"工具调用稳定失败"。
  勾选仍然表示"我声明这个库支持"，排查看服务端日志的 `[persona-ask]` 行；接入手册要写"先确认库版本再勾"。
- **手写 argv 解析的入口**会静默忽略 `--vector`：表现为"勾了没效果"，不报错。
- **条数风险**：库侧若在向量检索模式返回超过 `--limit` 的条数，工具结果会变长（harness 不减条）。
  §3.1 已写成库侧硬约束。
- **延迟挤占**：向量检索的 embedding 与 npy 读盘挤在 `askMs` 里。库侧若不能快速降级（§五），
  表现会是"超时"而不是"降级"——可接受的失败方向，但要知道。
- **`timeouts` 只对外部库生效**：内置 `recall` 不受它影响，界面必须写清，否则会被当成"调了没反应"。
- **向量检索质量未评估**：本方案不跑评测集，所以"勾了是否更准"没有证据；默认 false 也正因为此。
- **探测骗不了**：勾选不是"已验证能力"，只是一个声明位。
