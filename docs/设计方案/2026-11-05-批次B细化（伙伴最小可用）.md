## 〇、一句话

给服务端加"伙伴"：一个长期身份 = SQLite 两张表（档案+版本快照）+ 磁盘一个家目录（SOUL.md
为锚点）+ 记忆按 `partner:<uuid>` 键空间隔离 + 一个例行任务引擎（**触发层用 durable 任务图，
不是扫描定时器**）+ 模型候选链（不可用才切用户配好的下一项）。伙伴轮次 = 现有 chatStream
链路 + 按版本快照渲染的身份提示词 + 复用现行闸门/审批/工作区边界。

## 一、目标与明确不做

**做**：建/改/暂停/删除伙伴；伙伴有独立记忆、独立技能、独立模型候选链；例行任务能按时/按事件
跑伙伴专线会话；faux 链路全程可测。

**不做（v1 明确砍掉，与蓝图后置池一致）**：伙伴间互发消息；群聊分工；云漫游；伙伴专属上下文
压缩与回复后复盘（整理只走"夜间学习"式宿主批处理的话也**后置**，v1 连夜间学习都不做）；
手机端管理界面（契约纯增量，手机不消费）；伙伴的原始写工具越过 `workspace/`。

**关键架构适配（写死，防照抄跑偏）**：cindy 的 RoutineEngine 用自转 tick 循环做 cron 比对；
本仓库 `系统架构.md` §3 刻意没有"**定时扫描型 cron（用 durable 的 sleepUntil）**"。
因此本批只移植它的**纯逻辑内核**（规则校验/回执去重/单例串行/deferred 重试/状态机），
**触发层全部换成 durable 任务**（`defineTask` + `runtime.sleepUntil`，范式 =
`ts/apps/server/src/reminder.ts:23-52`）。

## 四、B2：伙伴档案双层存储

### 4.1 SQLite（新库 `.data/partners.sqlite`，env `PARTNERS_DB_PATH`）

照 projects.ts 惯例（IF NOT EXISTS 全量重放 + 懒建单例 + mkdirSync 兜底），三张表：

```sql
CREATE TABLE IF NOT EXISTS partners (
    id                   TEXT PRIMARY KEY,        -- uuid，对外 id
    name                 TEXT NOT NULL,
    status               TEXT NOT NULL DEFAULT 'active',  -- active|paused|archived
    canonical_session_id TEXT,                    -- 内部自增会话 id（不外泄；链接表另有唯一约束）
    current_version      INTEGER,
    created_at           TEXT NOT NULL,
    updated_at           TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS partner_versions (
    partner_id     TEXT NOT NULL,
    version        INTEGER NOT NULL,
    soul_source    TEXT NOT NULL,                 -- SOUL.md 正文快照（冻结）
    capabilities   TEXT,                          -- JSON：模型候选链（B4）+ 技能引用
    created_at     TEXT NOT NULL,
    PRIMARY KEY (partner_id, version)
);
CREATE TABLE IF NOT EXISTS partner_session_links (
    partner_id    TEXT NOT NULL,
    role          TEXT NOT NULL,                  -- canonical|routine|topic
    route_key     TEXT,                           -- 例行专线如 routine:<routineId>
    session_id    INTEGER NOT NULL,
    created_at    TEXT NOT NULL,
    UNIQUE (partner_id, role, route_key)
);
```

新文件 `src/partners.ts`：档案 CRUD + 家目录读写 + 版本推进，全部**用户操作**（HTTP），
模型没有创建/删除/改 SOUL 的工具。

### 4.2 磁盘家 `.data/partner-homes/<uuid>/`

- `SOUL.md`（身份）、`memories/USER.md`（主人画像，伙伴轮提示词拼用）、
  `workspace/`（**唯一默认可写区**）、`memories/`、`skills/<slug>.md`；
- 单槽 64KB 上限；全部原子写（临时文件 + rename，照 cindy `botProfileFolder.ts:209-233`）；
  播种幂等：只在 SOUL.md 缺失时写默认模板，**SOUL.md 最后写 = 家建好的标志**；
- **权限边界（复用现成 pathGuard）**：伙伴会话的 `workspaceRoot` 指到
  `partner-homes/<id>/workspace/`，beforeTool 的 `pathGuardBlockReason`（agent.ts:552-639）
  原样生效——伙伴写不出 workspace，家目录其余部分不可由原始文件工具触碰；
  记忆写走 `remember`（scope 自动落到伙伴）、技能写走新工具（见 4.3）；
- 删除伙伴 = 档案行标 archived + 家目录整体删除（二次确认走 HTTP 端点，模型无此工具）。

### 4.3 伙伴轮次（执行形态）

- **身份注入**：开轮前按 `current_version` 读 `partner_versions` 快照，渲染系统节：
  `SOUL 正文 + USER.md 摘要 + 技能索引`——**认版本号，整轮不变；改 SOUL 下一轮生效**
  （双层契约照抄 cindy，不做即时生效）；配置入口：`openChat` 后
  `conversation.configure({ instructions: 渲染结果 })`；
- **工具与闸门**：伙伴会话**不摘**扩展（不用 configureTaskChat），闸门/审批/pathGuard/
  WRITE_TOOLS 全部原样生效——伙伴就是一条普通会话加身份提示词，**不引入第二套权限系统**；
- **技能**：伙伴技能目录接 `createSkillStore(partner-homes/<id>/skills)`，按伙伴懒建
  `Map<partnerId, SkillStore>`；模型写伙伴技能 = 新工具 `partner_skill_write`
  （写 `skills/<slug>.md`，64KB 上限，**必须进 `WRITE_TOOLS`** 过闸门——硬约束"新工具要进闸门"）；
- **记忆**：伙伴轮 `scopeOf` 返回 `{ type: "partner", id }`（B1 接线点），recall 注入 scopes
  变为 `["global", "partner:<id>", "session:<内部id>"]`——伙伴能读到全局，主人会话读不到伙伴
  （键空间单向可见，写进方案才算数）。

### 4.4 HTTP 端点（新 `src/companion-api.ts`，`mountCompanions(app)`）

`POST /api/v1/partners`（建，必填 name）、`GET /api/v1/partners`、
`GET/PATCH /api/v1/partners/:id`（改 name/SOUL（进新版本行）/候选链/状态）、
`POST /api/v1/partners/:id/rot` （轮次触发，v1 手动试跑用）、`DELETE /api/v1/partners/:id`。

## 五、B3：例行任务引擎

### 5.1 纯逻辑内核（新文件 `src/routines.ts`，从 cindy `routine-engine.ts` 裁剪）

保留：规则校验（prompt ≤100k、触发四型）、**24h 回执去重**、`originRoutineId` 防自环、
OR 条件合并同一执行、**每规则串行**（上一次没跑完，下一次标 deferred）、deferred 30s 重试、
状态机（queued/running/success/failed/interrupted/skipped）、**终态落盘失败期间后续触发只排队
不执行**、**重启 running→interrupted 不自动重放**。
换血：cron 比对循环 **不移植**（见 §一 架构适配）——改为：

- **cron/interval/once 触发** = 每条启用的例行任务一条 durable 任务（ReminderTask 同款
  `defineTask`）：`wait` 相 `sleepUntil(下一次触发时刻)` → `deliver` 相投递执行请求；
  跑完重算下一次再建任务。规则的启用/停用/改期 = 停旧任务 + 建新任务
  （`tx.createTask` / 取消语义对照 reminder 现行操作）；
- **事件触发** = 进程内订阅：给 `emitPhase/emitTool/emitDelegation` 三个发射口加一个
  全局监听口（`watchAllEvents(cb)`，三处各加一行广播——实现为最小侵入，不动现有 sink 语义）；
  事件进引擎 → 回执去重 → 命中规则 → 入队；
- **去重回执与状态落盘**：`.data/routines.json`（原子写，照 approvals.json 惯例）；
  重启后 running 一律 interrupted，**不重放**。

### 5.2 执行 = 伙伴（或主人）会话的一轮

- 每条例行任务绑定 partnerId（v1 只做伙伴例行；主人例行后置）；
- 执行：按 `sessionMode` 取/建专线会话——persistent：`partner_session_links` 里
  `role='routine', route_key='routine:<id>'` 复用；fresh：每次 `openChat` 新建、跑完隐藏
  （`chat-meta` hidden 语义现成），空壳（未跑过模型）当轮回收；
- 投递 = `chatStream({ conversation, text: 渲染的例行指令, requestId })`，`onSettled` 收终态
  写状态机；**指令头注入一行 `turnAuthority: autonomous`**（批次C 的自主轮判定消费）；
- **mock 不空转**：faux 下例行任务走同一 chatStream 真链路 + 假模型（`chatModelRef` faux
  原样返回，已核实），探针必须断言这点。

### 5.3 端点（并入 `companion-api.ts`）

`GET/POST /api/v1/routines`、`PATCH/DELETE /api/v1/routines/:id`（停用=停任务）、
`POST /api/v1/routines/:id/run_now`、`GET /api/v1/routines/:id/runs`。
内置规则（如"跟进"）属批次C，本批不建。

## 六、B4：模型候选链

- 纯函数 `src/model-chain.ts`：输入候选链（存 `partner_versions.capabilities` JSON）+ 当前
  路由 + 失败原因，输出"下一候选"或"不切"；上限 5 项；去重；**只从用户显式配置的链里取**；
- **切不切的判据**（消费点 = `onSettled` 的 `unanswered` 分支，agent.ts:1554-1561，原因现在
  只进日志——本批把 reason 字符串归类后判断）：连接失败/鉴权失败/配额/容量/模型不可用 → 切；
  **账号额度耗尽 / 用户主动停止 / 权限拒绝 / 上下文超限 → 不切**（切了同死或掩盖真因）；
- 链项结构照 `ProviderEntry` 裁剪：`{ providerId, modelId, keyEnv 名, thinkingLevel }`——

- 验证：`providers` 探针已有假上游基建（startUpstream），扩"链头 5xx → 自动切链尾成功"与

## 十一、风险与坑（提前登记）

- **cron 语义靠 durable 任务**：任务取消/改期要幂等（同一例行任务重复启用不得叠两个任务）——
  细化实现时以 route_key 幂等建任务（建前查 active 同名任务）；
