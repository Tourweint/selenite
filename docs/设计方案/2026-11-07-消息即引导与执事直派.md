## 一、要解决的两个问题

### 1. 用户连发消息时，第二条要等第一轮彻底跑完才被看见

现状：`web/app.js` 在 `state.sending` 时把输入塞进前端内存队列（`submitNext`），本轮 `done` 之后才逐条 `submit`。
内核（pi-durable 1.4.0）本来就支持"忙时投递"，`submit` 的 `whenBusy` 分两种：

- `steer`：在 `postTools` 边界进入**当前这一轮**，模型下一步就能看到；
- `followUp`：在 `final` 边界进入，本轮结束后作为下一轮。

我们一次都没传过 `whenBusy`（全仓 grep 零命中），等于把内核能力锁在"排队"这一档。

### 2. 执事派活会绕回自己

现状：`delegate` 工具挂在全局扩展上，执事会话也能调。调用后：

1. `localIdentityHit(domain)` 按 domain 反查执事，把 `managerIdentity` 注入请求；
2. chancellor 看到 `domain` 且 `managers !== false`，为该领域起一个**分管宰相进程**；
3. 而那个领域正是调用者自己的领域——等于执事把自己叫了一遍，再让"另一个自己"去派 worker。

后果：多一层进程、多一轮模型调用、身份叠两层；任务单上的 `chiefName` 也会指回自己。

## 二、决策

### 决策 1：`whenBusy` 透传到内核，回执必须诚实

- `ChatRequestSchema` 增可选 `whenBusy: "steer" | "followUp"`，缺省 `followUp`（等于今天的行为）。
- `chatStream` 把它透传给 `conversation.submit`。
- **回执诚实**：请求了 `steer` 但内核返回 `status: "queued"` 时，向前端发一帧 `notice`：
  「已请求插话，会在本轮下一个边界生效」；请求 `followUp` 则说「已排队，本轮结束后发送」。
  不把"受理"说成"已插入"——这正是 cindy `steer_fallback_reason` 的用途。

**备选与否决**：

- 备选 A：前端继续本地排队，只在 UI 上加一个"插话"按钮，由前端在 `done` 时抢跑 → 否决。
  那不是插话，只是更快的排队；模型在当前轮里永远看不到补充，做不到"边说边引导"。
- 备选 B：新增一个 `/chat/steer` 端点 → 否决。同一条链路加第二入口，会多出一套幂等/重放/停止语义；
  `whenBusy` 是纯增量字段，老客户端零改动。

### 决策 2：多段生成的流式基线必须重置（前置缺陷）

`chatStream` 的 `offer()` 用"候选必须以上次已发文本为前缀"来防重复。工具轮之后内核会
`delete live.generation` 并起新的一段，新段文本不是旧段的前缀 → **第二段永远发不出去**
（`offer` 直接 return，收尾的 `offer(answerText())` 同样被挡）。

这不是新功能，是既有缺陷；但插话恰好落在"边界之后的新段"，不修就等于插话没反应。处置：

- 以 `pi.live.run.taskId` 作为"段代号"；段代号变化且此前发过正文时，先补一个空行分隔，再把基线清空。
- 同一段内的重试（attempt 变化）**不重置**，保持"只发增量、不回吐旧文"，避免重试时重复刷字。

**明确不做**：不做"整段替换"协议。SSE 只有增量，替换要新增帧类型和客户端重建逻辑，收益不抵复杂度。

### 决策 3：执事在自己领域内直派，`managers:false`

新增纯函数 `resolveDelegateRouting({ callerPartnerId, callerDomain, requestedDomain })`，
返回三种路由之一：

| 调用者 | 请求的 domain | 路由 |
|---|---|---|
| 总管 / 主人会话（`chief` 或 `null`） | 任意 | **原样**：注入该领域执事身份，chancellor 走分管路径 |
| 执事（有 domain） | 空，或等于自己 | **直派**：不带 `managerIdentity`，请求带 `managers:false`，`domain` 保留用于任务中心展示 |
| 执事（有 domain） | 别的领域 | **拒绝**：明确回「执事只能在自己领域内派活」 |
| 普通执事（无 domain） | 任意 | 原样（他没有分管身份，等同主人会话） |

理由：

- 执事本来就是该领域的负责人，再起一个"分管宰相"是同一身份跑两遍；
- `managers:false` 是 chancellor 已有的硬开关（`src/index.ts:161`），递归在参数层断掉，不需要改跨仓契约；
- 保留 `domain` 让任务单仍能标出"这活是哪个执事派的"，任务中心不掉信息。

**回滚**：`MINISTER_DIRECT_DISPATCH=false` → 一律回到"注入身份 + 走分管路径"的旧行为（一行 env）。

**明确不做**：

- 不做"执事再建执事"（`partner_manage` 已拒，且新路由不允许跨领域）；
- 不做执事之间的消息通道（cindy 的 `send_to_agent`）。那是另一种形态，需要防循环上限与独立存储，单独立项；
- 不改 chancellor 仓库。

## 五、已知边界（登记，避免被当成缺失）

- 前端普通 Enter 仍走**本地内存队列**（刷新即丢），本次只加插话快速路；持久队列另立方案。
- 插话落进当前轮后，UI 上不新开气泡：它属于同一轮，正文按段追加，用空行分隔。
- 执事直派只在**本机**生效；远程锚点会话本来就不装配身份缝，行为不变。
