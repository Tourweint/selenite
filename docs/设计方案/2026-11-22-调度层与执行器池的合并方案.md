## 零、人话版

把派活想成一家饭馆：

- **执行器池** = 后厨的 4 口锅。锅已经有了，一个锅同一时间只炒一盘菜，炒完接着炒下一盘；
  菜谱、灶台、油烟机（任务上下文、工具白名单、模型路由）也都配好了。
- **调度层** = 前台。现在还没有前台：
  - 客人直接冲进后厨，谁先到谁占锅；
  - 排队看不见，等 10 分钟没锅就自动把菜退掉（`no_idle_slot`）；
  - 取消只能停旧后厨（native），停不了新后厨（pool）；
  - 客人在半路提要求（steer/上报答复），只送得到旧后厨；
  - 一道菜炒糊了（429/断网/池进程崩），不会自动重炒，要人再点一次。

所以合并方案不是“再做一个池”，而是：**把前台补上，让后厨只管炒菜。**

## 一、两个东西各是什么

| | 执行器池（已落地） | 调度层（待落地） |
|---|---|---|
| 管什么 | **执行容器**：进程复用、内存回收、任务上下文、工具白名单、HTTP/SSE 通道 | **业务秩序**：谁先跑、同时跑几个、怎么排队、失败怎么重试、怎么取消 |
| 单位 | 池进程（锅） | ticket / task（菜） |
| 状态 | 槽位、PID、RSS、运行票、finishedTickets | 排队位置、车道占用、尝试次数、冷却截止时间 |
| 持久化 | 进程内队列 + supervisor 绑定表（重启即失） | ticket.json / inflight / 回执（durable，重启可恢复） |
| 失败半径 | 一个池进程崩 = 当前一票 | 一张票失败 = 这张票，不影响别人 |

**一句话：池是“怎么执行”，调度是“该不该现在执行”。**

来自 2026-11-22 的变更记录，代码在 `ts/apps/server/src/pool/`：

- `SUPERVISOR_POOL_SIZE=4` 个常驻进程，每个进程同一时刻只跑一票（`supervisor-core.ts`、`pool-main.ts`）。
- 已搬进池：任务上下文装配、工具白名单（read/write/edit/bash/escalate）、路径守卫、
  压缩 70%、回合上限、防打转、bash 超时、续行预算、上报等待（`task-profile.ts`、`pool-tools.ts`、
  `pool-settings.ts`、`pool-main.ts`）。
- 通道：`/run`、`/run/:id/events`、`/say`、`/abort`、`/health`（`pool-server.ts`），
  宿主侧 supervisor 负责起停/健康/回收/观测 jsonl（`supervisor.ts`）。
- 真模型双跑质量一致；pool 冷启动慢约 3s；全量单测 1256 绿。

**这些是池专属资产，调度层一律不碰。**

## 三、池还没做、但调度层需要的（本次重点）

| # | 现状 | 后果 |
|---|---|---|
| P1 | **取消没接 pool**：`cancelTicketAction` 只调 `abortNativeWorker`（`delegation-actions.ts:123`），supervisor 明明有 `abort()` | 池里的 worker 取消后继续跑，作废单还可能合并产物 |
| P2 | **插话/上报答复没接 pool**：`forwardWorkerMessageAction` 只走 native stdin；pool 明明有 `/say` | 任务详情里 steer 报 `worker_not_running`；worker 上报后，答复送不回去 |
| P3 | **async 模式不传 signal**：`tools.ts:1250` 只在非 async 时传 `context.abortSignal` | 即使接了 `/abort`，scheduler 也不知道这票被取消，仍会合并 |
| P4 | **池没有单票超时**：native/外部 CLI 有 `WORKER_TIMEOUT_MS=10min`，池没有；`pool-main` 只有回合上限/防打转 | 一票可以跑很久；`timedOut` 永远 false |
| P5 | **等槽位是隐形的**：`supervisor.run` 最多等 10 分钟（`IDLE_WAIT_LIMIT_MS`），超时返回 `no_idle_slot` | 任务显示“running”其实在排队；10 分钟后直接失败，没有排队位置/优先级 |
| P6 | **池崩了不重派**：SSE 断了就返回 `pool_crashed`/`stream_closed`，没有 supervisor 重派 | 和池方案 §4.5「按票重派」不一致；一张票直接失败 |
| P7 | **manager 不在池里**：managed 路径仍起 manager 子进程，child ticket 在 manager 进程里回落 native | 池的 4 口锅管不到 manager 路径；并发上限不是“一个数” |
| P8 | **等待上报不让位**：池方案 §3.6 的“等答复时释放槽位”没做 | worker 等人时仍占着一口锅，30 票场景会排队 |

## 四、对比：哪些可以共用，哪些只能各管各的

### 4.1 可以共用的（必须只有一份）

| 能力 | 共用口径 | 落点 |
|---|---|---|
| 并发容量 | **池大小 = native 车道容量**（默认 4）；调度层不再另发明一个 native 并发数 | `SUPERVISOR_POOL_SIZE` 被调度层读取 |
| 控制面 | `abort(ticketId)` / `say(ticketId, text, mode)` 对 native / pool / 外部 CLI 统一形状 | 宿主新增 `worker-control` 桥 |
| 错误分类 | `aborted` / `permission` / `pool_crashed` / `stream_closed` / `no_idle_slot` / `timeout` 等枚举，两边同一套语义 | chancellor 的 `FailureClass` |
| 状态投影 | 调度层状态里带池的 `running / slots / rss`；池的 `/health` 不重复做业务队列 | `GET /api/v1/scheduler` |
| 任务身份 | `ticketId + seq` 是唯一键；池的 `ticketId` 与 chancellor 同源（`ticketIdOfTask`） | 已有 |
| 取消语义 | 取消 = 停执行 + 不合并 + 释放槽位；两边都按这个口径 | 宿主 + scheduler |
| 重试边界 | 池只负责“执行一次”；重试由调度层决定并重新投递（attempt 递增） | 调度层 |

### 4.2 只适合池的（调度层不要学）

- 进程常驻、串行复用、冷启动遮罩、RSS/票数回收（`recycleReason`）。
- 每池一份 SQLite、Harness 装配、任务 profile、工具白名单、路径守卫闭包（`currentDirs()`）。
- 每票事件环形缓冲、SSE 回放、`/health`、`/say`、`/abort` 的传输实现。
- 池进程的父进程轮询/孤儿自退。
- 模型路由 `modelRoute`、供应商 key 只传变量名。

**理由**：这些是“锅和灶”的细节，调度层只需要知道“有几口锅、哪口空着、这票熟了没有”。

### 4.3 只适合调度层的（池不要学）

- ticket 准入、优先级、公平性、同领域串行。
- 外部 CLI 的车道帽（Claude/Codex/OpenCode 不进池）。
- 失败分类、退避、额度冷却、熔断、attempt 链。
- 队列位置/等待原因/队列上限/拒绝策略。
- 跨执行器的取消与超时策略。
- 任务级 worktree/租约/合并/越权检查（这些在 chancellor，不在池）。
- 观测指标：queue wait、lane 利用率、重试分布。

**理由**：这些是“前台怎么排号”的规则；池只该回答“我现在能不能接一票”。

### 4.4 只适合其中一个、不要硬搬的竞品做法

| 竞品做法 | 适合谁 | 为什么 |
|---|---|---|
| t3code 每 thread 只 1 个 active run | 调度层的**会话**，不是 ticket | 我们的 ticket 内部本来就要 3 个 task 并行；串行的是会话轮次，不是整张单 |
| orca 一个 Task 只 1 个 active Dispatch + `--retry-of` | 调度层 | 防同一 task 并发重试；池不需要知道 attempt 链 |
| orca 3 次失败熔断 | 调度层的**车道** | 池进程崩是执行容器问题，不是模型/CLI 额度问题 |
| vibe “一 workspace 一执行进程” | 调度层的**项目 git 锁**，不是全局并发 | 我们允许多 worktree 并行；要串行的是 merge/add/remove 这些 git 元数据操作 |
| t3code 队列 reorder/edit/hold | 调度层 | 需要用户可见的队列；池的队列是技术缓冲 |
| omnara wakeup + 租约 + SKIP LOCKED | 多机调度才需要 | 单机文件/内存足够；设备矩阵另说 |
| claude-squad tmux/PTY/屏抓 | 谁都不适合 | 非交互已经能跑 |

## 五、合并设计

### 5.1 队列归属：调度层是唯一业务队列

```text
ticket 准入（调度层，宿主/chancellor）
  → task 车道（调度层，按执行器）
      → native 车道：容量 = SUPERVISOR_POOL_SIZE
          → pool 的 supervisor.run（只负责找一口空锅）
              → 池进程的 RunQueue（只做单进程事件/重复/abort 缓冲，不是业务队列）
      → 外部 CLI 车道：容量 = CHANCELLOR_LANE_CAPS
```

- **不允许**“池里排一次、调度层再排一次”。池的 `RunQueue` 只保留每进程长度 1 的技术缓冲；
  业务排队全部在调度层，位置可见、可取消、有优先级。
- `supervisor.run` 的 10 分钟等待保留为**兜底**；调度层的 native 车道帽 = 池大小，
  正常情况下不会有超过池大小的 `run` 同时进入，等待只发生在回收/崩溃的瞬间。

### 5.2 容量口径

- native 车道：`SUPERVISOR_POOL_SIZE`（默认 4），不再单独配 `native:2`。
- 单票 task 并行：`MAX_PARALLEL_TASKS=3` 不变；一张票最多占 3 口锅，剩下一口给别的票。
- ticket 准入：`CHANCELLOR_MAX_ACTIVE_TICKETS=3`（含 managed/direct）。
- 同领域：`CHANCELLOR_MAX_ACTIVE_PER_DOMAIN=1`。
- 外部 CLI：`claude-code=2`、`codex=2`、`opencode=1`、`phone=1`、`mcp=1`。
- manager 路径：`CHANCELLOR_MANAGER_MAX_ACTIVE_TICKETS=1`（manager 子进程内），
  外加同领域串行；manager 未进池，child ticket 回落 native 时仍受该进程的车道帽约束。

### 5.3 统一控制面（M0 先做，属于补洞不是新功能）

宿主新增一个 `worker-control` 桥，按 `ticket.employee` 分派：

```ts
abortWorker(ticketId): Promise<{ok, message?}>
  - pool     → workerPool.abort(ticketId)
  - native   → abortNativeWorker(ticketId)
  - 外部 CLI → 进程注册表 killTree（新增）
  - 其它     → {ok:false, message:"该执行器不支持中止"}

sayWorker(ticketId, text, mode): Promise<{ok, message?}>
  - pool     → workerPool.say(ticketId, text, mode)
  - native   → forwardNativeWorkerMessage(...)
  - 外部 CLI → {ok:false, message:"外部 CLI 没有注入口"}（如实说）
```

- `cancelTicketAction` 改调 `abortWorker`；`answerEscalation` / `forwardWorkerMessageAction`
  改调 `sayWorker`。
- async 模式为每张 ticket 建独立 `AbortController`，传进 `runChancellor`；
  这个 signal 只由取消触发，不跟聊天轮次结束挂钩。
- pool employee 把 `reason==="aborted"` 映射成 `aborted:true`；`executeTask` 在合并前检查
  `run.aborted || signal.aborted`，**取消/超时不合并**，保留 worktree。

### 5.4 超时与失败分类

- 池补单票超时：空闲 `CHANCELLOR_WORKER_IDLE_MS=10min` + 最大 `CHANCELLOR_WORKER_MAX_MS=60min`
  （0=不限）。执行位置：supervisor 看 SSE 事件间隔（有 progress 就重置），
  或 pool-main 自己的 watchdog；两者只做一处，建议 pool-main（更靠近 worker）。
- 失败分类统一放在 chancellor（纯函数），池只上报原因字符串：
  - 可重试：`pool_crashed`、`stream_closed`、`no_idle_slot`、`timeout`、`transient`
  - 冷却：`usage_limit`、`rate_limit`
  - 不重试：`aborted`、`permission`、`unauthorized_write`、`merge_conflict`、`report_missing`
- 池进程崩：**调度层重试**（attempt+1，重新投递）；池不自己偷偷重跑，避免 attempt 账
  和 worktree 状态对不上。
- `no_idle_slot` 不再直接判失败：调度层把它当“车道忙”，重新入队并显示等待原因。

### 5.5 观测

- `GET /api/v1/scheduler` 返回：
  - ticket 队列：排队位置、优先级、等待原因；
  - 车道：`native`（容量=池大小、running、queued、cooldown）、各外部 CLI；
  - 池：复用 `workerPool.snapshot()` 的 slots/running/rss。
- 任务中心头部：`在跑 N / 排队 M`；单卡显示“等池槽位 / 等 claude 槽位 / 额度冷却到 X”。
- `.data/scheduler.jsonl` 记 queue/start/settle/retry/cooldown；池的 `worker-pool.jsonl` 保留，
  两者用 `ticketId` 能对上，不合并成一份（职责不同）。

## 六、分期

| 阶段 | 内容 | 规模 | 回滚 |
|---|---|---|---|
| **M0** | 补洞：worker-control 桥（abort/say 接 pool）、async signal、取消不合并、pool aborted 映射 | S-M | `CHANCELLOR_EMPLOYEE=native` 可回旧执行器；桥按 employee 分支，旧路径不变 |
| **M1** | 调度层：ticket 准入 + 同领域串行 + native 车道=池大小 + 外部 CLI 车道 + 队列可见 | M | `CHANCELLOR_SCHEDULER=false`；上限调大即退回无闸 |
| **M2** | 池对齐：单票超时、崩溃/等槽重试、`no_idle_slot` 入队、池状态接入 scheduler | M | 超时/重试各自 env 关 |
| **M3** | Attempt/失败分类/退避/额度冷却/车道熔断 | L | `CHANCELLOR_RETRY_ENABLED=false` |
| **M4** | 可选：等待上报让位、manager 进池、worktree 预热、设备矩阵队列深度 | M | 各自开关 |

**顺序理由**：M0 不做，默认池在“取消/插话/上报答复”三条路上比 native 还差；
M1 不做，池的 4 口锅会被无限多 ticket 同时敲门；M2 不做，池崩/等槽会直接判失败；
M3 最后做，因为它依赖稳定的 attempt 和失败分类。

## 七、明确不做

- 不在池里做业务队列/优先级/重试（池只做执行容器）。
- 不在调度层重做进程复用/上下文装配/工具白名单（池已经做了）。
- 不把 manager 立刻塞进池（M4 可选；先用同领域串行 + 每领域 1 票兜住）。
- 不做跨机分布式调度（设备矩阵是另一条线）。
- 不做抢占式调度（不暂停正在跑的票）。
- 不新增 `queued` 对外状态；排队先走 `message`/`lastAction`，要结构化再加可选字段。
- 不抄 t3code 的每 thread 单 active run、orca 的自动 fan-out、vibe 的整 workspace 串行。

## 八、验收

1. **M0 取消**：池里跑一票 60s 的任务，取消后 5s 内 `/health.activeTicket` 变空、
   `REPORT` 不再写、项目目录没有该票改动、worktree 保留。
2. **M0 插话**：池里跑动中，任务详情发 steer，worker 下一轮上下文里能看到；上报答复能回投并续跑。
3. **M1 准入**：连派 8 单，任务中心显示「在跑 3 / 排队 5」；池的 4 个槽位不被单票占满；
   同领域两单只有一个 manager 进程。
4. **M1 外部 CLI**：`claude-code` 车道帽设 1，同票 3 个 task 同时就绪时只有一个 claude 子进程。
5. **M2 池崩**：kill 一个池进程，正在跑的票自动重试一次并最终结算；`no_idle_slot` 不再直接 failed。
6. **M2 超时**：池内静默 10 分钟被杀；持续有 progress 的 20 分钟任务不被误杀。
7. **M3 额度**：mock 429 带 reset，车道冷却、到点自动续跑（若开关开）；权限拒绝不重试。
8. **回归**：`CHANCELLOR_EMPLOYEE=native` 时全部行为与切池前一致。
