# 归档模块：会话与项目目录统一归档

日期：2026-11-12
状态：**已落地（2026-11-13）**。下沉落点：契约 → `docs/基线文档/接口文档.md` §2.5 / §2.7 / §5；
字段与数据流 → `docs/基线文档/系统架构.md`；落地细节 → `docs/变更记录/2026-11-13-归档模块（会话与项目目录统一归档）.md`。
与长期文档冲突时，以长期文档为准。

## 起因

用户口径（2026-11-12）：

- 优化归档功能，把已删除的都改成归档，做一个**归档模块**；项目目录（子项目目录）的退场也叫归档。
- 归档界面要能看到"没什么用的对话"。
- 把已删除的**字段**都改掉。
- 没有删除按钮，只有归档；删除只是标记，不物理删（上一轮已拍板）。
- 上一轮遗留：移除项目时把项目内所有对话放进已归档（当时普通会话没有项目归属，没做成）。

本篇**覆盖** `2026-11-12-项目多根模型（工作区与项目平级）` 的第 5、6 条：
上一版定的是"目录叫移除、会话叫归档"，现在统一成"两者都叫归档"。

## 现状审计（2026-11-12）

| 对象 | 现在的状态字段 | 现在的界面词 | 现在的接口 |
|---|---|---|---|
| 普通会话 | `.data/chat-meta.json` 的 `hidden: string[]` | 归档（悬停图标）/ 已归档的会话 | `POST /agent/chat/:id/hide`、`POST /agent/chats/restore` |
| 项目登记 | `projects.sqlite` 的 `archived`（已有） | 移除 / 已移除 | `POST /projects/:id/remove`、`/restore`（`/archive` `/unarchive` 是别名） |
| 执事 | `partners.status = archived`（已有） | 暂停 / 恢复 | 不在此次范围 |
| 技能 / 记忆 / 供应商 / 例行任务 / 群 / 设备 | 物理删除 | 删除 | 不在此次范围 |

关键事实：

- `GET /api/v1/agent/chats` 现在返回 `{chats, removed}`；手机端只读 `chats`，不读 `removed`，改名不会断手机。
- 普通会话创建时**不记录项目**；只有派活回执 / 任务单带 `projectId`。所以"项目内所有对话"在旧数据里不存在归属关系。
- 侧栏"最近会话"里的是普通会话（`chatKind=worker`）；`chief` 是总管会话，`partner-` 前缀是执事/群会话，`task-` 前缀是任务会话，它们都不该被"项目归档"连带。

## 决策

### 1. 归档 = 软退场唯一说法

会话和项目登记都用「归档」：对象从活跃列表里收起，正文 / 记忆 / 磁盘目录 / 历史任务全部保留，可恢复。
界面不再用「已移除」作为状态词；「从列表里移除」只作为效果描述出现在解释里。

**归档永不物理删除**。归档模块里也不放「永久删除」按钮（用户明确：没有删除按钮，只有归档）。
代价（如实登记）：归档会一直留着，磁盘占用只增不减；将来要清理，必须另立"彻底删除"方案。

### 2. 归档模块 = 设置 → 归档

在设置左栏新增一个分区「归档」（`#/settings/archive`），集中管理两类对象：

- **已归档的会话**：标题 / 首句、轮数、最后一句时间、项目标签、归档时间；
  支持按标题/首句筛选、单条恢复、全部恢复。
- **已归档的项目目录**：名称、路径、目录是否还在、恢复；明确写"磁盘上的目录和文件一直没动"。

设置 → 会话、设置 → 项目只保留入口（"打开归档" / "查看归档"），不再各自维护折叠区。
项目页的「已移除」`<details>` 折叠区整体移入归档模块。

### 3. 会话字段统一为 `archived`

| 现名 | 新名 | 位置 |
|---|---|---|
| `chat-meta.json.hidden` | `archived` | `.data/chat-meta.json` |
| `chatMetaSummary().hidden` | `archived` | `agent/session.ts` |
| `hideChat()` | `archiveChat()` | `agent/session.ts` |
| `GET /agent/chats` 的 `removed` | `archived`（计数） | 接口响应 |
| `POST /agent/chat/:id/hide` | `POST /agent/chat/:id/archive` | 接口（`/hide` 保留兼容别名） |
| `state.removed` | `state.archived` | `web/app.js` |
| CSS `.is-removed` | `.is-archived` | `web/style.css` |
| 界面「已移除」 | 「已归档」 | `web/app.js` |
| `confirmRemoveProject()` | `confirmArchiveProject()` | `web/app.js` |

新增：

- `chat-meta.json.archivedAt: Record<string, number>`：归档时间，归档页按它倒序；旧数据没有就回退到最后一句时间。
- `POST /agent/chat/:id/unarchive`：单条恢复（幂等；不在归档里也返回 ok）。
- `GET /agent/chats/archived?limit=200`：归档会话清单，含 `archivedAt` / `projectId?` / `projectName?`。
  实现按 `chat-meta.archived` 的 id 反查，不用 `listChats` 的 `limit` 截断——归档的多是旧会话，截断会漏。

### 4. 项目动作改名「归档项目」

- `POST /api/v1/projects/:id/archive` 成为界面主入口；旧 `/remove` 保留兼容别名。
- `POST /api/v1/projects/:id/restore` 不变；`/unarchive` 保留别名。
- 项目页动作：`改名` / `归档`；确认弹窗标题「归档项目」，
  说明：从项目列表和派活选择里收起、磁盘不动、历史任务/会话都在、之后可在「归档」里恢复。
- 项目归档后 `archived=1`（字段本来就叫这个，不改库结构）；当前项目指针清空（既有行为）。

### 5. 项目归档连带归档"这个项目下新建的普通会话"

这是上一轮没做成的那半件。做法：

- 新增 durable doc `lifediary.chat-projects`，`{byInternal: Record<internalId, projectId>}`。
  与 `ChatKinds` 同层、同 scope（session），缺项 = 旧会话，没有归属。
- 新建**普通会话**（`chatKind=worker`）时，如果当前项目存在，在同一 init 事务里记 `projectId`。
  执事/群（`partner-` 前缀）、任务（`task-` 前缀）、OpenAI 兼容自动建会话不记。
- 项目归档成功后，按映射把对应会话批量置归档，接口返回 `archivedChats: N`。
- **旧会话不回溯**：没有归属记录就不猜。弹窗如实写"这个项目下新建的会话会一起归档；更早的会话没有项目归属，仍留在列表里"。
- **恢复项目不自动恢复会话**：归档是独立动作，用户可在归档页单条/全部恢复。项目恢复只恢复登记。

### 6. 只归档软对象，硬删除保留「删除」

技能、记忆、供应商、例行任务、群、设备、搜索源仍是**物理删除**，保留「删除」字样和确认。
理由：归档的承诺是"数据还在、可恢复"；把这些硬删叫归档就是撒谎。归档模块只收会话和项目目录。

### 7. `diary.deleted` 不改名

它是手机 ↔ 服务端同步协议的墓碑字段（表示上游把这条日记删了），不是用户的归档动作；
跨仓库契约，改名会断手机端。保留原字段名，也不进归档模块。

### 8. 回滚

- `PROJECT_ARCHIVE_CHATS=false`：关闭第 5 条连带归档，项目归档只改登记位（回到 2026-11-12 之前的行为）。
- `chat-meta.json` 读兼容 `hidden`，首次写入落新键并丢掉旧键；回滚代码仍能读。
- 旧接口 `/hide`、`/remove`、`/archive`、`/unarchive` 保留别名，旧客户端不 404。
- 归档模块本身是既有会话归档能力的可视化，不单独设开关。

## 契约变化（实施后下沉到接口文档）

| 端点 | 变化 |
|---|---|
| `GET /api/v1/agent/chats` | `{chats, removed}` → `{chats, archived}`（计数）；手机端不读旧字段，已核对 |
| `GET /api/v1/agent/chats/archived` | 新增；`?limit=200`，返回 `{chats, total}` |
| `POST /api/v1/agent/chat/:id/archive` | 新增主入口；`/hide` 保留别名 |
| `POST /api/v1/agent/chat/:id/unarchive` | 新增单条恢复 |
| `POST /api/v1/agent/chats/restore` | 不变；仍是全部恢复 → `{ok, restored}` |
| `POST /api/v1/projects/:id/archive` | 升为主入口（原来只是别名）；响应加 `archivedChats` |
| `POST /api/v1/projects/:id/remove` | 保留兼容别名，语义同 archive |
| `POST /api/v1/projects/:id/restore` | 不变；不恢复会话 |
| `GET /api/v1/projects?includeArchived=1` | 不变，归档页复用 |

`ChatIndexEntry` 增量字段：`archived?: boolean`、`archivedAt?: number`、`projectId?: string`、`projectName?: string`。
只在归档清单里保证有 `archivedAt`；活跃清单不改变现有字段。

## 数据与迁移

`chat-meta.json`：

```jsonc
// 旧
{ "titles": {}, "hidden": ["uuid"], "pins": [] }
// 新
{ "titles": {}, "archived": ["uuid"], "archivedAt": { "uuid": 1762900000000 }, "pins": [] }
```

- 读：`parsed.archived ?? parsed.hidden ?? []`；`archivedAt` 缺省 `{}`。
- 写：只写 `archived` / `archivedAt`，不再写 `hidden`。
- `archiveChat(id, at = Date.now())`：加入并记时间（重复归档更新时间）。
- `unarchiveChat(id)`：移除并删时间。
- `restoreArchivedChats()`：清空两组，返回条数。
- `chatMetaSummary()`：`{ archived: number }`。

`chat-projects` durable doc：

```ts
{ byInternal: Record<string, string> } // internalId -> project uuid
```

- 只在 `openChat` 新建普通会话（`kind === "worker"`）且 `projectsStore().getCurrentProject()` 非空时写。
- `openOrCreateChat`（群成员 / OpenAI 兼容）不写，避免把群会话算进项目。
- 项目改名不影响（存 id）；项目硬删除（`DELETE`，界面不用）留下悬空 id，归档页查不到项目名就不显示项目标签。

不新增 SQLite 表 / 列；`projects.archived` 已存在。

## 界面

- `SETTINGS_SECTIONS` 新增 `{ id: "archive", label: "归档", icon: 归档箱 }`，排在「项目」后面。
- 归档页两张卡：
  - 已归档的会话：标题/首句、`N 轮 · 最后一句 时间`、项目标签、归档时间；
    顶部筛选框 + 「全部恢复」；行内「恢复」；空态说明入口。
  - 已归档的项目目录：复用项目卡片（归档态只读路径 + 「恢复」），空态说明。
- 设置 → 会话：原来的「已归档的会话 N [恢复]」行改成「归档的会话 N [打开归档]」。
- 设置 → 项目：只渲染活跃项目；底部一行「已归档的项目目录（N）[查看归档]」；
  项目行动作「改名 / 归档」。
- 侧栏会话悬停图标仍叫「归档」，请求改 `/archive`；从归档页恢复后 toast「已恢复到列表」。
- 不把归档入口塞进侧栏轨道：设置左栏已经是常驻导航，避免再多一个一级入口。

## 备选与为什么不选

| 备选 | 为什么不选 |
|---|---|
| 所有「删除」都改成归档 | 技能/记忆/供应商等是物理删除，叫归档会承诺"可恢复"却做不到；只统一软对象。 |
| 项目继续叫「移除」 | 用户这次明确要求"把已删除的都改成归档"，两个词并存正是要消掉的歧义。 |
| 项目归档时按目录/时间猜旧会话归属 | 猜错会把无关会话一起归档；只认创建时记下的 `projectId`，旧数据如实不回溯。 |
| 恢复项目时自动恢复它的会话 | 用户可能只想恢复项目登记；会话归档是独立动作，自动恢复会让归档页"自己变空"。 |
| 归档页做成侧栏一级入口 | 设置左栏已是常驻导航；归档是低频清理动作，放设置里够用，避免一级栏继续膨胀。 |
| 归档里提供「永久删除」 | 用户明确"没有删除按钮，只有归档"；真删必须另立方案。 |
| 把 `diary.deleted` 改名 `archived` | 跨仓库同步协议，且语义是"上游墓碑"不是用户归档；改名会断手机端。 |

## 安全与回滚

- 归档不改变鉴权：归档会话正文仍可按 id 读取，但不出现在活跃列表；设备令牌权限不变。
- 项目归档后立即从 `workspaceRootsReal()` 消失，路径守卫边界随之收窄（既有行为，不是新增风险）。
- 项目连带归档只写 `chat-meta.json`，不碰 durable 会话正文、不碰磁盘。
- 回滚开关 `PROJECT_ARCHIVE_CHATS=false`；chat-meta 新键读旧键兼容；旧端点别名保留。
- 迁移只在首次写入时发生，读路径永不丢数据；`hidden` 键在写入后消失，不回写旧键。

## 明确不做

- 不做硬删除对象的归档化（技能 / 记忆 / 供应商 / 例行任务 / 群 / 设备 / 搜索源）。
- 不做归档对象的永久删除 / 清空 / 自动过期。
- 不做旧会话的项目归属回溯或按目录猜测。
- 不做项目恢复时连带恢复会话。
- 不做 `diary.deleted` 字段改名。
- 不做执事归档页（执事已有 active/paused/archived 状态，另立项）。
- 不改审批、派单、路径守卫的权限模型。

- `pnpm --filter @lifediary/server http` 端到端全绿；新增 §14.7 覆盖：
  `GET /agent/chats` 不再返回 `removed`、`/archive` 主入口、`/hide` 别名、`/unarchive` 单条恢复、
  `/chats/archived` 清单与 `archivedAt`、项目归档 `archivedChats>=1`、恢复项目不恢复会话。
- 编辑重发的 fork 也继承原会话的项目归属（实现时补上；否则项目归档会漏掉分叉出的新会话）。
- `archivedChats` 是"按归属表命中的条数"，重复归档已归档的会话也会计数；它表示"这些会话在归档里"，
  不承诺"本次新归档了 N 条"。
- 项目归档的连带动作失败只记服务端日志、返回 `archivedChats:0`，不回滚项目登记（主动作已成功）。
- `GET /agent/chats/archived` 的 `total` 取 chat-meta 归档计数；若手工写入不存在的 id，`total`
  可能大于可解析的 `chats` 条数（文档已写明口径）。
- 旧会话没有项目归属，项目归档不会连带它们；这是设计取舍，不是遗漏。
- 硬删除对象（技能 / 记忆 / 供应商 / 例行任务 / 群 / 设备 / 搜索源）仍叫「删除」；
  `diary.deleted` 保留原名（跨仓库墓碑字段）。
- 未跑 `pnpm probe`：本次不动内核提交 / 流式 / 闸门，语义由 http 探针与单测覆盖（如实记录）。
