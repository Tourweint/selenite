## 背景

2026-11-07 的 `web_search` 只接一家：DeepSeek `POST /v1/tools/search`，key 只有一个
`DEEPSEEK_SEARCH_API_KEY`，配置入口在「设置 → 服务 → 搜索」。用户当日提出：

1. 搜索 key 也要放到「设置 → 模型」页（供应商旁边），因为那才是配上游的地方；
2. 服务页那张卡解释性文字太多，课题相关文案也可以去掉；
3. 多接几家搜索源，点名百度搜索、元宝搜索、Tavily、Exa（语音里的「REX」按 Exa 理解）。

## 决策

### D1 配置入口搬到「设置 → 模型 → 搜索」

- 模型页新增一节「搜索源」：添加 / 填 Key / 测试 / 移除 / 上下移；
- 「设置 → 服务 → 搜索」整卡删除，不做两处重复入口；
- 服务页因此只留服务自身状态与开关（地址 / 通知 / 鉴权 / 用量 / 运行时 / 高级开关）。

### D2 多源 = 有序列表 + 失败/零命中回退

- 源清单落 `.data/search.json`：只存 `vendor`、顺序、可选地址覆盖；
  **不存 key**——key 仍落 `.data/provider-keys.json`，按各源 `keyEnv` 取 env。
- 一个搜索按列表顺序问源；上游报错或合法零命中就试下一个；第一个有结果的生效。
  这样某家额度用完 / 网络抖一下时，研究回合不会整轮空转。
- `searchConfigured()` 的判据改为「至少一个源可用」：需要 key 的有 key、需要地址的有地址。

### D3 源目录与适配

`search-vendors.ts` 一家一个 `SearchVendor`（id / name / keyEnv / 默认地址 / 拿 key 的地址 /
是否需要地址 / query 字数上限）+ 请求与回包映射。首批 10 家：

| id | 名称 | 认证 | 备注 |
|---|---|---|---|
| `deepseek` | DeepSeek | Bearer | 原有 `/v1/tools/search` |
| `tavily` | Tavily | Bearer | 英文资料强 |
| `exa` | Exa | `x-api-key` | 语义检索 |
| `baidu` | 百度搜索 | Bearer | 千帆 `/v2/ai_search/web_search` |
| `yuanbao` | 元宝搜索 | Bearer | 腾讯云 WSA `/SearchPro` |
| `brave` | Brave Search | `X-Subscription-Token` | |
| `firecrawl` | Firecrawl | Bearer | `/v2/search` |
| `doubao` | 豆包搜索 | Bearer | 火山引擎 `/search_api/web_search` |
| `tinyfish` | TinyFish | `X-API-Key` | 根路径 GET |
| `searxng` | SearXNG | 可选 Bearer | 自建，必须给地址 |

- 云厂商把错误放在 200 回包里的（元宝 `Response.Error`、豆包 `ResponseMetadata.Error`），
  先判错误再读结果；只回稳定说明（key 被拒 / 额度不足 / 太频繁），不贴回包原文。
- 所有请求 20s 超时；不跟跨站重定向（避免把 key 带去别处）。
- 回包防御式读取：缺字段当空串，URL 为空的行丢掉；不是数组 = `bad_response`，
  空数组 = 合法零命中（继续试下一个源）。

### D4 兼容与回滚

- 没有 `.data/search.json` 时，从 env 里的 key 反推源：`DEEPSEEK_SEARCH_API_KEY` 继续有效，
  其他 `*_API_KEY` 也一样生效（手写 .env 的旧习惯不打断）。
- 有 `search.json` 时以文件为准；显式清空后不会偷偷从 env 加回来。
- 旧 GET/PUT/DELETE 形状保持：`keyEnv` / `hasKey` 仍在；不传 `vendor` 一律按 `deepseek`。
- 回滚开关 `SEARCH_MULTI_VENDOR=false`（或 `0`/`off`）：只读 deepseek 一条源，
  目录只剩 DeepSeek，PUT 其他源返回 `multi_vendor_disabled`。旧 key 照旧可用。

### D5 文案收短

- 服务页旧卡「搜索（课题研究用）」「DeepSeek 搜索，给长期课题的每周研究查资料用……」
  全部随卡片一起删除；
- 课题未配置提示从「去 设置 → 服务页 填 DEEPSEEK_SEARCH_API_KEY（可在 .env 直接写）」
  改成「去 设置 → 模型 → 搜索 添加一个搜索源」；
- 模型页搜索节只留一句 `data-tip`：「模型不能上网时，按列表顺序找搜索源；第一个有结果的生效。」

## 备选与取舍

- **只做单源选择器**（一个下拉 + 一个 key）：实现更小，但没有回退，某家挂了研究回合直接失败；
  用户点名「多一些供应商」，多源回退更贴近 magpie 的做法，故选有序多源。
- **key 也存 search.json**：文件简单，但会与现有 `.data/provider-keys.json` 两套密钥纪律分叉，
  且 `.env` 手写路径会失效；故 key 仍走 env / provider-keys。
- **引入第三方搜索 SDK / 插件系统**：10 家的请求形状都小且稳定，手写适配层更可控；
  magpie 的插件搜索 hook 属于另一个量级，本仓先不做。
- **给每家都做独立配置页**：没有必要；一行 = 一个源，够用。

## 明确不做

- 不做 key 轮换 / 额度统计 / 自动计费；
- 不做每家的代理、站点过滤、时间范围等高级参数（只保留「查什么、几条」）；
- 不做手机端搜索源配置（手机不配上游，沿用既有分工）；
- 不做搜索源插件 / 动态加载；新增一家 = 在 `SEARCH_VENDORS` 加一条 + 映射函数；
- 不做「模型自己上网」的供应商原生搜索，`web_search` 仍由本仓适配层回答；
- 不做搜索历史的持久化 / 去重 / 缓存。
