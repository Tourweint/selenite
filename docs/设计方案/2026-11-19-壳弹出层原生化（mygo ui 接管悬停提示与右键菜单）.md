# 壳弹出层原生化（mygo ui 接管悬停提示与右键菜单）

**状态：批1 已落地并真机验收（2026-11-19 当日）。验收记录见文末「八、落地后记」。**
**下沉落点：机制与坐标口径 → `desktop/popovers.go` 文头注释 + 本文；开关与回滚 → `desktop/README.md`；冲突以长期文档（本文下沉后的口径）为准。**

用户目标（2026-11-19）：「把前端部分组件换成 go，一些比较核心对性能要求比较高的，可以自己上网找资料 mygo」。即：桌面壳（MyGo）里把**性能敏感的前端组件**换成 Go 原生实现。这是 2026-11-10「壳原生化立项时再拿出来用」那笔账的立项时刻。

## 一、为什么是弹出层（候选怎么定的）

"性能要求高"的口径 = **对延迟与流畅敏感**，不是"代码多"。全应用触发频率最高、对帧延迟最敏感的组件是弹出层一族：

| 组件 | 现状（web 实现） | 痛点 |
|---|---|---|
| 悬停提示 `hover-tip.js`（580 行） | data-tip 属性 + 450ms 计时 + DOM 小黑签，挂 body 下 fixed 定位 | 每次都要建 DOM、量宽、防裁切；快速划过工具栏时与页面动画争主线程；视口边缘被裁 |
| 右键菜单族 `sec-menu.js` + `context-menu.js`（220+223 行） | `openMenuAt` / `openSecMenu` 自绘菜单，挂 body 躲 `overflow:hidden` | 同上；「同一颗 ⋯ 关不掉」这类关闭次序坑已经踩过一次（2026-11-14 实测） |
| 「挂 body 躲裁切」绕法 | hover-tip、sec-menu、执行器模型下拉三处重复同一种 workaround | web 弹层永远被父容器裁切问题追着走 |

**原生 flyout 正面解决这一类**：`mygo.NewFlyout` 是独立小窗，GPU 自绘（`package ui`），不进 WebView2 合成树；`Anchor` 锚到父窗口内容区任意矩形，**能伸出窗口边缘**（web 弹层永远做不到）；Windows 11 自动圆角 + 系统阴影 + 菜单式外点击关闭语义。

反过来，聊天流 / 主界面**不进**本方案：三端同源（web 三件套）是 2026-11-10 的定调，手机端是另一套 Compose，弹出层本来只存在于桌面壳——把它换掉不破坏"三端同源"，反而是壳原生能力（Dialog/托盘/剪贴板一族）的自然延伸。

## 二、路线对比与取舍

| 路线 | 判断 |
|---|---|
| **A. 原生 flyout（本次）** | 框架内建、坐标/关闭/翻转/越界全包；组件自包含、不动主界面；**选它** |
| B. Go WASM 进页面 | 主界面计算下沉；但本应用慢点在 DOM 布局不在纯计算，且 2–4MB wasm 与 js_bridge 往返延迟不划算。**不做** |
| C. 整窗原生（聊天界面用 `ui` 重写） | 破坏三端同源，工程量一个季度级。**不做** |
| D. lobe-mygo 组件库 | 70+ 组件是 Lobe 设计语言，与本应用"纸感宋体"设计体系对不上；且会引入第二个 UI 依赖。**批1 不引入**，组件膨胀后再评估（2026-11-10 记忆里的"拿出来用"先记着） |
| E. mygo 升级 0.7.3 → 0.10.x | **初判"另立项"，落地中翻案（见 §八）**：v0.7.3 的 FitContent 明文不支持原生 Content（`Native UI (Content) does not fit`），而批1 两个组件都靠 FitContent 定尺寸——升级成了批1 的硬前提。已升 v0.10.0：壳代码零改动编译通过，全套单测绿 |

资料来源：[MyGo 官网](https://mygo.egoist.dev)、[GitHub releases](https://github.com/egoist/mygo/releases)（v0.7 起有 flyout 相关迭代，0.9+ 无 Go API 破坏）、本机 `D:/Projects/reference/mygo`（v0.10 克隆）与模块缓存 `mygo@v0.7.3`（钉版实测）。

## 三、批1 范围（本次落地）

1. **悬停提示 → `Shell.ShowTip` / `Shell.HideTip`**
   - 非 Focusable flyout（不抢键盘、不自动关，由页面在 mouseout/click/scroll 时收——与现有 web 行为逐条对应）。
   - 配色照抄 web 版拍板（2026-11-14）：**固定黑底白字** `#191919` / `#f7f7f5`，不跟主题；`max-width 320`、padding 5×9、字号 12、多行（`pre-line` → Go 侧按 `\n` 拆行）。
   - 锚点：有鼠标落点 = 光标点（零尺寸矩形，`top-start`，Gap 10）；键盘聚焦 = 元素矩形（`top-start`，Gap 10）——与 `showHoverTip` 现行定位算法一致，翻转/夹边交给 flyout。
2. **右键菜单族 → `Shell.ShowMenu`（阻塞返回所选序号，-1 = 没选）**
   - 咽喉点只有两个：`openMenuAt`（光标菜单：输入框三件事、侧栏行菜单、选中文字复制）与 `openSecMenu`（分区头 ⋯）。分叉点各一处，浏览器/老壳走原 DOM 路径不动。
   - Focusable flyout：Windows 上外点击**只关菜单不穿透**（framework 文档明文），与系统菜单一致，天然解决"⋯ 再点一下关不掉"。
   - 菜单项支持 label / hint / kbd / danger / separator / disabled，配色按**壳记的五套主题**取值（与 `style-01-tokens.css` 逐值对齐）。
   - 顺手补缺：壳的 `themeKnown` 此前不认识 celadon（青瓷，2026-11-14 加的第五套）——存不了、也配不了色。本批补上（`themeKnown` + 菜单色板 + 启动页底色）。
3. **能力探测与回滚**
   - `Shell.Capabilities()` 返回 `{nativePopups: bool}`；页面启动时探一次缓存。普通浏览器（无 `window.mygo`）恒走 DOM；老壳（无此方法）调用 reject → 也走 DOM。
   - 回滚开关：`LIFEDIARY_NATIVE_POPOVERS=off` → Capabilities 返回 false → 页面全量回 DOM 旧路，**回滚不等于改代码**（AGENTS 硬约束）。`LIFEDIARY_SHELL_BINDINGS=off` 仍整组摘掉 Shell。

## 四、坐标与线程口径（写死，别再猜）

- **锚点单位 = 父窗口内容区 DIP**（framework 文档明文）。页面 CSS px × `ZoomFactor` = DIP；壳不设 `ZoomFactor`（生产构建下 WebView2 缩放键只在检查器开启时有效，日常恒 1）→ **CSS px : DIP = 1:1**。将来若给页面开缩放，`popovers.go` 的换算要跟着乘。
- Bind 方法在独立 goroutine 跑，窗口 API 内部汇入主线程车道——`ShowTip`/`ShowMenu` 里直接建 flyout，**不需要**再包 `RunOnMain`。
- `ShowMenu` 阻塞等待用户选择（framework 允许 Bind 方法阻塞）；页面拿到 Promise resolve 的序号后再跑本地闭包，业务闭包不过桥。

## 五、明确不做（本批）

- 主界面任何区域原生化（见路线 C）。
- `skill-picker` / `plus-menu` / 执行器模型下拉 / `approval-pop`（批2 候选，走同一条 `ShowMenu`/新 flyout 通道，无需再写方案）。
- 托盘面板 / 提醒通知原生窗（批3，涉及"壳不该碰业务"的边界讨论，单独拍板）。

## 八、落地后记（2026-11-19，真机踩出来的三条）

1. **升级翻案**：方案原写"升级另立项"。实现后真机首验发现 flyout 停在默认 200×200、黑签下面拖一块白——v0.7.3 的 `FitContent` 文档明文 "**Native UI (Content) does not fit**"（原生内容参与 FitContent 是后续版本 #1069 才补的）。给 flyout 定尺寸是批1 硬前提，自研像素测量（透明渲染量 bbox）能做但每个未来组件都得配合，脆；遂升 **v0.10.0**：壳零改动编译过、全套测试绿、`go.sum` 净增两个 indirect（`go-text/typesetting`、`golang.org/x/image`——壳首次直接 import `ui` 包带出来的）。教训记下：**"升级另立项"的判断要在立项时把依赖特性核对进方案，而不是留给实现期翻案。**
2. **背景必须画在 `c.Root()` 上**：画在 Column 上时，FitContent 量出的窗口与内容差的那几像素会露出 Win11 系统底板（菜单底部一条白）。照官方示例改 `c.Root().Background(...)` 后根治。
3. **`Shadow: false` 才干净**：flyout 开阴影时，Windows 的阴影辅助窗会在窗口下方露出一条内衬圆角矩形（v0.10.0 的渲染怪癖，克隆 v0.10.0-30 里也无修复）。两个弹出层都关了阴影——Win11 的圆角与描边仍在，观感可接受；框架后续版本若修了阴影再开回来。
