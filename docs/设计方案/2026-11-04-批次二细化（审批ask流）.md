## 〇、一句话

给权限系统加一根**独立的确认轴**：`policy.confirmWrites`（默认关）开启后，写类工具在执行前挂起一条可答复的审批——SSE `approval` 事件 + HTTP 答复端点 + 超时默认拒绝（fail-closed）+ 可"本会话记住"。契约纯增量。**明说边界：手机走 OpenAI 兼容层、没有答复通道，confirmWrites 属桌面/web 专属能力**（开启后手机触发的写工具会等到超时按拒绝处理，文档写明）。

## 二、服务端机制

1. **policy**：`PolicyState`（agent.ts:82-85）加 `confirmWrites: boolean`；`initialPolicy` 读 env `AGENT_CONFIRM_WRITES`（"1"/"true"）；`loadPolicy` **照现有惯例回落 env 初值**（`typeof parsed.confirmWrites === "boolean" ? parsed.confirmWrites : base.confirmWrites`——不得写死 false，否则老安装设了 env 也不生效，审查 S10）；`setPolicy` 透传；`GET/POST /policy`（index.ts:270-285）GET 返回、POST 接受可选布尔、access 三值校验原样。
2. **审批判定独立纯模块** `src/approval-policy.ts`（不 import agent.ts——它加载即建库，照 reliability.ts 先例）：`needsApproval(policy, tool, blockReason)`——blockReason 优先；未拦 && confirmWrites && `tool ∈ WRITE_TOOLS` → 需审批。单测断言矩阵：read-only 不问直接拒 / 关不问 / 黑名单不问 / delegate、propose_project 也问。
3. **审批 store** `src/approvals.ts`：`.data/approvals.json`（小状态文件，照 chat-meta.json 惯例）。API：`create`（返回含 `promise`）、`decide(callId, decision, remember)`（幂等：已决返回原决定不二次 resolve）、`expireAll(conversationId, status)`、`pendingOf(conversationId)`、`load()`。语义要点（审查建议 5）：**`load()` 必须在 `harness.resume()` 之前调**；启动加载时把遗留 pending 置 `timeout`（fail-closed，内核 resume 重走 beforeTool 会生成新审批）；`create` 对同 callId 的旧终态记录**覆盖重置**。
4. **beforeTool 接线**（agent.ts:454-481，bash 注入之后）：
   - `needsApproval` 命中 → create → 发 `approval` 事件 → `await` **Promise.race([promise, abortPromise])**（context.abortSignal 存在时挂上；abort → 按 `aborted` 结算，审查建议 1）→ 超时定时器 `AGENT_APPROVAL_TIMEOUT_S`（**默认 120**，审查建议 9；非法/0 → 120）→ 超时按 rejected 结算（status=timeout）。
   - **批准后复判**（审查建议 2）：`readOnlyBlockReason(tool)` 再判一次，被切档 → block。
   - **唯一出口**：批准后**不 return undefined，落到钩子末尾既有的 `return injected ? {arguments: injected} : undefined`**（审查 S1——提前 return 会把批次一的 bash 超时注入丢掉）；rejected/timeout/aborted → `return { block: 理由 }`（这是钩子内合法的提前退出，与注入无冲突）。
   - `remember: true` → 进程内 `Map<conversationId, Set<tool>>`（重启失效重批，注释写明）。
5. **透传链（审查 S2/S3，两处必改）**：
   - `delegation.ts:21-48` `DelegationEvent` 加 `approval` 成员，**模块头注释补一句"审批事件借道本通道，与派活语义无关"**；agent.ts `ChatStreamEvent` 镜像。
   - **`agent.ts:1245-1268` 的三元必须改成按 type 分发（switch/if）**——不改的话 approval 会以 attention 形状（ticketId=undefined）发出且 TS 不报错，审查 S3。
   - **`openai-compat.ts` 两个消费方**：流式分支（:427 一带）照 `lifediary_attention` 惯例透传为 `lifediary_approval` 非标字段；非流式分支（:391 一带）**忽略**（不注入正文）。接口文档写明手机不可答复。
   - `index.ts:406-418` 白名单加 `"approval"`。
6. **与 /stop、并行**：stopChat（:1328-1330）调 `expireAll(conversationId, "aborted")`；并行工具各自 callId 独立；审批等待不计 MAX_TURNS。

## 六、文档回写与不做

- 变更记录；调研方案 A1 标已落地；系统架构 D6 同步；`delegation.ts`/`接口文档` 手机端口径。
- **不做**：审批进日志；持久化"记住"；ASK 第四档（独立轴）；手机端 Kotlin 实现；"新消息到达即拒绝 pending"（审查建议 9 的备选，先不做，120s 超时+界面倒计时兜底，真实用起来痛再说）。
- **升级路径注记（2026-11-04 补，源自参考项目调研）**：本方案的等待形态是 **in-flight await**——
  审批挂着时那一轮、那个进程都停在 `Promise.race` 上，超时 fail-closed。它适合**分钟级**确认
  （人在屏幕前）。如果哪天要"等几小时后回来批"（人下班了、手机端离线），就该换另一形态：
  **等待态落库成一行记录（带会话 id），本轮正常收尾、零进程零 token；答复作为事件触发续跑**。
  那是另一套可靠性机制（续跑幂等、跨重启恢复），不能靠给本方案加长 `AGENT_APPROVAL_TIMEOUT_S` 凑合——
  超时拉长只会让"没人批时工具被白占一轮"更糟。触发条件：真实使用中出现"人不在场等审批"的场景。
