# 模型分工：规划模型与干活模型（2026-11-19）

**状态**：已落地（2026-11-19）；结论已下沉 `接口文档.md` §6 / `接口-端点7` §2.23 / `系统架构.md` D33。
**冲突口径**：落地后以 `docs/基线文档/接口文档.md` §6、`docs/基线文档/接口-端点7-权限技能与开关.md` §2.23、
`docs/基线文档/系统架构.md` D33 为准；本文保留"当时怎么想的"。

## 1. 背景

用户 2026-11-19 提出：

- 总管 / 写日记的执事这类"做规划"的对话需要好模型，贵一点可以接受；
- 派出去的活（工人）可以用更便宜、更快的模型，效果能接受就行；
- 派活设置里本机内核只有一个模型框，留空应该"跟随默认"；
- 但一个默认模型没法同时服务"规划"和"干活"两头。

现状（2026-11-19 代码核实）：

- **规划/对话模型** = `.data/runtime.json` 的运行时选择（`readLlmConfig()`），设置 → 模型可切；
  总管、执事、普通会话、内部拆单/验收都用它。
- **本机派活工人** = `native` 子进程，`worker-main.ts` 的模型顺序是
  `CHANCELLOR_LLM_MODEL → LLM_MODEL → deepseek-v4.1-flash`，完全不读运行时主选。
- `executor-config.ts` 的 native 模型框填了值后 `executorForDelegation()` 会带上 `profile.model`，
  但 chancellor 的 `resolveProfile()` 对 native 直接 `return {}`，把模型丢掉；
  留空则只读启动 env。**界面说"跟随主选"与实现不符，填了模型也不生效（双 bug）。**

## 2. 目标与非目标

### 目标

1. **规划车道不变**：现有默认模型继续服务总管、执事、普通会话、内部拆单/验收。
2. **干活车道**：本机内核派活工人（native）单独一个模型；留空 = 跟随默认模型
   （真正的运行时默认，不是启动 env）。
3. 干活模型可以从任意已连接供应商里选；native 子进程按该供应商的 baseURL + key 走，
   不再只能吃启动 env 的百炼。
4. 设置 → 派活 native 卡能选、能保存、能回显；不新增页面。

### 非目标（本批明确不做）

- **不按人设 / 按任务 / 按项目选模型**：总管和日记执事仍共用规划车道；
  以后要"某个执事单独用更贵的模型"再立 per-partner override，不改本批契约。
- **不拆普通 Worker 会话的模型**（`chatKind=worker` 的会话仍用规划车道）：
  它和派活工人不是同一条链；模型 pill 是全局的，硬拆会让 pill 显示和实际不一致。
- **不给外部 CLI 下发模型目录**：Claude / Codex / OpenCode 等仍只填模型名，
  跟随各自 CLI 的配置。
- **内部拆单/验收不单独指定模型**：继续用规划模型（维持 2026-11-16 拍板）。
- **不做 native 的「检测」按钮 / 自动探测**：模型清单来自已连接供应商目录，不 spawn CLI。
- **不做按单覆盖干活模型**：全局默认 + 建单快照，续跑沿用原单。

## 3. 策略

### D1 两条车道，不按人细分

- 规划模型 = 现有全局默认，不做 per-partner override。
- 干活模型 = `.data/executor.json` 的 `profiles.native`。
- 理由：用户要的是"规划贵、干活便宜"；总管和日记执事都属于规划，不需要两个不同的贵模型。
  过去也明确拍板不做按任务分工人 / 内部单独模型，沿用"全局一份"的简单口径。

### D2 存储与 API

`.data/executor.json`：

```json
{
  "employee": "native",
  "profiles": {
    "native": { "model": "deepseek-v4.1-flash", "providerId": "bailian" }
  }
}
```

- `profiles.native.model` 空 / 缺省 = 跟随默认；非空 = 干活模型。
- `profiles.native.providerId` 仅 native 使用；空 = 按模型 id 在已连接供应商里推断
  （优先当前默认供应商）。
- `GET/PUT /api/v1/agent/executor` 的 `profiles` 形状扩一个可选 `providerId`（native）；
  其余执行器不变。`providerId` 是供应商 id，不是密钥、不是变量名。

### D3 解析顺序

`executorForDelegation()` 对 native：

1. 显式 `model` 非空 → 用它；按 `providerId`（或模型 id 推断）找到已连接供应商，
   带 `modelRoute {baseUrl, keyEnv}`；
2. `model` 空且 `EXECUTOR_NATIVE_FOLLOW_DEFAULT` 开（默认）→ 用
   `readLlmConfig().model`（运行时主选）+ 对应 route；
3. `model` 空且开关关 → 不带 model（老行为：worker 回落启动 env）。

- 找不到供应商 / key 没配 → 只带 `model`，不带 route，worker 回落启动 env 的 baseURL/key；
  服务端记一条不含密钥的 warning。
- 外部 CLI 仍走原逻辑（model + permission）。

### D4 跨进程透传

- `EmployeeProfile` 增可选 `modelRoute?: { baseUrl: string; keyEnv: string }`
  （chancellor 契约；`keyEnv` 只是变量名，不是密钥值）。
- `resolveProfile()` 不再对 native 返回 `{}`：保留 model / modelRoute。
- `native.ts` 的 `childEnvWithModel()`：`modelRoute` 存在时给子进程设
  `CHANCELLOR_LLM_BASE_URL`，并从宿主 `process.env[keyEnv]` 取 key 设
  `CHANCELLOR_LLM_API_KEY`；model 设 `CHANCELLOR_LLM_MODEL`。
- `profileEnv()` 对 native 同样映射（分管宰相子进程里再派 native 子单时靠 env 继承）。
- ticket 快照 `ticket.options.employeeProfile` 会带 baseUrl / keyEnv（无密钥值），续跑沿用。

### D5 为什么现在能跨供应商

2026-11-16 曾登记"native 不跟随主选"的理由是 worker 子进程只会 OpenAI 兼容单供应商栈。
2026-11-19 复核 `provider.ts`：所有 providers 都走 `openAICompletionsApi`，
模型目录里的 baseUrl / keyEnv 可直接下发；因此该理由不再成立。
worker-main 仍只支持 OpenAI 兼容，这是已知边界（当前所有已配置供应商都是 OpenAI 兼容，故无差异）。

### D6 界面

- native 卡：模型框留空占位改「跟随默认模型」；右侧箭头展开已连接模型清单
  （来自 `GET /api/v1/agent/model`），第一行「跟随默认模型（当前 X）」；
  选中后显示模型名，保存时带 `providerId`。
- 卡片 tip 讲清：留空 = 跟设置 → 模型的默认；选一个 = 本机派活工人单独用，
  可更便宜 / 更快；权限由本机策略管。
- 不新增「检测」按钮；native 的模型清单不 spawn CLI。
- `executor-probe.ts` 里 native 的提示改为新口径。

### D7 回滚

- `EXECUTOR_NATIVE_FOLLOW_DEFAULT=false/0/off` → native 留空回到启动 env（旧行为）；
  显式模型仍生效。
- `EXECUTOR_CONFIG=false` → 整层回 env。
- 清除 native 模型框 = 跟随默认。

## 4. 影响面 / 风险

- 主对话模型、Worker 会话模型、内部质检模型**不变**。
- 默认行为变化：`.env` 里 `CHANCELLOR_LLM_MODEL` / `LLM_MODEL` 若原本靠它给 native
  单独设模型，升级后会被运行时主选覆盖；用回滚开关或显式选干活模型。
- 跨供应商 route 会把 baseUrl / keyEnv 写进 ticket.json（无密钥值）；
  key 值只在 spawn 时从 env 读。
- 供应商 key 缺失 / 供应商被删：route 解析失败，回落启动 env；派活报告会如实报错，
  不伪造成功。
- native worker 的上下文窗口仍写死 131072（`worker-main.ts`），不随干活模型变；
  选了窗口更小的模型需要另立项传递窗口元数据。
- 提示词 `<delegate_executor>` 文本会变（模型展示从"启动 env"改为实际默认 / 干活模型），
  不影响工具定义缓存；进变更记录。
