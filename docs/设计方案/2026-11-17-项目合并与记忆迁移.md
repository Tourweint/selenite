# 项目合并与记忆迁移

- **日期**：2026-11-17
- **状态**：已实施（同日）
- **下沉落点**：契约 → `docs/基线文档/接口-端点2-杂项日记与项目.md`、`docs/基线文档/接口-端点6-记忆课题与搜索.md`；机制与边界 → `docs/基线文档/系统架构.md`；落地记录 → `docs/变更记录/2026-11-17-项目合并与记忆迁移.md`
- **冲突口径**：本文与基线文档冲突时，**以基线文档为准**（那里是"现在是什么规则"）

## 1. 问题

2026-11-17 核查确认（`project-scope-orphan-boundary-1117`）：

1. **删项目不动记忆**：`ProjectsStore.deleteProject` 只删 `projects` / `project_roots` 两行。项目记忆留在 `project:<旧uuid>` scope，成为**孤儿**。
2. **孤儿永久不可达**：`GET /agent/memory/scopes` 只遍历 `listProjects(true)`（活项目 + 归档项目），硬删项目的 scope 不出现在任何列表里；召回侧 `isRecallableProjectId` 只在会话归属该项目时才进候选。结果是「不可见即无害」——**无害是真的，永久封存也是真的**。
3. **没有改 scope 的能力**：全仓无 `setScope` / `UPDATE memories SET scope`。想让记忆跟着项目合并走，只能删了重记。
4. **合并项目功能不存在**：没有任何 merge 路径。用户要合并只能手工建新项目，旧记忆各留各的。

用户口径（2026-11-17）：「迁移项目或者归并项目，做成一种新模式，非常对。就这样，你把它全做了。」

## 2. 目标

| 目标 | 落点 |
|---|---|
| 孤儿记忆能被看见 | `GET /agent/memory/scopes` 增加 `kind:"orphan"` 行 |
| 记忆能在 scope 之间搬迁 | `POST /agent/memory/scope/move` |
| 项目能合并 | `POST /api/v1/projects/:id/merge` |
| 删项目时记忆有明确处置 | `DELETE /api/v1/projects/:id?memory=keep\|archive\|move&into=<scope>` |

## 3. 关键设计

### 3.1 记忆迁移：`moveScope`（memory 包）

`MemoryStore` 新增：

```ts
/** 把 from 的全部记忆与原文档案整体改挂到 to；返回搬迁条数。 */
moveScope(from: string, to: string): { records: number; documents: number };
```

- SQLite 实现：`UPDATE memories SET scope=? WHERE scope=?` + `UPDATE memory_documents SET scope=? WHERE scope=?`。
- **FTS 不用动**：`memory_fts` 只镜像 `content` 与 `content_id`，不含 scope。这是选逐列 UPDATE 而不是"读出再 put"的直接理由（后者会重灌 FTS、丢 `recall_count` 之外的列语义）。
- **引用链天然安全**：`superseded_by` 存的是记录 id，不存 scope；同一 scope 整体搬迁后引用仍指向本 scope 内记录。
- `InMemoryStore` 同语义实现（测试与 faux 链路用）。
- `MemoryEngine.moveScope` 只做参数校验（非空、`from !== to`）后转发，**不碰 scope 白名单**——白名单在服务端（只有服务端知道项目登记表）。

**刻意不做**：去重。两个 scope 合并后可能出现内容重复；那是「整理」的职责（`consolidate` 出建议、人逐条点应用）。迁移只搬不判，避免一次 API 调用悄悄改动记忆语义。

### 3.2 孤儿识别（服务端）

`GET /api/v1/agent/memory/scopes` 在现有三段（global / 执事 / 项目）之后追加第四段：

```
{ "scope": "project:<uuid>", "label": "已删除的项目 · a1b2c3d4", "count": 192, "kind": "orphan" }
```

判定：`engine.stats().byScope` 里所有 `project:` 前缀 key，减去 `listProjects(true)` 的 id 集合。

- **label 只能给 uuid 前缀**：项目行已删，名字无处可取；不落"删项目时把名字存墓碑"这类新存储（为了一个展示名加一张表不划算）。
- 前端兼容：旧的 `kind` 白名单 `["partner","project"]` 会把 `orphan` 降级成 `mine`，所以**前端必须同步加白名单**，否则孤儿行会渲染成没有标签的"人"。这是本批的一个坑，验证时要盯。
- 孤儿行**只在记忆页可读**：不参与召回（召回要会话归属）、不进每晚整理（`nightlyScopes()` 只认 global + 在职执事）。刻意：整理孤儿 = 给不可达数据花钱。

### 3.3 记忆迁移端点

`POST /api/v1/agent/memory/scope/move`

```jsonc
{ "from": "project:<uuid>", "to": "project:<uuid>|partner:<uuid>|global" }
```

校验顺序（全部 400 带说明）：

1. `from` / `to` 都必须过 `validTargetScope`（global / partner / project 三种形态）。
2. `from !== to`。
3. `from` 必须**真的存在**（`count > 0`），否则 `400 empty_source`——不把"搬了 0 条"当成功，那多半是 uuid 写错了。
4. `to` 若是 `project:` 必须是**登记项目**（活或归档都行）；不是登记项目 → `400 unknown_project`。这条与 `importMemory` 同口径：不制造新的孤儿。
5. `memory` 未启用 → 404（与其它记忆端点一致）。

响应：`{ ok, from, to, records, documents }`。

**刻意不做**：跨 scope 去重、迁移前的预览/二次确认（前端弹窗确认即可）、`session:` scope 作为目标（会话记忆没有搬走的语义）。

### 3.4 项目合并

`POST /api/v1/projects/:id/merge`，body `{ "into": "<targetProjectId>" }`。

语义：**把 `:id` 并进 `into`，源项目消失，目标项目吸收它的一切**。顺序：

1. **守卫**：源/目标都存在；`id !== into`；目标未归档；源没有非终态派单（复用 `projectHasInFlightTickets`，和删除同口径）。
2. **文件夹**：源项目的每个 root 调到目标名下（`role` 一律降为 `extra`；目标原本的主文件夹不动）。路径与目标已有 root 冲突（相同 / 互相包含）→ 400 `root_overlaps_root`，**不静默丢根**。
3. **会话绑定**：durable `ChatProjects.byInternal` 里值等于源的，全部改成目标。
4. **执事挂载**：`partners.projectIds` 里源的 id 换成目标（先去重）。
5. **记忆**：`engine.moveScope("project:<src>", "project:<tgt>")`。
6. **删源登记**：`deleteProject(src)`（不删磁盘、不删会话）。
7. **当前项目指针**：若当前项目是源 → 指向目标。

**顺序是有理由的**：2–5 都是"搬"，6 是"销毁登记"。任何一步失败都停在那一步之前，源项目仍然完整——**最坏情况是"搬了一半"**，所以 2–5 都做成幂等语义（root 已存在则跳过、绑定已是目标则跳过、记忆搬到空集返回 0）。

**刻意不做**：

- **不做跨库事务**。项目登记在 `projects.sqlite`、记忆在 `memory.db`、会话绑定在 durable，三库无法原子提交。合并失败可能部分完成——响应用 `moved: {...}` 分项回报已完成的部分，前端照实提示"部分完成，可重复执行补齐"。这是已知边界，写进 `系统架构.md`。
- **不合并会话标题 / 不重排历史**：会话只是换归属项目，其余不动。
- **不自动整理合并后的记忆**：内容仍分属原项目的语义，要不要并、并哪条是人的判断。

### 3.5 删项目时的记忆处置

`DELETE /api/v1/projects/:id` 增加两个可选查询参数：

| 形态 | 行为 |
|---|---|
| 不带参数（默认） | 现状：记忆保留为孤儿（`keep`）。**逐字节兼容**旧调用方 |
| `?memory=keep` | 同上，显式写法 |
| `?memory=archive` | 该 scope 全部记忆写 `archived_at`（封存：不出现在列表与召回，但行还在，可被 move 取走） |
| `?memory=move&into=<scope>` | 先 `moveScope` 再删登记；`into` 校验同 §3.3 |

- `archive` 是软封存，不是删除——与「记忆一条不删」的既有口径一致（用户多次强调）。
- 响应增加 `memory: { action, records, documents }`（`keep` 时 records 为 0，不扫库）。
- 前端删除弹窗给三选一（默认"保留"），只有选了 `move` 才出现目标选择器。

### 3.6 回滚开关

| env | 默认 | 关掉后 |
|---|---|---|
| `MEMORY_SCOPE_MOVE` | 开 | `/memory/scope/move` 404；删项目 `memory=move` 400；前端迁移钮不渲染 |
| `PROJECT_MERGE` | 开 | `POST /projects/:id/merge` 404；前端"合并到"菜单项不渲染 |

两个开关都只影响**新入口**，不影响既有行为（孤儿列表始终在，它只是只读）。

## 4. 备选与取舍

| 备选 | 为什么不做 |
|---|---|
| 删项目时把记忆一并删掉 | 违反「记忆一条不删」的既有口径；且不可逆 |
| 孤儿记忆自动归到 global | 会污染"我的记忆"，且用户没有授权这次搬迁 |
| 合并项目 = 新建第三个项目再搬两次 | 多一次登记写、多一次失败面；直接并进目标是一步 |
| 用墓碑表存已删项目的名字 | 为展示名加一张表；uuid 前缀足够人认出"这是那个项目" |
| 迁移时顺带跑一次整理 | 整理要模型、要人逐条应用；迁移应该是纯机械、零模型、可预测的 |

## 5. 已知边界（要写进 `系统架构.md`）

- 合并三库非原子；失败可部分完成，重复执行可补齐（2–5 幂等）。
- 孤儿 scope 不可召回、不进每晚整理——它只是可见、可搬、可封存。
- 迁移不去重；重复内容留给「整理」。
- 合并不迁移 `routines`（例行任务挂执事不挂项目）、不迁移派单历史（按 project 目录算，登记删了旧单仍在 chancellor 侧）。
- `project:` 之外的 scope（`session:`）不能作为迁移目标，也不能作为来源（会破坏会话记忆的封顶修剪口径）。
