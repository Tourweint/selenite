## 零、一句话

手机在配对/加入中继请求里多带一个**可选** `hardwareId`（客户端用系统 id + 包名算好的 hash）；
两端服务端只存它的二次 hash `hardwareHash`，同 hash 的未撤销设备**复用原 deviceId**、覆盖令牌，
于是反复扫码不再堆同名记录，旧令牌自然失效；不带字段的老客户端行为逐字不变。

## 一、要解决的问题（C-9 之后还剩什么）

C-9 让手机能看到电脑端设备名册并在显示层合并，但**服务端每次配对都新建一条**：

| 事实 | 位置 |
|---|---|
| harness `issueDevice()` 每次 `randomBytes(8)` 生成新 id 并追加，无硬件标识字段 | `pairing.ts:300-330` |
| relay `createDevice()` 同样每次新 id 追加 | `relay/src/store.ts:200-225` |
| 配对响应已回 `deviceId`（本次记录 id），但重配对后必变 | `index.ts:998` / `:1060` |
| 已有 `fingerprint = sha256(id + tokenHash)` 是**防篡改/人眼核对**字段，换 token 就变 | `pairing.ts:deviceFingerprint` |

结果：同一台手机反复扫码 → 桌面「已连接的设备」出现多条同名记录；C-9 显示层按 id/唯一名合并只能尽量合，旧记录仍并列占名额，甚至把真正的新设备挤出去（设备上限淘汰）。

## 二、拍板项（需用户确认）

| # | 决策 | 理由 | 错了的代价 |
|---|---|---|---|
| D1 | 客户端生成 `hardwareId = sha256(ANDROID_ID + "|" + 包名)`，明文不落盘、不进日志；服务端存 `hardwareHash = sha256(hardwareId)` | 双 hash 保证任何原始设备标识都不扩散到服务端存储/投影；ANDROID_ID 是系统给应用 Stabil 的 id，无需权限 | 重装 App 后 ANDROID_ID 变 → 视为新设备（本方案明确**不追求跨重装稳定**） |
| D2 | 同 `hardwareHash` 的**未撤销**记录存在 → **复用其 id**，覆盖 `tokenHash`、更新 `name`/`lastSeenAt`、重算 `fingerprint` | 主机位、设备描述、审计引用都挂在 id 上，复用最省迁移；旧 token 因 tokenHash 被覆盖自然 403 | 若误合两台设备（hash 碰撞）会串号；SHA-256 碰撞可接受，且只在同一账号内 |
| D3 | **已撤销**记录不复活：撤销过的新配对走新建 | 撤销是明确的「作废」意图，自动复活违背用户意志 | 撤销后重配会多一条记录；可接受，且这是低频操作 |
| D4 | `keyChangedAt`（fail-closed）记录**复用时清除** | 重配对是主人主动换凭据，等同确认新 key；不清会让新 token 永远 403 | 若 keyChangedAt 源于文件被篡改，重配对相当于「重新认领」——这是主人持码扫码才能触发的动作，可接受 |
| D5 | 两份库**各自内部去重**，不合并存储；字段与开关各自独立 | 守住 2026-11-14 口径；relay 与 harness 的 id 体系本就不同 | 同一台手机在两份库各有一条（C-9 显示层已合并，用户侧看不到重复） |
| D6 | 回滚开关 `DEVICE_HARDWARE_MERGE`（harness + relay 各一个 env），默认 `true`；`false` 时**完全忽略**请求里的 hardwareId，逐字回到旧行为 | 契约改动必须能一行 env 退回 | 关掉后重复配对又堆记录，但语义完全回到改前 |
| D7 | `hardwareHash` **不进任何对外响应/投影/日志**；只作为内部归并键 | 隐私最小暴露 | 调试时少一个可看字段；必要时用既有 fingerprint 人眼核对 |

## 三、契约变更

### 3.1 请求（可选字段，缺字段 = 旧行为）

| 端点 | 变更 |
|---|---|
| harness `POST /api/v1/pair/redeem` | body 加可选 `hardwareId: string`（≤128 字符；非字符串/超长忽略，不当错误） |
| harness `POST /api/v1/pairing/confirm` | 同上 |
| relay `POST /api/relay/join` | body 加可选 `hardwareId`（`RelayJoinRequestSchema` 加 optional 字段） |
| relay `POST /api/relay/pair/redeem` | body 加可选 `hardwareId`（该路由手工解析 body，加一处读取） |

**手机侧来源**：`PairingApi.redeem()` 与 `RelayJoinApi.join()` 各自在构造 payload 时读一次系统 id 并算 hash；读不到就**省略该字段**，让服务端按旧行为处理。不新增 DataStore 字段（明文 hash 由系统 id 现算）。

### 3.2 存储（内部字段，不外泄）

| 端 | 结构 | 新字段 |
|---|---|---|
| harness | `StoredDevice`（`pairing.ts:~48`） | `hardwareHash?: string` |
| relay | `StoredDevice`（`store.ts:~30`） | `hardwareHash?: string` |

两端的 `listDevices()` 投影**保持不变**（不带新字段），C-9 的 `PairDevicesApi` 无需改解析。

### 3.3 行为矩阵

| hardwareId | 同 hash 未撤销记录 | 动作 | 返回 |
|---|---|---|---|
| 有 | 存在 | 复用 id、换 token、重算 fingerprint、清 keyChangedAt、刷新名字/时间 | 新 `deviceToken` + **同一个** `deviceId` |
| 有 | 不存在 | 新建（现有逻辑） | 新 id + 新 token |
| 有 | 只命中已撤销记录 | 新建（D3） | 新 id + 新 token |
| 无（老客户端） | — | 逐字走现有逻辑（每次新建） | 新 id + 新 token |
| 开关 `false` | — | 逐字走现有逻辑 | 新 id + 新 token |

### 3.4 旧令牌失效

复用时 tokenHash 被覆盖 → 旧 token 的 `verifyDeviceToken()` 不再命中 → 403 空体（现有鉴权语义不变）。**不需要**额外撤销动作。

## 四、实现范围（拍板后才动）

### harness（仓 `lifediary-harness`）

- `pairing.ts`：`StoredDevice` 加 `hardwareHash`；`issueDevice(deviceName, now, hardwareHash?)` 加归并查找；`redeem` / `confirm` 调用处透传；`sealFingerprints()` 跳过新字段。
- `index.ts`：`/pair/redeem`（`:958`）与 `/pairing/confirm`（`:1020`）读取 body 的 `hardwareId` 并算 hash 传入；开关读 env。
- 单测：同 hash 两次 → 1 条/id 不变；旧 token 403；不同 hash → 2 条；缺字段 → 2 条；撤销后重配 → 新 id；开关关闭 → 旧行为。
- 文档：`接口文档.md` §6 env 表 + 两个端点请求字段；`系统架构.md` 配对段落补一句内部归并。

### relay（同仓 `ts/apps/relay`）

- `store.ts`：`StoredDevice` 加 `hardwareHash`；`createDevice()` 加归并；`redeem()` 透传。
- `server.ts`：`/api/relay/join`（`:196`）与 `/api/relay/pair/redeem`（`:218`）读取 `hardwareId` 算 hash 传入；开关读 env。
- 单测：同 hash 重复 join → 名册 1 条、主机位/描述引用不断；不同硬件不合并；缺字段旧行为。

### phone（仓 `lifediary`）

- `PairingApi.redeem()` / `RelayJoinApi.join()`：payload 加可选 `hardwareId`（系统 id + 包名现算 SHA-256；取不到省略）。
- 不新增依赖；不落盘明文；日志不打印该字段。
- 文档：`接口契约.md` 两个请求字段 + 归并语义。

## 五、验证口径

- harness `pnpm typecheck` + `pnpm --filter @lifediary/server test`；relay 单测；手机 `spotlessKotlinCheck` + `testDebugUnitTest` + `assembleDebug`（`spotlessMisc` 已知本机挂死，不强求）。
- 端到端真机：手机扫码两次 → 两端设备列表各只有一条；第一次 token 失效；电脑端主机位/描述仍在。
- 但**真机重配属于破坏性验证**（会让旧 token 失效），执行前确认测试设备，别在主力机上做。

## 六、明确不做

- 不合并 harness 配对库与 relay 中继库（D5）；不在显示层之外改 C-9 的合并结果。
- 不展示/认领 `unpaired` / `unclaimed`（安全面）。
- 不改设备上限淘汰策略；不改对外投影格式。
- 不追求跨 App 重装稳定（D1）；不做桌面端/浏览器的 hardwareId（浏览器无系统 id，保持旧行为）。
- 不把本字段当鉴权依据：它是**归并键**，不是凭据；鉴权仍只认 token。
