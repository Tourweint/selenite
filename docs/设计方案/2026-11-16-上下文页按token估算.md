## 1. 先核数：工具定义没有算错

2026-11-16 用活服务 `GET /api/v1/agent/context-defaults?role=chief` 核对：

| 块 | 字符数 | 说明 |
|---|---:|---|
| 系统提示词 | 1,017 | 28 个 section 里的真实文本（其余 0 字槽位不加） |
| 工具定义 | 16,163 | 22 个工具，`JSON.stringify({name,description,parameters})` 的紧凑长度 |
| 技能 | 2,040 | 技能索引原文 |
| 合计 | 19,220 | |

工具字符口径与请求里的工具定义是同一条 JSON（紧凑序列化，不含缩进），不是把 pretty JSON
算进了总数；每项 `chars` 相加正好 16,163，没有重复计数。工具块大是**描述本身长**：
`delegate` 2,996 字、`routine_manage` 1,630 字、`remember` 1,388 字，三个占 6,014 字。

按 cl100k 实测同一份内容的 token 数：系统 865、工具 8,337、技能 682，合计 9,884——
中文/JSON 的字符-token 比差很多（系统 ≈0.85 token/字，工具 JSON ≈0.52 token/字）。
所以「16,163 字」看起来比系统提示词大一个量级，换成 token 后工具约占固定前缀 84%，仍然最大，
但没有字符数那么吓人。**是否要压缩工具描述是另一个决定**（缓存前缀资产，改描述要单独记录），
本方案不动提示词。

## 2. 拍板

1. 页面主数字从字符改成 **token 估算**，所有行、计数、图例、分段条都按 token 算；
   数字前标 `≈`，表示估算。
2. 响应保留 `chars`（排查与兼容用），**新增 `tokens`**，纯增量字段。
3. 顶部「上一轮」的 `used` 改成**完整 prompt token**：`input + cacheRead + cacheWrite`。

## 3. 估算口径

`ts/apps/server/src/token-estimate.ts`：

```
tokens = CJK 字符数 × 1 + 其它字符数 × 0.25，向上取整
```

- CJK 范围：汉字 / 假名 / 谚文 / CJK 标点 / 全角字符；
- 2026-11-16 用同一份内容对 cl100k 校准：系统 -14%、工具 -5%、技能 +8%、合计 -5%；
- 不引入真 tokenizer：仓库没有词表依赖，接入的模型来自多家（DeepSeek / Kimi / GLM / …），
  任何一种词表都只是对其中一家的近似，还要多背一份词表；这页回答「谁在占地方」，
  不是计费。

**不用内核 `estimateTextTokens`**：它是 `chars / 3.5`，中文会低报约 2/3（1,017 字估 291，
实际 865），拿它显示反而误导；内核估算继续只服务压缩阈值，本页不共用。

## 4. `used` 为什么改

pi-ai 的 `Usage.input` 是**未命中缓存的输入 token**：OpenAI 系按
`prompt_tokens - cached - write` 算，Anthropic 的 `input_tokens` 本身就不含 cache read/write。
原实现直接取 `usage.input`，命中缓存时「上下文已用」会严重低报；全部命中时 `input = 0`，
整块 ring 直接隐藏。改成 `input + cacheRead + cacheWrite`：三家口径加起来都等于完整 prompt，
也和 `contextWindow` 的分母对得上。`/context` 的两个使用方（composer ring / 容量卡、设置页）
同时受益；容量卡的构成条仍按字符分摊，本次不改。

## 6. 明确不做

- **不做真 tokenizer / 按模型切词表**：估算即可，页面标 `≈`。
- **不改工具描述与顺序**：是否压缩 `delegate` 等长描述，另立方案。
- **不改手机端**：本页仍只做 Web 设置。
- **不改容量卡构成条**：它只显示百分比，继续按字符分摊；`used` 的正确性已由 §4 修正。
- **不把字符数从响应里删掉**：排查前缀变化仍要用它。
