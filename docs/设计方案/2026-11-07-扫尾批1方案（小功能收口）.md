## 一、A1 任务取消/重试（三轮挂账的端点）

**取舍核心：取消 = harness 侧"作废"，不杀 chancellor 进程。**
理由：单据状态与执行都在 chancellor 仓，harness 杀不到 worker；而用户要的是"这单别再来烦我、别写回我的对话"。杀进程属 chancellor 能力，登记为边界（将来 chancellor 支持取消时升级，接口不变）。

### 契约

- `POST /api/v1/tickets/:id/cancel` → 把单记入"作废位"。幂等（重复取消 200）；`done / failed / aborted` 已终态 → `400`（canceled 重复取消 200）。回 `200 {ok:true, status:"canceled"}`。
- `POST /api/v1/tickets/:id/retry` → 仅 `failed / aborted / canceled` 可重试；`needs_you` 不在列（它走既有 resume/回答链路，语义是"回话"不是"重来"）。读原单工作目录 `ticket.json` 的 `requirement`（及 domain/project 归属）→ 走既有 `startDelegation` 重派**新单**，返回 `200 {ok:true, ticketId:<新单号>}`。字段缺失如实 400，不编参数。

### 取消生效的四个点（`delegations.sqlite` 新表 `delegation_cancellations(ticket_id PK, canceled_at, conversation_id)`）

1. `startDelegation.settle()`：已取消单**不写回会话**（不 recordMessage、不发 report 事件）——用户明确不要结果。
2. `emitProgress()`：已取消单停止转发进度事件（SSE 安静）。
3. `delegation-api` 投影：列表/详情对已取消单叠加 `canceled: true`，status 显示为 `canceled`（原始状态保留在 `originStatus`，不丢事实）。
4. 前端：操作后本地立即置态 + 刷新；canceled 单显示"已作废"chip。

**已知边界（登记）**：chancellor 侧继续跑完、产物照常落盘——只是 harness 不再搬运结果。这不是丢工作，是"不再汇报"。
**回滚**：`DELEGATION_CANCEL=false` → cancel 端点 404、前端不渲染按钮（一行回滚）。
**前端**：非终态卡 → 「取消」；`failed/aborted/canceled` 卡 → 「重试」。列表行内小按钮 + 详情页动作区，操作走确认弹窗（取消不可逆要说明）。

## 二、B1 手动压缩（拍板：斜杠命令，不做按钮）

### 契约

`POST /api/v1/agent/chat/:conversationId/compact`，body `{ "instructions"?: string }`：
- 内核 `Conversation.compact(instructions, CTX)` 本就是**受理即返回**（返回 taskId，压缩在后台做、在空闲/边界落摘要）——端点照实：受理即回 `200 {ok:true, taskId}`。
- `?wait=1`：受理后 `harness.waitForTask` 至多 `AGENT_COMPACT_WAIT_MS`（默认 60000）→ 完成 `200 {ok:true, compacted:true}`；超时 `200 {ok:true, waited:false, taskId}`（受理仍然有效，客户端可走 SSE/刷新看结果）。
- 会话不存在 404；模型未配置 503（与 `/mode` 同口径）。压缩事件（`compaction_start/end`）内核本就发，SSE 侧已有的透传不动。

### 前端（composer 斜杠命令）

- composer 提交时若输入**精确等于** `/compact`（trim 后，大小写不敏感）：不作为消息发送、不进历史，改为调上述端点（wait=1），完成后气泡提示"上下文已压缩"。可带一段文字作为 instructions（`/compact <文字>`）。
- **刻意没有**：不做通用斜杠命令系统/自动补全（一个命令不值得一套框架，登记防扩散）。
- 回滚：前端不识别即无感；端点纯增量常在。

## 三、A4 项目改名/归档/删除（"后续任务中心再补"的补齐）

- `PATCH /api/v1/projects/:id` body `{name}` → 改名。校验同建项目（非空、长度、同工作区内不重名）。
- `POST /api/v1/projects/:id/archive` / `POST /api/v1/projects/:id/unarchive` → 写 `archived` 位（字段已在，无写入方——本批接上）。
- `DELETE /api/v1/projects/:id` → **只删登记，不动磁盘目录**（文案明说）。守卫：该项目存在非终态派单（chancellor 工作目录还在跑）→ `400` "先取消或等任务完结"；有历史单 → 允许删（历史单保留，project 字段变悬空引用，投影显示原名快照——若实现代价大则显示"已删项目"，不阻塞删除）。
- 列表 `GET /api/v1/projects` 默认不含 archived；`?includeArchived=1` 带上。前端项目页：归档折叠区 + 行内改名/归档/删除（删除走确认弹窗，与既有"新建待确认"弹窗同风格）。
- 回滚：纯增量端点；前端不接即旧行为。

## 四、session 作用域记忆保留策略（批 1 只做这件小的）

- 问题（2026-11-06 登记）：`session` / `partner:<id>` scope 的记忆只增不减，长期会话无限膨胀。
- 方案：**封顶修剪**——每次记忆落库后，若该 scope 条数 > `MEMORY_SESSION_CAP`（默认 200，`0`=关闭=回滚），按 `created_at` 最旧优先删除，**保护两类**：`kind=preference`、被 `supersededBy` 引用的记录。`global` scope 永不自动删。
- 实现：memory 包 store 加 `countByScope` / `pruneOldest(scope, keep, protect)`（SQLite 单条 DELETE 子查询，原子）；server 在记忆写入路径末尾调用。删除不通知、不进日志正文（只记条数，遵守 D8）。
- 测试：`pnpm memtest` 加用例（超限删旧、保护偏好、cap=0 不动）。
