## 零、结论先行

| 你的诉求 | 本方案的回应 |
|---|---|
| 工具 / 命令调用时间长了自动转后台 | **只有 bash / powershell 真做「超时转后台」**，复用现有 bg-jobs 机制；`delegate` 本来就是后台（返回任务单号），不重复做。其余工具**不做假后台**：没有作业句柄的工具说「转后台」就是骗模型，也骗用户。 |
| 每个工具 / 插件分别调 | 两层配置：**能力组默认 + 单工具覆盖**。但可配的只有「真有 I/O 等待、且能中止」的工具（v1 四个：`bash` / `powershell` / `recall`（外部库）/ `web_search`）；其余工具在界面上逐条列出并写明为什么锁定（本地同步 / 副作用不可撤销 / 必须人确认）。 |
| 入口放插件页 | **推荐在插件页新增「工具与命令」组**：先一张总开关卡，再一组工具卡，点开卡 = 超时 + 超时策略 + 完成通知 + 一句说明。**不是给现有 80 多个开关各加一项**——开关和工具不是一对一，硬加会造出一堆假对应。 |
| 记忆工具时长迁进总控 | `askMs` → `tools.recall.timeoutMs`，`lightMs` → `injections.memoryLight.timeoutMs`；`memory-bank.json` 保留一代兼容读，新界面只写 `tool-policy.json`。 |
| 记忆检索是例外 | 只允许「限时 + 失败 / 降级」，`onTimeout` 永远不能选 `background`（配置层直接拒）。 |

一句话：**这不是「给每个工具配一个超时数字」，而是「给每个有真实等待面的工具一条可解释的异常路径」**。
没有等待面的工具配超时是假能力；有等待面但不能中止的工具，超时只能「不再等」，不能假装「已经停」。

### 1.2 三条结论（后面方案都建立在这三条上）

1. **超时只对「有真实 I/O 等待、且能中止」的工具才有意义。** 本地读取 / 同步扫描类工具
   （`recall_sessions`、`skill`、内置记忆、`read` 小文件）加一个 `setTimeout`，要么在阻塞期间不触发，
   要么只能「不再等」而不能停止手里的活；给它们配超时是半截能力。v1 可配集合因此很小：
   `bash` / `powershell`（子进程）、`recall` 外部库（子进程）、`web_search`（网络）。
2. **「转后台」需要一个作业句柄。** 今天只有 bash 系有：`moveToBackground` 起独立子进程 + index + log + kill + 完成唤醒。
   `delegate` 是天然的作业句柄（任务单号）。其它工具没有句柄，不能把「超时后继续跑」说成后台。
3. **任务中心不是通用后台作业队列。** 它建在 chancellor 的票据模型上（`Store` / `Ticket`、租约、车道、死信、回执），
   把一条 bash 命令塞进去会污染取消 / 重试 / 回执语义。通用后台结果应复用 bg-jobs 注册表，任务中心最多做一个只读入口（本方案放二期）。

## 二、分类模型

### 2.1 四类

| 类 | 定义 | 超时后能做什么 | 默认策略 |
|---|---|---|---|
| **A. 当轮证据（不可后台）** | 结果必须参与当轮推理：记忆检索、会话考古、网络搜索、读文件 | **只能失败 / 降级 / 更短预算**；绝不允许 `background` | `onTimeout: "fail"`，`notify: false`；预算按工具给（见 2.2） |
| **B. 可后台（结果不参与当轮推理）** | 长命令、构建、跑测试、派活 | `fail` / `cancel` / `background`；`background` 只给有作业句柄的实现 | `onTimeout: "background"`，`notify: true`；未配置 = 今天的行为（不转） |
| **C. 必须前台（交互确认）** | `ask_user`、审批 | **不配超时、不转后台、不自动取消**；到点是人的决定，不是机器的决定 | 锁定，界面上只读并写明原因 |
| **D. 副作用不可撤销** | `write` / `edit` / `remember` / `partner_manage` / `group_manage` / `routine_manage` / `propose_project` / `send_to_agent` | 不加超时：写到一半说「超时失败」会让模型重试并写第二遍 | 锁定，界面上只读并写明原因 |

### 2.2 全量工具矩阵（v1 口径）

「可配」= 界面上有输入框；「锁定」= 有这一行、但没有输入框，附一句原因。

| 能力组 | 工具 | 类 | 可中止 | 可后台 | v1 可配 | 默认 / 今天的值 |
|---|---|---|---|---|---|---|
| 命令与文件 | `bash` | B | 是（内核杀进程） | **是**（bg-jobs） | 是 | 900s；今天不转后台（`AGENT_BASH_BG_TIMEOUT=false`） |
| 命令与文件 | `powershell` | B | 是 | **是**（bg-jobs） | 是 | 今天**没有**默认注入；建议默认 900s |
| 命令与文件 | `read` | A | 否（同步 FS） | 否 | 锁定 | 本地同步读；加超时只能不再等，读操作仍会跑完 |
| 命令与文件 | `write` / `edit` | D | 否 | 否 | 锁定 | 写到一半不能撤销 |
| 记忆 | `recall`（外部库） | A | 是（kill 子进程） | 否 | 是 | 15s（`timeouts.askMs`，clamp 1–120s） |
| 记忆 | `recall`（内置） | A | 否（同步） | 否 | 锁定 | 本地同步，无等待面 |
| 记忆 | `recall_sessions` | A | 否（无中止点） | 否 | 锁定 | 本地读取 + 同步子串扫描；超时只能不再等，不能停扫描 |
| 记忆 | `remember` | D | 外部库有 15s 常量 | 否 | 锁定 | 写操作；外部库已有实现级预算 |
| 搜索 | `web_search` | A | 是（`AbortSignal`） | 否 | 是 | 每源 20s，无整体预算 |
| 派活与协作 | `delegate` | B（天然后台） | — | 已经是后台 | 锁定（只读说明） | 不等结果；worker 超时在 `CHANCELLOR_WORKER_*` |
| 派活与协作 | `send_to_agent` | D | 否 | 否 | 锁定 | 会起对方模型轮，属于花钱动作 |
| 派活与协作 | `partner_manage` / `partner_skill_write` / `group_manage` / `routine_manage` / `propose_project` / `respond_escalation` | D | 否 | 否 | 锁定 | 改关系 / 写技能 / 建常驻轮 / 答复上报，都是落盘动作 |
| 交互确认 | `ask_user` | C | — | 否 | 锁定 | 120s 只是卡片过期展示，不等于工具超时 |
| 交互确认 | 审批（gate，不是工具） | C | — | 否 | 不进工具表 | async 零阻塞；blocking 120s |
| 技能与提醒 | `skill` / `save_skill_advice` / `set_reminder` / `save_reminder_advice` | D（本地小操作） | 否 | 否 | 锁定 | 本地同步 / 小文件 |
| 元工具 | `tool_search` / `report_progress` | D（本地小操作） | 否 | 否 | 锁定 | 本地注册表查询 / 写一条进度记录 |

> 「插件」在本文里指**能力组**（上表第一列），不是 `plugins.json` 里的单张开关卡。
> 原因见 §4.1：`plugins.json` 有 7 个组、84 个开关（2026-11-24 实读；其中一部分 `surface:settings` 不在插件页），
> 但开关和工具不是一对一：
> `bash` / `read` / `write` 没有对应开关；`CHANCELLOR_ENABLED` 间接管 `delegate`；`MEMORY_ENABLED` 管 `recall` / `remember`。
> 硬把「异常处理」挂到每张开关卡上，绝大多数卡没有对应的工具。

### 2.3 为什么不做「每个工具一个数字」

- 本地读取 / 同步扫描类工具加超时是**半截能力**：要么定时器在阻塞期间不触发，要么只能停止等待、停不下手里的活，配了也不会按预期生效。
- 写工具加超时是**危险能力**：超时只代表「不再等」，不代表「没写」；模型看到失败会重试，可能写第二遍。
- 交互确认加超时是**违背设计**：`ask_user` / 审批的意义就是等人；自动取消等于替人做决定。

所以界面上「每个工具都有一行」是真的，但只有四个工具可编辑；其余行是**解释**，不是可拨的假开关。
这比「每行都能填、填了不生效」诚实。

**备选（本方案不做，留作翻案条件）**：如果以后一定要让每个 A 类只读工具都能配一个数字，可以加
「fail-only 的停止等待模式」——到点返回失败，底层读 / 扫描可能继续跑完，结果丢弃。代价是界面必须明确写
「已不再等，不代表已停止」，否则用户会以为工具被杀掉了。只有真实出现「某个只读工具卡住整轮」的案例时再开。

## 三、配置模型

### 3.1 数据结构

落点 `.data/tool-policy.json`（`TOOL_POLICY_PATH` 可覆盖，供探针 / 测试隔离；与 `.data/tool-pool.json`、
`.data/approvals.json` 的 `*_PATH` 做法一致）。**写：同目录临时文件 + rename 的原子写；读：mtime + size 缓存**
（照 `tool-pool.ts` / `memory-bank.ts`）。下面只是**用户显式配过之后的形状示例**；
文件不存在 / 某条缺省 / 三个字段都空 = 今天的行为（不转、不额外限时）。

```json
{
  "v": 1,
  "tools": {
    "bash":       { "timeoutMs": 900000, "onTimeout": "background", "notify": true },
    "powershell": { "timeoutMs": 900000, "onTimeout": "background", "notify": true },
    "recall":     { "timeoutMs": 15000,  "onTimeout": "fail",       "notify": false },
    "web_search": { "timeoutMs": 20000,  "onTimeout": "fail",       "notify": false }
  },
  "groups": {
    "memory": { "timeoutMs": 15000, "onTimeout": "fail", "notify": false }
  },
  "injections": {
    "memoryLight": { "timeoutMs": 8000 }
  }
}
```

字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `v` | 1 | 版本号；未来形状变化时读旧版做迁移 |
| `tools.<name>` | object \| 缺省 | 单工具覆盖；**缺省 = 继承组 → 实现默认 → env 兜底** |
| `groups.<id>` | object \| 缺省 | 能力组默认；只对组内**可配**工具生效（锁定的行忽略） |
| `injections.<name>` | object \| 缺省 | 不是工具调用的预算（当前只有 `memoryLight`）；单独分区，避免污染「工具」语义 |
| `timeoutMs` | number | 毫秒；界面上按秒展示，存储按毫秒（与现有 `memory-bank.json` 一致） |
| `onTimeout` | `"fail" \| "background" \| "cancel"` | 语义见 §5；`background` 只允许出现在 `capabilities.backgroundable` 的工具上 |
| `notify` | boolean | 终态是否写回会话并唤醒；`false` = 只留 index / log，不写会话、不唤醒。默认：`background` → true，`fail` / `cancel` → false |

消毒规则（`sanitize`）：

- 未知顶层键读时丢弃；未知工具名 / 组名在 **PUT 时 400**（用户拼错要当场知道，不静默丢）。
- `timeoutMs` 非数字 / 非有限数 → 丢弃该字段（回继承）；越界 → clamp 到该工具的范围；小数取整。
- `onTimeout` 不认识 → 丢弃该字段（回默认）；对不可后台工具写 `background` → **PUT 400 `on_timeout_unsupported`**。
- `notify` 非布尔 → 丢弃（回默认）。
- 单条 policy 三个字段都缺 → 视为删除该条（回继承）。

**catalog 住在代码里**（`tool-policy-catalog.ts`）：能力组、工具 → 组映射、类别、`capabilities`（abortable /
backgroundable / configurable）、锁定原因、范围，全部是静态表。理由：工具名和实现能力是代码事实，
改工具就要改这份表；放 `plugins.json` 会让「清单」和「注册表」两处漂移。`plugins.json` 只加总开关这一张卡。

范围表：

| 工具 / 注入 | min | max | 默认 | 依据 |
|---|---|---|---|---|
| `bash` / `powershell` | 5_000 | 3_600_000 | 900_000 | 现有 `AGENT_BASH_TIMEOUT_S` 默认 900s；上限放到 60min，覆盖长构建 |
| `recall`（外部库） | 1_000 | 120_000 | 15_000 | 与 `MEMORY_BANK_TIMEOUT_RANGES.askMs` 完全一致，迁移不产生新边界 |
| `web_search` | 5_000 | 120_000 | 20_000 | 与现有每源 20s 对齐；这是**整次调用**预算，不是每源 |
| `injections.memoryLight` | 500 | 30_000 | 8_000 | 与 `MEMORY_BANK_TIMEOUT_RANGES.lightMs` 一致 |

### 3.2 为什么不是 flags（先纠正一个前提）

「flags 是布尔」这句今天不准确：`flags.ts` 的 `FlagDef.type` 支持 `"number"`，`plugins.json` 里已经有
`ARCHIVE_AUTO_DAYS`、`AGENT_COMPACT_TRIGGER_PERCENT`、`AGENT_COMPACT_TRIGGER_K` 三个数值开关（2026-11-24 实读）。

真正不适合放 flags 的原因是另外三条：

1. **一个 key 一个标量。** 一份 policy 是 `{timeoutMs, onTimeout, notify}` 三字段 × N 个工具。
   塞进 flags 会变成 `TOOL_TIMEOUT_BASH_MS`、`TOOL_TIMEOUT_BASH_ON_TIMEOUT`、`TOOL_TIMEOUT_BASH_NOTIFY`… 
   清单膨胀几十个键，且三者无法原子保存。
2. **flags 的键是环境变量名，语义是「功能开不开 / 档位」。** 工具策略是「这个工具超时后怎么办」，
   不是部署配置，也不是全局功能开关。
3. **flags 的读写模型是单键 PUT。** 工具策略需要「一次保存整张表 + 未知工具名报错 + 原子写」，
   放进 flags 会把 `flags.ts` 变成第二个配置中心。AGENTS 的「契约只有一份」也不希望出现两套真源。

所以：**per-tool policy 进 `tool-policy.json`；唯一进 flags 的是总开关 `TOOL_TIMEOUT_POLICY`（布尔）**。
总开关放 flags 是为了让用户在插件页就能打开，不用改 `.env`；它不是策略本身。

### 3.3 优先级

从高到低：

1. `tools.<name>`（单工具）
2. `groups.<group>`（能力组）
3. 实现常量 / 旧配置（`AGENT_BASH_TIMEOUT_S`、`memory-bank.json` 的 `timeouts`）
4. 代码默认（bash 900s、recall 15s、web_search 20s、memoryLight 8s）

每一层只覆盖**显式给了的字段**：工具条目只给 `timeoutMs` 时，`onTimeout` 继续往下继承。
GET 返回 `effective` 与 `source`（`"tool" | "group" | "legacy" | "default"`），界面能解释「这个值从哪来」。

### 3.4 与现有 env 的关系（只做兜底，不双写）

| 现有 env / 配置 | 新关系 |
|---|---|
| `AGENT_BASH_TIMEOUT_S` | **兜底**：policy 没有 `bash.timeoutMs` 时仍按它；有 policy 以 policy 为准。界面永不写 env。注意它是模块级常量（`policy.ts:BASH_TIMEOUT_S`），改 env 仍需重启；policy 是现读，下一轮生效。 |
| `AGENT_BASH_BG_TIMEOUT` | **旧开关保留**：master 关时行为完全不变；master 开且 `bash.onTimeout="background"` 时，以 policy 为准（无需再开旧 env）。不双写。 |
| `memory-bank.json` 的 `timeouts.askMs` / `lightMs` | **兼容读一代**：policy 没有对应条目时继续读它；新界面只写 `tool-policy.json`。详见 §4.4。 |
| `AGENT_APPROVAL_TIMEOUT_S` | 不动。`ask_user` / 审批是 C 类，不纳入本策略。 |
| `CHANCELLOR_WORKER_IDLE_MS` / `CHANCELLOR_WORKER_MAX_MS` / `CHANCELLOR_MANAGER_TIMEOUT_MS` | 不动。它们是 worker / 宰相的执行超时，不是宿主工具调用超时；策略页只做只读说明并指路「设置 → 派活」。 |
| `TOOL_TIMEOUT_POLICY` | **新增总开关**，默认关；注册进 `plugins.json`（布尔、`hot:true`），env 与界面二选一即可。 |

**bash 的特别口径**：`tools.bash.timeoutMs` 是**默认注入值**，不是硬上限。模型显式传了更长的 `timeout` 时，
beforeTool 不覆盖（保持今天的「只补没传的」语义）；后台触发的时点就是内核实际超时的时点。
要做「硬上限」就得覆写模型参数，那是另一种行为（可能杀掉合法的长构建），本方案不做。

## 五、后台化语义

### 5.1 什么叫「转后台」

一次工具调用在超时点发生三件事：

1. **当轮工具结果被替换**：模型收到的是「已转到后台（任务 `bg-…`），完成后会告诉你结果；不要重复执行」，
   不是原始超时错误。替换发生在 `afterTool` 发工具帧之前（现有代码已经这么做，避免 UI 先看到失败帧）。
2. **工作进独立作业**：bash 系复用 `moveToBackground`——新起一个 detached 子进程跑同一条命令，
   写 `.data/bg-jobs/index.json` + `<id>.log`。注意：内核在超时点已经把第一个进程杀了，
   所以后台是**从头重跑**，不是「接着跑」。前 N 秒的输出不会带过去；有副作用的命令可能重复执行。
   这是现有机制的边界，本方案不假装它是「续跑」。
3. **迟到结果独立成条**：`notify:true` 时完成写一条 `pi.assistant` 记录（`sayInChat` 的 `lifediary.say`）
   并投唤醒信封；`notify:false` 时只写 index / log。它**不会**合并回那次工具调用的 `structuredOutput`。

三种 `onTimeout` 的精确语义：

| `onTimeout` | 结算给模型 | 手里的活 | `notify` 默认 |
|---|---|---|---|
| `fail` | `isError:true` + 可行动文案（可换更小范围重试一次） | 能中止就中止（kill 子进程 / abort fetch）；不能中止就放弃等待，结果丢弃 | false |
| `cancel` | `isError:true` + 「已按策略取消」；明确告诉模型**不要重试**；诊断码 `canceled`（不记成功用量） | 能中止就中止；不能中止的实现不允许配这一档（PUT 400） | false |
| `background` | `isError:false` + 「已转到后台（任务 id）……不要重复执行」 | 交给后台作业继续（bash 系 = 重跑同一条命令） | true |

`fail` 与 `cancel` 在「进程必须死」这一点上一样；差别在**结算语义**：前者是「这次没成，可以换方式再试」，
后者是「这次不做了，别再试」。两者都不允许配在不可中止的实现上（`cancel`）或不可配工具上（两者）。

**实现挂点（不改内核）**：

- **bash 系**：`beforeTool` 按 policy 注入 `timeout`（秒）→ 内核超时杀进程 → `afterTool` 按 policy 选
  `fail`（原样透出错误）/ `cancel`（换成「已取消」+ `canceled` 诊断）/ `background`（才调 `moveToBackground`）。
  这就是现有 `AGENT_BASH_BG_TIMEOUT` 路径的 generalization，内核一行不改。
- **recall（外部库）**：`tools.ts` 的 `recall` 不 import policy；装配层注入的 `memoryBank.ask` 闭包里
  读 policy 并传 `timeoutMs` 给 `bankAsk` → `askPersona`。内置 recall 走原同步路径，policy 不生效。
- **web_search**：装配层注入的 `search` deps 里包一层：每次调用取 policy 预算，传给 `webSearch`；
  `webSearch` 把它变成整体 deadline，每个 vendor 的 `AbortSignal.timeout` 取 `min(剩余, 20s)`。

### 5.2 谁收结果、在哪看、能不能取消

| 问题 | 答案 |
|---|---|
| 谁收结果 | 发起调用的那个会话。执事会话经 `wakeOnBgJobFinish` 路由到 canonical 主会话（现有行为）；无执事时回到会话自己。 |
| 用户在哪看 | ① 会话里的一条记录（`notify:true` 时）；② 插件页「工具与命令」页脚的「后台任务」列表（读 `GET /bg-jobs`，按当前会话过滤可选）；③ 现有 `GET /bg-jobs/:id/log` 看尾部 200 行。 |
| 超时后还能取消吗 | 能，只要进程还是**本服务进程**起的：`POST /bg-jobs/:id/kill`。服务重启后 index 里的 `running` 记录不再归属本进程，`kill` 返回 `not_owned`（现有 `killBgJob` 的归属规则；pid 会复用，绝不按 pid 杀）。 |
| 服务重启后结果还会回灌吗 | **不会**。`onFinished` 是内存回调；重启后作业可能还在跑（POSIX detached / Windows 子进程存活），但没人收尾。日志和 index 还在，可以在列表里看到终态；自动回灌不做（见 §7）。 |
| `notify:false` 呢 | 只写 index + log，不写会话、不唤醒。用户要看得去后台任务列表。 |

### 5.3 迟到结果的处理（2026-11-24 用户拍板：保留插话）

现状：`wakeOnBgJobFinish` 的会话路径在忙时走 **steer**（`delegation-wake.ts` 约 872 行注释：
「continueConversation 的提交在忙时天然跟随批1 缺省 steer（插话式唤醒）」）。steer 会在本轮下一个边界
被模型看到——也就是说，后台结果**可能**在同一个 run 里被插进来。

**用户 2026-11-24 拍板：保留插话，不做「等空闲再投」。** 口径：

1. **工具结果层**：替换结果在当轮就是唯一事实；迟到的日志 / 退出码不得改写它（现有 `replacedResult` 已满足）。
2. **投递层**：保留现有两步——`onFinished` 先 `sayInConversation` 写一条会话记录，再投 `wakeOnBgJobFinish`
   信封；忙时 steer 插话，空闲时开新一轮。这就是用户要的「完成后自动发消息」。
3. **不做 `waitForIdle`、不加 `TOOL_BG_WAKE_AFTER_IDLE`**：插话可见性是优点（用户能看到后台结果什么时候回来），
   代价是它可能在当轮回答中途被模型看到——接受。
4. **`notify:false`**：只写 index + log，不写会话、不唤醒；用户去后台任务列表看。
5. 模型侧「已转到后台」的文案已包含「完成后会告诉你结果 / 别再重复执行同一条命令」，不改写它。

### 5.4 与任务中心的关系

- **不复用任务中心票据模型。** 任务中心是 chancellor 的 `Store` / `Ticket`：有租约、车道、死信、回执、
  取消投影、重试冷却。给一条 bash 命令造一张伪票据，会让「取消 / 重试 / 回话」这些语义全部失真。
- **复用 bg-jobs 注册表。** 它是为「后台作业」设计的，字段少、边界清楚；本方案只做 generalize：
  `BgJobRecord` 增加 `kind`（`"shell"` 默认）、`tool`、`conversationId`、`timeoutSeconds`；
  旧记录缺省按 shell 读，向后兼容。
- **任务中心最多做只读入口（二期）**：如果用户希望在一个地方看所有后台，可以在任务中心加一个
  「后台任务」tab，读同一个 `GET /bg-jobs`，**不建票据、不参与任务状态机**。一期不做，先看会话记录 +
  插件页列表够不够。

### 5.5 后台作业的安全口径（沿用现有）

- 完整命令只进 `.log`，index 只存 ≤120 字摘要（`summarizeCommand`）；服务端日志只记条数与耗时。
- 后台继承前台同一进程环境与权限边界，不放宽。
- 非 shell 工具将来若要后台（例如某个长任务），也必须有自己的日志 / 摘要 / kill 归属，不允许把参数原文塞进 index。
- 本方案**不**给 `web_search` / `recall` 开后门：它们是 A 类，永远不写 bg 索引。

### 6.2 回滚矩阵

| 想要的效果 | 怎么做 | 影响 |
|---|---|---|
| 整体回到今天 | `TOOL_TIMEOUT_POLICY=false`（env 或插件页开关） | 端点 404、策略不读、记忆旧卡回来；代码路径逐字节回到今天 |

## 七、明确不做

1. **不做全局单一大超时。** 一个 `AGENT_TOOL_TIMEOUT` 会误杀长构建、拖死证据检索，和「按工具」诉求相反。
2. **不把记忆检索转后台。** `recall` 与每轮轻召回是当轮回答的证据；超时只能失败 / 静默降级 / 更短预算。
   配置层直接拒绝 `recall.onTimeout="background"`。
3. **不做自动重试风暴。** 策略层不重试；只保留实现里已有的一次「库不认识检索开关」回退，且两次共享一个 deadline。
4. **不改工具描述 / 注册顺序。** 工具描述与顺序是 prompt cache 前缀资产（AGENTS 硬约束）；本方案只加配置与包装，不动 schema / 顺序。
5. **不给 `write` / `edit` / `remember` 加超时。** 超时不能撤销已写入；模型重试会写第二遍。
6. **不给 `ask_user` / 审批加自动取消。** 人到点没答是人的决定，不是机器的决定。
7. **不把 HTTP 长任务（记忆导入、整理、夜间任务）纳进本策略。** 它们不是工具调用；要后台化另立项（涉及请求生命周期与重试语义）。
8. **不做「服务重启后自动回灌」。** 需要 outbox / 投递状态机；现有 bg 机制明确不做，本方案不扩大。
9. **不做任务中心伪票据。** 见 §5.4；二期最多加只读 tab。
10. **不做按会话 / 按人设 / 按项目的 policy。** v1 全局一份；真出现「这个执事要更长」再立项（解析点应放在 policy resolver，而不是散在工具里）。
11. **不改 worker / 外部 CLI 的超时。** 它们归 `CHANCELLOR_WORKER_*` / 池 supervisor / 设置 → 派活；本方案只在页面里只读指路。
12. **不把 policy 塞进 flags。** 理由见 §3.2；唯一进 flags 的是总开关。
13. **不做工具耗时的 p95 自动推荐。** 现有 `tool-usage.json` 只有次数 / 成败，没有耗时；没有数据就不假装能推荐。

## 八、验证清单

> 本方案未落地，下面是**落地批**必须跑的；不是现在跑过的结论。

### 8.1 单测（纯函数优先）

- `tool-policy.ts`：`sanitize`（未知键丢弃、越界 clamp、非法枚举回落、单条空 = 删除）；
  优先级 `tool > group > legacy > default`；`source` 投影正确。
- 能力校验：`read` / `write` / `ask_user` 写 policy → `tool_locked`；`recall` 写 `background` → `on_timeout_unsupported`；
  `recall_sessions` 写 `cancel` → `on_timeout_unsupported`。
- 超时分支：`fail` 返回 `isError:true` + 可行动文案；`cancel` 返回「已取消」且不标记可重试；`background` 只对 `backgroundable` 生效。
- 迁移读：`memory-bank.askMs=30000` + 无 policy → effective 30s / `source:"legacy"`；
  policy 20s → effective 20s / `source:"tool"`；policy 删条目 → 回 30s。
- 总开关关：resolver 返回「未启用」，不读文件；所有调用点走原路径（用 spy 断言行数 / 参数不变）。
- `bankAsk` 的预算：`askPersona` 两次尝试共享同一个 deadline（用一个可控假 spawn 断言总耗时 ≤ 预算，而不是 2×）。
- `web_search`：多源时整体预算生效（第一源用掉 18s，第二源只剩 2s，不是再给 20s）。

### 8.2 HTTP 探针（真起服务 + 真 HTTP）

新增 `scripts/tool-policy-probe.ts`（照 `settings-probe.ts` / `memory-bank-probe.ts` 的写法）：

1. master 关：`GET/PUT /api/v1/agent/tool-policy` → 404。
2. master 开：`GET` 返回全部能力组，其中至少 4 个可配工具 + 锁定原因；`PUT` 局部更新 → 再 `GET` 值持久化。
3. 非法：未知工具 400、`tool_locked` 400、`on_timeout_unsupported` 400、坏 timeout 400。
4. 原子写：并发 PUT 两次，最终文件是完整 JSON（临时文件 + rename）。
5. 重启后仍在：进程重启再 GET，值不丢。
6. 记忆迁移：先 PUT `/memory/bank {timeouts:{askMs:30000}}`，再 GET tool-policy → `source:"legacy"`、30s；
   PUT tool-policy recall 20s → 20s；删条目 → 回 30s。

### 8.3 假慢工具探针（策略分支）

在探针脚本里注册一个只在探针中存在的工具（不进生产注册表）：

```text
probe_slow(ms) —— 睡 ms 毫秒后返回 "done"
```

用例：

- `fail`：policy 200ms、工具睡 5s → 工具结果在 ~200ms 返回 `isError:true`，文案含「超时」；探针退出前确认没有把 5s 的结果写进 transcript。
- `cancel`：同上，结果是「已按策略取消」，`isError:true` + 诊断码 `canceled`，明确不提示重试。
- `background`：探针工具在 catalog 里声明 `backgroundable:false`；把它写成 background 应在 PUT 时被拒，
  证明「没有作业句柄就不许假装后台」。
- 锁定工具：`read` / `write` 的 policy 被 400 拒。

### 8.4 真 bash 对比（新旧路径）

用现有 `scripts/bash-timeout-probe.ts` 扩展，或新增 `tool-policy-bash-probe.ts`：

| 场景 | 旧路径 | 新路径 | 断言 |
|---|---|---|---|
| `sleep 5`，预算 1s，`fail` | `AGENT_BASH_TIMEOUT_S=1` → 错误 | master 开 + `bash:{1000,fail}` | 两者都是错误、都含超时；新路径不产生 bg 索引 |
| `sleep 5`，预算 1s，`background` | `AGENT_BASH_TIMEOUT_S=1` + `AGENT_BASH_BG_TIMEOUT=true` | master 开 + `bash:{1000,background}` | 两者都返回「已转到后台」；bg index 有记录；log 有输出；`kill` 可中止 |
| `powershell` 长命令 | 今天没有默认注入（会一直跑） | 新路径应注入并转后台 | 证明 1.3 的缺口被补上 |
| 当轮不回填（工具结果层） | — | 后台完成时本轮仍在跑 | 工具结果仍是「已转到后台」；完成记录走插话，不改写当轮工具结果（§5.3） |

真跑时看输出，不只看 exit code（AGENTS 口径）。

- 移动端：不受影响（无新页面）；确认旧 `PUT /memory/bank {timeouts}` 仍工作。
