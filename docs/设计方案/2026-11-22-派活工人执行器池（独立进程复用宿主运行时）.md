## 一、结论

1. **worker 不在宿主进程里跑，也不再每票起一个新进程。** 改成**执行器池**：N 个常驻池进程，
   每个进程一个 Harness，**同一时刻只跑一个会话**（串行复用，进程不随票退出）。
2. **隔离单位 = 活跃会话 = 1 票；并发单位 = 池进程数 N。** 不在一个进程里堆多个并发会话。
3. **宿主进程只留主 Harness**（总管 / 执事 / 普通助手 / 群 / 定时轮），**永不跑任务会话**。
   worker 怎么崩，聊天与服务都不受影响。
4. **池进程复用宿主同一套运行时**（`pi-durable` + 同一份任务 profile + 同一份工具实现），
   不维护第二套内核、不复制注入逻辑。
5. **宿主 → 池的方向单向**：池进程起本地 HTTP（`127.0.0.1`，随机端口 + 一次性 token），
   宿主作为客户端连它；`submit / steer / abort / escalate / progress / report` 走 HTTP + SSE，
   **删掉「stdin 一行 JSON」那条通道**。
6. 调度器（chancellor）**仍在宿主进程内**（现状就是 `startDelegation → runtime.run → runChancellor`），
   只新增一个 `Employee` 实现：`pool`。外部 CLI 的 `Employee` 不动。
7. **并发不是「几路」的固定数字，是「有界池 + 队列 + 内存预算」三个量。** 默认 `WORKER_POOL_SIZE=4`，
   上限由内存预算决定（默认 4 GB ≈ 26 个进程），排队可见、可取消。二三十票的常态是**排队**，不是三十个进程。
8. **等的时候不占进程**（借 `agent-autoloop` 的「一轮不等人」）：worker 发上报或等人答复时结束本轮、
   把会话挂起并释放池进程，答复到了再接着跑。这样「30 票在飞」里真正占进程的只有正在调模型的那几票。
9. **本次只搬派活工人，普通助手留在宿主进程。** 理由与将来的迁移代价见 §三，这是本方案最容易被
   误读的一条边界，单独成章。

## 二、为什么

### 2.1 两种「Worker」的现状（2026-11-22 代码级核对）

仓库里 `worker` 一词指三种东西，先说清，否则后文全是歧义：

| 叫法 | 实体 | 跑在哪 | 代码 |
|---|---|---|---|
| **普通助手（对话）** | `chatKind=worker` 的会话 | **宿主进程**，与总管共用同一个 Harness | `agent/session-open.ts:337`、`agent/lifecycle-injections.ts:203` |
| **派活工人（native）** | `worker-main.ts` | 每票 spawn 一个独立子进程，干完退出 | `packages/chancellor/src/employee/native.ts` |
| **分管宰相（manager）** | `worker-main.ts --role manager --domain` | 子进程，会话与库常驻复用 | `packages/chancellor/src/worker-main.ts:587` |

本文的改造对象是第二种。第三种是「派活的脸」，另立方案（§待拍板 6）。

**普通助手 vs 派活工人对照**

| | 普通助手（对话，chatKind=worker） | 派活工人（chancellor employee） |
|---|---|---|
| 运行容器 | 宿主 `Harness` 里的一个会话 | 独立进程（native）或外部 CLI 进程 |
| 归属 | 主 app，用户直接对话 | `delegate` 工具 → chancellor 调度器 |
| 人设 | `.data/worker-persona.md` + `WORKER_PERSONA_CHAT_TOOLS`（代码常量） | 同一份人设文件；TASK.md「你是谁」段 |
| 固定文本 | 验证铁律、注入防线（代码常量） | TASK.md 开场 + 交付契约 + 边界 + `WORKER_RULES` |
| 记忆 | global + 绑定项目 + 会话（按相关度召回） | 无引擎；仅 ticket 项目记忆 16 条/2000 字 |
| 技能 | 全局 + `partners.worker` 覆盖层（2026-11-21 起） | 不读技能索引 |
| 工具 | 全量 harness（默认 16 件 + 按需池） | native 四件（read/write/edit/bash）+ `escalate`；外部 CLI 自带 |
| 模型 | 会话可切（composer pill） | native 走 `.data/executor.json` 的干活模型；外部 CLI 自己配置 |
| 产出 | 对话消息 | `REPORT.md`（status/summary/artifacts/attention） |
| 审批 | 有（按策略/审批档） | native 裸工具循环，无审批；外部 CLI 非交互全放行 |

### 2.2 运行时结构（关键）

- 调度器**已经在宿主进程内**：`startDelegation()` → `runtime.run` → `runChancellor()` 都是同进程调用
  （`delegation-delegation-kickoff.ts` / `delegation-actions.ts`）。
- 只有**执行器**是子进程：`employee/native.ts` spawn `worker-main.ts`；外部 CLI 由 `employee/*` spawn。
- `native.ts` 的注释「pi-durable 一个进程一个 Harness、一份存储，在同一进程里再开一个 Harness 会和宰相的库打架」
  ——限制的是 **chancellor 内部 manager 与 worker 同进程**，不是"宿主 Harness 不能多开一个任务会话"。
  宿主本来就一个 Harness 跑总管/执事/普通助手/群多个会话。
- `worker-main.ts` 自己也是 pi-durable，用的是**独立 DB、独立 registry、独立工具面**，不是另一套内核。

### 2.3 派活路由（谁派的）

- 执事在自己领域内派活：`delegate-routing` → `managers:false`，chancellor **直派**（planTicket + 执行器）。
- 总管 / 普通助手派活：默认 **managed**，chancellor 起一个 **manager 子进程**，由 manager 再拆单/派 worker。
- 也就是说：**"谁派的"只决定两张脸（manager 层）和汇报去处**，worker 本身同一份人设/同一套工具配置。
  但 managed 路径多了一层 manager 子进程，这是合并 native worker 时必须先处理的。

### 2.4 任务专线是投影，不是运行时

`task-<ticketId>` 会话（D22）只是把进度/REPORT/留言双写进宿主，方便用户查看与回话；
worker 实际仍在 chancellor 的独立进程里跑。**合并的天然落点就是让这条专线变成真正的运行时。**
（注：本文最终没有复用这条专线做运行时，理由见 §十 待拍板 11 的「另建 `task-run-`」——投影里混着给用户看的
进度通知、卡片文字与用户回话，混进任务上下文会污染模型。）

**结论：分离没有一条"产品/安全硬约束"级别的理由；只有历史复用、执行器形态和调度归属。**

### 2.6 为什么不选「路线 B：worker 跑在宿主进程内的隐藏会话」

那样失败半径从「1 票」变成「全部对话」，换来的是上下文/字段统一。但**统一不需要靠合并进程来换**：
池进程里同样是「一个 Harness + 一个任务 profile + 同一份工具实现」，字段表一处维护、一份注入逻辑，
宿主那边一行代码都不动。拿宿主稳定性去换统一，代价不对等。

### 2.7 为什么不维持「每票一进程」

- **每次都要重新装配**：起进程、开库、建 Harness、注册工具面、建模型客户端——票越多，这部分重复越多。
- **每票一份 `.agent.sqlite`**：文件数随票线性增长，票与票之间零复用（transcript 也没人看）。
- **通道太薄**：stdin 一行 JSON + stderr 文本行，插话、上报、审批、进度都得靠"约定"，这正是 chancellor
  显得毛坯的一半原因；问题不在"是进程"，而在"是个裸子进程"。

### 2.8 为什么不选「一个进程多个并发会话」

这是本文要回答的那个问题，单独放 §四 展开。一句话：**单线程 + 共享进程级资源（内存/DB/事件循环）
让"多点并发"变成"多一份共死风险"，而省下来的内存本来就不是瓶颈。**

### 2.9 现状容量事实

| 项 | 现状 | 来源 |
|---|---|---|
| 宿主进程 | 一个 `node --import tsx src/index.ts`，实测 RSS 159 MB；旁挂 Go 壳 85 MB（只管起停与探活） | 本机实测 |
| 内核实例 | 模块级单例 `opened / opening`，全进程一个 Harness | `apps/server/src/agent/lifecycle-harness.ts` |
| 总管 / 执事 | **同一进程、同一 Harness 里的两条会话**；执事 = `partners` 表一行 + 冻结 SOUL 快照，不是进程 | `partners.ts` / `partner-runtime.ts` |
| native worker | **每票 spawn 一个 `worker-main.ts`**，自带独立 `.agent.sqlite`、独立 Harness、独立工具面；进程退出码即结论 | `packages/chancellor/src/employee/native.ts` / `worker-main.ts` |
| 宿主↔worker 通道 | stdin 一行 JSON（插话/中止）+ stderr 结构化行（上报） | 同上 |
| 调度器 | 在宿主进程内（`startDelegation` → `runtime.run` → `runChancellor`） | `delegation-*` |
| 并发与超时 | `CHANCELLOR_MAX_PARALLEL_TASKS=3`（`scheduler.ts:106`）、`CHANCELLOR_WORKER_TIMEOUT_MS=10min` | `packages/chancellor/src/config.ts` |
| 机器余量 | 32 GB 内存，空闲 9.7 GB | 本机实测 |

由此得到今天真实的失败半径：**worker 崩 = 1 票；宿主崩 = 全部对话一起断**。

## 三、范围边界：普通助手留在宿主进程

用户 2026-11-22 的口径是「worker 要在独立进程」。落地时这条口径**只作用于派活工人**，
普通助手会话（新建对话产生的那个）仍在宿主 Harness 里跑。这不是遗漏，是明确的保留决定，
理由逐条可验证：

| # | 普通助手对宿主的硬依赖 | 代码位置 | 搬走要付的代价 |
|---|---|---|---|
| 1 | **历史读全走宿主 Harness**：会话列表 / 转录 / 搜索 / 地图 / 导出 / 用量，全部 `getHarness()` 读同一个 `agent.sqlite` | `agent/session-index.ts`、`agent/session-transcript.ts`、`agent/session-evidence.ts` | 要么多进程共写同一 SQLite 文件（WAL + busy_timeout 5s 能跑，但跨进程事务与迁移版本会变成新的失败面），要么给所有历史读接口加一层代理，等于重写半边 API |
| 2 | **记忆引擎是宿主进程内单例** | `agent/assist.ts:109`（`createMemoryEngine`，`MEMORY_DB_PATH`） | 每进程一份引擎 → 抽取/巩固/召回跨进程重复计费，或另做一个记忆服务 |
| 3 | **审批是进程内等待**：`waitForApproval` 靠内存表 + SSE 弹卡，人回来点才继续 | `agent/turn-gate.ts`、`approvals.ts` | 要把「等人」做成跨进程协议，比池的「让出进程」复杂得多（池的等待方是 worker 自己，普通助手的等待方是用户） |
| 4 | **流式输出直连 SSE**：`chatStream` 的 delta / thinking / tool 事件逐条推给界面 | `agent/session-stream.ts` | 要么代理流，要么池进程直接对外开 SSE（那它就不再是"内部执行容器"） |
| 5 | **交互频率**：普通助手是逐句对话，冷启动与进程边界成本按句计 | —— | 池化收益在长任务，对逐句对话是纯开销 |

反过来看，**派活工人一条都不占**：不流式、无审批、无记忆、无技能、历史只有 TASK.md / REPORT.md，
产出就是一个文件。所以「搬出去」对它是纯收益，对普通助手是纯代价。**同一条口号不能同时套在两个东西上。**

如果将来确实要把普通助手也搬出去，触发条件是：①历史读改成服务化（独立读服务或共库方案定案）；
②记忆引擎服务化；③审批改成可跨进程的状态机。三条都不满足就搬，等于把今天最稳的一条链
（聊天不断）押上去换一个用户看不见的收益。

**仍然合并的部分**：概念、配置页、上下文来源标注（原路线 A）——这三样不动运行时就能消掉大部分
「这俩到底什么关系」的困惑，见 §六 分期 P1。

## 四、隔离单位：一个进程同一时刻一个会话

### 4.1 先把「崩」分成三层

| 层 | 例子 | 会话级能不能兜住 |
|---|---|---|
| ① 轮次级 | 工具报错、打转（已有 `loop-guard`）、回合超限 | 能，而且今天就已经兜住了 |
| ② 票级 | 模型 4xx/5xx、连接断、超时、REPORT 不合规、无进展、验收 blocked | 能：这一票失败，其他票无关 |
| ③ 进程级 | 未捕获的异步异常、OOM、原生模块段错误、事件循环被同步活卡死 | **不能**：进程内没有任何东西能兜住 |

②占绝大多数，**在任何形态下行为都相同**——分不分进程、一进程几个会话，都不改变②。
只有③需要进程边界，而③的关键不是"一票一进程"，而是"别把两票放进同一个会被③带走的坑里"。

### 4.2 三个候选

| 形态 | 失败半径 | 装配/开库成本 | 内存 | 单线程互扰 |
|---|---|---|---|---|
| A 每票一进程（现状） | 1 票 | **每票一次** + 每票一份库 | 每票 60–120 MB 峰值 | 无 |
| B 一进程 N 并发会话 | **池内 N 票一起死** | 一次装配摊给 N 票 | 一份 | **有**：大文件读写、JSON 解析、SQLite 同步 IO 互相拖 |
| **C 一进程 1 个活跃会话，进程跨票复用** | **1 票** | **一次装配摊给该进程跑过的所有票** | 一份，池大小 N 决定总量 | 无（同一时刻只一个在跑） |

### 4.3 选 C：把并发放在进程维度，不放在会话维度

C 同时拿到 A 和 B 的好处，并且丢掉两者各自最贵的那部分：

- 相对 A：省掉每票的装配与开库（进程常驻，票来了只开会话）；库文件不再按票增长。
- 相对 B：失败半径从"N 票一起"回到"1 票"；没有单线程互扰；**每票的 cwd / 租约 / 路径守卫仍是进程级私有**，
  不需要在一个共享进程里给每个会话做路径隔离（那是安全边界上最容易退化的一处）。
- 代价只有一个：并发上限 = N，而不是"一个进程能塞几个"。而这是**可配置的资源问题，不是稳定性问题**。

判据写死一句话，方便以后回看：**隔离单位是「活跃会话」，不是「会话」。**
进程可以活很久、跑很多票，但同一时刻只有一个活跃会话，所以进程级崩最多带走一票。

### 4.4 池进程的生命周期

- 常驻：池进程起来后不随票退出；票结束 → 结束会话（abort + close）、清工具状态，接下一票。
- 回收：**每跑满 K 票（默认 20）或 RSS 超阈值（默认 1.5 GB）主动退出并由 supervisor 重拉**。
  串行复用会让内存泄漏跨票累积，回收是这条路线必须配的保险丝，不是可选优化。
- 空闲回收：超过 `WORKER_POOL_IDLE_MS`（默认 30 分钟）无活自动退出，池按需拉起。

### 4.5 崩溃的责任划分

| 谁崩了 | 谁负责 | 怎么做 |
|---|---|---|
| 会话级失败（②） | 池进程内 | 结算成该票的 `EmployeeOutcome`，REPORT 照旧；调度器按现有口径判 pass/failed |
| 池进程崩（③） | 宿主 supervisor | 按「票 → 进程」绑定表找到在跑的那一票，按票重派（`delegations.sqlite` 回执幂等 + `inflight.json` 已有）；崩溃写一条审计 |
| 会话卡死不崩（事件循环被占） | 宿主 supervisor | 心跳 + 超时（沿用 10 分钟，上报/插话往来算心跳）→ kill 该票绑定进程 → 按票重派 |
| 宿主崩 | 不变的现状 | durable 重启续跑；池进程发现连接断开 → 在跑的会话一律 abort 退出，不留孤儿 |

### 4.6 二三十票的时候怎么办（容量口径）

先把量算出来。**每进程基线 = 123 MB**（本机实测：`node --import tsx` 只加载服务端 harness 依赖图、尚未开会话，
RSS 123 MB、耗时 3.0 s；在线宿主 159 MB）。取 150 MB/进程做预算：

| 形态 | 并发 | 常驻内存 | 30 票的总时长 |
|---|---|---|---|
| 今天的每票一进程 | 3（`MAX_PARALLEL_TASKS`） | 峰值 3 × 150 ≈ 0.5 GB | 10 轮 |
| 每票一进程放开到 30 | 30 | **≈ 4.5 GB**，且 30 次 3 s 冷启动同时撞 CPU | 1 轮 |
| **有界池 N=4 + 队列** | 4 | **0.6 GB** | 8 轮 |
| 有界池 N=8 + 队列 | 8 | 1.2 GB | 4 轮 |

所以「两路够不够」的答案分两半：

- **作为兜底够**：队列是有界的，不会因为一次派 30 单把机器打爆。
- **作为默认不够**：2 会把 30 票排成 15 轮，用户看到的是「怎么这么慢」。
- **但也不该一路加到 30**：30 个进程 4.5 GB + 30 次冷启动，而且真实场景里大部分票在**等人/等上报**，
  不是在算——那部分票不该占进程（见结论 8）。

落地口径：

1. `WORKER_POOL_SIZE` 默认 **4**（可配 1–16），按「同时真在调模型的票数」设，不按「派出去的票数」设。
2. `WORKER_POOL_MEM_BUDGET_MB` 默认 **4096**：池内进程 RSS 合计超预算就不再起新进程，改为排队。
3. **排队一等公民**：任务中心要能看到「在跑 N / 排队 M」与队列顺序，能逐票取消；一次派 30 单时
   用户必须立刻知道这不是 30 个都在跑。
4. **等待让出进程**：`escalate` 之后到答复到达之前，该票不占池进程（会话挂起，答复到了再 resume）。
5. 冷启动要遮住：池在有活时预热到 N，回收与空闲退出不要和工作高峰重合（默认 30 分钟无活才退）。

### 4.7 别人是怎么做的

本机参考仓 `D:/Projects/reference/agent-autoloop`（中文自建实现，协议文档 `docs/protocol.md`）的做法几乎就是这个形状：

- **「Agent 就是一个进程」**：给它提示词，它打印最后一条消息；一轮 = 一次执行，交一份回执就结束。
  不要求 SDK、不要求同语言，外部 CLI 与脚本同一契约。
- **并发是三层闸 + 容量**：规则组 `parallel`、单条规则 `maxActive`、Agent 级 `maxActive`，
  再乘接单程序自己的 `worker.capacity`（默认 2）。三层同时生效，调低后等已领取的轮次收尾再派新单。
- **「一轮不等人」**：要问你就结束这一轮，收到回答后再开始，等你的时候**不占进程、不花 Token，重启也不丢**。
- 重复 claim / 心跳 / 停止 / 重启恢复都是协议层的事情，不靠进程活着来保证。
  其 README 给了个量级证据：1000 个同时等待的长轮询只占 170 MB RSS——**等待不占进程**是省资源的关键，不是靠共享进程。

主流 Agent 产品分两类，各自都自洽：

| 做法 | 代表形态 | 优点 | 代价 |
|---|---|---|---|
| 同进程内多 subagent | Claude Code 的 subagent、Codex 的子任务 | 零冷启动、上下文共享方便 | 无隔离，一起崩；长任务会拖慢主交互 |
| 一任务一沙箱 | 云端 background agent（容器 / VM 起一个跑一个） | 隔离最彻底、可跨机扩容 | 冷启动与成本最高，本地桌面机不划算 |
| **有界池 + 队列 + 租约** | 通用作业队列（BullMQ / Celery / Temporal / k8s Job 都是这个骨架） | 并发可控、成本可算、崩溃按单重派 | 要自己做排队可见性与背压 |

本仓要的是第三类：**本地桌面机、无云端预算、要求聊天永不断**。这类系统的通用答案是「池大小控制并发、
队列吸收尖峰、租约与重试兜崩溃」，而不是「一个进程塞多个会话」或「一票一进程」。

## 五、改动

### 5.1 新增池进程入口

`ts/apps/server/src/pool/pool-main.ts`（或独立 `apps/pool`）——单进程，内含：

1. 一个 `Harness`（`pi-durable`），库 = `WORKER_POOL_DB_DIR/pool-<n>.sqlite`（每进程一份，不与宿主库混）。
2. 一个**长度 1 的执行队列**：同一时刻最多一个活跃会话；票到 → 建会话 → 跑 TASK → 结算 → 关会话。
3. 一个本地 HTTP 服务（`127.0.0.1`、随机端口、启动时由 supervisor 生成一次性 token 经 env 传入）。
4. 任务 profile：复用宿主同一套注入（人设 / TASK.md / 项目记忆 / 交付契约 / 边界 / 上报规则），
   **不注入**聊天前缀、记忆召回、技能索引、关于我、低频工具索引。
5. 工具面硬白名单 `{read, write, edit, bash, escalate}`：定义层不给别的工具，`beforeTool` 再拦一次
   （防 deferred / `tool_search` 绕过——2026-11-16 踩过这个坑）。
6. 无审批：任务模式固定「无人值守放行」，边界只靠白名单 + 路径守卫 + 租约。

**部署边界（2026-11-22 实测）**：池进程入口是**源码 `.ts`**，用 `node --import tsx` 起。
- 源码态（桌面壳 `node --import tsx src/index.ts` / `pnpm dev`）：可用。
- `node dist/index.js` 单文件产物：没有 `src/pool/pool-main.ts`，**池不可用**；
  宿主启动时 `WorkerPoolSupervisor.available()` 为 false → **不注入 PoolClient** →
  `createEmployee("pool")` 回落 native + 告警（不会把单派进起不来的进程）。
  想让 dist 也支持池，需要把 `pool-main.ts` 作为第二个构建入口（或预编译），目前刻意没做。

### 5.2 IPC 契约（本地 HTTP + SSE）

| 端点 | 方向 | 语义 |
|---|---|---|
| `POST /run` | 宿主 → 池 | 派一票：`{ticketId, dir, workDir, instruction, doneWhen, upstream, model?, tools?}`；池内排队，返回 `{accepted, sessionId}` |
| `GET /run/:ticketId/events` | 池 → 宿主 | SSE：`progress` / `escalation` / `report` / `settled{ok,reason}` |
| `POST /run/:ticketId/say` | 宿主 → 池 | 插话（`steer` 语义与宿主一致） |
| `POST /run/:ticketId/abort` | 宿主 → 池 | 中止该票 |
| `GET /health` | 宿主 → 池 | `{ok, poolIndex, rss, activeTicket?, finishedTickets}` |

- **鉴权**：只监听回环 + 一次性 token（与宿主既有鉴权口径一致，不复用用户令牌）。
- **崩了就断**：宿主侧把 SSE 断开视为该票失败信号，进入重派流程；不需要额外的心跳协议。
- `escalate` 由池进程 **直接调宿主的既有上报路由**（HTTP，带内部凭据），不再走 stderr 文本行。
- 这条通道同时把「审批 / 进度 / 上报 / 插话」都变成一等公民，取代现在的 stdin 一行 JSON。

### 5.3 宿主侧 supervisor

`ts/apps/server/src/worker-pool/supervisor.ts`：

- 起停：按需拉起 N 个池进程；端口与 token 由 supervisor 发放；进程异常退出按退避重拉（熔断同壳的口径）。
- 绑定：内存表 `ticketId → poolIndex`（进程内，重启即失，靠重派补齐，不当账本）。
- 看门：心跳超时 → kill → 重派；`/health` 间隔探活；RSS 超阈值 → 优雅回收（等当前票结算再退）。
- 观测：每票记 `{ticketId, poolIndex, 启动/结算时刻, 退出原因, 峰值 RSS}`，落 `.data/worker-pool.jsonl`，
  只记枚举与数字，不记指令正文。

### 5.4 chancellor 侧：新增 `Employee` 实现

- `packages/chancellor/src/employee/pool.ts`：实现既有 `Employee` 契约（`run / capabilities`），
  内部通过注入的 client 调宿主 supervisor，**chancellor 不 import 宿主**（同 `setInternalAsk` /
  `setWorkerPersonaSource` 的先例，宿主推、chancellor 收）。
- `employee/index.ts` 增加 `pool` 档；`CHANCELLOR_EMPLOYEE=pool` 可全局切。
- `native` 档保留，作为回滚与「强制隔离」档。
- 影响面：`planTicket` / 工单 / worktree / 租约 / 合并 / 回执 / 崩溃恢复**一行不改**——
  池只换执行容器。

### 5.5 工作目录与路径守卫（安全上最容易退化的一处）

- cwd 不再是进程属性：`/run` 带 `workDir`，池进程在会话内**先用 `path-guard` 校验**再开工；
  bash 的 `cwd` 参数、`read/write/edit` 的路径都按该票根解析，跨票不继承。
- 每票结束清会话状态（工具缓存 / 当前目录 / 挂载），避免「上一票的根」渗到下一票。
- 越权写、租约、合并点判定留在调度器（宿主），池只负责执行与自证。

### 5.7 工具与审批（硬边界）

- **硬白名单**：任务会话只允许 `read / write / edit / bash / escalate`；其他工具在工具定义层不出现，
  并在 `beforeTool` 再做一次拦截（防 deferred/tool_search 绕过——2026-11-16 踩过这个坑）。
- **无审批**：任务会话的 write/bash 不经过 `needsApproval` 弹卡；策略固定为"无人值守放行，仅受白名单与路径/租约约束"。
  这与现状 native worker 的裸工具循环一致。
- **无记忆/技能**：`remember/recall/skill/tool_search/delegate/…` 不在白名单；注入层不注记忆/技能/关于我。
- **路径**：cwd = worktree / task 目录；沿用 `path-guard` + 写入声明 + 租约/合并。
  任务会话比 worker 多一层 path-guard（worker 只有 cwd + 提示词），边界不会更松。
- **上报**：`escalate` 直接调用宿主既有 escalation 路由（不再走 stderr/stdin），答复走 steer/插话。

### 5.9 两套运行时差在哪（一）：上下文管理

**这是"合并"真正要补的那一半。** 今天的 native worker 和宿主虽然用同一颗 `pi-durable`，
但**宿主把内核的能力都用上了，worker 一个都没接**——根因就一行：`worker-main.ts:313` 的
`Harness.open` 只传了 `models / registry / env / onReport`，**`settings` 一个字段都没传**。
所以下面这些在宿主是"每轮现算的策略"，在 worker 是"内核出厂默认"或者"干脆没有"。

| 能力 | 宿主（现状） | worker（现状） | 池内要做 |
|---|---|---|---|
| **压缩触发点** | `settings: () => buildHarnessSettings(...)`，默认按窗口 **70%** 压，按各模型 `contextWindow` 换算落 `modelOverrides`（`compaction-settings.ts:52`） | 不传 settings → 内核默认 `reserveTokens 16384`。窗口 131072 时触发点 = 131072−16384 ≈ **87.5%**，比宿主晚得多 | **接**：同一套 `buildHarnessSettings`，按票的模型窗口算。**坑**：`modelOverrides` 的键必须是 `${provider}/${modelId}`，内核 `compactionPolicy()` 精确查表、**没有通配档**（实读 `compaction.js:195-204`），写 `"*"` 能过类型检查但永远命中不了 |
| **压缩后保留量** | 内核默认 20000（不暴露给用户） | 同左（都是默认） | 保持默认，不新增旋钮 |
| **系统提示结构** | 9 个 `LIFECYCLE_SECTIONS` + 尾部动态注入（§5.6 已列） | 一个静态字符串：`WORKER_RULES` 8 条 + 整份 `TASK.md` | **不接**（任务模式只有 §5.6 那几段） |
| **动态内容走尾部** | 记忆召回 / 当前项目 / 技能斜杠 走尾部 user 消息，不污染缓存前缀（2026-11-19 前缀锁定） | 无 | **不接**（任务上下文一次成文，本来就不变） |
| **回合上限** | `MAX_TURNS` 默认 100，剩 5 轮先注收尾提示，撞限封工具（`turn-gate.ts:64`、`lifecycle-injections.ts:383`） | **无**。只有 `WORKER_TURN_BUDGET`（默认 3），那是"续行轮预算"，不是单轮工具回合上限 | **接**：单轮 `MAX_TURNS` 同宿主；续行预算保留，两者是不同层 |
| **工具结果投影** | `TOOL_PROJECTION` + `TOOL_PROJECTION_WORKER`（打手会话默认开），bash 输出超长先摘要（`tool-projection.ts:214`） | **无**：bash 原样吐全文，靠内核 `truncate` 截断 | **不做**（2026-11-22 定）：投影的挂载判定依赖宿主会话身份（`partner` / `chatKind`），池内没有这个概念；bash 输出本就被内核按 `DEFAULT_MAX_BYTES/LINES` 截断，再加一层摘要会丢代码任务最需要的原文 |
| **防打转** | `loop-guard`：同指纹 30 次、read 窗口 128/重复 4、乒乓 12/2、轮转 16/4（`loop-guard.ts:24-40`） | **无** | **接**：无人值守更需要它，这是纯收益 |
| **流超时 / 失败重试** | `stream.timeoutMs`、`afterFailedRun` 可配；重试吃内核默认 3 次 | 全吃内核默认 | 保持默认（够用，不新增旋钮） |
| **上下文窗口 / 输出上限** | `contextWindow` 取供应商目录元数据，回落 131072；`maxTokens` 回落 4096 | 写死 131072 / 4096（`worker-main.ts:940`） | **接**：按票的模型取元数据，别写死 |

一句话：**上下文管理上，worker 今天相当于"内核默认档"，宿主是"调过的档"。池内把宿主那套搬过去，
收益是压缩更早（省钱、少撞窗口）、有防打转、有回合兜底，成本是几十行 settings + 两个 hook。**

**为什么这件事没有想象中大**（2026-11-22 用户判断，核实后成立）：上面每一行都不是"重写一套"，
而是**把宿主已有的模块搬进池进程的装配里**——`compaction-settings.ts`、`loop-guard.ts`、
`turn-gate.ts` 的 `MAX_TURNS`、`reliability.ts` 的 `bashTimeoutSeconds` 全是纯函数或零 IO 的类，
`import` 过来即可。真正要新写的只有三样：池进程入口、IPC、supervisor。内核一行不用改，
因为两边本来就是同一颗 `pi-durable`。

### 5.10 两套运行时差在哪（二）：权限与护栏

| 能力 | 宿主 | worker | 池内要做 |
|---|---|---|---|
| **访问档** | 三档 `full / read-only / no-shell`（`policy.ts:14`），可运行时切 | **无** | **不接**：池内固定"全放行"，边界靠白名单 + 路径 + 租约（与现状 worker 一致） |
| **审批** | `ask-all / ask-critical / none` 三档，`waitForApproval` 弹卡等人 | **无**（没人可问） | **不接**：无人值守，要人就走 `escalate` |
| **无人值守策略** | `unattended`：deny / skip / allow 三态（`unattended.ts:133`） | **无** | **不接**：worker 天生无人值守，白名单已经是更硬的形态 |
| **路径守卫** | `path-guard`：read/write/edit 目标必须落在**多根**（工作区 + 已登记项目）内；`full` 档可旁路；`read` 对用户附件开例外（`path-guard.ts:120`） | `restrictPaths`：只允许 taskDir + workDir 两处；**只拦 read/write/edit，bash 不拦**（`worker-main.ts:878`） | **接**：每票现取 taskDir + workDir 作根（不能闭包进 registry——池进程跨票复用，第二票会拿到第一票的边界）。**bash 不加 cwd 校验**（2026-11-22 定）：bash 工具没有 `path` 参数，按命令文本判是误杀源（`git -C` / `pnpm --dir` 都是正常用法）；真正的边界是 worktree 副本 + 宿主合并时的越权检查 |
| **只读命令白名单** | `read-allowlist`：只读档下把 `ls/cat/grep` 这类降成放行 | **无** | 不接（没有只读档） |
| **bash 默认超时** | `beforeTool` 注入 `BASH_TIMEOUT_S`（默认 900s，`lifecycle-harness.ts:859`） | **无**：模型不传 timeout 就无限等 | **接**：同宿主，防一条命令挂死整票 |
| **写工具闸门** | `WRITE_TOOLS` 12 项 + `readOnlyBlockReason` | 白名单 5 项（定义层 + beforeTool 双拦） | 保持 worker 形态（白名单更窄，不需要再叠一层） |
| **闸门审计 / 时间线 / 用量账** | `gate-audit` + `turn-timeline` + `tool-usage` 三本账 | **无**，只有 `log()` 文本行 | **接（部分）**：池内按票记 `worker-pool.jsonl`（§5.3），工具级三本账不做 |

**这里有一条必须写在脸上的边界**：bash 在**宿主和 worker 两边都不做路径拦截**——`GUARDED_TOOLS`
只含 `read/write/edit`（`path-guard.ts:19`）。worker 的"只在两个目录里干活"一直是提示词规则 +
worktree 副本，不是内核级沙箱。池内如果只搬不改，这条会原样继承。要不要给 bash 加 cwd 校验是
**新增安全面**，见待拍板 14，不能算"和今天一样"。

## 七、验收标准

要能被别人独立复跑：

1. **隔离**：池进程 `kill -9` 时，宿主仍在服务（聊天可发、可回读），被杀进程正在跑的那一票自动重派并最终结算；
   `.data/worker-pool.jsonl` 有对应的崩溃与重派记录。
2. **串行复用**：一个池进程连跑 3 票，`GET /health` 的 `activeTicket` 任何时刻至多 1 个；票据库只有一份 `pool-N.sqlite`。
3. **回收**：跑满 `WORKER_POOL_RECYCLE_TICKETS` 票后进程 PID 变化，且没有半途丢票。
4. **通道**：插话（`say`）在跑动中生效且落进该票上下文；`escalate` 能在宿主侧出上报卡并回投续跑；abort 立即生效。
5. **边界**：白名单外工具调用被拒（含 `tool_search` / deferred 路径）；跨票路径不继承（第二票写上一票的 worktree 被路径守卫拒）。
6. **上下文**：会话注入快照 = §5.6 字段表，缺一漏一算失败；压缩触发点按 70% 生效（§5.9）；
   单轮工具回合上限、防打转、bash 默认超时都在池内生效。
7. **并发与队列**：一次派 12 单、池大小 4 时，任务中心立刻显示「在跑 4 / 排队 8」；逐票取消生效；
   聊天延迟无可感变化；池内 RSS 合计不超预算。
8. **等待让出**：worker 发上报后，其池进程的 `activeTicket` 立刻变空（进程可接下一票）；
   答复到达后该票 resume 并续跑，上下文不丢。
9. **外部 CLI**：三种 CLI 执行器行为逐字节不变。
10. **普通助手不受影响**：对话、记忆、技能、审批、提醒、历史读、导出、地图全部与改动前一致（本次不动它）。
11. **权限边界照实**：bash 的 cwd 校验按待拍板 14 的结论落地；若决定不加，验收项要写明
    "bash 仍不受路径守卫约束"——不许含糊成"边界更严"。
12. **回滚**：`CHANCELLOR_EMPLOYEE=native` 后完全回到今天的形态。

## 八、这条会怎么错

按"最可能被推翻"排序：

1. **③ 才是你们实际在崩的那一层。** 如果真实崩溃里 OOM / 未捕获异步异常占比很高，串行复用会让泄漏跨票累积，
   回收阈值调不好就会反复回收（表现为票总是重启、日志里 PID 频繁变）。反证方式：宿主 `server-errors.log`
   至今不存在，说明宿主没因未捕获异常死过；真实证据应来自 `.data/worker-pool.jsonl` 上线后的前 50 票。
2. **一进程一会话会显得"不够用"。** 如果用户真实并发经常 > 4，排队会被感知为"变慢了"，
   那时压力会推着去加会话并发（B 形态）。正确回应是加 N（受内存预算约束）而不是加会话；
   但这条需要有人守住，否则会漂移。
3. **「等待让出进程」是这套设计里最容易被砍掉的一半。** 如果它没做，30 票里 25 票在等人却照样占着进程，
   池就会被迫开大，内存和崩溃面都跟着涨，最后又回到「一票一进程」。它和串行复用是同一个目标的两半。
4. **IPC 会把"毛坯"从 stdin 挪到 HTTP。** 如果 SSE 断开、重连、乱序没处理好，会出现"票卡在 running"的假象；
   必须把「SSE 断开 = 该票失败」写成硬规则，而不是尽力而为。
5. **路径守卫退化的风险被低估。** cwd 从进程属性变成参数，是这次唯一新增的安全面；如果哪条分支忘了校验，
   就会变成"两票共用同一根"这类越权。单测要按"第二票越界写"直接构造负例。
6. **装配复用的收益可能不如预期。** 若真实票据都很长（接近 10 分钟），省下的装配时间占比很小，
   那这次改造的主要收益就只剩"通道变正经"和"库不再按票增长"——那就该在 P0 就把预期说清，别宣称省了很多时间。
7. **manager 层还在，形状没统一。** 池只换 native 执行器；managed 路径仍会起 manager 子进程。
   如果目标里有"一个 worker 概念"，这一层没做完就会继续出现"总管派的和执事派的还不一样"的困惑。
8. **「只搬派活工人」这条边界会被反复追问。** 用户的原话是"worker 要在独立进程"，而普通助手仍留在宿主
   （§三）。P1 的配置页必须把「对话里 / 派出去」标清，否则这条边界看起来像没做完。

### 8.1 实现后新增的已知边界（2026-11-22）

| # | 边界 | 影响 | 处置 |
|---|---|---|---|
| 1 | **managed 路径不走池** | `useManager`（总管/普通助手派活、带 domain）仍起 manager 子进程，manager 内部再起 `worker-main`（native）。也就是说"默认 pool"只覆盖**直派**（执事直派 / `managers:false`） | 方案 §十 #9 原本就写「manager 暂不动」；要做到"所有派活都进池"需另立 manager 方案 |
| 2 | **等上报时占用槽位** | 方案 §3.6「等待让出进程」没实现：一票等答复时仍占一个池进程 | 并发量小时无感；票多时是吞吐瓶颈，按 §3.6 补"会话挂起 + 释放槽位" |
| 3 | **dist 产物不支持池** | `node dist/index.js` 下池入口不存在 → 自动回落 native（有告警） | 要支持就把 `pool-main.ts` 加成第二构建入口 |
| 4 | **任务中心看不到队列** | `/health` 有 `queued`，但 UI 没展示「在跑 N / 排队 M」 | 方案 §3.6 要求的一等公民能力，待前端批 |
| 5 | **回合上限按"会话"计数** | 池内一票 = 一个会话，续行轮共用同一份 `MAX_TURNS` 计数；native 是每次 submit 重置 | 池内更严格（长任务更早收尾）；要完全对齐需在续行时重置计数 |

## 九、明确不做

- 不合并外部 CLI（它们必须是子进程）。
- **不把普通助手（对话）搬出宿主进程**（理由见 §三；将来要搬先满足那三条前置）。
- 不把任务会话放进宿主进程（路线 B 只留作对照档，验证后删）。
- 不在一个池进程里开多个并发会话（要并发就加 N）。
- 不搬 chancellor 的 worktree / 租约 / 合并 / 回执 / 崩溃恢复（那是另一条路线的事）。
- 不新增 `shared` 的 `ChatKind` 枚举值；池在宿主内不留任何对外会话。
- 不做任务会话的可视化聊天界面（任务专线 `task-<id>` 继续只做投影）。
- 不做按任务/按项目的人设变体。
