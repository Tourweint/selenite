# 来信前端几版：前端到底怎么"通信"，卡片该长什么样

> 一句话：前端不参与执事之间的通信，它只是"读账本的人"；所以方案的分歧不在"怎么传"，
> 而在"读的时机"（刷新才读，还是有人踢它一脚）和"读出来画成什么"。

现状：`send_to_agent` 递话已落成 `relay.message` 条目、作者进 `author` 结构，回读时前端把它画成
左侧来信卡（`chat-thread.js` 的 `mountLetter`）。本文明的是**在此之上还能怎么改**。

---

## 一、先讲清：前端在这条链路里的位置

执事 A 给执事 B 递话，发生在**服务端进程内**，全程不经过浏览器。浏览器只有两条通道能知道这件事：

| 通道 | 是什么 | 现在拿到什么 |
|---|---|---|
| 回读（HTTP） | 打开/刷新会话时拉一次 `GET /api/v1/agent/chat/:id/messages`，拿一页条目 | **有 `author`**，能画成来信卡 |
| 现场（SSE） | 会话正在跑时挂着的一条流，`delta/thinking/tool/notice…` 逐条推 | **没有 `author`**；只有主对话那边一条 `notice` 说"谁→谁递了一条话（正文不在这里）" |

用大白话说：**浏览器是个记账本读者，不是通信的一方**。它没有"收到一条消息"的推送能力，
只有"我去翻一遍账本"和"后台正在跑的时候，账本边写边念给我听"这两件事。而来信这条记录，
目前只在"翻账本"时能被认出来——边写边念的那一路没念它。

---

## 二、你没看懂的两处，用大白话讲

### 2.1 为什么"作者进结构"，正文里却还留着那段前缀？

一句话：**结构是给机器和界面看的，前缀是给模型看的，两者不能互相替代。**

| 谁在用 | 用什么 | 为什么不能只用另一个 |
|---|---|---|
| 界面 | `author` 字段 | 只靠正文前缀，就得在每处渲染点正则解析中文句子；改一个字、多一个括号，卡片就认不出来 |
| 模型 | 正文前缀 `[relay hop=1][来自执事 甲（inbox）]` | 模型读的是文本，看不到 `entry.data`。前缀同时干三件事：说明"这条不是你主人说的"、给出"只允许一跳"的边界、让"转述检测"有唯一判据 |
| 存储 | `relay.message` + `data` | 只靠前缀，等于"作者"是一段可被模型篡改的正文；落成 `data` 后，作者跟正文物理分离，改不了 |

代价是同一件事写了两遍（可读性差一点），收益是**两边都不依赖对方**：
前缀被模型改坏了，界面照样有作者；`data` 缺了（老库老数据），界面按前缀兜底。
所以不是"冗余"，是**两条互不依赖的证据链**——cindy 那份 `message-source.md` 的原话就是
"界面标签与模型说明同源，来自同一份 host 盖章数据"，翻过来就是这句话。

### 2.2 为什么"来信要刷新才看得到"？

因为递话落进 B 的账本时，**B 的那条 SSE 流没有"来信"这种事件**，只有正文 `delta`。
主人正开着 B 的会话时，服务端写账本这件事没有一个通道通知浏览器；浏览器下一次翻账本
（刷新、切走再切回、翻历史）才看到。

不是"故意不推"，是**当时没有这个口**：`ChatEvent` 里没有"这是一封来信"的事件类型，
`emitChiefNotice` 那一路又是发给主对话的全局口（而且只有文本，没有作者）。
所以现状的已知边界写着"现场不推来信正文"——**能修，但要想清楚用哪一档（见 §三）**。

## 三、传递三档（决定"什么时候能看到"）

| 档 | 做法 | 主人体验 | 代价 |
|---|---|---|---|
| **T0 现状** | 只在回读时认 `author` | 刷新/切回才出现；开着的会话不会自己长出来 | 零 |
| **T1 踢一脚再翻** | 递话落地时，向**收件方那条会话**推一个轻事件（复用 `watchRelayReceipt` 同款"按 conversationId 订阅"的口，新增 `watchRelayIncoming`）；前端收到后不猜内容，直接 refetch 尾部一页，按幂等插入 | 主人正看着 B 时，来信**一两秒内自己出现**，不需要动 | 多一次 HTTP 拉页；需要防抖（连续多封只拉一次）；`ChatEvent` **不用改**，手机端零感知 |
| **T2 直接把来信推过去** | 新增 `ChatEvent` 类型 `relay`，带 `{author, text, at}`，前端直接 `addMessage` | 零延迟，一条流走完 | 动契约（手机端要"不认识就忽略"）；**现场与回读必须同形**，否则刷新前后长相变——这是最容易出 bug 的地方 |

**取舍原则（这条比档位本身重要）**：现场渲染和回读渲染必须是**同一个函数产出同一张卡**，
抬头、折叠、宽度、颜色都不能有第二套。否则会出现"刚来时是卡片、刷新后变气泡"或反过来。
T2 最容易违反这条；T1 天然不违反（它就是回读）。

## 四、呈现四版（决定"长什么样"）

> 可交互校样：`docs/设计方案/来信四版校样/来信四版校样.html`（左栏切版本、开关演示 T0/T1、点开 C 的行、D 的抽屉）。

四版都用现有 token（纸底 `--bg #fdf9f2`、墨 `--text #2e2b3a`、金 `--c-secondary #b89b6e`），
不引入新色相，也不用紫。

### A 版 · 信封条（现状改良，成本最低）

```
┌─ 竖线（金色 2px）┌─────────────────────────────
│ 执事「甲」· inbox 发来            14:32
│ 明天的口径你按 9 点那版来，另外……
│ 展开全文
└──────────────────────────────────────────
```

- 变化点：`is-collapsed` 从 1 行放到 **2 行**（1 行太像报错条）；左边缘加一条 `--c-secondary` 细线；
  抬头时间右对齐；正文超过 2 行才出"展开全文"。
- 适合：来信是"偶发插曲"，主人多半扫一眼就过。
- 代价：改 CSS + 折叠阈值，半天。
- 风险：卡片底色和正文气泡差不多时，"这是一封信"仍要靠抬头那行字认。

### B 版 · 引文带（文档感）

```
│ 甲 · 14:32
│ 明天的口径你按 9 点那版来，另外周六那场我请假了，
│ 你替我跟主人说一声。
```

- 不用卡片、不用底色，就是一条 2px 竖线 + 小字署名 + 正文（可到 720px 宽，不挤在 560px 里）。
- 适合：信一般**两三行、要读完**；正文长时比卡片舒服（卡片宽 560 会频繁换行）。
- 代价：低（一个 flex 行 + 左 border）。
- 风险：**折叠不能用**——只剩一行"甲 · 14:32"就跟系统提示没区别，主人会以为是"某条状态"。
  另一风险：无底色会让它混进 B 的正文流，弱化"这不是主人说的话"。

### C 版 · 回执行 + 就地展开（扫读优先）

```
信使甲 → 14:32                                        ⌄      ← 收起：箭头朝下
信使甲 → 14:32                                        ⌃      ← 展开：箭头翻 180°

    （点了以后在**原位**长出来，不弹层、不跳转）
```

- 对话流里默认只有一行：**人名 + 箭头 + 时间**。收件人就是当前这个会话，不必写；
  "递来一条话" 这类说明也删掉——一行里只留三个信息。
- 右侧原来写"展开/收起"的文字，换成一枚**箭头**：收起朝下、展开翻 180° 朝上，
  箭头转动 + 正文高度同时过渡（`grid-template-rows: 0fr → 1fr`，不量像素）。
- 箭头是**一个组件**（`flow` 指向箭头 / `toggle` 折叠箭头，同一套 SVG 画法），
  以后凡是要"展开来看看"的地方都复用它，不各写各的符号。
- 适合：一个会话里连着好几封，主人只想看"有没有事"，需要时再点开。
- 代价：中（要一个内联展开器 + 展开状态跟消息 id 绑定；来信没 `id`，用 `data-at` 兜）。
- 风险：默认看不见正文，主人容易漏事；箭头语言偏运维，不像"家里人在说话"。

### D 版 · 信箱档（信多了才需要）

```
会话顶部： 来信 3   [查看来信]
点开 → 右侧抽屉：按时间列全部来信，可只看来自己 / 只看未读
```

- 对话流里仍留 A 或 B 的锚点，抽屉只是"汇总查阅"。
- 适合：来信量上来了（一天好几封），主人要抽查而不是逐条读。
- 代价：最大（新视图 + 未读状态 + 与主流的定位联动）。
- 风险：**"未读"要不要落库**？一落库就要动存储与清理策略；不落库则刷新后"未读"全消失，
  主人会觉得坏了。所以这版必须先把"未读算不算状态"定下来，否则做出来是残的。

## 五、已定

用户拍板：**C 版 · 回执行**，配 **T1**（推一条轻事件，前端自动回读）。

| 项 | 决定 | 备注 |
|---|---|---|
| 形态 | **C 版** | 行内只留"人名 + 箭头 + 时间"；A / B 留作候选，D 要等"未读算不算状态"定下来 |
| 箭头 | **一个组件**：`flow` 指向箭头 + `toggle` 折叠箭头（同一套 SVG 画法） | 收起朝下、展开翻 180° 朝上；箭头转与正文撑开同时发生（`grid-template-rows: 0fr→1fr`） |
| 动画 | 就地切换，不重绘节点 | 走 `render()` 会重建 DOM，CSS 过渡直接失效——这是这版唯一的实现陷阱 |
| 推送 | **T1** | 不动 `ChatEvent`、不碰手机端 |
| 以后 | 信平均超过 3 行再看 B；一天好几封再谈 D | 密度问题仍用形态解决，不新开视图 |

**不做**：E 版"一轮对照卷"（来信与回应上下折叠成邮件线程）。它要把"轮"重新投影一遍，
信息最强但破坏单时间线，且与"数信的数量"这件事无关，属于另一件事。

## 六、明确不做

- 来信卡上不放"引用/回复/编辑"按钮：来信没有 `id`，"以我的名义回话"的正确路径是切到该执事会话直接说话。
- 不做"两人私聊视图"（主人居中看 A↔B 的往来）：那是另一套账本投影，方案里已登记为不做。
- 不做来信的已读回执、离线队列、`hop>1`。
- 不给来信加"重要/紧急"标记：标记是权限与优先级问题，不是前端皮肤问题。

## 七、这条会怎么错

| 风险 | 说明 |
|---|---|
| 现场与回读不同形 | T2 最容易犯：SSE 走一套 `addMessage`，回读走另一套，刷新后折叠状态/抬头格式变样。故 T2 上线前必须有"同一函数、两路喂"的单测 |
| 折叠阈值拍脑袋 | 1 行→2 行是体验判断，不是数据；不同字宽/缩放下"两行"会抖。用 `line-clamp` 而不是 `max-height` 猜行高 |
| T1 被自己刷屏 | 连续 5 封来信触发 5 次 refetch；必须防抖合并，且 refetch 失败不能把已显示的卡片抹掉 |
| 信被当成 B 说的话 | A 版有底色尚可，B 版无底色时最危险；抬头那行必须**常驻**（不可随折叠消失） |
| 抽屉的"未读"落库 | 一旦落库就牵出清理、跨设备一致、压缩；不落库则"未读"是假状态，D 版要先答这一题 |
