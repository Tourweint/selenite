## 〇、为什么这条不能硬塞进批处理

它是**底座改造**：动的不是某个功能，而是"模型每一轮看到的上下文是怎么拼出来的"这件事本身。
现状是散的——7 个 section + 5 处 `extra.push` + 4 个文件里的零散注入。改它要一次性动
`lifecycle.ts` / `assist.ts` / `settled.ts` / `partner-context.ts` / `injection-guard.ts` 五处，
**任何一处漏改都会让某类会话悄悄少一段上下文**（这种 bug 极难发现，因为模型只是"变笨"了）。

所以：**先写方案，分批落，每批可回滚**。

## 一、现状（2026-11-10 实测）

| 落点 | 数量 | 特点 |
|---|---|---|
| `lifecycle.ts` 的 `sections[]` | 7 个 | 声明式、durable 按值变化追加 `pi.system`；`skills` 按会话冻结 |
| `lifecycle.ts` 的 `extra.push` | 5 处 | 每轮现拼，位置散落在钩子里 |
| `assist.ts` | 3 处 | 记忆召回注入 |
| `settled.ts` | 1 处 | 轮次收尾相关 |
| `partner-context.ts` | 11 处 | 执事轮的各段纪律（已比较规整，但仍是自己拼） |
| `injection-guard.ts` | 3 处 | 防注入防线 |

**问题**：
1. **不可审计**——想知道"这一轮模型到底看到了什么"，得同时读 5 个文件。
2. **不能去重**——同一段内容可能被两个地方各注一次（例如纪律段）。
3. **resume 后不稳定**——`extra.push` 的内容进了 transcript，重启后无法区分"这是注入的还是用户说的"。
4. **缓存前缀**——散落的 `extra.push` 插在消息流中间，会让缓存前缀反复失效（系列二 §9.5 的铁律）。

## 二、目标（一句话）

把"模型这一轮看到的所有注入"统一成**一种有身份、可去重、可审计、resume 稳定**的条目，
**行为不变**（同样的内容、同样的位置），只是把"怎么拼"从散落改成声明。

## 三、设计

### 3.1 条目形状

```ts
export interface InjectionEntry {
  /** 稳定身份：`<source>:<key>`，用于去重与审计。source 是模块名，key 是用途。 */
  id: string;
  /** 内容。固定字节：不含时间/会话 id/名字（否则缓存前缀每轮失效）。 */
  text: string;
  /** 优先级：数值小的先注入。用于确定稳定顺序（顺序也是缓存资产）。 */
  order: number;
  /** 生命周期： */
  scope:
    | "session"   // 每轮现算，值变才追加（当前 sections 的语义）
    | "once"      // 整个会话只注一次（如恢复注记）
    | "turn";     // 每轮都注（极少用，必须有理由）
  /** 是否进系统段（section）还是作为消息注入（extra.push 的语义）。 */
  channel: "system" | "message";
}
```

### 3.2 注册与消费

- 各模块导出自己的 `InjectionProvider`（`(ctx) => InjectionEntry | InjectionEntry[] | undefined`）。
- `lifecycle.ts` 里有一张**注册表**（显式列全，不自动扫描——自动扫描会让顺序不稳定）。
- 每轮：`收集 → 按 order 排序 → 按 id 去重（后来的覆盖先来的）→ 分流到 system / message`。
- **`scope: "once"` 的记账**落 durable（与 `resumeCount` 同族），保证重启后不重复注。

### 3.3 审计

新增 `GET /api/v1/agent/chat/:conversationId/injections`（只读）：
返回这一轮**实际注入的条目清单**（id / source / scope / 长度），**不返回正文**
（正文可能含记忆内容，日志纪律）。用于回答"模型到底看到了什么"。

开关 `AGENT_INJECTION_AUDIT`（默认 true）。

### 3.4 与缓存前缀的关系

- `order` 固定 → 注入顺序稳定 → 前缀稳定。
- `channel: "system"` 的条目走 section（durable 按值变化追加），不进消息流中间。
- **明确不做**：不把 `extra.push` 全部改成 section（有些注入必须在消息流里，例如"这一轮的工具结果"）。

## 四、分批落地（每批独立可回滚）

| 批 | 内容 | 风险 |
|---|---|---|
| **A** | 只建**框架 + 审计**：定义 `InjectionEntry`、注册表、收集器，**但先只接管 1 个最简单的注入**（`injection_guard`），其余保持原样 | 低 |
| **B** | 接管 `lifecycle.ts` 的 7 个 section（语义不变，只改写法） | 中（section 语义有"值变才追加"的细节） |
| **C** | 接管 `assist.ts` 的记忆注入与 `partner-context.ts` 的 11 段 | 中 |
| **D** | 接管剩余 `extra.push`（含 `settled.ts`），并上审计端点 | 中 |

**每批的验收标准一致**：`pnpm --filter @lifediary/server test` 全绿 + `http` 全过 +
**手工比对注入内容与改造前逐字节一致**（这条最关键）。

## 五、明确不做

- **不做自动发现**（provider 必须显式注册，顺序才稳定）。
- **不改注入内容**（本方案只改"怎么拼"，不改"拼什么"——内容改动是别的事）。
- **不做注入的 A/B 或开关矩阵**（那会让缓存前缀更难稳定）。
- **不动 `skills` 的按会话冻结语义**（它有单独的理由：技能索引中途变会让缓存整段作废）。

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| 漏改某处 → 某类会话悄悄少一段上下文 | 分批落 + 每批逐字节比对；审计端点可查 |
| `scope: "once"` 记账写错 → 重启后重复注入 | 复用 `resumeCount` 同族机制，不另造 |
| 顺序变化打掉缓存 | `order` 常量写死 + 一条顺序快照测试（照 `tool-schema-guard` 的做法） |
| 改造期间与并行会话冲突 | 每批只动 1-2 个文件；改造期冻结其他 agent 会话相关改动 |

## 七、建议

**先做批 A**（框架 + 审计 + 接管一个最简单的注入），拿到"逐字节一致"的证据后，
再决定要不要继续 B/C/D。**不要一次全改**——这是本方案最重要的一句话。
