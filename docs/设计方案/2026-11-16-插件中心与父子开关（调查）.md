# 插件中心与父子开关（调查）

> 行为开关拆成独立「插件」页之后：父子开关怎么定义、代码里已经有哪些硬门、下一步改哪里。

## 结论

1. **拆页已完成**：设置 → 插件（34 张卡），服务页只留通知 / 鉴权 / 运行时；判定、接口、白名单一字未动。
2. **父子开关不用从零发明**。代码里已经有四类硬门：记忆总闸（`MEMORY_ENABLED`）、记忆召回总闸
   （`PARTNER_MEMORY_RECALL`，跨层：插件页 → 人物页）、工具结果整理总闸（`TOOL_PROJECTION`）、
   执事体系总闸（`COMPANIONS_ENABLED`）。第一版只把这几类**已经存在的门**投影到界面，风险最低。
3. **语义按「非破坏性硬门」做**：总闸关 → 子闸一律显示为关、拨杆灰掉、API 也拒绝单独打开；
   **总闸重新打开 → 子闸回到自己原来的值**。不把子闸的值清零——关一次总闸等于把 7 个设置重置，
   代价太大，也不是用户想要的「总闸 / 子闸」。
4. **只画码里真有门的关系**。「语义上像父子、代码里没门」的（自主轮 → 自建巡逻、宰相 → 执事派发权），
   先补服务端门，再上界面；否则会出现「界面显示被锁、实际仍可绕过」的假锁。
   还要区分两种「父」：**级联关**（父关 → 子不可用，适合上锁）与**功能总开关**（父关 → 整块功能回到旧行为 /
   子项消失，不是级联）。后者按独立插件处理，不要套「子闸不能用」的文案。
5. **前置补丁（比父子开关本身更急）**：`MEMORY_ENABLED` 现在标 `hot:true`，但它是**启动期装配**的：
   - 启动时关着、运行期再打开 → 引擎仍是 null，记忆功能不回来；
   - 启动时开着、运行期再关掉 → 引擎还在、`mountMemoryApi({enabled:true})` 仍在，`/memory/*` 照常响应，
     召回注入也照常跑（`memoryRecallOff` 只认 `PARTNER_MEMORY_RECALL`，不认 `MEMORY_ENABLED`）。
   只有「新记忆自动抽取」（`memory-ingest.ts:28`）和两处伙伴模块（`partner-living` / `partner-proactive`）
   在运行期真停；召回注入与 `/memory/*` 都不停。所以不做这一步，父子锁在
   `MEMORY_ENABLED` 上就是假的。第一版建议直接改 `hot:false`（重启才生效、界面标「待重启」），
   要做真热关再引入 `memoryEnabled()` 活读并把 API 的 `deps.enabled` 换成函数。

## 1. 现状

- `flags.ts` 的 `FLAG_DEFS` 是**一张平表**：40 项，没有 `parent` / `requires` 字段；每一项都能独立 `PUT`。
- 插件页显示 34 项（40 减 6 个在设置 → 会话有专属卡的键），六组分区；页首计数只数 `value === "false"`，
  不知道「谁是总闸、谁被谁关」。
- 父关时，代码里的效果分两种：
  - **真的死**：引擎不装配、端点 404、注入 provider 直接 `undefined`；
  - **还活着但没意义**：比如执事体系关掉后，派发权函数仍可被测试调用；`PARTNER_TEMPLATES` 仍可拨，
    只是执事页根本打不开。
- 界面因此有两个问题：
  1. 总闸关着时，子闸还能拨到「开」，但打开后什么也不会发生——界面在撒谎；
  2. 总闸开着时，用户不知道哪些子项依赖它，关了总闸才发现一串功能一起消失。

## 3. 像父子、但代码里没有直接读父（P1，先别上锁）

| 表面父子 | 现状 | 建议 |
|---|---|---|
| `COMPANIONS_ENABLED` → `PARTNER_TEMPLATES` / `MINISTER_DISPATCH_AUTHORITY` / `DEVICE_AUTO_DISPATCH` | 执事路由 404 后这些开关事实上有意义，但它们的消费函数本身不读 `COMPANIONS_ENABLED`；`MINISTER_DISPATCH_AUTHORITY` 只读自己 | 先确认是否要在函数里补父门，再上「随总闸关闭」；不然会出现假锁 |
| `CHANCELLOR_ENABLED` → `MINISTER_DISPATCH_AUTHORITY` / `DEVICE_AUTO_DISPATCH` / `DELEGATION_WAKE_ENABLED` | 宰相关 = 派活工具不注册，派发链路整体不成立；但 `DELEGATION_WAKE` 守卫只认执事体系，不认宰相 | 同上。`DELEGATION_WAKE` 只在「已存在的派活」场景才需要宰相，是否锁要拍板 |
| `AUTONOMY_ENABLED` → `ROUTINE_SELF_SERVICE` / `TOPICS_ENABLED` | `runPartnerTurn` 不读 `AUTONOMY_ENABLED`；自主轮影响的是审批 / 提醒 / 观察档，不是「例行引擎启不启动」。本次只核到这里，未穷尽 | **先不锁**。等把「自主轮关掉后例行任务到底还跑不跑」查完，再决定是父子还是独立 |
| `MEMORY_ENABLED` → `MEMORY_PAGE_A` | 记忆关掉后记忆页仍会渲染，只是渲染成「记忆未启用」的空壳；A / 旧版只决定这层空壳长什么样 | **不锁**。它是页面皮肤，不是记忆模块；锁了反而挡住「先选好页面样式、以后再开记忆」 |
| `MEMORY_ENABLED` + `PERSONA_MEMORY_ENABLED` → `MEMORY_EXTERNAL` | 启动即关时 `MEMORY_EXTERNAL` 先过 `MEMORY_ENABLED`（硬 404）；运行期关则因为 `deps.enabled` 是启动快照，仍然可访问。再过 `personaAskEnabled()`（软：返回 `ready:false` 而不是 404） | 只把 `MEMORY_ENABLED` 当硬父（先修它的 hot 语义）；`PERSONA_MEMORY_ENABLED` 在卡面写「外部库未启用」即可，不做锁 |

### 3.5 人物页的「总闸」不全是级联关

| 父 | 子（人物页） | 语义 | 能不能按「父关 → 子显示关 + 拨不动」做？ |
|---|---|---|---|
| `COMPANIONS_ENABLED` | 整个执事页 | 级联关：路由一个不挂（`companion-api.ts:68/102`） | 能（但整页 404，父关时人物页本来就不存在） |
| `PARTNER_MEMORY_RECALL` | 「记忆 + 项目记忆」 | 级联关：父关 → 所有会话不自动带（`assist.ts:371-379`） | 能；子开关应显示锁态 |
| `TOOL_PROJECTION` | 「结果整理」三态 | 级联压制：父关 → 三态失效（`tool-projection.ts:175-200`） | 能；三态控件灰掉 |
| `PARTNER_PERSONA_MODULES`（**不在 `FLAG_DEFS`**） | 14 个人格模块 | **功能回滚，不是级联关**：false 时 `personaModuleOn` 一律 true（= 回到「谁也不裁」的旧行为，`partner-persona.ts:8-9`） | 不能。它是「关掉模块裁剪功能」，不是「把 14 个模块全关」；应作为独立功能开关，或明确写着「部署配置」 |
| `PARTNER_PROJECT_MEMORY`（**不在 `FLAG_DEFS`**） | 「负责项目」 | **功能总开关**：false 时 `projectIds` 字段整块不投影（`companion-api` 单测口径） | 不能。父关 = 这张卡消失，不是卡片变灰 |
| `MINISTER_DISPATCH_AUTHORITY` | 「接派单」个人位 | 功能总开关 + 个人位：总闸关 → 所有执事都不直派 | 可以只做「总闸关 → 个人位灰掉」，但个人位 UI 已退役（机制在） |

结论：**插件页能上「父子锁」的只有级联关那三组**；`PARTNER_PERSONA_MODULES` / `PARTNER_PROJECT_MEMORY`
这类部署配置要么补进 `FLAG_DEFS` 当独立插件（P2），要么在人物页写明「部署配置」，不要伪装成父子。

## 4. 三档数据语义（要拍板的地方）

| 档 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 非破坏（推荐）** | 子闸的存储值不动；父关时 `effective=false` + `locked`，界面显示关；父开恢复 | 关一次总闸不会重置一串设置；和 Chrome 扩展 / 系统设置的直觉一致 | 父关期间子闸「显示关、其实值为开」，需要在卡面写清「总闸关闭期间不生效」 |
| B. 父关即写子关 | 父关时把每个子键写 `false` | 存储值与显示一致，最符合「子闸默认关」的字面 | 破坏性：父开回来后所有子项都关着，用户要重新拨 7 次；误关一次总闸就丢配置 |
| C. 快照恢复 | 父关时记一份「哪些子项原本为开」，父开时只恢复这些 | 没有 B 的丢失，也不像 A 那样"表面关、里面开" | 多一份状态要维护；子项在父关期间被 API 改成开，快照 / 现值会打架 |

用户这次的说法是「记忆总闸关了，其他记忆模块默认关闭，并且不能再打开」——**界面效果按 A 就成立**：
父关时子闸一律显示关、拨不动；差异只在存储层。推荐 A，除非用户明确要求「父开回来子闸也必须重开」。

## 5. 接口与数据模型改法

### 5.1 `FlagDef` 增加 `requires`

```ts
interface FlagDef {
  // ...现有字段
  /** 硬父：任一为 false → 本项 locked（effective 一律 false）。允许多父，不允许环。 */
  requires?: string[];
}
```

第一版只登记 P0：

- `MEMORY_EXTRACT` / `MEMORY_EXTRACT_NOISE` / `MEMORY_CONSOLIDATE_JOB` / `MEMORY_EXTERNAL` /
  `MEMORY_INJECT_DEDUPE` / `PARTNER_MEMORY_RECALL` / `PARTNER_WORK_RECORD` → `["MEMORY_ENABLED"]`
- `TOOL_PROJECTION_WORKER` → `["TOOL_PROJECTION"]`
- `GROUPS_ENABLED` / `ROUTINE_SELF_SERVICE` / `DELEGATION_WAKE_ENABLED` → `["COMPANIONS_ENABLED"]`

注意 `PARTNER_MEMORY_RECALL` 自己既是 `MEMORY_ENABLED` 的子，又是人物页「记忆 + 项目记忆」的父——
父子链允许嵌套，环检测要能处理「中间节点」而不是只认两层。

启动时做一次环检测（`requires` 必须能在 `FLAG_DEFS` 里解析到且 DFS 无环），坏配置直接 throw，
不要留到运行期表现成「某个开关永远锁着」。

### 5.2 `GET /api/v1/agent/flags` 增加三个字段

```json
{
  "key": "MEMORY_EXTRACT",
  "value": "auto",              // 原样：存储 / env 现值
  "effectiveValue": "false",    // 父关 → false；枚举型也回落 "false"
  "lockedBy": "MEMORY_ENABLED", // 第一个关着的硬父；没锁 = null
  "requires": ["MEMORY_ENABLED"]
}
```

- 布尔子项：界面读 `effectiveValue`，父关时显示关。
- 枚举 / 数值子项：没有「关」这一档，界面只用 `lockedBy` 灰掉控件，卡面写「由 XX 关闭」。
- 页首计数改成按 `effectiveValue` 数：`当前 26 开 / 8 关（其中 7 个随总闸关闭）`。
- 保留 `value` 字段不动，避免现有 `ensureFlag()` 等调用方一次性全改。
- **`hot:false` 的父要看「已装载值」而不是「文件现值」**：`setFlag` 会立刻写 env，但进程要重启才装载；
  在这段窗口里父卡显示「待重启」，子闸不能按新值锁——否则界面锁了、实际功能还在跑。
  `listFlags` 里已有 `bootValues` 机制，锁态用启动装载值算，或用 `pendingRestart` 把父卡标成「未生效」。

### 5.3 `PUT /api/v1/agent/flags/:key` 拒绝被锁子项

```http
400 { "error": "flag_locked", "message": "「记忆总闸」关闭时，「记忆提取方式」不能单独打开" }
```

必须在服务端做——只在界面灰掉拨杆，直接打 API 仍能写；父关时写进去的值不会生效，但会留下
「界面关着、文件里开着」的脏状态，下次父开就突然复活。

### 5.4 父开关切换后的界面刷新

现在 `toggleFlag()` 只更新当前卡与 `state.flagsCache` 的一行，子卡 / 页首计数不会变。父开关的
`requires` 被别人引用时，保存成功后要 `loadFlagsSettings()` 整页回读一次（或本地按 `requires` 重算
`effectiveValue`）。建议直接整页回读：34 张卡的一次 GET 很便宜，少一套双份逻辑。

### 5.5 跨层子项

- 人物页「记忆 + 项目记忆」：读 `PARTNER_MEMORY_RECALL` 的 `effectiveValue`；父关时开关灰掉，
  文案「总闸在插件页关闭」。人物页已经拿到 flags 缓存（`ensureFlag`），加一个判断即可。
- 人物页 `tool_projection` 三态：父关时同样灰掉 / 写「总闸关闭」，避免拨了三态没效果。

## 6. 界面表达

- **父卡**：卡尾加一行小字「控制 7 个子插件」，不新增按钮。
- **子卡**：控件灰掉（`disabled` + `aria-disabled`），卡尾一行「由「记忆总闸」关闭」；
  `data-tip` 末尾补「总闸关闭期间不生效；重新打开总闸后回到原来的设置」。
- **组头计数**：仍显示组内项数；如果组里有总闸，再补一句「1 个总闸 · 7 个随它关闭」（可选，别做成第二套徽标）。
- **不要做的**：不要给子卡也加一个「总闸」拨杆（会变成双开关）；不要在总闸卡上加「全部开启 / 全部关闭」批量操作
  （用户没要，且会把「非破坏」语义搅乱）。

## 7. 分步落地

| 步 | 内容 | 风险 |
|---|---|---|
| P0-a | 修 `MEMORY_ENABLED` 的 hot 半真：改 `hot:false`（最省事），或做引擎动态装配 + 把 `memory-api` 的 `deps.enabled` 从启动布尔换成活读函数 | 低–中。改 `hot:false` 会让界面标「待重启」，但行为从此诚实；动态装配要处理引擎生命周期 |
| P0-b | `FlagDef.requires` + 环检测 + `listFlags` 三字段 + `setFlag` 锁拒绝 + 单测 | 中。要覆盖「父关时 PUT 子项 400」「父开恢复」「多父」「枚举子项」 |
| P0-c | 插件页子卡锁态 + 父卡徽标 + 计数按 effective + 父切换整页回读 | 低。纯前端 |
| P0-d | 跨层：人物页记忆子开关 / 工具投影三态跟随父闸 | 低。已有 `ensureFlag` 缓存 |
| P1 | 给「执事体系 → 招聘模板 / 派发权 / 设备自动派活」「宰相 → 派发权 / 设备派活」补真正的函数门，再上锁 | 中。要先确认这些函数还有没有别的调用方 |
| P2 | 把未上页但确实是功能开关的 env 补进 `FLAG_DEFS`：至少 `PARTNER_PROJECT_MEMORY`、`PARTNER_PERSONA_MODULES`、`PARTNER_GREETING_ENABLED`、`WORKER_CHAT_ENABLED`、`CHAT_CONTEXT_INSPECT` | 中。要逐个确认默认值与 hot 口径，不能把部署配置误当日常开关；`PARTNER_PERSONA_MODULES` 还要先定「false = 全开旧行为」的文案，别写成「关掉 14 个模块」 |

## 8. 这条会怎么错

- **只做 UI 锁**：API 仍可 `PUT`，父关时写进去的值会在父开时复活；界面和文件长期不一致。
- **把子闸值清零**：用户误关一次记忆总闸，7 个设置全没了；这是最容易后悔的一档。
- **给语义关系上锁、但不补码门**：比如把「执事派发权」挂到「执事体系」下，函数层却不读父；
  用户看到锁、实际仍能通过内部调用绕过，锁变成装饰。
- **`MEMORY_ENABLED` 的 hot 半真不修**：父关 → 子锁 → 父开，界面全绿，实际记忆引擎仍是 null；
  反过来运行期关掉后，`/memory/*` 与召回还在跑，子闸锁了也没用——这比不做父子更糟，因为界面给了
  确定性的假承诺。
- **未上页的隐藏 gate**：`PARTNER_PROJECT_MEMORY` 控制「负责项目」整块功能，但不在 `FLAG_DEFS`；
  人物页 tooltip 之前甚至写着「总闸在 设置 → 服务 → 行为开关」——那个卡片根本不存在。
  父子开关只治理插件页内的 40 项，管不到这些 env；要么补上页，要么在相关 UI 写清「部署配置」。
- **跨层子项漂移**：`PARTNER_MEMORY_RECALL` 在插件页关掉，人物页的子开关如果仍能拨，
  用户会以为「我只关了全局、这个执事还开着」；实际全局关压过一切。必须让子项也显示锁态。
