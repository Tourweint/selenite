## 背景与问题

用户要求"总管派出去的活，一定能收到回信"。2026-11-15 全链路只读审计（静态，HEAD `13cbbd8`）结论：正常路径（完成 / 失败 / 中断且宿主不崩）闭环稳——settle 三写（留言表 in + 任务专线镜像 + 会话正文）+ 唤醒轮（批 29）；忙时正文走 durable inbox 持久排队。但查出四个真缺口：

1. **终态落盘 → 汇报写回之间的崩溃窗口**：chancellor 在 `setTicketStatus` 落终态的瞬间就删 inflight（`chancellor/src/store.ts:152-154`），而汇报写回在 run promise resolve 之后才执行（`delegation-start-delegation.ts` settle）。窗口内进程崩 / 重启，恢复扫描因 inflight 已删而跳过该单 → **汇报正文永久丢失**，只剩 ticket.json 的 lastAction。无测试覆盖。
2. **重试路径不唤醒**：`delegation-actions.ts` `defaultRetryRuntime.report` 只调 `reportDelegationResult` 且 `.catch(() => undefined)`——重试单跑完执事不会被叫起来接结果，写回失败也无声。
3. **忙退避耗尽 / 唤醒链超 5 轮 → 唤醒队列内存清空**（`delegation-wake.ts` `clearConversation`）：正文还在会话里，但执事不再被叫醒；重启也会丢掉整个内存 pending。
4. **唤醒轮模型失败 → pending 已被 collectPending 取走，不重试不回灌**：转述轮丢失（正文仍在）。

## 目标

- **回信正文 at-least-once 必达**：任何单进程崩溃窗口都不再丢汇报正文。
- **唤醒尽力而为且不静默丢**：队列可恢复、失败可重试、放弃必留一行日志。
- 不改跨仓契约（chancellor 的 inflight 语义不动）。

## 方案

### A. 待送达记账 + 启动补送（堵缺口 1）

**思路**：settle 落 in 留言时记"待送达"（delivered=0），会话写回成功才销账（delivered=1）；启动时补送所有未销账的。留言表本来就是写回**之前**落库的持久旁路，正好当账本，不引入新存储。

1. `delegation-messages.ts`：`delegation_messages` 表加列 `delivered INTEGER NOT NULL DEFAULT 1`。
   - 新库 CREATE TABLE 直接带列；老库用 `PRAGMA table_info` 检查后 `ALTER TABLE ADD COLUMN`（默认 1 = 历史留言视为已送达，升级不触发批量补送）。
   - `append` 返回自增 id；新增 `markDelivery(id, 0|1|2)` 与 `listUndelivered()`（`direction='in' AND delivered=0`）。
2. `delegation-start-delegation.ts` settle()：
   - in 留言以 delivered=0 落库，拿到行 id 附进 `DelegationReport.deliveryMessageId`（新增可选字段，内部类型）。
   - **idle 分支**（按设计不写回会话）：同步把该行标 2（跳过），防止下次启动误补送。
   - canceled 单在 recordMessage 之前就 return，天然无行、无补送——口径不变。
3. `lifecycle-harness.ts` 装配处（唯一真实 report 组装点）：`reportDelegationResult` 改为返回 `"ok" | "missing" | "error"`；装配处按结果销账——ok→1，missing（会话已不存在）→2，error→留 0（下次启动再补）。`DelegationRuntime.report` 的类型签名不变（仍 fire-and-forget void）。
4. `recovery-report.ts` 新增 `redeliverUndeliveredReports(deps)`（与 A3b 回灌同款可注入风格）：
   - 扫 `listUndelivered()`；宿主会话解析：回执表 `lookupByTicket` 优先，缺回执退 `ticket.json` 的 `originConversationId`（数字直接用内部 id；uuid 用 Chats.byExternal 反查）。
   - 写回文本 = 留言表 in 行原文，前缀「（重启补送）」，日志只记条数。
   - 写回成功 → 标 1 并调 `wakeOnDelegationReport`（走既有守卫链）；会话不存在 → 标 2；异常 → 留 0 下次再试。
   - 开关 `DELEGATION_REPORT_REDELIVERY`（默认开，显式 false 才关），回滚 = 老行为。
5. 调用点：`index.ts` 启动恢复段，排在 `reportRecoveredTickets` 之后。

### B. 重试路径补唤醒（堵缺口 2）

`defaultRetryRuntime.report` 在调 `reportDelegationResult` 之外补 `wakeOnDelegationReport`（懒加载同款动态 import）；`.catch` 改为 warn 一行再吞。重试单同样走唤醒轮。

### C. 唤醒队列落盘 + 失败重排（堵缺口 3/4）

`delegation-wake.ts`：

1. **落盘**：pending 每次变化（入队 / 取走 / 清空 / 重排）原子写 `.data/wake-pending.json`（照 chat-meta 的临时文件 + rename；`AGENT_WAKE_PENDING_PATH` 供测试隔离）。新增导出 `restoreDelegationWakeQueue(deps)`：启动时读回、逐会话排防抖 flush；文件坏 / 无内容当空。`index.ts` 启动调用（ waking 开关关着时 flush 的守卫链会自行清空）。
2. **忙退避耗尽 / 链保险丝**：从"清空丢弃"改为**重排**——保留 pending，`REQUEUE_MS`（10 分钟）后重试一轮；连续重排超过 `MAX_REQUEUES`（3 次）才真正清空并 warn（翻案登记：2026-11-10 批 29 的"耗尽即放弃"按用户"确保收到回信"口径改为"有限次重排"）。唤醒轮成功即清零计数。
3. **唤醒轮失败**：`collectPending` 取走的 reports **回灌队首** + 10 分钟后重排；同样受 3 次上限约束。
4. 守卫链不过（开关关 / 非 canonical / 执事停用）维持"清空 + 落盘"——那是设计内不该唤醒的形态，不是丢失。

## 取舍与备选

- **记账载体选留言表加列**，备选是独立"待送达"表 / 文件——弃：同一类簿记同库（留言/回执/死信已在 delegations.sqlite），少一处备份；补送要用的正文恰好就在 in 行里。
- **补送只在启动时扫**，不做运行期定时重试——运行期的写回失败（error→留 0）本来就会被下一次启动兜住；个人机重启频率远高于写回失败率，够用。已知边界：写回连续失败且长期不重启期间，任务中心与专线里始终看得到结论（留言表 + 镜像双写不受影响），只是宿主会话里晚一条。
- **唤醒重排 3 次封顶**：防"宿主会话卡死导致无限 10 分钟轮询"；封顶后正文仍在会话里，损失只是转述轮。
- 备选"把汇报写回改成同步 await 再删 inflight"——跨仓改动 chancellor 的终态时序，动静大，弃。

## 明确不做

- 不补"派活方会话被永久删除"的回信（删除有闸门挡着，闸门被绕过属另一类事故；missing→2 已如实记账不重试）。
- 不为回执 accept 前的极窄崩溃窗做处理（uncertain 语义已有单测口径，不自动重派）。
- `DELEGATION_WAKE_ENABLED=false` / 非 canonical 会话派活 → 维持"只有裸汇报无唤醒"的设计形态。
- 不改 chancellor 的 inflight 删除时序（跨仓契约）。
