# 派活可见：把"那条消息"落进任务

- 日期：2026-11-07
- 状态：**待落地**（本文件先写取舍，实现与验证见变更记录）
- 用户口径（2026-11-07）：「你在任务里应该能看到总管或者其他执事发给任务的那条消息，对吧？他们现在通信应该是靠消息的」——用户预期是**消息**，实际是**命令行参数 + 文件**。

## 一、问题：现在不是消息，所以看不见、回不了

| 方向 | 现在靠什么 | 后果 |
|---|---|---|
| 总管 → 执事 | `spawn` 参数 `--requirement=<原文>` | 需求只是一段裸文本落在 `ticket.json.prompt`，没有发送者、没有时间、没有"这是给你的指令"这层意思 |
| 执事 → worker | 拼成 `TASK.md` | 同上，且 TASK.md 的格式是 chancellor 内部约定 |
| worker → 执事 | `REPORT.md` + stdout 最后一行 | 过程不在任何可回看的位置 |
| 执事 → 总管 | stdout 最后一行 → `formatReport` 截 80 字 | 只剩一句结论 |

关键差别（对照 cindy）：cindy 派活投递的是**一条 user message**，格式化后**进入目标会话的 transcript**：

```
[From Orca Lead]
<正文>
```

所以它在任务历史里可见、可回看、带发送者。**本质是"投递物是消息还是参数"**——参数进不了 transcript。

## 二、决策

### 决策 1：派活落成"一条留言"，存在宿主的派单库里

不试图改 chancellor 的 CLI（那是跨仓契约，且 CLI 无法承载"会话"概念）。做法：

- 宿主侧新增 `delegation_messages` 表（`delegations.sqlite`，与回执同库）：
  `ticket_id` / `direction`(out/in) / `from_kind`(chief|partner|worker|system) /
  `from_name` / `body` / `created_at`。
- 派单受理时写一条 `out`：「来自 总管 / 某执事」+ 原文。
- 任务终态时写一条 `in`：结论。attention 写一条 `system`。
- `GET /api/v1/tickets/:id` 增 `messages: []`（纯增量字段，老客户端忽略）。

**为什么不写进会话 transcript**：任务不是会话（这是上一轮讨论过的"任务即对话"改造，属结构性问题）。先用独立表把"谁、什么时候、说了什么"补上，成本低、可回滚、不碰 chancellor。

### 决策 2：任务详情页显示这条留言，带发送者

- 详情页顶部加一段「派活留言」：`来自 总管 · 2026-11-07 14:02` + 原文。
- 终态结论作为第二条。
- 这是**只读**展示；"在任务里回话"仍需 `resume`（已有能力，不扩展）。

### 决策 3：domain 降级为可选标签（用户已选）

- 建执事时 `domain` 可以留空；
- 派活路由改按**执事 id / 名字**，不再靠 domain 字符串；
- 已有 domain 保留，继续能路由（老数据不迁）；
- 界面上把 domain 从"必填路由键"改成"备注标签"，可改。

**明确不做**：不删 `managers/<domain>/` 目录结构（chancellor 依赖它），不迁移历史单。
