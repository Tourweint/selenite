# Agent 间通信记录：作者标记与只读来信

> 一句话：执事递给同事的话，别再用"主人说的"这个槽位落库；作者进结构，界面按作者画成左侧来信。

> 状态：**已落地（2026-11-15）**。下沉落点：契约字段 → `docs/基线文档/接口-端点1-对话与兼容层.md`；
> 通道取舍 → `docs/基线文档/系统架构.md` D21；落地与验证 → `docs/变更记录/2026-11-15-来信作者标记与只读卡片.md`。
> **与长期文档冲突时以基线文档为准**；本文留的是"当时怎么想的"。

## 结论

1. 现在的 `send_to_agent` 通道**功能是对的、账本是错的**：消息本体落成 `pi.user`，
   于是"同事说的话"在存储层、回读层、界面层都等同于"主人说的话"。同一个人（主人）坐在
   两个位置上，谁说的就分不清了。
2. 修法只有一个动作：输入时带上 `entry`，把它落成 `relay.message` 应用条目，
   作者（执事 id / 名字 / 领域 / hop）写进条目的 `data`。内容仍是提示词原文，**作者不进正文**。
3. 界面按作者画：非主人来源收成左侧"来信"一行（首行预览、点开看全文、不可编辑）；
   右侧只代表主人本人或替主人发的输入。这条完全对齐 cindy 的 `botLetter` 口径。
4. 零新增存储、零新增表；回滚开关 `PARTNER_RELAY_ENVELOPE=false` 回到 8d 的纯文本形态。

## 一、现状（2026-11-15 全量实读确认）

### 1.1 六条通道

| # | 谁 → 谁 | 介质 | 落库形状 | 主人可见性 |
|---|---|---|---|---|
| 1 | 主人 ↔ 总管 | 主对话 | `pi.user` / `pi.assistant` | 可见、可编辑 |
| 2 | 主人 ↔ 执事 | `partner-<id>` 专线 | 同上 | 可见、可编辑 |
| 3 | 主人 ↔ 群 | 群时间线（`partners.sqlite`） | 带 `authorKind` / `authorName` 的消息行 | 可见（时间线完整） |
| 4 | 总管/执事 → 工人 | `delegate` 工单 | 任务单 + `task-<票号>` 专线（系统写 `pi.assistant`） | 可见、可插话 |
| 5 | 执事 → 执事 | `send_to_agent`（8d） | **`pi.user`**（正文带 `[relay hop=1][来自执事 A（域）]`） | 只能进对方会话看到，且显示成主人说的 |
| 6 | 本机 ↔ 别机 | 中继矩阵派活 | 远端单台账 | 部分 |

### 1.2 第 5 条的具体毛病（都在代码里，不是推测）

| 现象 | 证据 |
|---|---|
| 落成纯用户输入 | `agent/lifecycle-harness.ts` 的 `deliverPartnerRelay()` → `submit({type:"input", content, whenBusy:"followUp"})` |
| 界面画成主人气泡 | `session-transcript.ts` 的 `foldTranscriptEntries()` 只认 `pi.user` → `role:"user"`；`chat-thread.js` 的 `addMessage()` 按 role 给 `msg user` |
| 同事的话能被"编辑重发" | `chat-thread.js` 的 `syncEditEntry()` 按 `.msg.user` 找最后一条挂按钮；`session-open.ts` 的 `forkForEdit()` 只认 `pi.user` → 恰好命中递话那条 |
| 主人只收到一句通知、无正文、不落盘 | `partner-relay.ts` 的 `emitChiefNotice()`（进程内轻事件） |
| 作者只存在于正文文本里 | `relayBody()` 拼 `[relay hop=1][来自执事 A（域）]` |

最后一条是根因：**文字不是结构**。压缩、改写、模型转述都能把它弄丢。

## 二、cindy 怎么做的（2026-11-15 实读 `<reference>\cindy`）

> 只看一家。它是"内容还是提示词、作者是结构"这条路线做得最完整的公开实现。

### 2.1 一份裁决，三处同源

`docs/product-rules/message-source.md`（2026-10-05 裁决）原文：

> 非本机用户亲手输入的消息，界面上显示的来源与模型收到的来源说明必须来自同一份 host 盖章的
> 数据、说同一件事。新增任何自动发送或远程发送路径时，两侧一起补。

### 2.2 作者是字段

- 沿用 `agentMeta`：`origin`（scheduler / session / orca）、`imSource`、`hookSource`、
  `sourcePlugin`、`sourceDevice`、`sharedTaskAuthor`；群场景再加 `sourceGroup` / `groupRequest` / `groupThread`。
- **wire 传进来的同名字段一律丢弃，由 host 重写**——作者只由接收方盖章。
- 这些字段**只用于归属展示，不是权限判据**。

### 2.3 模型侧只有一句说明

`[消息来源] 本条由任务「X」(session_id: …) 发送，不是用户本人输入。` 只进当次那条用户消息；
**不进系统提示词、不进落库正文、不进 `getAgentFacingText`**。名字一律配 id，按不可信文本清洗。

### 2.4 界面：非主人来源不占右侧

`UserMessage.tsx` 的 `botLetter` 分支（2026-11-10 主人裁决）：

> 收成左侧与伙伴回复对齐的一行（与「开了任务」同形的胶囊：任务名 + 回信 + 首行预览），
> 点开看全文和「打开任务」，展开后才有操作栏；**右侧只代表主人本人或替主人发的输入**。

`letterPreview` = 正文第一个非空行。Orca 另有 `[From Orca Lead]` / `[From Orca Worker <角色> (worker_id: …)]`。

### 2.5 一个反面参照

cindy 的 `send_to_agent` **2026-11-08 已移除**，改成 `send_to_session`（跨任务、正文就是 Agent 原文、不拼包装）。
**我们不跟这个**：我们的 `send_to_agent` 是同机执事间通道，与对方形态不同；本文只借它的来源体系。

## 三、设计

| # | 决策 | 理由 |
|---|---|---|
| D1 | 作者进结构（`entry.data`），不进正文 | 文字会被压缩/改写/转述；结构不会 |
| D2 | 正文前缀**保留** | 模型需要知道"这条不是主人说的"，且 `[relay hop=1]` 是转述检测的唯一判据；结构供展示，文本供模型，同源同一次递送 |
| D3 | 只有非主人来源带 `author` | 对齐 cindy「设备标签只标别人的消息；本机输入不盖章」。主人自己的消息不标注 = 它就是主人 |
| D4 | 落成 `relay.message` 应用条目 | durable 的 input 支持 `entry:{kind,data}`（`kind` 不得以 `pi.` 开头）；一条改动三件事：作者、不可编辑、不占 `pi.user` 槽 |
| D5 | 回读层必须同时认这个 kind | `foldTranscriptEntries` 对未知 kind 直接 `continue` → 不改就**整条消息从历史里消失** |
| D6 | 轮边界同口径 | `transcript-page.ts` 的 `turnStartOf` / `splitTurns` / 扫描条件都以 `pi.user` 切轮；不改就跨轮串味 |
| D7 | 界面左侧来信，`不挂 .user 类` | 编辑入口按 `.msg.user` 找 → 不挂类就天然不可编辑；比再加一层判断稳 |
| D8 | `session-index` / `session-search` **不改** | 侧栏首句与检索口径维持"只认主人输入"；来信不当会话标题、不进跨会话检索（见 §四） |
| D9 | 回滚开关 `PARTNER_RELAY_ENVELOPE` | 默认开；`false` 时逐字节回到 8d 形态 |

### 3.1 契约（纯增量）

```ts
// shared/src/index.ts
export const TranscriptAuthorSchema = z.object({
  kind: z.enum(["partner"]),   // 只放非主人来源；主人自己的消息不带
  id: z.string(),              // 执事 uuid
  name: z.string(),
  domain: z.string().optional(),
  hop: z.number().optional(),   // 递话跳数（当前恒 1）
});
// TranscriptMessageSchema 上加：author: TranscriptAuthorSchema.optional()
```

老客户端（手机端只读 `role`/`text`/`at`）忽略即可。

### 3.2 落库形状

```jsonc
{ "type": "input",
  "content": "[relay hop=1][来自执事 信使甲（inbox）] …",
  "whenBusy": "followUp",
  "entry": { "kind": "relay.message",
             "data": { "kind": "partner", "id": "…", "name": "信使甲", "domain": "inbox", "hop": 1 } } }
```

模型看到的仍是那条 user message（durable 口径：`entry` 只换"落成哪条条目"，不换模型消息）。

### 3.3 界面

- `.msg.letter`：左侧、与执事的回答对齐；卡片内一行 `执事「名字」· 领域 发来`；
  正文默认折叠为首行预览，点击整卡展开/收起。
- 不挂 `.msg.user` → 不出现"编辑重发"；不挂 `.msg.assistant` → 不出现复制脚注。
- 历史回读与现场渲染同一套（`renderTranscriptMessage` 传 `author`）。

## 四、明确不做

1. **不做跨会话聚合的"两人私聊视图"**：来信只活在接收方的会话里；要看往来就进那个人的会话。
2. **不做信箱表 / 离线队列 / 已读回执**（8d 的老取舍继续有效）。
3. **不做 hop>1**：通道仍只有一跳。
4. **不把来信计入会话标题与轮数**：侧栏首句仍取自主人自己的第一句。
5. **不进 `recall_sessions` 检索**：检索结果的行只有 `user`/`assistant` 两种角色，装不下作者，硬放会把同事的话当成主人说过的话。
6. **不做主人"署名"落库**：主人发言不写 `author`（D3）。
7. **不改手机端**：lifediary 仓另批；新字段可忽略，不破协议。
8. **不做通知落盘**：递话时主人时间线的那条 notice 仍是进程内轻事件（8d 口径）。

## 六、这条会怎么错

| 风险 | 说明 |
|---|---|
| 压缩把条目吃掉 | `relay.message` 与普通条目一样会被压缩替换成摘要；历史里早年的来信会退化成摘要里的一句话。接受：不新做归档账本 |
| 会话只在来信里存在 | 若某会话的第一条就是来信（几乎不会，执事会话有问候），侧栏看不见它——D8 的代价 |
| 正文前缀与结构漂移 | 两处都由 `relayBody()` / `relayEntryOf()` 从同一个 `from` 生成；将来若有人只改一处，就会出现"界面说 A、模型看到 B"。故两函数必须同签名、同调用点 |
| 前端漏改 | 新 kind 在回读层认了、前端没认 → 来信会掉成空气泡或抛错；验证项里必须有"历史回读一条来信"的人工确认 |
| 三方渲染分叉 | 现场 SSE 不推来信正文（只有回读能看到）；正在看 B 的会话时新来信不会即时出现，下一次回读才出现。登记为已知边界 |
