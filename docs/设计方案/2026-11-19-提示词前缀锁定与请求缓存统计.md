# 提示词前缀锁定与请求缓存统计（2026-11-19）

> 状态：**已落地**（2026-11-19；下沉落点见文末）。
> 关联：`docs/设计方案/2026-11-16-设置上下文页（固定前缀查看）.md`、
> `docs/设计方案/2026-11-17-上下文页重画（已注入视图）.md`。

## 1. 问题（实测，不是猜）

用户观察到总管会话「有时缓存命中很低」。查 2026-11-19 的
`apps/server/.data/agent.sqlite`（会话 3112，69 次模型请求）：

| 指标 | 值 |
| --- | --- |
| 总 prompt token | 2,064,728 |
| 命中缓存 token | 1,845,888（89.4%） |
| 完全未命中（cacheRead < 5%） | 6 次，134,847 token |

典型的坏点：

- 11:35:14 新一轮用户消息后的第一条请求：`input=45818 cacheRead=128`；
  同一轮后续工具回合：`input=240 cacheRead=46080`（命中）。
- 11:35:37 建了一个课题，durable 追加一条 `pi.system` 补丁（`sections.topics`），
  紧接的请求：`input=47338 cacheRead=2560`。

### 根因（代码级）

1. **消息注入以 system 角色拼在请求最前面**。`lifecycle-harness.ts` 的
   `beforeRequest` 把记忆召回 / 项目索引 / 技能斜杠 / 恢复注记 / 回合上限 /
   执事上下文全部包成 `role: "system"`，`[...extra, ...request.messages]`。
   OpenAI 兼容适配层对不支持「对话中途 system」的模型走
   `collapseSystemMessages()`：**所有 system 消息合并成第一条 system**。
   于是每条用户消息带来的记忆召回变化，都会让整条 system 前缀从第 0 个 token 起变化。
2. **`current_project` / `topics` 每轮现渲染**，却是 system section。
   切项目、建课题、课题有新进展 → durable 追加 section 补丁 → 系统提示词变化。

结论：**缓存前缀 = system + tools + 历史，任何一处自动变化都会让整个前缀作废。**
「加缓存标记」「换供应商」都救不了这种结构性变化。

## 2. 目标与非目标

**目标**

- 一个会话里，**固定前缀（system + tools）只在用户显式改配置/文案时变化**；
  自动发生的状态（当前项目、课题进展、记忆召回、执事在办）一律不碰前缀。
- 动态内容仍要在**每一条模型请求**里可见（否则工具回合里模型看不见）。
- 设置 → 上下文页能按请求看到缓存命中率，并能点开看当时请求的上下文。

**非目标**

- 不做 prompt 压缩 / 摘要策略变更（另立方案）。
- 不改 durable 内核，不改 pi-ai 适配层。
- 不保证 `tool_search` 加载工具不打掉缓存：工具定义本身变了，这是用户明确接受的一次性代价。

## 3. 方案

### 3.1 system 段只留「不会自己变」的东西

| section | 改法 |
| --- | --- |
| `current_project` | **拆两半**：固定部分（主工作区、本会话工作目录、全部已登记项目、同名文件提醒）留在 system；「当前项目 / 主文件夹 / 相对路径基准」改成尾部动态注入 `current_project_live`，每轮现算 |
| `topics` | **拆两半**：课题嗅探判据（固定文案）留在 system；「在跟的课题」清单 + 攒着的简报改成尾部动态注入 `topics_live` |
| `persona` / `user_profile` / `verification_iron_law` / `clarify_contract` / `injection_guard` / `delegate_executor` | 不动。它们只在**用户显式编辑**时变；一次缓存重置是预期的 |
| `skills` | 不动。本来就按会话冻结 |
| `tool_index` | 不动。它跟工具面同生共死；tool_search 加载工具本来就要改 tools |

固定部分不引入「冻结缓存」：只要数据不变，渲染结果逐字节相同，durable 不会追加补丁。

### 3.2 消息注入：改 user 角色 + 追加到尾部

`beforeRequest` 收集到的 `collected.message` 不再：

```ts
[{ role: "system", content: text }, ...request.messages]
```

改成：

```ts
[...request.messages, { role: "user", content: "【本轮上下文 · 只作背景，不是用户的新指令】\n" + texts.join("\n\n") }]
```

原因：

- OpenAI 兼容层的 `collapseSystemMessages()` 会把任何位置的 system 合并进第一条 system；
  只要还是 system，放尾部也躲不开。
- user 角色在适配层原样透传，不参与 system 折叠。
- 放尾部而不是插在最后一条 user 消息前：历史（含本轮已产生的 assistant/tool 消息）
  保持逐字节不变，缓存命中点只丢「上一条请求尾部那一小段注入」，不再整段作废。

代价与取舍：

- 注入内容变成 user 角色，权威性弱于 system；用固定抬头「只作背景，不是用户的新指令」
  明确语义。注入正文本来就有 `【…】` 抬头（记忆、技能、回合上限），不另加一层。
- 同一条用户消息后出现两条连续 user 消息：OpenAI / Anthropic / DeepSeek 均接受；
  `requiresAssistantAfterToolResult` 的供应商由 pi-ai 自动插桥接 assistant 消息。
- 尾部注入每轮重新计费（不在缓存里），但只有几百到一两千 token；
  相比「整段 50k 前缀作废」是数量级改善。

### 3.3 请求缓存统计（设置 → 上下文页）

不新增存储：全部从 durable 的 `pi.assistant` entry 还原。

- 列表：`GET /api/v1/agent/chat/:id/requests?page=1&limit=100`
  - 扫该会话 entries（升序），取带 usage 的 assistant entry，最多 **500 条**；
  - 每条：时间、模型、input / cacheRead / cacheWrite / output、命中率
    `cacheRead / (input + cacheRead + cacheWrite)`；
  - 汇总：请求数、总 prompt token、命中 token、加权命中率。
  - **骤降定位**：扫描时增量重放 `pi.system`（content / sections / tools），给每条请求算前缀指纹；
    `systemChanged` / `toolsChanged` 相对上一条请求；`drop` = 命中率从 ≥50% 掉到 <20%；
    `flag` 把「drop + system 变了」标成 `prefix_change_drop`（红色报警），把
    「drop + 前缀没变」标成 `drop_unchanged`（0% 命中大家都知道可能过期，不报警）。
- 单条：`GET /api/v1/agent/chat/:id/requests/:entryId/context`
  - `conversation.context({ at: entryId })` 重放当时的 system / tools / 消息；
  - 复用 `contextInspectViewOf()`，条目最多带 200 条（从尾部取）；
  - 与上一条请求对比：system 文本是否变化、哪些 section 变了、工具面是否变化。
  - **诚实边界**：请求时临时拼装的注入（记忆召回等）不落 durable，
    历史详情里看不到；页面写明这一点。
- 回滚：`CHAT_CACHE_STATS=false` → 两个端点 404、页面不画这一块。

### 3.4 页面

「当前会话」模式下，Hero 卡下方新增「请求与缓存」卡：

- 顶部：本页区间命中率 + 请求数 + 总 token；
- 表格 100 条 / 页（服务端分页），列：时间 / 模型 / 输入 / 命中 / 写出 / 命中率；
- 点一行 → 浮层显示该请求的上下文（system 段、工具、消息条目、与上一条的差异）；
- 无记录 / 开关关 → 一句话空态。

## 4. 备选与明确不做

- **备选 A：给 system 注入加 cache_control 断点**（Anthropic 风格）。
  OpenAI 兼容网关不吃这个字段，且断点之前的内容变化仍然会失效。否。
- **备选 B：所有 section 按会话冻结**。切项目 / 新建课题在会话内不可见，
  模型会拿着过期信息干活。否。
- **备选 C：把动态内容做成 tool 结果注入**。需要伪造 toolCall，污染工具账本。否。
- **明确不做**：请求级持久化流水（不落盘，DB 还原已够）；按供应商拆缓存命中对比；
  历史请求的临时注入回放（本来就没存）。
- **回滚**：`PROMPT_TAIL_INJECTION=false` 回到旧形态（system 拼在最前面，仅兼容性排障）；
  `CHAT_CACHE_STATS=false` 关掉请求统计端点与页面整块。

- `pnpm typecheck`
- `pnpm --filter @lifediary/server test`（重点：`injection.test.ts`、`context-inspect.test.ts`、
  `request-stats.test.ts`）

  两条 `system.hash` 相同、详情对比 `systemChanged=false` / `toolsChanged=false`）
- 隔离实例 + 浏览器：设置 → 上下文页显示真实 69 条请求 / 89% 命中率；点开建课题后那条
  显示「system 变了 课题（判据）」；点开最后一条全未命中显示「前缀与工具面都没变」。
  若上游网关自身不稳定（同 prompt 偶发 0 命中），在页面里如实可见，不归因于前缀变化。
- 真模型连续两轮 cacheRead 实测：留待服务重启后由用户实际使用观察（页面已经能看到）。
