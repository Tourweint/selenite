# 2026-11-14 中继连接稳定性：心跳 · 半开检测 · 单身份互斥

## 背景

用户 2026-11-14：「你说它时而连上，时而连不上，这是咋回事啊？把这处理一下，把比较稳定的部分弄一下，安全性方面肯定也要做。」

查出来的不是一个原因，是**两个独立原因叠在一起**，任何一个都能单独造成"时而连上时而连不上"。

## 结论：两个根因，都已修

### 根因一：同一台电脑上有两个 harness 抢同一枚设备令牌（主因）

一台电脑在中继名册上只有一个 `deviceId`（由 `RELAY_TOKEN` 决定）。两个 harness 进程同时用它连中继时，
中继按"同设备顶替"语义把旧连接以 **4409 superseded** 关掉——于是两边互相顶替，**每秒断一次、永远握不上手**。

实测证据（本机）：

| 观测 | 数值 |
|---|---|
| `relay/status.reconnects` 三分钟增长 | 64 → 85 |
| `lastCloseCode` | 一直是 `4409`，`reason=superseded` |
| 每次连接存活 | ≈ 1.2 秒 |
| 同时在跑且都连中继的 harness | 2 个（39847 与 **39899**，后者是早先遗留的实例） |
| 启动后日志里的"已连接"行数 | 891 行，而"断开"零行（旧代码不记断开原因） |

页面上看到的就是：绿一下、红一下、绿一下。

### 根因二：客户端握手后完全不说话，静默长连接被回收

旧客户端握手成功后只在"要发业务帧"时才写 socket。家用宽带 / 运营商 NAT 对静默长连接的空闲回收常在
30–90 秒，中继侧也有 `IDLE_TIMEOUT_MS=90s` 的入站静默 terminate。被掐掉时客户端只等 `close` 事件，
没有任何主动判活手段——TCP 半开（对端断网未挥手）时甚至等到 timeout 才反应。

### 另外两处让问题无法被看见

- 断开原因不入日志（只记"已连接"），`relay/status` 也只有 `connected` 一个布尔；
- 退避的 `attempts` 在"连接活不到 10s"时会停在 0（`Math.max(0, attempts - 1)`），退避永不增长，
  于是变成每秒一次的高频重试，把问题放大成"一直在闪"。

## 改了什么

| 文件 | 改动 |
|---|---|
| `ts/apps/server/src/relay-client.ts` | **NS-01 心跳**：每 20s 发 `{kind:"ping"}`（中继 hub 早已支持回 pong，老版本中继也认，**不改协议**）；**半开检测**：45s 无任何入站 → 主动 `terminate` 重连；**断开诊断**：close code/reason、存活时长、入站静默时长、下次延迟全进日志；退避加 ±20% 抖动；`stats` 暴露 `reconnects / lastConnectedAt / lastCloseAt / lastCloseCode / lastCloseReason / lastPongAt` |
| `ts/apps/server/src/index.ts` | **NS-02 身份互斥**：`.data/relay-identity.pid` 钉住"谁代表这台电脑连中继"，后起进程发现对方进程还活着就不连（服务照常起），`relay/status` 出 `blockedByPid`；`POST /relay/link` 撞上时回 **409 `relay_busy`**；启动与退出时登记/释放锁。status 增补 `reconnects / lastCloseCode / lastCloseAt / lastConnectedAt / lastPongAt / blockedByPid` |
| `ts/apps/server/src/relay-link.ts` | **安全**：`relay-link.json` 在 Windows 上用 `icacls /inheritance:r /grant:r <当前用户>:F` 真正收紧 ACL（`mode 0o600` 在 Windows 上是空操作，之前同机其他账户能读到两枚令牌） |
| `ts/apps/server/src/relay-client.test.ts`（新） | 假中继两例：心跳正常不重连 / 对端装死时按 liveness 主动重连 |
| `web/settings-connection.js` | 「重连中（第 N 次）」替代原来的"未连上"；提示行带最近断开时间 + 关闭码人话（4409 = 有另一个同名连接在顶替）；`blockedByPid` 时直接说清"本机另有 harness（pid X）在连中继，两个一起连会互相顶断" |

回滚开关：

- `RELAY_HEARTBEAT_MS=0` → 不挂心跳、不做半开判定（回到"只等 close"）
- `RELAY_IDENTITY_LOCK=off` → 不做身份互斥（回到"谁先连谁占位、双连互相顶替"）

## 没验的

- **真断网 / 换网络**（拔网线、切 WiFi、睡醒唤醒）没有实测——半开检测的阈值（45s）是按"3 个心跳周期"定的，
  真断网后会 45 秒内发现并重连，这个时间没在真实断网下量过。
- **浏览器实机点验**（本机没有图形界面自动化授权）："重连中 / 被占用"两种新文案只做了代码与接口层核对。
- **中继侧部署仍是旧代码**：本次没动中继（心跳用的是 hub 早就支持的 ping 帧，不需要升级）；
  但上一轮的 `isOwner` 鉴权修复要重新部署 + 配 `RELAY_OWNER_TOKEN` 才生效，**到现在仍未部署**。

## 遗留建议（未做，需要你决定）

`RELAY_TOKEN` 是一枚"长期设备令牌"，任何拿到它（`.env` 泄漏、旧备份、另一台机器复用）的进程都能顶替这台电脑。
要不要给设备令牌加"单次使用 + 定期轮换"，是产品口径问题，不在这次修 bug 的范围内。
