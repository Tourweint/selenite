# 打开本地目录的顶部回执（浮在最上层的明显提醒）

日期：2026-11-11
状态：**已撤销（当天）**——用户口径："这样体验还是不好，上边的弹窗提醒就不要了，把它直接弹到顶层。"
web 三件已还原（`toast` 顶部变体、`openExplorerInOs` 顶部回执、`.toast.is-top` 样式全部撤干净），
后续见《2026-11-11-打开目录直弹顶层.md》。本文保留当时的做法与测量，留"当时怎么想的"。

## 起因

用户口径（2026-11-11）：点项目「在资源管理器中打开」后，"它不在最上面这层，而是在最底下这层，
所以没有这个感觉。把它做成浮在最上层、比较明显的提醒。"

核对（2026-11-11）：两层原因叠加——

1. **窗口被压在底下**：资源管理器窗口是服务端（后台 node 进程）`spawn explorer` 拉起的
   （`files.ts:44` platformOpen），Windows 前台规则不给后台进程"抢前台"的权限，新窗口经常
   开在所有窗口的最底层，只看得见任务栏——点了像没点。
2. **界面零回执**：`openExplorerInOs` 成功路径只 `closeProjectMenu()`，一句话都不给；
   失败才弹 toast，而 toast 挂在屏幕底部（`bottom: 96px`），离开输入区远的地方更看不见。

## 改了什么（纯 web 三件里的两件，零契约）

- **`web/app.js`**
  - `toast(text, opts)` 加 `opts.top`（浮层变体）与 `opts.title`（悬停看全文）两个可选参；
    缺省行为与原来逐字节一致（底部、无 title），约 40 处旧调用不受影响。
  - `openExplorerInOs` 成功 / 失败 / 404 旧版本 / 断连四种出口统一走顶部回执；
    成功文案 `已在资源管理器打开「目录名」`，悬停显示完整路径（服务端本来就回 `path`）。
- **`web/style.css`**：`.toast.is-top`（`top: 18px`，z-index 仍 60，压过 modal 55 / 抽屉 56）
  + 220ms 下落入场动画（`--ease-standard`，与全站弹出同拍）；`prefers-reduced-motion` 时去动画。

## 刻意没做

- **没让资源管理器窗口真置顶**。要让窗口稳拿前台得从有前台权的进程拉起（MyGo 壳）或加原生
  调用（SetForegroundWindow），两条都要动壳/引依赖，超出"补回执"的范围；界面回执先兜住感知。
  真要窗口置顶，另立项（壳加"打开目录"桥能力）。
- **没把全局 toast 都挪到顶部**。错误类提示都在输入区附近弹出（那正是人在看的地方），
  只有"系统里做了件事"的回执走顶部——两类提示语义不同，落点也不同。

## 验证

- 浏览器实机（隔离实例：临时 cwd + PORT=39999 + LLM_PROVIDER=faux，独立 .data，不碰生产）：
  - **成功回执**：点侧栏主项目「在资源管理器中打开」→ 真 HTTP 200 → 顶部浮出
    「已在资源管理器打开「lifediary-harness」」，悬停 title = 完整路径（截图 ✅）。
  - **失败回执**：`EXPLORER_OPEN=false` 重启实例 → 真 400 `explorer_disabled` →
    顶部浮出「打不开资源管理器：资源管理器入口已关闭（EXPLORER_OPEN=false）」（截图 ✅）。
  - 两条都是真按钮 + 真服务 + 真 HTTP，没有 stub。
- **验证事故（如实记）**：本环境浏览器 evaluate 跑在隔离世界，页面内 fetch 拦截写不进去，
  前几轮"拦截后点击"实际全打到了真实端点，验证机上真弹了 6 个资源管理器窗口——
  已逐一定位关闭（Shell.Application Windows 按 LocationURL 匹配后 Quit）。生产实例未受影响。
- **普通底部 toast 未做浏览器实测**（代码审查代替）：基样式块未动，`toast(text)` 缺省分支
  只多一次 `classList.toggle("is-top", false)`（无类时是空操作），位置行为不变。
- 服务端零改动，`files.test.ts` 既有断言不涉及（未重跑全量单测，如实记录）。
