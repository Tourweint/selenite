# 归档管理对齐 ZCode：分组页 + 防误触 + 自动归档 + 永久删除

日期：2026-11-13
状态：已落地（服务端 + 桌面端 + 探针 + 浏览器联调 + 文档）；方案见
`docs/设计方案/2026-11-13-归档管理对齐ZCode（分组页+防误触+自动归档+永久删除）.md`（文首有下沉落点表）。

## 起因

用户口径（2026-11-13）：调查 ZCode 的归档管理后认为"全都要"。四件差距：归档页分组重做
（项目分组折叠卡 + 排序/项目筛选 + 50 条递增 + 组级恢复）、归档防误触（运行中禁止 + 行内二次确认）、
自动归档（翻案：上一轮拍板"不做自动过期"，翻回"有能力但默认关"）、永久删除协议
（翻案："没有删除按钮只有归档"，翻为"归档是唯一门槛 + 预检清单 + 连分叉子树连根删"）。
上一轮"磁盘只增不减"的登记由第 4 条兑现。落地分三批：A 服务端、B 桌面端、C 收口
（本篇三批合成一段记录）。

## 改了什么

### 服务端（批A）

- 新增 `agent/durable-delete.ts`：
  - `GET /api/v1/agent/chat/:id/deletion-preview` → `{conversationId, title, rounds, lastAt, archivedAt?, blocked?, subtree, estimate}`；
    `blocked.reason` 收敛为三值 `not-archived / kind / busy`（chief / `partner-` / `task-` 细分进 `detail` 文案），
    blocked 时 `subtree` 为空数组（不给名单）；`estimate` 走 SQL COUNT。
  - `POST /api/v1/agent/chat/:id/delete` → 执行前**重跑一遍预检**（预检与执行之间状态可能漂移），
    任一 blocked → 400；成功 `{ok, deleted:{conversations, entries, tasks, submissions}}`。
  - 子树 BFS：全表扫 `conversations.record.parent.conversationId`（fork 边只存在于 record JSON，无反向索引），
    整条子树连根删（从叶到根）。裸 SQL 单事务，顺序 documentRevisions → documents → entries → tasks →
    submissions → conversations；`record_ids` 孤儿行刻意不清（方案已登记）。
  - 不删：文件与附件、记忆四层、派活回执、磁盘目录；日志只记计数与 id 数量。
- `agent/lifecycle.ts` 新增**维护闸**：`beginHarnessMaintenance / endHarnessMaintenance /
  runExclusiveMaintenance / getHarnessForMaintenance / closeHarnessForMaintenance`——
  删除手术期间 `getHarness()` 对其他调用方合闸排队（排队不重开 Harness），并发删除在
  `runExclusiveMaintenance` 的串行链上排队。
- 新增 `agent/auto-archive.ts`：调度器照 autonomy.ts 的 `syncSweepTimer` 范式（按需开停 + `unref`），
  启动首轮延迟 5 分钟、之后每小时一轮；判定只收普通会话（chatKind=worker），跳过已归档 / 置顶 /
  运行中 / 空会话，`lastAt` 超过天数门槛才收，**每轮上限 50**；全量枚举 `Chats.byExternal`
  （不走 listChats——它按 limit 截断，要收的恰是旧会话）。日志一轮一行，只记条数与 id 数量。
- `index.ts`：归档端点换 `archiveChatGuarded`（session.ts）——运行中（`pi.live.run` 存在）归档
  → `400 {error:"conversation_busy", message:"会话正在运行，请先停止再归档"}`（`/hide` 别名同口径；
  解析失败与忙态读不出来时按原行为照旧归档）；挂 `mountDurableDelete`；
  flags 端点接 `onChange` 回调（`ARCHIVE_AUTO_*` 写成功即 `autoArchiveScheduler().sync()`）。
- `flags.ts`：新增三键 `CHAT_HARD_DELETE`（hot，默认 true） / `ARCHIVE_AUTO_ENABLED`（hot，默认 false） /
  `ARCHIVE_AUTO_DAYS`（hot，默认 30）；`FLAG_DEFS` 扩展**数值型开关**（`values` 留空 + `min:1`，
  按「≥min 的整数」校验，不再查枚举表）。`chat-meta.json` 写路径补原子写（临时文件 + rename）。

### 桌面端（批B）

- 设置 → 归档的会话卡重做：**按项目分组折叠卡**（真实项目名一组；有 projectId 但查不到项目 →
  「项目已删除」；无 projectId → 「未归类」）+ 组计数 + 组头「全部取消归档」（组内逐条串行
  `/unarchive`）；顶部 标题搜索 + 排序下拉（归档时间 / 最后活跃，倒序）+ 项目下拉，三者叠加生效；
  每组展开首屏 50 条，「显示更多」50 条递增；行内动作 = 恢复 + 永久删除。
  **组间顺序：真实项目组优先（组内最新一条新的在前），未归类 / 项目已删除固定垫底。**
  页级「全部恢复」按钮退役（组级恢复取代之）；`POST /chats/restore` 端点保留不删。
- 永久删除确认弹窗：预检（`GET deletion-preview`）→ blocked 只给原因不给确认框（人话文案）；
  正常态「将永久删除「标题」，含 N 条编辑分叉，将一并删除。名单：」+ 子树逐条标题与时间 +
  「预计删除 会话 X 条 / 记录 Y 条；文件、记忆、磁盘不受影响。删除不可恢复。」+
  **输入会话标题确认**（逐字匹配才放开按钮）。**N = subtree.length − 1**（名单含目标自己）。
- 会话行归档防误触：点归档图标出现行内「归档？确认 / 取消」小条（非弹窗），确认才 POST；
  当前会话开跑时同步侧栏归档图标禁用态 + 悬停提示；其余行 UI 不知忙态，由服务端 400 兜底，
  toast 显示服务端说明。
- 设置 → 会话新增「自动归档」区：开关（走 toggleFlag）+ 天数数字输入（change 即存，
  失败回显旧值），标签悬停文案随天数变；两键未上架（404）时 toast 报原因，不静默失败。
- CSS：分组折叠卡 / 删除名单 / 行内确认条等样式。

### 收口（批C）

- `scripts/http-probe.ts` 新增 **§14.8 永久删除 + 忙时归档**（36 项断言，见"验证"）：
  归档 → 预检形状（subtree/estimate）→ 执行删除（计数>0）→ 归档清单 / 活跃清单 /
  `sessions/search`（对照：删前搜得到、删后搜不到）都不含它；未归档 preview → blocked
  not-archived；chief preview/delete → blocked kind；忙时归档 400；`CHAT_HARD_DELETE=false`
  → 两端点 400「永久删除已关闭」→ 改回 true。
- 顺手修一处批B 前端缺陷（浏览器联调时发现）：`app.js` 行内归档确认的 400 分支
  toast 取值顺序 `data?.error || data?.message`——忙时会 toast 出机器码 `conversation_busy`
  而不是服务端说明；改为 `message || error`（注释同步：error 是机器码，人要看说明文字）。

## 为什么这么做（关键取舍）

- **分叉连根删，不保留独立分叉**（与 ZCode 相反）：durable 的 fork 是引用不是复制
  （entry 全局 id 单调递增、按 id 序回放），物化父历史进子会话会时序错乱，等上游提供删除 API 等不起。
- **删除互斥先合闸再关门**（实现与方案步骤表的刻意调整，见下）：窗口更小、闸内复核省一次重开。
- **自动归档不走 durable sleepUntil**：清扫任务不需要"到点必响"，每小时定时器 + 错过补扫够了。
- **确认用名单 + 标题输入**，不用 ZCode 的三清单确认：删除对象是"会话+它的编辑分叉"，清单天然短。
- 备选与明确不做的全表见方案文档（分叉保留 / 扩删除范围 / 连附件清 / 天数分档等）。

## 实现与方案的偏差（逐条登记）

1. **删除时序调整**：方案写"先 `discardHarness` 再拿互斥"，实现反过来——
   先 `runExclusiveMaintenance`（合闸）再 `closeHarnessForMaintenance`（关门）。
   反过来不存在"Harness 已关但闸还没合"的缝隙，且闸内重跑预检复用还没关的 Harness。
   保证等价：手术期间进程内必然无 Harness、且无人能重开（`durable-delete.ts` 模块头有完整论证）。
2. **blocked reason 收敛三值**：方案草案列了 `not-archived / kind / busy / chief / task / partner`
   六值，实现收敛为 `not-archived / kind / busy` 三值，chief/partner/task 细分进 `detail` 文案
   （前端本来就不 switch reason 出文案，三值足够；接口文档按三值记）。
3. **维护互斥落地为 `runExclusiveMaintenance` 串行链**：方案只说"拿一把删除互斥"，实现发现
   闸内两段（SQL 手术 → 重开 Harness 清映射）不能共用同一个"绕闸"通道，否则第二段会和
   第一段并发抢库——串行链保证第二段看到删完后的状态。
4. **数值型 flag**：`ARCHIVE_AUTO_DAYS` 要"≥1 的整数"校验，枚举表装不下，
   `FLAG_DEFS` 扩了 `min` 字段（`values` 留空即数值型）。
5. **flags onChange**：`ARCHIVE_AUTO_*` 是 hot 开关但调度器定时器不在"懒读"面里——
   `mountFlags` 加 `onChange` 回调，写成功即 `sync()`，运行中开/关都当场生效
   （否则动态开要等重启，hot 名不副实）。
6. **组间顺序**：方案没定组间排序，实现取"真实项目组优先（组内最新一条新的在前），
   未归类 / 项目已删除固定垫底"——项目组是主人有意识整理的，垫底的是没有归属的。
7. **分叉计数 = subtree − 1**：预检 `subtree` 名单含目标自己，弹窗"含 N 条编辑分叉"的
   N = `subtree.length − 1`（`Math.max(0, …)` 兜底）。
8. **「项目已删除」组造不出真数据**：要有 projectId 但项目查不到才会进该组，
   测试环境造不出这条真实链路（删项目是软归档、登记还在），该组逻辑由前端分支代码保证，
   未在浏览器联调中真数据复验（如实登记，见"没验什么"）。

## 回滚开关

- `CHAT_HARD_DELETE=false`：deletion-preview / delete 两端点 400「永久删除已关闭」。
- `ARCHIVE_AUTO_ENABLED=false`：调度器不开（flags 端点写完即生效，不用重启）。
- 归档页 UI 回退 = revert（纯前端）；`POST /chats/restore` 端点保留，旧客户端不 404。

## 已知边界（如实登记）

- 不做归档事件广播：正在界面里开着的会话被自动归档后，要等下次 `loadChats` 才从列表消失；
  该会话仍可继续聊（归档不影响正文读写）。
- 删除不删：文件与附件、记忆四层、派活回执、磁盘目录、`record_ids` 孤儿行；项目登记的删除不做；
  执事 / 群 / 任务会话的删除不做（扩范围另立方案）。
- 自动归档每轮上限 50，剩余下轮继续；空会话（没有轮次）不收。
- 「项目已删除」组：见偏差第 8 条，未用真数据复验。

## 没验什么

- `pnpm probe` 没跑：本次未动内核提交 / 流式 / 闸门语义（闸门语义由 http 探针与单测覆盖）。
- 自动归档的"真归档"动作没在隔离实例里走通：判定命中要求 lastAt 超过天数门槛（最小 1 天），
  造不出"1 天没动静"的真会话；命中 / 上限 50 / 跳过置顶忙态等判定语义由
  `auto-archive.test.ts` 单测钉住，浏览器只验到"开关生效 + 首轮扫描日志出现"。
- 「项目已删除」分组未用真数据复验（见偏差第 8 条）。
- ARCHIVE_AUTO_DAYS 非法值"回落 30"是**消费处 env 懒读层**的行为
  （`archiveAutoDays()`，auto-archive.test.ts 钉住）；flags 端点层 0 / 负数直接 400，
  两层口径不同、各自有测。
- 手机端未回归（零契约面变化）。
