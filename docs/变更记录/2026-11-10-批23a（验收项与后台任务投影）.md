## 一、`steps` 的「验：」前缀与验收项逐项投影（§一）

- **约定**：`delegate` 的 `steps` 每项仍是纯文本，`验：`（全角；半角 `验:` 同样认）开头 = 验收项，
  其余 = 动作。旧格式逐字节兼容，不新增参数、不改 `delegate` 返回形状。
- **投影**：`delegation-api.ts` 新增纯函数 `projectAcceptanceChecks(steps, reviews)`，
  详情顶层加 `acceptanceChecks`。每项 `{text, status, note?}`。
  - `text` = 去掉前缀后的验收原文；
  - `reviews[]` 全 `pass` → 全部 `passed`；
  - 有 `fail` → 全部 `failed`，`note` 列未通过的 slug；
  - 没有 `reviews` → 全部 `unknown`，`note` 写「没有验收记录（reviews 为空），无法逐项判定」；
  - 只有 `blocked` 这类非 pass 非 fail 的结论 → 同样 `unknown`，`note` 带原 verdict。
  **不按条猜哪一条过了**——任务书要求"只按已有事实"，这里把"没有逐项证据"如实写出来。
- **形状与任务书字面的差异**：任务书写作 `acceptanceChecks: string[]`，但同时要求"每项状态"与
  "note 写清原因"；纯字符串数组装不下状态。这里取 `Array<{text,status,note?}>`，已回写接口文档。
- **开关** `DELEGATION_ACCEPTANCE_CHECKS`（默认 true；false/0/off → 详情不带 `acceptanceChecks`，
  `steps` 原样保留）。没有 `验：` 项时同样不带键（老单零影响）。
- **工具描述**：`delegate` 的 `steps` 参数描述加一句前缀约定。描述属于提示词缓存前缀资产，
  本次改动会打掉一次上游 prompt cache（工具顺序未动，`tool-schema-guard` 仍绿）。

## 二、后台任务投影到任务详情（§二）

- `delegation-api.ts` 新增纯函数 `projectTicketBgJobs(ticket, jobs, now?)`，详情顶层加 `bgJobs`：
  `{id, commandSummary, startedAt, endedAt?, exitCode?}`，**只有摘要，不返回日志正文**
  （正文仍走 `GET /api/v1/agent/bg-jobs/:id/log`）。
- **时间窗口**：`bg-jobs/index.json` 没有 ticketId，只能按单的时间窗过滤——起点 `created_at`，
  终点 = 终态单的 `updated_at` / 在办单的当前时刻；`startedAt` 落在 `[起点, 终点]` 才算。
  没有 `created_at` → 返回空（没有依据就不猜）。
- **开关** `TICKET_BG_JOBS`（默认 true；false/0/off → 详情不带 `bgJobs`）。窗口内没有 → 不带键。
- 读索引失败不挡详情（try/catch 回空数组，与 gates / 死信同一口径）。

## 已知边界 / 没做

- **后台任务归属是 best-effort**：索引不记 ticketId，时间窗口内同时开着的别的单的后台任务会混进来；
  要按单归属得改 `bg-jobs/index.json` 的落盘结构（本批明确不做）。
- `acceptanceChecks` 是**单级状态**：不做"每条验收项对应哪次 review"的映射——`reviews[]` 只有
  task slug，没有验收项下标，硬映射就是编造。
- 前缀只认 `验：` / `验:`；英文 `check:` 之类不认（任务书未定义，不扩语义）。
- 未做前端渲染（任务书未要求；字段纯增量，老客户端忽略）。
