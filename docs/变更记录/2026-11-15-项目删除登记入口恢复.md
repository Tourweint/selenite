# 项目删除登记：界面入口恢复 + 连带解除执事挂载

日期：2026-11-15　范围：电脑端设置 → 项目 + `DELETE /api/v1/projects/:id` + 执事库

## 改了什么

1. **界面恢复删除入口，位置在归档页**（推翻 2026-11-12「界面不提供入口、仅程序化面」的旧决定；
   位置按用户拍板：**只放归档页**，活跃项目卡没有删除——不常用就归档放着不管，要清登记
   只能去归档里删，与"归档 = 冷却区，可以永久删除但很少删"的心智一致）：
   设置 → 归档 → 项目卡，在「恢复」旁加红色「删除登记」钮（`.btn-primary.is-quiet.is-danger`），
   普通确认弹窗。弹窗文案说清四件事：磁盘不动；**记忆一条不删**；执事挂载一并解除；
   登记删了不可恢复（重新登记=新项目）。成功 toast 带解除条数，刷新归档页与侧栏项目列表。
   第一稿把入口放在活跃项目卡 ⋯ 菜单，用户当场纠正"逻辑反了，只能从归档里删"，已改回。
2. **连带解除执事挂载**：`PartnersStore.detachProject(projectId)` ——
   `UPDATE partners SET project_id = NULL WHERE project_id = ?`，返回解除条数。
   端点顺序固定为**先解除、后删登记**（反过来登记删了就没人清悬空引用）；
   删除失败时挂载已摘，重试即成（摘的是"指着存活项目的挂载"，无损失）。
   响应新增纯增量字段 `detachedPartners`。
3. **`project_in_flight` 错误文案**改为"再归档或删除登记"（同一守卫两个入口共用）。
4. `project-api.ts` 新增 `resetProjectsStoreForTest()`（关+清单例，容忍已关闭的库）——
   DELETE 端点测试需要换临时库重开；`projects.ts` 同步 re-export。

## 为什么

- 用户问"物理移除目录有没有异常处理 / 要不要自动落归档"。核对结论（2026-11-15）：
  丢失兜底已齐（设置页黄标「主文件夹丢失」/「不在了」、侧栏「丢失」、切当前项目 400
  `project_missing`、派单前复核拒绝、读写边界自动退出集合），**自动归档不做**——
  物理移除多半是挪位/改名/暂时没挂载，自动归档属于无感自动化（用户既定口径：说不清
  用途的自动化不做），丢失态可见 + 处置动作（改路径/归档/删除）全在菜单里就是对的形态。
- "注册多了"走既有归档（软退场，归档页可恢复），不新增机制。
- 删除登记只删 SQLite 行；执事挂载（2026-11-15 跟人走方案）此前删除时不清理，会留悬空引用。

## 不确定 / 边界

- **活跃项目卡刻意没有删除入口**（用户拍板）：删登记是"冷却后的清理"，先归档再删；
  删除端点仍可被程序化调用，但界面只从归档页可达。
- **记忆一条不删**（用户强调）：`project:<uuid>` scope 数据在登记删除后保留成孤儿，
  不丢东西；想连记忆一起清另立项。
- 手机端不渲染删除入口（本项目分区的既有边界）。
