# 执事点击「不存在」谎报修复（open 404 拆义）+ 问候不报模型名

日期：2026-11-06
类型：缺陷修复（前端行为 + 问候提示词一行）

## 问题

用户报告：花名册里明明有两个执事，点其中一个提示「没有这个执事」。

排查（2026-11-06 当日全量核实）：两个执事（阅读助手/记账助手）档案都在、`GET /api/v1/partners`
正常、`POST /api/v1/partners/:id/open` 逐个调通（阅读助手 existing，记账助手真实生成并发出了
首次问候）。**「执事不存在」是谎报**，根因两层：

1. **主因：页面与服务的版本错位。** 侧栏调整批次把「点执事」改成新契约
   `POST /partners/:id/open`（C 批），但后端代码要重启服务进程才生效；旧进程没有
   `/open` 路由，Hono 对未知路由一律 404，前端把 404 一律翻译成「没有这个执事」。
2. **次因：花名册残留幽灵行。** `loadRoster` 拉失败时保留上一次列表（防闪烁的容错），
   档案被删后又赶上一轮拉取失败，就会残留一个点了必然 404 的行。重启窗口期点击同理。

即：`/open` 的 404 有两种含义（「档案真没了」和「服务版本旧没这个路由」），前端没拆义，
报错后也不自愈。

## 修复（纯前端 app.js + partner-runtime 一行）

1. **404 拆义**：`openPartnerChat` 收到 404 后用 `GET /api/v1/partners/:id` 复核一次——
   - 复核 200（档案在）→ 服务旧：错误卡「服务还是旧版本，先重启服务再点」+ 重试按钮；
   - 复核 404（档案真没了）→ 静默刷花名册让幽灵行消失 + toast「这个执事已删除，列表已刷新」；
   - 复核失败/403 → 通用「读不到」卡，不猜。
   新增 `partnerExistsAfter404`（复核）与 `showPartnerOpenFailureCard`（轻量错误卡，
   不切路由不做 canonical 探测）。
2. **失败自愈**：`showPartnerOpenFailure`（503 等）与 409 分支都顺手静默 `loadRoster()`，
   名字/状态点/幽灵行自动对齐——「点开失败但列表还说在」的观感来源一并消掉。
3. **问候不报模型名**：`GREETING_REQUIREMENTS` 加一行「你就是这个执事本人，不是某个
   大模型的客服」。实测模型会自称「商汤日日新·商量」（隔离生成会话只有 SOUL 快照，
   没有约束时模型亮供应商名），主人不想看到。

## 验证

- `pnpm typecheck` 过；`pnpm --filter @lifediary/server test` 239/239 过。
- 浏览器实测（真服务 :39847，三场景全绿）：
  - **幽灵行**：建测试执事 → 页面加载后服务端删除 → 点残留行 → 行自动消失，
    无「执事不存在」谎报、无误挂错误卡、主区干净；
  - **服务旧**（fetch 拦截模拟 `/open` 404、档案 GET 放行）：错误卡给「先重启服务」
    文案 + 重试按钮可复用，不再说「执事不存在」；
  - **恢复真网络**：拆掉拦截再点 → 执事专线正常打开（表头「阅读助手」、历史正常回读）。
- 问候约束属提示词改动，新生成时生效；不回写已 sent 的历史问候。
