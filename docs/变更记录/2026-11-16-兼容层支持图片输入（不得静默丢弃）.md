# 2026-11-16 兼容层支持图片输入（不得静默丢弃）

**改了什么**

1. **`messages[].content` 的 `image_url` 不再被压掉**（新增 `openai-compat-content.ts`）
   - `parseOpenAiMessages()`：字符串 / `text` 段仍按旧 `textOf()` 口径拼（数组用**空串**连，
     不是 `attachments.ts` 的 `\n`）——纯文本逐字节不变；`{ "type": "image_url", "image_url": { "url": "…" } }`
     拆成内部 `{ type: "image", mimeType, data }`，以 `parts` 挂在消息上。
   - `data:image/*;base64,...` 内联 URL：拆 mimeType + 裸 base64（schema 大小写不敏感，
     内嵌换行 / 空白先删掉再校验形状）。
   - 外部 `http(s)` URL：**400 `unsupported_image_url`**，message 写明请客户端下载后改成
     data URL 内联。本单不做下载转发（拉取、防 SSRF、临时文件生命周期都是另一件事），
     但**绝不静默丢**——静默丢正是这次要修的缺陷。
   - 其它非法形状（缺 `url` / 相对路径 / 非 base64 data URL / 非 `image/*` / 空数据 /
     base64 形状坏）：**400 `bad_image`** 带可读原因。
   - 上限与开关**复用 `attachments.ts`**，不另写一套：单图解码后 ≤8MB、单条消息 ≤4 张；
     `AGENT_ATTACHMENTS=false` 时带图 → **400 `attachments_disabled`**（纯文本请求不受影响）。

2. **两条分流共用同一处解析**（`openai-compat-mount-open-ai-compat.ts`）
   - 解析挪到分流之前：`X-Task` 任务通道与普通聊天（无 `system`）都拿得到 parts。
     带 `system` 仍 400 `system_prompt_not_supported`（2026-10-31 直通已删除；文件里
     "带 system → 直通上游"的旧注释本次一并改正）。
   - `openai-compat-agent-chat.ts`：只有**最后一条 `user`** 的 `parts` 随 `chatStream` 提交；
     纯文本仍提交字符串，老链路形状不变。
   - 纯图消息（没有文字）不再被"空白消息"过滤掉；`messages 里没有可用内容` 只在真没有
     可用消息时出现。
   - 会话 id：纯图消息没有正文，`conversationIdFor` 改用图片指纹
     （`image/png:<base64 前 64 字符>`）当种子；否则所有纯图新会话都会落到同一个
     `oa-<空串哈希>` 上互相串历史。纯文本的种子与改动前完全相同。

**为什么**

手机端实现时实读确认：`POST /api/v1/llm/chat/completions` 用 `textOf()` 把 content 压成纯文本，
`image_url` 段被**静默丢弃且不报错**——只用兼容层的客户端发图，模型收不到图、也不会报错，
属于"看着成功、其实残废"的缺陷。

**验证（2026-11-21 实跑）**

- `pnpm typecheck`：通过（exit 0）。
- `pnpm --filter @lifediary/server test`：1252 条 / 通过 1247 / 失败 5；5 条与改动前基线**完全相同**
  （基线 1243 / 通过 1238 / 失败 5）。本单新增 9 条全绿，`attachments.test.ts` 26/26：
  纯文本逐字不变、data URL 拆 mime+base64、大小写/换行、纯图不丢、>4 张、>8MB、
  `AGENT_ATTACHMENTS=false`、外部 URL、非法形状、会话种子。
- 路由级冒烟（临时 SQLite + `LLM_PROVIDER=faux`，真 `app.request()`，脚本跑完即删）：
  - 内联图 + 文字 → 200；回读 transcript：`{"role":"user","text":"看看这张图","images":["image/png:…"]}`
    ——图确实进了会话；
  - 纯图（无文字）→ 200；transcript 里 `text:""` + `images` 1 张；
  - 5 张图 → `400 {"error":{"code":"bad_image","message":"一条消息最多 4 张图片"}}`；
  - 外部 URL → `400 unsupported_image_url`；
  - `AGENT_ATTACHMENTS=false` + 图 → `400 attachments_disabled`；同一开关下纯文本仍 200。
  - `X-Task: segment` + `task_vars` + 内联图 → 200；任务会话 transcript 同样是
    `text` + `images`（任务通道与聊天共用同一处解析，不是只修了一路）。
- 基线那 5 条既有失败与本单无关（未代修）：`arch-guard.test.ts` 3 条
  （`respond_escalation` / `tool_search` 未进闸门白名单，来自并行会话在途的 `tools.ts`）、
  `auxiliary.test.ts` 1 条（HEAD 的 `AUX_USES` 已含 `split`，测试仍按 6 个用途断言，
  提交状态就红）、`partner-work.test.ts` teardown `EPERM`（Windows 临时目录清理，环境问题）。

**已知边界 / 明确不做**

- 外部 `http(s)` 图片 URL **只报错、不下载转发**。
- 只支持 Chat Completions 的 `image_url` 段；Responses API 的 `input_image` 不认。
- `image_url.detail` 忽略（内核不吃这个字段）。
- 只有**最后一条 `user`** 的图进入本轮（与"只取最后一条 user"的既有契约一致；历史文本
  同样不转发）。前几轮的图落在 durable transcript 里，续话时模型仍能回读。
- 非图片的未知分段（如 `input_audio`）仍按改动前忽略——本单只修图片这一类。

**回滚**

无新增开关：`AGENT_ATTACHMENTS=false` 就是图片路径的总闸（带图请求 400，纯文本照旧）。
回滚代码 = 撤销本单三个 TS 文件 + 两处文档回写。
