> 任务书：`docs/设计方案/2026-11-07-扫尾批2任务书（CodeBuddy）.md`。范围：`ts/` + 基线文档注记，不碰 desktop/。

## 一、根因链（2026-11-07 读码核实）

1. **会话创建即绑模型**：`openChat`（agent.ts:1598/1641）写 `agent: { model: chatModelRef("off") }`，
   模型引用是派生变体 id `<模型>#think-<档>`（provider.ts），随 durable 会话持久化，重启不丢。
2. **派生变体懒注册**：`chatModelRef()` 只在被调用时才把 spec 写进 `variantSpecs`；调用点 = 新建会话 / 切档。
3. **重启后注册表只剩基础模型**：`variantSpecs` 是进程内内存、不落盘。旧会话 resume 不走创建路径；
   `syncConversationModel`（agent.ts:1246，每轮 :1974 调用）在"会话模型仍是当前全局模型"时直接 return，
   也不再调 `chatModelRef`。于是旧会话的 `#think-off` 无人注册，内核
   `generation.js:38/273` 的 `getModel()` 返回 undefined → `failNoModel` →
   `Model provider/<模型>#think-off is not available`（ref 空时 "No model is configured"，`no_model null`）。
   表现为"旧会话全坏、新建正常、重启后才坏"。
4. **任务/研究专线的温度型变体**（`<模型>#t…`）在每次派发时现派生现注册、随派自愈；但重启后续跑的
   历史专线会话暴露在同一洞上。

## 二、修法

**主修（已做）：变体随注册表重建确定性预注册。** `provider.ts` 的 `rebuild()` 在清理已消失基座之后、
`buildProvider` 之前调 `preseedThinkingVariants(doc)`：目录内每个模型恒注册 `#think-off`；其余档按
`thinkingLevelsFor`（声明的 `modelThinkingLevels` 优先，缺省 `off/low/high`，**刻意不含 medium**）注册。

- **派生逻辑不复制第二套**：把 `chatModelRef` 内联的派生拆成
  `thinkingVariantSpec(provider, baseModelId, thinking)`（纯派生）+ `registerVariantSpec(spec)`（只补 map、
  不动 revision、不触发发布）；`chatModelRef` 调用点行为逐字不变，重建期复用同一对函数（任务书 §1）。
- **不动 `revision`**：重建本身会把 `variantSpecs` 带进单例，若预注册再 `revision += 1`，会让
  `builtRevision` 永远追不上，触发无限重建。
- **回滚**：`MODEL_VARIANT_PRESEEDED=false` 跳过预注册，回到懒注册形态（即本 bug），纯逃生门；
  env 读法与 `PROVIDERS_CONFIG` 等相邻开关一致（接口文档 §6）。
- **任务温度变体不预注册**：`taskModelRef(params)` 的参数来自 OpenAI 兼容端点请求体
  （openai-compat.ts:354-358 的 `temperature` / `max_tokens` / `response_format`），后缀
  `t…m…r<sha256 前 8 位>th1` 把 `response_format` 哈希掉了、无法从 id 反推参数重新派生——
  **非确定性规范形**。方案 §四登记为边界：首跑报一次错后由派发路径重派生自愈。

**兜底（resume 自愈，判定"不做"）：** 内核确有便宜的现成 API——`Conversation.agent(CTX)` 返回 resolved
`Agent`（`model?: ModelRef`），`configure({model}, CTX)` 可回写（harness/types.d.ts:674-676；
agent.ts:1099/1252/1270/1289 已在用）。按方案 §二/§四仍走"不做"，理由：

- 主修已覆盖聊天会话的全部实际形态（目录内模型的应注册变体全在重建期补齐）；
- 供应商被删/改名的旧会话回退，既有 `syncConversationModel` catch（agent.ts:1280-1290）已做且日志可见
  （方案 §四第二条描述的就是它）；
- 温度变体参数非确定、id 无法反推，兜底的"剥 `#` 后缀取基础模型与档位重派生"对它无效，
  按 §四第一条由派发路径重派生自愈；
- 在会话运行路径新增 `configure` 回写会触碰方案 §三"不改会话创建绑模型语义 / 不让全局切模型回写旧会话"
  的敏感区，相对其实际收益（只剩边缘边界）代价不成比例。

方案 §二允许不做、要求实现者写明走了哪条，故据实登记为已知边界（下 §五）。

## 三、明确不改的语义（方案 §三，一条都没动）

- **会话创建时绑模型维持现状**：旧会话修好后继续用它创建时的模型，不跟随全局运行时选择
  （"每个对话独立模型"的 UI 是登记过的刻意没有；全局切换只影响新会话）。
- 用户在会话里显式切模型走 `applyChatMode`，照旧只改当前会话。
- 不做"重启后全量回填所有会话"的写库动作（自愈只按需触发；本批未做兜底）。

## 五、已知边界（不修，方案 §四）

- 温度型变体参数非确定组合，重启后该专线会话首跑报错一次后由派发路径重派生自愈；
  真实多供应商环境的逐模型组合不做穷举测试（等真实使用暴露）。
- 供应商被删/改名后的旧会话回落到"当前运行时选择"可能不是用户当初那个模型——供应商目录变更的
  自然后果，回落动作在 `syncConversationModel` 日志可见。
- 主修按"生效支持域"预注册；历史会话若存了当前支持域外的档位（如曾显式声明又删掉的 medium），
  该变体不预注册。极边缘，不做穷举。
