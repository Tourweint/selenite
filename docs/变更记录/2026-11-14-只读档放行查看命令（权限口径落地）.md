# 只读档放行查看命令（权限口径落地 / 外观页气泡宽度滑杆自绘）

用户原话两句："只读应该是可以输入那些查看的命令，你这个真正的权限管理是不是没做呀"、"外观页这个气泡宽度打开气泡之后，这个条是黑的，不知道你咋弄的，改一下"。

前一句是对的，而且不是措辞问题：上一轮把三档改成「只读 / 在工作区内修改 / 完全访问」之后，**只读档连 `ls` 都跑不了**——`bash` / `powershell` 在 `WRITE_TOOLS` 里，只读档一刀全拦。那按名字叫"只读"，实际是"什么都干不了"。

## 改了什么、为什么

### 1. 为什么之前是假的

判定的顺序是 `readOnlyBlockReason()`（拦）→ 审批判定 → `isReadOnlyShellCommand`（降噪白名单）。旧白名单有一条铁律：**只能把 `ask` 降成 `allow`，永远碰不到 `block`**。所以只读档里 `bash` 在第一步就被拦死，白名单根本没机会看命令内容。

它这么设计是有原因的：旧词表是**降噪**口径，按"这条路大概没风险"筛的，不按"这条命令一定碰不到写操作"筛。`find` 就在里面，而 `find . -delete` 是删文件；`sort -o out.txt` 是写盘；`uniq in out` 的第二个位置参数就是输出文件；`rg --pre ./x` 直接指定一个程序去跑。这份词表拿来当"能不能放行"的边界，等于把删文件当成"查看"。

所以要么继续不做（假的），要么**另做一份更严的判定专门给权限档用**。选后者。

### 2. 新的判定 `isViewOnlyShellCommand`（`src/read-allowlist.ts`）

与降噪白名单同住一个文件，但是两套口径，谁都别混用。

| 维度 | 降噪 `isReadOnlyShellCommand` | 权限 `isViewOnlyShellCommand` |
|---|---|---|
| 参与哪个判定 | 只把 `ask` 降 `allow` | 参与 `block` 判定（两档放行的就是它） |
| 词表 | cat/head/tail/grep/rg/ls/dir/type/where/file/stat/wc/sort/uniq/find | cat/type/head/tail/ls/dir/grep/rg/find/wc/stat/file |
| 旗标 | 不看 | **看**：`find` 的 `-delete`/`-exec`/`-execdir`/`-ok`/`-okdir`/`-fprint`/`-fprint0`/`-fprintf`/`-fls`/`-files0-from`，`rg` 的 `--pre`/`--pre-glob`；`--pre=./x` 先按 `=` 归一化再比 |
| 命令首词 | 允许带路径（按 basename 认） | **只认裸名字**：`./cat`、`C:\tmp\ls.exe` 一律不算（防同名脚本冒充） |
| 不带路径的写法 | 只看 cwd 圈在根集合内（旧版没显式查 cwd） | `ls` / `rg hello` 这种看的就是 cwd → **cwd 必须在已登记根里** |
| 默认 | 关（`AGENT_READ_ALLOWLIST`） | 开（`AGENT_READ_VIEW_COMMANDS`） |

刻意剔掉的三条：`sort`（`-o` 写盘）、`uniq`（第二位置参数是输出文件）、`where`（PowerShell 里是 `Where-Object`，根本不是"查找文件"）。

其余规则与旧的共享：单条命令、去掉一层引号、出现管道 / 重定向 / 分隔符 / 变量 / 通配 / 反引号 / 子 shell / 换行一律不算，字面量路径经 `realTargetOf` 解析后必须落在任一根内，`~` 开头拒绝。

### 3. 接进两档，保证档位单调

`readOnlyBlockReason(name, context?)` 的第二参是 `{ args, workspaceRoots, cwd }`：

- `read-only` 档：`WRITE_TOOLS` 命中时**先试**查看判定，命中放行，否则照旧拦；
- `no-shell` 档：`bash`/`powershell` 命中时**先试**查看判定，命中放行，否则照旧拦。

两档都放同一批命令，不是手滑：只读 ⊂ 在工作区内修改 ⊂ 完全访问 这条单调性要求"更放开的档不能比更保守的档干得更少"。只读能 `ls`、中间档不能，那三档的次序就成了假的。

`context` 缺省时**不看查看命令**（保守照旧拦）：拿不到命令文本和根集合，就没有"它是只读的"这回事。三个调用点（`lifecycle-harness.ts` 的执行前闸门、批准后复判的 async / blocking 两条）都补上了上下文。

### 4. 文案跟着闸门走

闸门行为变了，副文不改就是骗人。

| 档 | 旧副文 | 新副文 |
|---|---|---|
| 只读 | 能看，不改文件，不跑命令 | 能看、能查（ls / cat / grep 这类查看命令），不改文件 |
| 在工作区内修改 | 只能改工作区和项目里的文件，命令不跑 | 文件只改工作区和项目里的；命令也只限查看 |
| 完全访问 | 能改文件、能跑命令 | 能改文件、能跑命令（设置页 tooltip 写"能跑任何命令"，抽屉里位置窄，用短句） |

服务端两条 block 文案同步（`policy.ts`）：只读档改成"只放行 ls / cat / grep 这类查看命令"，中间档改成"命令只放行查看"。全屏设置页 `settings-router.js` 的权限行 tooltip、抽屉 `settings-permission.js` 的三条 `cs-opt-sub` 全改。

### 5. 外观页气泡宽度：黑条是引擎原生轨道

滑杆原来只写了 `accent-color: var(--accent)`，轨道交给引擎自己画。开关一开（`disabled` 撤掉、不再吃 `.45` 透明度），轨道就露出引擎自带的深色底——亮色主题下是一条黑杠，暗色主题下又和卡片底几乎同色。

改成自绘：`-webkit-appearance:none` + `::-webkit-slider-runnable-track`（4px、圆角）+ 13px 圆点滑块，Firefox 两个伪元素同步写一份。

**轨道分两截**（用户第二遍明确要的：已填的那截要有颜色，没选中的那截不能是黑的）：`--bubble-p` 由 `bubble-mode.js` 的 `syncFill()` 按当前值算出（`(value-min)/(max-min)`），写成行内自定义属性；轨道的背景是
`linear-gradient(to right, var(--accent) 0 var(--bubble-p), var(--outline) var(--bubble-p) 100%)`——左边已填一截是强调色，右边未填一截是中性轨道色。伪元素能继承宿主元素上的自定义属性，所以不需要额外 DOM。

`syncFill()` 在挂载时先调一次（首屏就是对的），拖动/点击（`input`）时再调；`:disabled` 仍走整条 `.45` 透明度。

## 这条会怎么错

- **"查看"的边界靠词表划，词表一定漏。** 比如 `cat --help` 之类无路径的写法会落到 cwd 检查上（cwd 在根里才放）；`find` 的新式旗标（将来 GNU 加新的写操作）不会自动进黑名单。方向是对的：不确定就不放。真出现漏，往 `DANGEROUS_FLAGS` 加，别放宽词表。
- **PowerShell 的别名语义仍然混在同一个词表里。** `cat`/`type`/`ls`/`dir` 在 PowerShell 里是 `Get-Content`/`Get-ChildItem`，安全；但 `head`/`tail` 在 PowerShell 里没有别名、`find`/`stat`/`wc` 靠外部程序——命令跑不起来是"可用性问题"，不是"放行错误"。要精确到平台就得按 `toolName` 分两套词表，本轮没做。
- **`AGENT_READ_VIEW_COMMANDS` 默认开，是一处行为放宽。** 它默认开是因为"只读档不能 `ls`"本身就是 bug；但严格讲这是把 `block` 变 `allow` 的第一次。以后再加"只读放行 X"，都应走同一套流程：新判定 + 参与 block 的测试 + env 回滚。
- **两档共用一批命令，是刻意的。** 将来若有人给中间档单独开"在工作区里跑构建命令"，必须同时保证只读档不因此变窄，否则档位次序又会断。
- **滑杆的填充比例是 JS 算出来的。** `--bubble-p` 只在挂载与 `input` 时更新；如果以后有别的代码改 `range.value`（比如程序化恢复状态），必须同时调 `syncFill()`，否则填充会停在旧位置。另外不要把 `accent-color` 加回轨道——那就是黑条复发。
