## 改了什么

1. **`web_search` 结果去重 + 封顶**（`tools.ts`）：正常命中改回 `{ count, hits }`，删掉
   与 `hits` 逐条重复的 `message`；0 命中仍回 `{ count: 0, message: "没有找到相关结果。" }`。
   新增 `WEB_SEARCH_MAX_RESULT_CHARS = 32_000` 与纯函数 `shapeWebSearchHits()`：按 `hits`
   序列化后的字符数从排名最后开始丢，至少保留 1 条；`count` 取裁剪后的条数。
   工具 name / description / 参数 / 注册顺序与搜索适配层均未改动。
2. **历史 thinking 不回放**（新增 `agent/reasoning-replay.ts` + `agent/lifecycle-harness.ts`）：
   `beforeRequest` 默认剥离 assistant 的 `type:"thinking"` block 与多余的 `reasoning_content`
   字段，再拿剥离后的视图做 `lastUser` 判断与尾部注入拼接。只影响这一次请求；durable
   entry 不动，UI 的步骤展示与刷新还原不受影响。`CHAT_REPLAY_THINKING=true` 回到旧形态。
3. **设置页显示「当前生效」**（`web/settings-compaction.js`）：把当前生效的触发点写进
   `% 窗口` / `K token` 两个单位后缀的 `data-tip`（悬停小黑框；隐藏档也写，切档后可直接悬停），
   **主界面不新增可见文字**，也没有样式文件改动。进页时取一次 `GET /api/v1/agent/model` 的
   当前默认模型 `contextWindow`（失败 / faux / 找不到按「窗口未知」静默处理，不阻塞页面），
   再按开关 / 档位 / 两个输入框的活值算出五类文案：已关、按 token 已设、按 token 未设、
   按百分比（窗口已知）、按百分比（窗口未知）；另一档用「未生效」标注。
   数字用十进制 K/M（1M、250K）；token 档直接显示用户填的 `300K`（不显示 307K）。
   输入框 `input`、档位点击即时重算（不保存）；开关回填与保存失败回滚后也刷新。
4. 测试：新增 `web-search.test.ts`、`agent/reasoning-replay.test.ts`；两个新文件已加入
   server 的 `test` 脚本清单。前端静态 JS 用 `node --check` 验证。

## 为什么

同一会话 58 次请求、最后 prompt 213,804 token：`web_search` 结果占 37%（其中 `message`
把 66 条命中又抄一遍 = 10.9 万字符），被回放的 thinking 占 14%（约 29k token，每轮重发）。
两处都是纯浪费，不涉及契约语义：`web_search` 的模型可见内容仍是同一批同构字段；
thinking 剥离后适配层会为需要的供应商补空 `reasoning_content`，工具调用不受影响。

另：用户实际用的是 `tokens` 档 300K（307,200），213K 没触发是因为没到 307,200——而设置页
把两档并排摆着，看不出哪档生效、换算成多少 token。故把「当前生效」写进单位后缀的悬停提示，
把死值说明白。

**缓存前缀变化**：
- `web_search` 只改工具返回、不改工具声明，工具面与 system 前缀都不变，**前缀确实不变**。
- thinking 剥离改的是请求里 assistant 消息的字节，因此会带来**一次性的前缀重算**：升级 / 重启后
  第一条含历史 assistant 的请求必然整段缓存 miss，之后每轮都按剥离后的稳定形态发送，恢复命中。
  durable / system / tools 均不变，UI 步骤展示也不变；miss 是这次重算的已知代价。

工具描述 / 注册顺序未动。设置页显示只读 `GET /api/v1/agent/model`，不改任何请求 / 响应契约。
