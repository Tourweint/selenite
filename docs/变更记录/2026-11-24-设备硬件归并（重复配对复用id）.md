# 2026-11-24 设备硬件归并：重复配对复用原 deviceId（C-10）

> 批次 C 第 5 组。仓库：`harness`（基线 `f28edb0`）。跨仓契约（手机 `lifediary` 同批改请求体）。
> 方案：`docs/设计方案/2026-11-24-设备稳定标识与重复配对去重.md`（2026-11-24 用户四项全按默认拍板）。
> 本文件记**落地**；契约口径已下沉到 `接口文档.md` §6 / 分册8 §5 / 分册5「中继与群组」、`系统架构.md` 配对段。

## 1. 背景

同一台手机反复扫码配对 / 重新加入中继时，服务端每次 `randomBytes(8)` 新建一条记录：
桌面「已连接的设备」与手机设备页都会堆出多条同名记录。C-9 只在**显示层**合并（按 id / 唯一名），
服务端记录仍并行占名额（设备上限淘汰还可能把真正的新设备挤出去）。

## 2. 决策（沿用已拍板方案，未改口径）

| # | 决策 |
|---|---|
| D1 | 客户端算 `hardwareId = sha256(ANDROID_ID + "\|" + 包名)`；服务端只存**二次** `sha256`（`hardwareHash`）。明文不落盘、不进日志、不进任何响应/投影 |
| D2 | 同 `hardwareHash` 的**未撤销**记录 → 复用原 id：覆盖 `tokenHash`、刷新 `name`/`lastSeenAt`、重算 `fingerprint`（relay：刷新 `platform`/`capabilities`/`lastSeenAt`） |
| D3 | **已撤销**记录不复活：撤销后重配走新建 |
| D4 | 复用时清 `keyChangedAt`（重配对 = 主人持码重新认领） |
| D5 | 两份库（配对库 / 中继库）各自内部去重，**不合并存储**；显示层合并仍是 C-9 的事 |
| D6 | 回滚开关 `DEVICE_HARDWARE_MERGE`（harness 与 relay **各自**读自己的 env），默认开；`false`/`0`/`off` = 完全忽略请求里的 `hardwareId`，逐字回到改动前 |
| D7 | `hardwareHash` 是**内部归并键**，不是鉴权依据；鉴权仍只认 deviceToken（失败 403 空体） |

## 4. 行为矩阵（现行）

| hardwareId | 同 hash 未撤销记录 | 动作 | 返回 |
|---|---|---|---|
| 有 | 存在 | 复用 id、换 token、重算指纹、清 keyChangedAt、刷新名字/时间 | 新 `deviceToken` + **同一个** `deviceId` |
| 有 | 不存在 | 新建 | 新 id + 新 token |
| 有 | 只命中已撤销 | 新建（D3） | 新 id + 新 token |
| 无 / 形状不对 | — | 逐字旧行为（每次新建） | 新 id + 新 token |
| `DEVICE_HARDWARE_MERGE=false` | — | 逐字旧行为 | 新 id + 新 token |

旧令牌失效不需要额外撤销：`tokenHash` 被覆盖后 `verifyDeviceToken` 不再命中 → 403 空体。

## 6. 回滚

- 一行 env：`DEVICE_HARDWARE_MERGE=false`（harness 与 relay 各自进程），请求里的 `hardwareId` 被完全忽略，行为逐字回改前。
- 代码级回滚：删 `hardwareHashForRequest` 调用与 `issueDevice` / `createDevice` 的复用分支即可；
  `hardwareHash` 字段留在已落盘记录里无消费者（不参与投影），不需要迁移。

## 7. 已知边界（刻意不做）

- 不追求跨 App 重装稳定（重装后 ANDROID_ID 可能变 → 视为新设备）。
- 不合并两份存储（D5）；不改设备上限淘汰策略；不改对外投影格式。
- 不把 `hardwareHash` 当凭据；`unpaired` / `unclaimed` 的认领逻辑不变。
