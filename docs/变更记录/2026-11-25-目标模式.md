# 2026-11-25 目标模式（方案 B，默认关）

**一句话**：目标原来只是执事档案上的一行文本；现在它带一个四态状态机、每轮收尾的确定性结算、
durable 续跑任务、暂停 / 继续 / 清除。`GOAL_MODE` 默认关，关着时行为与改动前一致。

## 为什么这么做

- **不设裁判轮、不翻 D13**：完成由执行方自报（末行标记），宿主只管确定性硬闸——轮数上限、token 预算、
  零工具连击。验收层 2026-11-19 已删，这里不借目标模式把它加回来。
- **只数续跑轮的零工具**：主人亲手发的那一轮可能只是问一句"你觉得这目标怎么拆"，不该因此暂停。
- **新建默认 `paused / not_started`**：设个目标不等于让它现在就跑，由人点「开始推进」。
- **暂停后的恢复全靠显式动作**：`stopped` / `blocked` / `no_progress` 都不会自己回到 `active`。
- **状态表与目标正文分开放**：正文仍在 `partners.current_goal`，注入逻辑一行没动；开关关掉只是不结算，
  目标还是原来那一行文本。
- **续跑提示词只追加在那一轮尾部**：不进固定前缀，非目标轮的缓存前缀一字不变。

## 踩的坑（都是探针查出来的）

1. **续跑任务排上了但不醒。** 单测 28/28、typecheck 全过，第一遍探针却在"等续跑"上超时。
   起初以为是会话之外建的任务要再踢一下调度（试过 `conversation.waitForIdle()`），没用。
   真正的原因：Harness 打开时传的是一张**显式的任务定义表**（`lifecycle-harness.ts` 的 `tasks`），
   `GoalContinueTask` 不在表里，建得出来但"缺定义"。补进表之后，不踢调度也能醒；那段试出来的代码已撤掉。
2. **动作端点的成功响应回了内部行**：带 `partnerId` 与 `updatedAt`（后者兼作续跑 token），与文档写的六字段不符。
   改为过 `goalView`。
3. **探针自己的两处预期写错**：以为 `/run` 是第一轮（其实 `start` 会立刻排一轮续跑，到 `/run` 时已到上限）、
   以为 `resume` 后立刻 `pause` 轮数会 +1。产品行为与 `接口-端点4` 的动作表一致，改的是探针。

## 返工（同日）：三处失败路径的兜底

主人审代码指出两处，落地时按同一类缺口多修了一处。都不改开关关着时的行为，也不改状态机与结算顺序。

| # | 缺口 | 修法 |
|---|---|---|
| 1 | `settleGoalTurn` 结算抛异常（库锁、临时异常）时 `catch` 里返回 `false`，调用方当成"目标模式没开"——**不剔 `[[goal-done]]` / `[[goal-blocked:…]]`、不带工具数与用量**，标记原样显示在聊天里 | `catch` 改返回 `true`（开关那道门已经过了）；函数头注释写明"返回值只回答目标模式是否开着，不表示结算成功"；日志 `[goal] 结算失败（本轮不记账、不排续跑；partner=…）` |
| 2 | `GoalContinueTask.deliver` 里 `void runGoalContinuation(...)` 没人接，`runPartnerTurn` 一旦 reject 就是未处理的 Promise rejection | 加 `.catch`，日志 `[goal] 续跑轮异常（已吞，不影响进程；partner=…）` |
| 3 | **（主人没列，核实可达后一并修）** `applyGoalAction` 里 `void scheduleGoalContinuation(...)` 同样没人接。它内部的 `ensurePartnerSession` 直接透传 `openPartnerSession`（开会话 / configure / 钉工作目录都可能抛，没有 try/catch）——点「开始推进 / 继续 / 重新打开」时这一步抛了就是同一种 reject | 在源头修：`scheduleGoalContinuation` 用 try/catch 包住取会话，抛了打 `[goal] 执事会话打不开，续跑没排上（partner=…）` 并返回 `false`；注释加"保证不 reject" |

另外把 `settleGoalTurn` 的开关判定（`goalModeEnabled()`）也挪进了 `try`：它原本在 `try` 之外，万一抛了会从 `finish` 一路抛出去，
把已经跑完的那一轮变成失败。这也是超出原话的小改，目的是让这个 sink 真正做到不抛。

三条日志都只带 partner id 前 8 位与错误消息前 120 字，不带对话内容。

**新增回归单测** `src/goal-mode.test.ts`（3 条，已进 `package.json` 的 `test` 清单）。库和家目录指向 mkdtemp 临时目录，
造异常的办法是把库关掉（之后任何查询都抛 `database is not open`）：

- 开关关 → `settleGoalTurn` 返回 `false`；
- 开关开且库已关 → `settleGoalTurn` 返回 `true`、自己不抛；
- `scheduleGoalContinuation` 取会话失败 → 返回 `false`、不 reject。

探针逐项覆盖（真起服务 + 真 HTTP + faux 模型）：

- `GOAL_MODE=false`：详情与 PATCH 不带 `goal`、动作端点 404；
- 动作端点：没目标文本 / 不认识的 action / `maxRounds=0` / `tokenBudget=1` / 没在推进时 pause / 没完成时 reopen → 400；
  执事不存在 → 404；没带 token → 403 空体；一串 400 之后状态一行没动；列表投影不带 `goal`；
- 续跑：`start` 后 durable 任务真醒真跑，连续 3 轮零工具 → `paused / no_progress`（3/4 轮，没到轮数上限）；
  暂停后等 6 秒轮数不变；
- 用户亲手的那一轮：目标没在推进时不记账；推进中记轮数、**不记连击**（第 4→5 轮连击停在 1，第 6、7 轮才到 2、3）；
- 上限：跑满 → `budget_limited(rounds)`；不抬上限 / 抬到同一个数 / token 预算低于已用 → 400；
- `pause` 后在路上的续跑作废（等 5 秒仍是 `paused`、轮数不变）；`clear` 同事务清正文与状态行。

## 没验证的

- **真模型三条走查没跑，需真机验**：① 首轮零工具不暂停、续跑轮零工具 3 次暂停；② 写 `[[goal-done]]` 即 `done`、
  reopen 后能续；③ 跑满进 `budget_limited`、resume 后再跑。faux 不调工具、不写末行标记，
  所以"真实工具调用让连击清零""标记在真实回复里稳定落在最后一行"只有纯函数单测，没有端到端证据。
- **Stop → `paused / stopped` 与首页主对话的轮末结算**没在真服务上走过（探针只走 `/partners/:id/run` 与动作端点）。
- **总管的续跑轮跑在 `partner-chief`** 是按 `chatKindOf` 推断出的形态，没实测。
- **`GOAL_MODE=false` 下真发一轮普通消息、看提示词尾部没有目标段**：没做真模型手验（开关关时不会排续跑，
  目标段也就无从追加；探针只验了 HTTP 形状）。
- **前端两处弹层没有在浏览器里点过**：只过了语法检查与命名导出护栏。
- **返工的三处兜底见上面"返工"一节末尾**。
- **例行任务在运行期新建后是否也依赖后续 submit 才启动调度**：这次没查、没动（不在范围内）。

## 回滚

`GOAL_MODE=false`（默认值）：不结算、不排续跑、动作端点 404、详情与 PATCH 不带 `goal`、界面不出状态行。
`partner_goals` 表与已写的数据保留不清；要彻底移除需删表（没做迁移脚本，开关关着时它只是一张空转的表）。

## 没做（方案 §8「明确不做」）

裁判轮、多目标并存与目标历史页、目标跨副会话推进、空闲时常驻检查、把派活 / 进度 / 结果记到目标下面、
手机端目标状态界面、按目标选模型或配权限档、重启后自动恢复续跑、改例行任务与工人续行的任何口径。
shared 与手机端一行没动。
