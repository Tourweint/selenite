# P2：LLM 透传代理迁入

> 日期：2026-10-27。范围：`llm` 包三个类 + 配置/过滤器小改；契约与 backend §3 逐字一致。
> 依据：拆分方案 D1/D3/D7、backend 接口文档 §3（契约总源）、backend LlmProxyController（对照基线）。
> 依赖 P1（同仓库 2026-10-25：JWT 过滤器、AiConfigPuller、频控）。

## 背景

P1 打通了部署面后，P2 把最重的依赖方——LLM 透传代理——迁进 harness，连带 D1 的扣额联动
（"先扣再转发"铁律的 harness 侧执行）。backend 侧端点进入废弃期（不删除，下线条件 =
最低支持 App 版本已认识 `aiBaseUrl`）。

## 决策

1. **扣额联动（D1）**：`InternalQuotaClient` 调 backend `POST /internal/quota/consume`
   （requestId=每请求一个 UUID，幂等在 backend 侧），连接 200ms / 读 1s；**任何拿不到成功结果
   的情形都拒绝本次调用**（fail-closed）：429 → 原样透传 4029+文案（额度文案只此一份，由 backend
   生成）；401 → 4010（App 按"登录已过期"处理，D2 注销兜底）；其余/异常 → 503+5001。
2. **SSE 透传逐行对照迁移**：状态码/Content-Type 透传、逐块回写 + flush、`Cache-Control: no-store`、
   路径别名 `/chat/completions`、`ModelOverride`（LLM_MODEL 非空覆盖请求体 model）——与 backend
   行为逐字节一致，App 零改动切换。
3. **闸门口径**：LLM 端点不再叠 IP 频控——鉴权挡匿名滥用、每用户每日额度挡刷量（扣额是前置闸门）；
   signal 端点无额度概念，才需要 IP 闸。两端口径分别写进 harness 接口文档 §0.1/§2。
4. **密钥只走环境变量**：`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` 加入 HarnessProperties
   （key 绝不入库、绝不进 ai-config 下发——沿 P1 口径）。
5. **userId 传递**：JwtAuthFilter 校验通过后把 userId 放入请求属性（`harness.userId`），
   扣额调用从那里取——不引 Spring Security，保持 P1 的纯过滤器形态。

## 已知环境问题（如实登记，2026-10-27 夜）

**本机 loopback TCP 被 v2rayN/Xray 劫持**：所有走真实本地 socket 的测试（MockWebServer 系，
10 例）在 v2rayN 开启 TUN/增强模式期间无法连接——`ConnectException`（约 1s，OS 层 .NET 监听+
连接同样超时，判决非本仓库代码问题）。同一批测试在 v2rayN 关闭时全绿（2026-10-25 P1 验证 18/18；
P2 代码在环境恢复后需复跑确认）。**跑测试前退出 v2rayN（或关 TUN 模式）即可**。

## 验证

- 纯逻辑测试（非 socket）：5+3 例全绿；
- socket 系测试：逻辑已按 MockWebServer 断言写就（透传/4029/4010/fail-closed/别名/模型覆盖），
  2026-10-25 环境正常时同构测试全绿；**环境恢复后 `mvn test` 复跑为上线前必做项**；
- 真机双端对比（同一入参打 backend 与 harness 的 LLM 端点）列入上线清单。

## 回滚

App 端把 `aiBaseUrl` 置空即回到 backend 全包；harness 停掉即可。backend 侧端点未动。
