# 上下文容量卡（学 ZCode · 按字符分摊构成 · 分段进度条）

> 2026-11-14。用户口径：对话输入框旁的上下文标签不要只显示一个环，要像 ZCode 一样
> 能看见「已用 / 总量 + 占比」「进度条」「什么样的消息占了多少」。
> 一句话：`/context` 多返回一份按上下文实文统计的 `breakdown`，环点开是一张 320px 的容量卡。

## 结论

- **接口只增字段**。`GET /api/v1/agent/chat/:conversationId/context` 在原有 `used` / `window` 上
  增加 `breakdown: [{ source, chars }]`；旧客户端忽略新字段，带 `aroundIndex` 的旧定点找回分支不变。
- **构成按字符算，不按 token 凑**。`used` 是上一轮 assistant 的 `usage.input`（token），
  构成条回答的是「这一窗里什么在占地方」，和 ZCode 一样用 `chars` 分摊；两类数字不混算。
  实测同一会话 `used=14,463 tokens`、`breakdown` 合计 56,343 字符，量级关系合理。
- **卡片贴着环弹**。320px 宽、圆角 14、`position: fixed`；默认在环上方，放不下翻到下方，
  左右夹在视口内。鼠标移入卡片不关，移出 140ms 关；点击钉住，点外面 / Esc 关。
- **不做缓存命中率与压缩按钮**。ZCode 那两项分别要缓存统计和 `/compact` 动作，本轮数据源
  没有，先不摆假按钮；只做占比、构成、进度条三件。

## 卡片结构

1. 标题「上下文容量」，右侧等宽数字 `已用 / 总量（百分比）`。
2. 8px 高分段进度条：外层轨是 `--surface-low`，内层按 `pct` 填宽，再按 breakdown 比例切段。
3. 构成 legend：色块 + 标签 + 右对齐百分比；百分比用最大余数法补齐到 100%（避免 6 段各四舍五入后合计 101%），非零但不足 1% 的显示「＜1%」。空构成时整块隐藏。

## 这条会怎么错

- **低占比时进度条很短**。3% 只有 8.7px，分段几乎看不出；构成信息靠 legend，不靠条。
  没有给低占比做最小可视宽度，避免 6 段时互相挤爆。
- **字符与 token 不同单位**。legend 百分比是「字符构成占比」，不是「token 构成占比」；
  两者只在同一窗内做比例，不能拿 94% 去乘 `used` 算 token。
- **没有缓存与压缩**。ZCode 的「平均缓存命中率（低于 78% 不显示）」和 `/compact` 按钮
  需要额外数据与动作，本轮没有；以后补时不要塞进 `breakdown` 字段，另开字段。
- **构成分类比 ZCode 少**。「其他 / 系统工具 / MCP 工具」没有单列；当前数据源只能稳定
  分出上面六类，硬拆会给出假精度。
