- **日期**：2026-10-29
- **类型**：新增端点 + 新增独立存储（不动 `pi-durable` 的表、不动通道分流）
- **状态**：已实施；`typecheck` 与端到端探针全绿
- **需求来源**：App 仓库 `docs/设计方案/2026-10-29-对话正文归位Harness（手机只留索引）.md` §7.1 / 「阶段 0」
- **契约文档**：`docs/基线文档/接口文档.md` §2.6、§6

## 1. 背景

需求方 2026-10-29：**"最后这个 harness 里也能保留成文的日记"**——两个来源：①自己在日记本里写的一大段；
②每天对话之后的总结。后期要靠这些成文做记忆巩固 / 长期分析 / 周报素材聚合。

同时手机丢了就全丢，所以同步必须**双向**（下行 = 换机恢复）。

## 2. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **手机权威，这里只做镜像**：唯一写入路径是 `POST /api/v1/diary/sync` | 不变量 I1/I2 的权威在手机；提供写入口等于造第二份真相 |
| D2 | 独立库 `.data/diary.sqlite`（`DIARY_DB_PATH`） | 不混进 pi-durable 的表（内核升级会痛），与配对存储同一取舍 |
| D3 | 一次请求完成上行 + 下行 | 两趟之间多一次失败机会，而客户端失败是静默的（用户无从得知） |
| D4 | `deleted` 软标记、软删保留正文 | 后期要分析"写过又删了" |
| D5 | 上行比镜像旧时**把胜出行塞回响应** | 否则客户端会一直拿着旧版本、每轮都被拒，两边各留一份 |
| D6 | 只加一个只读自检 `GET /api/v1/diary/status`（不含正文） | 验收/排障需要它；正文不外泄，避免被当接口读全文 |
| D7 | 不实现成 pi-durable 的 tool（不注册 `remember_diary` 之类） | 本次范围只有"镜像"，任何"让 Agent 改日记"的口子都超出需求 |

## 6. 真机联调暴露的问题与修复（2026-10-30 补记）

**症状**：手机删掉一条日记后，镜像里这条变成 `deleted=true / chars=0 / entryDate=null` —— 正文和日期都被抹掉了。

**原因**：手机发的墓碑是"**只带 id + 删除时刻**"的最小形状（`finalText`/`rawSnapshot`/`entryDate` 都是空）。
服务端合并时先按 `updatedAt` 判定"手机赢"，然后走了 `overwrite()` 整体覆盖 → 空值把已有正文写没了。
`deleted=true` 走"只置标记"的那条分支只在 `updatedAt` **相等**时才命中，所以原来的探针（发的是"带正文的墓碑"）看不出问题。

**修复**：`deleted=true` 一律走 `markDeleted()`（只置 `deleted` + `updated_at` + `mirrored_at`，其余字段一律不动），
不管 `updatedAt` 是新是旧；探针用例 4 改成发**最小形状的墓碑**，并额外断言 `entryDate` 没被抹掉。

**教训**：契约里写"软删保留正文"还不够 —— **探针必须照客户端的真实请求形状发**，否则测的是自己想象出来的报文。
