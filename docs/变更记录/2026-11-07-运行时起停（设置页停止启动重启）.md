# 2026-11-07 运行时起停：设置页里的「停止 / 启动 / 重启」

## 为什么

`2026-11-07` 那次 500 排查暴露了一件事：**服务挂了，用户手里没有任何工具**。
当时唯一的办法是开任务管理器按 PID 杀进程，再从壳里等它自己拉——而且还得先知道
`tsx` 会 fork 子进程、只杀父进程会留孤儿占着端口。

顺着这个需求，用户的原话是「拿这个 GO 写一下……把这个运行时给关掉，就是 Node，
然后重新连接这一块，做到设置里头」。

## 为什么这件事必须写在 Go 里

不是"顺手用壳的能力"，是**页面做不到**：

1. 页面要停的就是它自己的后端。点下去之后所有 `fetch` 都失败，连"现在是什么状态"
   都问不出来——它没法给自己画一个"已停止"的界面。
2. 只有壳知道三件事：服务从哪个目录起（`serverDir()`）、PID 是多少、这次是不是
   用户主动停的。

所以分工照旧，和 `Shell.SelectDirectory` 同一条边界：**壳管进程，业务全走 HTTP**。

## 改了什么

### `desktop/runtime.go`（新增）

`runtimeCtl` 是唯一的进程状态持有者：

| 方法 | 语义 |
|---|---|
| `Status()` | 现探，不读缓存。四态：`running / starting / stopped / failed` |
| `Start()` | 已在跑则幂等返回；否则起进程并等 `/healthz`（最多 25s） |
| `Stop()` | 立闩 → `taskkill /T /F` → 等端口腾空（最多 8s） |
| `Restart()` | 先停再起 |
| `Ensure()` | 给自动路径用：**认闩**，用户停过就不动 |

三个决定写在这里，因为都不是显然的：

- **`pidOnPort()` 以端口为准，不以记忆为准。** PID 会被系统回收，我们自己记的那个数
  可能早就变成别的进程；端口上那个才是现在真在服务的。所以 Status/Stop 都先查端口，
  查不到才回落到 `r.pid`。
- **`taskkill` 必须带 `/T`。** `tsx` 是 loader，它会再 fork 真正的服务进程。只杀父进程
  会留下孤儿占着 39847，用户下次点"启动"直接 `EADDRINUSE`。
- **`stopped` 闩是这次改动最容易漏的一处。** `watchService` 每 10s 探一次、连续 3 次
  失败就自动重拉。没有这个闩，用户点完"停止"半分钟后服务自己回来，按钮就成了摆设。

### `desktop/main.go`

- `ensureService()` 退役。它不是"想重构"：它只会拉起、不会记住、也不会停，没有
  承载"这次是用户让我别拉"的地方。逻辑并进 `runtimeCtl`。
- `loadService` 与 `watchService` 都改走 `runtime.Ensure()`，守护分支多了
  `if runtime.UserStopped() { failures = 0; continue }`。
- **托盘「重新连接」改走 `runtime.Start()`**：这是**人的明确要求**，要能越过闩，
  否则停完服务后托盘就再也救不回来。区分"人点的"和"系统自己撞见的"，是这次改动的
  分界线——自动路径认闩，人工路径不认。
- `main()` 里 `runtime.base = baseURL()`：起停与端口解析都以它为准。
- `Shell` 新增四个方法：`RuntimeStatus / StopRuntime / StartRuntime / RestartRuntime`。
  返回 `(RuntimeStatus, error)`，MyGo 把 error 映射成前端 reject，所以"没停成"能和
  "停成了"区分开。

### `web/app.js` + `style.css`

设置 → **服务** 分区新增「运行时」一节（不另开分区）：

- 状态行 + 三个互斥按钮：跑着显示「重启 / 停止」，没跑显示「启动」。
- 走 `window.mygo.call`，**浏览器里没有这个对象**，退化成「仅桌面端可操作」，不出按钮。
- 停服后盖一块遮罩（`.runtime-curtain-card`）：服务没了，页面右上角所有轮询都会失败，
  先把话说清再给一颗能点的「启动服务」。同时 `body.dataset.runtime = "stopped"`，
  让 `checkHealth` 短路——**否则每 8 秒把状态灯刷成"服务离线"，那是我们自己的操作，
  不是故障**。
- 启动成功后 `location.reload()`：SSE、健康轮询、会话列表一起重建，比逐块热修可靠。

## 验证

单测（`desktop/runtime_test.go`，不碰真进程）：

```
go test -run "TestServicePort|TestStopped|TestStopIsIdempotent|TestStatusSeparates|TestPidOnPort" .
```

覆盖：端口解析（含没写端口/非法 URL 的回落）、无监听时 `pidOnPort` 返回 0（不误杀）、
**停过之后 `Ensure` 不再拉起**、`Stop` 幂等、`stopped` 与 `failed` 两态不混。

真停真起（`desktop/verify_runtime_test.go`，默认 skip）：

```
LIFEDIARY_E2E_RUNTIME=1 LIFEDIARY_SERVER_DIR=<abs>/ts/apps/server \
  go test -count=1 -run TestRuntimeStopStartE2E -v .
```

实测输出：`PID 53020 → 停止 → 端口释放 → Ensure 未重拉 → 启动 → PID 47768 → /agent/chats 200`。

界面（Playwright 注入假壳，验的是真 `app.js` + 真 DOM）：
运行中显示 `运行中 · PID 49120` + 重启/停止；点停止后状态翻为「已停止」、启动按钮出现、
遮罩升起、`body.runtime=stopped`；浏览器直开则显示「仅桌面端可操作」。控制台无报错。

`go build` / `go vet` 干净。

## 发现但没改的

- **`loadService` 在闩生效时会卡 3 秒**：`runtime.Ensure()` 什么都不做，然后
  `waitHealthy(base, probeTimeout)` 等默认探活超时，最后加载离线页。功能正确（页面会
  告诉你连不上），只是慢。要改得让 `Ensure` 回报"我没打算拉"，属于壳与页面的时序细节，
  不在这次范围。
- **离线页文案仍写着「pnpm dev 然后点重新连接」**：对开发者是对的，对只用界面的用户
  已经过时（现在设置页能起）。改它要重画那一页的排版，留作下一批。

## 回滚

- `LIFEDIARY_SHELL_BINDINGS=off`：整组 `Shell` 不挂，前端退化成「仅桌面端可操作」，
  与改动前"浏览器里的表现"一致；
- 进程行为回退：把 `loadService`/`watchService` 里的 `runtime.Ensure()` 换回直接起进程
  即可，`runtimeCtl` 不参与自动路径。
