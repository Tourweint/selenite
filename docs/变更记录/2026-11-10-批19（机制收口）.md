影响面：`ts/apps/server/src/{delegation,delegation-api,delegation-authority,verified-answer,world-state,approvals,approval-api,tools,relay-matrix}.ts`、

## 一、总管 clarify 契约（§一）

- `delegation.ts` 新增固定字节常量 `CLARIFY_CONTRACT` + `clarifyContractEnabled()` / `clarifyContractFor()`。
  大活开工前用 `ask_user` 确认三件事（对象 / 期望 / 验收）、一次一问、小活不问。
- 注入点：`agent/lifecycle.ts` 的 section `clarify_contract`，紧跟 persona / 验证铁律之后。
  **只给总管与主对话**；普通执事（走 partner-context 的 `ATTENTION_ONE_QUESTION`）与 worker 不注入。
- 开关 `AGENT_CLARIFY_CONTRACT`（默认开）；关掉 → 整段不出现，逐字节回到改动前。

## 二、VerifiedAnswer：提问答案沉淀（§二）

- 新模块 `verified-answer.ts`：`ask_user` 答复成功后（`POST /approvals/:callId/answer` 且
  `wasPending && status==="answered"`）写一条 `kind=fact`、`source="verified_answer"`、
  `veracity="stated"` 的记忆，scope 用 `scopeOf(发起会话)`，正文固定 `问：…\n答：…`。
- **群会话不落**（与记忆引擎的群策略一致）；写失败只 warn（不含正文），不挡答复与续跑。
- 开关 `AGENT_VERIFIED_ANSWER`（默认开）。幂等重发不重复写（只在 pending→answered 那一次触发）。

## 三、执事「产物交接」（§三）

- `agent/partner-context.ts` 新增 `ARTIFACT_HANDOFF` + `artifactHandoffEnabled()`；注入
  `buildPartnerDisciplineSection`（总管与普通执事共用）：产物必须落盘、交接点名路径、
  下一棒从产物开始而不是从转述开始。
- 开关 `PARTNER_ARTIFACT_HANDOFF`（默认开）。会改变执事纪律段的固定字节（预期内）。

## 四、任务中心过程关口（§四）

- `delegation-api.ts` 新增纯函数 `buildTicketGates()`：`reviews[]` → 每条 `验收：<slug>`；
  `DELEGATION_JUDGE` 打开且有 `judge.json` → 一条 `裁判`（取最后一轮）；`repairRound > 0` → 一条 `返工`。
  **只投影落盘事实，不新增判定**；`judge.json` 在宿主侧只读（`store.ticketDir(id)`），chancellor 零改动。
- 详情顶层可选字段 `gates: [{name, passed, note?}]`；`TICKET_GATES=false`（默认开）时不出现该键。
- 前端：阶段条下方 `.td-gates` 小徽章（✓/✕ + 悬浮 note），没有 gates 不渲染。

## 五、多副本对齐（§五）

- 列表与详情返回可选 `groupId`：取 `ticket.idempotencyKey`（= requestId）；没有 requestId → 列表 `null`、
  详情不带键。`DELEGATION_FANOUT_GROUP=false`（默认开）时一律不返回。
- 前端 `fanoutLayout()`：同一 `groupId` 的 ≥2 张单折叠成「N 个副本，已完成 M」，点开展开逐张；
  单张仍按普通行渲染，老服务端不带字段时零变化。
- **只归并展示**：不做自动等待 / 自动消费（明确不在本批）。

## 六、授权依据 + 恢复前重验（§六）

- 新模块 `delegation-authority.ts`：
  - `currentAuthority()` 给受理回执写 `{level, at}`（`delegation_receipts.authority` 早就有列）；
    写点：`tools.ts` 的 delegate 受理、`delegation-api.ts` 的重试、`relay-matrix.ts` 的远程单受理。
  - `recheckAuthority()` 纯函数：现在更严 → `stricter` + warning；更松 / 相同 → 直接跑；
    任一边读不到 / 认不出 → `unknown`，**按更严处理**。
- 续跑点：`startDelegation`（所有 resume 都经过它）在派活前比对；**只 log warning，永不阻断**。
  `DELEGATION_AUTHORITY_RECHECK=false`（默认开）时跳过比对。
- 档位来源接缝：`setApprovalLevelSource()` 由 `agent/lifecycle.ts` 注入 `policy.approvalLevel`。
  **刻意不让 `tools.ts → delegation.ts` 静态 import `agent/policy.ts`**：那会让 policy 在
  arch-guard 设 env 之前加载，只读闸门回归会全部失真（本批踩过，见验证）。

## 七、ConfirmationGate 世界状态重验（§七）

- 新模块 `world-state.ts`：`WorldFingerprint {path, exists, mtimeMs, size}`；路径解析复用
  `path-guard.realTargetOf`。只对 `write` / `edit`（`WORLD_STATE_TOOLS`），bash 不假装能验。
- 流程：创建 pending 时拍快照 → 批准端点用 `snapshotPath` **重拍**（"批准时"的口径）→
  `ApprovalStore.decide(..., worldState)` 覆盖记录 → 放行条目带快照 →
  异步放行核销（`consumeGrantEntry`）后、执行前再拍一张比对；不一致 → `blocked(..., "approval", "world-state")`。
- 文案固定：「目标文件在你批准之后变过了，请重新确认：<path>」。
- 开关 `AGENT_CONFIRM_WORLD_STATE`（**默认关**，收紧行为先观望）。关着时 `create` 不写快照、
  执行前不比对；`consumeGrant` 对外行为不变（新增 `consumeGrantEntry` 只是把条目交回）。

## 九、边界与刻意不做

- 零 `shared` 改动、零 chancellor 改动；所有新字段都是宿主侧投影（纯增量，旧客户端忽略）。
