# P1：仓库骨架与会话信号迁移

> 日期：2026-10-25。范围：新建 `lifediary-harness` 仓库 + 迁入 `POST /api/v1/signal/session`；
> 不搬 LLM 代理、不做 Agent、不建库。
> 依据：拆分方案 §2/D2/D3/§6-P1、backend 接口文档 §7.1（契约总源）、backend signal 包（对照基线）。

## 背景

拆分方案定稿后（D1~D8，backend 仓库 2026-10-25），AI 编排从 backend 迁往独立服务。
P1 先把最简单、零领域依赖的信号评估搬过来，跑通"同密钥 JWT + 内网配置拉取 + 自带频控 +
Xray 出口代理"整套部署面，为 P2（LLM 代理迁移）铺路。

## 决策

1. **技术栈与 backend 对齐**：Java 17 + Spring Boot 3.5 + Maven；jjwt 0.12.6 / okhttp 4.12.0
   与 backend 同版本（D2/R2：语言与库不另起炉灶）。
2. **鉴权用纯过滤器**，不引 spring-security：校验口径（HS256 + subject=userId、失败 403 空响应体）
   与 backend 的 Spring Security 行为一致，App 侧无需区分两端；secret 未配置/过短 = 全 403（fail-closed）。
   端点不消费 principal——信号是 advisory、无用户态，账号存在性由 P2 的扣额闸门兜底（D2 注销语义）。
3. **密钥只走环境变量**：`TYPESAFE_API_KEY` / `TYPESAFE_PROXY` 不进 ai-config 下发
   （backend 后台规划 §2.3"密钥绝不入库"同口径；接口文档 §7.1 把 key 列为 `ai.signal.*` 的表述
   以本决策为准修正，ai-config 只承载非秘密策略参数）。
4. **契约金样测试**：backend 的归一化/钳制是确定性纯函数，故用"固定 Jev 应答 → 固定响应 JSON"
   的金样锚定两端一致；跨服务真机对比（同一入参打两端）列入 P1 上线清单人工执行。
5. **配置拉取惰性触发**（不同步起定时线程）：60s 缓存 + `since` 增量 + 失败沿用上次成功 +
   从未成功用内置默认（P1 = 空表）；每次上游调用日志带 configVersion（D7 审计闭环）。
6. **频控等价移植**：backend 闸门只护它的 `/auth/**`，harness 自带同构实现
   （SIGNAL 桶 30/分钟 + 并发 4，环境变量可调，测试覆盖频次/并发/开关三行为）。

## 影响范围

- backend 侧零改动（`/signal/session` 迁移期并存，见 backend 接口文档 §7.1 状态表与下线条件）；
- App 侧零改动（真机验收：`aiBaseUrl` 指向 harness 后收尾提示行为与今天一致）。

## 验证

`mvn test` 全绿：**Tests run: 18, Failures: 0, Errors: 0**。覆盖验收前三条：
金样逐字段一致、available=false 三路径（未启用/无 key/上游失败+解析失败）、鉴权 403。
**未验**（列入上线清单）：真机 `aiBaseUrl` 切换后的收尾提示行为对比——需要 backend/harness
双服务并行部署，属部署验证不在单测范围。

已知问题（如实登记）：`AiConfigPuller` 的"从未成功→内置默认"在 backend 不可达时每次拉取都要
吃一次 200ms 连接超时（60s 一次，可接受）；`IpRateLimitGuard` 为内存实现，多实例部署需换 Redis。

## 回滚

App 端把 `aiBaseUrl` 置空（或 backend 侧清掉该配置）即回到"全走 backend"，harness 直接停掉即可；
backend 侧端点未动，无数据迁移。
