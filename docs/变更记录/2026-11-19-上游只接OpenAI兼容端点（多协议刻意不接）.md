# 2026-11-19 上游只接 OpenAI Chat Completions 兼容端点（多协议刻意不接）

> 只登记决定，不改代码。上游协议面属于「看不见但到处生效」的边界，结论已下沉到 `docs/基线文档/系统架构.md` §7.1。

## 决定了什么

- 上游只接 **OpenAI Chat Completions** 一种线协议：`/chat/completions`，流式 SSE + `choices[0].delta` + `tool_calls`。
- 各家的原生协议（Anthropic Messages / OpenAI Responses / Gemini generateContent / Bedrock Converse 等）不直接接；协议差异由**本地网关或供应商的兼容端点**归一。
- 宿主只维护一个适配器：`ts/apps/server/src/provider.ts:554` 的模型写死 `api: "openai-completions"`，`buildApi()` 用 `openAICompletionsApi()`（`:581`）。
- pi-ai 1.4.0 本身支持十种线协议（`KnownApi`，见 `node_modules/@earendil-works/pi-ai/dist/types.d.ts:20`），本决定是**刻意只启用一种**，不是库能力不足。

## 为什么

- 一套鉴权、一套请求参数、一套工具调用形状，业务代码与 UI 不感知供应商差异。
- 网关已经承担了协议转换；宿主再开多适配器，等于长期维护两套协议面与两套探针。
- 当前所有已配置供应商（百炼 compatible-mode、DeepSeek 等）本来就以 OpenAI 兼容端点接入，现状不需要改代码。

## 边界（没验证的不冒充已知）

- **「有 OpenAI 兼容端点」≠「能力等价」**：工具调用流（尤其并行工具调用）、`reasoning_content` 这类思考字段、缓存用量字段，可能被网关降级或丢弃。
- 接新网关时先跑两件事：流式工具调用能不能透传、`usage` 里的缓存字段还在不在；这两项决定审批/闸门与上下文统计是否准确。
- 未逐一实测各家网关的兼容覆盖；本决定只约束宿主侧的协议面，不替网关背书。

## 刻意没做

- 没改 `provider.ts` / `providers.json` / 设置页：当前实现已经符合本决定。
- 没写多协议接入方案：只有翻案条件成立（网关无法转发必需能力、且用户点名要接某家原生端点）时才立项。
