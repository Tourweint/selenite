## 动手前：按 MemoryKind 分支的代码清单（2026-11-08 核对，以代码为准）

新增 `MemoryKind = "work"` 前，逐处核对了所有按 kind 分支 / 按 kind 过滤的落点，逐条定下 work 行为。

## 与任务书的口径差异 / 取舍（以代码为准，已核对）

1. **「终态」按真终态收窄**：`TicketOutcomeStatus` 有 5 个值，其中 `needs_you`（等你回答）/ `idle`（等子单）在
   `TERMINAL_TICKET_STATUS` 里算"终态"，但对履历是**中间态**——续跑会再 `settle`，写了就是同一单两条。
   故只对 `done / failed / aborted / canceled` 落账；`fail()`（派单跑挂）也算一条 failed。
   「取消/中止也结算」由 `isCanceled` 判定写在作废位早退**之前**兑现（终态记 `canceled`）。
2. **「超出 400 带说明」落在工具侧**：`routine_manage` 是模型工具，没有 HTTP 状态码。
   上限拒绝落成 `code: "limit"` + 明确中文说明回给模型（"每个执事最多 10 条活动例行规则…"），
   不落库、不动别人的规则。归属失败一律 `code: "not_found"`（HTTP 端点仍是既有 404 语义）。
3. **work 写入口另开一个 `SqliteMemoryStore` 连接**：`recordWorkSettlement` 若反向 import `agent/assist.ts`
   的 `memoryEngine` 会绕成环（结算链 → agent → tools → 结算链）。照 `memory-ingest.ts` 的既有先例，
   在 `MEMORY_DB_PATH` 上自己开一个连接；`workSummaryFor` 的读口 `create=false`（库不存在不建文件），
   避免纯装配在无记忆机器上凭空造 `.data/memory.db`。
4. **work 的 cap 在写入点现算，不改 `engine.pruneSessionScopes`**：`MEMORY_SESSION_CAP=0` 会关掉通用修剪，
   但履历 200 条上限不该跟着失效；用 `pruneOldest({kinds:["work"]})` 每次写完现算最稳，且不动刀一之前的
   通用修剪行为（§11 用例守着）。
5. **`companion-api.test.ts` 纳入 `test` 列表**：任务书要求 currentGoal 的迁移 / PATCH / 列表形状被
   `pnpm --filter @lifediary/server test` 覆盖，而该文件原先不在脚本里（单跑是过的）。一并纳入，
   原有 6 条头像用例也进全量。

## 设计上的刻意选择

- **履历只由结算写**：模型 `remember` 的 kind 枚举、导入白名单都不含 work；语义整理建议剔除 work。
  append-only 是履历可信的前提——能被模型随手写一条的"履历"不是履历。
- **召回排除放在候选集这一层**：work 因此既不进 hits，也不触发 `touchRecall` 的衰减 / 强化写回，
  「不衰减」不需要在 `decay.ts` 加 kind 特判（纯函数无 kind 参数，改它等于污染契约）。
- **两层互补别混**：在办 = 现在时（runs 扫描，刀一），履历 = 过去时（work 结构化查询，刀二），
  同一个 system 注入点、两段数据，不互相推算。
- **目标不版本化**：契约是岗位（低频、慎重、下一轮生效），目标是"现在在奔什么"（现取现用）。
  放在同一装配点但语义分开，不 bump `partner_versions`。
- **不建第二条注入通道**：刀二的目标段 / 履历段都长在刀一的 `buildPartnerTurnContext` 里，
  `group-runtime` 仍只留注释（私聊 / 例行 / 群成员轮共用同一条 `beforeRequest`）。
- **工具的 partnerId 由会话认出、不接受模型传参**：越权改别人例行规则的面直接堵死；
  `routine_manage` 进 `WRITE_TOOLS` + 高危清单 + 自主轮风险表（D14 备忘）三处同时登记。
- **不自动建周回顾规则**：静默的自动轮 = 意外 token 账单。规则由主人配，或说一句后执事自建，
  且第一次要人点头（高危审批）。系统架构「刻意没有」条目**按分工由派单人落**，执行者未写。

## 已知边界（如实登记）

- **work 只认 `partnerIdOfSession(originConversationId)`**：主人 / 总管 / 无链接会话发起的单不落履历（"发起执事"的口径，不是缺陷）；老单没有 `originConversationId` 也认不出，与刀一「当前在办」同款边界。
- **`needs_you` / `idle` 不落账**：续跑后终态才落。跨进程恢复若同一单重复 `settle`，稳定 id `work:<票号>` 的 upsert 保证不新增（`created_at` 保留首次）；但 content 会被最新一次终态覆盖（这是"以最后终态为准"，append-only 指**不追加第二条**，不是不改字段）。
- **「近 10 单」是最近 10 条 work 记录的聚合**：`中止` = aborted + canceled + 认不出的旧格式；不打分、不搞 KPI 数字。零记录整行省略。
- **work 也受 `MEMORY_SESSION_CAP` 整体封顶影响**（取严）；work 专属 200 条上限在写入点现算，不受 `MEMORY_SESSION_CAP=0` 影响。`engine.list()` 的分组 rank 刻意不给 work 特殊位置（落默认档最末）。
- **`PARTNER_WORK_RECORD=false` 同时停写入与读口**（装配段据此不加摘要行）；既有 work 记录保留不删，不回滚数据。
- **产物只记目录路径**（`TicketResult.tasks[].dir`，最多 3 个），不透传文件清单；8e（A25 chancellor v0.5 产物透传）之前不阻塞、不等待。
- **`GET /partners/:id` 多了 `currentGoal` 一列**（纯增量）；`currentGoal` 不进 `GET /partners` 列表、不进 shared（刀三与 9-P / 手机端联动）。手机端 / 前端若做严格 schema 校验需忽略未知字段（现状没有这种校验）。
- **system 注入的正文不可从 transcript 断言**（刀一同款）：单测覆盖装配函数，探针覆盖「一轮真链路能跑通、没有装配异常日志」；"模型真的收到了这段"由派单人真模型手验。
- **`routine_manage` 不提供 list action**（任务书只列 create/disable/enable/delete）；执事要知道自己有哪些规则，靠主人侧的 `GET /api/v1/routines?partnerId=` 或工具回话里的规则名 / id。
- **`providers` / `diary` / `tasks` / `phone` 探针没跑**：改动不经过供应商配置、日记镜像、任务中心只读投影、手机 worker 链路；`delegation-api.ts` 只给 `defaultRetryRuntime` 补一个可选回调，重试 / 回话的 HTTP 形状未动，http 探针 §24 已覆盖 routines 列表读口。
- **系统架构「刻意没有」条目按分工由派单人落**，执行者未写基线架构文档；**未 commit**。
