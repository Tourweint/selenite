# 2026-11-21 请求详情消息层对比与命中率列对齐

**改了什么**

1. **详情对比补上消息层（`compare.messages`）**
   - `request-stats.ts`：`RequestCompare` 新增 `messages: { shared, replaced, appended }`——
     把两条请求当时的**非 system 消息**逐条做指纹（sha1(JSON)），取最长公共前缀。
     `shared` = 逐条一致的消息条数（可缓存的消息前缀长度）；`appended` = 追加条数；
     `replaced` = 上一条有、这一条被换掉的条数（>0 才是真的前缀断裂，正常只有压缩 / 改写会这样）。
   - 前端详情浮层（`settings-context.js`）的对比块随之改口：
     - 前缀没变 + 消息纯追加 → 「已存档消息与上一条逐条一致，往后只追加了 N 条（追加不改前缀）」；
     - `replaced > 0` → 警示「已存档消息从第 X 条起与上一条不同（旧 N 条被换掉）——可缓存前缀在这里断掉」；
     - 命中率 < 5% 且前缀完全一致 → 明写「没命中是上游把缓存丢了（过期 / 淘汰 / 上游不稳），
       不是这边改了前缀」——0% 的归因写在脸上，不再让人猜。
   - 诚实边界不变：临时注入不落 durable，`compare.messages` 只覆盖已存档消息。

2. **命中率列左对齐**
   - `style-24-context.css`：`.ctx-req-rate` 与表头第 7 列改 `text-align: left`。
     原因：骤降标志（`!` / `↑` / `·`）跟在百分比后面，右对齐时会把 % 顶得参差；
     用户口径「别右对齐了，左对齐 / 按百分比号对齐」——取左对齐。
     prompt / 命中 / 写出三列数字仍齐右不动。

**为什么**

用户看「请求与缓存」页问：降到 0% 是什么意思、是不是前缀过期、两次请求之间到底什么变了。
列表行的 `flag` 只回答 system / 工具面，消息正文层没有对比——补上后，「0% 但本地前缀完全一致」
与「0% 且前缀真断了」在一处就能分清；顺带把命中率列对齐按用户口径修掉。
