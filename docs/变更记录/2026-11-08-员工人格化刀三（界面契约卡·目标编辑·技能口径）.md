## 设计上的刻意选择

- **两张卡各自独立保存，不并进人设卡那次 PATCH。** 人设卡一次提交 `avatar/name/soul`（服务端多槽位同批校验），
  契约走独立 `PUT .../contract`（调岗 = 独立版本事件，不该被人格 diff 顺手带上），目标走独立 `PATCH {currentGoal}`
  （不版本化）。三者写的是不同语义、不同端点，合到一个"保存"里反而会出现"改目标却把没改的人设再提交一遍"。
- **降级只读提示与空态合并成同一份卡。** `PARTNER_CONTRACT=false` 时 detail 干脆不带 `contract`/`contractVersion`
  两列（刀一既定形状），所以判据是 `"contract" in csDetail` 而不是"字段是不是空串"；PUT 回 400「未启用」
  （两次请求之间开关被关的竞态）走同一个 `csContractDisabledCard()`，两条路径长得一样，用户不会看到
  "一会儿能编辑一会儿不能"的两套空态。降级时顺手 `delete csDetail.contract/contractVersion`，保证重进人设页
  仍停在只读态。
- **保存成功只就地改 DOM，不重画整页。** `renderCsPersonaPage` 的 `if (!csDetail)` 早退会等详情回来重画，
  但保存后不会触发；三张卡各有自己的 `original` / `saving` / `refresh`，互不引用，避免"改完契约把正在打的
  人设草稿冲掉"（`refreshCsDetail` 只在首页重渲染，`loadRoster` 只刷侧栏，都不重画抽屉）。
- **契约 textarea 不强制非空。** SOUL 卡要求非空（人设不能空），但契约四节全空是合法状态
  （刀一：`四节全空则整段不出现`），清空 = 撤掉岗位契约，是有效调岗。校验一律交给服务端，界面不重复立规矩。
- **目标成功提示写"下次对话起生效"、不带版本号。** 目标不是身份、不 bump `partner_versions`（刀二既定），
  照任务书口径不写 `v2`，与契约卡的 `v{n} · 下一轮生效` 形成对比。
- **工具描述只补口径、不动行为。** 两句都是 `description` 字符串拼接（含中文注释标 E3 来源），
  参数 / enum / `execute` 一字未动；`remember` 的 `MEMORY_KINDS` 仍不含 `work`（刀二既定，不碰）。
