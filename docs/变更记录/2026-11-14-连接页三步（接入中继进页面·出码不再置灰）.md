# 2026-11-14 连接页三步：接入中继搬进页面，出码不再置灰

## 背景

用户 2026-11-14：「咱们现在不在同一个 WiFi，依靠这个中继……我怎么能让电脑能连上 VPS 呢？那现在肯定连不上」
「添加设备这个是灰色的呀，我没有用」「点开添加设备好像是输入地址……我不应该在没连上的时候就输入地址吗」
「这逻辑不符合正常人操作逻辑。你先给正常人操作逻辑想明白，然后再去调整」。

核对后的实情：**电脑其实连着中继**（`书房主机` 在名册里、`isHome`、在线），灰按钮是另一回事——
见下面第 2 条。手机 `vivo手机` 自 2026-11-06 之后没有再上过线。

## 结论

链路是单向的：中继是门牌，**电脑先登记，手机才有码可扫**。所以页序必须等于操作序；
第一步的动作（地址 + 主令牌）以前只存在于 `.env`，页面上只有一段教程，于是用户看到的是
「一个灰按钮 + 一段说明书」。不是按钮坏了，是第一步没有入口。

方案全文：`docs/设计方案/2026-11-14-连接页三步（接入中继是第一动作）.md`。

界面口径（用户最在意的三条）：

1. 链路图下面永远只给**一个**动作，指向还没做的那一步（接入中继 / 重新检测 / 添加手机）。
2. 「添加手机」不置灰：没接入时文案是「先接入中继」，点了直接开接入弹窗，不再是死路。
3. 经中继加入的手机出现在「不在同一个 WiFi」一列（中继名册），与「已连接的设备」（本地配对指纹）**分组不合并**——
   扫完码能看到它，才算"加上了"。

## 没验的

- **浏览器实机点验**（本机无 GUI 自动化授权）：链路图三态、接入弹窗、出码弹窗、名册刷新只做了代码与接口层核对。
- **接入成功路径没在真中继上跑**：会生成第二台同名设备并把当前连接顶掉（4409），留到用户自己在页面上点一次，
  或换 VPS 时验证。
- **手机端扫码**（`lifediary` 仓）本轮没动，手机 App 侧仍是旧文案「点经中继添加设备」——按钮名现在叫「添加手机」。

## 运行状态处理（本轮实做过）

发现两种进程同时跑在 39847 上：桌面壳拉起的旧实例（`node --import tsx src/index.ts`，旧代码）
与一个重复的 `pnpm dev`（tsx watch），后者每次热重载都用同一设备令牌连一次中继、把前者顶掉
（中继 4409），于是出现"中继显示在线、harness 说自己未连接"的假象。已停掉重复的 dev 树，
按壳的方式重启服务（`node --import tsx src/index.ts`，日志 `.data/runtime-manual.log`）。
**注意**：现在这个进程不是壳的直属子进程，壳里点「重启/停止」仍按端口杀进程，行为一致；
下次点「重启」后即回到壳托管。

## 回滚

- 界面与端点：`RELAY_LINK_UI=off`（两个端点 404，页面回"只认 .env"形态；本文件的 UI 改动需回滚两个 web 文件）。
- 中继鉴权修复：不建议回滚（旧口径等于对公网开放）；要临时放行就在中继上配好 `RELAY_OWNER_TOKEN`。
- 数据：删 `.data/relay-link.json` 即回到 `.env` 形态，无库变更、无契约破坏性改动。
