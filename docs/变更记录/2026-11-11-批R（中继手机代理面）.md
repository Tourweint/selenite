## 做了什么

### R1 `/api/v1/*` 反向 HTTP 代理（`ts/apps/relay/src/server.ts` + `hub.ts`）

手机把 base 指到 `http://<relay>/api/v1`，REST 由中继收下 → `invoke` 帧投给名册里的
**任务主机**（`isHome=true`）→ 主机回 `invoke_result` → status/body 原样回手机。

- 鉴权走既有 `deviceIdOf()`：无效 403 空体（不开免鉴权口子）；
- 无主机 / 主机离线 → **502 `device_offline`**；15 秒无回包 → **504 `device_timeout`**；
  帧超过 `RELAY_MAX_FRAME_BYTES` → **413 `payload_too_large`**（先算帧长再发，不让目标端 ws 静默丢帧）；
- 只路由到主机、**不支持手机指定目标设备**：token 能打到谁收敛成"主机一台"，越权面最小；
- 帧契约进 `shared`：`RelayInvokePayloadSchema` / `RelayInvokeFrameSchema` /
  `RelayInvokeResultFrameSchema`，全部 `.strict()`。

### R2 扫码加入（新文件 `ts/apps/relay/src/pairing.ts`）

`POST /api/relay/join-code`（owner 签发）→ `{joinCode, expiresAt}`；`POST /api/relay/join` 用码
换 `{deviceId, deviceToken, protocolVersion}`，明文令牌只回这一次。

- 码 **256 位随机**（32 字节 base64url，43 字符）、**只存 sha256**、TTL **10 分钟**、
  一次性、同时最多 **5 个**（超出顶掉最旧）；
- 与既有 6 位配对码（`store.issueCode`）**刻意两套**：24 位熵的短码需要"错 5 次作废"的
  防爆破状态机，256 位随机不需要；两套都只存 sha256；
- `store.createDevice()` 从原 `redeem()` 抽出，配对码与扫码加入共用同一套
  令牌生成 / 名字截断 / 设备上限淘汰，两条路不发散（`redeem` 行为逐字节不变）；
- 加入码记录落 `relay-state.json` 的 `joinCodes`（`hash/expiresAt/createdAt`），
  过期条目读时过滤。

### R3 presence 广播（`hub.ts`）

hello 成功（welcome 之后）与连接关闭（名册删位之后）向**所有在线连接**推
`{kind:"presence", devices:[RelayDeviceView…]}`。全量投影、复用 `store.listDevices`，
帧小频低不做增量；慢消费者跳过本条（不为名册帧触发 1013，下次广播自然对齐）。
契约 `RelayPresenceFrameSchema` 进 `shared`。`welcome` 与 meta `devices` 语义不变；
协议版本仍是 v1（增量帧，老客户端静默忽略）。

### 回滚开关

`RELAY_MOBILE_PROXY_ENABLED`（默认开；`off/false/0`）：`/api/v1/*`、`/api/relay/join-code`、
`/api/relay/join` 整段 **404**。WS 隧道与既有管理面完全不受影响。每次请求读 env
（联调可中途切，不用重启进程）。

   14 项全过，关键行：

   - `join 换 deviceToken（只回一次）` / `同一加入码第二次用 → 403 空体`

## 与任务书字面不一致的地方（都记录理由）

1. **join 失败统一 403 空体**，而不是"403 或 400 带说明"。任务书 R2 §3 两种都允许，
   probe 明确要求"码第二次用 403"；统一成 403 空体同时满足两端，也贴合仓库既有
   "鉴权失败一律 403 空体"口径——码就是凭证，验不过就是鉴权失败。**body 形状不对**
   （缺字段 / 超长）仍走 400 带说明，那是业务拒绝不是验码失败。
2. **新增 413**：任务书只写了 502/504 两种失败。但 `invoke` 帧上限 2MB 是既有硬约束，
   超长请求若不拦会以"目标端静默丢帧 → 504"的形式出现，语义骗人；改成显式 413 并写进接口文档。
3. **presence 也发给刚 hello 的连接**（任务书说"所有在线连接"）。它自己的 `welcome`
   已带同样快照，这一帧是冗余的；不做特例是为了让广播逻辑只有一条路径
   （"所有在线连接"字面执行），代价是每次上线多一帧。
4. **没有为 join 加限流**：256 位随机码暴力枚举不可行；既有配对码的每分钟 30 次限流
   保留不动。若将来加入码熵降低，这里必须补限流。

## 刻意没有（二期）

- **Ed25519 设备签名**：一期靠"中继覆写 src + 哈希凭证"够用，签名要动 hello 协议与
  两端密钥生命周期，二期单独立项。
- **手机经中继的 SSE 仿真**：反代是"一问一答"，流式需要额外的帧通道与背压策略；
  先通"发→回读"。
- **手机 token ↔ harness token 的映射**：第一版要求手机配的令牌就是 harness 的
  `AGENT_TOKEN`（中继不存 harness 令牌、不替换 Authorization）。映射表是鉴权模型改动，
  要与数据边界一起设计，不塞进这一批。
- **指定目标设备的反代**（`?deviceId=`）：默认只打主机，收敛越权面；多目标等真需求。
- **join 码的设备能力位**（`capabilities`）：手机当前不需要自报能力，join 建出的设备
  能力位为空；旧配对码路径仍可带。

## 已知边界

- 中继日志每条反代记一行 `[relay] invoke device=<id> id=<uuid>`（与既有 forward 同口径），
  不记路径正文、不记码；高频轮询时日志量随请求数增长。
- presence 是"事件触发"广播：sweep（idle terminate）清出的连接走 close 事件仍会广播；
  但没有周期性心跳广播，客户端若丢了一帧应靠 meta `devices` 兜底。
