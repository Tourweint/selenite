## 背景

§5.7 把四件事标成"待验证"：Windows 下 pid 存活判断、`harness.resume()` 遇到未收尾提交、
worktree 残留清理、60% 阈值下"压缩还是换段"的判定。四项都不阻塞设计，但一直是靠读代码推断。
本批把它们变成可复现的实测：每个结论都有探针或命令输出，不再写"看起来没问题"。

## 做法与结果

### 1. pid 存活判断（`scripts/pid-liveness-probe.ts`）

`chancellor/src/lease.ts:isPidAlive()` 是恢复（inflight）与租约（lease）唯一的"进程还在不在"判据，
实现是 `process.kill(pid, 0)` + EPERM 当活。实测（Windows 11 / Node v24.22.1）：

| 输入 | 结果 | 判定 |
|---|---|---|
| 当前进程 pid | 活 | 正确 |
| 刚退出的子进程 pid | 死（ESRCH） | 正确 |
| Windows pid 4（无权限） | `process.kill` 抛 EPERM → 判活 | 正确取舍 |
| pid 0 | 死（函数先挡 `pid <= 0`；`process.kill(0,0)` 本身会成功） | 正确 |
| 负数 / 非整数 / 999999 | 死 | 正确 |

**误判面**：判据只看 pid，不看进程启动时间。若崩溃后 pid 被系统回收给另一个进程，
恢复会把原单判成 `still_running` 并**无限期跳过接管**（inflight 没有心跳超时）。
探针把"无关活进程的 pid"写进 inflight（与 pid 复用对函数是同一份输入），跑到
`recoverDelegations` 那一层，实测 `stillRunning=1 / resumed=0`，单子确实卡住。
租约侧有两道闸，最坏只拖 `LEASE_STALE_MS`（默认 5 分钟）：心跳过期会回收，pid 死会立刻回收；
pid 复用只影响"心跳仍新鲜"的那 5 分钟。

结论：**符合设计，但 pid 复用是登记在案的残留风险**（见"发现的问题"1）。

### 2. `harness.resume()` 与未收尾提交（`scripts/harness-resume-busy-probe.ts`）

造法：子进程提交后让 faux 模型响应永不返回，等提交 `placed`、生成任务已在存储里，
外部 `taskkill` 杀进程；父进程重开同一 SQLite。两种顺序各跑一遍：

- A：先 `resume()`，再提交新输入；
- B：先提交新输入，再 `resume()`（用户抢在恢复前说话）。

两轮结果一致：

```
重开时旧提交 placed、旧生成任务 tasks=1
新输入 admission=queued
旧提交最终 done；新输入最终 done
上下文顺序：["旧输入：未收尾", "新输入：…"]（旧在前，新在后）
```

结论：**符合设计，新输入不会顶掉旧提交**。默认 `followUp` 下新输入排在旧轮之后；
`submit()` 自己也会触发调度，所以 B 顺序也没有把旧提交挤掉。

### 3. worktree 残留清理（`scripts/worktree-cleanup-probe.ts`）

真起一个 git 仓库，按 `worktree` 隔离跑 `runScheduledTasks`，worker 用 native + faux
（拆单跳过：本项验的是调度层，不是 Qoder 拆单）。

| 路径 | 实测 | 清理时机 |
|---|---|---|
| 正常完成 | 进程 exit 0、产物合并、副本消失 | `executeTask` 合并后立刻 `removeWorktree` |
| 失败（worker 非 0） | 副本保留、inflight 记录也在 | **刻意保留**（看现场）；同 seq 下次开工时 `prepareTaskWorktree` 先 `removeWorktree` 再检出，成功后删掉 |
| 崩溃（中途 taskkill） | worktree + `inflight.json` + 半成品都在 | 重启恢复 `cut_off` → 自动续跑 1 次 → 复用副本 → 成功后删掉 |

结论：**符合设计**。三条路都没有非预期残留；崩溃残留的最终归宿是"续跑成功即清"。
失败副本若这张单永远不重试也不取消，会一直留着——这是设计里的"刻意保留"，不是泄漏。

一个实测细节：崩溃留在 worktree 里的半成品文件**必须在 `writes` 里声明**。
探针第一版没声明 `partial.txt`，续跑时被 `collectTaskChanges` 判成"越权写入" → 失败 → 副本继续保留；
补进 `writes` 后恢复路径才走通。声明是硬契约，崩溃续跑也不例外。

### 4. 60% 阈值"压缩还是换段"（`scripts/context-ratio-probe.ts`）

判定在 `worker-main.ts`：本轮 `record.status === "done"` 且有助手文本 → 换段
（`handoff.md` + `reset` + `rotations+1`）；否则 → `compact`。把窗口压到 8000、
阈值 60%（4800），跑真 `worker-main` 进程：

- **A 正常收尾 × 5**：faux 回复 5200 汉字。5 轮全部 `已换段`，`rotations` 1→5，
  `handoff.md` 5 段；第 6 轮短回复不再触发（说明 `reset` 生效，历史没累积）。
- **B 没正常收尾**：本地 OpenAI 兼容端点全 400，需求本身 5200 字。
  实测日志 `上下文 5856/8000 到阈值，未告一段落，已压缩`，`rotations` 不变、`handoff.md` 不增段。
- **C 压缩到底有没有落地**：端点只让第 1 个请求失败，后续成功（压缩可用）。
  结果：`requests=1`，本进程内压缩任务**没有发出任何模型请求**；进程退出时上下文仍是 5200 字全文。
- **D 下一次启动**：同一领域再跑一轮，`resume()` 把上一轮积压的压缩任务续上，
  上下文从 5200 字降到 353 字。

结论：**判定方向符合设计（done→换段、非 done→压缩），但"已压缩"日志提前说谎**：
`conversation.compact()` 只完成"入队"，进程紧接着关闭，压缩任务在本轮不会跑；
它在下一次负责人启动时才落地。功能上不是丢数据（D 证明会补），但本轮日志与实际不符，
且下轮启动要多付一次压缩延迟。**登记为偏离（只登记，未修产品代码）**。

## 发现的问题（均只登记，未修）

1. **pid 复用会让 inflight 永久 `still_running`**（风险，非本批引入）。
   `recoverDelegations` 只看 `isPidAlive(record.pid)`，没有启动时间/心跳兜底。
   崩溃后若 pid 被别的进程占用，这张单每次启动都被判"还在跑"，既不接管也不转「待你处理」。
   租约侧有 5 分钟心跳兜底，不受影响。建议方向：inflight 记进程启动时间（或 `startedAt` + 心跳），
   单纯 pid 只作辅助；需单独立项。
2. **非 done 分支的"已压缩"日志不真实**（偏离，2026-11-08 实测）。
   `await conversation.compact()` 返回的是"已受理"，不是"已完成"；随后 `harness.close()`，
   压缩任务留到下一次启动。当前日志在压缩尚未发生时就写"已压缩"。
   如果要改，最小改法是等压缩任务终态（`waitForTask`）再打日志，但这会把本轮进程留得更久；
   也可以把日志改成"已入队压缩，下次启动生效"。涉及行为取舍，未在纯验证批里动。
3. **崩溃半成品未声明会被判越权**（设计契约，提示后来者）。
   崩溃恢复复用 worktree 时，半成品与最终产物一样过 `writes` 校验；没声明就按越权写入判失败，
   副本也不会清。这不是 bug，但写任务计划时要把"中途可能落盘的文件"也声明进去。

## 没验证到的 / 不确定点

- **真实 PID 复用没有在系统里强行制造**：Windows 不能稳定指定复用哪个 pid。
  探针用"无关活进程顶着记录里的 pid"作为等价输入——对 `isPidAlive` 而言两者不可区分，
  但"复用发生的概率/时间窗"没有实测。
- **真实模型下的自动压缩与手工换段的先后**：faux 模型的 `contextWindow` 不是
  `MANAGER_CONTEXT_WINDOW`，所以第 4 项只验到了应用层判定，没有验 pi-durable 在真实模型
  （`contextWindow = MANAGER_CONTEXT_WINDOW`、`reserveTokens = 40%`）下会不会先做阈值压缩。
  应用层判定本身已被 A–D 钉死；两者叠加后的实际走向仍属推断。
- **崩溃路径的"卡住"用注入 runner 撑住任务**：worktree、租约、inflight、恢复都是真的，
  只有"让任务停在中途"这一步是探针注入的；没有用真实模型跑到一半再杀。
- **失败副本长期不重试/不取消**：只验到"下次开工会清"，没验"永远不重试"时的最终归属
  （按代码是没有回收点，只能人工删）。
- 本批未跑全量 `pnpm test`：改动只有新增探针与文档，没有触碰产品代码；typecheck 与四个探针
  已覆盖本批范围。
