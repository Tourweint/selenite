# 2026-10-31 · 直通分支下线（OpenAI 兼容层只剩"任务 + 聊天"两条路）

## 背景

`2026-10-30-X-Task任务通道` 引入任务通道后，兼容层一直是三路分流：

| 请求特征 | 路径 |
|---|---|
| 带 `X-Task` | 任务通道（服务端渲染模板、走 durable 会话） |
| 有非空 `system` | **直通**（整套 messages 原样转发、不建会话） |
| 都没有 | 聊天 Agent |

直通当初是为了让 App 把整份 prompt 塞进 `system` 而不至于被 Agent 丢掉。到 10-31，App 的 **12 个任务全部改走任务通道**、
聊天从不带 `system`，直通**已无生产调用方**；它继续留着只有坏处：客户端落后一个版本就会静默降级成"聊天轨迹"，
模板被当普通消息丢掉，产出看着成功、其实残废。

## 决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **删除直通分支** | 零调用方；三路分流本身是认知负担 |
| 2 | 带 `system` 的请求一律 **400 `system_prompt_not_supported`** | 报错比静默降级好：错误信息直接告诉客户端"任务请用 X-Task" |
| 3 | 保留 `X-Task` 头与 body `task` 两种写法 | 前者是既有契约，后者是方案 D8 的正规字段 |
| 4 | 同步删除 App 侧的 `ContextAssembler`（见 App 仓库同日变更记录） | 它已无生产调用，留着会让人以为"上下文还在客户端拼" |

## 变更清单

- `openai-compat.ts`：删 `passthrough()` 与 `passthroughWarned`（约 180 行），分支改为 400；文件头注释重写为"两条路"；
- `ChatRequest.temperature/max_tokens/response_format` 的注释改为"任务通道透传；聊天路径由服务端配置决定"；
- 文档：`接口文档.md` §2.4.1 分流表由三行改两行 + 400 说明。

## 影响范围

- **客户端必须**：任务用 `X-Task`（或 body `task`）+ `task_vars`；聊天不要带 `system`；
- 老版本 App（还带 `system` 的）会立刻拿到 400，而不是"看起来成功"的坏输出——这是刻意选的失败方式；
- 采样参数（`temperature/max_tokens/response_format`）在任务通道仍然生效（派生模型透传），聊天路径仍由服务端决定。

## 验证结果

```
> pnpm typecheck                             通过
> pnpm --filter @lifediary/server tasks      ✓ 任务通道全部通过
> pnpm --filter @lifediary/server http       ✓ 端到端全部通过
> pnpm --filter @lifediary/server diary      全部通过 ✅

手工抽验（真实上游）：
· 无 task / 无 system 的聊天 → 200，正常回复
· 带 system 的请求          → 400 system_prompt_not_supported
```

**过程中踩到一个坑（如实记）**：第一次删分支时，把 `return agentChat(c, body, messages);` 这条兜底返回
一起删掉了，于是"聊天"路径的 handler 返回 `undefined` → Hono 抛
`RangeError: init["status"] must be in the range of 200 to 599`。typecheck 不报（语法合法），
是 `pnpm...tasks` 的 §4「通用聊天回归」抓到的。教训：删分支后要确认"兜底 return"还在，
探针里那条"无 X-Task 回归"就是为这个存在的。

## 回滚建议

`git revert` 本提交即可恢复直通（代码是自包含的一段函数 + 一个 if）。数据无迁移。
