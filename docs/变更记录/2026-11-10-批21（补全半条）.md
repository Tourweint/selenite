## 一、工具能力声明接管审批判定（§一，零行为变更）

- `approval-policy.ts`：`needsApproval()` 改读 `tool-capability.ts` 的声明——
  `WRITE_TOOLS.has(tool)` → `capabilityOf(tool).destructive`；`critical.has(tool)` →
  `needsApproval === "critical"`。**优先级：调用方显式清单 > `AGENT_APPROVAL_CRITICAL_TOOLS` > 声明**
  （人配的整体覆盖仍然压过声明）。
- 未登记的工具 → 保守当作 `destructive: true` + `needsApproval: "critical"`，同一工具只 `console.warn` 一次
  （`capabilityForApproval()`）。
- `WRITE_TOOLS` 保留：`readOnlyBlockReason()`（只读档 = 能力边界，与审批正交）仍读它；
  声明与它的等值由单测双向钉住。
- `tool-capability.ts` 文件头注释、`approval-policy.ts` 的注释同步改写（"只登记不接管" → "已接管"）。
- 一致性守卫加强为**集合级双向断言**：`destructive` 集合 === `WRITE_TOOLS`、
  `needsApproval==="critical"` 集合 === `DEFAULT_CRITICAL_TOOLS`，并断言 `declaredCriticalTools()`
  （运行时真正用的那一份）与常量一致。另加 1 条"未登记工具按最严处理"的行为测试。
- **验证口径**：§一 改完单独跑 `pnpm --filter @lifediary/server test`，
  原有 **635 条一条不红**（新增 1 条未登记测试后共 636 全绿）。没有为了过测试改任何行为。

## 二、bash 后台任务：列表 / 日志尾部 / kill（§二）

- `bash-background.ts` 新增管理面：`listBgJobs` / `readBgJobLog`（最多 200 行、返回总行数）/
  `killBgJob` / `pruneBgIndex`（>200 条时只裁最旧的**已结束**索引条目，**日志文件一个都不删**）。
- 归属安全：`liveJobs` 只记**本进程**起的子进程；重启后 index 里的 `running` 一律返回
  `not_owned`，**绝不按 pid 杀**（pid 会复用）。POSIX 杀整个进程组（detached 即组长），
  Windows 用 `taskkill /T /F`。
- id 严格校验 `^bg-[a-z0-9]+-[a-z0-9]+$`（防 `../` 拼路径）；日志只进响应体。
- 新文件 `bg-jobs-api.ts` 挂三个端点（`index.ts` 装配）：
  `GET /api/v1/agent/bg-jobs`、`GET .../:id/log`、`POST .../:id/kill`。
  开关沿用 `AGENT_BASH_BG_TIMEOUT`，关着时整组不挂（404）；启动时执行索引裁剪。
- 新增 `AGENT_BG_JOBS_DIR`：**只给探针/测试隔离**（同既有 `.data/*` 的 `*_PATH` 口径），
  默认仍是 `.data/bg-jobs`。

## 三、例行触发器 `if` / `ends`（§三）

- `RoutineTrigger` 增加两个可选字段（放在共用基类型 `RoutineTriggerGates`）：
  `if?: {note}`、`ends?: {at?, after?}`。
- 新模块 `routine-gate.ts`：`evaluateRoutineCondition()` 用一次独立 `completeSimple`
  （`auxiliaryModel("review")` 可 pin 小模型，15s 超时，maxTokens 4，temperature 0）问"成立吗"；
  `parseConditionAnswer()` 只认明确 YES/NO（中英），解析不出来 = 不成立。
  **失败即跳过**：没配模型 / faux / 超时 / 报错 / 答非明确 → 当不成立。
- `routines.ts`：`runOnce` 在建 run 之前逐条问 `if`（多个触发器**全部成立才跑**）；
  不成立记一条 `status:"skipped"`、`outcome:"skipped"`、`skipReason:"condition_not_met"` 的 run，
  **不跑模型、不认领看护、不推进游标、不消耗 `maxRuns`/`ends.after` 额度**（`completedRunCount` 排除这类）。
- `ends.at`：`nextFireFrom` 不再为过期触发器排闹钟、`onExternalEvent` 不再被过期触发器唤醒
  （在飞闹钟若排在 `at` 之前仍会响一次，属已知边界）。`ends.after` 与 `maxRuns` 取更小。
- `validateTriggers` 校验新字段（`if.note` 非空 ≤200；`ends` 至少给一个、`at` 合法 ISO、
  `after` 1..1000 整数），形状不对直接 400。HTTP 端点与 `routine_manage` 共用这一份。
- 开关沿用 `ROUTINE_CONDITIONAL`（false/0/off 时 `if`/`ends` 完全不看）。

## 四、键控基线：验收标准压缩后还原（§四）

  `task-conversation.ts` 不 import 任务中心，维持单向。任何读取 / 写入失败只 warn，不挡专线主写入。

## 五、记忆敏感闸：Luhn / 身份证校验位（§五）

- `packages/memory/src/redact.ts` 在形状规则之后加两条**校验位**规则：
  - 18 位（17 数字 + `X/x`）+ GB 11643 校验位 → 打码；
  - 16 位连续数字 + Luhn → 打码（全同数字如 `0000…` 不算卡号）。
- 只认独立数字段（前后都不是数字）：19 位流水号里的 18 位、17 位订单号不会被误切。
- 故意放行：手机号（11 位）、生日、邮编、14 位旧卡号、17/19 位、过不了校验位的 16/18 位。
- `luhnValid` / `idCardValid` 导出（纯函数，可单测）。memtest 的凭据打码段补到
  **24 个正例 / 14 个反例**（含首尾边界、小写 x、校验位错一位、全 0 等）。

## 六、例行游标推进时机（§六）

- `routines.json` 新增 `cursors: {<规则id>: ISO}`（per-routine 游标；没有就建）。
- 推进规则（`shouldAdvanceCursor`）：只有 `ok && !quiet && 没跳步` 才把游标推到本轮 `run.endedAt`；
  quiet / skipped / failed（含读失败）一律原地不动，下一轮仍从同一处看。
  读失败本来就记 `failed`（不是 quiet），本批把"不推进"补齐。
- 提示词：有游标时在原文前插 `[上次看到这里] <ISO>；这一轮只看这之后的新内容。`（首次运行没有）。
- 手动 `run_now` 不推进（试跑不是"看过了"）。
- 开关沿用 `ROUTINE_QUIET`（关 = 不读不写游标）。

## 已知边界 / 没做

- **§一 只改审批**：`readOnlyBlockReason()` 仍读 `WRITE_TOOLS`（能力边界与审批正交，改它就不是零行为变更）。
- **后台任务不跨进程接管**：#5 的"跨进程续跑 / output 落任务单"仍未做，重启后旧 running 只能看不能杀；
  `ends.at` 已过时，排在它之前的在飞闹钟仍会响一次。
- **`if` 的判定是模型自报**：没配模型 / 401 / 超时一律跳过（fail-closed）；用 faux 时带 `if` 的规则永远不跑。
- **游标的"读失败"**：宿主只认 run 终态；模型内部读失败却回了 `[[no-update]]` 这一层区分不了（模型自报不是宿主事实）。
- **键控基线**：只在任务专线里生效；首次写入时 `plan.json` 可能还没生成，`writes` 为空；
  还原只看"块在不在"，被压缩改写过的正文不会重写（避免刷屏）；并发写入理论上可能出现重复块（按单串行队列已覆盖主路径）。
- 不改 `shared`、不改 chancellor、不做无关重构。
