## 为什么

用户口径：「主管的对话太多了……随着我们使用越来越多，以后检索肯定有问题，应该按天存。
往上滑加载时，按照每天加载，往上滑一段就加载当天的一段，避免主管说的话过多。」

实际病因不只是界面显示多：`readTranscript()` 每次把整段活跃上下文读进内存再切最后 N 条，
对话越长每次打开越慢；界面上也没有"往上滑看更早"。

## 口径

- **不按天拆存储**：主管会话必须保持连续上下文（模型、派活、记忆、搜索都挂在同一条会话上）；
  按天是显示层。存储已有时间戳与 `(conversation_id, id DESC)` 索引，durable 自带 cursor 分页。
- **一页 = 最多 `limit` 条（默认 50）**，最小单位是"轮"（`pi.user` 开头）；累计 ≥20 条后
  优先在自然日边界收页，一天特别长就当天分段。日期条由前端按 `at` 用**本地**日历日渲染。
- **游标不透明**：AES-256-GCM 加密 `{会话 uuid, entry 上界}`，key 由 `AGENT_TOKEN` 派生；
  跨会话 / 被改 / 换过令牌 → 400，客户端提示刷新，不重试。
- **活跃上下文语义不变**：分页倒扫遇到最新 `head` 标记（reset/压缩）就停，与 `readTranscript`
  的 `context()` 同口径；压缩前的旧段不会因为翻历史又冒出来。
- **旧契约零改动**：不带 `page`/`before` 时 `limit`（含 `limit=0` 全量）与 `sinceSeq` 补帧逐字不变；
  手机端仍发 `?limit=N`，Kotlin 零改动。

## 验证

- `pnpm --filter @lifediary/server typecheck`：全绿（2026-11-13 复跑）。
- `pnpm --filter @lifediary/server test`：**841 项全绿**；本批新增 7 项与 shared 契约快照都过。
- `pnpm --filter @lifediary/server http`：新增 §8.1 8 项全过——
  第一页 ≤ limit 且从 user 开头、`hasMore`/`nextBefore` 配套、逐页翻完与全量逐条一致
  （10 vs 10）、最后一页终止、非法游标 400、跨会话游标 400、`limit=0` 分页 400、
  不带分页参数时响应没有 `hasMore`/`nextBefore`。同场 1 项失败「系统提示带项目根路径」
  属并行会话的多根改动（提示词里的 `根路径：` 格式变了），非本批。
- 浏览器实测（隔离实例 39860 + faux，18 轮对话按时间戳铺到 3 天）：
  - 打开总管对话：首屏 **24 条**（今天 12 + 昨天 12），日期条「昨天」「今天」，右上"加载更早"可见；
  - 触发向上翻页：**24 → 36 条**，日期条变成「11月11日 / 昨天 / 今天」，出现
    「没有更早的记录了」，`scrollTop` 从 0 恢复到 **856**（原高度差 850）——视口没被跳走；
  - 用户消息 18 条唯一、无重复，首条「第 1 轮」、末条「第 18 轮」；
  - 回滚开关 `CHAT_HISTORY_PAGING_ENABLED=false`：一次拉 **36 条**、**0 条日期条**、
    没有顶部条，首条从「第 1 轮」开始（旧形态）。
- **没验的**：真实滚轮手势（IAB `cua.scroll` 超时）；用 `dispatchEvent(new Event("scroll"))`
  验证了同一条监听路径（监听器不看 `isTrusted`）。日期条的"今天/昨天"按本机时区算，
  跨时区设备未验。没跑 `pnpm probe`（本批不碰内核提交/流式/闸门语义）。

## 已知边界

- 检索仍只覆盖每个会话**最近 200 条**（`searchTranscripts` / `recall_sessions`）；更早的搜不到
  是独立缺口，另立一批。`session-search.ts` 的显式搜索页仍是全量扫描。
- 服务端重启且 `AGENT_TOKEN` 变过时，正在打开的长页面里旧游标会 400；界面提示刷新，
  不会自动重载（避免打断正在流的回复）。
- 压缩/重置之前的旧消息不在活跃上下文里，翻历史也翻不到——既有口径，本批不改变。
- 一页的 DOM 量最多约 50 条消息；更大的会话若滚动仍卡，再考虑虚拟列表（未做）。
