# 长记忆拆分与原文档案（记忆原子化）· 2026-11-16

**承接**：`docs/设计方案/2026-11-16-记忆整理与原子拆分（调查）.md`（用户拍板路线 B：两层存储；迁移预览后一次确认；项目 changelog 仍进项目记忆但特殊处理）。
**状态**：已落地并执行真实库迁移；未提交。

## 为什么

2026-11-16 实测 `.data/memory.db`：

| 项 | 实测 |
|---|---|
| 总条数 / 总字数 | 268 条 / 175,141 字 |
| 导入条目 | 193 条（占 98% 字数） |
| ≥1000 字 | 84 条（全部是导入） |
| Agent 自己写的 | 75 条，平均 39 字 |

根因不是记忆四层，而是导入：`memory-import-sources.ts` 在文件有正文时把整篇正文当一条记忆，
frontmatter 的 `description` 只在正文为空时兜底。ZCode 记忆文件 234/234 都有 `description`
（平均 70.7 字），正文平均 1,857 字；已导入的 154 条里 131 条能对上源文件，摘要合计仅 8,528 字
（原导入 163,076 字，约 19 倍压缩）。另有 63 个文件因正文 >2,000 字被整份跳过。

召回预算 16 条 / 2,000 字，一条 951 字的 fact 就吃掉近一半，库里有货但装不进去。

## 改了什么

### 1. 数据模型（`packages/memory`）

- 新增 `memory_documents`：`{id, scope, title, content, source, source_ref, sha256, chars, created_at, updated_at}`；
  原文默认**不进召回**。
- `memories` 新增列：`doc_id / quote / quote_start / quote_end / archived_at`。
  - `doc_id + quote` = 原子事实回指原文与逐字依据；
  - `archived_at` 非空 = 已归档/已拆，退出召回与默认列表（不删除）。
- `MemoryRecord` / `MemoryDocument` 类型、`SearchFilter`（`includeArchived / minChars / maxChars`）、
  `MemoryStore`（文档四方法）、SQLite 与内存两套 store、`engine`（`archive` / `putDocument` /
  `listDocuments` / `countDocuments` / `importItemsToScope`）同步补齐。
- 落盘沿用 `ensureColumns()` 补列模式：老库启动即补列，不引入迁移框架。

### 2. 拆分引擎（`apps/server/src/memory-split.ts`）

- 只处理 **≥200 字**、未归档、未带 `docId` 的 `fact / episode / preference / entity`；
  `work / impression` 不拆。
- 有 ZCode 源文件：frontmatter `description` 当原子（<20 字或只有日期时用正文前 3 段）；
  完整文件（含 frontmatter）进原文档案；`preference` 把 `Why / How to apply` 并进第一条原子（≤400 字）。
- 没有源文件：记录正文按句号/问号/分号/换行拆成 ≤200 字（preference ≤400）的原子；
  超长句按字数硬切，英文优先在空格处断开（避免 `order domain,` 这种碎片）。
- `quote` 必须是原文逐字子串；原记录 `archivedAt` + 文档 `docId`；已归档/已带 `docId` 的记录不再进候选（幂等）。
- 迁移脚本 `scripts/memory-split.ts`：默认 dry-run，`--apply` 前用 `VACUUM INTO` 生成备份；
  `--scope all` 遍历 global / partner / project。

### 3. 接口（`memory-api.ts`）

新增：

| 端点 | 说明 |
|---|---|
| `GET /api/v1/agent/memory/split/candidates?scope=` | 拆分预览 `{ok, scope, scanned, unmatched, total, items[]}` |
| `POST /api/v1/agent/memory/split/apply` | `{scope, ids?}`；不传 ids = 全部候选，空数组 = 一条不拆 |
| `GET /api/v1/agent/memory/documents?scope=&limit=&offset=` | 原文档案列表（不带正文） |
| `GET /api/v1/agent/memory/documents/:id` | 读一份原文（含 content） |

`GET /agent/memory` 新增能力位 `canSplit`；`items[]` 新增 `docId / quote / archivedAt`。
`MEMORY_SPLIT=false` → 拆分两端点 404。

### 4. 导入改口径（`memory-import-sources.ts`）

- 文件有 frontmatter `description` 且无 splitter 时：`text = description`，完整文件进 `memory_documents`；
  `preference` 附带 `Why / How`（≤400 字）。
- 没有 `description` 的来源保持原切分；`MEMORY_IMPORT_ATOMIC=false` 逐字节回到旧行为。
- `IMPORT_MAX_CHARS=2000` 只限制摘要，不限制文档（文档受 `MAX_SOURCE_BYTES=2MB` 保护）。

### 5. 前端（`web/memory-page.js` / `memory-items.js` / `style-21-answer-memory.css`）

- 原「整理记忆」拆成两个手动动作：**「拆分记忆」**（长文拆原子）和 **「整理」**（只做多条之间的重复/过时，路径仍 `consolidate`）。
- 拆分弹窗：候选列表（标题 / kind / 字数 / 原子数 / 样例）、勾选、一次确认「开始拆分」；
  无候选时直接说"这个范围没有超过 200 字的长记忆"。
- 记忆页新增 **「原文档案」折叠块**：标题 / 字数 / 来源 / 文件名；点开弹层读正文（阅读时剥掉 frontmatter）。
- 原子条目（有 `docId`）右上角新增 **「看原文」** 图标。

### 6. 每晚任务合并：拆分 + 整理（同日追加）

用户口径：每个执事都有自己的定时任务，总管也有；整理和拆分合并成一个每晚动作。

- `memory-nightly.ts` 每个 scope 现在跑三步：**① 机械拆分**（≥200 字 → 原子 + 原文档案，无模型、幂等、无损）
  → **② 确定性审计**（`runConsolidatePass`，只写 diff）→ **③ 语义整理**（`startReview`，只出建议，D18 不变）。
- 没有可用模型时：拆分和审计照跑，整理安静跳过（不报失败）。
- 范围仍是 `global`（总管 + 我的记忆）+ 每个在职执事 `partner:<id>`；总管没有独立 scope。
  项目 scope 不在每晚任务里（导入时已原子化；需要时在项目 tab 手动「拆分记忆」）。
- 新增 `MEMORY_NIGHTLY_SPLIT`（默认开，`false` 当晚只整理不拆）。
- 每晚状态文件 `memory-nightly.json` 的 `lastScopes[]` 增加可选 `split:{documents,atoms,archived,skipped,failed}`；
  老页面忽略即可。

### 6.1 成本与上下文：拆分是代码，整理才用 LLM

| 步骤 | 机制 | 调模型 | 成本 | 占当前对话上下文 |
|---|---|---|---|---|
| 拆分 | 代码：frontmatter `description` / 正文按句切；写原文档案 | 否 | **0 token** | 否 |
| 确定性审计 | 代码：规范化全等 / 90 天未用等 | 否 | **0 token** | 否 |
| 整理建议 | 辅助模型**独立请求**（≤200 条 × 300 字，输出 ≤2000 token） | 是 | 每个 scope 每晚一次；`AUX_MODEL_REVIEW` 可 pin 便宜模型 | **否**（不读主对话历史，也不写回主上下文） |

- 每晚任务 = 拆分 + 审计 + 整理建议；只有第三步用模型。没有可用模型时前两步照跑，第三步安静跳过。
- `MEMORY_CONSOLIDATE_LLM=false` 只关第三步；`MEMORY_NIGHTLY_SPLIT=false` 只关第一步。
- **LLM 拆分的定位**：智能拆分是**手动可选**动作，不进每晚任务。它能更好地提炼多条主张、处理无摘要的长叙事，
  但每条要一次模型调用、要引文校验、要人确认；成本与风险都比代码拆高。
- 不做：智能拆分自动应用（永远先预览）、批量超过 12 条、把原文全文喂给模型（只喂前 6000 字）。

### 8. 智能拆分（同日追加：用模型拆，手动、可选模型、先预览）

用户口径：记忆本来就是 LLM 总结出来的，长短、质量、结构都不稳定；有些（没有摘要、特别长、写得乱、
一条里混好几件事）用模型拆更好。但**不能塞进主对话**——又贵又慢、还多一轮、污染当前上下文。

- 新增 `apps/server/src/memory-split-smart.ts`：`runSmartSplit`（只出候选）+ `applySmartSplit`（确认后落库）。
- **调用方式**：`completeSimple` 的独立一次性请求（与整理建议同一套先例），
  **不读对话历史、不写回主上下文**，只消耗所选模型的额度；用途枚举加 `split`，
  可用 `AUX_MODEL_SPLIT` pin 默认模型。
- **提示词**：一条长记忆一次调用，输入最多 6000 字；要求输出 `{atoms:[{content, quote}]}`，
  最多 20 条、content ≤200 字（preference ≤400），**quote 必须从原文逐字复制**。
- **机械校验（服务端）**：`locateQuote` 归一化后必须能在原文找到（空白折叠容错，不做同义替换）；
  找不到引文、超长、重复、过短的原子直接丢弃；一条都不剩 = 该条失败，不写半截。
- **落库**：与代码拆分同一套落点（原文进 `memory_documents`、原子带 `docId + quote`、原记录归档），
  应用前再校验一次引文（防前端篡改）。
- **一次最多 12 条**（`MAX_SMART_SPLIT_RECORDS`）：防手滑点一下打几十次模型。
- **不进每晚任务**：只有手动按钮；每晚仍是"代码拆分 + 审计 + 整理建议"。

接口（`memory-api.ts`）：

| 端点 | 说明 |
|---|---|
| `POST /api/v1/agent/memory/split/smart` | body `{scope, ids?, model?:{provider,modelId}}`；只出候选，不写库。返回 `{ok, model, calls, candidates, records:[{recordId,title,kind,chars,atoms:[{content,quote}],dropped,error?}]}`。模型不可用 → 503 `llm_not_configured` |
| `POST /api/v1/agent/memory/split/smart/apply` | body `{scope, records}`；按预览结果落库，引文二次校验 |

前端（`memory-items.js`）：右上角**仍是三个按钮**，没有新增入口。
「拆分记忆」弹窗里加模式切换：

- **代码拆分**（默认）：文案标"不调模型、不花 token"；
- **智能拆分**：展开模型下拉（选项来自 `GET /agent/model`，只列有 key 的供应商，默认选中当前模型），
  按钮变成「智能拆分选中 N 条」，旁边提示"每条调用一次模型（独立请求，不占当前对话上下文），会消耗 token"；
- 点下去先出**预览**：每条长记忆 → 它拆出的原子 + 引文；确认后按钮变「应用这批拆分」。

### 9. 环境变量与回滚

| 开关 | 默认 | 回滚 |
|---|---|---|
| `MEMORY_SPLIT` | 开 | `false/0/off` → 拆分端点 404、前端不渲染「拆分记忆」；已拆出的原子/档案不自动回滚 |
| `MEMORY_IMPORT_ATOMIC` | 开 | `false/0/off` → 新导入回到"正文整篇当记忆、不建文档" |
| `MEMORY_NIGHTLY_SPLIT` | 开 | `false/0/off` → 每晚只整理、不拆；拆分端点仍可手动用 |
| `AUX_MODEL_SPLIT` | 未配置 | 智能拆分的默认模型（`auxiliary.ts` 的 `split` 用途）；不配 = 用当前模型。前端下拉里选的模型优先于它 |
| 回到迁移前 | — | 恢复 `.data/memory.db.bak-split-<时间戳>`（`VACUUM INTO` 一致性快照） |

## 刻意没有

- 不做语义提炼/摘要重写：拆分是机械的"摘要或短句 + 原文档案"，不判断哪条更重要。
- 不自动应用拆分：预览后一次确认；没有"整库一键拆分"以外的自动动作。
- 不删原记录、不删原文档案：归档可查，原文只读。
- 不做事件 / 实体 / 张力对层；不引入向量召回/LLM 重排。
- 不改原生 `remember` / 抽取链路（实测原生平均 39 字，已经原子）。
- 不把长文写进 persona.db；`persona_recall` 仍是"一生库"的只读入口。

## 已知边界

- `description` 本身可能是多句，一条原子仍可能 200–400 字（preference 上限 400）。
- 没有源文件的记录用正文拆，质量低于有 `description` 的（17 条走 fallback）。
- 原文档案只读、不提供删除；文档存整份文件（含 frontmatter，逐字引文偏移依赖它），
  界面阅读时剥掉 frontmatter。
- session scope 的旧长记录（UI 不展示）不在这次迁移范围内；它们的 `archivedAt` 仍为空。
- 全量测试中的无关失败见上；本次改动范围内的测试全绿。
- 同日另加 `persona_memory` 技能（个人长期记忆库检索说明书），见
  `docs/变更记录/2026-11-16-个人长期记忆检索技能（persona_memory）.md`；与本批的原子记忆是两套入口：
  原子记忆是 Agent 的热记忆，persona 是只读的长期库。
