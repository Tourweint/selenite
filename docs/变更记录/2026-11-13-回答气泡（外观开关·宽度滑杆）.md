## 为什么

用户原话：「现在助手回答我的消息应该长啥样，对吧？因为这个咱们应该在设置里保证它能改。现在它没有聊天气泡，但咱们有。可以加一个有聊天气泡的情况，还能改聊天气泡的宽度。」

## 口径（2026-11-13 定，后续按这三条走）

- **气泡只包 `.body`（他说的话）**。工具灰块 `.tchips-wrap` 是 `.flow` 里的兄弟节点，天然留在泡外；
  气泡的语义是「一条消息」，灰块是「他做了什么」，混进去流式时会被新灰块忽高忽低地撑开。
  所以「工具调用怎么选」的答案是**不选**——它从来不进气泡。
- **宽度只作用于助手这侧**（60–92%，默认 80%）。用户气泡的 480px 不动：用户打的短句跟着 80% 走会变成一面墙。
- `width: fit-content` + `max-width`：短回答收成窄泡，长回答到上限才折行，不是一律拉满。
- 只走前端、只落 localStorage，不进服务端开关、不动 `shared` 契约。

## 验证

- `node --check bubble-mode.js` 通过。
- 三档对照（真实 `style.css`，对话列 918 / 内容列 874）：80% 上限 699px、60% 上限 524px 确实生效；
  短段被 fit-content 自己收在 574 / 442，属于预期（宽度是上限，不是固定宽度）。
- 本地静态服务真点开关一次：`aria-checked` 变 true、宽度滑杆解锁并可拖、`<html>` 上出现
  `data-answer-bubble="1"`、两段话各自成泡且工具块位置留在泡外。截图已随临时测试页删除。
- **没验的**：产品整页（`web/app.js` 当时仍被另一个会话改，不往真实会话里塞测试消息）；
  流式过程中气泡逐字生长的观感、以及 E1 灰块与气泡混排的最终间距，都要等 E1 接线后一起看。

## 已知边界

- 「回答」这一节现在由 `bubble-mode.js` 用 MutationObserver 挂进 `#settings-inner`（只盯设置容器、
  只盯 childList，不跟聊天流式抢回调）。等 `app.js` 那边收工，把这一节搬进 `renderSettings` 的
  appearance 分支、删掉模块与 `index.html` 那行 script 即可——行内结构用的就是 `.card / .row /
  .divider / .switch`，搬过去不用改样式。
- E1 灰块的 `.tchips*` 样式还在「待应用补丁」里没落地，气泡外那条工具行的最终间距等 E1 一起定。
- 窄泡里的宽表要在泡内横滚、长代码块同理：这是气泡模式的固有代价，不是这次引入的 bug。
