## 一、B3 设备活豁免项目前置

### 判别字段（先定位，以代码为准）

`delegate` 工具入参（`tools.ts` `delegate.parameters`）只有 `requirement` / `project` / `domain` /
`targetDevice` / `resume` / `requestId`，**没有 `worker` / 雇员类型字段**；`delegate-routing.ts` 判的是
"谁名义派、走不走分管宰相"，与执行体类型无关。代码里"执行体是设备 worker"由两处表达：

1. `targetDevice`（明确点名另一台设备）——`tools.ts` 远程分支在 `dispatchRemoteDelegation` 后
   `return`，**根本走不到项目前置**（既有注释「本机的项目前置不参与」），天然豁免；
   `"auto"` 挑不出 `fallbackToLocal` 时是本机执行，不算设备活。
2. chancellor 雇员档 `CHANCELLOR_EMPLOYEE=phone`（`chancellor/src/config.ts:9` 的
   `EMPLOYEE: WorkerKind`，`WorkerKind` 含 `"phone"`）——本机 chancellor 把活派给手机 worker，
   活去手机屏幕、不落本机磁盘（`plan.ts` 把 phone 单 `writes` 置空、`review.ts` 按汇报验收）。
   这条**会**走到 `resolveDelegationProject`，正是被 `needs_project` 硬拦的一条。

结论：判别落在 `tools.ts:isDeviceWorkerDelegation(args, env)`（纯函数，入参只看 `targetDevice`、
env 只看 `CHANCELLOR_EMPLOYEE`）。外部执行三档（`codebuddy` / `qoder-intl` / `qoder-cn`，
`2026-11-03-外部执行三档统一适配`）都是本机执行体，照旧要项目。

### 改了什么

- `tools.ts`：新增 `DELEGATION_DEVICE_PROJECT_EXEMPT`（`envFlag(..., true)`，读法与相邻
  `DELEGATION_PROJECT_REQUIRED` 一致）；前置处算 `deviceWork = deviceProjectExempt &&
  isDeviceWorkerDelegation(args)`，`if (projectRequired && !deviceWork)` 才进原来的
  `resolveDelegationProject` 分支。**豁免只放行前置**：设备活根本不进那一段，
  `resolveDelegationProject` 的 realpath / 工作区 / 符号链接复核一行未动，worktree/租约语义未动。
  设备活按无项目单受理（`project` 保持 `undefined`，`DelegationKickoff` 不带 `project`）。
- 工具 `description` 补一句事实口径（手机/设备活可省 `project`），避免模型对着
  「必须带 project」给设备活去 `propose_project`；**不做**项目"建议"提示。
- 回滚：`DELEGATION_DEVICE_PROJECT_EXEMPT=false` → 设备活也要 `project`，回到本批前行为。
- 探针：`src/projects.test.ts`（项目前置既有覆盖处）补三场景 + 判别纯函数断言，
  env-before-import 纪律照旧（`createTools` 调用那一刻读开关、`execute` 那一刻读雇员档，
  每档设后调、用完还原；回执/工作根指临时目录，不碰真实 `.data`）：
  - 设备活（phone worker）无项目 → 受理、真起单、单里不带 `project` ✓
  - 本机活（codebuddy）无项目 → 仍 `needs_project`、不起 worker ✓
  - 回滚开关关后设备活 → 也 `needs_project` ✓
  - 另钉死 `targetDevice` 明确点名 / `auto` 回落 / phone / codebuddy / native 五种判别。

## 二、relay 投影补 `dispatchAuthority`：**本批不硬塞，留后批**

上位方案 §三 原写「顺带做（一行投影 + 探针断言）」，任务书给的落点是
`/api/v1/relay/overview` 的"设备/执事段"。**2026-11-08 核对：该落点不存在，按任务书
"结构上放不进就不硬塞"留后批**。结构证据：

- `/api/v1/relay/overview`（`relay-mobile-proxy.ts:38-54`）返回
  `{enabled, connected, selfDeviceId, devices[], matrixEnabled, homeEnabled}`；`devices = client.devices`
  是**中继设备名册**（机器：`id` / `name` / `platform` / `online` / `capabilities`，另带
  `isHome` / `description`，见接口文档 §2.13 名册投影），**不认识执事 uuid**。正是任务书点名的
  "relay 名册根本不认识执事 id"。
- `dispatch_authority` 是本机 `partners.ts` 执事档案的列，对外投影**已存在**且只有一处：
  `GET /api/v1/partners`（`companion-api.ts:624`，只对带 `domain` 的执事给）+ shared
  `PartnerProfileSchema.dispatchAuthority`（`shared/src/index.ts:898`，2026-11-06 执事派发权开关落地）。
- `/api/v1/relay/home/overview` 的 `actors` 是**另一套命名空间**：`companion-homes.json` 里
  `actorId = randomUUID()`，`relay-home.ts:11-12` 明写「这是归属与路由的底座，不是执事本身……
  B 落地后把 `partners.actorId` 对到这里的路由表即可」——即执事档案与设备归属**现在没有 id 关联**；
  且该端点 `COMPANION_HOME_ENABLED` 默认关、默认 404。

结论：把 `dispatchAuthority` 挂到 `devices[]` 的机器条目上是挂错对象；要在 overview 里给执事开
一段则等于**新增一个投影面**（本机执事名单混进中继代理面），不是"补字段"，且没有
执事↔设备 id 关联时手机端也读不出"哪个执事在哪台机"。

**建议落点（后批，与执事管理面一起做）**：

1. 首选零新契约：手机执事管理面直接消费 `GET /api/v1/partners`（`dispatchAuthority` 已在投影里）。
2. 若确要塞进 `/api/v1/relay/overview`：等 `relay-home.ts:11-12` 的 `partners.actorId ↔
   actors.actorId` 关联落地后，新增**独立** `executors[]` 段（每项 `id` / `name` / `domain` /
   `dispatchAuthority` / 归属设备），同步改 shared schema、接口文档、手机消费端——那是跨仓契约，
   按 AGENTS.md 必须先写方案，不属本批"一行投影"。

本批**没有**改 relay 投影、没有加字段、没有改 shared；对应地接口文档 §2.13 不动。

## 四、明确不做 / 不确定点

- 不碰手机仓、不做手机 UI、不动 worktree/租约、不做设备活的项目"建议"提示（任务书"明确不做"）。
