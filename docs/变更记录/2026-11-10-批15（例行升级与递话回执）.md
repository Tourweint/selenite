## 一、触发器基线比较 + 边沿 + 冷却（#29）

- `partners.ts` 的 `RoutineTrigger` event 分支新增**可选** `baseline?: {key,delta}` /
  `edge?: true` / `cooldownSec?: number`；字段沿用 triggers JSON，不动表结构。
- `routine-conditions.ts` 新增纯函数 `evaluateTriggerGate()`：判定顺序
  **cooldown → edge → baseline → 原 match**，返回"是否触发 + 下一份门状态"。
  细节：冷却期内状态完全不动；edge 只认 false→true；baseline 首次记基线、之后
  `|变化| > delta` 才触发，观测值非有限数字直接不触发；只有真正触发时才写基线/冷却起点。
- `routines.ts` 的 `onExternalEvent` 接线：门状态按 `<规则id>:<触发器序号>` 落
  `routines.json` 的 `gates`；开关 `ROUTINE_TRIGGER_GATES`（默认开）关着时不读不写门状态。
- 已知边界：三件门只对 `event` 触发器生效（定时触发没有真假跃迁 / 观测值）。

## 二、brief / 日报卡三规则（#41）

- `agent/partner-context.ts` 新增常量 `BRIEF_CARD_RULES`（三条固定文案）与开关
  `BRIEF_CARD_RULES`；注入 `buildPartnerDisciplineSection()` 的普通执事分支。
- **总管不注入**：总管纪律段保持逐字节不变（界面时间线自承载），既有
  `prompt-discipline` / `partner-context` 的固定字节断言不被改写。
- 本批只落文案与纪律；推送时机 / 就地编辑的宿主实现不在本批。

## 三、run_source 触发来源列（#44）

- 新增 `run-source.ts`：`RunSource` 枚举、开关 `RUN_SOURCE`（默认开）、测试进程识别、
  派单来源判定（测试 > 设备 > 例行轮 > 人）。
- `delegation_receipts` 表加可空 `run_source`（旧库自动 `ALTER TABLE`）；`begin()` 接收来源，
  `lookupByTicket()` 读回；旧行 null → 详情投影视为 `human`。
- 来源落点：`delegate` 工具（例行轮 `routine` / 设备 `device` / 人 `human`）、
  HTTP 重试 `script`、设备矩阵受理 `device`。
- `routines.ts` 的 run 记录加可空 `runSource`：定时/事件 `routine`；`routine_manage` 自建规则
  的**首轮** `routine_self`（建规则时落一笔 `selfCreated`，首轮取走即清）；`run_now` `script`。
- 任务详情 `GET /api/v1/tickets/:id` 增加可选 `runSource`；没有回执 / 开关关着时不出现。

## 四、watch.json 单例交接（#47）

- `routine-conditions.ts` 新增纯决策 `planRoutineWatch()` / `releaseRoutineWatch()`；
  交接只记一次 `handedTo`，同一规则重复认领不重写文件。
- `routines.ts` 的 `runOnce` 入口 `claimWatch()`：新看护接手时旧规则
  `enabled=false`（revision+1 让在飞闹钟作废），**不删除**；账落
  `.data/routine-watch.json`（`ROUTINE_WATCH_PATH` 可改）。规则置停时从 `watches` 摘除。
- 用**当前**定义判断是否仍是看护，避免旧规则的迟到触发把看护抢回去。
- 开关 `ROUTINE_WATCH_SINGLETON`（默认开）关着 → 不读不写此文件。
- 已知边界：交接发生在"新的一轮开始前"，旧规则**已经在跑的那一轮**不会被打断；
  做不到严格意义上的"同一毫秒只有一个进程在跑"，保证的是"账上只有一个看护 + 旧的被停"。

## 五、执事递话两态回执（#30）

- `partner-relay.ts`：开关 `PARTNER_RELAY_RECEIPT`（默认开）；`relayDeliveredText()` 负责
  `queued` 文案（关着时逐字节等于旧文案）；`relaySettledText()` 生成一句话结果（≤160 字）；
  `relayOutcomeEntry()` 生成发送方 transcript 的 `pi.assistant` 留言；新增按会话的
  进程内通知口 `watchRelayReceipt()` / `emitRelayReceipt()`。
- `deliver` 注入函数签名增加发送方上下文；`agent/lifecycle.ts` 的 `deliverPartnerRelay()`
  提交成功后**不阻塞地**等待目标 submission 结算：读对方答案 → notice 回流到发送方
  正在流式的会话 → 发送方 transcript 写一条 `【留言】…`。
- `agent/session.ts` 订阅该通知口，复用既有 `relayNotices` 队列发 `notice` 帧。
- 仍为 hop=1；不做多跳、不做 bot_loop_guard（任务书明确不做）。
- 已知边界：发送方流已结束时 notice 收不到（进程内轻事件，与 8d 主人通知同一口径）；
  transcript 那条留言照写。
