## 一、契约（shared，唯一 schema 变更点）

`packages/shared/src/index.ts`：

- `ChatMessageSchema.content`：`z.string().min(1)` → **union** `z.union([z.string().min(1), z.array(ContentPartSchema).min(1)])`。
- `ContentPartSchema = z.union([TextPartSchema, ImagePartSchema])`：
  - `{ type:"text", text:string }`
  - `{ type:"image", mimeType:string, data:string }`（`data` = 裸 base64，不带 `data:` 前缀）
  - 两个 part 都是 `.strict()`；导出 `ContentPart` / `TextPart` / `ImagePart`。
- `TranscriptMessageSchema` 加两个可选字段：
  - `id?: string` —— 可寻址 messageId（见 §三）；
  - `images?: [{ mimeType, data }]`（`TranscriptImageSchema`，`.strict()`）。
- 新增纯函数 `chatContentText(content)`：多段文本用 `\n` 连（与 pi-ai `contentText` 同口径），
  给 openai-compat / 记忆抽取这类"只要文字"的调用方复用。
- `snapshot.test.ts`：`shapeOf` 支持 `ZodUnion` / `ZodDiscriminatedUnion` / `ZodLiteral`，
  内联快照同步成 union 新形状。

**旧 string 全兼容**：手机、OpenAI 兼容层、旧脚本不带分段，走原分支逐字节不变。

## 二、服务端

### 附件判定 / 拼装（新文件 `src/attachments.ts`，纯函数）

- `assembleUserContent(content) → { text, parts?, imageCount } | { ok:false, message }`：
  - 纯字符串原样返回（不二次 trim）→ 提交仍是字符串；
  - 分段数组：文本 parts 按顺序 `\n` 连成 `text`（全空白视同没有文本）；图片逐张复核
    mimeType 前缀（`image/`）、base64 形状、解码后体积；超过 4 张 / 单张 >8MB / 既无文本
    又无图 → 失败文案（路由回 400 带 message）；
  - 有图才产出 `parts`（`[{type:"text",text}?, ...images]`），纯图消息 `text` 为空串。
- `base64Bytes(data)`：只算长度不真解码（8MB 口径够用）。
- 两个开关：`attachmentsEnabled()` / `editResendEnabled()`，**只有显式 `false` 才关**（默认开）。

### `POST /api/v1/agent/chat`（`index.ts`）

- 解析后先算 `assembleUserContent(最后一条 user.content)`；`AGENT_ATTACHMENTS=false` 时
  **分段请求** `400 attachments_disabled`（纯字符串照常）。
- `chatStream` 入参新增 `parts?`；`agent.ts` 的 `submit` 改为 `content: input.parts ?? input.text`
  （内核原生收 `string | (TextContent|ImageContent)[]`）。
- 记忆/日志仍用 `text`（图片不进记忆）；`streamMock` 收纯文本参数。
- 收尾动作抽成 `turnSettledHandler(chat, messages)`（观察层 + 记忆抽取 + 会话记忆修剪），
  `/chat` 与 `/edit` 共用一份。

### `POST /api/v1/agent/chat/:conversationId/edit`（新端点）

- 校验：会话存在；`pi.live.run` 在跑 → **409 conversation_busy**；`messageId` 属于本会话且是
  `pi.user` → 否则 **400 message_not_found**；`text` 非空否则 400。
- **fork 语义**：durable 的 fork 上界是 `id <= at`（含该条目），所以传目标条目的**前一条**
  (`Conversation.fork(at, …)`);编辑第一条时没有"之前"，开一个同模型、同种类的新会话。
- 新会话在同一事务里写 `lifediary.chats`（uuid ↔ 内部 id）与 `lifediary.chat-kinds`（种类），
  与 `openChat` 新建分支同口径。
- 提交走 `chatStream` 主链路（后台消费整条流）：用量、记忆 onSettled、内存注入全继承；
  端点立即回 `202 {ok:true, conversationId}`。老会话原样保留（列表里多一条旧会话，方案登记）。
- 回滚 `AGENT_EDIT_RESEND=false` → 端点 404。
- `readTranscript`：user 消息加 `id`（`messageIdOf`）与 `images`；**纯图消息不再被丢掉**
  （原来 `!text` 会 continue）。

### messageId 的口径（与硬约束"对外 id 一律 uuid"对齐）

- `messageIdOf(externalId, entryId) = sha256("${externalId}:${entryId}")` 切成 uuid 形状。
- **不下发 durable 内部自增条目 id**；读历史时按同一函数重算，编辑时反查匹配。
  代价：每次编辑多扫一遍 active entries（一次 `context()`，已有）。

### policy 投影

- `GET /api/v1/agent/policy` 增加 `attachments` / `editResend`（只读，源自 env）；
- `POST` 响应仍不含 `label`，额外带这两个字段（形状与 GET 一致的那两项）。

### 全部数据导出

- `GET /api/v1/agent/export` 的 `messages[]` 增加可选 `images`（同 §2.2 形状）：
  导出是"全部数据"，不能把附件悄悄丢掉（体积随图片增长，用户主动下载）。

## 三、前端（web/）

- composer 附件：`#composer-add` 接真（文件选择器 `#composer-file`）+ 输入框**粘贴** +
  composer **拖拽**；待发缩略条 `#composer-attachments`，单张可移除；只收图片、
  前端先挡 8MB / 4 张，服务端仍全量复核。
- 发送：有图才用 `content: [text?, image…]`，纯文本仍是 `messages[].content: string`；
  纯图消息可发（发送按钮的空判算上附件）。忙时（排队/插话）不带图，提示等这一轮结束。
- 回读：user 消息 `images` 渲染缩略图（`.msg-images`），点击开原生 lightbox（`#lightbox`，
  点任意处 / Esc 关闭）。
- 编辑重发：**最后一条** user 消息 hover「编辑」→ 行内 textarea（Ctrl/⌘+Enter 提交）→
  `POST .../edit` → 用返回的新 id `openConversation()` 切换 → 轮询 `GET .../messages`
  直到新一轮回答落库，再整屏重读（`waitEditedTurn`，窗口 90s；期间按钮是停止）。
- 现场刚发出的消息没有 messageId（SSE 未动）：点编辑时按"从末尾对齐"拉一次历史补齐
  （`resolveMessageId`）。
- 能力开关：启动时 `GET /agent/policy`，`attachments=false` 隐藏附件按钮、`editResend=false`
  不渲染编辑入口（`loadCapabilities`）。
- 样式：沿用现有 token / 圆角 / 过渡，不引第三方库。

## 五、偏差 / 不确定（照任务书要求写明）

1. **"流式响应在新会话上收" 的实现形态**：方案 §二写编辑端点回 `202 {ok:true, conversationId}`
   并"流式响应在新会话上收"。按 202 JSON 的契约，编辑那条请求本身不返回 SSE；新会话的生成在
   服务端后台跑完并落库。前端因此用 `openConversation(新id)` + **轮询回读**补齐回答
   （不是逐字流式）。要真正逐字，需要客户端在 202 之后再挂到同一条提交上，而那需要
   编辑 body 多带 `requestId`（契约新增）——本批按"契约语义以方案为界"没有加。
2. **任务书 §4④ 的措辞**：「新会话 transcript 首条 user 是新文本且分叉点之前的历史完整」
   在"编辑最后一条"时两者不能同时成立（第一条 user 是更早的历史）。探针两种都测了：
   编辑最后一条 → 旧历史完整 + 末条 user 是新文本；编辑第一条 → 首条 user 是新文本。
3. **messageId 用哈希而非条目 id**：方案原话是"回读帧/GET messages 的 message id 已存在"，
   实际 2026-11-08 核对**并不存在**。为守住"对外 id 一律 uuid、内部自增整数不外泄"，
   加了可选 `id` 并由 `(会话 uuid, 条目 id)` 哈希；若将来要"从任意条目 fork"，同一函数可复用。
4. **编辑执事专线会话**：新会话按 `chief|worker` 落 `chat-kinds`（`partner` 是链接表判定，
   克隆不出链接），会变成一个带着执事人格的总管会话。前端编辑入口目前对所有 user 消息一视同仁，
   未做特殊屏蔽；个人使用场景下不常见，登记在案。
5. **纯图消息的编辑**：编辑端点只收 `text`，所以纯图消息没有可编辑的文本（前端保存空内容被挡）。
   方案未要求"改图"，本批不做。
