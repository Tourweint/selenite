# 2026-10-30 · X-Task 任务通道（prompt 模板上移）

## 背景

"对话正文归位 harness、手机只留索引"（App 仓库 `docs/设计方案/2026-10-29-对话正文归位Harness（手机只留索引）.md`）
的前提是**日记任务的对话也要在 harness 落库**。现状做不到：日记任务（收敛 / 周报 / 分段 / 题目 / 回忆）
由 App 把整份 prompt 塞进 `system` 走**直通**路径 —— 直通不建会话，那段对话过完即弃。
设计文档 §4 选方案 A：模板上移，客户端只报任务名，服务端渲染模板并走 Agent 会话。

本轮范围 = 设计文档 §5 **阶段 1（harness 侧）**。App 侧切换（4 处调用点改发 `X-Task`）**不在本轮**，
原因见文末"未执行项"。

## 决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 任务模板存成 `apps/server/prompts/<name>_v<N>.md`，**与 App 资产同名同字节** | 让"上移"不改一个字：黄金用例可以直接断言字节相等，回退 = 改一张表 |
| 2 | 变量走请求体 `task_vars`，不塞进 `system` | 客户端再发一份渲染好的 `system` 就等于模板没上移；变量动辄几 KB，头/URL 放不下 |
| 3 | 渲染后的模板写进会话 `instructions`（durable 持久化），输入仍是那句固定指令 | 重启后任务会话照样拿着同一份 prompt；transcript 里留的是人话，回读才有意义 |
| 4 | 任务会话**摘掉我们的扩展 + `tools: []`** | 无人格、无记忆注入（收敛把记忆当事实写进草稿是真事故，日记收敛与记忆 §4）、无工具（它只产出文本） |
| 5 | 参数透传用**派生模型 id**（`<model>#t..m..r<hash>`，参数挂 `samplingParams`） | pi-durable 的 `configure()` 只认 `ModelRef`，没有 per-request 参数口子；pi-ai 会把 `samplingParams` 原样合并并**最后写入**请求体 |
| 6 | 缺变量 → 500 且**先渲染再开会话** | App 的 `render` 漏注入会留下 `{{x}}` 进模型（不报错、难排查）；先渲染保证失败时不留半条会话 |
| 7 | 未知任务 → 400 `unknown_task` | 明确错误码优于"当成通用聊天"（后者会静默把模板丢掉） |

## 影响范围

- **通用聊天（无 `X-Task`）行为未变**：仍走快/深档判定、人格、记忆与工具（探针 §4 有回归断言）。
- **直通路径未变**：不带 `X-Task` 就还是老路（App 现在正走这条，切过去之前不会受影响）。
- 任务通道的会话会出现在 `GET /api/v1/agent/chats` 里（"任务会话要不要进列表"仍是待议项，见设计文档 §9.2）；
  客户端若在意，可后加标记过滤。
- 派生模型只存在于进程内存里：任务会话若在**重启后**被继续追问，`<model>#t..` 这个 id 可能不在目录中
  （同参数再来一次会重建）。一次性任务不受影响；如实登记。

## 未执行项

1. **App 侧切换**：`core:ai`/`feature` 的 6 处任务调用仍按旧直通方式发（带 `system`）。切换要动 App 的
   `LlmRequest`（加 `task` / `taskVars`）与 4 个调用点，并逐任务上真机对照成稿质量；本轮按设计文档 §5 只做 harness 侧，
   探针已把契约钉死，App 改完即可对接。
2. **真实上游的逐字对照**：本轮用假上游验参数与模板；真模型下的输出对照（第一人称、JSON 结构、长度约束）
   需要 `LLM_API_KEY`，未跑。
3. **任务会话不进会话列表**：仍是设计文档 §9.2 的待议项，本轮未做标记过滤。
4. **派生模型的持久化**：重启后若继续追问同一个任务会话，需同参数重发才会重建模型 id。

## 补记（2026-10-30 深夜，真实上游联调）

接上真实 `DASHSCOPE_API_KEY` 后，四个任务全部返回「这次没能生成回复，请再试一次。」——
日志里是上游 `404 model_not_found`，模型名赫然是 `qwen-plus#t0.4m4000r-`：

**根因**：派生模型把参数编进 `id`，而 `id` 会被 pi-ai 当成请求体里的 `model` 发给上游。
探针没抓到，是因为断言写的是 `startsWith("fake-deep")`，带后缀的 id 也满足。

**修法**：在派生模型的 `samplingParams` 里补一行 `model: <基础模型 id>`——pi-ai 把 `samplingParams`
**最后** `Object.assign` 进请求体（`openai-completions.js:752`），所以正好盖掉。
`id` 仍保留派生后缀（模型目录里需要唯一键），只是不再外泄给上游。

**回归**：探针断言改成**全等** `model === "fake-deep"`；`pnpm typecheck` 与 `pnpm --filter @lifediary/server tasks` 全绿。
真实模型下四条任务的输出与 App 现版直通逐条对照（模板/变量/采样参数都相同），结构与质量等价。

**教训**：假上游能验"参数到没到"，验不了"名字对不对"——凡是会被原样转发的字段，断言都要用全等而不是前缀。
"真实上游的逐字对照"自此由本补记兑现，但**App 侧仍未切 `X-Task`**（未执行项 1 依然成立）。

## 补记 2（2026-10-31，客户端接上之后才暴露的两件事）

App 切到 `X-Task` 之后，模拟器联调暴露了两个只有"真有人在用"才会出现的问题：

1. **同一个任务的多次调用挤进同一条会话**：任务会话沿用了 Agent 路径的"首条 user 内容哈希"推导，
   而任务的固定输入恒为「请整理成稿」——于是三次收敛滚进同一条 `oa-186099d…`，
   历史越滚越长（正是当初"模板任务共用会话、逐轮涨 token"那个病的复发）。
   修法：任务通道**默认一次调用一个 `task-<uuid>` 会话**，要续跑必须显式带 `X-Conversation-Id`。
2. **任务会话混进"历史对话"列表**：首句是"请整理成稿""请按上面的格式只输出 JSON"，对用户毫无意义。
   修法：`GET /api/v1/agent/chats` 过滤 `task-` 前缀；正文仍可按 id 回读。

探针新增 §7 钉住这两条（两次调用 → 两个不同 `task-` id、列表 0 条任务会话、任务会话仍可回读）。

**更正（2026-10-31 深夜，查库后推翻当天早些时候的结论）**：一度以为"pi-durable 把会话钉在创建时的模型上"，
**这是错的**——`applyChatMode` 每轮都会比对 `agent.model.modelId` 并 `configure()`，日志 `[agent] 会话 N 切档 → fast（qwen-flash）`
就是它在换模型，档位每轮可换（这也是 2026-10-29 就确认过的）。

真实原因是**历史污染**：库里 `entries.id=184` 那条记录写得清清楚楚——
`provider: "bailian", model: "qwen-flash"`（真实模型在答），`content` 却是「（faux 模型）链路已通。」
因为这条会话的 transcript 里堆着十几条 faux 时期的同款回复，模型照着历史说话（`input: 1553 tokens`）。
换句话说：**复用会话 = 共享上下文（这是设计如此），代价是历史里有什么，模型就会跟着学什么**。
所以老会话"越用越怪"时，正确动作是**换一条干净会话**，而不是怀疑模型没切。

> 复现命令（留档）：`X-Conversation-Id: oa-ce2f2801…` + 任意一句 → 秒回「（faux 模型）链路已通。」；
> 换一个全新 id → 正常真实回复。对照实验还发现：短对话里复用会话**不一定**串味
> （同一会话第二次收敛"晚上去江边跑步"，输出干净、没混进第一次的"方案/会议室"），
> 所以"每次新会话"是**默认干净**，不是"不复用就一定出错"。

## 回滚建议

`X-Task` 是**新增头**：客户端不发时行为与改动前完全一致（直通/通用聊天两条路未动）。
需要回滚时删掉 `mountOpenAiCompat` 里的 `X-Task` 分支即可，模板文件与派生模型机制不影响其它路径。
