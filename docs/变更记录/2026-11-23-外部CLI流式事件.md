## 事件模型与落点

- 统一事件：`{ type: "tool" | "status" | "text", name?, detail?, failed?, at }`；`detail` 只放文件名 / 命令 / 失败原因摘要，**不放工具结果全文、不放思考过程**。
- 落点一：任务目录 `<ticket>/<seq>-<slug>/steps.jsonl`（追加，按需查；重试 / 续跑开头清掉上一轮）。
- 落点二：`ChancellorEvent.step` → 服务端 translate 成既有 `delegate` 事件（`phase=running`，`current/lastAction` = 步骤一句话）→ 任务中心「最近动作」；同时 `progressOfEvent` 把它落进 `ticket.json.lastAction`，详情 / 列表轮询可读。
- **没进**：主管 / 执事 / 用户模型上下文、任务专线（不 mirror）、`requirement`、系统提示、自动总结。结果回写只多一行统计，例如 `（过程：读了 3 个文件、跑了 1 条命令、改了 2 个文件；1 次失败）`。
- 回滚：`CHANCELLOR_CLI_STREAM_EVENTS=false/0/off` 同时关掉采集、`steps.jsonl`、UI 步骤与统计行；Claude 退回 `--output-format json`。

## 已知边界 / 不确定

- **Codex 既有成功判定**：magpie 网关会发 `item.type=error` 的元数据提示（`Configured service tier priority ...`），现有 `parseCodexStdout` 把它当失败，导致整单 `ok=false`。本批未改（不属事件采集范围）；要修需单独立项确认口径。
- **管理侧可见性**：统计行已追加到 `TicketResult.line`（结果事件 / 留言 / 专线镜像可见）；`formatReport` 仍按 80 字截断唤醒文本，长结果时统计行可能被截掉。
- **`steps.jsonl` 读取**：本批未新增 HTTP 端点；任务中心「跑动中」靠 `delegate` 事件的 `lastAction`，结束后细节需在服务端文件系统按任务目录查（方案 D4 的「按任务号读取」留给后续决定）。
- **豆包无实时步骤**：最终 `tool_calls` 只能结束后补发；`tool_calls_truncated=true` 时统计会不完整（已保留标志，当前统计行不额外标注）。
- Codex 本机 0.163 通过 shell 写文件时不会产生 `file_change` 事件，因此「改了 K 个文件」可能偏少；只把能看到的 `file_change` 计入，不从命令文本猜。
