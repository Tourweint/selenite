# 2026-11-17 上下文页重画（会话版只列已注入）

两轮同日：**上午**把五张卡改成“一次请求的装配清单”（分组列表 + 可读原文）；
**下午**用户看到列表后要求学 magpie 出图形、点击浮卡片、加动画、会话名用执事名、撤掉页内编辑入口，
于是页面收敛成“总量 + 棋盘 + 图例 + 档案页链接”一张卡。

## 改了什么

**背景**：用户 2026-11-17 打开「设置 → 上下文」，提了五点：
(a) 「系统底稿」这一行是啥、没用、我们也没有这东西；(b) 会话版 0 token 要藏掉、默认开销 0 token 要留着，
0 token 的行点开写一句「当前没有开销」；(c) 工具描述这类解释性文字别在前端展示，前端尽量少展示点；
(d) 这页看不出用途——普通消息和工具调用都看不到；(e) 顶部那个会话选择显示「未命名会话」，还是个竖着的下拉。

**核实**：活服务 39847 上取的 `context-inspect` payload 里 `system.content` 恒为空（0 字），
`changing` 只有 `{count, chars, tokens}`，消息与调用正文确实一条都没有——用户的判断是对的。

### 契约（§2.2.4 / §2.2.5）

- `ContextInspectView.entries: ContextEntryView[]`：`kind` = `user` / `assistant` / `toolCall` / `toolResult`，
  带 `label` / `index`（在 `view.messages` 里的下标）/ `chars` / `tokens` / `text` / `truncated?`。
  只取 user / assistant / toolResult；system 消息属于“系统提示词”，不重复进条目。
- assistant 的文本与它发出的每个 `toolCall` 各成一条（调用排在文本后，保住原序）。
  工具调用 token 口径沿用紧凑 `JSON.stringify({name, arguments})`，与 `changing.toolCalls` 同口径——
  **组内各行相加 = Hero 的「对话」段**，不会出现两套数。
- `MAX_CONTEXT_ENTRY_CHARS = 4000`：单条正文超长截断，`chars` / `tokens` 仍按全文算，
  页面读原文时写「已截断 · 共 N 字」。工具结果可能是整份文件，不能把设置页变成另一个会话视图。
- `memory.last.others[]` 加 `text`（同样 4000 字截断）：其它临时注入也能点开看，不再只有 id 与字数。
- `system.content` 字段**保留但不渲染**：真实请求里恒空，删字段没必要，留着兼容。
- `SECTION_META` 补三个裸 key 的中文名：`delegate_executor`（派活执行器）、`tool_index`（低频工具索引）、
  `instructions`（执事说明）。此前页面直接显示英文 key。

### 第一轮页面（已撤销的部分）

- **骨架**：顶部一张总览（总量 + 六段堆叠条 + 图例 + 上一轮真实用量），下面一张「请求内容」卡，
  分组头 + 每行可展开读原文。两个模式共用一套 `buildGroups()`。
- **会话版**：`tokens <= 0` 整行不显示，整组为 0 连组头一起不显示；总量改成**整条请求**。
- **默认开销版**：30 个字段全列（含 0），0 token 行展开写「当前没有开销」。
- **工具**：列表只有工具名 + token，描述不进前端。
- **删掉**：系统底稿行、`空字段` / `可编辑` 徽标、技能 / 记忆卡的「管理 X」按钮、旧的“会变的部分”卡。
- **选择器**：只有一条真实会话都没有时才用兜底「当前会话」；工具栏独占一行，窄屏不再用 100% 宽下拉。

## 第二轮：棋盘 + 浮层（同日）

### 页面被推翻重画

第二轮的反馈是“分块还是不够清楚”“想要 magpie 那种图形，点一块浮起卡片”“每次变化有动画”
“会话名要执事的名字”“这一块尽量不在这里改，留链接到编辑这个人的地方就行”。

- **一张卡收口**：工具栏（模式 + 会话/角色 + 刷新）→ 总量与上一轮用量 → 棋盘 → 图例 → 档案页链接。
  上一轮那张「请求内容」大列表整体删除，逐条内容只在浮层里出现。
- **棋盘**：384 格（32×12 的逻辑分辨率），`paintWaffle()` 用最大余数法按占比分配、每组至少 1 格，
  缩放基准是**请求总量**而非上下文窗口，所以格子总填满——表达“组成占比”，
  窗口占用率留给右上角「上一轮 7.5K / 1.0M · 1%」。
- **格子形状**：列数只能取 384 的约数（96/64/48/32/24/16/12/8，取格宽 ≥13px 的最大一个），
  行数才一定是整数，不会在最后一行剩几个空格看着像“这组突然变长”；棋盘固定 `min(512px, 100%)`，
  512 宽时 32 列 × 12 行、格子 14×16；窗口变化时重排。图例竖排在右侧，和颜色一一对号。
- **配色换了口径**：原来的 `--ctx-seg-1..6`（accent 单色阶 6 段）深浅太接近，正是“分块不清楚”的来源。
  改成三主色 + 三混色：`g1=--c-primary`（靛蓝）、`g2=--c-tertiary`（琥珀）、`g3=--c-secondary`（沙），
  `g4..g6` 是同三色 52/50/50% 混 `--surface`。全部 `color-mix`，换主题自动跟随。
- **动画**：384 个格子一次建好，之后只改 `className`，颜色靠 `background-color .38s` 过渡；
  悬停某组时其它格 `opacity .5`、本组 `scale(1.06)`；浮层 `transform-origin` 落在触发格，
  `scale(.955) translateY(-6px)` → `is-open`；`prefers-reduced-motion` 关闭过渡与缩放。
- **浮层**：先 `visibility:hidden` 量尺寸再定位，默认贴触发点下方、下方不够翻到上方并与视口夹紧；
  点浮层外（含设置页侧栏、顶栏）、Esc、resize 关闭；卡片体可滚动（`max-height:62vh`）。
  单条正文上限 `POP_TEXT_MAX=3000`，超出写「卡片只显示前 3,000 字 · 共 N 字」。
- **0 token 的组**（默认开销里的「记忆：预算 16 条 / 2,000 字」）：卡片正文直接写「当前没有开销」；
  它没有格子，所以悬停时只亮图例行、**不压暗棋盘**（否则整张图像被取消选中）。
- **会话名**：`chatLabel()` 把 `partner-<id>` 映射成执事名（「小记」），chief → 「总管」，
  worker → 「普通 worker」，重名补时间；与「默认开销」的角色选择器同一套口径。
- **撤掉页内编辑**：`DISCIPLINE_EDIT_SECTIONS`、`parseDisciplineSource` / `serializeDisciplineSource` /
  `openDisciplineEditor`（约 200 行）与 `openModal` / `closeModal` / `toast` 三个 import 一并删除，
  `rowMarkup` 不再输出 `ctx-edit-row`。底部改为一行：
  `这个执事的人设、纪律与岗位契约在档案页改：去 小记`，点击跳 `#/settings/partners/<id>`。
  执事档案页的 `PF_DISCIPLINE_SECTIONS` 七节一次改完，能力没有丢。

### 修掉的两个坑- **浮层用 rAF 才加 `is-open`**：标签页不在前台时 rAF 被节流，卡片会永远停在 `opacity:0`。
  改成“量完尺寸 → 强制一次 `void offsetWidth` → 同步加类”，动画照样从缩着的那帧开始。
- **点外部收不起来**：原先只在 `#ctx-content` 上监听，点侧栏 / 顶栏收不掉。
  补一个 `document` 级 `pointerdown`，排除浮层自身与格子 / 图例触发点。

## 第三轮：加一个「占比 / 窗口」基准开关

用户看到棋盘后问：**上一轮用了多少、还剩多少**能不能看出来？「空余的上下文区域固定做一定数量的格子」，
而且只用在对当前会话（默认开销不看剩余），**做成小开关也行**。

- 工具栏加一个两档小开关（`占比｜窗口`，只在「当前会话」出现）：
  - **占比**（默认）：384 格 = 这一条请求本身，看到的是组成占比——原来那张图；
  - **窗口**：384 格 = 整条上下文窗口，已用部分铺满 269 格、剩 115 格（30%）是余量。
- **余量固定 30% 而不是真比例**：1M 窗口里只用 6K（0.6%），按真比例只有 2~3 个格子，什么都看不出来。
  参考 magpie 的做法固定留一块，用户原话“虽然这么着不符合事实，但是对调试来说还是很好的”。
  真实占用率不撒谎——右上角仍是「上一轮 6.3K / 1.0M · 1%」，图例里的「未使用 ≈993,743」是真实剩余。
  用量超过 70% 时余量按真实剩余收窄（不会出现“明明快满了还留 30%”）。
- 余量在棋盘上是极淡的格子（`color-mix(text 7%)`），看得出是格子；图例多一行不可点的「未使用」，
  色块是空心方框，悬停有 tooltip 说明“面积是示意的”。
- 选择存 `localStorage.lifediary.ctxScale`，重渲染 / 刷新都记得；会话没跑过一轮（无 usage）时「窗口」置灰。
- 切换时只重画格子颜色，走的还是那条 `background-color .38s` 过渡——所以切换本身也带渐变。

## 为什么不是别的做法

- **没把 `entries` 做成“最近 N 条”**：本页仍然只回答“这一条请求装了什么”，不做请求历史。
- **没做 treemap / 气泡**：格子图是用户点名的形态，且 384 格能把 1% 级的小组也画出来。
- **没在上下文页做逐节编辑**：用户明确“推荐不能改”，跳档案页既省一套弹层，也不会出现两处编辑入口。
- **没按供应商词表分词**：token 仍是 `≈`（CJK 1 字 1 token + 其它 4 字符 1 token）。

## 没验 / 边界

- **颜色过渡与浮层展开动画没在屏幕上看到过**：本机浏览器动画时钟会整体冻结
  （`main.main` 与 `.set-page.enter` 的 `set-fade` 停在 `currentTime=0`、opacity 恒 0），
  截图只能靠“新标签首帧”或注入 `*{animation:none}` 取证。代码层面只改了 `className`，
  过渡交给 CSS，逻辑上不会闪；但“看起来顺不顺”没做过肉眼确认。
- **「小记」默认选中**：`selectedChatId()` 优先 `state.conversationId`，浏览器实例里打开的是 worker 会话，
  所以默认落到「普通 worker」；用户自己的实例在跟小记聊时才会默认选中小记。是否需要“执事会话优先”未拍板。
- 真发生注入的「临时注入」组只在 worker 会话里看到（服务重启后进程内注入表会清空，要等下一轮真跑过）。
- 单条正文 4000 字截断只在单测里覆盖，没在真实长工具结果上验。
