2. **`pool/pool-settings.ts` — 上下文管理档位（纯函数）**
   - `poolHarnessSettings(env, contextWindow, modelKey)`：压缩触发点按窗口 **70%**
     （reserve = 30%），换算复用宿主的 `compaction-settings.ts`，不重写第二套。
   - `poolMaxTurns(env)` / `POOL_MAX_TURNS`：`AGENT_MAX_TURNS`，默认 100。
   - `bashTimeoutSeconds(env)`：直接转调宿主 `reliability.ts` 的同名函数，两边同判据。
   - **踩到的真坑（写方案时写错了，实施时纠正）**：方案的 §5.9 原本写 `modelOverrides: { "*": ... }`。
     实读内核 `pi-durable/dist/harness/compaction.js:195-204`，`compactionPolicy()` 按
     `${provider}/${modelId}` **精确查表，没有通配档**——`"*"` 能过类型检查但永远命中不了，
     是一条静默失效的配置。改成同时写全局 `reserveTokens` 与 `modelOverrides[modelKey]`。

3. **`pool/pool-tools.ts` — 工具面与边界**
   - `buildPoolRegistry(deps)`：`CodingTools` + `escalate` 工具 + 一条 `beforeTool` 钩子。
     钩子三步固定顺序：白名单 → 路径边界 → bash 超时注入
     （被拦下的调用不该拿到补过的参数）。
   - `pathBlockReason()` / `isInside()`：判据**照抄** chancellor `worker-main.ts`，
     用 `path.relative` 分段比较，不用 `startsWith` 字符串比较
     （后者会让 `A-sibling/` 以 `A` 为前缀被误判成界内）。
   - `escalate` 的出口是 `deps.submitEscalation` 回调，**不走 stderr**——
     池进程与宿主之间已经有 HTTP + SSE，另开一条 stderr 行协议就是第二条通道。

4. **三个单测文件**，共 25 条：`task-profile.test.ts`（7）、`pool-settings.test.ts`（7）、

**为什么**

用户 2026-11-22 口径：worker 与宿主用的是同一颗 `pi-durable`，改动没有想象中大——
把宿主的上下文管理与权限机制搬进池进程即可。核实成立：`compaction-settings.ts`、`loop-guard.ts`、
`turn-gate.ts` 的 `MAX_TURNS`、`reliability.ts` 的 `bashTimeoutSeconds` 全是纯函数或零 IO 的类，
`import` 过来就行；真正要新写的只有池进程入口、IPC、supervisor。

本轮刻意**不碰**那 185 个在途改动，也不碰 `package.json`（新单测不进 `pnpm test` 清单，
用 `npx tsx --test src/pool/*.test.ts` 单独跑）。

**验了什么**

- `pnpm typecheck`：0 错误（`ts/` 全量）。
