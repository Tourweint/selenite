## 与任务书的两处口径差异（以代码为准，已核对）

1. **装配点只有一处（不是两处）。** 任务书写「`agent/lifecycle.ts` runPartnerTurn 与
   `group-runtime.buildMemberInput` 两处装配」。实际 `runPartnerTurn` 在 `partner-runtime.ts`；
   更要紧的是：私聊 / 例行专线 / 群成员轮走的是**同一条 harness + 同一个扩展**，`beforeRequest`
   对三种会话都会跑并都能 `partnerIdOfSession` 认出执事。所以在 hook 里装配一次即覆盖全部；
   在 `buildMemberInput` 再拼一遍会让群轮看到两份。`group-runtime.ts` 只留注释说明。
2. **列待审批用 `pendingOf`，不是 `findPending`。** 任务书写 `approvals.findPending`；
   它的实际签名是 `(conversationId, tool, argsHash)`，用途是"同工具 + 同指纹去重"，不是列清单。
   列清单的正确入口是 `pendingOf(conversationId)`（8c 早已存在），未改 approvals。

另：`remember` 要写 `source="taught"` 必须在模型侧有可判定的信号，因此加了可选参数 `taught`
（工具 schema 不是跨仓契约；`delegate` 的参数结构才是，那个一字未动）。

## 设计上的三个刻意选择

- **注入走 system 消息，不拼进用户正文。** 「当前在办」每轮都变，拼进正文会被 durable 固化进
  transcript：既污染历史，又让模型下一轮读到一段旧状态。与记忆召回注入同一条通道。
- **契约取当前版本快照、每轮现取。** 与 SOUL 共用版本号；改契约 bump 版本，下一轮读到新的，
  当场不变身。老库 / 手工放了文件但没快照的退磁盘当前值（与 `chiefSoul` 同口径）。
- **"该执事发起的单" = `originConversationId` 落在他的会话链接里。** 派单记账本来就带着发起会话
  （`tools.ts` → `kick.conversationId` → `ticket.json`），零新存储。老单没有该字段就看不到——
  状态感要的是"我在办什么"，不是全量归档（历史单反查回执是任务中心的职责，这里不重复）。

## 已知边界（如实登记）

- **system 注入的正文不可从 transcript 断言**：它只进当次模型请求。单测覆盖装配函数，
  探针覆盖「一轮真链路能跑通、没有装配异常日志」，但"模型真的收到了这段"只能由派单人真模型手验
  （任务书已把真模型手验归派单人）。
- **状态段只认 `originConversationId`**：老单、从别的会话（例如总管代为转派）发起的单不会出现在
  "在办"里。这是口径不是缺陷，登记在案。
- **`GET /partners/:id` 多了两列**：纯增量，但手机端 / 前端若做严格 schema 校验需忽略未知字段
  （现状没有这种校验）。
- **总管（`chief`）没有岗位契约**：不播种、不注入（他是主人本体，不是被派的执事）；
  有人手工往他家目录放 `CONTRACT.md` 才会读到。
- **界面编辑区未做**：契约只能经 HTTP 端点写（刀三与 9-P 联动）。
- **`pnpm probe`（内核语义）没跑**：本刀不碰提交 / 流式 / 闸门 / 睡眠 / 重启续跑。
- **providers / diary / tasks / phone 探针没跑**：改动不经过这些链路（供应商配置、日记镜像、
  任务中心投影、手机 worker 的代码路径均未动）；任务中心投影只被本刀新增的只读扫描复用，
  其自身的 `http` 覆盖已通过。
- **真模型手验未做**（归派单人）：教一次 → 同类活行为变化；契约段 / 在办段在真实模型眼里的效果。
