## 做了什么

### H1 `mobile/proxy` 通道（`ts/apps/server/src/relay-channels.ts` / `relay-client.ts` / `relay-config.ts`）

中继 R1 的反代帧是**第二种入站帧**（`kind:"invoke"`，不走 deliver/routed），所以两端都要动：

- `relay-client.ts`：识别 `invoke` 帧（`RelayInvokeFrameSchema.strict()` 校验）→ 调
  `onInvokeHttp` → 回 `{kind:"invoke_result", id, payload:{status, body}}`。中继只认这一种回包，
  所以**所有失败都折成 HTTP 状态**（400/404/500），绝不让手机干等 15 秒吃 504。
- `relay-channels.ts`：白名单显式加 `mobile/proxy`；`handleHttpInvoke()` 用 shared 的
  `RelayInvokePayloadSchema` 校验，**只放行 `/api/v1/` 前缀**，交给装配层传进来的
  `dispatchHttp` 执行；异常折 500（细节不外泄）。
- `index.ts`：`dispatchHttp` = **本进程内 `app.request()`**（不真发 HTTP、免端口自环），
  status 与正文原样返回；逐跳头（host/connection/content-length/transfer-encoding）不带进内部调用。
- 回滚：`RELAY_MOBILE_PROXY_ENABLED=off` → 装配层**不传 `dispatchHttp`**（通道未注册），
  中继发来的 invoke 一律回 **404 `{"error":"not_found"}`**；`join-code` 端点同开关 404。
  真起进程验过（见下 probe），不是单测假装的。

### H2 「添加设备」弹窗（`relay-mobile-proxy.ts` + `web/app.js` / `style.css`）

- 新端点 `POST /api/v1/relay/join-code`：body `{relayUrl?}`，**harness 代调**中继
  `POST /api/relay/join-code`（带 `RELAY_OWNER_TOKEN`，从进程 env 读，不进浏览器/日志），
  回 `{joinCode, expiresAt, relayUrl, url, dataUrl}`。二维码由服务端 `qrcode` 渲染成 PNG dataURL
  （与既有配对码同款）。
- 中继地址默认取 `RELAY_URL` 的对外形态（`ws→http` / `wss→https`、去掉末尾 `/ws`），
  弹窗内可改；只收 http/https、拒绝带账号密码的 URL。
- web「设置 → 连接」卡片加「添加设备」一行 → 弹窗：中继地址输入 + 大字加入码 + 二维码
  （`lifediary://relay/join?u=<中继地址>&c=<码>`）+ `m:ss` 过期倒计时 + 「换新码」。
  倒计时随弹窗关闭自停；不回显手机是否已加入（去同页「已连接的设备」看）。

## 与任务书字面不一致的地方（都记录理由）

1. **鉴权映射不是"仅在缺 authorization 时补"，而是内部调用一律用本进程 `AGENT_TOKEN`。**
   任务书说"headers.authorization 缺则补"，隐含"手机令牌 = AGENT_TOKEN"；但批R 的 join
   发的是**中继 deviceToken**，与 harness `AGENT_TOKEN` 不是同一套，原样透传必然 403，
   扫码加入这条路就永远打不通。中继在投 invoke 前已经验过设备令牌（R1 第一步），
   所以到 harness 的请求已获授权，harness 用自家令牌执行即可。
   **安全含义**：能拿到有效中继 deviceToken 的设备（即被 owner 扫码/配对加入过的设备）
   可以使用这台电脑的全部 `/api/v1` 能力——这正是"扫码加入 = 授权这台手机用这台电脑"
   的产品语义；撤销走中继撤设备（令牌立即失效、连接被踢）。未配 `AGENT_TOKEN` 时不注入，
   退回 harness 自己的鉴权（fail-closed）。
2. **harness 侧 `off` 回 404，而不是超时。** 任务书说"通道不注册"；若只抛错，中继会等 15s
   才 504，手机看到的是"设备超时"而不是"没有这个能力"。现在通道不执行、直接回
   `invoke_result{status:404}`，两端开关语义一致（中继侧 off 也是 404）。
3. **join-code 由 harness 代调，浏览器不直连中继。** 任务书只写"调中继 join-code"；
   浏览器直连会撞 CORS，且 owner 令牌必须下发客户端（违反密钥纪律）。改由服务端代调，
   owner 令牌只读进程 env。
4. **二维码里的 `u` 做百分号编码**（`encodeURIComponent`）。任务书写作 `u=<地址>`；
   地址含 `://` 与端口，Android `Uri.getQueryParameter` 会自动解码，编码后更稳。

## 刻意没有（本批不做）

- 手机端 join 的轮询回显（任务书明确不做；看名册页）。
- 弹窗里改地址时自动重签：改完要点「换新码」才用新地址重新签发（避免每敲一个字符就打中继）。
- 反代的多目标路由（只打任务主机）、SSE 仿真、Ed25519 签名：仍是批R 登记的二期的项。
- 反代路径的额外白名单：只卡 `/api/v1/` 前缀，不按端点列（避免新增端点时忘加一条就悄悄不可用）。

## 已知边界

- **反代不放行 `POST /api/v1/relay/join-code`**（回 404）：加入码是电脑本地管理动作。
  不堵这一条的话，任一已加入设备都能经反代调它，让 harness 用 owner 令牌替它继续发码、
  拉更多设备进来——绕过中继侧 owner-only 的签发口径。单测与 probe 各有断言。
- **反代 = 已加入设备的全量 `/api/v1` 面**：除上面一条外不做端点级白名单。中继撤销设备即失效；
  但反代能读的写的能力与主人自己用 harness 相同（扫码加入的产品语义如此）。
- 中继日志每条反代一行 `[relay] invoke device=<id> id=<uuid>`；harness 只记
  `[relay] invoke_result status=<n>`。都不含路径正文、令牌、加入码（probe 有断言）。
- harness 侧 `RELAY_MOBILE_PROXY_ENABLED` 是**启动期**决定通道是否装配；改开关要重启
  （中继侧同名开关是每请求读 env，可热切）。
- 「添加设备」依赖 harness 能访问中继的 HTTP 面；`RELAY_URL` 写的是内网/回环地址时，
  弹窗里要改成手机也能访问的对外地址，否则二维码扫了也连不上（地址可改就是为这个）。
