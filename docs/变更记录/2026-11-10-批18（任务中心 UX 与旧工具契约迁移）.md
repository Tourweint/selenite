## 一、任务中心：阶段条 + 验收证据 + 返工次数（§一）

- **阶段条**：`renderTicketDetail` 里新增「受理 → 规划 → 执行 → 验收 → 完成」，当前阶段高亮，
  前面已完成阶段降为次要色。数据只来自 `ticket.status`（`received`→受理、`planning|planned`→规划、
  `dispatching|idle|needs_you`→执行、`reviewing`→验收、`done`→完成）。
- **失败 / 中止 / 作废不猜阶段**：`failed` / `aborted` / `canceled` 映射为"无当前阶段"（五段全暗），
  真实状态仍由状态片（失败待看 / 已中止 / 已作废）说——宁可不说，不编一个假阶段。
- **返工次数**：`repairRound > 0` 时阶段条右侧出现「返工 N 轮」（批 11 字段，读 `data.repairRound`
  或 `ticket.repairRound`）。与详情里既有的「返工第 N 轮」计划附件同一份数据，两处说法一致。
- **验收证据块**：原「验收记录」改成「验收证据」，逐条给出判定、对应任务标题、核对类别与原因；
  标题计数与列表长度**相等**（原来只渲染最近 6 条、标题却写总数，属七原则②违背，本批一并修掉）。
  核对类别由内部枚举 `process/report/artifacts/llm` 译成「过程 / 汇报 / 产物 / 模型」（七原则③）。
- **裁判结论暂无界面**：`judge.json` 由 chancellor 逐票落盘，`GET /api/v1/tickets/:id` **没有投影**它
  （2026-11-10 核对 `delegation-api.ts`）。按任务书不新增端点/字段，本批界面无这一块。
  要展示得先给详情端点加可选字段（契约改动），单独立项。
- **「改了哪些路径」没有结构化数据**：`changedPaths` 只在各任务的 `run.json`，`reviews` 表只有
  `seq / slug / verdict / reason / stage`（2026-11-10 核对 `chancellor/src/store.ts` 表结构）。
  artifacts 阶段的 `reason` 文本里本来就带路径清单，界面原样呈现；**不解析自由文本、不新造字段**。

## 二、执事列表：忙因胶囊（§二）

- `renderRoster` 在状态点左侧加一枚小胶囊（`.roster-busy`），优先级
  **等审批 > 跑任务 > 等回答 > 空闲**；空闲不画（七原则⑥）。
- 数据只用现成三路，**没有新端点**：
  - `/api/v1/partners`（`domain`）+ `/api/v1/domains`（`activeTickets`）→ 「跑任务」；
  - 全局待办 `/api/v1/agent/approvals`（不带 conversationId）→ 「等审批」/「等回答」
    （`kind === "ask_user"` 或 `tool === "ask_user"` 算等回答，其余算等审批）。
- **按会话反查执事**：主会话 `partner-<id>`，群成员轮 `partner-<id>-group-<gid>`
  （复用既有 `parseGroupMemberConversation`），两者都记到该执事头上。
- **降级口径（写清）**：待办快照**拿不到**（请求失败 / 503 未配置模型 / runtime 停）时，
  不声称"不在等审批"，只显示「忙 / 空闲」——忙 = 该领域有未结束的任务单。
- 不额外打接口：直接复用审批浮窗已有的 5 秒轮询快照；快照变了只改胶囊文字，不重绘整份花名册
  （不打断 hover / 焦点）。

## 三、面板七原则评审（§三）

结论单独成文：`docs/设计方案/2026-11-10-批18-面板七原则评审（任务中心与审批浮窗）.md`。
本批**只改明显违背**的三处（其余"符合"或"暂不改 + 原因"都在那份文档里）：

1. 验收证据标题数字 ≠ 列表长度（只渲染 6 条）→ 逐条全渲染。
2. 验收阶段直接印 `process/report/artifacts/llm` → 中文。
3. 已作废的单被算进「已完成」（统计条、聚合灯、已完结横条）→ 统一改叫「已完结」；
   标题副行「N 次派活」原用票数（把子单也算成派活），与统计条不一致 → 两处统一走
   `dispatchedCount()`（父单一行算一次）。

未动视觉结构：三列、统计条五块、折叠区、审批浮窗布局都没改。

## 四、技能用量进界面（§四）

- 设置 → 技能：每行 meta 追加「用过 N 次 / 从未用过」，`stale === true` 时挂「90 天未用」小徽章
  （title 写明"只标记，不删不移"）。字段来自批 17 的 `GET /api/v1/agent/skills`
  （`usageCount` / `lastUsedAt` / `stale`），开关关着时字段不出现，界面自然不显示。
- **只加展示，不加操作**：技能仍然只能由人删，不做「归档」按钮。

## 五、只读工具迁到统一返回契约（§五）

按 `tool-result.ts` 文件头的顺序迁了四件：`recall` / `web_search` / `propose_topic` / `skill`。

| 工具 | 成功 | 失败 |
|---|---|---|
| `recall` | `ok({ count, message })` | 群会话 → `err("group_session")` |
| `web_search` | `ok({ count, hits, message })` | `err(result.error, result.message)`（code 用适配层枚举） |
| `propose_topic` | `ok({ proposalId, question, flavor, cron, message })` | `err(reason, message)`；已在跟的 id 放 `hint` |
| `skill` | `ok({ name, message })` | `err("skill_not_found", 原句)` |

- **人读文案逐字不变**：`message` / `error.message` 全部是迁移前那句原文；只是外面多了
  `{ ok, data }` / `{ ok, error: { code, message, hint } }` 的壳。
- `recall` 不把原始 `record` 塞进 `data`：那里带 `scope` / `id` 等内部字段，模型不需要，
  以前也看不到（正文只走 `message`）。
- `propose_topic` 的 `existingTopicId` 在 `ToolError` 里没有位置，改放 `hint`
  （HTTP 端点 `POST /topics` 的返回形状**未动**，那里仍带 `existingTopicId`）。
- `web_search` 失败分支原来是手搓的 JSON 串，现在走 `err()`；错误码与搜索适配层同一套稳定枚举。
- **单测**：`src/tool-result.test.ts` 追加 7 条（四件的成功/失败形状 + 文案逐字对照），
  用临时 `PARTNERS_DB_PATH` / `AGENT_SKILL_USAGE_PATH` 隔离，不碰仓库 `.data/`。
- **还没迁**（写进 `tool-result.ts` 注释）：`remember` / `set_reminder` / `persona_recall` /
  `send_to_agent` / `delegate` / `propose_project` / `partner_skill_write` / `partner_manage` /
  `group_manage` / `routine_manage`；`read` / `write` / `edit` / `bash` 由 durable 的 `CodingTools`
  提供，不在范围内。写类工具本批明确不动（结果被回执 / 恢复链路读取，要单独一批）。
