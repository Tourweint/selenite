## 改了什么

### 一、验收「核对-修复」循环（§1，`DELEGATION_ACCEPT_ROUNDS`，默认 1）

1. **chancellor `src/repair.ts`（新，纯逻辑）**：`acceptRounds()` 读 env（**0 是合法值**，不能用
   现有的 `readPositiveInt`——它把 0 当非法回落默认值；负数按 0、非法按 1）、`shouldStartRepair()`、
   `buildRepairRequirement()`（上轮验收原话 + 声明路径逐项状态 + "只修这些别重做" + 原始要求）、
   `lastFailReason()` / `renderAcceptLimitLine()`。
2. **chancellor `src/index.ts`**：直派路径拆成 `runRound()`（拆单 → 执行 → 验收），外面套循环：
   `finishRuns` 失败时把这一轮的 `{reviews, runs}` 填进调用方给的槽位（新增可选 `repair` 字段，
   不传 = 旧行为，崩溃恢复 / resume 两个调用方零改动）。轮次未用完 → **同一张 ticket** 再跑一轮：
   `ticket.repairRound` 递增落盘、上一轮任务目录归档到 `round-<n>/`、sqlite 任务/验收行清掉、
   `startInflight` 重新标记进行中、emit 一条 `ticket` 事件说明"第 N 轮返工"。
   轮次用完仍失败 → `needs_you`，文案 `已自动修 N 轮仍失败，原文：<最后一轮验收结论>`。
   `finishWithoutReview`（硬失败）、review fail、整体目标核对失败三处都接进循环。
3. **chancellor `src/store.ts`**：`resetRoundRows(ticketId)`（只清该单的 tasks/reviews 索引行，不动 ticket 行，
   不改 schema）。
4. **投影**：`TicketResult.repairRound?`（只在返工过时出现）；`ticket.json.repairRound` 幂等命中时也还原。
5. **回滚**：`DELEGATION_ACCEPT_ROUNDS=0` → while 一次都不进，结果与改动前逐字节一致
   （单测直接断言 `shouldStartRepair("failed", 0, 0) === false`）。
6. **路线选择**：按 T0 结论走"同一张单重跑"，**不是宿主二次派单**——`decideAfterReview` 保持纯函数，
   `delegate` / 宿主装配零改动，验收结论天然带反馈。

### 二、任务单计划附件 steps（§2）

7. **`delegate`**：新增可选 `steps: string[]`（≤12 条、每条 ≤200 字）；校验在
   `delegation.ts:normalizeDelegationSteps()`（纯函数），不过直接回
   `{"ok":false,"error":"invalid_steps","message":…}`、**不建单**。描述里补一段
   "≥3 个动作或跨文件的多步活必写、一句话小活不写"，与任务书四段并列。
8. **chancellor**：`ChancellorRequest.steps` / `Ticket.steps`（落 `ticket.json`）；`plan.ts:appendPlanSteps()`
   把步骤拼成 `## 步骤` 段交给规划器（空 / 不传 → 原样返回）。不参与验收判定。
9. **详情**：`GET /api/v1/tickets/:id` 顶层新增可选 `steps`（§2.3）；`GET /api/v1/tickets` 列表不变。
10. **前端**（`web/app.js` + `style.css`）：任务详情顶部加一行 `<details>`「现在到哪一步」，
    当前项按已过任务数估（没有逐 step 状态，不编假进度），点开展开全部步骤；没有 `steps` 时整块不渲染。
    返工单在行尾带「返工第 N 轮」。

### 三、结构化提问 `ask_user`（§3，`AGENT_ASK_USER` 默认开）

11. **`ask-user.ts`（新）**：参数校验（题 ≤200 字；options 2-3 个、每个 ≤60 字、互斥不重复；
    recommended 必须在范围内且给了 options）+ `createAskUserPending()`（借审批 pending 表，
    `tool=ask_user, kind=ask_user`，`args` 是问题 JSON，供客户端渲染；同会话已有提问 pending 时拒绝——
    "一次只问一个"）+ 工具定义（描述写明三条纪律）。
12. **`agent/lifecycle.ts`**：beforeTool 在闸门最前面拦下 `ask_user`，落 pending 后 `{block}` 收本轮
    （校验失败只回模型、不建 pending）。
13. **`approval-api.ts`**：GET 两种形态都额外透出 `kind`；新增
    `POST /api/v1/agent/approvals/:callId/answer`（body `{answer}`，≤1000 字）。答复后
    `continueConversation` 发 followUp「主人回答了你刚才的问题：…」；approve/reject 打到提问记录 → 400。
14. **`approvals.ts`**：记录加 `kind?` / `answer?`，状态加 `answered`，新增 `answer()`（幂等）。
15. **`flags.ts`**：白名单加 `AGENT_ASK_USER`（`hot:false`，工具注册启动冻结）。
16. **闸门清单**：**不进** `WRITE_TOOLS`、**不进** `DEFAULT_CRITICAL_TOOLS`（注释写明判断）；
    `arch-guard.test.ts` 的"不需要进闸门"读类白名单加 `ask_user`，让架构守卫继续能抓"新工具漏登记"。

### 四、拒绝带反馈（§4）

17. **`approvals.ts`**：记录加 `feedback?`；`decide()` 第四参收 feedback，只在 rejected 时落库。

    「你拒绝了这次 `<tool>` 调用。主人的要求：`<feedback>`」，不带**逐字节等于**旧文案。
19. **`agent/turn-gate.ts`**：`approvalRejectedInstruction(tool, feedback?)` 同口径（async 路径的 followUp）。
20. **`approval-api.ts`**：body 加可选 `feedback`（>500 字 → 400），reject 时传给 decide；
    async 续跑把 feedback 拼进拒绝指令。blocking 路径从记录里取 feedback 交给 `denialReason`。
21. **前端**：对话流审批卡与右下角审批浮窗都加一行小字「带说明拒绝」，默认折叠；展开后是一个可选
    输入框 +「拒绝并说明」，不填就是普通拒绝。手机端不做。

### 五、闸门拒绝留痕（§5，`AGENT_GATE_AUDIT` 默认开）

### 七、chancellor 仓库改动（单列说明，按铁律 §2）

本任务**必须**改 chancellor：验收循环的判定点、`steps` 落点、`repairRound` 都长在它身上，
宿主侧看不到 `reviewTask` 的结果。改动清单：

- `src/repair.ts`（新，纯函数）；
- `src/index.ts`：直派路径抽 `runRound` + 循环、`finishRuns` 加可选 `repair` 槽位、归档目录；
- `src/store.ts`：`resetRoundRows()`（无 schema 变更）；

**回滚**：`DELEGATION_ACCEPT_ROUNDS=0` 关闭循环（其余改动是可选字段，旧数据 / 旧调用方零影响）；
`steps` 不传即旧行为。chancellor 侧没有独立的 env 开关——它的行为完全由宿主传的
`steps` 与 `DELEGATION_ACCEPT_ROUNDS` 决定。为什么不能只改宿主：验收结论（`Review[]`）与
声明路径状态（`TaskRun.changedPaths`）只在 chancellor 进程里，宿主拿不到，二次派单只能靠文案猜。

## 已知边界 / 没跑的验证

- **验收循环只覆盖直派链路**（v0.3 / 执事直派 `managers:false`）。分管（`domain` + `managers!=false`）
  单的验收在宰相子进程里，宿主看不到 `Review[]`，本轮不接循环；0 轮 / 分管路径行为与改动前一致。
- **修复循环的真实模型端到端未跑**：规划与验收都要 qoder 真模型，探针无法稳定复现。
  已用纯函数单测锁死"该不该修 / 修什么 / 上限文案"三件事；重跑与目录归档的副作用代码审查过，
  但**没有真跑过一轮"失败 → 返工 → 通过"**。建议派单人在隔离环境用一张声明了 `writes` 的小单实测。
- **`ask_user` 的答复是 followUp 用户消息，不是工具结果回填**：pi-durable 1.4.0 没有向已收尾 run
  回填工具结果的入口（与 8c 审批同一约束）。模型在下一轮的用户消息里读到答复；任务书原文"从工具结果里读"
  按现有内核做不到，已在接口文档写明。
- **手机端零改动**：`ask_user` 的 pending 会出现在全局待办里，但手机只会当普通审批卡（approve/reject
  会被 400）。要真正在手机答复，需要手机端加 `kind` 分支与 `/answer` 调用，另行安排。
- **闸门类别 `routines` 目前没有落点**：枚举先占位；现有代码没有"被 routines 拦下"的工具调用。
- **闸门审计只追加、不做轮转**：`.data/gate-blocks.jsonl` 会一直长（每行几十字节），本批没做清理策略；
  需要时另立一个小任务（按大小切分 / 保留最近 N 天）。
- **"现在到哪一步"是估算**：任务中心没有逐 step 状态，前端按已过任务数映射到 `steps` 下标；
  修复轮里任务清零，会显示第 1 步——它表达的是"这一轮从哪开始"，不是逐动作精确进度。
- **前端只做了 `node --check` 级别的语法验证**（`pnpm typecheck` 不含 `web/app.js`）；
  浏览器真点（任务详情"现在到哪一步"展开、审批卡"带说明拒绝"、问题卡选项与自由输入）归派单人。
- `pnpm probe` / `pnpm memtest` / `providers` / `tasks` / `phone` 等其余探针未跑：本次没动提交 / 流式 /
  睡眠 / 记忆 / 供应商链路；改动集中在工具闸门、审批、派单输入输出与 chancellor 收尾。
