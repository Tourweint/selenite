### M2a：单票超时（池 + 外部 CLI）

- `pool/supervisor-core.ts` 新增纯函数 `runTimeoutReason({startedAt,lastActivityAt,now,idleMs,maxMs})`
  → `"max" | "idle" | null`；0/负数 = 该项不限。
- `pool/supervisor.ts` 的 `followEvents`：
  - 每收到一条 SSE 事件（progress / escalation / report / settled）刷新 `lastActivityAt`；
  - 1 秒轮询判超时（不用 15s 健康心跳当节拍，窗口会抖）；
  - 超时先 `postAbort` 请 worker 自己收尾，10s 宽限仍无 `settled` 就 `killSlot("run_timeout")`；
  - 超时判定不因 worker 随后自己发 `settled` 改口，`finishedTickets` 只加一次；
  - 调用方已取消（`callerSignal.aborted`）时不再判超时，不抢取消的账。
- `employee/pool.ts`：`timedOut = result.reason === "timeout"`。
- `employee/cli.ts`：新增 `idleTimeoutMs` / `maxTimeoutMs`。给了 `idleTimeoutMs` 走活动口径
  （stdout/stderr 任意 data 重置空闲计时，`maxTimeoutMs` 再压墙钟上限）；没给仍是旧墙钟 `timeoutMs`，
  还没迁移的调用方行为不变。错误文案区分「空闲超时（Nms 无输出）」与「超时（Nms 总时长）」。
- `config.ts` 新增 `WORKER_IDLE_TIMEOUT_MS`（`CHANCELLOR_WORKER_IDLE_MS`，默认 10min）与
  `WORKER_MAX_TIMEOUT_MS`（`CHANCELLOR_WORKER_MAX_MS`，默认 60min，0=不限）；
  `readEnvIntUnlimited` 让 0/负数表示"不限"而不是回落默认。
- 五个外部 CLI 适配器（claude / codex / opencode / codebuddy / qoder）改传 idle+max。

### M3：失败分类 · attempt 重试 · 车道冷却

- 新增 `chancellor/src/failure-class.ts`（纯函数）：
  - 11 类 `FailureClass`；`classifyRunFailure` 优先级 = 调度层判定（越权/冲突）→ aborted →
    timedOut → 只有进程真失败才扫错误文本（额度 → 长 reset 的 429 归额度 → 限流 → 权限 →
    崩溃 → 传输）→ REPORT 缺失 → unknown；
  - `retryDecision`：transient 2 次(1s/4s)、rate_limit 3 次(5s/30s/120s)、timeout 1 次、
    crashed 2 次(2s/8s)、usage_limit 3 次；权限/越权/冲突/报告缺失/取消/未知不重试；
  - `parseResetAt` 认 `reset after 1h 2m 3s` / `retry after 30s` / `冷却 5 分钟` / `2 小时后恢复`；
  - `cooldownUntil`：额度用 resetAt（上限 24h）、限流 30s、其它 null。
- `lane.ts` 加 `setLaneCooldown` / `laneCooldown` / `recordLaneOutcome`：同一车道连续 3 次失败
  → 5 分钟冷却，成功清零；冷却期间 `acquireLane` 返回 `granted:false + cooldownUntil`（不阻塞）。
- `scheduler.ts`：`executeTask` 改为 attempt 循环，每轮重新拿车道/租约/worktree；
  - 每轮写 `attempt-<n>.json`（只有 seq/attempt/class/exitCode/timedOut/durationMs，不写正文）；
  - 重试前删 `REPORT.md` 与 `session.json`，避免上一轮报告被当本轮结果；
  - usage_limit 只在 reset ≤10min 时进程内等，更长的直接判失败并冷却车道（不占进程睡几小时）；
  - 冷却期间 `waitingOn="执行器冷却到 HH:mm"`、30s 探槽、不消耗 attempt；
  - 退避与冷却等待都可被取消信号打断；
  - `CHANCELLOR_RETRY_ENABLED=false` 同时关掉重试、attempt 记账与车道冷却。
- `index.ts` 的 `finishRuns` 给每个 run 填 `failureClass`；对外五态不变。
- `delegation-mount.ts` 的任务投影从任务目录读最后一个 `attempt-<n>.json`，
  纯增量补 `attempt` 与失败类（unknown 不展示）。

- **worktree 决策数据**：`attempt-<n>.json` 增 `queueMs`（等车道/冷却耗时）与
  `worktreeMs`（worktree 检出耗时）。方案里 worktree 预热"等 P4 数据"说的就是这两个数，
  现在开始攒，不靠猜。

**为什么**

- 池没有单票超时，一票可以无限跑；外部 CLI 是墙钟 10 分钟，长任务被误杀、挂死任务占满槽。
- 失败即终态：429、5xx、CLI 瞬断都要人再点一次，且重派立刻又撞同一车道。
- 用户看不见「在跑几单、排队几单、哪条车道在冷却」，无法判断"变慢"是不是排队。
- 设备矩阵只看在跑数，不看排队深度，会挑到"在跑少但排队长"的机器。

**没做 / 没验（如实登记）**

- 没真起 Claude / Codex 打真 429 验证分类与 reset 文本；分类靠单测与现有 `failureReason` 口径。
- 没端到端真跑池崩溃 / 超时的自动重派（只覆盖假 runner 的调度账与分类）。
- 车道冷却期间任务行 sqlite 状态仍是 `running`，只通过 `task-waiting.waitingOn` 表达。
- 车道 / 准入 / 冷却都是**进程内**状态：manager 子进程、远程设备各一份（M1a 已知边界）。
- 前端「排队 N」没做真浏览器目测，只做了语法检查 + import 护栏。
- `parseResetAt` 不认绝对时间（`resets 3pm` / ISO），无时区信息时回落 5 分钟。
- M4 做了设备挑机 tie-break、等待上报 10 分钟超时释放、worktree/排队耗时记账；
  **仍未做**（原因不是"影响小"，是动核心不变量）：
  - **立即让位**（上报一发生就释放池槽位）：池进程一条活跃会话，要让位只有两条路——
    同一进程挂多条会话（破坏"一进程一会话"的失败隔离），或把会话持久化后换进程 resume
    （池库按进程分文件，跨进程读不到）。两条都是池核心模型改动，不是小改；
    当前先用"10 分钟超时释放"兜住无限占槽。
  - **worktree 预热池**：提前建的副本会随其他任务合并而过期，必须配刷新队列（orca 那套），
    预热到合并之间还有 base 不一致风险；方案本来就定了"先看 queueMs/worktreeMs 数据"。
  - **manager 进程本身进池**：manager 是长驻领域会话（自己的库、delegate 循环、上下文换段），
    pool 是每票一会的执行容器；而且 manager 大部分时间在等子单，占一个池槽反而降低吞吐。
    manager 的子单已经经池桥进池，容量问题已解决。

**回滚**

| 开关 | 作用 |
|---|---|
| `CHANCELLOR_SCHEDULER=false` | 车道 / 领域 / 准入全部直通（不含重试与超时） |
| `CHANCELLOR_RETRY_ENABLED=false` | 关重试、attempt 记账与车道冷却 |
| `CHANCELLOR_WORKER_IDLE_MS=0` + `CHANCELLOR_WORKER_MAX_MS=0` | 池与外部 CLI 都不设超时 |
| `CHANCELLOR_LANE_CAPS` / `CHANCELLOR_MAX_ACTIVE_TICKETS` / `CHANCELLOR_QUEUE_MAX` | 放宽或收紧各闸 |
| `CHANCELLOR_EMPLOYEE=native` | 回每票一进程执行器 |
| `DEVICE_AUTO_DISPATCH=false` | 关设备自动挑机（队列深度 tie-break 一并失效） |
