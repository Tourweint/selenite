**为什么要做**

见方案 §2：native 每票 spawn 一个裸子进程，装配重复、每票一份库、通道只有 stdin/stderr。
池化后一个进程串行跑多票，失败半径仍是 1 票，通道升级成 HTTP+SSE，且上下文/权限与宿主同源
（同一颗 pi-durable，宿主的压缩/回合上限/防打转/bash 超时都是现成的纯函数，搬过来即可）。

**踩到并修掉的两个真 bug（都是跨票复用引入的）**

1. **路径边界闭包成快照**：`buildPoolRegistry` 原先把 `taskDir/workDir` 闭包进进程级 registry，
   第二票会继续用第一票的目录边界（越权）。改成 `currentDirs()` 每票现取，并加单测钉住。
2. **faux 脚本 `callCount` 跨票累计**：faux 的 `callCount` 是 provider 级进程累计，
   `setResponses` 不重置它，第二票落到"收尾话"分支、根本不写 REPORT。改成工厂自带闭包步数 +
   每票 `armFaux()` 重装。

**第三段（同日调查修复）：三个集成 bug + 部署边界**

调查默认切 pool 后的真实可用性时抓到三个 bug，都是"单测全绿、真跑才炸"的类型：

1. **池入口路径在桌面壳下拼错**：`defaultEntryPath()` 只认「仓库根」与「ts/」两种 cwd，
   而桌面壳把服务 cwd 设在 `ts/apps/server` → 拼成 `ts/apps/server/apps/server/...`（不存在），
   **一票都起不来**。改成三种 cwd 都试（仓库根 / ts / apps/server），按文件存在性择优。
2. **`say` / `abort` 打错路由**：supervisor 打 `/say`、`/abort`，池服务端是
   `/run/:ticketId/say`、`/run/:ticketId/abort` → 404。后果是**插话与取消全部静默失效**，
   上报等待会一直挂到流超时（实测 5 分钟才以 `stream_closed` 结算）。
   修复后实测：上报 → `say(ok:true)` → 续跑 ready（~2s）；`abort` → 1.4s 结算 `aborted`。
3. **上下文窗口写死 131072**：`contextWindowOf()` 现在读 `.data/providers.json` 的
   `modelMeta[modelId].contextWindow`（三种 cwd 落点都试，读不到才回落 131072），
   并真正传给 `modelSpec`——否则小窗口模型永远压不到、最后撞 400。

**部署边界（必须知道）**：池进程入口是**源码 `.ts`**，用 `node --import tsx` 起。
- 桌面壳 / 手工 `pnpm dev`：源码态，**可用**（tsx 在 `ts/node_modules`，Node 会向上找）。
- `node dist/index.js` 单文件产物：没有 `src/pool/pool-main.ts`，**池不可用**。
  宿主启动时 `WorkerPoolSupervisor.available()` 发现入口不存在就**不注入 PoolClient**，
  `createEmployee("pool")` 回落 native 并告警——不会把单子派进一个起不来的进程。
  这也是"默认切 pool"能安全落地的前提。

**没做 / 没验（如实登记）**

- **manager 层未收进池**：默认 pool 只换 native 执行器，managed 路径仍起 manager 子进程。
- **孤儿保护是轮询**：宿主被 `taskkill /F` 强杀时，池进程最多 5 秒后自退（`ppid` 轮询）；
  Windows 上进程被带走前的那几秒仍会占着 `pool-<n>.sqlite`。
- **回收 / 崩溃重拉 / 心跳超时**只有代码路径，没逐一构造实跑（supervisor 探针只跑正常票）。
- **池内无「等待让出进程」**：方案 §3.6 那条（等上报时释放槽位给下一票）本批没实现——
  当前是"占着槽位等答复"。需要时按方案补。
- **P1 只做了最小版**：上下文页的"来源/可否修改"三列没做（要 `context-inspect` 扩字段），
  任务书样例也没做。
