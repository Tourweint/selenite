# 自动归档把「已结束的任务专线」也收进来

用户这一句是补范围：**"这个任务就是一个会话，也应该收，自动归档，对吧？这个也应该自动归档啊。"**

上一轮（同日）我按 2026-11-13 方案 §3 的口径回答"`task-` 专线不收"，用户当场否掉这个范围。

## 结论

**改成收，但只收"单已经翻不了身"的那些。** 原先 `task-` 一律不收，理由是方案里那句"`task-` 有自己的生命周期"；问题是它确实是会话——你在任务卡上点开就是一条对话，一张单一条，越派越多，堆着没人管。现在规则：

| 情况 | 收不收 | 判断依据 |
|---|---|---|
| `ticket.json` 的 status ∈ `TERMINAL_TICKET_STATUS`（done / needs_you / failed / idle / aborted） | **收** | 单已落终态，不会再有进度写进来 |
| 哪个目录都找不到 `ticket.json` | **收** | 单已不在磁盘上，不可能再动 |
| 在办 / 在等 / 跑着（status 非终态） | **不收** | 随时会有新的进度、汇报写进这条会话 |
| `ticket.json` 存在但读不出来（坏 / 没权限） | **不收** | 宁可漏收，不收在办的单 |

`chief`（总管）与 `partner-`（执事 / 群）仍然不收：前者是你的主对话，后者不是会话行、是执事专线。置顶、已归档、正在跑的照旧跳过，每轮上限 50 不变。

目录口径与任务中心、执事状态段同源：派活工作根 + 各领域 `managers/<domain>/runs/`；领域清单读不出来就只看顶层，不因一个目录坏了停掉整轮采集。

## 验证

- `npx tsx --test src/agent/auto-archive.test.ts` → **5/5 pass**；sweep 日志实测
  `扫描 62：命中 55，归档 50（上限 50，余 5 下轮继续）；跳过（非收集类 1 / 单还在办 1 / 已归档 1 / 置顶 1 / 空会话 1 / 未到期 1 / 忙 1）`
  ——「单还在办 1」正是那张 `running` 的夹具，没被收。
- `npx tsc --noEmit` → exit 0。
- `node --check web/settings-router.js`、`web/settings-switches.js` → exit 0。
- **没跑**：没对真实库手动触发一轮（真服务在跑，第二个进程开同一个 SQLite 会抢锁）。到点由调度器自己跑：
  服务重启后 5 分钟首轮、之后每小时一轮。

## 这条会怎么错

- **"单不在磁盘 → 算结束"是推断，不是事实。** 如果某张在办的单落在没被扫到的目录（新领域、`runs_dir` 元数据坏了、工作根改过），它会被当成"已结束"收进归档。兜底是归档不影响派活（`/tickets/:id/say` 与镜像写入照常），影响仅限"归档页里多一条、要手动恢复"。
- **归档 ≠ 可以删。** 永久删除的范围（2026-11-13 方案 §4）明确拒绝 `task-`，这些专线进了归档仍然删不掉。用户要的是"收起来"，本轮只做到这一步；要不要放开任务专线的永久删除是另一件事。
- **存量是一次性的，不是瓶颈。** 我原先写成"收得慢"，这条判断是错的（用户当场指出）：30 天门槛决定"每小时到期"的会话本来就只有个位数，50 条/小时永远碰不到。唯一吃上限的场景是开关**首次打开**时把历史上已经超期的存量扫一遍（50 条/小时 = 1200 条/天），几小时就到底；归档页没人盯着看，晚几小时没有任何影响。上限留着只是为了单轮别阻塞太久，不是容量问题。
- **`needs_you` 算终态。** 等你回话的单超过天数也会被收。它的会话仍能继续答（任务卡里的回话入口不受归档影响），但界面上它已经从"活跃"挪到了"归档"。
