# 2026-11-19 服务端联网工具白名单（实测、接入与端到端验证）

> 结论：`deepseek_web_search` 只在「收到请求的端点」上生效。本机七个 DeepSeek 路由里只有一个认。
> 已落成白名单 + 反例表，并**接入主流程**：命中白名单时把 function 版 `web_search` 换成服务端工具，搜索改由服务端执行，客户端不再跑一轮工具往返。开关默认关闭。

## 做了什么

**一、判定（`ts/apps/server/src/server-tool-support.ts`）**

- 判据 = `baseUrl` 的 **origin（协议 + host + 端口）精确相等**，不用 `includes`（仿冒域名会骗过字符串包含）；
- 模型名再卡一道；
- 总开关 `SERVER_WEB_SEARCH_TOOLS`，默认关闭（回滚只改一行 env）；
- `SERVER_TOOL_REJECTIONS` 记录实测不认的端点 × 模型，防止后来者照着「名字里有 deepseek」往白名单里加。

**二、接入（`ts/apps/server/src/provider.ts`）**

- `buildApi()` 包住 `openAICompletionsApi()`，在 `onPayload` 里调纯函数 `swapWebSearchTool()`；
- 选 `onPayload` 的理由：pi-ai 在 `buildParams` 之后、发请求之前会调它，这是不 fork 库就能改 `tools` 的唯一口子（`dist/api/openai-completions.js:188`）；
- 三条语义：原 tools 里没有 `web_search` 就不注入（尊重「搜索被禁用」）、非白名单一个字节不动、命中则摘掉本地那个再追加服务端那个；
- 只加 `web_search`，不加 `read_url`（最小变更）；
- 日志只打 model 与 providerId，不打 query 与响应体。

**三、测试**

`server-tool-support.test.ts` 20 条断言：白名单命中/不命中、反例表逐条拒绝、白名单与反例表不重叠、替换后长度不变且 read/bash 保留、替换不改入参、无 `web_search` 不注入、百炼原样不动、开关关闭不替换。

## 实测结果（2026-11-19，本机真实请求，非推测）

| 端点 | 模型 | HTTP | 耗时 | 是否执行搜索 |
|---|---|---|---|---|
| magpie `127.0.0.1:3425` | `deepseek/deepseek-flash` | 200 | 6s | **是**，回答引用多条实时气象来源 |
| magpie | `qwen-cn/deepseek-v4.1-flash-1017` | 200 | 3s | 否，自述「系统没有提供浏览工具」 |
| magpie | `workbuddy/deepseek-v4.1-flash` | 200 | 2s | 否，自述「我无法联网搜索」 |
| magpie | `auto/deepseek-v4.1-flash` | 200 | 3s | 否，自述「没有实时联网能力」 |
| magpie | `codearts/deepseek-v4.1-flash` | 200 | 8s | 否，自述「系统没有 web 工具列表」 |
| magpie | `trae-cn/deepseek-v4.1-flash-max` | 200 | 17s | 否，自述日期停在 2026-05-07 |
| magpie | `raccoon/sn-deepseek-v4-1-flash-1017` | 404 | 0s | 否，网关无此模型（providers.json 过期配置） |
| 百炼 `dashscope.aliyuncs.com` | `deepseek-v4.1-flash` | 400 | — | 否，`'function' is a required property - 'tools.0'` |

**七分之六是 200，但只有一个是真搜。** 静默丢弃比 400 危险：状态码正常，答案却来自旧知识。

唯一成功的那条 `deepseek/deepseek-flash` 经用户确认就是官方路由（2026-11-19）。

另一个副作用观察：非官方路由自述的「当前日期」是 2026-05-07，比真实日期晚半年——它们接的不是同一份上游快照。

## 端到端验证（`scripts/server-tools-probe.ts`，真走 `buildApi`）

三轮，都是真实请求：

| # | 系统提示 | 耗时 | 结果 |
|---|---|---|---|
| 1 | 无日期 | 12.3s | 注入生效（日志出现）、带来源链接、stopReason=stop；但把「今天」答成 7 月 |
| 2 | 无日期 | 5.3s | 仍答 2026-07-16，且引 7 月新闻 |
| 3 | 明确写「今天是 2026-11-19」 | 5.4s | **日期正确，新闻为当日** |

三条确定的事：

1. 注入发生（`[server-tools] deepseek/deepseek-flash → deepseek_web_search（magpie-local）`）；
2. 客户端**零工具调用**：SSE 里只有 `delta.content` / `delta.reasoning_content`，没有 `tool_calls`，解析器不受影响；
3. 第 1、2 轮答错日期，**不是搜索坏，是模型不知道今天**——它的 system prompt 里没有日期，就把网页里最显眼的日期当成「今天」。补上日期后立刻正确。

第 3 条对本仓是通用隐患，不只影响这条路由：目前 `src/` 里没有任何「当前日期」注入，所有模型答时间类问题都会瞎猜。

## 刻意没做

- **没加 `deepseek_read_url`**：读用户消息里的链接是另一件事，先只换搜索，少一个变量。
- **没实测官方 `api.deepseek.com`**：手上没有可用的官方 key，条目登记为 `verified: false`，不冒充已验证。
- **没确认网关的计费账号**：`deepseek/deepseek-flash` 用的是自有官方 key 还是共享池，决定它是否享受 11-18 起的「服务端搜索不单列计费」。客户端看不到，未测不写。
- **没清理 `providers.json` 里的 404 路由**：属于用户的配置，未授权不动。
- **没动 system prompt 的日期注入**：属于全局行为变更，影响所有模型，等拍板。
