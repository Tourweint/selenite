# 2026-11-04 批次二落地（审批 ask 流）

方案：`docs/设计方案/2026-11-04-批次二细化（审批ask流）.md`（第三轮审查后的施工图纸）。
范围 = 图纸 §一 契约、§二 服务端、§三 HTTP、§四 web、§五 验证、§六 文档回写。
一句话：给权限系统加一根**独立的确认轴** `confirmWrites`（默认关）；开启后写类工具执行前挂一条可答复的审批，
超时默认拒绝，可「本会话记住」。契约纯增量，手机端 Kotlin 代码零改动。

  `deadlineAt` = ISO 截止时间。解码器/编码器零改动。

    重启遗留 pending → `timeout`。
  - §4 闸门段：「默认无逐次确认」改为「默认无；`AGENT_CONFIRM_WRITES` 开启后写类工具需审批（桌面/web 专属）」。
  - §6 env 表加 `AGENT_CONFIRM_WRITES` / `AGENT_APPROVAL_TIMEOUT_S` / `AGENT_APPROVALS_PATH`。

### 2. 服务端机制

- 新建 `ts/apps/server/src/approval-policy.ts`（无副作用纯函数，不 import agent.ts）
  - `WRITE_TOOLS` 从 agent.ts 搬来这里：只读闸门与审批必须共用一份清单。
  - `needsApproval(policy, tool, blockReason?)` → `block` / `ask` / `allow`；**blockReason 优先**。
  - `denialReason(status, tool, timeoutS)`：拒绝 / 超时 / 中止三句话（只含工具名与状态，无参数内容）。
  - `approvalTimeoutSeconds(env)`：默认 120，非法值或 0 回落 120。
- 新建 `ts/apps/server/src/approvals.ts`
  - `.data/approvals.json`（`AGENT_APPROVALS_PATH` 可改）是**有意落盘**的状态文件：
    callId / 内部会话 id / 工具 / 参数摘要 / 截止时间 / 终态。**永不进日志**。
  - `create`（返回含 `promise`；同 callId 旧记录覆盖重置，旧等待方按 `aborted` 放走）、
    `decide`（幂等：已决返回原决定）、`expire` / `expireAll`、`pendingOf`、`load`。
  - `load()` 只做一次；启动时把遗留 pending 置 `timeout`（fail-closed），并清掉超过 24h 的终态记录。
  - `remember`：进程内 `Map<会话, Set<工具>>`，重启失效需重批。
- `ts/apps/server/src/agent.ts`
  - `PolicyState.confirmWrites`；`initialPolicy` 读 `AGENT_CONFIRM_WRITES`（`1` / `true`）；
    `loadPolicy` 对老 policy.json 回落 env 初值（不写死 false）；`setPolicy` 透传。
  - `openHarness()`：`approvalStore().load()` 在 `harness.resume()` **之前**。
  - `beforeTool`：判定 → bash 超时注入 → 审批等待（`Promise` + 超时定时器 + `context.abortSignal` 竞速）→
    **批准后复判** `readOnlyBlockReason()` → 走既有 `emitPhase` / `emitTool` / 切思考档 →
    **末尾唯一出口** `return injected ? {arguments: injected} : undefined`（批次一的注入不会被丢掉）。
    rejected / timeout / aborted → `{ block: 理由 }`。
  - `ChatStreamEvent` 加 `approval` 镜像；`chatStream` 的派活透传从**三元改成按 type 分发**（approval 形状不同）。
  - `stopChat()` 先 `expireAll(conversationId, "aborted")`，再 `abort()`。
- `ts/apps/server/src/delegation.ts`：`DelegationEvent` 加 `approval` 成员；模块头注明「借道传输，与派活无关」。
- `ts/apps/server/src/openai-compat.ts`：流式分支透传 `lifediary_approval`；非流式分支**忽略**（不注入正文）。
- `ts/apps/server/src/index.ts`：SSE 白名单加 `approval`；`POST /policy` 接受 `confirmWrites`（只认布尔，其余 400）；
  挂载 `mountApprovalApi`。
- 新建 `ts/apps/server/src/approval-api.ts`：GET 先 `openChat` 换内部 id 再查 pending；POST 未知 404 /

## 与图纸的偏差

1. **新增 `AGENT_APPROVALS_PATH`**（默认仍 `.data/approvals.json`）：仓库里每个状态文件都有路径覆盖，
   探针也需要隔离，否则会动开发环境的审批文件。已写进接口文档 §6 与 `.env.example`。
2. **终态记录保留 24h**：`load()` 与每次落盘时清理，避免「小状态文件」长跑后无限增长；pending 永不清。
3. **`WRITE_TOOLS` 搬到 approval-policy.ts**：只读闸门与审批判定必须共用一份，不能两处各写一份。
4. **多抽了两个纯函数**（`denialReason` / `approvalTimeoutSeconds`）：图纸只要求返回 block 理由，
   抽出来才能覆盖「拒绝/超时/中止」三态与超时解析的单测。
5. **GET approvals 未配置模型时回 503**：照 `/stop` 的口径；此时 `openChat` 恒 null，直接 404 会误导成「会话不存在」。
6. **探针「并行两个审批」用两条会话**：faux 一次响应只发一个工具调用，造不出单轮两个并行调用；
   验的仍是「A 的批准不会带起 B」。
7. **探针用「工具报错 + 耗时约 1 秒」证明超时注入**：内核把 timeout 消息放在 diagnostics，
   而 tool 事件只转发 output（既有口径，本批不改）。不为此扩契约。

## 已知风险 / 挂起点

- **手机触发的写工具会挂住一轮**：`confirmWrites` 开启时，手机没有答复通道，最坏等满 120s 后按拒绝处理。
  这是明说的边界（接口文档 §2.1/§4）。真要支持，得给手机加答复 UI 与端点调用。
- **「记住」不持久**：重启后同一工具会重新问。图纸刻意不做持久化规则。
- **审批与排队插话的交互**：等待审批期间，Web 端仍可发下一条（走 durable 排队），本轮审批不会因此取消；
  如果用户想放弃，用停止按钮（已按 aborted 结算）。
- **审批卡片不会跨刷新恢复「已决」痕迹**：GET 只回 pending，刷新后已批/已拒的卡片消失，只剩对话结果。
