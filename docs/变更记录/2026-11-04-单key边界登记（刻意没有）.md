# 登记：一个供应商只配一把 key（刻意没有）

日期：2026-11-04
类型：边界登记（不做任何代码改动）

## 缘起

刷到一条推文：很多服务可以多层授权——按项目发 key（如 Clarity，一个令牌只对应一个项目）、
按 key 限速需要轮换。设计成"一个供应商 = 一把钥匙"的工具碰到这类服务，就得回头把
单数字段改成数组。作者提醒大家设计时留好口子。

对照本项目：`ProviderEntry.keyEnv` 确实是单个变量名
（`ts/apps/server/src/provider.ts`，2026-11-04 核对），结构上正是推文说的形态。

## 处置：登记，不做

- 2026-11-04 把这条写进 `docs/基线文档/系统架构.md` §7「已知边界与风险」，
  作为**刻意没有**的边界：不预先抽象多 key。
- 变通办法（现在就能用）：同一上游登记成多个供应商条目（同 `baseUrl`、不同 `keyEnv`），
  手动切换。
- 将来要补的退路：底座 `envApiKeyAuth` 本就接受变量名数组（第一个有值的生效），
  `providers.json` 有 `schemaVersion`，`keyEnv` 升级成数组是起步即可的改动。
- 前提是单人自用、撞不上"一把钥匙不够用"的场景；场景来了再立项写方案
  （要动存储结构 + 接口文档 §2.10 + 设置页，属"必须先写方案"级别）。

## 验证

纯文档，无代码改动，无需跑探针。
