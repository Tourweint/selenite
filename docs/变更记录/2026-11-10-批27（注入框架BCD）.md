## 三、发现的重复（§5.1 要求）

**1 处，已合并**：

- `injection_guard`（【材料安全】）**注了两遍**：
  ① lifecycle `sections` 的 system 段（无身份门槛，所有会话都有）；
  ② `partner-context.buildPartnerTurnContext` 的执事轮尾巴（`guard` 字段，所有执事会话都有）。

  这是**全批唯一一处有意的内容变化**：模型仍看到同一段纪律一次，只是不再重复；
  `partner-context.test.ts` 与 `injection.test.ts` 都断言执事尾巴不再含【材料安全】、lifecycle 段仍在。

其余候选核对后**不是重复**（保留原样）：

- `verification_iron_law`：lifecycle 只注总管/无身份会话，partner-context 只注普通执事（`lifecycleOwnsVerification` / `verificationIronLawFor` 互补），同一轮不会两遍；
- persona：非 chief 执事不注 persona，SOUL 走 instructions（不在 `text` 里），不构成两份身份。

## 五、已知边界（如实写下，不写"暂不支持"）

1. **审计列不出"需要一轮真实请求"的注入**：`memory_recall` / `skill_slash` / `turn_limit` 要用户正文 / 回合数；会话静置时这几条不出现。
2. **审计跳过 `skills`**：按会话冻结属于首轮渲染的副作用，读端点不冻结索引，故不列。
3. **审计跳过 `task_memory`**：`taskMemoryBlock` 会先摄入日记镜像（写库），读端点不做写。
4. **审计不列执事「当前在办」（`partner_status`）**：要扫 chancellor `runs/` 目录 + 开 SQLite，代价与副作用都不适合读端点；契约 / 目标 / 纪律照常列。
5. **section 的异步取数顺序微调**：persona / clarify / topics 现在先取一次 `ChatKinds` 快照再由 provider 分流（改造前是分流命中后才取）。只多一次只读快照，**注入内容不变**；非 chief 执事/群会话会多这一读。
6. **去重只在一次收集内生效**：section 各自 render，跨 section 的同 id 不会互相覆盖；本批实际重复只有 `injection_guard` 一处，已按上面的方式结构性合并。
