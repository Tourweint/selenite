# 项目合并与记忆迁移（2026-11-17）

> 方案：`docs/设计方案/2026-11-17-项目合并与记忆迁移.md`
> 一句话：项目可以合并了，记忆可以搬了；删项目时记忆有明确处置，孤儿记忆不再"永久封存"。

## 改了什么

### 1. 记忆 scope 迁移（memory 包 + 新端点）

- `MemoryStore` / `MemoryEngine` 新增 `moveScope(from, to)`：`memories` 与 `memory_documents` 各一条
  `UPDATE ... SET scope`；**不动** `memory_fts`（只镜像 content / content_id，不含 scope），
  也不逐条 `put`（那会按新默认值重写缺省列）。
- 新增 `archiveScope(scope)`：写 `archived_at` 软封存（行还在，可再被 move 取走）。
- `MemoryEngine.listScopes()` 暴露给服务端（孤儿识别用；此前只有 store 层有）。
- 新端点 `POST /api/v1/agent/memory/scope/move`（`memory-scope-move.ts` 收口校验与执行）：
  形态校验 → 不能自己搬自己 → 目标项目必须已登记 → 源必须真的存在（`empty_source`）。
  **纯搬家，不去重**：重复内容交给「整理」，迁移保持零模型、可预测。

### 2. 孤儿 scope 可见

- `GET /api/v1/agent/memory/scopes` 追加 `kind:"orphan"`：`listScopes()` 的 `project:` 减去
  `listProjects(true)`；label = `已删除的项目 · <uuid 前 8 位>`（刻意不建墓碑表存项目名）。
- 孤儿仍不召回、不进每晚整理——只是可见、可整理、可迁走。

### 3. 项目合并

- `ProjectsStore.mergeInto(source, target)`：源的文件夹全调到目标名下（降 `extra`、label 重名加序号、
  同路径跳过、互相包含 409），当前项目指针改指目标，删源行；**单库事务**。
- `PartnersStore.reparentProject(source, target)`：挂载从源换到目标（JSON 数组读出改再写回，去重）。
- `rebindChatsOfProject`（session-index）：durable `ChatProjects.byInternal` 里值等于源的改成目标。
- 新端点 `POST /api/v1/projects/:id/merge {into}`：会话改绑 → 记忆搬迁 → 挂载改挂 → 登记合并。
  守卫：都存在 / 不是同一个 / 目标未归档（`409 target_archived`）/ 源无非终态派单
  （`400 project_in_flight`，与删除同口径）。
- **跨三库（projects.sqlite / memory.db / durable）没有原子事务**：顺序"先搬后删"，前三步幂等，
  失败可重调补齐；响应分项回报 `rootsMoved / rootsSkipped / chatsRebound / partnersReparented / memory`。

### 4. 删项目时记忆三选一

- `DELETE /api/v1/projects/:id?memory=keep|archive|move&into=<scope>`：缺省 `keep`（逐字节兼容旧行为：
  记忆留成孤儿）；`archive` 软封存；`move` 先搬后删（`into` 校验同迁移端点）。
- 响应增加 `memory:{action, records, documents}`。

### 5. 前端

- 记忆页：孤儿 tab（徽章「已删除」）+ 顶部「迁移」钮（只在项目 scope 显示，含孤儿）→ 弹窗选
  目标（我的记忆 / 其他项目）→ `POST /memory/scope/move`，成功后切到目标范围。
- 项目页 ⋯ 菜单新增「合并到另一个项目」（弹窗选目标，说明跨库非原子、可重试）。
- 删除登记弹窗新增「这个项目的记忆」三选一（默认保留）；选「迁移」才出现目标选择器并去读项目清单。

### 6. 回滚开关

| env | 关掉后 |
|---|---|
| `MEMORY_SCOPE_MOVE=false` | 迁移端点 404、删项目 `memory=move` 400、记忆页不渲染「迁移」；孤儿清单与 `keep/archive` 不受影响 |
| `PROJECT_MERGE=false` | 合并端点 404、项目卡菜单不渲染「合并到另一个项目」 |

## 为什么这么做

- **问题实证（2026-11-17 核查）**：`deleteProject` 只删 projects / project_roots 两行，记忆一条不删
  （`types.ts` 原注：「项目移除后 scope 成孤儿——不可见即无害」）。实测那批记忆**永久不可见、不可召回**，
  而且全仓没有任何改 scope 的代码路径——不是"暂时看不见"，是"永远搬不回来"。
- **合并功能此前不存在**（grep `mergeProject` / `合并项目` 零命中），用户要合并只能手工建新项目、旧记忆各留各的。
- **迁移不去重**：去重是「整理」的职责（模型出建议、人逐条点应用）；迁移如果顺手合并，等于一次 API 调用
  悄悄改动记忆语义。这是刻意的分工。
- **孤儿 label 只给 uuid 前缀**：项目行已删，名字无处可取；为一个展示名加一张墓碑表不划算。
- **合并顺序"先搬后删"**：2–5 步都是"搬"，第 6 步才是"销毁登记"；任何一步失败都停在破坏性动作之前。

## 不确定 / 没验的

- **项目合并端点本身没有单测**（`POST /projects/:id/merge` 要真起 harness 才能测会话改绑）；
  其四个组成件（root 合并、挂载改挂、记忆搬迁、durable 改绑）分别有测试，但"装配起来一次跑通"
  没验。建议实机跑一次小项目合并看 `chatsRebound` 与响应分项。
- 前端只过了 `node --check`，没有浏览器联调（孤儿 tab 渲染、迁移弹窗、合并菜单、删除三选一的下拉联动）。
- 跨库部分完成时的提示只是"再点一次可补齐"，没有实测中断场景。
