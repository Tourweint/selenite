# 2026-11-07 对话设置抽屉二次修（黑圈根因 · 人设/模型双入口 · 备选链共用编辑器）

## 为什么

上一版（b70631a、a8a7043）把右上角设置从下弹面板换成右侧抽屉，但用户验收后仍判定
"做得还是非常差"，并逐条点名：

1. **外面带一个黑圈是啥东西**——右上角入口按钮外圈有一道黑环；
2. **选模型应该跟设置里那个是一个方法**——设置页是下拉选，抽屉里却是另一套菜单；
3. **调整人设要加到右上角这里**，换头像也在这里（"其实无所谓，但是也可以换"）；
4. **调人设的页面，和打开一个人后点右上角那个设置页面，这两个应该差不多，都可以用 EP（API）接口**。

即：入口的视觉脏、抽屉与设置页各写一套、人设入口缺失。

## 判定

免写方案类（AGENTS.md）：视觉与信息架构重排 + 复用既有端点，不动契约、不动存储、无新 env。
新提交的字段全部来自既有 `GET/PATCH /api/v1/partners/:id`、`GET/POST /api/v1/agent/model`、
`GET /api/v1/agent/providers`，**没有新增任何端点**。

## 根因（不是猜的，是量出来的）

黑圈：`.top-gear` / `.cs-icon-btn` / `#group-settings-btn` 只写了 `background/color`，
**从未重置 UA 的 `border`**。实测 `getComputedStyle` 返回 `2px outset rgb(0,0,0)`——
`outset` 在圆角按钮上渲染成上亮下暗的立体环，就是用户看到的"黑圈"。
全站审计（设置页/群组/人设弹窗/头像浮层）只有这三处中招，因为其它按钮都显式给了 `border`。

排版：`.cs-row-title` / `.cs-row-sub` 都是 `span`（默认 `inline`），
所以"模型 / magpie 本地网关 · auto/glm-5.3-flash"挤在同一行；`.cs-row` 也无边框分隔，
四行贴边排，看起来像一份没排版的清单。

## 改了什么

### 1. 黑圈（根因修 + 就地兜底）

- `style.css`：`button` 全局补 `border: 0`（现有按钮都已显式给边框，不受影响）；
  `.top-gear`、`.cs-icon-btn` 再各写一次 `border: 0`，单独改这两处也不会再生圈。
- 入口按钮补 `[aria-expanded="true"]` 与 `:focus-visible` 态，展开/聚焦不再靠"画圈"表达。

### 2. 抽屉重排（卡片化）

- `.cs-body` 基础样式保持原样（群设置抽屉共用），新增 `.cs-body[data-cards]`：
  14px 边距 + 14px 卡间距 + 纵向排列；对话设置的五个页面打 `data-cards`，
  群设置不打包（仍是 `block`，1px 分隔线不受影响——已实测 `display:block / gap:normal`）。
- 新增 `.cs-card`（`--card` 底 + 16px 圆角 + 行间 1px 分割）与 `.cs-card-label`（分组小标题，
  下面不画线）；`.cs-row` 改 52px 行高、标题/副文本各占一块、`value` 槽、focus 环。
- 抽屉左缘补一道极浅投影（`-18px 0 40px -28px`），让"板"与聊天区不再糊成一片。

### 3. 首页信息架构：单卡 → 分层

`身份行（人设入口）` / `这个角色`（人设）/ `模型`（主选 + 备选）/ `助手`（权限档 + 通知）/ `更多`（全部设置）。
身份块从"居中大头像 + 三行灰字"改成**横排一行**（头像 40px + 名字 + `人设 vN · 点头像或名字改` + chevron），
与下面的设置行同节奏——原来那版占了 1/5 屏高，像个人主页而不是设置面板。

### 4. 人设页（新增 `csPage = "persona"`）

与「全部设置 → 人设 → 改人设」**同一批接口**：

- `GET /api/v1/partners/:id` 读 `soul` / `soulVersion` / `modelChain`；
- `PATCH /api/v1/partners/:id` 把**头像 + 名字 + 正文放在同一个请求**里提交
  （服务端本来就支持多槽位且先整体校验，任一不合法整批 400，不会半写）；
- 头像是人设的一部分：头像按钮就在页内，点开共用面板（预设 30 张 / 本地选图 / 不使用），
  选中只进本地草稿，点「保存」才落库。
- 版本说明挂在名字框下方，不再单独挂在卡片尾部当脚注。

### 5. 模型页：主选与备选「一个方法」

- **主选**：`select` 分组下拉（`<optgroup>` = 供应商），与设置页「默认模型」同一个
  `POST /api/v1/agent/model`，切完就地刷新，下一轮生效。
- **备选**：执事的候选链（`PATCH /partners/:id { modelChain }`），
  每行也是**一个分组下拉**（供应商/模型合一）+ 序号 + 上移/下移/删除 + 「加一条备选」。
  `keyEnv` 不再手填——由供应商记录带出（手填只会让人把密钥值写进去，正是契约反复拦的那件事）。
- 原来"批量添加模型"保留在页尾；导入成功后**自动重拉目录**，新模型立刻能选
  （`importBatchModels` 现在返回布尔，调用方据此刷新）。

### 6. 设置弹窗里那套「手打候选链」删掉了

`ptParseChain` / `ptSaveChain` 与 `providerId|modelId|KEY_ENV_NAME` 文本框整套移除，
改成调用 `mountChainEditor()` —— 与抽屉**同一份实现**。用户那句"这两个应该差不多"由此落实为
"同一段代码"，不是"长得像的两段代码"。

### 7. 身份判定按聊天种类分流（避免谎报）

`csResolveTarget()` 原来把所有非 `partner-` 会话都当总管。现在：

| 会话 | 结果 |
|---|---|
| `partner-<id>` / `partner-<id>-group-<gid>` | 该执事 |
| `chatKind=chief` | `chief`（总管就是主对话的身份） |
| `chatKind=worker` | `null` —— 不摆身份块、不摆人设行、不摆备选行/卡 |

worker 的人格是服务端的 `WORKER_PERSONA`，不是某个执事；给它一个人设入口等于让用户
"改了总管却以为改了当前助手"。人设页对 worker 直接说明原因并指向全部设置。

## 事实校正（写进文案之前核过代码）

**备选链只在执事的试跑与例行任务轮次里生效**（`partner-runtime.runPartnerTurn` →
`nextChainCandidate`）；主对话走 `chatStream`，**不读链**。
所以文案写的是"只在试跑与例行任务轮次里生效（主对话不换）"，
而不是"主模型失败就自动换"——后者是虚假承诺。

## 明确不做

- 不做"每个对话独立的模型"：主选仍是全局运行时模型（既有语义不变）。
- 不给 worker 会话造人设：它的身份在服务端，前端不提供假入口。
- 不在抽屉里重做供应商增删改：仍走「全部设置 → 服务」，抽屉只做"从已有里选"。
- 群设置抽屉的排版不动（共用骨架，只把 `data-cards` 限定给对话设置）。
