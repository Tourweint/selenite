# 2026-11-23 Codex 元数据提示误判修复

## 问题

Codex 派活「正常干完」被判失败（2026-11-23 实测，本机 codex-cli 0.163.0 + magpie 网关）。

成功回合的 `--json` 输出里会先出现一条 `item.completed` + `item.type=error` 的**元数据提示**：

```json
{"type":"item.completed","item":{"id":"item_0","type":"error","message":"Configured service tier `priority` is not advertised as supported for model `auto/glm-5.3-flash` and will be omitted from requests."}}
```

旧 `parseCodexStdout` 把任何 `item.type=error` 直接记成 failure，整单 `ok=false`；
事件采集本身正常（`parseCodexStepLine` 早已不把它算工具失败），只有终态判定错了。

## 实测证据（2026-11-23，临时目录，未入库）

命令形状（magpie env + 本机 `~/.codex/config.toml` 已指向 magpie）：

```bash
NO_PROXY=127.0.0.1,localhost codex exec --json --skip-git-repo-check \
  -m auto/glm-5.3-flash -s read-only -c 'approval_policy="never"' \
  "读取当前目录的 sample.txt，只回答其中的魔法词。" < /dev/null
```

### 正常成功（退出码 0，8 行 JSON）

```text
thread.started
item.completed  item.type=error  "Configured service tier `priority` is not advertised as supported for model `auto/glm-5.3-flash` and will be omitted from requests."
turn.started
item.completed  item.type=reasoning
item.started    item.type=command_execution
item.completed  item.type=command_execution  exit_code=0
item.completed  item.type=agent_message      "BLUE-OTTER-42"
turn.completed  usage={...}
```

### 真失败：模型不存在（退出码 1）

```text
thread.started
item.completed  item.type=error  "Configured service tier `priority` is not advertised ... auto/model-does-not-exist-xyz ..."
item.completed  item.type=error  "Model metadata for `auto/model-does-not-exist-xyz` not found. Defaulting to fallback metadata; ..."
turn.started
error           "Reconnecting... 1/5 (unexpected status 404 Not Found: magpie no longer serves \"group/auto-model-does-not-exist-xyz\" ...)"   ×5 次重试
error           "unexpected status 404 Not Found: magpie no longer serves ..."
turn.failed     "unexpected status 404 Not Found: magpie no longer serves ..."
```

### 关键差异

| 维度 | 正常成功 | 真失败（模型不存在） |
|---|---|---|
| `turn.completed` | 有 | 无 |
| `turn.failed` | 无 | **有** |
| 退出码 | 0 | 1 |
| `item.type=error` 文案 | service tier / priority 元数据降级 | 元数据提示 + `no longer serves` 的 404（同时伴随顶层 `error` 与 `turn.failed`） |
| 顶层 `error` | 无 | 有（重试 5 次 + 终态） |

结论：元数据提示与真失败在「有没有 `turn.completed` / `turn.failed` / 非零退出码」上可区分；
真失败的 item error 文案本身也会带模型不可用特征。

## 改法

文件：`ts/packages/chancellor/src/employee/codex.ts`（`parseCodexStdout`，仅这一处判定；流式事件、权限、isolation、调度、验收未动）。

判定改为两层，不做「忽略所有 error」的一刀切：

1. **硬失败**（保持原样）：`turn.failed`、退出码非 0、没有任何 JSON 事件、
   `既无 turn.completed 又无 agent_message`。
2. **软错误**：顶层 `error` / `stream/error`、`item.type=error` 先收进列表，不立即判死：
   - 有 `turn.completed` → 默认不推翻成功；
   - message 命中致命特征（模型不存在 / 不再提供、认证失败、网络失败等，
     `FATAL_CODEX_ERROR_PATTERNS`）→ 即使有 `turn.completed` 也判失败；
   - 没有 `turn.completed` → 软错误判失败（错误文案优先回报它）。

选关键词表而不是「service tier 白名单」：网关的元数据提示文案会变，白名单会漏；
反过来漏判真错误代价更大。关键词只收「这一单肯定没干成」的特征，**刻意不收 `rate limit`**：
限流可能被 Codex 自动重试后成功，而真正的限流失败会同时给 `turn.failed` / 非零退出码。

## 边界 / 不确定

- **软错误 + 有 `turn.completed` 的判定依赖关键词表**：如果上游出现全新措辞的致命错误、
  同时又错误地发了 `turn.completed`，仍可能漏判；当前实测的真失败一定带 `turn.failed` + 非零退出码，所以影响面有限。
- **认证失败 / 断网未实测**：本机 magpie 正常、Codex 已配置，无法在不破坏环境的前提下制造；
  关键词表覆盖了常见文案（401/403、invalid api key、ECONNREFUSED/ETIMEDOUT 等），但未真机验证。
- **`Model metadata ... not found. Defaulting to fallback metadata` 当警告**：它可能只是元数据缺失、
  模型仍可用，因此不列入致命特征；若某次它确实是失败前兆，仍会由随后的 `turn.failed` / 非零退出码兜住。
- `parseCodexStepLine` 的「item error 不算工具失败」口径不变，未做额外修改。
