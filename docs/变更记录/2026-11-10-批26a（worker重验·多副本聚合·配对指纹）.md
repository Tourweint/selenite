## 一、手机 worker：执行前重验（`PHONE_ENSURE_ACTIVE`，默认开）

"执行"在手机上，服务端能守住的是**交付**与**收结果**两个时刻，代码只改了这两处：

- **交付前**（`nextQueuedTask`）：排队中的单逐张判 `inactiveReason`（`signal.aborted` → canceled；
  `now >= deadlineAt` → expired），失效的**跳过不交**；同一 `taskId` 被重派过时，认领一次即清掉
  队列里其余重复项，绝不重复发。
- **收结果前**（`POST /worker/result`）：登记已不在但墓碑在 → `200 {ok, applied:false, reason:"canceled"}`；
  登记还在但已失效（计时器被事件循环拖延）→ 同样 `applied:false`，**不 resolve、不写回**。
  日志只记单号与原因，不记 summary。
- **取消墓碑**：abort 时记 `taskId → 时间`，内存保留 10 分钟、上限 200 条；仅用于把"迟到结果"
  判成"已丢弃"而不是"未知单"。`PHONE_ENSURE_ACTIVE=false` 两者都不做，回到本批前（迟到结果 404）。
- **顺带修掉一个连坐 bug**：同 `taskId` 重派时，旧单的超时收尾原本会删掉新单的登记与队列位，
  使新单永远交付不出去。`finish` 现在只在 `pending.get(id) === 自己` 时才清理；单测钉死。
- 单测（`phone-worker.test.ts`，8 条）：判定口径 / 开关解析 / 取消后不发出 / 超时后不发出 /
  已认领不重复发 / 取消后结果被丢弃（`applied:false`）/ 开关旁路 404 / 同 id 重派不连坐。

**已知边界（如实登记）**：手机拿到单之后、真正开始执行之前那一段在手机侧，服务端无法代查；
本批**不新增 preflight 端点**、不改手机端契约。取消只有发生在交付窗口内才保证"不产生副作用"。
另外，"取消后不发出"两条端到端用例在旧代码上也能过（原来的 abort 监听本就会清队列），
新代码真正新增的是**过期判定早于计时器**与**迟到结果的显式丢弃**，这两点分别由
`inactiveReason` 纯函数用例与 `applied:false` 用例钉住。

## 二、多副本聚合端点（`DELEGATION_FANOUT_GROUP`，沿用批 19）

新增 `GET /api/v1/tickets/groups/:groupId`（只读）：

- 扫顶层 `workRoot/` 与各领域 `runs/` 的 `ticket.json`，按 `idempotencyKey === groupId` 数
  `total / done / pending`；`status = settled` **仅当全部终态**（终态表同任务中心，
  **作废位也算终态**——harness 不再搬它的结果）。`total = 0` → `404 not_found`。
- 开关关着 → 同样 404（组这个概念不存在）。**不自动消费、不改任何单**。
- **人的消息不等**：主人回话走 `POST /tickets/:id/say`（单线），不进组、不影响 settled；
  这层语义写进了路由注释与接口文档，代码没改。
- 单测（`delegation-api.test.ts` 新增 1 条）：跨目录 2 副本 1 终态 → `pending(2/1/1)`；
  全终态组 → `settled(2/2/0)`；未知组 404；开关关 404。
- 同库的 `idempotency_key` 有唯一约束，所以"同组两张"必须分目录落——探针第一次写夹具时
  撞了这个约束才发现，已在探针注释里写清。

## 四、配对设备指纹 + 键变更 fail-closed（`PAIR_DEVICE_FINGERPRINT`，默认开）

- **指纹**：`sha256("lifediary-device-v1|<deviceId>|<tokenHash>")` 前 12 位十六进制，
  按 `XXXX-XXXX-XXXX` 分组。只用于**人眼核对**（电脑设备面板 / 手机端逐字符比对），
  48 bit 不可反推令牌，**不当凭据**。
- `POST /pair/redeem` 增 `deviceId` / `fingerprint`（纯增量）；`GET /pair/devices` 每台带
  `fingerprint`（开关关着时不出现）。`/pair?token=…` 设备面板显示指纹，`keyChanged` 显示
  「⚠ 凭据已变更，已停用」，撤销按钮文案改成「撤销（需重配）」。
- **键变更 fail-closed**：加载配对库时逐台复算指纹——
  - 老记录没有指纹 → **补算写入**（一次性迁移，不算键变更）；
  - 有指纹但对不上（文件被改 / 从别的机器搬来）→ 标 `keyChangedAt`，`verifyDeviceToken`
    **一律拒绝**，直到撤销 / 重配。标记持久化，重启不消失。**不静默按新键认**。
- `PairingStore` 构造可传路径（默认仍是 `PAIRING_STORE_PATH` / `.data/pairing.json`），
  仅为单测隔离；生产行为不变。落盘失败只 warn（与 `load` 同口径），不让服务起不来。
- 单测（`pairing.test.ts`，4 条）：格式与可复算 / 清单不含哈希 / 键变更标记 + 旧凭据失效 +
  重配可用 / 老记录迁移不误判 / 开关关掉不生成也不判。

## 已知边界 / 没做

- **两段式配对（扫码 + 电脑端输码双确认）没做**：#26 的"两段式"那半需要手机端一起改
  （手机绝不代确认），本批只落了服务端能独立交付的"指纹呈现 + 键变更 fail-closed"。
  台账里 #26 仍应记为**半条**。
- **指纹不是安全边界**：它证明"两台屏幕上是同一台"，不证明"拿手机的人是主人"；
  鉴权仍只认 deviceToken 的 sha256。
- **键变更判定的触发面**：只覆盖"文件里的键与指纹对不上"。正常路径没有换键 API，
  所以不会误报；将来若加换键 / 迁移功能，必须同时更新指纹，否则会被判成 fail-closed。
- **聚合端点每次全量读 `ticket.json`**（每库上限 500 张），不做缓存与索引；
  单很多时会慢，真到那时再加"按 idempotency_key 建索引"的迁移。
- 取消墓碑只在内存：服务重启后，重启前取消的单其迟到结果会回到 `404 unknown_task`
  （结果同样不写回，只是回执语义退化）。
